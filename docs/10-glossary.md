Словарь терминов проекта.

## ETN

База знаний по проекту **ETN** — self-hosted «цифровому мозгу». Единый источник знаний для агентов, работающих над проектом, и для человека, который управляет разработкой.

Это точка входа. Дальше — обязательные первые шаги, модель базы, протокол чтения и карта разделов.

### С чего начать (обязательно)

1. **Прочитай правила ведения** — поле `conventions` сети (приходит одним вызовом `etn.networks.structure`): протокол поиска, обязательность инструкций, правила записи, связей и отчётов. Соблюдай строго — здесь правила не дублируются.
2. **Найди инструкцию по своей ситуации** — `etn.instructions { keywords: <слова ситуации> }` (витрина: перечень / keywords / полный текст по id) или `etn.thoughts.query { type: ["инструкция"], keywords: <слова ситуации> }`. Нашёл — выполняй строго; не нашёл — сообщи пользователю и предложи создать инструкцию (см. «Создать или актуализировать инструкцию для агентов»); процедуру не импровизируй.

### Модель: сеть, а не каталоги

Мысль может иметь несколько родителей и связей; разделы — не адреса обязательного хранения. Ошибка может лежать под версией, задача — под компонентом, термин — внутри задачи. Поэтому:

- **ищешь конкретное — запросом**, а не просмотром разделов;
- **не знаешь, что вообще есть — обозревай разделы** итеративно;
- **записываешь новое — пройди самопроверку** (два вопроса, см. `conventions`).

### Протокол чтения

#### Знаешь, что ищешь — запрос

- `etn.thoughts.query { keywords, type: [<имя типа>] }` — отбор по словам и типу (тип адресуется именем или `type_id[]` после `etn.types.list`). Добавляй `in_subtree_of`, когда нужно найти что-то **внутри конкретной структуры** — в фазе, в пользовательской документации, в спецификациях; если место не важно — родителя не указывай.
- Свойства — тоже фильтр: `properties: [{ key: "Статус", operator: "eq", value: "согласовано" }]`.
- `etn.thoughts.search` — полнотекстовый поиск (названия, тексты, хроника).
- Поиск без стемминга: «дублей» не найдёт «дубля». Пробуй словоформы и `*` (`дубл*`); если мысль могла быть уже закрыта — повтори с `active: "any"`.
- Нашёл кандидатов — `etn.thoughts.subgraph { seed_ids, radius: 1, include_comments: true, max_chars: 8000 }`: содержимое и окружение одним вызовом. Обрезанный комментарий дочитывай `etn.comments.get` по его `id`.

Пример: «ошибка поиска дублей, запланированная на версию X» → `query { keywords: "дубл*", type: ["ошибка"], properties: [{ key: "версия", operator: "eq", value: "<id версии X>" }] }`. Проматывать раздел «Ошибки проекта» не нужно: ошибка может лежать и не в нём.

**Осторожно с `in_subtree_of`:** типизированные связи вроде «зависит от» — тоже направленные рёбра, поэтому обход поддерева притягивает и то, от чего зависит его содержимое. Для точных списков используй фильтры по свойствам и типу.

#### Не знаешь, что есть — обзор раздела

Вопросы вида «какие компоненты есть?», «из чего состоит этот модуль?», «как устроена документация?». Итеративно:

1. Открой ключевой раздел по карте ниже: `etn.thoughts.query { in_subtree_of: <id>, max_depth: 1 }`.
2. Выбери релевантные подразделы и спускайся глубже тем же запросом.
3. Ориентируйся на счётчики `meta` (`children_count`, `chrono_count`, `deletion_blocks`), решая, что дочитывать.

### /activity — лента, свёртка и обрезка журнала активности

Чтение и обслуживание журнала активности.

```
GET  /api/v1/networks/{nid}/activity
     ?from_ms&to_ms&user_id&entity_type&entity_id&limit&offset
     → 200 { data: [ { id, user_id, user_name, action, entity_type,
                       entity_id, entity_title, layer_id, occurred_at_ms } ] }
POST /api/v1/networks/{nid}/activity/rollup   { until_ms }  → 200 { removed, kept }
POST /api/v1/networks/{nid}/activity/truncate  { until_ms }  → 200 { removed }
```

- фильтры комбинируются (период × пользователь × сущность); сортировка по `occurred_at_ms` убыв.; пагинация `limit`/`offset`;
- `rollup`/`truncate` необратимы; сервер возвращает счётчики удалённых/оставшихся записей;
- запись журнала отдельной операцией не редактируется (append-only).

---

**Термины (глоссарий 10).** **Свёртка** (`rollup`) — агрегация повторяющихся событий журнала в одну запись со счётчиком за окно времени. **Обрезка** (`truncate`) — ретенция старых записей журнала по порогу. Авто-свёртка журнала выполняется при слиянии или удалении слоя.

<a id="pub-14ad55d1"></a>

### /networks/{id}/preferences — серверные предпочтения пользователя в сети

Настройки уровня «пользователь × мыслесеть», хранимые на сервере и общие для всех устройств пользователя.

```
GET /api/v1/networks/{id}/preferences         # все ключи
PUT /api/v1/networks/{id}/preferences/{key}   { value: <json> }
```

Поддержанный ключ — `show_inactive` (показывать ли неактуальные мысли и связи). Значение служит умолчанием для фокуса, поиска, отборов и списков связей, если запрос не передал `show_inactive` явно.

Не путать с клиентским состоянием (геометрия окон, последний фокус): то живёт локально и на сервер не ездит.

**Второй ключ видимости — `show_trash`** (задача 77923b49, коммит e55e5c6, 0.8.2): показывать ли помеченные на удаление мысли и связи. Дефолт — `true` (поведение после 355319d4 не меняется); `false` прячет помеченное в фокусе и соседях, рёбрах, иерархии и списке связей мысли. Флаг резолвит сервер (`resolveShowTrash`), явный параметр запроса сильнее настройки. Поддержанные ключи: `show_inactive`, `show_trash`, `canvas_link_filter`.

---

**Термин (глоссарий 10).** **Серверные предпочтения** (`user_preferences`) — пользовательские настройки в сети, хранимые на сервере (например `show_inactive`), в отличие от локальных UI-state, которые остаются на клиенте.

### activity_log — журнал активности сети

Таблица БД сети — неизменяемый журнал «кто что сделал» для рабочего стола «События». Append-only: записи создаются, но никогда не правятся. Источник — НЕ `event_log` (тот — буфер синхронизации с окном удержания).

| Столбец | Тип | Описание |
|---|---|---|
| `id` | INTEGER PK | автоинкремент |
| `user_id` | TEXT NOT NULL | автор действия |
| `action` | TEXT NOT NULL | `created` / `updated` / `deleted` / `trashed` / `restored` |
| `entity_type` | TEXT NOT NULL | `thought` / `link` / `thought_type` / `link_type` / `property` / `comment` / `attachment` / `layer` |
| `entity_id` | TEXT NOT NULL | логический id сущности |
| `entity_title` | TEXT NOT NULL | краткий снимок описания («мысль без типа, "Название"»); лимит 256 символов, излишек обрезается — ссылок на удалённые сущности нет |
| `layer_id` | TEXT NULL | слой, в котором произошло событие |
| `occurred_at_ms` | INTEGER NOT NULL | время события, миллисекунды |

Индексы: `(occurred_at_ms)`, `(user_id, occurred_at_ms)`, `(entity_type, entity_id, occurred_at_ms)` — под три оси ленты.

**Ветвимость:** ветвимая таблица — события слоя пишутся в слое со своим `layer_id`; при слиянии и удалении слоя обрабатывается свёрткой (см. требование об авто-свёртке).

**Чего здесь нет.** Событий захвата (`edit.*`) и per-user состояния — журнал хранит только историю изменений сущностей сети.

---

**Термин (глоссарий 10).** **Журнал активности** (`activity_log`) — лента мутирующих операций сети (создание/правка/удаление мыслей, связей, типов, комментариев, вложений, слоёв); поддерживает свёртку и обрезку.

<a id="pub-cb8a1fd8"></a>

### ADR: авторство — служебные колонки таблиц, не свойства реестра

#### Контекст

Авторство можно хранить как значения свойств реестра — но свойства типизированы, привязаны к владельцу-типу и выборочны; автор нужен ЛЮБОЙ сущности всегда, включая сами типы и свойства.

#### Решение

`created_by`/`updated_by`/`created_at_ms`/`updated_at_ms` — служебные колонки таблиц сущностей (мысли, связи, типы, свойства, слои, комментарии, вложения), заполняются сервером при каждой записи; отображение — до секунды, хранение — миллисекунды.

#### Следствия

Отборы «Автор»/«Редактор» — серверные фильтры по колонкам, не зависят от реестра свойств. Типы и свойства — сущности первого класса с тем же авторством.

#### Что нельзя

Заводить авторство значениями свойств; доверять заполнение авторства клиенту.

---

**Термины (глоссарий 10).** **Автор** (`created_by`) — пользователь, создавший сущность; заполняется при создании и не меняется. **Редактор** (`updated_by`) — пользователь, последним изменивший сущность; обновляется при каждой записи. У объектов старше 0.7.1 — первый пользователь сервера.

<a id="pub-705fb6d3"></a>

### ADR: захват объекта — мягкая серверная блокировка записи

#### Контекст

Два участника правят один объект — результат непредсказуем. Уведомление о конфликте приходит постфактум. Варианты: CRDT/автослияние, блокировка записи на время редактирования.

#### Решение

Мягкий серверный захват: клиент сигнализирует начало/конец редактирования, сервер хранит активные захваты (`object_locks`) и отклоняет чужие операции записи; чтение не блокируется. Сбор автоматический: старт сервера, разрыв WebSocket; ручной — командой «Снять все блокировки».

#### Следствия

Захват предотвращает конфликт, а не разрешает: отказ в записи с понятной ошибкой. Захват — текущее состояние, в историю не пишется. Все равноправны: захватить и снять может любой участник.

#### Что нельзя

Автослияние правок или версионность полей ради «одновременного» редактирования; блокировка чтения.

---

**Термин (глоссарий 10).** **Захват** (`object_locks`) — мягкая серверная блокировка объекта на время редактирования; чужой захват показывается индикацией, снимается по завершении правки или командой «Снять все блокировки».

### API-key

Статичный bearer-токен `etn_<32 hex>`. Хранится на сервере только SHA-256 хешем; сам ключ восстановить нельзя. Полный ключ возвращается ровно один раз при создании.

<a id="pub-f009d46e"></a>

### comments — постоянные и хронологические комментарии

Комментарии мыслей и связей. **Ветвимая** таблица.

| Столбец | Тип | Описание |
|---|---|---|
| `pk` | INTEGER PK AUTOINCREMENT | Суррогат |
| `id` | TEXT NOT NULL | Логический UUID |
| `layer_id` / `deleted` / `base_version` | | Слой-колонки |
| `owner_type` | TEXT NOT NULL | `'thought'` или `'link'` |
| `owner_id` | TEXT NOT NULL | Логический id владельца |
| `kind` | TEXT NOT NULL | `'permanent'` или `'chronological'` |
| `title` | TEXT | Заголовок (для хронологических) |
| `body_md` | TEXT NOT NULL | Исходный markdown |
| `body_html` | TEXT NOT NULL | Предрендеренный HTML (кеш) |
| `valid_from` | TEXT NOT NULL | Начало; у постоянного равна дате создания; у хронологического — полный UTC-инстанс ISO-8601 с мс |
| `valid_to` | TEXT | Окончание. У постоянного всегда `NULL`. У хронологического `NOT NULL`: не заполнено = равно `valid_from` |
| `use_time` | INTEGER NOT NULL DEFAULT 0 (bool) | Флаг «учитывать время»: показ и правка времени в клиенте; на формат `valid_from`/`valid_to` не влияет |
| `version` / `created_at` / `updated_at` / `created_by` / `updated_by` | | |

Индексы: по владельцу, по владельцу с датой начала (хроника), по слою; частичный **уникальный** по владельцу и слою для постоянных — он и есть гарантия «один постоянный комментарий на владельца в пределах слоя».

**Два вида комментариев решают разные задачи.** Постоянный — суть владельца, верная всегда; хронологический — датированная запись о событии или периоде.

**Предрендер.** HTML хранится рядом с markdown и обновляется при записи — клиенту не нужно рендерить текст при каждом показе. Отсюда требование: рендерить обязан общий markdown-рендерер, иначе кэш разойдётся с тем, что показывает клиент.

**Отдельного хранения Markdown-AST нет** и не планируется: пары «markdown + HTML» достаточно.

#### Время в датах (0.10.1)

`valid_from`/`valid_to` хронологической записи — всегда полный UTC-инстанс ISO-8601 с миллисекундами; date-only не хранится. Сервер не придаёт датам смысла «календарного дня» и не конвертирует часовые пояса. `valid_to` у хронологической обязателен (незаполненное = `valid_from`), у постоянного остаётся `NULL`. Флаг `use_time` хранится на записи и управляет только отображением/правкой времени в клиенте. «Голая дата» во входных параметрах = сутки UTC. Правила — требования «Формат дат хроно-записи», «Флаг «учитывать время»», «Миграция дат хроники», «Голая дата во входных параметрах API» и ADR времени.

#### Модель 0.8.1: у рёбер остаётся только постоянный комментарий

Хронологические комментарии у связей (`owner_type: "link"`) упраздняются; постоянный комментарий ребра сохраняется и трактуется как комментарий к значению свойства-связи. Хроника остаётся у мыслей.

---

**Термин (глоссарий 10).** **Комментарий** — markdown-описание мысли или связи (`comments`). Виды: постоянный (`kind=permanent`, один на владельца, без даты) и хронологический (`kind=chronological`, с `valid_from`/`valid_to`).

### deletion-check — проверка возможности удаления мысли или связи

Предварительная проверка: можно ли физически удалить запись и что именно мешает.

```
GET  /api/v1/networks/{nid}/thoughts/{id}/deletion-check
→ 200 { data: { blocked: boolean,
                blocking: { properties: <число ссылающихся мыслей>,
                            layers: [ { id, title } ] },
                orphaned_children: <число> } }

POST /api/v1/networks/{nid}/thoughts/deletion-check-batch   { ids: […] }
→ 200 { data: { "<id>": { blocked, blocking, orphaned_children }, … } }

GET  /api/v1/networks/{nid}/links/{id}/deletion-check
POST /api/v1/networks/{nid}/links/deletion-check-batch
→ 200 { data: { blocked, blocking: { layers: [ { id, title } ] } } }
```

У связи тот же формат без `properties` и `orphaned_children`: на связь не ссылаются свойства и у неё нет детей.

**Проверка контекстно-зависима**: в рабочем слое собственные теневые строки текущего слоя удержанием не считаются, а живая строка основы попадает в `blocking.layers` элементом `{ id: <id основы>, title: «Основа» }`: «удалить совсем» такую строку в слое нельзя (получилось бы лишь надгробие), разрешена только пометка на удаление.

Batch-вариант — источник данных для диалога группового удаления и диалога «Корзина»: один запрос вместо N.

---

**Термин (глоссарий 10).** **Удерживающие ссылки** (`holding_layers`) — входящие формальные ссылки, мешающие удалить мысль: пока они есть, доступна только пометка на удаление, не стирание.

### etn init — инициализация сервера и первого администратора

CLI-команда первичной инициализации сервера.

```
etn init --username admin --display-name "Administrator"
```

**Что делает.**

- создаёт системную БД `_system.db` и применяет миграции;
- создаёт первого пользователя: `is_admin = 1`, `is_first_user = 1` — администратор системы и root инсталляции;
- генерирует первичный API-ключ и **выводит его в консоль один раз**; повторно ключ показать невозможно, только перевыпустить;
- пишет в журнал аудита запись с `category = system`, `action = init`.

**Без инициализации сервер не стартует.** Пока на сервере нет ни одного администратора, запуск отклоняется — иначе получился бы работающий сервер, которым некому управлять.

**Инвариант, который закладывает команда.** Первого пользователя нельзя удалить и нельзя снять с него права администратора — защита от сервера, оставшегося без единого администратора.

**Когда вызывается.** Один раз, при развёртывании. Повторный вызов на уже инициализированном сервере второго root-администратора не создаёт.

---

**Термин (глоссарий 10).** **`etn init`** — CLI-команда инициализации сервера: создаёт каталог данных и `_system.db`, применяет миграции, создаёт первого администратора и печатает его API-key.

### Диалог «Корзина»

Пункт «Корзина (N)» меню «Мыслесеть». Список — `GET /trash` одним запросом (все помеченные на удаление мысли и связи сети; без пагинации — прокрутки достаточно).

Таблица в три колонки — что в корзине | Ссылок | Действия (ошибка 009784ad; было строкой с текстовыми ссылками «вернуть»/«удалить», которые не относились к строке, и с id вместо названий у связей):

- **Колонка 1** — название мысли; для связи — подпись «источник → назначение · тип связи». У ребра в `GET /trash` есть только id концов, поэтому имена догружаются батчем `POST /thoughts/resolve`, а имя типа берётся из кэша типов сети; форма подписи — та же, что у тултипа ребра локального графа. Заблокированная строка несёт статичную метку `🔒` (причина — в подсказке метки), чтобы видеть блокировку, не наводя курсор.
- **Колонка 2** — число мест использования помеченного элемента: у мысли `GET /thoughts/{id}/usage` → `total` (сколько раз на неё ссылаются свойствами); у связи — прочерк, использования в свойствах у связей нет (§5a.3).
- **Колонка 3** — кнопки-иконки с подсказками (значки — из общего набора `lib/icons.ts`): **«Восстановить»** — `PATCH { marked_for_deletion: false }`, доступна всегда; строка сразу пропадает из списка, а с облачка/линии снимаются значок корзины и бледность (если сущность не неактуальна сама по себе). **«Удалить»** — физическая чистка: мысль — `DELETE /thoughts/{id}`, связь — пометка + точечный `POST /trash/purge { ids: [id] }` (0.8.1: `DELETE /links/{id}` снят). «Удалить» активна только при `blocked = false`; у недоступной её подсказка объясняет причину (использование в свойствах, удерживающий слой).
- Строки не переносятся: название или подпись — одна строка с многоточием, полный текст — в подсказке; ширина окна — `clamp(520px, 70vw, 1100px)`.

Внизу — **«Удалить всё, что возможно»** (`POST /trash/purge`): список перечитывается, в статус-баре «Удалено N, осталось заблокировано M».

### Диалог добавления и выбора мыслей

#### Переключатель «по всем сетям» (0.8.3)

В шапке диалога — переключатель охвата живого поиска: «текущая сеть» (умолчание) / «по всем сетям». Включённый направляет живой поиск кандидатов и дедупликацию в веерный режим (`network_ids`): найденные из чужих сетей показываются с именем сети (различение одинаковых заголовков); выбор существующего из чужой сети возвращает адрес `n:<net>#<id>` вызывающему полю (для свойств вида «кросс-сетевая ссылка»); создание новых мыслей всегда выполняется в текущей сети — диалог не создаёт мысли в чужих. Состояние переключателя хранится на клиенте и переживает перезапуск; охват в каждом вызове выбирает пользователь. Поле значения кросс-сетевой ссылки вызывает диалог сразу в принудительном кросс-режиме (`crossNetwork`, кнопка «…» в углу поля), минуя переключатель: текущая сеть исключена, создание новых мыслей недоступно.

#### Поле «Свойство связи» в диалоге добавления с карты (0.8.3)

В холстовом диалоге добавления (пункты контекстного меню мысли «Добавить дочернюю/родительскую мысль») поле выбора связи — не «Тип связи», а **«Свойство связи»**: в списке только свойства вида «связь», отдельными пунктами имена обеих сторон одного свойства (прямое имя в источнике и обратное в назначении, например «запланировано в версию» и «включает работы»). Выбранное имя стороны заполняется у ДОБАВЛЯЕМОЙ мысли (новой или существующей) значением якоря — мысли, от которой строится связь; сервер выводит направление ребра из имени стороны, поэтому ребро попадает в типизированное свойство, а не в «Свойства вне типа». У существующей мысли текущий набор значения читается и объединяется с якорем — уже проставленные значения не теряются. Пустой пункт «без свойства» оставляет прежнее поведение — нетипизированную (структурную) связь в направлении диалога «вверх/вниз». Прочие вызывающие универсального диалога сохраняют выбор типа связи (поле «Тип связи»). Коммит `0d9485d` (ошибка `1dd08949`).

**Доработка 0.8.3 (ошибки `dc175a5b`, `5817b009`).** Поле — ввод с живым поиском, а не «открывашка»: отдельный переиспользуемый компонент `lib/link-property-field.ts` (`buildLinkPropertyField`), поиск идёт общим фильтром списка свойств (по имени стороны, любому имени пары типа связи, описанию) и находит свойство целиком — обе его стороны. В списке — значок направления связи (единый значок конца связи общего списка свойств: у стороны-источника стрелка сверху вниз, у входящей — снизу вверх, задача `88def930`) и пара имён типа связи в скобках `(прямое -> обратное)`; прежние подписи «источник/назначение · связь …» убраны. ### Корзина и проверки удаления в MCP

**Актуализация 0.8.4 (задача 09f19952).** Все перечисленные вызовы сняты с постоянного набора MCP — это действия исполнителя `etn.ops`: `thoughts.trash` (пометить/вернуть из корзины), `thoughts.deletion_check` (read-only), `trash.list` (read-only, каждая строка сразу с результатом проверки блокировки), `trash.purge` (confirm). Отдельного действия «проверка блокировки связи» нет — проверка отдаётся по каждой строке в `trash.list`. Детали — `etn.guide { topic: "trash.list" }`.

Группа инструментов S13 — мягкое удаление и проверки перед физическим:

- **`etn.thoughts.trash` / `etn.links.trash`** (idempotent) — пометить на удаление (`trashed: true`) / вернуть из корзины (`false`); блокировку не проверяют — это делает только физический `delete`;
- **`etn.thoughts.deletion_check`** (read-only) — что блокирует физическое удаление мыслей: использование в `thought_ref`-свойствах, удерживающие слои, будущие «сироты» среди детей. Принимает массив `thought_ids[]` — один вызов покрывает одиночную и групповую проверку;
- **`etn.links.deletion_check`** (read-only) — то же для связей: только удерживающие слои, без использования в свойствах и сирот;
- **`etn.trash.list`** (read-only) — вся корзина сети: помеченные мысли и связи, каждая сразу с результатом проверки блокировки (без отдельного `deletion_check` на строку);
- **`etn.trash.purge`** (destructive) — «удалить всё, что возможно»: физически удаляет помеченные, для которых проверки не дают блокировки; заблокированные молча пропускаются. Возвращает `{purged, skipped}`.

---

**Термин (глоссарий 10).** **Пометка на удаление** (`marked_for_deletion`) — состояние сущности в корзине: видима, но помечена; окончательное удаление возможно только при отсутствии удерживающих ссылок.

**Добавление (меню «Выделение», Ctrl+клик, поиск):** дубликаты пропускаются; убрать — только toggle. Правый клик по элементу — контекстное меню мысли (без команды выделения); клик — фокус, список не меняется.

**Меню «Выделение»:** добавить подчинённые (дети всех); добавить родительские; добавить мысль… (диалог поиска); очистить список.

**Меню «Действия»:** «Скопировать мысли» (все выделенные + связи между ними — во внутренний буфер; без хоткея). С фокусом: «добавить мысль в фокусе к родительским…» (связи фокус → каждая), «сделать мысль в фокусе единственным родителем…» (с подтверждением: удалить у выделенных входящие, кроме связи с фокусом), «добавить к подчинённым…» (выделенная → фокус), «исключить из родителей», «исключить из подчинённых». Прочее: Экспорт → Markdown/PDF/HTML (асинхронная задача с опросом), Экспорт → .etnx (диалог параметров), Импорт… (прикрепляется к фокусу), Удалить (одна — диалог одиночного; больше — группового).

**Меню «Свойства»:** пометить неактуальными/актуальными; изменить настройки… (цвета/стиль, применяется ко всем сразу, «Сброс» — наследование от типа); изменить тип мыслей… (с поиском, «Без типа»); изменить значение свойства… (таблица свойств всех типов списка; применение — только мыслям, чей тип предусматривает).

**Перетаскивание:** элемент списка на холст — по правилам облачка (упорядочивание недоступно). Бросок мысли в список — добавить в выделение. Эллипсов в строках нет.

---

**Термин (глоссарий 10).** **Панель выделения** — панель со списком выделенных мыслей и меню действий над выделением.

**Слить в основу… (0.10.3, задача `f5c363a3`).** В меню «Действия» — активен при наличии среди выделенных мыслей, перекрытых в текущем не-основном слое; открывает диалог точечного слияния (см. «Меню слоёв» → «Точечное слияние мыслей»).

<a id="pub-f7623077"></a>

### Панель использования

Интерактивная панель разбора блокировок удаления — не путать с пассивной группой «Использование» вкладки «Связи» редактора (та без изменений). Открывается по ссылке из диалогов удаления или по значку 🗑 для конкретной мысли/связи.

**Позиция:** слева, на месте панели выделения (если закрыта) или правее неё (обе видны одновременно); та же механика сплиттера, ширина в `window_layout.u`.

Источник данных — `GET .../usage` (с полем `holding_layers`). Две сворачиваемые группы (id `usage_panel:properties`, `usage_panel:layers`):

- **«Используется в свойствах»** — только для мыслей. Строка: ссылающаяся мысль + имя свойства (по строке на свойство). Контекстное меню строки — меню облачка + **«Очистить свойство»** (`DELETE .../properties/{key}`). Кнопка **«Очистить все свойства»** — `POST .../usage/clear`, с подтверждением (необратимо, затрагивает чужие мысли).
- **«Используется в слоях»** — слои, чья теневая строка удерживает мысль/связь (с 0.5.2). Кнопка **«Удалить слой»** — как в меню слоёв, с диалогом каскада; после удаления панель перечитывает `deletion-check` и обновляет открытые диалоги удаления.

Закрывается крестиком или повторным вызовом для той же мысли/связи (toggle).

**Термин (глоссарий 10).** **Панель использования** — панель входящих формальных ссылок на мысль (кто и через какое свойство её использует); показывает «удерживающие ссылки».

<a id="pub-3e8fdb83"></a>

### Редактор мысли/связи

Панель редактирования выбранной мысли или связи. По умолчанию справа; переключается: слева / сверху / снизу / скрыто (`ui_state.editor_position`). По умолчанию в редакторе — мысль в фокусе; клик по связи на холсте — содержимое связи (фокус не меняется).

**Заголовок панели:** «Мысль» или «Связь». Для помеченной на удаление мысли — значок корзины перед словом «Мысль» (ярко-красный на чёрном кружке, как на облачке) и поле «Название» зачёркнутым, оставаясь редактируемым. Лейблов у полей нет — placeholder.

**Шапка мысли:** квадратик иконки (нет иконки — плейсхолдер; клик — диалог выбора иконки); заголовок крупный (1.5×), жирный, авто-высота до 5 строк; синонимы (однострочное, запятая — разделитель); тип ▾ — поле одиночного выбора типа (пусто — ввод с живым поиском и пункт «без типа»; заполнено — облачко типа прямо в поле, ввод недоступен, крестик очищает; кнопка «…» открывает диалог выбора одного типа); ⚙ (диалог настроек мысли); чекбокс «актуально» (для HOME заблокирован). При смене типа меняются только незаданные вручную визуальные настройки (NULL наследуются от нового типа), иконка, стили, цвета и состав свойств (прежние скрываются, но не очищаются).

**Шапка связи:** строк иконки/заголовка/синонимов нет; тип связи ▾ — то же поле одиночного выбора (пусто — ввод с живым поиском и «без типа»; заполнено — облачко типа связи в поле, ввод недоступен, крестик очищает, «…» — диалог выбора одного типа); ⚙ (настройки связи: цвет/штрих/толщина + «Сброс»), чекбокс «актуально».

**Явная навигация в помеченную мысль и команды корзины** (задача ff991fb2, коммит `0a10755`, 0.8.2). Переход в помеченную мысль по явному указанию (wiki-ссылка, deep-link) разрешён и при выключенной настройке «Показывать содержимое корзины» — ссылки не должны умирать молча. Чтобы это было очевидно и давало выход, метка корзины в заголовке панели — кнопка: клик открывает общий диалог восстановления/удаления (`openThoughtDeleteDialog`, как метка на карте). Поле «Название» при этом остаётся зачёркнутым и редактируемым.

**Инкрементальная смена открытой сущности** (ревизия 2026-09-28, задача 90b2256e, коммит `8158da25`, 0.10.2). Смена открытой сущности в редакторе не пересоздаёт каркас панели: полоса вкладок с кнопками, хост вкладок и overflow-механика сохраняются; заменяются только шапка и содержимое активной вкладки, счётчики «(N)» перечитываются по новой сущности. Переход «загрузка → загружено» строит каркас ровно один раз (двойной пересборки нет). Прокрутка при смене сущности не сохраняется — у другой сущности другой контент (сознательное решение, зафиксировано в модуле `editor.ts`). Полная пересборка панели остаётся для смены вида сущности (мысль ↔ связь), смены дока, слоя и первой отрисовки.

**Уточнение (круг 1, коммит `0df8b9b0`, 0.10.2).** При смене открытой сущности того же вида и того же типа поля шапки (иконка, «Название», «Синонимы», «Тип», «актуально») не пересобираются — обновляются только их значения на месте; структурно иная шапка (мысль ↔ связь, «загрузка → загружено», смена типа) по-прежнему пересобирается. Содержимое уже построенных вкладок перечитывается под нового владельца без сброса кэша вкладок: «Свойства» сверяет строки по ключам привязок (keyed), прочие вкладки пересобирают содержимое внутри того же узла панели. Устаревший асинхронный загрузчик счётчика «(N)» не перезаписывает счётчик новой сущности.

**Уточнение (ошибка 253505a6, коммит `d07fa954`, 0.10.2).** При смене открытой сущности того же вида, когда полная новая цель ещё не загружена (карта, клавиатурная навигация, список мыслей связи, миникарта, редактор значения — экраны, открывающие мысль по одному id и подгружающие её сами), редактор УДЕРЖИВАЕТ на экране прежнюю показанную сущность и НЕ показывает загрузочную заглушку: шапка и вкладки не разбираются, повторной сборки нет; переход «прежняя → новая» выполняется одним приёмом, когда сущность приходит. Это выравнивает карту с экранами «Структуры»/«Дневник»/«События», которые передают редактору уже загруженную сущность. При сбое загрузки новой сущности цель редактора возвращается к прежнему состоянию (редактор не «залипает» на новой цели с прежним содержимым).

### Строка поиска вида «Карта мыслей»

Строка поиска — **строка вида «Карта мыслей»**: под верхней панелью, над холстом. В видах «Структуры» и «Дневник» скрыта; `Ctrl+Shift+F` там не действует. Глобальный поиск вызывается по `Ctrl+Shift+F` (перенесён с `Ctrl+F` в 0.12.1, задача `045f98db`, требование `778e13f4`); `Ctrl+F` закреплён за поиском внутри текущего текстового поля (панель поиска комментария — `b8eabc22`).

#### Ревизия 0.8.2 (задача 3742dd59, коммит 3b09f50)

Настройки отбора строки поиска переведены на общую модель конструктора отбора: `SearchOptions` и собственный парсер сохранённого убраны, `search_state` пишется теми же ключами. Типы мыслей и типы связей выбираются общим чип-полем и хранятся МАССИВОМ — прежде комбо хранило один id и остальные выбранные типы терялись. Автор/редактор по-прежнему одиночные: серверный поиск принимает только `author_id`/`editor_id` без операторов. Попутно починена ошибка 65382113: клик по строке результата связи/хронологии и Enter на ней снова открывают хит.

**Уточнение (ошибка 72a06e01).** Панель скрывается только по `Escape` или клику вне неё — клик по всплывающему слою, открытому ИЗ панели (общая выпадашка подсказок в `document.body`, модальный диалог), панель не закрывает. Иначе поле отбора теряет фокус, выпадашка снимается до `click`, и выбранный тип (подкорень, тип связи) не доезжает до отбора. Зона «настройки поиска» живёт внутри панели, поэтому клик по ней (в т.ч. по кнопке-лейке) панель тоже не закрывает.

#### Ревизия 0.8.2 (задача a1766c7d, коммит 7be39cd)

Подсветка совпадений запроса в заголовке облачка-результата: фабрика облачка (`lib/thought-cloud.ts`) получила опцию `highlightTerms`, термы даёт `searchHighlightTerms` (`lib/pure.ts`) из текущего запроса. Термы передают обе группы мыслей («по именам», «по текстам») и секция «Мысль по ID»; `<mark>` в названии выглядит как серверный сниппет (общее правило в `styles.css`).

`Enter` по выбранной записи запускает ту же функцию активации, что и клик по ней (реестр `rowActivations` в `search/search.ts`): прежде `Enter` синтезировал `click()` по строке, а у хита-мысли обработчик живёт на облачке-ребёнке — синтетический клик до него не доходил, и мысль по `Enter` не активировалась вовсе. Без выбранной записи `Enter` по-прежнему повторяет поиск.

#### Ревизия 0.8.2 (ошибка aa5d0aff, коммит 2d64bbb)

Прокрутка зон панели независима. Прежде общая полоса жила на самой панели (`overflow-y: auto` у `.search-panel`), и результаты с настройками скроллились вместе. Теперь панель — flex-колонка с `overflow: hidden`, тело (`min-height: 0`) отдаёт остаток высоты зонам, и каждая зона прокручивается своей полосой — и при положении «справа», и при положении «сверху».

В положении «сверху» высота зоны настроек ограничена `min(240px, 25vh)` с внутренней прокруткой: остаток высоты панели забирают результаты, настройки их не съедают. Предел задан в определённых единицах намеренно — процент от высоты тела не разрешается (тело получает высоту флексингом, Chromium считает её неопределённой, и `max-height: 45%` молча превращался в `none`). Раскладка проверена CSS-зондом в обоих положениях при переполнении обеих зон.

### Три роли доступа: администратор системы, владелец и участник сети

Ролей ровно три, дробить их на более мелкие права не предусмотрено.

| Роль | Область | Права |
|---|---|---|
| **Администратор системы** | весь сервер | Всё на любой сети с эффективными правами владельца — **даже без явного членства**. Управление пользователями и их ключами. Управление любой сетью и её членством. Удаление любой сети. Чтение журнала аудита. |
| **Владелец сети** | одна сеть | Всё внутри сети плюс управление её членством: добавить и исключить участника, передать владение. Переименование и удаление своей сети. |
| **Участник сети** | одна сеть | Полный доступ к данным сети — мысли, связи, типы, комментарии, свойства, вложения — без отличий от владельца. Членство менять не может, только просматривать список участников. |

**Где хранятся роли.** `users.is_admin` — глобальный флаг администратора системы; `network_members.role` (`'owner'` или `'member'`) — роль в конкретной сети.

**Главное, что путают.** Для операций с данными сети `owner` и `member` не различаются вообще. Различие ролей действует только при управлении самим членством сети. Не выдумывай ограничений участнику на запись данных — их нет.

---

**Термины (глоссарий 10).** **Администратор системы** (`is_admin=1`) — глобальная роль: пользователи и их ключи, любая сеть и её членство, чтение `audit_log`. **Владелец сети** (`role=owner`) — создатель сети или получатель владения; управляет членством. **Участник сети** (`role=member`) — полный доступ к данным сети без управления членством.

<a id="pub-951227f0"></a>

### активность

Признак актуальности (`active`) мысли или связи. `false` + выключено «показывать неактуальное» — сущность скрыта. Выполненные задачи и исправленные ошибки помечаются неактуальными, но не удаляются.

<a id="pub-a3fe546c"></a>

### версия (сущности)

Целое число, монотонно растёт при каждом изменении сущности. Используется для оптимистичного контроля (`If-Match`).

<a id="pub-91110685"></a>

### вложение

Ссылка на интернет-страницу или файл. На MVP файлы не загружаются на сервер (`kind=file` хранит путь в ОС клиента).

<a id="pub-e583a314"></a>

### дедупликация

Проверка при добавлении мысли: поиск по названию и синонимам, предложение использовать существующую вместо создания новой. Перед созданием мысли агент обязан вызвать `etn.thoughts.find_duplicates`.

<a id="pub-dafe448f"></a>

### конфликт

Серверная версия сущности опередила клиентскую при изменении. Для того же поля — `409 VERSION_CONFLICT`; для разных полей — мирное слияние.

<a id="pub-62dbebfc"></a>

### мыслесеть

Отдельная база данных для мыслей и связей (физически — каталог `networks/<id>/` с `data.db`). В коде — `network`. У пользователя может быть сколько угодно мыслесетей; каждая экспортируется, импортируется и бэкапится независимо.

<a id="pub-cc63d3c1"></a>

### мысль

**Мысль** (`thought`) — обособленная запись, описывающая информацию, слабо зависящую от времени. Базовая сущность системы, хранится в таблице `thoughts`.

Признаки:
- может быть актуальной или неактуальной (`active`);
- может иметь один тип (`thought_type`);
- может иметь синонимы (для поиска и дедупликации);
- может иметь иконку, цвет и стиль;
- имеет заголовок (до 400 символов).

Особый подвид — **корневая мысль** «HOME» (`is_root=1`), одновременно защищённая (`is_protected=1`).

<a id="pub-207baaf9"></a>

### облачко мысли

Визуальное представление мысли на холсте: иконка, заголовок, строка индикаторов, два эллипса.

<a id="pub-8d883523"></a>

### постоянный комментарий

Один на владельца (мысль или связь), не зависит от даты. Здесь — суть, которая верна всегда.

<a id="pub-2afedf9d"></a>

### свойство мысли

Поле, доступное мыслям определённого типа. Значения: текст, дата, число, булево, ссылка на мысль (`thought_ref`).

<a id="pub-e2b1a585"></a>

### связь

Направленное отношение между двумя мыслями: источник (`source_id`) и назначение (`target_id`), опционально тип. Бывает актуальной/неактуальной. Петли запрещены. В коде — `link`.

<a id="pub-ab98849c"></a>

### синоним мысли

Дополнительное имя мысли, по которому она находится в поиске и дедупликации.

<a id="pub-aaccbf44"></a>

### событие real-time

JSON-сообщение по WebSocket: `{type, seq, ts, actor, network_id, data, meta}`. `seq` монотонный, для пропуска и повторной доставки.

<a id="pub-356a499f"></a>

### тип мысли

Пользовательский тип, назначаемый мыслям. Определяет вид по умолчанию (цвет, шрифт, иконку) и набор свойств. Одна мысль — один тип.

### тип связи

Пользовательский тип связи. Определяет цвет/стиль линии и два направленных имени: `name_forward` и `name_reverse` — они отображаются на линии и в заголовках групп.

<a id="pub-4e7ca4f7"></a>

### упоминания

Мысли и связи, в чьих комментариях встречается название или синоним заданной мысли. Реализовано через FTS.

<a id="pub-3644462e"></a>

### фокус на мысли

Мысль, выбранная в центре холста. Запоминается сервером (последний фокус пользователя в сети).

<a id="pub-d8ba01bb"></a>

### холст

Центральная часть GUI с четырьмя зонами: фокус (центр), источники (верх-лево), родственники (верх-право), назначения (низ).

<a id="pub-70a65ad2"></a>

### хронологический комментарий

Много на владельца. Имеет `valid_from`/`valid_to`. Здесь — факты выполненной работы, привязанные к дате.

<a id="pub-c7a4b106"></a>

### эллипсы облачка

Индикаторы наличия входящих/исходящих связей и точки drag для создания новых мыслей в соответствующем направлении.
