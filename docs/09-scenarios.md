## /admin/networks — админский обзор и правка мыслесетей

Админский взгляд на все мыслесети сервера — в отличие от личного `GET /networks`, который показывает только сети явного членства даже админу.

```
GET    /api/v1/admin/networks                       # все сети сервера
DELETE /api/v1/admin/networks/{network_id}          # удалить сеть
PATCH  /api/v1/admin/networks/{network_id}/members  # принудительно менять членство
```

Удаление сети — необратимая операция: вместе с записью в реестре удаляется вся её база данных со всеми мыслями, связями и вложениями.

Право доступа админа к конкретной сети по id не зависит от его членства: он проходит проверку доступа на любую сеть и её вложенные ресурсы.

**Дополнительные материалы**
- относится к подсистемам: REST API, Аутентификация и права доступа
- зависит от: networks — реестр мыслесетей и самоописание сети, network_members — членство пользователей в мыслесетях
- применяется к: Администратор системы имеет доступ к любой сети без членства

## etn init — инициализация сервера и первого администратора

CLI-команда первичной инициализации сервера.

```
etn init --username admin --display-name "Administrator"
```

**Что делает.**

- создаёт системную БД `_system.db` и применяет миграции;
- создаёт первого пользователя: `is_admin = 1`, `is_first_user = 1` — администратор системы и root инсталляции;
- генерирует первичный API-ключ и **выводит его в консоль один раз**; повторно ключ показать невозможно, только перевыпустить;
- пишет в журнал аудита запись с `category = system`, `action = init`.

**Без инициализации сервер не стартует.** Пока на сервере нет ни одного администратора, запуск отклоняется — иначе получился бы работающий сервер, которым некому управлять.

**Инвариант, который закладывает команда.** Первого пользователя нельзя удалить и нельзя снять с него права администратора — защита от сервера, оставшегося без единого администратора.

**Когда вызывается.** Один раз, при развёртывании. Повторный вызов на уже инициализированном сервере второго root-администратора не создаёт.

---

**Термин (глоссарий 10).** **`etn init`** — CLI-команда инициализации сервера: создаёт каталог данных и `_system.db`, применяет миграции, создаёт первого администратора и печатает его API-key.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа

## GET /admin/audit — журнал аудита сервера

```
GET /api/v1/admin/audit?actor=&network=&category=&from=&to=&limit=&offset=
```

Чтение журнала административных и критичных операций сервера — **только для админа**. Фильтры: автор действия, сеть, категория, период; пагинация через `limit`/`offset`.

Состав записи и перечень журналируемых событий определяются таблицей журнала и требованием о журналировании: сам маршрут только читает и ничего не меняет.

**Дополнительные материалы**
- относится к подсистемам: REST API, Аутентификация и права доступа
- зависит от: audit_log — журнал административных операций
- применяется к: Журналирование критичных операций сервера

## Агент собирает дайджест по теме

Действующее лицо — внешний AI-агент, подключённый по MCP. Задача: собрать сводку по теме из мыслесети и вернуть её пользователю.

1. `etn.thoughts.search { query: "<тема>", scope: "all" }` — получить кандидатов с оценками.
2. Для топ-5 результатов — `etn.thoughts.subgraph { seed_ids: [...], radius: 2, include_comments: true }` — готовый контекст: мысли, связи, превью комментариев.
3. Сформировать контекст и сгенерировать Markdown-дайджест в своей LLM.
4. Опционально — `etn.thoughts.write` с `chronicle[]`: хронологический комментарий у корневой мысли с дайджестом и `valid_from = сегодня`.
5. Участники сети тут же видят новый комментарий через WebSocket (real-time).

Ветвления: превью обрезаны — полные тексты через `etn.comments.get`; подграф усечён (`truncated/reason`) — сузить `radius` или повторить от других seed'ов.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- зависит от: etn.comments.* — комментарии в MCP, etn.thoughts.search — полнотекстовый поиск, etn.thoughts.subgraph — подграф вокруг мыслей

## Версионирование записей и разрешение конфликтов

Каждая содержательная запись несёт целочисленный `version` и `updated_at`. Версия растёт при каждой правке **собственных полей записи**. Запись значения свойства обновляет `updated_at/by` владельца, но его `version` не поднимает: маршрут значений (§9) `If-Match` не несёт, а приравнивание «правка значения = правка владельца» действует по `updated_*` (требование e6d4165e), не по версии (ревизия 2026-09-28, ошибка af104f16, фикс 01bf39fe).

Клиент, изменяющий запись, передаёт версию, которую он видел (контракт `If-Match` в REST, `expected_version` в доменных вызовах и MCP).

`If-Match` проверяется на **текущей версии сущности**. Дальше — политика MVP: last-write-wins на уровне поля + явный сигнал конфликта:

- изменяемые поля не пересекаются с чужими правками — **мирное слияние**: сервер применяет только свои поля, не трогая чужие, и возвращает 200 с актуальной версией. Пример: А поменял заголовок при v=5 → v=6; Б шлёт `If-Match: 5` с новой иконкой — поля разные, сервер применяет иконку, не трогая заголовок → v=7, 200;
- набор изменяемых полей совпадает (заголовок против заголовка) — `409 VERSION_CONFLICT` с телом `{ server_value, server_version }`; клиент показывает уведомление и предлагает «перезаписать» или «оставить чужое».

Передача версии необязательна: без неё действует last-write-wins пополёвно.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, Real-time канал (WebSocket)
- применяется к: links — направленные связи между мыслями, thoughts — таблица мыслей

## Вид «Дневник» (рабочий стол)

Третий рабочий стол (ранее «Хроника»): лента дневниковых записей с календарной навигацией и панелью отбора. Панели выделения и редактора остаются на месте; статус-бар с историей посещения — общий.

**Компоновка (уточнено 0.10.1, задача 46057359).** Над ВСЕЙ областью дневника — строка поиска записей (элемент «Поиск в дневниковой ленте»): во всю ширину, правый край — у сплиттера редактора. Под ней: слева — панель отбора, её ПЕРВЫМ элементом сверху идёт календарь месяца; в центре — непрокручиваемая верхняя панель с кнопкой «Добавить хроно-запись», под ней лента записей по дням (положение и размер панели отбора — по общему каркасу панелей отбора).

**Календарь.** Выбор даты или недели; клик = «Применить» с новым периодом (пишет в поля периода панели, прочие критерии не трогает). Клик распознаёт шаблон и пишет ТОКЕНЫ, когда период совпал: день=сегодня → `$today`; ровно эта/прошлая/будущая неделя → `$week.start`/`$week.end` с `±1w`; ровно этот/прошлый/будущий месяц → `$month.start`/`$month.end` с `±1mo`; иначе — точные даты. Кнопка «Сегодня» переносит к текущей дате и выделяет её. См. элемент «Календарь месяца в «Дневнике»».

**Панель отбора.** Общий каркас `lib/filter-form.ts`; критерии — единый конструктор `lib/filter-builder.ts`; сохранённые отборы — `lib/saved-filter-bar.ts` (сервер, `view=chronicle`, audience=user). Состав (набор «Структур», 306f74cc): календарь месяца (header панели), период «с»–«по» с пресетами токенов («Поле периода», панельный вариант), ключевые слова + чекбоксы области поиска (наименование/синонимы/комментарий), типы мыслей, типы связей, родительские мысли, свойства мыслей, дополнительно (актуальность + корзина), сортировка — только направление; внизу «Применить»/«Очистить» + сохранённые отборы. Критерий «Ключевые слова» — как в отборе «Структур»: место поиска задают флаги «наименование»/«синонимы»/«комментарий» (`keyword_scope`); «наименование» и «синонимы» относятся к мыслям-целям записей, «комментарий» — к постоянным комментариям мыслей и к тексту/заголовку самих записей. Критерии ЗАПИСИ (ключевые слова с двухпутевым поиском по телам/заголовкам записей и мыслевому пути, период) живут на верхнем уровне модели; критерии ЦЕЛЕЙ — вложенной моделью `targets` (тот же конструктор, что у «Структур»; запись проходит, если хотя бы одна привязанная мысль удовлетворяет). Убраны «сторона связи», поле «мысли»-корней и отдельная группа «критерии целей» — верхние критерии и есть критерии целей. Поля периода — единственный источник дат.

**Лента.** Записи сгруппированы по дням периода; порядок — класс записи, затем `valid_from`/`valid_to`, тайбрейкеры `created_at`/`id`; длительная запись видна в каждом дне периода; дозагрузка «+50» по прокрутке. Слот псевдо-записи — над записями дня. Каждая запись: заголовок, дата/время по флагу «учитывать время», чипсы привязок с «+»/«✕», правка по месту (оболочка `lib/ui` комментария). См. элемент «Лента дневных записей».

**Запись дня.** Первичный владелец — HOME; чипсы — вторичные привязки (`/comments/{id}/targets`); снятие последнего чипса оставляет запись и поднимает её в верхний блок. Несколько записей на дату разрешены.

**Кнопка добавления** всегда создаёт псевдо-запись (в базу не пишется до первого содержательного сохранения), дефолт даты = `clamp(сегодня, начало, конец периода)`.

**Поиск (уточнено 0.10.1, задача 46057359).** Самостоятельная строка поиска записей над панелью и лентой (элемент «Поиск в дневниковой ленте»), а НЕ поле критерия панели. Механизм — как у строки поиска вида «Карта мыслей»: debounce/Enter, выпадающий список совпадений, клавиатурная навигация, мини-синтаксис keywords; ищутся только дневниковые записи. Настройки строки — две опции: «включать неактивные мысли» и «включать корзину» (мысли-цели записей). Выбор результата: дата начала записи становится периодом, запись делается текущей и видимой в ленте; если запись не проходит текущий отбор — отбор сбрасывается, дата начала остаётся. Прежняя временная выборка с плашкой упразднена. Строка — общий компонент `lib/record-search.ts` (переиспользуется на других экранах).

**Realtime.** Лента обновляется по `comment.*` и изменениям мыслей/связей.

**Состояние.** Критерии, страница, месяц и выбранный отбор — L4 `chronicle_state`; настройки строки поиска записей — L4 `record_search`; восстанавливаются при входе.

**Реализация** — `screens/chronicle/chronicle.ts`, стили `styles/screens/chronicle.css`; контролы — `lib/period-editor.ts` (вариант `panel`), `lib/filter-builder.ts`, `lib/filter-form.ts`, `lib/saved-filter-bar.ts`, `lib/entity-picker.ts`; строка поиска записей — `lib/record-search.ts`; календарь — `screens/chronicle/calendar.ts`, панель — `screens/chronicle/filter-panel.ts`.

**Ревизия (2026-09-26, задача 7edd1cce, приёмка №2).**

- **Лента.** Показ и правку текста записи ведёт единая оболочка комментария `lib/ui/comment.ts` (та же, что в редакторе мысли и вкладке «Дневник»), а не самодельный каркас; пустой текст даёт приглашение и область двойного клика для входа в правку. Псевдо-запись слота — тоже через оболочку.
- **Группы дат.** Подпись дня — кнопка-заголовок: вдвое крупнее базового шрифта (токен темы), клик сворачивает/разворачивает группу. Состояние свёрнутых групп — клиентские настройки экрана (L4 `diary_collapsed_days`). В верхней панели рядом с «Добавить хроно-запись» — компактные кнопки-иконки «Развернуть все»/«Свернуть все».
- **Поля выбора панели.** «Типы мыслей», «Типы связей», «Родительские мысли» — единое чип-поле общего модуля `lib/entity-picker.ts` (`buildEntityChipField`): мини-облачка значений, поле живого поиска, угловые кнопки «…» (полный список-пикер) и «✕» (очистить всё), приглашение «+ ещё один тип/мысль». Отдельные текстовые кнопки «список типов…»/«выбрать…» у полей убраны — те же элементы, что у поля значения свойства-связи в редакторе.
- **Период.** Группа «Период» — переключатель «Пресеты»/«Даты» (см. «Поле периода»); режим сохраняется в определении отбора (`date_mode`).
- **Правка даты записи по месту.** Пока контрол даты открыт, лента не перерисовывается — иначе открытый контрол сносился вместе с карточкой, и смена режима «Дата/Дата и время/Диапазон» сбрасывалась на «Дата».

## Вкладка «Вложения»

Две области со сплиттером (перетаскивание меняет высоту таблицы).

**Список вложений** (≤5 строк, дальше прокрутка): строки с превью (картинки через `etnimg:`, favicon для URL, глиф для остальных), зона перетаскивания, кнопка «Добавить вложение». Заполняется при активации; счётчик — всегда. Перетаскивание ссылки/файла: автозаполнение заголовка (имя файла; для URL сервер best-effort тянет `<title>` и favicon). Вставка из буфера в поле комментария: файлы загружаются и вставляются ссылкой (`![имя](etnimg:…)` / `[имя](etnimg:…)`).

**«Добавить вложение»** — две вкладки: «Создать новое» (URL/путь, заголовок, комментарий; для «Файл (путь)» кнопка «Открыть с диска…» — системный диалог, путь в поле, имя файла в заголовок если пуст; вложение создаётся по «Добавить» с загрузкой копии на сервер ≤10 МиБ) и «Найти существующее» (поле + результаты `GET /attachments?q=…` с исключением текущего владельца; клик — новая строка у владельца с теми же полями, файл не дублируется).

**Просмотр:** клик выбирает, двойной — открыть в программе по умолчанию. Картинки — просмотр с масштабированием, у URL-картинок кнопка «Открыть оригинал»; текстовые/markdown — как постоянный комментарий (просмотр, двойной клик — правка, клик вне — перезапись файла `PUT …/attachments/{id}/content`); прочие — кнопка «Открыть в приложении по умолчанию»; до выбора — «Выберите вложение для просмотра».

**Контекстное меню строки:** «Открыть в программе по умолчанию» (`shell.openPath`/`openExternal`; опасные схемы `javascript:`/`data:`/`vbscript:`/`blob:`/`about:` не открываются, при неудаче — сообщение с причиной); «Назначить иконкой мысли» (владелец — мысль; доступно для картинки-файла и для url-ссылки с извлечённой иконкой (favicon), см. ниже; у картинки-файла — самодостаточный `data:` URL ≤256 КБ, большие ужимаются в превью 256×256, `icon_attachment_id` указывает на вложение, `Ctrl+наведение` — полная картинка); «Перенести в мысль…» (диалог поиска; `PATCH owner`); «Скопировать в мысли…» (мульти-выбор без создания; для каждой — новая строка `POST /attachments/{id}/copy`; дубликаты url/file_path+kind пропускаются тихо; отчёт «Скопировано в N мыслей, уже было в M»); «Удалить…» (с подтверждением; серверная копия файла удаляется).

**Иконка мысли из url-вложения (0.8.3, задача 2fd41d3a).** У url-вложения с извлечённой иконкой (favicon) в контекстном меню есть пункт «Назначить иконкой мысли»; у file-вложений и url-ссылок без иконки пункта нет, ошибка извлечения меню не ломает. Назначение ставит мысли `icon_kind='image'` из того же источника, что перетаскивание интернет-ссылки в зону карты: favicon берётся из `attachment.icon` (`data:`-URL, best-effort заполняет сервер при создании ссылки) и кладётся как есть; `icon_attachment_id` при этом не ставится — у url-вложения нет файла для `Ctrl+наведения`. Новая иконка сразу видна на карте и в карточке (общий `reflectThoughtUpdate`, см. fixes/045). Правило видимости и назначения — `urlAttachmentIcon`/`canAssignAsThoughtIcon`/`assignDataIconToThought` в `client/src/renderer/editor/attachments.ts`.

**Ошибка добавления — в панели кнопок (0.8.2, ошибка add8d09d).** В диалоге «Добавить вложение» сообщение о неудачном добавлении выводится в футере (рядом с «Отмена»/«Добавить»), а не в теле вкладки «Создать новое»: оно видно и когда открыта вкладка «Найти существующее». Локальная ошибка поиска (вкладка «Найти существующее») остаётся в теле вкладки — это операция самой вкладки. Правило — требование «Ошибка записи диалога с вкладками показывается в панели кнопок».

**Обновление списка и счётчика (0.8.2, ошибка 05bd8809).** Список и счётчик вкладки обновляются сразу при любом изменении набора вложений владельца, без переоткрытия мысли: вставка картинки/файла из буфера в поле markdown (постоянный комментарий или текст вложения), «Назначить иконкой мысли» из файла, а также добавление и удаление на самой вкладке. Кэш неактивной вкладки при этом сбрасывается, активная вкладка перечитывает список на месте (её встроенный просмотрщик-редактор с несохранённой правкой не уничтожается).

**Обновление при внешних правках (0.8.2, ошибка abd25adb).** Список и счётчик вкладки обновляются и когда набор вложений показанной сущности меняет другой клиент или MCP. Realtime-события `attachment.created/updated/deleted` доходят до открытого редактора: гейт — по показанной сущности, владельца у `updated`/`deleted` (в событии только id) находит индекс показанных вложений (`client/src/renderer/lib/attachment-events.ts`). Изменение применяется тем же локальным каналом, что и собственные правки: показанная вкладка перечитывает список на месте (встроенный просмотрщик с несохранённой правкой цел), скрытая — сбрасывает кэш. События чужой сущности и чужой сети игнорируются.

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор)
- применяется к: Стабильные размеры диалога: роли S/M/L/XL, высота не зависит от вкладки, Ошибка записи диалога с вкладками показывается в панели кнопок, Сообщения диалога: любая ошибка — строкой на панели кнопок, клик ведёт к полю

## Вкладка «Дневник» редактора

Две области со сплиттером; содержимое заполняется при активации вкладки, счётчик в заголовке — всегда.

**Таблица записей (ревизия 2026-09-27, задача 8012a9b0; заголовок — ревизия 2026-09-29, задача 8e4a965f).** Три колонки — «Период», «Заголовок», «Редактор». Строится общим фасадом списков `lib/ui/table.ts` (клавиатурная навигация: стрелки, Home/End, PgUp/PgDn, Enter; контекстное меню строки). Ячейки — в одну строку, переполнение обрезается многоточием, полный текст — в подсказке. Клик — выбрать запись, двойной клик — выбрать и войти в правку. «Период» — единое отображение периода дневниковой записи (то же, что в ленте экрана «Дневник»): `formatRecordPeriod`, `lib/date-period-dialog.ts`. «Заголовок» — `title` записи, а при его отсутствии — первая непустая строка заметки СО СНЯТИЕМ ведущих markdown-маркеров (`#`, списки, `>`), разэкранированием HTML-сущностей и снятием хвостового «…», не более 250 символов; разбор общий с лентой экрана «Дневник» — модуль `lib/record-title.ts` (`recordDisplayTitle`, ограничение длины — параметр). «Редактор» — пользователь, последним изменивший запись (`updated_by`).

**Контекстное меню строки (ревизия 2026-09-27).** «Открыть в дневнике» — открывает экран «Дневник», ставит в календаре дату записи и делает запись текущей в ленте; «Удалить» — с подтверждением. Кнопка «Добавить» создаёт новую запись и сразу переводит её в правку (новая строка выделена).

**Нижняя область (ревизия 2026-09-27).** Без выделения — надпись «Дневниковых записей нет. Нажмите „Добавить“ для новой записи». При выделении — шапка записи и markdown-поле постоянного комментария (HTML-просмотр, двойной клик — правка, клик вне — сохранение, Esc — отмена). Автосохранение: первый непустой blur по тексту **создаёт** комментарий, дальнейшие — обновляют (`If-Match`); правки метаданных — по blur. После каждого изменения таблица и счётчик обновляются.

**Шапка записи (ревизия 2026-09-27).** Одна строка: период записи в едином отображении (клик — диалог «Дата/период», период разрешён; переключателя «учитывать время» в шапке нет, время включается кнопкой «С указанием времени» внутри диалога) и поле ввода заголовка на всю оставшуюся ширину панели.

### Ревизия 0.10.1

Вкладка переименована в «Дневник» (имена модели/API не меняются). Даты начала/окончания правятся диалогом «Дата/период»; даты — полные UTC-инстансы с мс, `valid_to` не может остаться пустым (незаполненное = `valid_from`). См. ADR времени и требования к формату дат.

**Ревизия приёмки №5 (2026-09-27, задача 7ce662c4).** Даты начала/окончания правятся не инлайн-контролом периода, а диалогом «Дата/период», открываемым кликом по значению даты в шапке записи. Период в диалоге разрешён; время доступно по кнопке «С указанием времени». Значения диалога переводятся в полные UTC-инстансы (`resolveDatePeriodInstants`, ADR 994d076a, требование d58aa1a4), `valid_to` непуст.

**Ревизия 2026-09-27 (задача 8012a9b0, итерация доработки вкладки).** Вкладка переустроена по требованиям пользователя: таблица из трёх колонок на общем фасаде списков (взамен самодельной таблицы из семи колонок), контекстное меню строки с переходом на экран «Дневник», нижняя область с явным пустым состоянием, шапка записи одной строкой. Удаление записи — из контекстного меню строки (в шапке кнопки удаления нет).

**Триггер персистенции псевдо-записи (2026-09-27, задача 972803b7, коммит `d5753c74`).** Псевдо-запись (`commentId === null`, комментарий ещё не создан в сети) не сохраняется, пока не появится содержание. Содержанием считается непустой текст заметки **или** непустой заголовок: первый непустой blur по полю «Заголовок» создаёт запись (`etn.comments.create`, `kind: 'chronological'`, пустой `body_md`) — так же, как первый непустой blur по тексту заметки. Пустой заголовок и правка только дат/периода запись не создают. Правило — паритет с экраном «Дневник» workspace, где содержание определяется `hasRecordContent` (требование `26f0aa52-a3f2-4f2b-98cf-173778b96e18`). Реализация — `commitMeta` в `client/src/renderer/editor/chrono-tab.ts` (компонент `b5248f08-d0ff-471e-9829-424443c69b20`).

**Ревизия (2026-09-29, задача 41ed99ab, 0.10.2).** При открытии вкладки текущей становится САМАЯ ВЕРХНЯЯ строка таблицы (порядок — обратный хронологический, `defaultSort: { key: 'period', dir: 'desc' }`, `table.getRows()` возвращает отображённый порядок), чтобы сразу показывался текст её комментария в нижней области. Авто-выбор выполняется ОДИН РАЗ при открытии вкладки и только при отсутствии выбора: явно выбранную строку возврат на ту же мысль не сбрасывает, поздние перезагрузки (правка, добавление) выбор пользователя не перебивают. Пустой список — прежнее пустое состояние. Реализация — `editor/chrono-tab.ts`.

**Ревизия (2026-09-29, задача 8e4a965f, 0.10.2).** Производный заголовок колонки «Заголовок» при пустом `title` — первая непустая строка заметки СО СНЯТИЕМ ведущих markdown-маркеров, не более 250 символов. Разбор — ОДНА реализация в `client/src/renderer/lib/record-title.ts` (`recordDisplayTitle`, ограничение длины — параметр), общая с лентой экрана «Дневник» (лента — лимит 150); прежний собственный разбор строк в `chrono-tab.ts` удалён, кросс-экранной зависимости `editor/` ← `screens/` нет. Сторож `guard-record-title.test.ts`. Реализация — `editor/chrono-tab.ts` (компонент `b5248f08`), коммит `b67a8995`.

**Уточнение (2026-09-29, задача 8e4a965f, приёмка).** Общий разбор производного заголовка `lib/record-title.ts` помимо снятия ведущих markdown-маркеров, разэкранирования HTML-сущностей и снятия чужого хвостового «…» также УДАЛЯЕТ HTML-теги (`<...>`). Перечень преобразований в ревизии выше был неполон. Для сырого `body_md` это означает, что строка-автоссылка вида `<https://…>` будет вырезана — осознанный паритет с лентой экрана «Дневник» (там источник — серверный `snippet`/тело).

## Границы MVP: чего в системе намеренно нет

Явные ограничения, принятые осознанно. Наткнувшись на любое из них, не надо считать это дефектом и «чинить» попутно:

- **Один серверный процесс.** Нет кластеризации и реплик; pub/sub — внутрипроцессный, в памяти.
- **Записи сериализованы** write-lock’ом WAL в пределах одной сети. Расчёт — на 2–5 одновременных активных редакторов.
- **Нет шардинга сетей по дискам** — все сети в одном каталоге данных.
- **Поиск только внутри одной сети** — сквозного индекса по нескольким мыслесетям нет.
- **Нет офлайна на клиенте.**
- **Нет встроенной генерации документов и презентаций** — это работа для внешнего агента.
- **Нет векторного (семантического) поиска.** Задел оставлен только в схеме данных — зарезервированной таблицей эмбеддингов, чтобы будущая реализация не требовала миграций.

**Ограничения модели слоёв (13-layers.md §11).** Осознанные следствия модели «слой — плёнка, а не снимок»; наткнувшись на любое, не считать дефектом:

- **Состояние слоя на прошлую дату невоспроизводимо** — слой видит текущую основу, история пересчитывается при каждом чтении.
- **«Отличие слоя» двусмысленно**: относительно основы-сейчас (показ пользователю) и относительно основы-на-момент-создания слоя (слияние, через `base_version`).
- **Логическое противоречие с основой не обнаруживается**, если строки не перекрываются.
- **Слияние не разрешает конфликты, только детектирует**; three-way merge с выбором стороны — вне фазы S.
- **Разделение прав по слоям не входит в фазу S** — права у всех участников одинаковые (см. «Равные права на слои у всех участников сети»).

**Вне рамок фазы S по слоям (13-layers.md §17).** Кроме разделения прав и three-way merge (см. выше): автоматическая сверка `git_branch` слоя с состоянием git-репозитория — поле зарезервировано, но скрипт сверки в MVP фазы S не входит.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), Хранилище (SQLite), Полнотекстовый поиск (FTS5), Десктоп-клиент (Electron)
- применяется к: Хранилище (SQLite), Real-time канал (WebSocket), Десктоп-клиент (Electron), Полнотекстовый поиск (FTS5)

## Групповые операции: выбор, действия, экспорт

**Действующее лицо.** Пользователь.

**Шаги.**

1. `Ctrl+клик` по облачкам — мысли добавляются в панель выделения. Альтернативы: контекстное меню, `Ctrl+клик` по эллипсу облачка (все родители или все дети), меню «Выделение» (дети/родители уже выбранных, поиск существующей мысли).
2. Групповое действие: в панели выделения меню «Действия» / «Свойства» → операция → `POST /networks/{nid}/thoughts/batch { ids, op, args }` — сервер применяет операцию ко всем и возвращает результат с перечнем неудач.
3. Экспорт выбранных: «Действия» → «Экспорт» → формат → `POST /networks/{nid}/export { thought_ids, format }` → `202 { job_id }`; клиент опрашивает `GET /jobs/{job_id}` и по готовности скачивает файл.

**Результат.** Операция применена к набору мыслей, либо получен файл экспорта.

**Ветвления.** Частичные неудачи batch не откатывают успешные — клиент показывает список неудач.

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор), REST API, Экспорт и импорт
- зависит от: Панель выделения, POST /thoughts/batch — групповые операции над мыслями, POST /export и GET /jobs/{id} — экспорт подграфа в файл

## Диалог выбора иконки

Диалог выбора иконки (мысли или типа) — АДАПТЕР универсального компонента выбора ресурса `editor/resource-picker.ts` (задача d1a56d76); общая механика (вкладки-источники, доступность «Применить», закрытие) живёт в нём. Переключатель вверху: **Эмодзи / Библиотека / Иконки мыслей / Вложения / URL** (порядок вкладок фиксирован: «Эмодзи» — первая, «Библиотека» — следующая за ней).

- **Эмодзи** — полный набор Unicode 16.0 (без дублей тона кожи), категории CLDR («Смайлики и эмоции», «Люди и тело», «Животные и природа», «Еда и напитки», «Путешествия и места», «Занятия», «Предметы», «Символы», «Флаги»); группы сворачиваемые (первая развёрнута), контент строится при раскрытии; клик устанавливает (`icon_kind='emoji'`) и закрывает.
- **Библиотека** — вкладка библиотеки иконок (ТП0): живой поиск по каталогу имён, ленивая сетка значков; клик применяет и закрывает (`icon_kind='icon'`, `icon` = имя). На вкладке есть **поле выбора цвета символа** (тот же механизм выбора цвета, что у текста/фона) — задаёт `icon_color` (HEX `#rrggbb`), независимый от `fg_color`/`bg_color`; пусто — значок рисуется `currentColor`. Поведение — требование «Вкладка библиотеки в диалоге выбора иконки: поиск и выбор значка».
- **Иконки мыслей** — сетка иконок типов мыслей (клик применяет иконку типа сразу, `icon_kind` типа); пустой набор — подсказка. Список растянут **на всю доступную высоту** контейнера (как соседние вкладки) — варианты просматриваются до клика, без немедленного выбора.
- **Вложения** — ОБЩИЙ компонент выбора вложения `editor/attachment-picker.ts` (0.12.1, задача 0f6c3e39; тот же компонент, что вкладка «Вложения» диалога обложки публикации): список картинок сети с живым поиском (закреплён сверху), пагинацией по 200 («Показать ещё») и ФИКСИРОВАННЫМ предпросмотром справа (не прокручивается со списком); кнопка «Загрузить из файла» (системный выбор картинки) с предпросмотром; строк ввода и «ОК» внутри вкладки нет — применяет нижняя «Применить». Файл ужимается в самодостаточное `data:`-превью ≤256 КБ (`icon_kind='image'`); для **мысли** оригинал загружается во вложения (`icon_attachment_id`, `Ctrl+наведение` показывает полную картинку), url-вложение даёт иконку-URL. Для **типов мыслей** (вложений нет) — самодостаточное `data:`-превью. Текущее вложение/картинка отмечаются при открытии (подсветка `att-pick-preview-current`), применение без изменений сохраняет `icon_attachment_id`/превью без повторной загрузки (0.12.1, ошибки 846c426a, 844c426a).
- **URL** — поле + предпросмотр; применяет «Применить» (`icon_kind='image'`, `icon` = URL).

**Результат диалога.** За один проход возвращает **иконку, её вид и цвет** — `{ icon, kind, color }` (0.12.1, задача 4105bd6a): цвет заполнен для библиотечной `icon`, пуст для остальных видов.

**Восстановление выбора при открытии (0.12.1, ошибки e2407f6d, e748e323, 846c426a, 844c426a).** Если у объекта иконка уже выбрана, диалог при открытии сам открывает вкладку по виду: `emoji` → «Эмодзи», `icon` → «Библиотека», `image`-файл (вложение мысли с `icon_attachment_id` ИЛИ самодостаточное `data:`-превью иконки типа) → «Вложения» (текущее изображение показано выбранным, подсветка `att-pick-preview-current`, «Применить» активна; применение без изменений сохраняет `icon_attachment_id` для вложения и само `data:`-превью для типа — без повторной загрузки), `image`-URL → «URL». Разворачивается нужная группа (категория эмодзи) и выделяется текущий вариант; «Применить» активна — смена ТОЛЬКО цвета ранее выбранной библиотечной иконки доступна без повторного поиска.

**Футер:** «Очистить» (убрать собственную иконку `icon=NULL`, закрыть — мысль отображается с иконкой типа), «Отмена», «Применить» (доступна при корректном выборе на активной вкладке). Вкладки «Эмодзи» и «Иконки мыслей» — опциональные источники каркаса.

**Актуализация 0.12.1 (задача 4105bd6a).** На вкладке «Библиотека» добавлено поле выбора цвета символа; результат диалога расширен до `{ icon, kind, color }`; вкладка «Иконки мыслей» растянута на всю высоту.

**Актуализация 0.12.1 (задача 0f6c3e39, ошибка 3250096a).** Вкладка «Вложения» переведена на ОБЩИЙ компонент выбора вложения `editor/attachment-picker.ts` (была отдельная реализация `fileImageSourceTab`): список картинок сети с поиском, загрузкой из файла и отметкой текущего; строка поиска закреплена сверху, предпросмотр зафиксирован (не прокручивается со списком); пагинация по 200 записей. ## Добавление мысли через диалог: одиночное и пакетное

**Действующее лицо.** Пользователь на карте мыслей.

**Предусловия.** Есть фокус-мысль, под которую добавляется новая.

**Шаги.**

1. Вызов диалога добавления: правый клик по фокусу → «Добавить вниз»; либо drag-жест на нижнем эллипсе облачка; либо двойной клик по пустому месту зоны «верх-лево»/«низ» и пункт «Добавить мысль» в контекстном меню этих зон. Владелец вызова — фокус-мысль.
2. Ввод названия → живой поиск существующих мыслей: выбор строки найденной (клик или Enter) связывает существующую мысль; «Добавить» — создаёт новую.
3. Создание: `POST /networks/{nid}/thoughts { title, create_link: { direction: "parent", target_thought_id: focus_id, type_id } }` — `"parent"` значит, что фокус становится родителем новой мысли. Мысль и связь создаются одной транзакцией; сервер эмитит `thought.created` + `link.created`.
4. Пакетный режим: переключатель «несколько»; названия вводятся по одному с Enter и копятся в списке, либо вставляется многострочный буфер — по строке на мысль, для каждой строки ищется дубликат. `Ctrl+Enter` — множественная отправка (batch-эндпоинт или последовательные POST); `Ctrl+Shift+Enter` — то же, но первая мысль списка сразу становится фокусом холста.

**Результат.** Одна или несколько мыслей подвешены под фокусом (или связаны существующие); участники видят их в real-time.

**Ветвления.** Серверная транзакция и доставка события — сценарий «Создание мысли клиентом: от запроса до real-time доставки».

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор), REST API
- зависит от: POST /thoughts — создание мысли со связью-родителем, Диалог добавления и выбора мыслей

## Жизненный цикл черновика правки: отправка, дослать, восстановление

Черновик создаӑтся, как только пользователь начал править поле, и живӑт до подтверждӑнного сохранения.

**Отправка.** Каждое изменение поля сначала пишется в черновики со статусом `pending`. Есть связь — правка уходит на сервер немедленно, при успехе черновик помечается `sent` и удаляется. Связи нет — остаӑтся `pending`; при восстановлении соединения все `pending`-черновики отправляются в порядке создания. Если версия, на которой правили, разошлась с серверной — приходит конфликт версий, и он показывается пользователю, а не разрешается молча.

**Удаление после сохранения.** После успешного сохранения поля (заголовок мысли, постоянный комментарий) удаляются **все** черновики этого поля по ключу «профиль + сеть + сущность + поле», а не только последняя известная строка: черновик от debounce, чей идентификатор не успел вернуться к моменту сохранения, иначе останется мусором.

**Открытие сущности не включает режим правки.** Постоянный и хронологические комментарии всегда открываются в режиме просмотра; правка начинается только по двойному клику. Наличие черновика этого не меняет. «Мӑртвые» черновики, текст которых уже совпал с сохранӑнным, удаляются при открытии.

**Восстановление черновика заголовка никогда не затирает поле.** Черновик подставляется, только если поле ещӑ содержит сохранӑнный заголовок (пользователь ничего не печатал) и версия-основа совпадает с версией мысли. Версия ушла вперӑд — черновик устарел и остаӑтся только для повторной отправки. Поле уже изменено пользователем — черновик удаляется как устаревший.

**Дополнительные материалы**
- относится к подсистемам: Десктоп-клиент (Electron)
- применяется к: drafts — черновики правок на клиенте

## Идемпотентность изменяющих запросов через client_request_id

Каждый изменяющий запрос принимает `client_request_id` (UUID, генерирует клиент). Сервер сохраняет результат обработки на ограниченное время и на повторный запрос с тем же идентификатором возвращает **сохранённый ответ**, а не выполняет операцию заново.

Зачем: клиент и агент могут повторить запрос после таймаута или обрыва связи, не зная, дошёл ли первый. Без этого механизма ретрай порождает дубль мысли или связи.

Сохранённые ответы живут в системной БД с ограниченным TTL и чистятся фоновой задачей — это кэш дедупликации, а не журнал операций.

**Дополнительные материалы**
- относится к подсистемам: REST API, Ядро (доменный слой), MCP-сервер

## Изменение мыслесети AI-агентом через MCP

**Действующее лицо.** Внешний AI-агент с API-ключом.

**Предусловия.** Ключ действителен и не read-only; владелец ключа — участник мыслесети.

**Шаги.**

1. Агент вызывает изменяющий инструмент MCP.
2. MCP-сервер передаёт вызов **в тот же доменный слой**, что использует REST.
3. Ядро выполняет те же проверки и ту же транзакцию, что и для человека, и эмитит событие.
4. Агент получает ответ инструмента.
5. Участники сети видят изменение по WebSocket наравне с человеческими правками.

**Результат.** Изменение применено и неотличимо от правки человека — разница только в авторе события.

**Зачем этот сценарий важен.** Он — проверка главного инварианта архитектуры: если после правки агента участники не увидели изменение или поведение отличается от REST — где-то появилась логика в обход ядра.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер, Ядро (доменный слой), Real-time канал (WebSocket)
- зависит от: MCP-сервер

## Инициализация новой мыслесети

**Действующее лицо.** Пользователь, создающий мыслесеть; он же становится владельцем.

**Шаги клиента.**

1. Меню сети → «Создать сеть» → ввод имени (`display_name`) и описания.
2. `POST /api/v1/networks` — выполняются серверные шаги ниже.
3. Сеть появляется в списке «Мои сети» и открывается на мысли HOME.

**Шаги сервера.**

1. Генерирует идентификатор сети (UUID).
2. Создаёт каталог сети и внутри него каталоги вложений и снапшотов.
3. Открывает БД сети и выполняет миграции схемы. Одновременно создаётся **строка основы** в таблице слоёв — основа существует ещё до первой мысли.
4. В транзакции создаёт корневую мысль HOME: защищённая, корневая, актуальная. Слой явно не указывается — срабатывает значение по умолчанию (основа).
5. В системной БД добавляет запись в реестр сетей и членство создателя с ролью владельца.
6. Эмитит событие о создании сети.

**Результат.** Пустая сеть с единственной корневой мыслью, готовая к работе.

**Почему порядок важен.** Каталоги и основа создаются до первой записи данных; запись в системную БД делается после успешного создания БД сети — иначе в реестре появится сеть без файлов.

**Дополнительные материалы**
- относится к подсистемам: Хранилище (SQLite), Ядро (доменный слой), Слои изменений (подсистема), REST API
- зависит от: Раскладка каталога данных сервера, thoughts — таблица мыслей, layers — таблица слоёв изменений, networks — реестр мыслесетей и самоописание сети
- применяется к: Миграции схемы баз данных

## История посещения в статус-баре

Поле в статус-баре между именем сети и блоком счётчиков/зума: мини-облачка предыдущих мыслей + раскрывающийся список с остальной историей.

**Единая история для всех видов** (карта, структуры, дневник): попадают мысли, **открытые в редакторе**, независимо от экрана и способа открытия. Своих историй у видов нет. Связи в историю не попадают. Логика хранения и дедупликации — сущность `visit_history` (лимит 50, свежие в начале).

Облачка слева направо — самые свежие (облачко₁ — только что открытая); сколько помещается — по фактической ширине; лишние уходят в dropdown `[▾ N]` (при N=0 кнопки нет; пустая история — область скрыта или заглушка). Мини-облачко: иконка + заголовок (в панели до 24 символов с `…`), цвет/стиль мысли; помеченная на удаление — бледная с красной меткой-корзиной; заголовки всегда актуальные. Элементы dropdown — как строки поиска (неактивные `dim`, полные заголовки).

**Клик:** на карте — переход в фокус; в структурах/дневнике — открытие в редакторе без смены фокуса; открытая мысль выделяется ореолом, если видна на экране. Текущая мысль в списке не показывается — попадает в историю при открытии следующей.

**Перетаскивание:** элемент истории на холст — по правилам облачка (связь / Ctrl-переподчинение / зона → связь с фокусом; упорядочивание недоступно). Бросок мысли на панель истории — открыть её.

**Удалённые/неактивные:** удалённая на сервере автоматически уходит из истории по `thought.deleted` (автор — локально после DELETE); удаление фокуса переводит фокус к самой свежей существующей записи истории, иначе к HOME (то же — при `focus-lost`). Неактуальные — только при включённом `show_inactive`. Применение нового отбора в структурах историю не трогает.

**Помеченные на удаление** (задача 77923b49, коммит e55e5c6): облачко в истории скрывается и при выключенной настройке сети «Показывать содержимое корзины» (`show_trash`) — той же проверкой при рендере, что и неактуальные. Сама история посещений по-прежнему не чистится (см. выше).

**Контекстное меню (0.10.1, `b674fc1a`).** Чипы истории — и мини-облачка в полосе статус-бара, и строки дропдауна — вызывают общее контекстное меню мысли (`showThoughtContextMenu` из `canvas/context-menu.ts`); открытие из меню маршрутизируется по активному виду, как обычный клик. Новые места отображения облачка мысли обязаны делегировать этому же конструктору (сторож `cloud-context-menu.test.ts`).

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор)
- зависит от: visit_history — история открытых мыслей на клиенте

## Контекстное меню зоны и сортировка зон

Меню правого клика по зоне холста.

- **Добавить мысль** — только в зонах «верх-лево» (родительская) и «низ» (дочерняя): диалог добавления с владельцем — фокусом. В «верх-право» пункта нет (у фокуса может быть несколько родителей).
- **Сортировка** — для верх-лево, верх-право, низ: по алфавиту (возр/убыв), по дате создания (возр/убыв), по дате последнего просмотра (возр/убыв), ручной (только родители/дети; для родственников недоступен). Текущий пункт (по `focus.sorts[dir]`) отмечен галочкой; переезжает после ответа сервера.

**Ручная сортировка:** направление фиксировано `asc` (сверху вниз по порядку зоны); переключатель возр/убыв скрывается; сервер отвергает `PUT focus-preferences` с `sort='manual' && order='desc'` (`VALIDATION_ERROR`). При **первом** переключении на ручной клиент сначала коммитит текущий видимый порядок зоны в `user_focus_order` через `POST focus-order` (replace-семантика), затем вызывает `PUT focus-preferences` — иначе позиции `null` и индикатор номера скрыт у всех («ручной режим сломан»).

Порядок сохраняется **для мысли в фокусе** (per-focus); дефолт — по дате создания (возр). Ручной порядок меняется `Ctrl+Shift`-перетаскиванием (цель зелёная, FLIP после броска); обычное перетаскивание порядок не меняет.

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор)
- зависит от: user_focus_preferences — сортировка зон холста

## Линия связи на холсте

Отрисовка связи между облачками.

**Геометрия:** кубическая кривая Безье от нижней границы нижнего эллипса источника к верхней границе верхнего эллипса назначения (от внешних краёв эллипсов); контрольные точки уходят по нормалям точек крепления, изгиб ограничен. Бейдж-счётчик пачки и подписи типов — в середине кривой (t=0.5).

**Условие отрисовки (0.9.1, ошибка 16a77453):** линия проводится, если каждое из двух облачков видно ХОТЯ БЫ ЧАСТИЧНО — пересечение прямоугольника облачка с окном прокрутки его сектора больше пикселя. Облачко, полностью выехавшее за окно, линий не создаёт. Прежнее правило «только между полностью видимыми» обрезало бандлы у края прокрутки и делало линии ненаводимыми — заменено.

**Оформление:** штрих — градиент от цвета источника к цвету цели (собственный/типовой цвет фона мысли; нет цвета — стиль связи; один цвет — сплошная). Подпись типизированной линии читается **от фокуса**: исходящая из фокуса — `name_forward`, входящая — `name_reverse`; названия групп в разделе «Связи» редактора — так же от редактируемой мысли. Перекрытая в слое связь — штриховая фиолетовая `#8c9eff` (пачка помечается, если перекрыто хоть одно ребро; источник — `overridden.link_ids`).

**Слои и интерактив:** визуальные кривые и широкие hit-полосы лежат **под облачками** — интерактивна только открытая между облачками часть линии; выделенная при hover линия с подписью перерисовывается поверх облачков. Hover: подсветка цветом выделения, tooltip только с `name_forward`/`name_reverse` — иконок-счётчиков комментариев/хроники/вложений в нём нет; Ctrl+hover по tooltip — предпросмотр постоянного комментария связи, если он есть (комментария нет — предпросмотр не открывается); концевые эллипсы увеличиваются вдвое с оранжевой рамкой.

**Пачки:** несколько связей пары — линия толще с числом; hover — всплывающий список имён всех связей (общего комментария у пачки нет, поэтому Ctrl-предпросмотра нет); клик по элементу открывает связь в редакторе (фокус не меняется).

**Контекстное меню линии** (для пачки — после выбора связи): «Изменить свойства» (диалог стиля линии), «Изменить актуальность», «Инвертировать» (поменять источник/назначение; обратная уже есть — сообщение; облачко перетекает между зонами с FLIP), «Удалить» (диалог одиночного удаления).

Масштаб холста действует на кегль подписей, радиус бейджа и толщину линий.

**Корзина** (0.8.2, ошибка 355319d4). Ребро, помеченное на удаление, рисуется помеченным, а не пропадает: штрих — нейтральный приглушённый пунктир (`4 4`, прозрачность 0.45), подпись типа — с суффиксом «(в корзине)», попап — с пометкой «· в корзине», сама линия — с `<title>` «Связь в корзине». На трети кривой (t = 0.3, чтобы не перекрывать подпись типа и бейдж пачки) — кликабельная метка корзины (чёрный кружок с красной иконкой, как у помеченного облачка): клик открывает диалог связи «Вернуть из корзины»/«Удалить совсем». Помеченной линия считается, только если помечены ВСЕ рёбра направленной пачки — смешанная пачка (есть живое ребро) остаётся обычной; метка рисуется только у пачки из одного ребра.

## Переключение слоя сессии — полный ресинк через switched_at_seq

**Актуализация 0.8.4 (задача 09f19952).** `etn.changes.list` снят с постоянного набора MCP — это действие `changes.list` исполнителя `etn.ops` (read-only). Детали — `etn.guide { topic: "changes.list" }`.

`last_seq` глобален по сети, а фильтр видимости — по слою подписчика, поэтому после смены слоя кэш клиента невалиден целиком и дельта через границу переключения невозможна (она смешала бы два разных фильтра).

Сервер запоминает в `session_layers.switched_at_seq` (миграция 028) — `max_seq` сети на момент переключения — и использует его как границу, аналогично окну удержания:

- `resume` с `last_seq < switched_at_seq` → `resume.stale { last_seq: switched_at_seq }`, даже если позиция ещё внутри окна удержания;
- позициям `>= switched_at_seq` доверяют: подписчик, выполнивший ресинк после `layer.switched`/`layer.deleted`/`resume.stale`, продолжает с них и больше не получает stale по этой причине;
- `etn.changes.list` зеркалит правило: `truncated: true` при `since_seq < switched_at_seq`.

Переключение на уже текущий слой — не переключение: `switched_at_seq` не трогается, ресинк не форсируется.

**Дополнительные материалы**
- относится к подсистемам: Real-time канал (WebSocket), Слои изменений (подсистема)
- зависит от: session_layers — текущий слой клиентской сессии
- применяется к: Управляющие кадры layer.switched и layer.deleted, Событие layer.merged — одно событие на слияние, Кадр resume — догон пропущенных событий после обрыва

## Перетаскивание облачка по холсту

Перетаскивание облачка любой зоны и фокус-облачка мышью (не HTML5 DnD — модификаторы не блокируют старт). Модификаторы действуют в любой момент перетаскивания. У облачков родителей/детей есть зона-источник; облачка родственников и фокус-облачко ведут себя как элементы списков: бросок на мысль — связь, в зону родителей/детей — связь с фокусом в направлении зоны, на панель закреплённых — закрепление.

- **Без модификаторов:** бросок на верхний эллипс мысли Б → связь A→Б (A родитель); на тело/нижний эллипс Б → связь Б→A; в другую упорядочиваемую зону (родители↔дети) → развернуть направление связей с фокусом (типы сохраняются); в свою зону, в родственников или вне целей — ничего; **порядок мыслей не меняется**.
- **Ctrl/⌘** — «переподчинить» (не копировать): бросок на любую часть мысли Б делает Б единственным родителем перетаскиваемой (все родительские связи заменяются одной Б→A).
- **Ctrl+Shift** — ручное упорядочивание (только при сортировке зоны «ручной»): бросок на мысль Б ставит A перед Б, остальные сдвигаются; броски в пустое место — no-op. Эллипсы не задействуются, цель подсвечивается зелёной рамкой (у связей — синей); после броска облачка переезжают с FLIP-анимацией.

Существующие связи переиспользуются (повтор — no-op); обратная связь удаляется первой, её тип переносится на новую.

**Esc во время drag** отменяет жест: смещение сбрасывается, индикаторы скрываются, состояние очищается; повторные нажатия игнорируются; обработчик стоит выше глобального Esc (чтобы не закрыть открытый до drag диалог).

### Бросок в поля значений и панели отбора

Тем же pointer-жестом мысль можно бросить (задача d144ef71, ADR Единый pointer-канал перетаскивания мыслей):

- на поле значения свойства-связи в редакторе — станет его значением; перенос чипа из другого такого поля убирает мысль из источника, Shift — копирует;
- на поле «Родительские мысли» панелей отбора (Структуры, Хроника, отбор типа мысли, рецепт публикации) и в любое место панели «Структур» — добавит мысль в условие «Родительские мысли» (единая трактовка с панелью «Хроники»);
- мысль, поднятая из поля значения, брошенная на любое облачко вне поля, открывает диалог выбора свойства-связи и создаёт связь.

## Применение real-time событий клиентом и пропуск эха

Правила applier — как клиент применяет входящие события к локальному кэшу и UI:

- `created` — добавить в кэш, обновить холст/редактор при необходимости;
- `updated` — при `meta.version < local.version` игнор (устаревшее); иначе применить; сущность в фокусе/на холсте — обновить визуально; сущность открыта в редакторе с несохранёнными локальными правками — индикатор «изменено другим пользователем» + актуальная версия при следующем сохранении;
- `deleted` — убрать из кэша; если была в фокусе — возврат к HOME или последней доступной мысли;
- `reordered` — обновить сортировку зоны холста.

**Пропуск эха.** REST-ответ на изменяющий запрос уже несёт применённое состояние (новую версию), поэтому WebSocket-эхо того же события не применяется дважды. Клиент распознаёт эхо по `meta.request_id` = `Client-Request-Id` своего запроса либо по `actor.client_id` = собственному `Client-Id`. Совпадение — игнор или пометка «подтверждено».

### Инкрементальное применение к видимым спискам (2026-09-28, задача afcfb144, коммит 3b1967de)

Видимые списки «Структуры мыслей» и «Дневник» применяют чужие события к локальному снимку точечно, без полного перезапроса страницы. Очередь событий за окно дебаунса (400 мс «Структуры», 250 мс «Дневник») применяется ОДНИМ батчем → один reconcile/renderFeed на окно. Событие, которое нельзя применить уверенно, помечает окно как fallback: батч отбрасывается, выполняется полный путь (перезапрос страницы и раскрытых уровней). Таблица «событие → инкрементальное действие или fallback»:

| Событие | «Структуры мыслей» | «Дневник» |
|---|---|---|
| `thought.updated` | видимая мысль, правка без влияния на отбор/порядок → обновление `refs` + `update()` одной строки; иначе/невидима → fallback/игнор | fallback (чипсы показывают заголовки мыслей) |
| `thought.deleted` | убрать мысль из снимка (строка уходит removed-путём сверки) | fallback, если мысль — чипс загруженной записи |
| `thought.created` | fallback (вхождение в отбор не проверяется) | — |
| `link.updated` | нарисованное ребро, правка оформления → `edges` + перерисовка линий; смена концов/активности → fallback | fallback (подписи чипсов связей) |
| `link.deleted` | нарисованное ребро → убрать + перерисовать линии | fallback |
| `link.created` | fallback | — |
| `property-value.*`, каталог типов, `layer.merged`, `thought.reordered` | fallback | fallback |
| `comment.created` | — (постоянные комментарии ленту не наполняют) | хроно-запись хотя бы с одной привязкой, отбор только период/порядок → доар целей + вставка строки; иначе fallback/игнор |
| `comment.updated` | — | строка в ленте → слияние + доар `body_html`, переразрешение привязок; вне периода — удаление строки |
| `comment.deleted` | — | строка в ленте → удаление строки |
| `attachment.*`, настройки | fallback/без изменений | fallback/без изменений |

Границы fallback «Структур»: сортировка `alpha` + смена заголовка; текстовый отбор + синонимы; отбор по типам + тип мысли; скрытые неактуальные/корзина + `active`/`marked_for_deletion`. Событие по невидимой сущности игнорируется — состав отбора по нему не перестраивается. Локальные производители зовут полный путь сами (своё realtime-эхо до рендерера не доходит).

#### Уточнение fallback (2026-09-28, задача afcfb144, круг 1 проверки, фикс 0da22ff5)

Ряд границ полного пути уточнён после независимой проверки:

- `thought.updated` в «Структурах» уходит в полный путь также при сортировке `updated` (ключ `updated_at` — порядок сдвигает любая правка) и при смене `title`/`synonyms` ПОД АКТИВНЫМ ТЕКСТОВЫМ ОТБОРОМ (ключевые слова по умолчанию ищут по наименованию/синонимам — переименование может вывести мысль из отбора).
- `comment.updated` в «Дневнике» по записи, которой нет в загруженной ленте: полный комментарий читается точечным додаром (`etn.comments.get`) и строка вставляется, если запись попадает в применённый период (отбор без дополнительных критериев); при доп. критериях — полный путь. Правка даты переставляет строку по серверному порядку; локальная вставка помечает страницу к сверке (`pendingReconcile`).
- Снимок «Структур» поддерживается и когда вид НЕ показан (гейт по `activeView` снят) — `thought.deleted` вне экрана чистит `refs`/активную мысль, чтобы при возврате не оставалось устаревшей строки.

#### Додар направлений раскрываемости (2026-09-28, ошибка 989691da, фикс fd886daf)

Для `link.updated`/`link.deleted` в «Структурах» инкрементальный путь помимо точечного применения к `edges` и перерисовки линий помечает концы ребра к точечному додару направлений: `refreshDirections(ids)` перечитывает флаги раскрываемости через `fetchHierarchy` с тем же `link_filter` отбора и видимостью корзины (соседей ответа в снимок не сливает — сервер считает directions по всем активным связям мысли, включая невидимые, поэтому локальный пересчёт из `edges` неверен); сбой додара уводит в полный путь. Чистое оформление ребра (цвет/стиль/ширина) дадара не требует; смена концов, `active`, а также `type_id` под активным фильтром — полный путь.

#### Ревизия 2026-09-28 (ошибки 8da8e6b4 и 0af1d810, коммит 3afe73f2)

Границы полного пути расширены: пометка ребра корзиной (смена `marked_for_deletion`) при скрытой «корзине» и смена `type_id` при активном `link_filter` — всегда полный путь. Как следствие, точечный додар направлений выполняется только для `link.deleted`; для `link.updated` оба прежних триггера додара стали полным путём и мёртвый код удалён.

#### Ревизия 2026-09-28 (ошибка 8e702d8c, коммит ee2968af)

Полный путь realtime в «Структурах» выполняется ТОЛЬКО когда вид показан. При скрытом виде fallback-событие (а также сбой точечного додара `refreshDirections`) не запускает `reloadAll()`, а помечает снимок «грязным» (`fullRefreshPending`); перезагрузка страницы и раскрытых уровней идёт при следующем показе вида. Инкрементальные события по-прежнему поддерживают снимок вне экрана (гейт по `activeView` не возвращается). Отложенная пометка сбрасывается при полной инициализации снимка (смена сети/вкладки) — там снимок и так грузится целиком.

**Дополнительные материалы**
- относится к подсистемам: Real-time канал (WebSocket), Десктоп-клиент (Electron)
- зависит от: Конверт события real-time
- применяется к: События real-time об изменении каталога

## Редактор мысли/связи

Панель редактирования выбранной мысли или связи. По умолчанию справа; переключается: слева / сверху / снизу / скрыто (`ui_state.editor_position`). По умолчанию в редакторе — мысль в фокусе; клик по связи на холсте — содержимое связи (фокус не меняется).

**Заголовок панели:** «Мысль» или «Связь». Для помеченной на удаление мысли — значок корзины перед словом «Мысль» (ярко-красный на чёрном кружке, как на облачке) и поле «Название» зачёркнутым, оставаясь редактируемым. Лейблов у полей нет — placeholder.

**Шапка мысли:** квадратик иконки (нет иконки — плейсхолдер; клик — диалог выбора иконки); заголовок крупный (1.5×), жирный, авто-высота до 5 строк; синонимы (однострочное, запятая — разделитель); тип ▾ — поле одиночного выбора типа (пусто — ввод с живым поиском и пункт «без типа»; заполнено — облачко типа прямо в поле, ввод недоступен, крестик очищает; кнопка «…» открывает диалог выбора одного типа); ⚙ (диалог настроек мысли); чекбокс «актуально» (для HOME заблокирован). При смене типа меняются только незаданные вручную визуальные настройки (NULL наследуются от нового типа), иконка, стили, цвета и состав свойств (прежние скрываются, но не очищаются).

**Шапка связи:** строк иконки/заголовка/синонимов нет; тип связи ▾ — то же поле одиночного выбора (пусто — ввод с живым поиском и «без типа»; заполнено — облачко типа связи в поле, ввод недоступен, крестик очищает, «…» — диалог выбора одного типа); ⚙ (настройки связи: цвет/штрих/толщина + «Сброс»), чекбокс «актуально».

**Явная навигация в помеченную мысль и команды корзины** (задача ff991fb2, коммит `0a10755`, 0.8.2). Переход в помеченную мысль по явному указанию (wiki-ссылка, deep-link) разрешён и при выключенной настройке «Показывать содержимое корзины» — ссылки не должны умирать молча. Чтобы это было очевидно и давало выход, метка корзины в заголовке панели — кнопка: клик открывает общий диалог восстановления/удаления (`openThoughtDeleteDialog`, как метка на карте). Поле «Название» при этом остаётся зачёркнутым и редактируемым.

**Инкрементальная смена открытой сущности** (ревизия 2026-09-28, задача 90b2256e, коммит `8158da25`, 0.10.2). Смена открытой сущности в редакторе не пересоздаёт каркас панели: полоса вкладок с кнопками, хост вкладок и overflow-механика сохраняются; заменяются только шапка и содержимое активной вкладки, счётчики «(N)» перечитываются по новой сущности. Переход «загрузка → загружено» строит каркас ровно один раз (двойной пересборки нет). Прокрутка при смене сущности не сохраняется — у другой сущности другой контент (сознательное решение, зафиксировано в модуле `editor.ts`). Полная пересборка панели остаётся для смены вида сущности (мысль ↔ связь), смены дока, слоя и первой отрисовки.

**Уточнение (круг 1, коммит `0df8b9b0`, 0.10.2).** При смене открытой сущности того же вида и того же типа поля шапки (иконка, «Название», «Синонимы», «Тип», «актуально») не пересобираются — обновляются только их значения на месте; структурно иная шапка (мысль ↔ связь, «загрузка → загружено», смена типа) по-прежнему пересобирается. Содержимое уже построенных вкладок перечитывается под нового владельца без сброса кэша вкладок: «Свойства» сверяет строки по ключам привязок (keyed), прочие вкладки пересобирают содержимое внутри того же узла панели. Устаревший асинхронный загрузчик счётчика «(N)» не перезаписывает счётчик новой сущности.

**Уточнение (ошибка 253505a6, коммит `d07fa954`, 0.10.2).** При смене открытой сущности того же вида, когда полная новая цель ещё не загружена (карта, клавиатурная навигация, список мыслей связи, миникарта, редактор значения — экраны, открывающие мысль по одному id и подгружающие её сами), редактор УДЕРЖИВАЕТ на экране прежнюю показанную сущность и НЕ показывает загрузочную заглушку: шапка и вкладки не разбираются, повторной сборки нет; переход «прежняя → новая» выполняется одним приёмом, когда сущность приходит. Это выравнивает карту с экранами «Структуры»/«Дневник»/«События», которые передают редактору уже загруженную сущность. При сбое загрузки новой сущности цель редактора возвращается к прежнему состоянию (редактор не «залипает» на новой цели с прежним содержимым).

## Редактор постоянного комментария

Вкладка «Комментарий» редактора (до 0.8.1 называлась «Основное»; обёртки-группы «Комментарий» больше нет — вкладка целиком занята полем). Содержимое сразу HTML-рендером (единый `@etn/markdown`); пустой текст — пустое поле без заглушек.

**Режимы.** Двойной клик — редактирование на CodeMirror 6 (подсветка markdown, Undo/Redo, автопродолжение списков, перенос строк; высота от 5 строк). Клик вне поля или `Ctrl+Enter` — сохранить и вернуться к просмотру; `Esc` — отмена.

**Live preview.** Блочные элементы (заголовок, цитата, код, картинка, таблица) показывают исходник, пока каретка внутри блока; внутристрочные — пока каретка внутри или у границ. Символы разметки при редактировании не скрываются.

**Типографика режимов единая:** интерфейсный шрифт (не моно) для текста, общий моношрифт для кода, размеры h1–h6, рамки/цвет цитат, плашка inline-кода, единый акцент ссылок (без подчёркивания до hover). `Ctrl+колесо` масштабирует виджеты-блоки (общий множитель markdown-полей, хранится на сеть — независимо от масштаба холста).

**Выделение текста** — акцентный цвет темы с альфой (`--selection-bg`: светлая `rgba(47,111,237,0.4)`, тёмная `rgba(91,140,255,0.5)`), одинаково в просмотре и редакторе; текст, подсветка кода и ссылки сохраняют цвета. Не путать с `--selection` (teal-рамка выделения облачек).

**Wiki-ссылки.** Ввод `[[` + текст — выпадающий список мыслей (по названиям и синонимам); выбор вставляет ID-форму `[[#<id>]]` (имя подтягивает резолвер), алиас — вручную после `|`. Клик по ссылке открывает мысль (карта — фокус+редактор; структуры — активация, нет на экране — вопрос «Переключиться на карту?»; неактуальная при скрытии — уведомление; не найдена — уведомление).

**ID-based wiki-ссылки:** в редакторе виден только `#<id>` скрыт за виджетом имени; формы `[[#<id>]]`, `[[#<id>|alias]]`, `[[n:<net>#<id>]]`. Автокомплит вставляет `[[#<id>]]`. Normal-mode — вся последовательность одним виджетом (alias приоритетнее); edit-mode — виджет снимается, но `#<id>` остаётся виджетом с именем; токен atomic (Backspace/Delete целиком, `←`/`→` перепрыгивают), имя выделено `cm-wiki-id-edit`; удалённая мысль — серый курсив; копирование из редактора сохраняет исходник с `[[#<id>]]`. Полная спецификация ID-ссылок — 12-wiki-id-refs.

**Legacy-ссылки** `[[Имя|alias]]` работают по имени; правый клик — «Обновить формат на `[[#<id>]]`» (резолюция поиском по названиям, точное совпадение приоритетно; иначе первый кандидат).

**Код:** подсветка (highlight.js в просмотре, CM в редакторе), длинные строки переносятся по ширине поля во всех режимах. Блоки `mermaid` рендерятся диаграммами (и в просмотре, и в редакторе); ошибка синтаксиса оставляет код; широкая диаграмма скроллится внутри блока.

**Картинки:** размер в alt-тексте — `![alt|600px]`, `![alt|600x400]`, `![alt|50%]`; без размера — по ширине поля. `Ctrl+V` в редактировании (и в хронологии) — файл сохраняется на сервере (`networks/<nid>/attachments/`), создаётся вложение, у курсора `![имя](etnimg://…)`.

**Авто-упоминания** (в HTML-просмотре): слова, совпадающие с названием мысли (в т.ч. отдельной частью составного имени) или синонимом (включая wildcard), подчёркиваются пунктиром; клик — меню «Перейти к „…“» и «Вставить ссылку на „…“» (заменяет текст на `[[имя|текст]]`). Совпадений несколько (до 5) — каждый своим пунктом. Мысль в своём комментарии не подчёркивается (в «Хронике» исключается первая мысль-привязка). Текст внутри ссылок не проверяется. Неактивные кандидаты — только при «Показывать неактуальные», приглушённо.

**Контекстное меню** (в режиме редактирования): «Вставить текст шаблона из типа мысли» — когда у мысли есть тип с непустым `comment_template_md`; вставка в позицию курсора как есть; в view-режиме поле сначала переключается в edit с подставленным текстом.

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор), Markdown-рендерер
- зависит от: Markdown-рендерер
- применяется к: Доступ к кросс-сетевым и внешним ссылкам, Команды поля комментария действуют во всех местах его переиспользования, Позиция курсора при входе в редактирование соответствует месту клика в просмотре, HTML-комментарии скрыты в просмотре и публикациях, Сочетания клавиш применяются по текущему элементу (фокус), Legacy wiki-ссылки: без sweep и автопереименования, Резолюция ID-ссылок в режиме просмотра комментария

## Слой изменений — свойство таба, а не клиента

Серверная сессия слоёв — одна на клиента (ключ «пользователь + `Client-Id`»). Табов же несколько, и они могут работать в разных слоях, поэтому **выбранный слой — свойство таба** и хранится локально в его строке (`layer_id`; NULL — основа).

**Порядок при активации таба обязателен.** Рендерер сначала переключает серверную сессию на слой таба, затем грузит список слоёв и перекрытия — и только после этого читает фокус. Все последующие чтения и записи этого таба идут в его слое. Нарушение порядка даёт чтение из чужого слоя — баг, который выглядит как «пропали правки».

**Протухший слой** (удалён из другого сеанса) ремонтируется сбросом `layer_id` в NULL. Управляющий real-time кадр об удалении слоя делает то же самое с живой сессией.

**Дополнительные материалы**
- относится к подсистемам: Десктоп-клиент (Electron), Слои изменений (подсистема)
- зависит от: POST /layers/{id}/select — выбор текущего слоя сессии
- применяется к: tabs — открытые табы клиента

## Создание мысли клиентом: от запроса до real-time доставки

**Действующее лицо.** Человек в десктоп-клиенте.

**Предусловия.** Живое соединение с сервером; пользователь — участник мыслесети.

**Шаги.**

1. Клиент отправляет запрос создания мысли в REST API, приложив `client_request_id`.
2. Ядро валидирует вход и проверяет права на сеть.
3. Запись выполняется **одной транзакцией** в БД этой мыслесети; в той же транзакции инкрементируется счётчик `network_seq` в `_system.db` — событие получает свой `seq`.
4. После коммита транзакции ядро эмитит событие создания в `EventEmitter` по `network_id`.
5. WebSocket-шлюз доставляет событие подписчикам с фильтрацией: `audience=user` — только подключения того же `user_id`; `audience=network` — все участники **за вычетом фильтра видимости по слою подписчика**; источник по `actor.client_id` эхо не получает.
6. Клиент-автор получает успешный ответ с созданной мыслью.
7. Остальные клиенты применяют событие к текущему состоянию холста и редактора — без перезагрузки.

**Результат.** Мысль создана и видна всем участникам сети.

**Ветвления и ошибки.** Событие эмитится только после успешной транзакции — при откате подписчики ничего не видят. Повтор запроса с тем же `client_request_id` вторую мысль не создаёт, а возвращает сохранённый ответ.

**Дополнительные материалы**
- относится к подсистемам: REST API, Ядро (доменный слой), Хранилище (SQLite), Real-time канал (WebSocket)
- зависит от: REST API, Конверт события real-time

## Создание пользователя администратором

**Действующее лицо.** Администратор сервера.

**Шаги.**

1. Меню пользователя → «Администрирование» → «Пользователи» → «Добавить».

**Ветвления.** Удаление пользователя — каскадное, но запрещено, пока он владеет хотя бы одной сетью: сначала передай владение.

**Дополнительные материалы**
- относится к подсистемам: REST API, Аутентификация и права доступа

## Создание типа мысли или связи

**Действующее лицо.** Участник сети (типы — администрирование внутри мыслесети, отдельной роли не требует).

**Шаги.**

Тип мысли — как прежде, через менеджер типов:

1. Раздел «Типы мыслей» → «Новый тип»: имя, иконка, цвет и стиль по умолчанию.
2. Свойства добавляются на вкладке «Свойства» редактора типа — выбором из реестра «Свойства и связи» или созданием нового через единый диалог «Свойство / связь» (таблица стороны предзаполнена текущим типом).
3. Сохранение: `POST /thought-types` + каскад `POST /type-properties`.
4. Тип появляется в выпадающем списке «Изменить тип» у мыслей.

Тип связи (0.8.1) — через свойство-связь, отдельного шага создания больше нет:

1. Пользователь открывает «Свойства и связи» (меню «Мыслесеть») или вкладку «Свойства» редактора типа.
2. ## Сценарий: совместное редактирование — захват и запрет записи

**Действующие лица.** Два участника сети (клиент и/или AI-агент).

**Предусловия.** Оба подключены; никто не редактирует объект O.

**Шаги.**

1. Участник A открывает редактирование объекта O (правка комментария / диалог настроек / диалог типа / диалог удаления) → клиент шлёт `POST /locks` → сервер создаёт захват, рассылает `edit.acquired`.
2. Клиент B получает событие: значок 🔒 на объекте, поля редактора заблокированы.
3. B пытается записать O (UI заблокирован; напрямую REST/MCP) → `409 LOCKED` с именем держателя.
4. B читает O и его связи — без ограничений.
5. A завершает редактирование (закрытие/сохранение/отмена) → `DELETE /locks/{id}` → `edit.released` → у B индикация снимается, запись доступна.

**Ветвления.** A потерял связь — разрыв WebSocket сбрасывает его захваты (`edit.released`); клиент A «завис» — участник B выполняет «Снять все блокировки» A (`POST /locks/clear` → `edit.cleared`).

**Дополнительные материалы**
- относится к подсистемам: REST API, Пользовательский интерфейс (холст и редактор), Real-time канал (WebSocket)

## Увидеть работы версии на карте мыслей

**Действующее лицо.** Пользователь, ведущий разработку по версиям.

**Предусловия.** У типа «версия» заведён отбор «Работы версии» с условием по свойству «версия» = `$thought` и пометкой «по умолчанию».

**Шаги.**

1. Пользователь переводит мысль-версию 0.7.3 в фокус.
2. Клиент получает окрестность мысли и эффективный набор отборов её типа; полоса под фокусом показывает «Потомки», «Работы версии», «+».
3. Отбор «Работы версии» помечен по умолчанию — клиент сразу исполняет его для мысли 0.7.3.
4. Сервер подставляет `$thought` = id версии 0.7.3 и выполняет отбор мыслей по свойству.
5. Нижняя зона показывает задачи и ошибки, запланированные на 0.7.3, — облачками, как потомков.
6. Пользователь нажимает «Потомки» и видит обычных детей версии; выбор действует, пока версия в фокусе.
7. Пользователь переводит в фокус версию 0.6.6 — тот же отбор без единой правки отдаёт работы 0.6.6.

**Результат.** Планирование версии просматривается с карты, без перехода в «Структуры мыслей» и без ручной настройки критериев под каждую версию.

**Ветвление.** У версии не заполнено свойство «версия» ни у одной работы — зона показывает «Ничего не найдено». Отбор ссылается на свойство, отключённое от типа, — зона объясняет, какой токен не разрешился.

**Тот же маршрут у агента:** `etn.thoughts.get` версии → в `meta.views` виден отбор с описанием → `etn.views.run` → список работ.

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор), REST API, Ядро (доменный слой)
- зависит от: POST /thoughts/{id}/views/{view}/run — исполнение отбора относительно мысли, etn.views.run — исполнение отбора типа агентом, Полоса отборов под мыслью в фокусе

## Удаление мысли: проверка блокировок и корзина

**Действующее лицо.** Пользователь.

**Шаги.**

1. Контекстное меню мысли → «Удалить» → клиент запрашивает `GET /thoughts/{id}/deletion-check`.
2. Блокировок нет → диалог с кнопками «Удалить совсем» и «Поместить в корзину». «Удалить совсем» → `DELETE /thoughts/{id}` — мысль сразу исчезает с холста (каскадом уходят связи, комментарии, вложения, значения свойств).
3. Блокировки есть (например, мысль используется в свойстве другой мысли) — «Удалить совсем» недоступна: показан текст блокировки и ссылка «Открыть использование…».
4. Открывается панель использования; в группе «Используется в свойствах» — ссылающаяся мысль. «Очистить свойство» в её строке обнуляет значение.
5. Повторное «Удалить» — блокировок больше нет, физическое удаление доступно.
6. «Поместить в корзину» — мысль остаётся на холсте со значком 🗑 (помечена на удаление).
7. Позже: меню сети → «Корзина» — список помеченного; «Удалить всё, что возможно» → `POST /trash/purge` физически удаляет всё незаблокированное.

**Результат.** Мысль либо физически удалена, либо помечена и вычищена через корзину; блокировки показаны пользователю, а не обойдены молча.

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор), REST API
- зависит от: Диалог «Корзина», DELETE /thoughts/{id} — физическое удаление мысли и его каскад, GET /trash и POST /trash/purge — корзина мыслесети, deletion-check — проверка возможности удаления мысли или связи, Диалог одиночного удаления

## Управление участниками сети: приглашение, владение, исключение

**Действующее лицо.** Владелец мыслесети.

**Предусловия.** Приглашаемый — уже существующий пользователь сервера (ключ ему выдан администратором).

**Шаги.**

1. Меню сети → «Участники сети» → «Добавить участника» → выбор из существующих пользователей сервера.
2. `POST /networks/{id}/members { user_id }` — пользователь становится участником: видит сеть в своём списке, получает полный доступ к данным сети. Онлайн-участники получают событие `member.added`.
3. Передача владения: в списке участников выбрать участника → «Сделать владельцем» → `PATCH /networks/{id}/members/{uid} { role: "owner" }` — в одной транзакции: новый владелец, бывший становится `member`. Всем участникам улетает `member.role_changed`.
4. Исключение: «Исключить» напротив участника → `DELETE /networks/{id}/members/{uid}` — участник теряет доступ.
5. Если исключённый в этот момент онлайн в сети, его клиент получает `member.removed` со своим `user_id` и закрывает сеть с уведомлением.

**Результат.** Состав участников и владелец сети изменены, изменения доставлены участникам в real-time.

**Дополнительные материалы**
- относится к подсистемам: REST API, Аутентификация и права доступа, Real-time канал (WebSocket)
- зависит от: /networks/{id}/members — участники сети и передача владения, События real-time о сети и членстве

## Управляющие кадры layer.switched и layer.deleted

Точечные управляющие кадры протокола — адресуются ровно тем подключениям, чья сессия изменилась, а не рассылаются по аудитории (ни `network` — все участники, ни `user` — все клиенты пользователя — не соответствуют одной клиентской сессии):

- `layer.switched { layer: { id, title } }` — при переключении слоя сессии (`POST /layers/{id}/select`): фильтр живых подключений той же сессии переключается на месте;
- `layer.deleted { layer: { id, title } }` — при удалении слоя: подключения на удалённом слое или его потомке пересаживаются на родителя удалённого.

Слой подключения — это слой сессии `(user_id, client_id)` из `session_layers`, разрешаемый при подключении и повторно при позднем кадре `hello` (клиент мог не передать `Client-Id` в момент upgrade).

Кадры не несут `seq` и `network_id`, поэтому старый клиент без поддержки слоёв безопасно их игнорирует (не проходят валидацию конверта события). После любого из кадров кэш клиента невалиден целиком — обязателен полный ресинк.

**Дополнительные материалы**
- относится к подсистемам: Real-time канал (WebSocket), Слои изменений (подсистема)
- зависит от: session_layers — текущий слой клиентской сессии, DELETE /layers/{id} — удаление слоя вместе с поддеревом, POST /layers/{id}/select — выбор текущего слоя сессии
- применяется к: Переключение слоя сессии — полный ресинк через switched_at_seq

## Черновик в слое: правка, отличия, слияние

**Действующее лицо.** Участник сети с правом правки.

**Шаги.**

1. Меню слоёв → «Создать новый слой…»: название и комментарий (например, «реструктуризация раздела X») → «Создать». Заголовок меню меняется на имя слоя — все дальнейшие правки идут в слой, основа не затрагивается.
2. Пользователь правит мысли и связи (смена типа связи, перецепка, добавление мыслей, переупорядочение) — перекрытые мысли и связи помечаются на холсте пунктирными рамками и линиями.
3. «Отличия от „Основа“…» (ревизия 0.10.3, `52c776f1`): единая лента различий, сгруппированная по секциям (добавлены / удалены / сменился тип / сменился родитель / порядок / перекрытые мысли и связи), с догрузкой при прокрутке; клик по перекрытой мысли открывает отдельный диалог её текстового диффа. До 0.10.3 — вкладки «Связи»/«Содержание» с текстовым диффом всех документов.
4. Если другой участник успел изменить в основе строку, которую правил слой, «Слить … в „Основа“…» отклоняется **целиком** со списком расхождений; пользователь согласовывает правки и повторяет слияние.
5. Успешное слияние показывает отчёт: перенесённые строки, свёрнутые пачки правок порядка, резервный слой для отката. Основа обновилась, слой опустел, пометки перекрытий исчезли. Слой остаётся выбранным — его можно удалить (основа не пострадает) или продолжить в нём новую серию правок.

**Результат.** Черновые правки проверены и влиты в основу одним слиянием; конфликт показан явно и молча не разрешается.

**Ветвления.** Участники получают событие `layer.merged` и полный ресинк; параллельные табы и удаление слоя из другого сеанса — см. связанные мысли.

**Дополнительные материалы**
- относится к подсистемам: Слои изменений (подсистема), Пользовательский интерфейс (холст и редактор)
- зависит от: GET и POST /layers — список слоёв и создание слоя, Меню слоёв, POST /layers/{id}/merge — слияние слоя с родителем, GET /layers/{id}/diff — структурный дифф слоя против родителя

## Эллипсы облачка: создание связи drag-жестом

Верхний эллипс облачка (на верхней рамке) — индикатор входящих связей и точка drag для создания **родителя**; нижний — исходящих и точка для **ребёнка**.

Жест: `mousedown` в любой точке эллипса → перетаскивание → `mouseup` открывает диалог добавления мысли в соответствующем направлении; «бросить» на другую мысль — связать с существующей. Жест всегда видим: курсор-прицел (crosshair), эллипс подсвечен, облачко-цель обведено, от эллипса к курсору — пунктирная линия будущей связи. У облачков зон native HTML5-drag на время жеста подавляется.

После броска связь создаётся немедленно; холст и раздел «Связи» редактора обновляются без realtime (действующему клиенту эхо не приходит — обновляет себя сам).

**Hover на эллипсе:** эллипс увеличивается вдвое по высоте, рамка оранжевая и на 1 px толще; все видимые связи соответствующего направления (верхний — входящие, нижний — исходящие) перерисовываются поверх облачков цветом выделения. Снимается при уходе курсора.

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор)
