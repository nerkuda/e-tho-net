# 09. Пользовательские сценарии

> Сценарии сгруппированы по темам. Все приведенные сценарии входят в MVP, если
> явно не помечено «(будущее)». Каждый сценарий связан с API/UI по ссылкам.

## A. Управление мыслесетями и доступом

### A1. Создание мыслесети
**Кто:** любой участник сервера.
1. Меню сети → «Создать сеть» → ввод имени (display_name) и описания.
2. `POST /api/v1/networks` → сервер создаёт каталог `networks/<id>/`, `data.db`,
   корневую мысль «HOME» (`is_protected=1, is_root=1`), добавляет создателя в
   `network_members` с ролью `owner`.
3. Сеть появляется в списке «Мои сети», открывается на мысли HOME.

### A2. Предоставление доступа (владелец)
**Кто:** владелец сети.
1. Меню сети → «Участники сети» → «Добавить участника».
2. Выбор из существующих пользователей сервера.
3. `POST /api/v1/networks/{id}/members { user_id }` → пользователь становится
   участником, видит сеть в своём списке, получает полный доступ к данным сети.
4. Участник получает real-time-событие `member.added` (если онлайн).

### A3. Передача владения
**Кто:** владелец сети.
1. В списке участников → выбрать участника → «Сделать владельцем».
2. `PATCH /api/v1/networks/{id}/members/{uid} { role: "owner" }` → в одной
   транзакции: новый владелец, бывший — `member`.
3. Событие `member.role_changed` улетает всем участникам.

### A4. Подключение с нового клиента
**Кто:** пользователь.
1. Первый запуск клиента → экран приветствия → ввод URL сервера + API-key.
2. `GET /api/v1/me` → проверка; успех → профиль сохраняется в `server_profiles`
   (ключ зашифрован через safeStorage).
3. Загрузка списка сетей, выбор сети, фокус на последней просмотренной мысли.

### A5. Исключение участника (владелец)
1. «Участники сети» → «Исключить» напротив участника.
2. `DELETE /api/v1/networks/{id}/members/{uid}` → участник теряет доступ.
3. У исключённого клиента, если он онлайн в сети, приходит `member.removed` с его
   `user_id` → клиент закрывает сеть с уведомлением.

### A6. Администрирование пользователя (админ)
**Кто:** администратор.
1. Меню пользователя → «Администрирование» → «Пользователи» → «Добавить».
2. Заполнение формы → `POST /api/v1/admin/users` → ответ содержит **API-key один
   раз**.
3. Админ копирует ключ кнопкой «Копировать» и передаёт новому пользователю.

## B. Навигация

### B1. Навигация по холсту
1. Открыта сеть, фокус на мысли X.
2. Клик по мысли-ребёнку в нижней зоне → она переходит в фокус:
   - `POST /networks/{nid}/thoughts/{child_id}/focus` →
     обновляется `last_viewed_at`, `thought_views`.
   - Сервер возвращает новый набор соседей (parents/children/siblings).
3. Редактор переключается на новую фокус-мысль.

### B2. Сортировка зон
1. Правый клик по зоне (например, нижней) → «Сортировка» → выбор порядка.
2. Сохраняется per-focus (для текущей фокус-мысли) в `ui_state.canvas_sort`.
3. Для родственников ручной порядок недоступен.

### B3. Поиск мысли
1. `Ctrl+F` → строка поиска **восстанавливает** предыдущий запрос (текст + опции
   + результаты).
2. Ввод → `GET /networks/{nid}/search?q=...&scope=all&type_id=...`.
3. Группы результатов разворачиваются. Клик → фокус.

### B4. Возврат к предыдущей мысли (история фокуса)
1. Пользователь перемещался по холсту: A → B → V → … Каждая бывшая в фокусе
   мысль (кроме текущей) попадает в историю (локально, L4).
2. В статус-баре отображаются 3 облачка последних из истории + кнопка `▾ N` для
   остальных.
3. Клик по облачку в истории → обычная смена фокуса: выбранная мысль становится
   фокусом (и удаляется из истории), текущая попадает в историю.
4. Метаданные облачек для истории клиент подтягивает через
   `POST /networks/{nid}/thoughts/resolve` или берёт из локального кэша.

Подробно: [11-settings-and-state.md](11-settings-and-state.md), п. 2.3.

## C. Создание мыслей и связей

### C1. Добавление мысли в связь (через диалог)
1. Правый клик по фокусу → «Добавить вниз» → диалог (см. [08-ui-spec.md](08-ui-spec.md),
   п. 4).
2. Ввод названия → живой поиск существующих → выбор «использовать» или «создать
   новую».
3. `POST /networks/{nid}/thoughts { title, ..., create_link: { direction: "child",
   target_thought_id: focus_id, type_id } }`.
4. Сервер создаёт мысль + связь в одной транзакции, эмитит `thought.created` +
   `link.created`.

### C2. Пакетное добавление
1. В диалоге переключатель «несколько».
2. Ввод по одной с Enter → накапливаются в верхнем списке.
3. Альтернатива: вставка многострочного буфера → автоматический парсинг по
   строкам, для каждой строки — поиск дубликата.
4. `Ctrl+Enter` → множественный вызов (либо серверный batch-эндпоинт, либо
   последовательные `POST`).

### C3. Перетаскивание ссылки/файла на холст
1. Drag URL/файла из браузера/эксплорера.
2. Допустимые цели: верх-лево (новый родитель), низ (новый ребёнок). Верх-право
   запрещён.
3. На `drop`: создаётся мысль с заголовком (имя файла; для URL — пустой, т.к.
   клиент не ходит в сеть на MVP), к ней автоматически добавляется вложение.

### C4. Связь через эллипс (drag)
1. `mousedown` на нижнем эллипсе фокуса → тащить → `mouseup` → диалог добавления
   ребёнка (C1). Бросить на существующую мысль — `POST /links` напрямую.

### C5. Типизированная связь между существующими мыслями
1. Из редактора связи (клик по линии на холсте) → выбор типа.
2. `PATCH /networks/{nid}/links/{id} { type_id }` → обновляется подпись на линии.

### C6. Перетаскивание облачка (08-ui-spec.md §2.3.1)
1. Обычный drag: бросок на мысль → создать связь (верхний эллипс — A→Б,
   тело/нижний эллипс — Б→A); бросок в другую зону (родители↔дети) → разворот
   направления связей с фокусом. Порядок мыслей не меняется.
2. `Ctrl`+drag на мысль → переподчинение: все родительские связи мысли
   заменяются одной с мыслью, на которую бросили (`GET /thoughts/{id}/links`,
   `DELETE /links/{id}`, `POST /links`). Копия не создаётся.
3. `Ctrl`+`Shift`+drag (только при сортировке «ручной»): бросок на мысль →
   встать перед ней (`PUT /thoughts/{id}/focus-order`); бросок в пустую часть
   зоны — no-op. Место вставки показывается живым превью (зазор +
   раздвигание облачков), после броска облачка переезжают с FLIP-анимацией.

## D. Редактирование содержания

### D1. Постоянный комментарий
1. В редакторе → группа «Постоянный комментарий» → «Редактировать».
2. Изменение markdown → сохранение → `POST/PATCH /comments` → сервер хранит
   `body_md` и `body_html`.
3. В облачке мысли индикатор `📝` становится ярким.
4. Событие `comment.updated` улетает остальным.

### D2. Хронологический комментарий
1. Группа «Хронологические комментарии» → «Добавить» → диалог (заголовок, текст,
   С = По = сегодня).
2. `POST /comments { kind: "chronological", ... }` → создаётся, дата
   редактируется.
3. В облачке `📅 N` обновляется.

### D3. Вложение
1. Перетащить файл/ссылку в зону вложений ИЛИ кнопка «Добавить вложение».
2. Диалог (URL/путь, заголовок, комментарий) → `POST /attachments`.
3. Для картинки — превью, для прочего — иконка.

### D4. Изменение типа и свойств
1. Контекстное меню мысли → «Изменить тип» → выбор (или выпадающий «тип ▾» в шапке).
2. `PATCH /networks/{nid}/thoughts/{id} { type_id }`.
3. Меняются только визуальные поля, не заданные вручную (`NULL`): иконка, стиль
   шрифта, цвета начинают наследоваться от нового типа (02-data-model.md §3.1.1).
   Ручные (`не-NULL`) настройки сохраняются.
4. В редакторе появляется таблица свойств этого типа. Свойства прежнего типа
   скрываются, но их значения **не очищаются** — при возврате прежнего типа они
   снова отображаются.
5. Заполнение значений → `PUT /networks/{nid}/thoughts/{id}/properties/{key}`.
   Для `value_type=thought_ref` — выбор мысли через тот же диалог поиска.

### D5. Изменение активности
1. Контекстное меню мысли/связи → «Изменить активность».
2. `PATCH ... { active: 0 }`.
3. Если у получателя выключено «показывать неактуальное» — сущность исчезает с
   его холста/из поиска; у остальных, с включённой опцией — остаётся приглушённой.

### D6. Визуальные свойства (диалоги в шапке редактора)
1. Иконка — через **диалог выбора иконки** (§6.8): эмодзи / файл (оригинал
   загружается во вложения мысли, иконкой становится превью ≤256 КБ,
   `Ctrl+наведение` показывает оригинал — L16) / URL. Цвета текста/фона и стиль
   шрифта — через **диалог настроек** (§6.9) с кнопкой «Сброс» (убирает ручные
   настройки → `NULL`).
2. `PATCH /networks/{nid}/thoughts/{id} { icon, icon_kind, icon_attachment_id,
   fg_color, bg_color, font_bold, font_italic, font_underline, font_strike }`.
   Любое из этих полей может быть `NULL` («наследовать от типа»);
   `icon_attachment_id` — вложение-оригинал иконки (L16).
3. Изменения немедленно отражаются на холсте: своё значение имеет приоритет над
   унаследованным от типа (`NULL` → значение типа → дефолт). То же правило для
   связи — `PATCH /networks/{nid}/links/{id} { color, style, width }`
   (переопределение цвета/штриха/толщины линии, `NULL` — от типа связи).

### D7. Синонимы
1. В шапке редактора — строка «Синонимы» (через запятую).
2. Сохранение → клиент парсит строку в массив, синхронизирует
   `thought_synonyms` (add/remove).

## E. Групповые операции

### E1. Множественный выбор
1. `Ctrl+клик` по мыслям → добавление в панель выделения.
2. Альтернативы: контекстное меню, `Ctrl+клик` по эллипсу (все родители/дети),
   меню «Выделение» (дети/родители уже выбранных, поиск существующей мысли).

### E2. Групповое действие
1. В панели выделения → меню «Действия» / «Свойства» → операция.
2. `POST /networks/{nid}/thoughts/batch { ids, op, args }` → сервер применяет к
   всем, возвращает результат с неудачами.

### E3. Экспорт выбранных
1. Меню «Действия» → «Экспорт» → формат в панели выделения.
2. `POST /networks/{nid}/export { thought_ids, format }` → `202 { job_id }`.
3. Polling `GET /jobs/{job_id}` → по готовности — скачивание.

## F. Совместная работа

### F1. Real-time-редактирование
1. Два клиента открыли одну сеть.
2. Любое изменение автора → `created`/`updated` событие доставляется второму
   клиенту по WebSocket.
3. Второй клиент применяет изменение: на холсте/в редакторе/в результатах поиска
   — без перезагрузки.

### F2. Конфликт правок
1. Два клиента правят **одно и то же поле** одной мысли с одной `version`.
2. Первый `PATCH If-Match` проходит, version++.
3. Второй `PATCH If-Match` (с устаревшей) → `409 VERSION_CONFLICT` с серверным
   значением. Клиент показывает уведомление.
4. Если поля **разные** — сервер мирно сливает (см. [04-realtime.md](04-realtime.md),
   п. 8).

## G. Типы (администрирование внутри сети)

### G1. Создание типа мысли со свойствами
1. Раздел «Типы мыслей» → «Новый тип» → имя, иконка, цвет/стиль по умолчанию.
2. Добавление свойств: имя, тип значения (text/date/number/bool/thought_ref),
   обязательность, положение.
3. Сохранение → `POST /thought-types` + cascade `POST /type-properties`.
4. Тип доступен в выпадающем списке «Изменить тип» у мыслей.

### G2. Создание типа связи
1. Раздел «Типы связей» → «Новый тип» → `name_forward`, `name_reverse`, цвет,
   стиль, толщина.
2. Доступен при выборе типа связи (C5, в диалоге добавления).

## H. Внешние AI-агенты (через MCP)

### H1. Агент читает мыслесеть
1. Агент (Claude/IDE/кастом) авторизуется API-key пользователя.
2. `etn.networks.list` → `etn.thoughts.search` по теме →
   `etn.thoughts.subgraph` для топ-результатов.
3. Агент получает JSON-контекст, генерирует ответ в своей LLM.

### H2. Агент дополняет сеть
1. По результатам анализа агент вызывает `etn.thoughts.find_duplicates` для
   каждой новой мысли.
2. При отсутствии дубликата — `etn.thoughts.create` + `etn.links.create`.
3. При наличии — использует существующую мысль.
4. Опционально — `etn.comments.upsert` с резюме (`kind=chronological`,
   `valid_from=сегодня`).
5. Все изменения видны участникам сети через WebSocket как обычные правки.

### H3. (будущее) Генерация документа/презентации
- Через `etn.export.subgraph` + внешний шаблонизатор. Не входит в MVP.

## I. Управление сервером (админ)

### I1. Инициализация
1. `etn init --username admin` → создаётся `_system.db`, первый пользователь
   (`is_admin=1, is_first_user=1`), первичный API-key печатается в консоль.

### I2. Управление сетями
- `GET /admin/networks` → список всех сетей.
- Принудительная смена владельца, удаление сети (см. [02-data-model.md](02-data-model.md),
  п. 6).

### I3. Аудит
- `GET /admin/audit` с фильтрами → журнал операций по пользователям/сетям/категориям.

## J. Защита от потери данных

### J1. Разрыв связи во время правки
1. Пользователь правит постоянный комментарий, сеть пропадает → индикатор 🔴,
   сохранение заблокировано.
2. Правка лежит в `drafts` (status=pending) локально.
3. При восстановлении соединения — retry, на успех — удаление черновика.
4. Если серверная версия уже отличается — конфликт (F2), пользователь решает.

### J2. Повтор запроса (double-submit)
- Каждый изменяющий запрос содержит `Client-Request-Id`. При retry с тем же id
  сервер возвращает кешированный ответ (см. [01-architecture.md](01-architecture.md),
  п. 6). Дублей не возникает.
