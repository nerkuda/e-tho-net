## Подключение AI-агентов (MCP): обзор

ETN умеет подключать внешних AI-агентов (Claude, IDE-ассистенты, ZCode, собственные скрипты) как **равноправных участников мыслесети**: агент видит и меняет данные сети наравне с человеком — те же права, та же проверка доступа и та же защита от одновременного редактирования.

### Что такое MCP

MCP (Model Context Protocol) — стандартный способ, которым AI-агент запрашивает инструменты у приложения. Сервер ETN предоставляет такой интерфейс, поэтому агент общается с ETN не «скриншотами», а готовыми командами: найти мысли, прочитать окружение, записать комментарий и т. д.

### Как агент авторизуется

Агент работает от лица пользователя, чей API-key ему передан. Важное следствие: **ключ даёт агенту полные права этого пользователя** — агент видит и меняет ровно те мыслесети, в которых пользователь состоит.

Чтобы подключить агента:

1. Заведите **отдельный ключ** для агента (не переиспользуйте свой основной). Это позволит в любой момент отозвать именно агентский доступ, не задев остальные устройства. При желании выдайте ключ «только для чтения» и ограничьте частоту записи (см. «Пользователи и API-ключи»).
2. Узнайте адрес сервера и убедитесь, что администратор включил подключение агентов.
3. Пропиньте сервер ETN в клиенте-агенте: для удалённой работы — адрес `https://<сервер>/mcp` и заголовок `Authorization: Bearer <ключ>`.

### Общий порядок для любого клиента

- Для **удалённых агентов** используется сетевой режим: агент обращается к адресу `/mcp` сервера, передавая ключ в заголовке авторизации.
- Для **локальных агентов**, запускаемых на том же компьютере, что и сервер, возможен запуск процесса средствами самого агента (ключ передаётся параметром запуска).
- В любом клиенте нужно создать запись о новом MCP-сервере: дать имя, указать транспорт и способ авторизации, сохранить конфигурацию и перезапустить клиент. После перезапуска агент должен увидеть инструменты ETN и список доступных ему мыслесетей.

### Безопасность

- Ключ агента = доступ пользователя. Не публикуйте ключ и не передавайте его в открытых каналах.
- Выделяйте **отдельный ключ каждому агенту и устройству** — при утечке отзывается только он.
- Если агенту нужно только читать, выдайте ключ «только для чтения».
- Все изменения агента фиксируются в журнале аудита и ленте событий с указанием владельца ключа (см. «Журнал аудита — для администратора»).

## Подключение ZCode (Windows) к удалённому MCP-серверу

**Актуализация 0.8.4 (задача 09f19952).** В шаге 4 проверка подключения — `etn.networks.list` снят с постоянного набора MCP: проси агента вызвать действие `networks.list` исполнителя `etn.ops` (`etn.ops { action: "networks.list" }`) либо инструмент `etn.networks.structure`. Детали — `etn.guide { topic: "networks.list" }`.

Пошаговая процедура подключения AI-агента ZCode на Windows к удалённому MCP-серверу ETN (протестирована 2026-08-25 на etn.rivsala.ru). Общие режимы подключения (stdio/HTTP, авторизация) — на странице «Подключение AI-агентов (MCP): обзор»; здесь — конкретная рабочая схема для ZCode.

### Зачем прокси (важно)

Клиент ZCode подключается к HTTP MCP напрямую и **не умеет пересоздавать сессию** при серверном 404 «Unknown or expired MCP session». Простаивающая HTTP-сессия агента живёт на сервере ограниченное время (по умолчанию 24 часа, настраивается переменной `ETN_MCP_SESSION_IDLE_TTL_MS`) — если пауза в работе агента её превысит, следующая отправка получит 404, а ZCode сам повторную инициализацию не выполнит. Обход: подключаем ZCode по **stdio** через локальный прокси `mcp-remote` (npm) — он сам держит HTTP-сессию и переживает её протухание (проверено: пауза 12 мин → вызов прошёл). Симптомы и разбор — ошибка «HTTP MCP-сессия etn-remote протухает» (id `66dc78ef-1f8c-4629-88c4-cdbe01030feb`).

### Что нужно на целевой машине

- Windows, Node 22 (LTS), ZCode.
- Доступ к `https://<сервер>` (443) и к npm-registry (первая загрузка `mcp-remote`).
- Репозиторий ETN **не нужен** — это просто MCP-клиент.

### Шаг 1. Отдельный API-ключ на машину

С уже работающей машины (или через admin-API):

```bash
curl -X POST https://<сервер>/api/v1/me/keys \
  -H "Authorization: Bearer <существующий ключ>" \
  -H "Content-Type: application/json" \
  -d '{"label":"<имя-машины>"}'
```

Ответ `201 { data: { id, key, prefix } }` — полный ключ показывается **один раз**, скопировать сразу. Отдельный ключ на устройство позволяет отозвать его независимо (DELETE `/api/v1/me/keys/{id}`). Допустимо переиспользовать существующий ключ, но отзыв тогда затронет все машины сразу.

### Шаг 2. Прогреть кэш npx

```bash
npx -y mcp-remote --help
```

Скачивает и кэширует пакет — первый старт MCP в ZCode не упрётся в таймаут загрузки.

### Шаг 3. Конфиг ZCode

`C:\Users\<Имя>\.zcode\cli\config.json`, секция `mcp.servers`:

```json
"etn-remote": {
  "type": "stdio",
  "command": "npx",
  "args": ["-y", "mcp-remote", "https://<сервер>/mcp",
           "--header", "Authorization: Bearer ${ETN_REMOTE_KEY}", "--silent"],
  "env": { "ETN_REMOTE_KEY": "<ключ из шага 1>" }
}
```

После правки проверить валидность JSON: `node -e "JSON.parse(require('fs').readFileSync(process.env.USERPROFILE + '/.zcode/cli/config.json','utf8'))"` — тишина = ок.

### Шаг 4. Перезапуск и проверка

Перезапустить ZCode → `etn-remote` зазеленел → попросить агента вызвать `etn.networks.list` (или действие `networks.list`): должен вернуться список сетей пользователя.

### Не заводится

- Корпоративный прокси → добавить флаг `--enable-proxy` (возьмёт `HTTP_PROXY`/`HTTPS_PROXY`).
- Диагностика → заменить `--silent` на `--debug`, лог в `~/.mcp-auth/{server_hash}_debug.log`.
- 401 → ключ скопирован не целиком/с кавычками; полный ключ повторно не показать — завести новый.
