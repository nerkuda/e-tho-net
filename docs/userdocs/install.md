# ETN — установка и обновление

**Автор:** Проект ETN

Установка и обновление сервера и клиента ETN, подключение клиента к серверу.

<a id="pub-f0ce366b"></a>

## Установка сервера ETN

Сервер ETN — один процесс Node.js; все данные он хранит в SQLite в каталоге данных. Работает на Linux, Windows 10/11 и macOS. Клиент подключается к нему по сети (в примерах ниже — порт 4321).

Готовые сборки версии 0.15.2 публикуются в релизах проекта:

- `ETN-Setup-<версия>.exe` — установщик Windows: ставит сервер службой Windows и/или клиент;
- `etn-server-<версия>.tar.gz` — серверная поставка Linux (нужен установленный Node.js 22 LTS);
- `ETN-Client-<версия>-linux-x64.tar.gz` и `install.sh` — клиент Linux (см. «Установка и подключение клиента ETN»);
- `SHA256SUMS` — SHA-256 всех бинарных ассетов релиза: сверяйте скачанное.

### Установка в Windows (установщик)

Запустите `ETN-Setup-<версия>.exe` и выберите компоненты на первом экране: сервер, клиент или оба. Установщик:

- создаёт первого пользователя-администратора и показывает первичный API-key — сохраните его, повторно ключ не показывается;
- ставит сервер службой Windows `ETN` и запускает её;
- использует фиксированный каталог данных `%ProgramData%\ETN`; Node 22 входит в поставку, внешний Node не нужен;
- по умолчанию слушает порт 4321 (порт можно изменить при первой установке);
- проверяет готовность сервера запросом `GET /api/v1/health`.

Параметры установки (порт, режим, адрес прослушивания) сохраняются в `%ProgramData%\ETN\install.json`; при обновлении они берутся из этого файла и заново не запрашиваются. Каталог данных, каталог программы и порт установщик проверяет до изменений: занятый порт или отсутствие прав отменяют установку с понятной причиной, файлы не заменяются.

Повышение прав (UAC) нужно серверу и клиенту «для всех пользователей»; клиент «только для меня» ставится без UAC (см. «Установка и подключение клиента ETN»). Обновление службы установщик запускает сам под учётной записью службы, поэтому отдельного запроса UAC при обновлении из клиента нет. Служба работает под `LocalSystem`, её журнал — `%ProgramData%\ETN\logs\service\` (`etn-service.out.log`, `etn-service.err.log`). Проверить службу:

```powershell
Get-Service ETN
sc qc ETN
```

Подробности экранов установщика и раскладки файлов — в `installer/README.md` репозитория.

### Установка в Linux из поставки

Скачайте из релиза `etn-server-<версия>.tar.gz` и `SHA256SUMS`, сверьте хеш и распакуйте:

```bash
sha256sum -c SHA256SUMS --ignore-missing
tar -xzf etn-server-0.15.2.tar.gz
cd etn-server-0.15.2
```

Нужен Node.js 22 LTS. Первый запуск и работа — из распакованного каталога `etn-server-<версия>/` (в нём лежит `dist/`):

```bash
export ETN_DATA_DIR="$HOME/.local/share/etn"
export ETN_HOST=0.0.0.0   # доступ из локальной сети; без этого — только 127.0.0.1
export ETN_PORT=4321
node dist/cli.js init --username admin --display-name "Администратор"
node dist/index.js
```

Для постоянной работы оформите запуск службой (systemd и т.п.), задав `ETN_DATA_DIR`, `ETN_PORT` и — для доступа по сети — `ETN_HOST`.

### Установка из исходников

Нужен Node.js 22 LTS — он зафиксирован в `.nvmrc`; для него у `better-sqlite3` есть готовая сборка (на Node 24 понадобится Python в PATH).

```bash
git clone <репозиторий ETN>
cd etn
npm install
npm run build
```

Так сервер ставится на Linux, macOS и Windows (обычным процессом). Для работы сервера после сборки достаточно каталогов `server/`, `shared/` и `markdown/`: сервер зависит от `@etn/markdown` — им рендерятся комментарии, публикации и экспорт. Но `npm run build` из корня собирает весь workspace, включая клиент: без каталога `client/` команда падает. Собрать только сервер можно командой `npm run build:shared && npm -w @etn/server run build` (`build:shared` собирает `shared/` и `markdown/`).

### Первый пользователь-администратор и первичный API-key

Первый пользователь-администратор создаётся один раз командой `etn init` (при установке в Windows это делает установщик). Пока администратора нет, сервер не запускается.

```bash
export ETN_DATA_DIR="$HOME/.local/share/etn"     # каталог данных, пример
node server/dist/cli.js init --username admin --display-name "Администратор"
```

Команда печатает **первичный API-key ровно один раз**:

```
Создан пользователь-администратор: admin
Первичный API-key (показан один раз — сохраните его):
  etn_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx
```

Сохраните ключ в надёжном месте: восстановить его нельзя, можно только выпустить новый (см. «Пользователи и API-ключи»). Дальше пользователи создаются обычным способом через клиент.

### Настройка переменными окружения

| Переменная | Назначение | По умолчанию |
|-----------|------------|--------------|
| `ETN_DATA_DIR` | **Обязательна.** Каталог данных сервера | — |
| `ETN_HOST` | Адрес прослушивания | `127.0.0.1` |
| `ETN_PORT` | Порт HTTP | `3000` |
| `ETN_TLS_CERT` / `ETN_TLS_KEY` | Свой сертификат и ключ (включают HTTPS) | — |
| `ETN_LOG_LEVEL` | Подробность журнала в консоли: `trace`/`debug`/`info`/`warn`/`error` | `info` |
| `ETN_MCP_ENABLED` | `1` — включить подключение AI-агентов | `0` |
| `ETN_MCP_PORT` | Отдельный порт только для AI-агентов | — |
| `ETN_MCP_SESSION_IDLE_TTL_MS` | Сколько живёт простаивающая сессия агента, мс | `86400000` (24 ч) |
| `ETN_UPDATE_FEED` | Адрес фида метаданных релизов для проверки обновлений | релизы GitHub проекта |
| `ETN_UPDATE_CHANNEL` | Канал проверки: `stable` или `prerelease` | `stable` |
| `ETN_UPDATE_CHECK_INTERVAL_HOURS` | Период фоновых проверок обновлений, часы (минимум 1) | `12` |
| `ETN_DEPLOYMENT` | Режим развёртывания: `windows-service`, `standalone` или `docker`; обычно определяется сам | `standalone`, в контейнере — `docker` |

Дефолты в таблице — для ручного запуска: без переменных сервер слушает `127.0.0.1:3000`. Windows-установщик и `docker-compose.yml` задают `0.0.0.0:4321` явно; в примерах ниже порт задаётся вручную.

**Зачем нужен `ETN_DEPLOYMENT`.** От режима зависит обновление: из клиента обновляется только сервер-служба Windows (`windows-service`) — установщик умеет остановить и снова запустить именно службу. Обычный процесс (`standalone`) и контейнер (`docker`) из клиента не обновляются: у сервера нет прав останавливать чужой процесс, а установщик Windows в контейнере неприменим. Поэтому шаблон службы `installer/service/etn-service.xml` задаёт `ETN_DEPLOYMENT=windows-service` сам, при установке и обновлении; вручную эту переменную не задают. Значения по умолчанию в таблице относятся к ручному запуску `node dist/index.js` (`standalone`) и к Docker (`docker` — по маркеру `/.dockerenv`).

Задать переменные можно тремя способами:

1. Разово перед запуском (до закрытия терминала):

```bash
export ETN_DATA_DIR="$HOME/.local/share/etn"
export ETN_PORT=4321
```

2. Постоянно в системе — переживает перезагрузку; задаётся штатными средствами ОС (`~/.bashrc`, «Переменные среды» в Windows).
3. Файлом `.env` рядом с проектом. Сервер не читает его сам — запускайте с флагом `--env-file=.env` (см. «Запуск»). Пути в `.env` указывайте с прямыми слешами, а при пробелах — в двойных кавычках:

```env
ETN_DATA_DIR=C:/ETN/data
ETN_PORT=4321
```

### Каталог данных

В `ETN_DATA_DIR` сервер хранит всё:

```
_system.db          # пользователи, ключи, список мыслесетей
networks/<id>/      # данные каждой мыслесети и её вложения
logs/               # журналы сервера (см. «Логи и диагностика»)
```

При установке в Windows каталог фиксирован — `%ProgramData%\ETN`; рядом живут служебные файлы установщика `install.json` и архивы баз `backups/` (см. «Обновление сервера ETN»). В остальных случаях каталог задаётся `ETN_DATA_DIR`.

Чтобы сделать резервную копию вручную, остановите сервер и скопируйте каталог целиком; для восстановления положите его на место и запустите сервер. Windows-установщик при обновлении создаёт архив баз автоматически — `%ProgramData%\ETN\backups\<YYYYMMDD-HHmmss>\`, хранятся три последних архива. Коды возврата установщика (10/20), журнал `install-YYYYMMDD-HHmmss.log`, автоматический откат и ручное восстановление баз — в разделе «Обновление сервера ETN».

### Запуск

```bash
node --env-file=.env server/dist/index.js
```

Проверка готовности:

```bash
curl http://localhost:4321/api/v1/health
```

Ответ должен быть вида `{"status":"ok","db":"ok","version":"...","uptime":...}`.

Для постоянной работы запускайте сервер как службу средствами ОС (systemd в Linux; служба ETN, которую ставит установщик, — в Windows) либо контейнером Docker (пример — `docker-compose.yml` в репозитории). Во всех случаях задайте `ETN_DATA_DIR`, порт и, если нужен доступ по сети, `ETN_HOST`.

### Доступ по HTTPS

Для работы через интернет поставьте сервер за обратный прокси с TLS: прокси принимает HTTPS, а внутрь перенаправляет на HTTP-порт ETN. Пример конфигурации nginx (адреса и пути условны):

```nginx
server {
    listen 443 ssl;
    server_name etn.example.com;

    ssl_certificate     /etc/ssl/etn.crt;
    ssl_certificate_key /etc/ssl/etn.key;

    location / {
        proxy_pass http://127.0.0.1:4321;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

Важно: клиент держит постоянное соединение (WebSocket) — прокси обязан пропускать заголовок `Upgrade`. Если прокси не хотите, сервер умеет TLS сам: задайте `ETN_TLS_CERT` и `ETN_TLS_KEY`.

## Обновление сервера ETN

Версия 0.15.2. Сервер, установленный службой Windows, обновляется из клиента: администратор запускает обновление, сервер скачивает установщик `ETN-Setup-<версия>.exe`, проверяет его SHA-256 и передаёт управление установщику. Схема базы данных обновляется автоматически при первом старте новой версии. Сервер из исходников и в Docker обновляется вручную — см. разделы ниже.

Автообновление возможно только для службы Windows: режим `windows-service` задаёт шаблон службы (см. «Настройка переменными окружения»). Обычный процесс и контейнер из клиента не обновляются — причины в «Ограничениях».

### Обновление из клиента

Обновление запускает администратор из клиента ETN: меню пользователя → «Обновление сервера». У остальных пользователей пункта нет; серверные операции обновления тоже требуют прав администратора. Диалог показывает текущую и доступную версии, канал обновлений и дату последней проверки.

**Проверка.** Сервер проверяет канал при старте и каждые 12 часов (`ETN_UPDATE_CHECK_INTERVAL_HOURS`, минимум 1 час; `ETN_UPDATE_CHANNEL` — `stable` или `prerelease`; `ETN_UPDATE_FEED` — адрес фида, по умолчанию релизы GitHub проекта). Кнопка «Проверить» запускает проверку немедленно; если проверка уже идёт, повторный запрос отклоняется.

**Шаг 1. Проверка и выбор версии.** Администратор видит текущую версию, доступную версию, канал и время проверки. Обновление предлагается, только если доступная версия новее текущей; понижение версии запрещено.

**Шаг 2. Подтверждение.** Кнопка «Обновить сервер» открывает подтверждение: сервер будет остановлен, база данных скопирована в архив, установщик заменит программу и запустит новую версию; клиенты на время обновления получают ответ «сервер обновляется» (503/1012) и переподключаются автоматически.

**Шаг 3. Подготовка задания.** Сервер создаёт задание обновления, скачивает установщик и сверяет SHA-256. Это может занять до 10 минут; диалог показывает «Сервер скачивает установщик и проверяет SHA-256…». Если установщик не скачался или не сошёлся по хешу, сервер продолжает работу на текущей версии, обслуживание ещё не включалось: задание получает `failed`, диалог показывает причину. Если установщик не удалось запустить, обслуживание уже включено — сервер останется в нём до перезапуска (см. «Если обновление не удалось»). Повторный запуск в этом диалоге не предлагается — устраните причину и откройте диалог заново.

**Шаг 4. Обслуживание.** Непосредственно перед запуском установщика сервер записывает этап `backing-up` и переводится в обслуживание. Что это значит:

- изменяющие запросы REST (создание, правка, удаление) получают `503 SERVER_UPDATING` с заголовком `Retry-After` (по умолчанию 300 секунд, не меньше 30);
- изменяющие инструменты MCP отвечают ошибкой `SERVER_UPDATING`;
- клиенты по WebSocket получают кадр `maintenance` и закрытие соединения с кодом `1012`; статус-бар показывает «Сервер: обновление»;
- чтение продолжает работать, пока служба не остановлена.

С этого момента новые правки не сохраняются: клиент сообщает «сервер обновляется, попробуйте позже».

**Шаг 5. Работа установщика.** Установщик останавливает службу — связь с сервером прерывается, это ожидаемо: диалог показывает «Связь с сервером прервана — так и должно быть при обновлении. Ждём перезапуска сервера.» Пока служба остановлена, установщик:

- создаёт архив баз в `%ProgramData%\ETN\backups\<YYYYMMDD-HHmmss>\` (только при смене версии, см. «Бэкапы»);
- сохраняет снимок текущей программы в `%ProgramData%\ETN\.install\rollback\<YYYYMMDD-HHmmss>\`;
- заменяет файлы, настраивает и запускает службу;
- ждёт до 60 секунд (опрос каждые 2 секунды) ответа: `GET /api/v1/health` → 200, `status: "ok"`, `db: "ok"`, версия равна целевой; `GET /api/v1/version` → версия равна целевой, `api: "v1"`. Проверяется тело ответа, а не только HTTP-код.

Замену файлов, health-check и откат клиент по шагам не видит: процесс сервера в это время остановлен, и эти этапы никуда не записываются.

**Шаг 6. Итог после перезапуска.** Итог задания фиксирует первый старт новой версии, а не работавший до обновления сервер — его процесс установщик останавливает. Если запущенная версия равна целевой или новее, задание читается как «Обновление завершено» (`done`); поле причины у него несёт справочный текст «Обновление завершено после перезапуска…», который клиент ошибкой не показывает. Если версия ниже целевой — установщик откатился или служба поднялась на прежней версии — задание читается как «Обновление не удалось» (`failed`) с причиной «Сервер перезапущен до завершения задания обновления (этап „…“); задание автоматически не возобновляется».

**Если откат вернул версию без таблицы задания.** Восстановление итога работает в версиях, которые знают таблицу `update_jobs`, — 0.15.x и новее. Ближайший предыдущий релиз — 0.14.1 (версии 0.15.0 не было); в нём нет ни модуля `server/src/update`, ни миграции, создающей `update_jobs`, ни эндпоинта `GET /api/v1/system/update/progress`. Поэтому после отката на 0.14.1 задания и его итога нет вовсе: установщик возвращает `_system.db` из архива, снятого до миграции с этой таблицей, и восстанавливать задание некому. Диалог обновления на откатившемся сервере тоже не открыть: клиент 0.15.1 совместим только с сервером `>=0.15.0 <0.16.0`; 0.14.1 вне этого окна, и клиент блокирует работу диалогом несовместимости ещё до первых запросов данных. Итог и причину в этом случае ищите в журнале установщика `%ProgramData%\ETN\logs\install-YYYYMMDD-HHmmss.log` (если каталог данных недоступен — `%TEMP%`): в нём код возврата, причина, путь к архиву баз и следующий шаг.

Диалог опрашивает `GET /api/v1/system/update/progress` раз в 3 секунды и показывает итог, как только сервер снова отвечает. Если диалог был закрыт, откройте «Обновление сервера» заново: последнее задание читается с сервера. Клиент переподключается сам и продолжает работу на новой версии.

**Что видно в диалоге.** Показываются только этапы, которые сервер действительно записывает: «Подготовка задания…» (`preparing`) и «Резервное копирование базы данных…» (`backing-up`; подпись появляется перед передачей управления установщику — сам архив создаёт установщик), затем итог «Обновление завершено»/«Обновление не удалось» (`done`/`failed`). Живого прогресса замены файлов, health-check и отката нет и быть не может: сервер в это время остановлен. Обрыв связи во время обновления — штатное состояние, а не ошибка.

**Где искать причину и время завершения.** Для `failed` диалог показывает серверную причину и, когда она содержит путь, строку «Журнал установщика: …». Сам журнал — `%ProgramData%\ETN\logs\install-YYYYMMDD-HHmmss.log` (если каталог данных недоступен — `%TEMP%`); путь последней попытки записан в `last_log` файла `%ProgramData%\ETN\install.json`. Итог задания и время его завершения (`finished_at`) хранятся в служебной таблице `update_jobs` системной базы `%ProgramData%\ETN\_system.db`; в клиенте видны только итог и причина. Журнал самой службы — `%ProgramData%\ETN\logs\service\`.

### Если обновление не удалось

Установщик возвращает один из контрактных кодов:

- **10 — сбой выполнения:** не создан архив БД, не удалась замена файлов или запуск службы, не прошёл health-check либо не удался сам откат;
- **20 — не выполнено предусловие:** занят порт, служба не остановилась или не зарегистрирована, сервер запущен не службой (в silent-обновлении), режим «обычное приложение».

Любой другой код Inno Setup трактуется как 10. Журнал установщика: `%ProgramData%\ETN\logs\install-YYYYMMDD-HHmmss.log` (если каталог данных недоступен — `%TEMP%`). В журнале причина, путь к архиву БД, путь к снимку отката и следующий шаг.

**Если служба осталась работать.** Если установщик отказал до остановки службы (например, код 20: занят порт, служба не остановилась или не зарегистрирована) либо не запустился, сервер уже переведён в обслуживание и сам из него не выходит: изменяющие запросы продолжают получать `503`, пока службу не перезапустят. Перезапустите службу (`Restart-Service ETN`) или процесс сервера — состояние обслуживания живёт в памяти процесса.

**Автоматический откат.** Установщик останавливает службу, возвращает каталоги `server` и `service` из снимка этого запуска и восстанавливает базу **только из архива этого запуска** (журналы `-wal`/`-shm` неудачного запуска удаляются), затем запускает прежнюю версию и проверяет её health-check без требования целевой версии. Если архива в этом запуске не было (ремонт той же версии), база остаётся как есть: изменения, сделанные после остановки службы, не восстановимы — в журнале и сообщении об этом сказано прямо. Если откат не удался, журнал называет пути к архиву и снимку; данные восстанавливаются вручную.

#### Ручное восстановление базы данных

1. Остановите службу: `Stop-Service ETN` (или `"%ProgramFiles%\ETN\service\etn-service.exe" stop`).
2. Откройте каталог архива `%ProgramData%\ETN\backups\<YYYYMMDD-HHmmss>\`. В нём лежат `_system.db` и `networks\<uuid>\data.db` для каждой мыслесети.
3. Скопируйте `_system.db` в `%ProgramData%\ETN\_system.db`, а каждую базу мыслесети — в `%ProgramData%\ETN\networks\<uuid>\data.db`, заменив файлы.
4. Удалите рядом с восстановленными файлами журналы `-wal` и `-shm` (остатки прерванной работы).
5. Запустите службу: `Start-Service ETN`. Готовность — `GET http://127.0.0.1:4321/api/v1/health` → 200 и `{"status":"ok","db":"ok",...}`.

```powershell
Stop-Service ETN
$backup = 'C:\ProgramData\ETN\backups\20261030-120000'
Copy-Item "$backup\_system.db" 'C:\ProgramData\ETN\_system.db' -Force
Get-ChildItem "$backup\networks" -Directory | ForEach-Object {
  Copy-Item (Join-Path $_.FullName 'data.db') (Join-Path "C:\ProgramData\ETN\networks\$($_.Name)" 'data.db') -Force
}
Get-ChildItem 'C:\ProgramData\ETN\_system.db-wal','C:\ProgramData\ETN\_system.db-shm' -ErrorAction SilentlyContinue | Remove-Item -Force
Get-ChildItem 'C:\ProgramData\ETN\networks' -Recurse -Include 'data.db-wal','data.db-shm' | Remove-Item -Force
Start-Service ETN
```

Вложения в архив не входят: установщик копирует только базы данных и сами файлы вложений не меняет. В каталоге данных они лежат в `networks\<uuid>\attachments\`.

### Бэкапы

При смене версии установщик после остановки службы и до замены файлов создаёт архив в `%ProgramData%\ETN\backups\<YYYYMMDD-HHmmss>\`:

- копии `_system.db` и `networks\<uuid>\data.db`;
- формат — каталог, не zip: архиватора в серверной поставке нет;
- только базы данных: вложения не копируются;
- перед копированием WAL-журнал базы сводится чекпойнтом; если чекпойнт не удался, рядом копируется `-wal`, чтобы архив остался согласованным;
- каждая копия проходит `PRAGMA integrity_check`; результат не `ok` — архив удаляется, обновление отменяется до замены файлов (код 10).

Хранятся три последних архива: при создании четвёртого самый старый удаляется. Чужие файлы и каталоги в `backups` не трогаются; ошибка удаления старого архива обновление не отменяет — только предупреждение в журнале.

Ремонт той же версии (повторная установка без смены версии) выполняется без архива. Первая установка и подключение существующих данных без записи установки — тоже без архива: прежней версии нет, данные установщик не меняет.

### Ограничения

- **Только администратор и только из клиента.** Обновление запускает администратор из клиента кнопкой «Обновить сервер». Серверные операции обновления требуют прав администратора; у остальных пользователей кнопки нет.
- **Только служба Windows.** Обновление из клиента работает, только если сервер запущен службой `ETN` и определил режим `windows-service` — его задаёт шаблон службы. Если сервер запущен обычным процессом (`node server/dist/index.js`, режим `standalone`), обновление из клиента невозможно: задание сразу завершается статусом «Обновление не удалось» с инструкцией. Остановите сервер вручную и запустите установщик либо установите ETN службой Windows — прав на остановку чужого процесса у сервера нет.
- **Docker.** Сервер в контейнере не обновляет себя сам: кнопки «Обновить сервер» в диалоге нет, показывается команда, а попытка запустить обновление отклоняется с пояснением. Обновление выполняет администратор на хосте (см. «Обновление сервера в Docker»).
- **Клиент не обновляется сам.** Новую версию клиента скачивает и устанавливает пользователь; клиент только показывает баннер «Доступна версия …» с кнопкой, открывающей страницу релиза в браузере (см. «Обновление клиента ETN»).
- **Не выключайте компьютер сервера** до завершения обновления: установщик остановил службу и заменяет файлы.

### Обновление сервера в Docker

Сервер в контейнере не обновляет себя сам: вместо кнопки «Обновить сервер» диалог обновления показывает команду, а попытка запустить обновление из клиента отклоняется с пояснением. Обновление выполняет администратор на хосте, где лежит compose-файл.

#### Перед обновлением

Сделайте резервную копию каталога данных — тома `etn_data`, внутри которого `/data` (он же `ETN_DATA_DIR`); в примере compose-файла служба называется `etn`:

```bash
docker compose stop
docker compose cp etn:/data ./etn-data-backup
```

Схема базы данных обновляется автоматически при старте новой версии и только вперёд: старая версия может не понять обновлённую базу. Без копии откат на предыдущую версию невозможен.

#### Порядок

```bash
docker compose pull
docker compose up -d
```

`pull` забирает новый образ, `up -d` пересоздаёт контейнер — данные в томе при этом сохраняются. С 0.15.2 серверный образ публикуется в реестре GHCR: `ghcr.io/nerkuda/e-tho-net/etn-server:<версия>`. Если compose-файл ссылается на него в `image:`, `pull` забирает новую версию. Если compose-файл собирает образ из исходников (в нём указан `build:`), `pull` ничего не скачивает: обновите исходники и пересоберите образ.

```bash
git pull
docker compose build
docker compose up -d
```

Готовность — успешный ответ `GET /api/v1/health` на вашем порту (см. «Запуск» в разделе установки).

#### Откат на предыдущую версию

Верните установленную ранее версию и пересоздайте контейнер. Если compose-файл собирает образ из исходников, переключитесь на тег прежней версии и пересоберите:

```bash
git checkout v0.14.1        # тег, который был установлен до обновления
docker compose build
docker compose up -d
```

Если вы используете опубликованный образ из реестра, укажите прежний тег в `image:` compose-файла и выполните `docker compose up -d`.

Если новая версия уже обновила схему базы, перед запуском старой версии верните копию каталога данных, сделанную до обновления:

```bash
docker compose stop
docker compose cp ./etn-data-backup/. etn:/data
docker compose up -d
```

#### Что происходит с клиентами

Пока контейнер пересоздаётся, сервер недоступен несколько секунд: клиент показывает потерю связи и сам переподключается, когда сервер поднимается, — открытая сессия восстанавливается. Правки в это время не сохраняются, поэтому обновляйте сервер, когда с ним не работают.

Ответы `503` и закрытие соединения с кодом `1012` — это путь обновления службы Windows из клиента (см. «Обновление из клиента»); в Docker он не используется, здесь клиенты просто переподключаются после перезапуска контейнера.

После обновления сервера клиент может потребовать обновления и себя: если версии сервера и клиента несовместимы, обновите клиент (см. «Совместимость клиента и сервера»).

### Что происходит при первом старте новой версии

- **Обновление схемы данных (миграции).** Сервер сам приводит базу к новой версии — отдельных команд не требуется. Если у вас несколько мыслесетей, обновление идёт по одной; сервер при этом может отвечать не сразу — дождитесь готовности.
- **Перерисовка старых комментариев.** Если в новой версии изменился движок форматирования текста, сервер при старте один раз обновляет оформление всех ранее сохранённых комментариев. На большом объёме данных это может занять от секунд до минут; прерывать процесс не нужно — при сбое он корректно повторится.

Признак готовности — успешный ответ `GET /api/v1/health`.

### Совместимость клиента и сервера

Совместимость — **minor-окно**: сервер версии `X.Y.Z` принимает клиентов в диапазоне `>=X.Y.0 <X.(Y+1).0` (например, для 0.15.1 — `>=0.15.0 <0.16.0`). Диапазон вычисляется из версии сервера и отдаётся в `GET /api/v1/version` (поле `client_compatibility`); клиент дополнительно сверяет версию сервера со своим встроенным диапазоном — так ни старый сервер не пустит новый клиент, ни наоборот.

**При подключении.** Клиент сверяет обе стороны до первых запросов данных. Несовпадение — блокирующий диалог: работа не начинается, данные не запрашиваются. В диалоге нет «Отложить»: его нельзя закрыть (крестика нет, `Esc` не действует), пока версия не станет совместимой. Выходы — «Повторить» (та же проверка), «Обновить клиент» (открывает страницу релиза в браузере) и у администратора «Обновить сервер». Если сервер старше клиента, неадминистратору вместо кнопки показывается «Обратитесь к администратору сервера». Это защита от порчи данных рассогласованными версиями.

**В середине сессии.** Сервер проверяет заголовок `Client-Version` на изменяющих запросах desktop-клиента (создание, правка, удаление). Запрос с версией вне диапазона получает `426 CLIENT_VERSION_UNSUPPORTED` — правки не сохраняются, хотя чтение продолжает работать. Поэтому после обновления сервера обновите и клиент: старый клиент упрётся в 426 при первой попытке записи, даже если сессия была открыта до обновления. Если после обновления одной стороны клиент отказывается подключаться — обновите отставшую сторону.

### Обновление из исходников и из поставки Linux

Если сервер развёрнут из исходников (Linux, macOS или Windows обычным процессом) либо из `etn-server-<версия>.tar.gz`, обновление выполняет администратор вручную:

```bash
git pull
npm install
npm run build
# перезапустите процесс сервера
```

Для поставки Linux распакуйте новую версию рядом, остановите процесс, переключите каталог (или символическую ссылку `current`) и запустите: миграции выполнятся при старте. Службу перезапустите штатно (`systemctl restart etn`, `Restart-Service ETN`).

Перед обновлением сделайте копию каталога данных: в отличие от Windows-установщика, архива баз здесь никто не создаёт. Откат возможен только из этой копии, а схема базы обновляется только вперёд.

### Размер журнала WAL

Рядом с базой каждой мыслесети лежит файл `data.db-wal` — журнал предзаписи SQLite. Сервер ведёт его сам и до определённого предела переиспользует, а усекает до нуля только явный чекпойнт (программа сама решает, когда он уместен — данные при этом не трогаются). Вот почему у остановленного сервера `-wal` может занимать несколько мегабайт «впустую» — это нормально и на сохранность данных не влияет.

Начиная с 0.13.1 сервер приводит журнал в порядок сам: раз в минуту (настройка `ETN_WAL_CHECKPOINT_INTERVAL_MS`; `0` — выключить) и при остановке — журналы всех мыслесетей усекаются. Отдельного шага при обновлении не нужно.

Если журнал вырос несоразмерно (десятки и сотни мегабайт — признак того, что сервер старой версии чекпойнт не делал), проще всего штатно перезапустить сервер: при остановке он усечёт журнал сам. Жёстко убивать процесс (kill) не надо: при штатном завершении журналы усекаются, при аварийном остаются как есть.

## Установка и подключение клиента ETN

Клиент ETN — настольное приложение (Windows 10/11 x64, Linux x64, macOS). Оно работает **только при связи с сервером**: без соединения правки не сохраняются.

### Установка
Готовые сборки версии 0.15.2 — в релизах проекта.

**Linux** — одной командой, без sudo (клиент ставится в `~/.local/opt/etn`). Нужен `curl` или `wget`; в минимальной Ubuntu 24.04 `curl` нет — поставьте его один раз: `sudo apt-get install -y curl`.

```bash
curl -fsSL https://github.com/nerkuda/e-tho-net/releases/latest/download/install.sh | bash
```

Вариант через `wget`, если `curl` ставить не хочется:

```bash
wget -qO- https://github.com/nerkuda/e-tho-net/releases/latest/download/install.sh | bash
```

Скрипт скачивает последнюю версию, сверяет архив с `SHA256SUMS`, распаковывает рядом со старой и переключает симлинк `current`; ярлык появляется в меню приложений, а повторный запуск той же команды обновляет клиент. Внутри скрипт скачивает через `curl`, при его отсутствии — через `wget`; если нет ни того, ни другого, сообщает об этом до установки.

Варианты:

- конкретная версия — `bash install.sh --version 0.15.2`;
- системная установка в `/opt/etn` (нужен root) — `sudo bash install.sh --system`;
- удаление без потери профилей и ключей — `bash install.sh --uninstall`;
- вручную — распакуйте `ETN-Client-<версия>-linux-x64.tar.gz`.

### Первый запуск и подключение к серверу

При первом запуске открывается экран подключения. Укажите:

- **Адрес сервера** — вида `http(s)://host:port`, например `https://etn.example.com`.
- **API-key** — ключ, который выдал администратор (см. «Пользователи и API-ключи»).

Нажмите **«Подключиться»**: клиент проверяет ключ и доступность сервера. При ошибке показывается понятная причина — неверный ключ, сервер недоступен или несовместимая версия (см. «Обновление сервера ETN»).

Если ключ принят, откроется список доступных вам мыслесетей. Клиент запоминает последний выбранный сервер и восстанавливает сессию (открытые вкладки и активную сеть) при следующем запуске. Адрес сервера и ключ хранятся локально; ключ шифруется средствами операционной системы и не покидает приложение.

**Язык интерфейса.** На экране подключения клиент говорит на языке операционной системы. После подключения язык приходит из вашего профиля на сервере: по умолчанию сервер предлагает английский. Выбрать русский или китайский можно в «Все настройки» → «Клиент» → «Язык приложения»; перезапуск не нужен. Подробнее — «Настройки клиента» → «Язык интерфейса».

### Смена сервера и несколько профилей

В меню пользователя есть команда смены сервера: выберите сохранённый сервер из списка или введите другой адрес и ключ. Несколько сохранённых серверов сосуществуют, клиент подключается к последнему выбранному.

Чтобы держать одновременно несколько независимых наборов настроек и подключений, запускайте клиент с отдельным каталогом профиля:

```
etn.exe --user-data-dir=<путь>
```

### Если подключиться не удаётся

- **Неверный ключ** — проверьте, что ключ скопирован целиком; напоминаем, полный ключ показывается только один раз, при необходимости выпустите новый.
- **Сервер недоступен** — проверьте адрес и порт, доступность сервера и HTTPS.
- **Несовместимая версия** — версия клиента должна входить в диапазон `>=X.Y.0 <X.(Y+1).0` от версии сервера; пока стороны несовместимы, работа блокируется. Обновите клиент или сервер (см. «Совместимость клиента и сервера»).

## Обновление клиента ETN

Клиент ETN **не обновляет себя сам**: механизм автообновления `electron-updater` из клиента удалён (регресс-сторож `client/tests/guard-no-electron-updater.test.ts`), скачивания файла и запуска установщика в клиенте нет. Новую версию скачивает и устанавливает пользователь либо администратор сервера.

### Как клиент сообщает об обновлении

При подключении клиент сверяет свою версию с поддерживаемым диапазоном сервера (`GET /api/v1/version`: `client_compatibility`, `recommended_client_version`, `client_download_url`) и версию сервера — со своим встроенным диапазоном. Если рекомендована новая версия, клиент показывает баннер «Доступна версия …» с кнопкой «Обновить клиент» — она открывает страницу релиза в системном браузере; файл не скачивается и не запускается. Кнопка «Позже» скрывает баннер до следующей проверки (новое подключение или переподключение). Если версия несовместима, работа блокируется диалогом с той же кнопкой (см. «Совместимость клиента и сервера»); если сервер не сообщил адрес страницы релиза, кнопки нет — откройте релизы проекта вручную.

### Обновиться вручную
- **Windows:** скачайте `ETN-Setup-<версия>.exe` из релизов проекта и установите поверх текущей версии — профили, серверы и ключи сохраняются. Область установки при обновлении не меняется (только для меня / для всех пользователей).
- **Linux:** та же одношная команда — `curl -fsSL https://github.com/nerkuda/e-tho-net/releases/latest/download/install.sh | bash`. Нужен `curl` или `wget`; в минимальной Ubuntu 24.04 `curl` нет — `sudo apt-get install -y curl`, либо используйте вариант `wget -qO- https://github.com/nerkuda/e-tho-net/releases/latest/download/install.sh | bash`. Новая версия ставится рядом со старой, симлинк `current` переключается только после проверки SHA-256; профили и ключи в `~/.config/ETN` не трогаются. Конкретную версию задаёт `--version X.Y.Z`, системную установку — `sudo bash install.sh --system`. Либо распакуйте `ETN-Client-<версия>-linux-x64.tar.gz` и замените файлы вручную.
- **macOS:** готового DMG в релизе 0.15.2 нет — соберите клиент из исходников (`npm install`, `npm -w @etn/client run package`) и замените приложение.

Хеши ассетов — в файле `SHA256SUMS` соответствующего релиза.

### Важно

Клиент и сервер должны быть совместимы: сервер `X.Y.Z` принимает клиентов `>=X.Y.0 <X.(Y+1).0`, и клиент сверяет обе стороны ещё до первых запросов данных. При несовместимости работа блокируется диалогом без «Отложить»: пока версии не совместимы, данные не запрашиваются; старый клиент в уже открытой сессии получит `426 CLIENT_VERSION_UNSUPPORTED` на первом изменяющем запросе. Обновляйте обе стороны вместе (см. «Совместимость клиента и сервера»).
