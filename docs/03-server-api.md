## /activity — лента, свёртка и обрезка журнала активности

Чтение и обслуживание журнала активности.

```
GET  /api/v1/networks/{nid}/activity
     ?from_ms&to_ms&user_id&entity_type&entity_id&limit&offset   # плоские фильтры
   | ?ast=<json>&limit&offset                                    # AST-путь (XOR)
     → 200 { data: [ { id, user_id, user_name, action, entity_type,
                       entity_id, entity_title, layer_id, occurred_at_ms } ],
             meta: { total, offset, limit } }
POST /api/v1/networks/{nid}/activity/rollup   { until_ms }  → 200 { removed, kept }
POST /api/v1/networks/{nid}/activity/truncate  { until_ms }  → 200 { removed }
```

- фильтры комбинируются (период × пользователь × сущность); сортировка по `occurred_at_ms` убыв.; пагинация `limit`/`offset`;
- `rollup`/`truncate` необратимы; сервер возвращает счётчики удалённых/оставшихся записей;
- запись журнала отдельной операцией не редактируется (append-only).

### Тело-отбор (AST), 0.13.1 — задача `2b230e8e`
`GET /activity` и MCP `etn.activity.list` принимают `ast` — тело профиля «события» (`{ version, filter, sort? }`). Коммиты `cb45c574` (компилятор, исполнитель, REST/MCP, профиль, подвыборка `entity_id`) и `e92189c0` (жёсткие AST-эталоны полей компилятора). Требование «События REST/MCP компилируются в общий AST».

- **Один источник критериев.** `ast` XOR плоские фильтры (`from_ms`, `to_ms`, `user_id`, `entity_type`, `entity_id`) — одновременная передача `VALIDATION_ERROR` (поле `ast`, `details.conflicts`). Пагинация (`limit`/`offset`) — отдельно от критериев.
- **Операнды профиля `events`:** `occurred_at` (колонка `occurred_at_ms`; сравнения/«между», границы — миллисекунды, ISO-дата или токен, профиль несёт время), `action` (только «в»/«не в» — множественное перечисление), `entity_type` (только «в»/«не в» — множественное перечисление), `entity_title` (колонка `activity_log.entity_title`; «содержит»/«не содержит» — LIKE по снимку заголовка сущности), `entity_id` (равно/не равно — литеральный id; `in`/`not_in`/`all_of` — значение-под-выборка по мыслям: событие по сущности, чей id ∈ выборке), `user` (колонка `user_id`).
- **Плоские фильтры** компилируются в AST тем же движком (`compileActivityToAst`); порядок — `occurred_at_ms DESC, id DESC` (как и обещает операция). Токены `$weekStart`/`$weekEnd` учитывают первый день недели сети; профиль несёт время (`$now`/`$hour*`). Грамматика AST, операторы и токены — `etn.guide { topic: "thoughts.query" }`, состав профиля — реестр профилей `@etn/shared/filter-profiles` (ADR `0c02ab4f`).
- Свёртка (`rollup`) и обрезка (`truncate`) — отдельные операции над `activity_log`, не затронуты.

**Ревизия 0.13.1 (2026-10-15, задача b2aa2444).** В профиль `events` возвращён текстовый операнд `entity_title` («Заголовок сущности»): операторы «содержит»/«не содержит» — LIKE по снимку заголовка в `activity_log.entity_title`; поиск события по слову заголовка, утраченный при пересборке ленты на единый редактор (направление — решение пользователя, вариант 1). Здесь же уточнён состав `action`/`entity_type` — только «в»/«не в» (ошибка 50d9bf4e п. C1).

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: activity_log — журнал активности сети
- применяется к: Требование: свёртка activity_log, Сценарий: события — изменения за последний час, События REST/MCP компилируются в общий AST, Требование: обрезка activity_log

## /admin/networks — админский обзор и правка мыслесетей

Админский взгляд на все мыслесети сервера — в отличие от личного `GET /networks`, который показывает только сети явного членства даже админу.

```
GET    /api/v1/admin/networks                       # все сети сервера
DELETE /api/v1/admin/networks/{network_id}          # удалить сеть
PATCH  /api/v1/admin/networks/{network_id}/members  # принудительно менять членство
```

Удаление сети — необратимая операция: вместе с записью в реестре удаляется вся её база данных со всеми мыслями, связями и вложениями.

Право доступа админа к конкретной сети по id не зависит от его членства: он проходит проверку доступа на любую сеть и её вложенные ресурсы.

**Дополнительные материалы**
- относится к подсистемам: REST API, Аутентификация и права доступа
- зависит от: networks — реестр мыслесетей и самоописание сети, network_members — членство пользователей в мыслесетях
- применяется к: Администратор системы имеет доступ к любой сети без членства

## /admin/users — администрирование пользователей и их ключей

Админские маршруты управления учётными записями сервера. Доступны только ключу пользователя с `is_admin = 1`; остальным — `403 FORBIDDEN`.

```
GET    /api/v1/admin/users
POST   /api/v1/admin/users            { username, display_name, is_admin? }
                                      → 201 + автоматически созданный API-ключ
GET    /api/v1/admin/users/{id}
PATCH  /api/v1/admin/users/{id}       { display_name?, is_admin?, disabled? }
DELETE /api/v1/admin/users/{id}

POST   /api/v1/admin/users/{id}/keys  { label, read_only?, max_writes_per_minute? }
                                      → 201 { key, prefix }
PATCH  /api/v1/admin/users/{id}/keys/{key_id}  { max_writes_per_minute: null | int }
DELETE /api/v1/admin/users/{id}/keys/{key_id}
```

- создание пользователя сразу выдаёт ему ключ; передать ключ владельцу — забота админа (повторно ключ не показывается);
- **первого пользователя сервера (`is_first_user = 1`) удалить нельзя** — `422`: иначе сервер можно оставить без администратора;
- `disabled` блокирует вход, не удаляя данные пользователя;
- админ выпускает и отзывает ключи любого пользователя теми же правилами, что и владелец через `/me/keys`.

**Дополнительные материалы**
- относится к подсистемам: REST API, Аутентификация и права доступа
- зависит от: users — таблица пользователей сервера, api_keys — таблица ключей доступа
- применяется к: Удаление пользователя: каскад и запрет при владении сетью, Требование: запрет физического удаления пользователя-автора

## /api/v1/users/me/settings — серверные настройки пользователя вне сети

Чтение и запись серверных настроек пользователя уровня «пользователь × сервер» (таблица `user_settings` системной БД).

```
GET  /api/v1/users/me/settings          # все ключи пользователя
PUT  /api/v1/users/me/settings/{key}    { value: <json> }
```

**Первый ключ:** `comment_hotkeys` — JSON-карта «команда → сочетание» пользовательских хоткеев комментария.

**Семантика.** Значения общие для всех сетей сервера и всех устройств пользователя. Ответ GET — карта ключей. PUT идемпотентен (last-write-wins на ключ).

**Не путать** с `GET/PUT /networks/{id}/preferences` ([/networks/{id}/preferences — серверные предпочтения пользователя в сети](#pub-14ad55d1)), который хранит настройки уровня «пользователь × сеть».

**Дополнительные материалы**
- применяется к: Пользовательские сочетания клавиш хранятся на сервере на уровне «пользователь × сервер»

## /comments/{id}/targets — привязка хроники к нескольким владельцам

Хронологическая запись может принадлежать нескольким владельцам сразу — одно событие касается сразу нескольких мыслей и связей.

```
POST   /api/v1/networks/{nid}/comments
       { kind: "chronological", title?, body_md, valid_from?, valid_to?,
         targets: [ { owner_type: "thought"|"link", owner_id } ] }   # 1..100
GET    /api/v1/networks/{nid}/comments/{id}
POST   /api/v1/networks/{nid}/comments/{id}/targets
       { owner_type, owner_id }
DELETE /api/v1/networks/{nid}/comments/{id}/targets/{owner_type}/{owner_id}
```

- `Comment` в ответах несёт полный массив `targets`; `owner_type`/`owner_id` — **первичная** (первая) привязка; дубли в `targets` схлопываются;
- **постоянный комментарий всегда имеет ровно одну привязку**; попытка добавить ему вторую — `422`, повторная привязка того же владельца — `409 DUPLICATE`;
- **отвязка первичного владельца** переносит первичность на другую оставшуюся, а отвязка последней привязывает запись к HOME — запись никогда не остаётся без владельца;
- список комментариев владельца показывает запись у **каждого** её владельца; изменение привязок эмитит `comment.updated` с `changes.targets`;
- при удалении мысли или связи комментарии, где она первичный владелец, удаляются целиком со всеми привязками, а вторичные привязки удалённой сущности просто отвязываются. То же касается связей, удаляемых каскадом вместе с мыслью.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: comment_targets — привязки комментария к нескольким владельцам
- применяется к: Инварианты привязки комментариев к владельцам, Сервер: тест записи покрывает каждое значение вида REST-контракта

## /import/preview и /import/commit — импорт архива .etnx

```
POST /api/v1/networks/{nid}/import/preview   { archive_b64 }
→ 200 { data: { manifest_version, source_network_name, counts: {…} } }

POST /api/v1/networks/{nid}/import/commit    { archive_b64, parent_thought_id }
→ 200 { data: ImportSummary }
```

Архив `.etnx` — zip с `manifest.json` и (опционально) каталогом вложений; передаётся base64 в JSON-конверте, максимальный размер — настройка `ETNX_MAX_BYTES` (50 МБ).

- **два шага**: `preview` показывает, что внутри архива и сколько чего приедет, `commit` выполняет импорт;
- оба маршрута требуют членства в сети; `commit` дополнительно идемпотентен по `Client-Request-Id`;
- **корневые мысли архива** (без входящих связей внутри архива) прикрепляются к `parent_thought_id` как дети;
- политика дедупликации — по id, затем по нормализованному имени, иначе создать;
- ответ несёт счётчики (создано/обновлено мыслей, создано связей, импортировано вложений).

**Дополнительные материалы**
- относится к подсистемам: Экспорт и импорт, REST API
- зависит от: Формат .etnx — архив переноса мыслей
- применяется к: Экспорт и импорт .etnx в контексте слоя, Импорт .etnx: сопоставление мыслей и правила слияния

## /locks — захват, снятие и сброс захватов объектов

Управление захватами объектов редактирования.

```
POST   /api/v1/networks/{nid}/locks
       { entity_type, entity_id }  → 200 { lock_id, user_id, acquired_at_ms }
       чужой активный захват → 409 LOCKED { holder: { user_id, name } }
DELETE /api/v1/networks/{nid}/locks/{lock_id}   → 204 (свой захват)
POST   /api/v1/networks/{nid}/locks/clear
       { user_id }  → 200 { cleared }   — снять все захваты участника
GET    /api/v1/networks/{nid}/locks   → 200 { data: [активные захваты] }
```

- захват привязывается к WebSocket-подключению; без живого WS-сокета acquire отклоняется (`VALIDATION_ERROR`);
- `clear` доступна любому участнику сети (равноправие); рассылает `edit.cleared`;
- acquire/release рассылают `edit.acquired` / `edit.released` по сети (audience=network).

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: object_locks — захваты объектов редактирования
- применяется к: Требование: захват объекта — границы и запрет записи

## /me/keys — управление своими API-ключами

Пользователь сам заводит и отзывает свои ключи доступа — отдельный ключ на каждый клиент и на каждого агента.

```
GET    /api/v1/me/keys        # список: только prefix, без полного ключа
POST   /api/v1/me/keys        { label, read_only?, max_writes_per_minute? }
                              → 201 { data: { id, key, prefix } }
PATCH  /api/v1/me/keys/{id}   { max_writes_per_minute: null | int }
DELETE /api/v1/me/keys/{id}   # отозвать
```

**Полный ключ возвращается только один раз — в ответе на создание.** Дальше виден только префикс: в базе хранится хеш, восстановить потерянный ключ невозможно — только выпустить новый.

- `read_only` — ключ только для чтения (пригоден агенту-наблюдателю);
- `max_writes_per_minute` — персональный бюджет записей ключа; `null` снимает персональный лимит и возвращает к серверному умолчанию;
- `DELETE` — отзыв: ключ перестаёт работать немедленно.

**Дополнительные материалы**
- относится к подсистемам: REST API, Аутентификация и права доступа
- зависит от: api_keys — таблица ключей доступа
- применяется к: Отзыв ключа разрывает активные WebSocket- и MCP-подключения

## /networks/{id}/members — участники сети и передача владения

Управление составом участников мыслесети; операции доступны владельцу сети (и админу).

```
GET    /api/v1/networks/{id}/members         # список участников
POST   /api/v1/networks/{id}/members         { user_id }   # добавить как member
PATCH  /api/v1/networks/{id}/members/{uid}   { role }      # передача владения
DELETE /api/v1/networks/{id}/members/{uid}                 # исключить
```

**Передача владения** — `PATCH { role: "owner" }`: в одной транзакции текущий владелец становится `member`, а указанный участник — `owner`. Двух владельцев одновременно у сети не бывает.

Администратор может менять членство принудительно через админский маршрут — без участия владельца.

**Дополнительные материалы**
- относится к подсистемам: REST API, Аутентификация и права доступа
- зависит от: network_members — членство пользователей в мыслесетях

## /networks/{id}/preferences — серверные предпочтения пользователя в сети

Настройки уровня «пользователь × мыслесеть», хранимые на сервере и общие для всех устройств пользователя.

```
GET /api/v1/networks/{id}/preferences         # все ключи
PUT /api/v1/networks/{id}/preferences/{key}   { value: <json> }
```

Поддержанный ключ — `show_inactive` (показывать ли неактуальные мысли и связи). Значение служит умолчанием для фокуса, поиска, отборов и списков связей, если запрос не передал `show_inactive` явно.

Не путать с клиентским состоянием (геометрия окон, последний фокус): то живёт локально и на сервер не ездит.

**Второй ключ видимости — `show_trash`** (задача 77923b49, коммит e55e5c6, 0.8.2): показывать ли помеченные на удаление мысли и связи. Дефолт — `true` (поведение после 355319d4 не меняется); `false` прячет помеченное в фокусе и соседях, рёбрах, иерархии и списке связей мысли. Флаг резолвит сервер (`resolveShowTrash`), явный параметр запроса сильнее настройки. Поддержанные ключи: `show_inactive`, `show_trash`, `canvas_link_filter`.

---

**Термин (глоссарий 10).** **Серверные предпочтения** (`user_preferences`) — пользовательские настройки в сети, хранимые на сервере (например `show_inactive`), в отличие от локальных UI-state, которые остаются на клиенте.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: user_preferences системной БД — серверные настройки пользователя в сети

## /networks/{nid}/properties — справочник свойств сети

Управление справочником свойств сети — свойства живут рядом с типами, а не внутри них.

```
GET    /api/v1/networks/{nid}/properties              # весь справочник
POST   /api/v1/networks/{nid}/properties              { name, value_type, config?, description? }
GET    /api/v1/networks/{nid}/properties/{id}
PATCH  /api/v1/networks/{nid}/properties/{id}         { name?, value_type?, config?, description? }
DELETE /api/v1/networks/{nid}/properties/{id}
GET    /api/v1/networks/{nid}/properties/{id}/usage   # где подключено и где заполнено
```

**Создание свойства-связи.** `POST` с `value_type: "link"` создаёт и тип связи: имена сторон передаются в том же теле и записываются в `name_forward`/`name_reverse`. Свойство-связь и тип связи живут одним жизненным циклом (Свойство-связь и тип связи — единый жизненный цикл).

**Список** — плоский, без иерархии; у каждого свойства кроме своих полей есть `types_count` (сколько типов его подключило, считая и типы связей) и `values_count` (сколько значений заполнено). Для свойства-связи `types_count` распадается на счётчики сторон — сколько типов подключено со стороны источника и сколько со стороны назначения. Сверх счётчиков свойство-связь несёт производные `binding_source_type_ids` / `binding_target_type_ids` — id типов привязок каждой стороны (вычисляются по `type_properties`, не хранятся; те же поля отдаёт `GET /properties/{id}`). Из них строки без эффективного определения типа (внетиповая строка, массовый диалог) строят ограничение значения по противоположному концу привязки — см. «Ограничение типов значения свойства-связи» в properties — справочник свойств сети. (2026-10-24, ошибка f8f8fa49.)

**`usage`** возвращает список типов с привязками (id, имя, мысли или связи, обязательность) и счётчики значений — раздельно для значений в типе и значений вне типа.

**Ошибки.**

- `409 DUPLICATE` — имя занято (регистронезависимо); `details.property_id` — кто занял, чтобы клиент предложил подключить существующее;
- `409` на `DELETE` — свойство держат привязки или значения; в `details` оба счётчика — действует для скалярных свойств;
- `422` — неверный `value_type` или `config`.

**Удаление свойства-связи** удаляет и его тип связи — принудительно (Свойство-связь и тип связи — единый жизненный цикл): рёбра не удаляются, а теряют `type_id` и становятся структурными; в ответе — число затронутых рёбер. Для скалярных свойств прежняя блокировка удаления (`409` по привязкам и значениям) сохраняется.

**Смена `value_type`** через `PATCH` в той же транзакции преобразует значения во всех типах, где свойство подключено, и во всех значениях вне типа; несовместимые удаляются. Ответ несёт число преобразованных и число удалённых значений. Внутри скалярной категории (`text`/`number`/`date`/`bool`/`url`) конвертация работает как раньше; переход между скалярной категорией и видом «связь» в обе стороны — `422 VALIDATION_ERROR` (Категория вида значения неизменна: скаляры и «связь» не конвертируются).

**События real-time:** `property.created`, `property.updated`, `property.deleted` — отдельные от `property-definition.*`, которые теперь относятся к привязкам.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: properties — справочник свойств сети
- применяется к: Категория вида значения неизменна: скаляры и «связь» не конвертируются, Свойство-связь и тип связи — единый жизненный цикл, Вид значения «тип связи» в реестре свойств

## /pins — закреплённые мысли пользователя

```
GET /api/v1/networks/{nid}/pins   → 200 { data: [ { thought_id, position } ] }
```

- список персонален и синхронизируется между клиентами событием `pinned-thoughts.updated` (`audience = user`);
- метаданные мыслей панель берёт пакетным запросом метаданных, как панель истории.

**Дополнительные материалы**
- относится к подсистемам: REST API, Пользовательский интерфейс (холст и редактор)

## /saved-filters — именованные отборы «Структур», «Хроники» и «Событий»

Именованные наборы критериев и сортировки для трёх видов: «Структуры мыслей» (`structures`), «Дневник» (`chronicle`) и «События» (`events`).

```
GET    /api/v1/networks/{nid}/saved-filters?view=structures|chronicle|events
       → 200 { data: [ { id, view, name, definition, created_at, updated_at } ] }
POST   /api/v1/networks/{nid}/saved-filters       { view?, name, definition }
PATCH  /api/v1/networks/{nid}/saved-filters/{fid} { name?, definition? }
DELETE /api/v1/networks/{nid}/saved-filters/{fid}
```

- хранятся **per-user** в базе сети и синхронизируются между клиентами пользователя событиями `saved-filter.*` (`audience = user`);
- пользователь видит и меняет **только свои** отборы; публикация другим — вне MVP; уникальность `name` — в пределах пары (пользователь, вид), поэтому одинаковые имена в разных местах разрешены;
- `view` по умолчанию `structures` (обратная совместимость) и **не меняется** при правке. На `PATCH` вид определения берётся из **сохранённой строки**, а не из тела: присланный `view` не выбирает парсер и не переписывает вид (0.13.3, задача c0c7b834);
- `name` — 1..200 символов, уникально в пределах пары (пользователь, вид); повтор — `409 DUPLICATE`;
- `definition` валидируется **по виду строки**: `structures` — AST (`{ version, filter, sort? }`) либо легаси `definition v1`; `chronicle` — `{ ast, order }`; `events` — только AST профиля `events` **без сортировки** (присланный `sort` снимается — порядок ленты задаёт сервер, `occurred_at_ms DESC`). Форма чужого вида и операнд/оператор вне профиля `events` — `422 VALIDATION_ERROR`;
- миграций нет: `saved_filters.view` не имеет CHECK, новое значение вида пишется строкой.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: saved_filters — именованные отборы видов
- применяется к: Сервер: тест записи покрывает каждое значение вида REST-контракта

## /thoughts/{id}/properties — чтение и запись значений свойств

```
GET    /api/v1/networks/{nid}/thoughts/{id}/properties
PUT    /api/v1/networks/{nid}/thoughts/{id}/properties/{key}   { value: …, side?: "source"|"target" }
DELETE /api/v1/networks/{nid}/thoughts/{id}/properties/{key}?side=source|target

# /links/{id}/properties — контракт существует, в 0.14.1 НЕ меняется (ADR «у ребра нет собственных атрибутов» не пересматривается)
```

`PUT` — upsert с валидацией по свойству из справочника.

**Чтение возвращает и значения вне типа.** У каждого значения есть `property_id`, имя, тип значения и флаг `outside_type`: `true` — свойство не подключено к типу владельца (после смены типа, отключения свойства от типа или прямой записи — 0.14.1). Такие значения клиент показывает отдельной группой; см. требование «Значения вне типа сохраняются».

**Разрешение свойства при записи (0.14.1)** — по **всему справочнику сети**: привязка свойства к типу владельца не проверяется, `422` — только для свойства, отсутствующего в справочнике (требование «Запись значения допускается для любого свойства справочника», ADR «внетиповое значение — штатное состояние»). До 0.14.1 действовал резолв по привязкам типа владельца с `422` для неподключённого — отменён.

**Параметр `side` у свойств-связй (уточнение аудита, цикл 3).** `side` — **адрес стороны**. При записи: указывает, рёбра какой стороны создаёт операция (симметричный тип с одной живой стороной: запись со `side=target` создаёт рёбра целевой стороны, сверки с живыми рёбрами этой стороны нет — их ещё нет). Сверка с фактическим направлением применяется при удалении/очистке и когда у стороны уже есть рёбра (`422` при расхождении). Неоднозначность (симметричное имя и обе стороны живы) без `side` — `422`.

**Множественные значения** (`config.multiple`): `url` — массив строк: пустой массив очищает значение, одиночная строка нормализуется в массив из одного, массив без флага `multiple` — `422`, дубликаты схлопываются. Set-запись свойства-связи работает по живым рёбрам: цель в корзине set-набором не восстанавливается и не удаляется.

### Свойства-связи (0.8.1)

`GET` возвращает и свойства-связи: по каждому — `property_id`, вычисленное имя `property_name` (из типа связи по стороне привязки; у внетиповых — по положению владельца в ребре), `value_type: "link"`, `side` — сторона у владельца, `link_type_id`, счётчик `count` живых рёбер и список `values` (по каждому ребру: `link_id`, `target_id`, `target_title`, `target_type_id`, постоянный комментарий ребра `comment`). Значения таких свойств в `property_values` не хранятся — проекция рёбер (ADR «свойство-связь — проекция ребра»). Пустых внетиповых свойств-связей не существует: `count = 0` — свойство исчезает из выдачи.

### Ревизия 2026-10-19 (устарела частично 0.14.1)

В 0.13.2 `DELETE` на свойстве-связи снимал пометку корзины со всех живых рёбер свойства у владельца (команда «Очистить свойство» панели использования). **С 0.14.1 это поведение отменено** — см. следующую секцию.

### Ревизия 0.14.1

- **Запись**: резолв ключа по всему справочнику (выше); правка внетипового значения разрешена. **Создание/правка значения свойства-связи (создание ребра) через REST `PUT` и MCP write-wrapper входит в задачу Z1 техпроекта 0.14.1** со сверкой обоих путей.
- **`DELETE` на свойстве-связи — умное удаление живых рёбер** (в основе — физически; в слое — корзина для существующих в основе/предках, физически для созданных в слое; уже помеченное — no-op; слияние — стандартный посрочный реплей) — требование «Удаление цели свойства-связи — умное», ADR a967d865. Восстановление рёбер — `PATCH /links/{id} { marked_for_deletion: false }` (REST, «Очистить» в GUI) или `links.restore` (MCP).
- **Порядок внетиповых** — отдельная операция PUT /thoughts/{id}/properties/order; `GET` возвращает эффективный порядок (явные позиции, хвост — по `property_values.created_at` / `MIN(created_at)` живых рёбер; колонка добавляется миграцией 0.14.1).

**Уточнение по верификации Z1 (0.14.1).** Правило выбора создаваемого ребра при отсутствии живых: если у владельца нет живых рёбер этого свойства, направление для создания выводится из стороны привязки / `config.direction` — это выбор того, какое ребро создать, а не хранение направления (ADR «свойство-связь — проекция ребра» не нарушается). Симметричное имя с двумя записями в эффективном наборе типа, живых рёбер нет — `side` не обязателен (выводится по этому правилу); обязателен только при живых рёбрах обеих сторон.

**Уточнение 2 (финал Z1, коммит 8343aee3).** Правило выбора направления при отсутствии живых рёбер уточняется: направление берётся от ЯВНОЙ (не зеркальной `mirrored`) записи привязки; `config.direction` синтетического зеркала из `allowed_target_type_ids` игнорируется; при нескольких явных записях одного свойства — каноническое направление общего `config`. Авто-вывод стороны действует только когда все кандидаты набора — одно свойство; коллизия display-имён разных свойств без `side` — `422` (details.field: side).

### Уточнение 3 — приоритет `side` при записи (ошибка d9bc6012, 0.14.1)
При записи явный `side` **приоритетен над именем**: имя только резолвит свойство (в том числе реестровое имя, чья display-форма адресует противоположную сторону), а `side` адресует сторону создаваемого/правимого ребра. Отдельного отказа «сторона противоречит имени» нет — его не было ни в техпроекте `bd349082`, ни в ADR `cb95fb4e`, ни в этой спеке. Клиент передаёт согласованную пару «имя видимой стороны + её сторона», но сервер на явный `side` ограничений от имени не накладывает. То же правило у `etn.properties.add`.

`422 VALIDATION_ERROR` при записи свойства-связи:
1. свойства нет в справочнике сети (`details.key`);
2. настоящая неоднозначность без `side` — симметричное имя, обе стороны живы (`details.field = "side"`, `details.reason = "side-required"`);
3. коллизия display-имён разных свойств сети: без `side` — `details.field = "side"`, `details.reason = "side-required"`; с `side`, если сужение по стороне не оставило ровно одно свойство, — `details.field = "property"`, `details.reason = "property-ambiguous"`;
4. значение не того типа, который допускает привязка целевой стороны (`details.key`, `details.ref`, `details.allowed_type_ids`, `details.actual_type_id`).

Сверка при удалении/очистке сохраняется: указанная сторона пуста, а противоположная жива — `422` с `details.field = "side"`, `details.reason = "side-mismatch"`. Машиночитаемые причины — `PROPERTY_SIDE_ERROR_REASON` в `@etn/shared`; клиент переводит их в человеческий текст без внутренних терминов `source`/`target`. Тексты `422` этой группы — русские и пользовательские, без английских фраз: их читают и MCP/REST-клиенты.

**Ограничение цели при записи (уточнение круга 2, 2026-10-27).** Явный `side` НЕ отменяет валидацию цели по привязке. Если запись адресована **типовым ключом** (ключ строки эффективного набора типа владельца), тип значения проверяется по привязке той стороны, на которой стоит владелец в создаваемом ребре: стороной явного `side`, а без него — стороной привязки/имени. Допустимые типы — привязки противоположной стороны (`loadBindingTypesBySide`, поддеревья раскрываются). Пример: `PUT` задаче типовым именем «версия» + `side=target` со значением-версией → `422` (для стороны назначения допустимы типы источников ребра — задача/ошибка); то же имя + `side=source` со значением-задачей → `422` (допустимы версии); типовое имя без `side` со значением-версией → `200`.

**Внетиповая строка — без реестрового ограничения.** Если ключ — display-имя свойства-связи, не подключённого к типу владельца этой строкой/стороной (внетиповая строка: обратная сторона на задаче и т. п.), привязки владельца у строки нет — реестровое ограничение цели не применяется, остаётся legacy `config.allowed_target_type_ids`. Это сохраняет пользовательский сценарий ошибки: задача пишет «работы версии» (видимое имя обратной строки) + `side=target` со значением-версией — ребро создаётся. Имя реестра, не совпавшее с ключом эффективного набора (устаревший снимок после переименования типа связи), трактуется так же — legacy `config`.

Тип ВЛАДЕЛЬЦА не проверяется ни в одном случае: свойство назначается любой мысли, включая представителя целевого типа (ADR `cb95fb4e`). `allowed_opposite_type_ids` остаётся ограничением ЦЕЛИ для живой подсказки/пикера выбранной стороны (прямая строка — типы target-привязок, обратная — типы source-привязок).

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: property_values — значения свойств мыслей и связей
- применяется к: Запись значения допускается для любого свойства справочника, Карточка отдаёт связи счётчиками; запрос значений возвращает идентификатор ребра, Удаление цели свойства-связи — умное, ADR: пер-мысленный порядок внетиповых — отдельная ветвимая таблица, ADR: умное удаление ребра — физически в основе, корзина в слое только для существующих выше, Операции над набором значений: добавить, убрать, заменить, Запись кросс-сетевой ссылки: валидация и первичный снапшот, Наследование привязок по цепочке типов, ADR: внетиповое значение — штатное состояние, запись свободна, Заполнение свойства-связи создаёт ребро без указания направления, Свойство-связь можно навесить на мысль вне типа, Обязательное свойство-связь проверяется сервером при записи

## /types/{id}/properties — определения свойств типа и их порядок

Управление **привязками** свойств к типу — контракт действует только для `/thought-types/{id}/properties`: у типов связей привязок нет (упразднены в 0.8.1). Природа свойства правится не здесь, а в справочнике (`/networks/{nid}/properties`).

```
GET    …/types/{id}/properties     # ЭФФЕКТИВНЫЙ список: свои привязки + унаследованные
POST   …/types/{id}/properties     { property_id }  |  { name, value_type, config?, description? }
PATCH  …/types/{id}/properties/{propertyId}                { required?, position?, side? }
DELETE …/types/{id}/properties/{propertyId}                # отключить; значения остаются
PUT    …/types/{id}/properties/reorder                     { ordered_ids: […] }
PUT    …/types/{id}/properties/{propertyId}/default        { value: … | null }
PUT    …/types/{id}/properties/{propertyId}/description    { description: string | null }
```

**Подключение (`POST`) — две формы.** С `property_id` подключается существующее свойство справочника. С `name` + `value_type` свойство сначала создаётся в справочнике, потом подключается — это форма для быстрого ввода из редактора типа; занятое имя даёт `409 DUPLICATE` с id занявшего, и клиент предлагает подключить его.

**Эффективный список** сохранил прежнюю форму ответа: `key`, `value_type`, `required`, `config`, `inherited`, `defined_on`, `defined_on_name`, эффективные `default_value` и `description`, флаги `overridden_here`/`description_overridden`. Добавлено поле `property_id` — идентификатор свойства в справочнике; именно им адресуются значения и условия отбора.

**Подключение свойства, уже подключённого потомком,** удаляет избыточные привязки во всём поддереве типов в той же транзакции (см. «Наследование привязок по цепочке типов»). Значения при этом не меняются. Прежний `409 DUPLICATE` по совпадению ключа в цепочке или поддереве отменён.

**`PATCH` меняет только роль** — обязательность, порядок и сторону привязки `side` (`'source'`/`'target'`, для привязок свойств-связей). Попытка передать `value_type`, `config` или имя — `422`: это поля свойства, а не привязки.

**`DELETE` отключает свойство от типа и значения НЕ удаляет** — они становятся значениями вне типа (см. «Значения вне типа сохраняются»). Прежнее каскадное удаление значений отменено.

**`default` и `description` переопределяются только для унаследованного** свойства; для подключённого самим типом — `422` (правь в справочнике, там одно значение на всю сеть). `null` сбрасывает переопределение, сброс одного аспекта не трогает второй. `PUT …/default` работает для обеих сторон привязки: у стороны назначения значение по умолчанию — это набор мыслей-источников (Привязка со стороны назначения равноправна с привязкой источника).

**События real-time:** `property-definition.created/updated/deleted` — теперь про привязки; изменения самого свойства приходят как `property.*`.

**Идемпотентность подключения (0.8.2, ошибка 0bfd7180).** Повторный `POST` того же свойства к тому же типу — идемпотентная операция, а не ошибка: привязка не дублируется и не пересоздаётся, а обновляется на месте (тот же логический `id`), роль берётся из тела запроса, порядок без явного `position` не меняется. `409 DUPLICATE` остаётся только для привязки ПРЕДКА (свойство и так наследуется) и для занятого имени в форме `{ name, value_type }`. Прецедент — MCP `etn.ontology.write` (`type_properties[].action` `unchanged`/`updated`): клиенту не нужно знать, создаёт он привязку или до-писывает существующую, поэтому «создал свойство из диалога выбора → выбрал → сохранил тип» всегда заканчивается успешной записью.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: type_property_overrides — переопределения значений по умолчанию, type_properties — привязка свойства к типу
- применяется к: Наследование привязок по цепочке типов, Пара «тип связи + направление» уникальна в наборе свойств типа

```
GET    /api/v1/networks/{nid}/thoughts/{id}/attachments   → вложения объекта (по владениям)
POST   /api/v1/networks/{nid}/thoughts/{id}/attachments
       { kind: "url"|"file", url? | file_path?, title?, description?, mime_type? }
PATCH  /api/v1/networks/{nid}/attachments/{id}
       { title? | description? | icon? }
# аналогично для /links/{id}/attachments и /publications/{id}/attachments (owner_type ∈ thought|link|publication)
```

`GET …/attachments` возвращает вложения, которыми владеет объект (через `attachment_owners`), в порядке владения (`attachment_owners.position`). Счётчик вкладки «Вложения» — число владений объекта.

Полное удаление вложения и файла выполняет owner-cleanup автоматически, когда снят последний живой владелец во всех слоях. Снятие ОДНОГО владения — `DELETE /attachments/{id}/owners` (с защитами требования `6b524569`).

- относится к подсистемам: REST API
- зависит от: attachments — вложения мыслей и связей

## CRUD комментариев мыслей и связей

```
GET    /api/v1/networks/{nid}/thoughts/{id}/comments
POST   /api/v1/networks/{nid}/thoughts/{id}/comments
       { kind: "permanent"|"chronological", title?, body_md, valid_from?, valid_to?, use_time? }
PATCH  /api/v1/networks/{nid}/comments/{id}   If-Match
       { title?, body_md?, valid_from?, valid_to?, use_time? }
DELETE /api/v1/networks/{nid}/comments/{id}   If-Match
# аналогично для /links/{id}/comments
```

Два рода комментариев:

- **постоянный** — содержимое мысли; у владельца он **ровно один**: попытка создать второй — `409`. Поля `valid_from`/`valid_to` для него игнорируются;
- **хронологический** — датированная запись о событии; таких записей сколько угодно, и она может быть привязана к нескольким владельцам.

Сервер хранит и исходный `body_md`, и рендер `body_html`: клиенту не нужен собственный markdown-движок.

### Даты и флаг (0.10.1)

Создание и правка хронологического комментария принимают `valid_from`/`valid_to` как полный UTC-инстанс ISO-8601 или «голую дату» (сутки UTC). `valid_to` у хронологической не может остаться пустым: незаполненное = `valid_from`. Флаг `use_time` («учитывать время») — обычное поле записи; его принимают и `POST`, и `PATCH` — правка может включить или снять флаг, не трогая даты. У постоянного комментария `valid_to` остаётся `NULL`. См. ADR времени и требования к формату дат.

**Ревизия (2026-09-27, итерация приёмки №11, ошибка f45fac74).** В сигнатуру `PATCH /comments/{id}` добавлены поля тела `valid_from`/`valid_to`/`use_time`; уточнено, что `use_time` правкой включается и снимается. Раньше REST-карта правки не читала `use_time` (поле было только в zod-схеме контракта `RestCommentUpdate`) и флаг терялся — ошибка f45fac74, исправлено в контракте.

### Пустое тело (2026-10-13, ошибка 00f1d0e6)

`body_md` может быть пустой строкой — и на создании (`POST`), и на правке (`PATCH`): пустой комментарий не является ошибкой, очистка текста и сохранение проходят синхронно у постоянного и у хронологического комментария. Пустая строка сохраняется как пустая (комментарий не удаляется), повторное наполнение работает штатно. Ограничение по содержанию осталось только у хроно-записи и оно не про текст: нужна хотя бы одна привязка (`targets`), иначе `VALIDATION_ERROR` с `details.field = targets` (требование 53ce7e9b).

- относится к подсистемам: REST API
- зависит от: comments — постоянные и хронологические комментарии
- применяется к: Сервер: тест записи покрывает каждое значение вида REST-контракта, Инварианты привязки комментариев к владельцам, Серверный рендер markdown и политика безопасности HTML

## CRUD отборов типа: GET, POST, PATCH, DELETE /thought-types/{id}/views

Отборы — вложенный ресурс типа мысли.

```
GET    /api/v1/networks/{nid}/thought-types/{id}/views
→ 200 { data: [ View ], meta: { effective } }

POST   /api/v1/networks/{nid}/thought-types/{id}/views
       { name, description?, definition, position?, is_default? }
→ 201 { data: View }

PATCH  /api/v1/networks/{nid}/views/{view_id}   If-Match
       { name?, description?, definition?, position?, is_default? }
DELETE /api/v1/networks/{nid}/views/{view_id}   If-Match
```

`View`: `id`, `type_id`, `name`, `description`, `definition`, `position`, `is_default`, `version`, `created_at`/`updated_at`/`created_by`.

**`GET` отдаёт собственные отборы типа;** `meta.effective` — эффективный набор с учётом наследования от предков, каждый элемент помечен типом-владельцем и признаком перекрытия. Редактор типа показывает первое, холст — второе.

**`definition` валидируется целиком:** неизвестные поля критериев отвергаются `422` (как и в отборе мыслей), токены проверяются по пространству имён типа — свойство должно быть подключено к типу или его предкам.

**`is_default: true`** снимает пометку с прежнего отбора того же типа в той же транзакции. **`position`** — перестановка внутри типа; пропуски в нумерации допустимы. **Без `position` новый отбор встаёт в конец списка:** сервер назначает позицию как максимум+1 среди отборов типа (0.7.4, ошибка a62190d1). Раньше дефолт был `0`, поэтому у типов, чьи отборы заводили через UI (клиент `position` не передаёт), все строки получали позицию 0, и перестановка ▲/▼ обменом позиций соседей не меняла порядок.

Правки идут в текущий слой сессии. Удаление отбора в слое поверх основы — надгробие, а не физическое удаление.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: thought_type_views — именованные отборы типов мыслей, thought_types — типы мыслей и их иерархия

## CRUD связей: POST, GET, PATCH, DELETE /links

```
POST   /api/v1/networks/{nid}/links   { source_id, target_id, type_id?, active? }
GET    /api/v1/networks/{nid}/links/{id}
PATCH  /api/v1/networks/{nid}/links/{id}   If-Match
       { source_id?, target_id?, type_id?, active?, marked_for_deletion? }
DELETE /api/v1/networks/{nid}/links/{id}   If-Match
```

Связь направленная: `source_id` — родитель, `target_id` — ребёнок. `type_id` может быть `NULL` — это нормальная нетипизированная связь.

`marked_for_deletion` работает так же, как у мыслей: «Поместить в корзину» / «Вернуть из корзины».

**Удаление** физическое и только если связь не заблокирована; при блокировке — `422 VALIDATION_ERROR` с `details.blocking`, связь не меняется. У связи нет собственного использования в свойствах и нет детей, поэтому блокировать её может только удерживающая теневая строка в слое.

Вместе со связью удаляются её комментарии, вложения (включая серверные копии файлов) и значения свойств — полиморфные владельцы без SQL-FK; отдельные события на них не эмитятся.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: deletion-check — проверка возможности удаления мысли или связи, links — направленные связи между мыслями
- применяется к: Удаление значения свойства-связи помечает ребро в корзину, Инварианты связи: без петель, уникальная тройка, смена концов только парой, Семейство операций etn.links.* упраздняется, кроме восстановления из корзины, Смена концов связи в рабочем слое создаёт новую связь с новым id

## DELETE /attachments/{id}/owners — снять владение вложения

```
DELETE /api/v1/networks/{nid}/attachments/{id}/owners
     { owner_type: "thought"|"publication", owner_id: string, confirm?: boolean }
→ 200 { data: { removed: true, attachment_deleted: boolean } }
```

Снимает владение пары (вложение, объект) — кнопка удаления на вкладке «Вложения» (элемент `d3c419a9`). Защиты:

- `409 ATTACHMENT_OWNER_IS_ICON` — ЗАПРЕТ, если сам объект использует вложение как свою иконку/обложку (`icon_attachment_id`/`cover_attachment_id` = это вложение), без `confirm`;
- `409 ATTACHMENT_OWNER_IN_TEXT` — ПРЕДУПРЕЖДЕНИЕ, если вложение в текстах комментариев объекта, без `confirm`; повтор с `confirm: true` снимает владение (ссылки в текстах остаются, картинки перестают отображаться);
- иначе — тихое снятие.

После снятия последнего живого владельца ВО ВСЕХ слоях вложение и его файл удаляются (`attachment_deleted: true`). Идемпотентно; нет владения — `404`.

**Уточнение (аудит).** `owner_type` ∈ `thought` | `link` | `publication`. Эта операция — ЕДИНСТВЕННЫЙ путь снятия владельца; менить «Удалить вложение» с клиента должна звать её, а не несуществующий DELETE вложения (K2).

**Дополнительные материалы**
- зависит от: attachment_owners — владения вложения (вложение ↔ объект)
- применяется к: Снятие владения: защита своей иконки/обложки, предупреждение о текстах, чужие не мешают

## DELETE /layers/{id} — удаление слоя вместе с поддеревом

```
DELETE /api/v1/networks/{nid}/layers/{id}?cascade=<N>
→ 200 { data: { deleted, purged, skipped } }
```

- **основу удалить нельзя** — 422;
- `cascade` обязан равняться `children_count` из списка слоёв: без него при живых потомках — 422 с `details.children_count`; при несовпадении — 409 (картина клиента устарела); слой без потомков удаляется без параметра;
- удаление **каскадно сносит поддерево слоёв целиком** и физически удаляет все их теневые строки и надгробия. **Это не слияние**: ничто не переносится родителю, работа в слое теряется;
- сессии, сидящие на удаляемом поддереве, переключаются на родителя удаляемого слоя и получают real-time событие `layer.deleted`;
- сразу после удаления сервер сам выполняет автоочистку корзины (семантика `POST /trash/purge`): удалённые тени больше ничего не удерживают. Ответ несёт `purged`/`skipped`, а для автоудалённых строк эмитятся обычные `thought.deleted`/`link.deleted`.

**Дополнительные материалы**
- относится к подсистемам: Слои изменений (подсистема), REST API
- зависит от: GET и POST /layers — список слоёв и создание слоя, layers — таблица слоёв изменений

## DELETE /system/logs/:filename и DELETE /system/logs — удаление файлов журнала

```
DELETE /api/v1/system/logs/:filename     — удалить один файл
DELETE /api/v1/system/logs               — удалить все файлы журнала
```

## DELETE /thoughts/{id} — физическое удаление мысли и его каскад

```
DELETE /api/v1/networks/{nid}/thoughts/{id}   If-Match: <version>
→ 204
```

**«DELETE всегда значит удалить прямо сейчас, если не заблокировано»** — предварительная пометка на удаление не требуется.

Отказы:

- `422` для защищённой мысли (`is_protected = 1`);
- `422 VALIDATION_ERROR`, если удаление заблокировано: тело ошибки несёт `details.blocking` в том же формате, что и проверка возможности удаления; запись не удаляется и `marked_for_deletion` не меняется.

**Каскад** (если не заблокировано): мысль → синонимы, связи с обеих сторон. Комментарии, вложения и значения свойств — полиморфные владельцы без SQL-FK — чистятся приложением в той же транзакции — и у самой мысли, и у её удаляемых связей. Серверные копии файлов-вложений удаляются с диска по тому же правилу, что и при удалении вложения; отдельные события на зависимые строки не эмитятся.

**Дети мысли НЕ удаляются**: каскад бьёт по строкам связей, а не по дочерним мыслям. Ответ несёт `meta.orphaned_children` — сколько дочерних мыслей лишились этой связи; клиент показывает предупреждение ДО удаления — через проверку возможности удаления, а не постфактум.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: thoughts — таблица мыслей, deletion-check — проверка возможности удаления мысли или связи
- применяется к: Что блокирует физическое удаление мысли или связи и что уходит каскадом

## deletion-check — проверка возможности удаления мысли или связи

Предварительная проверка: можно ли физически удалить запись и что именно мешает.

```
GET  /api/v1/networks/{nid}/thoughts/{id}/deletion-check
→ 200 { data: { blocked: boolean,
                blocking: { properties: <число ссылающихся мыслей>,
                            layers: [ { id, title } ] },
                orphaned_children: <число> } }

POST /api/v1/networks/{nid}/thoughts/deletion-check-batch   { ids: […] }
→ 200 { data: { "<id>": { blocked, blocking, orphaned_children }, … } }

GET  /api/v1/networks/{nid}/links/{id}/deletion-check
POST /api/v1/networks/{nid}/links/deletion-check-batch
→ 200 { data: { blocked, blocking: { layers: [ { id, title } ] } } }
```

У связи тот же формат без `properties` и `orphaned_children`: на связь не ссылаются свойства и у неё нет детей.

**Проверка контекстно-зависима**: в рабочем слое собственные теневые строки текущего слоя удержанием не считаются, а живая строка основы попадает в `blocking.layers` элементом `{ id: <id основы>, title: «Основа» }`: «удалить совсем» такую строку в слое нельзя (получилось бы лишь надгробие), разрешена только пометка на удаление.

Batch-вариант — источник данных для диалога группового удаления и диалога «Корзина»: один запрос вместо N.

---

**Термин (глоссарий 10).** **Удерживающие ссылки** (`holding_layers`) — входящие формальные ссылки, мешающие удалить мысль: пока они есть, доступна только пометка на удаление, не стирание.

**Дополнительные материалы**
- относится к подсистемам: REST API, Слои изменений (подсистема)
- зависит от: property_values — значения свойств мыслей и связей
- применяется к: Что блокирует физическое удаление мысли или связи и что уходит каскадом, Блокировка удаления цели — флаг определения свойства-связи

## GET /attachments — поиск вложений по сети

```
GET /api/v1/networks/{nid}/attachments
    ?q=<keywords>&exclude_owner_type=<thought|publication>&exclude_owner_id=<id>
    &kind=<url|file>&limit=50&offset=0          # плоский путь (q-поиск)
  | ?ast=<json>&limit=50&offset=0               # AST-путь (XOR с плоскими полями)
→ 200 { data: Attachment[], meta: { total } }
```

Ищет по `title`, `description`, `url` и `file_path` (регистронезависимый LIKE с экранированием; отдельного FTS-индекса нет). Синтаксис `q` — общий мини-синтаксис ключевых слов (AND, `*`, `-слово`).

**С мульти-владением (ADR `9f90b010`)** список возвращает УНИКАЛЬНЫЕ вложения сети (одна строка — один файл/URL) независимо от числа владельцев; в элементе `Attachment` отдаётся число владельцев и признак «текущий объект владеет».

**Плоский путь без `q` возвращает пустой результат** — защита от случайного полного скана; полный листинг вложений сети не предусмотрен. С приходом AST-пути (см. ниже) «без `q` всегда пусто» больше НЕ верно: `ast`-тело даёт выборку по операндам профиля, а `q`-поиск не изменился.

`exclude_owner_type`/`exclude_owner_id` скрывают вложения, которыми УЖЕ владеет указанный объект (отбор по `attachment_owners`). Этим пользуется диалог добавления вложения в редакторе, чтобы не предлагать уже имеющееся.

**AST-тело (0.13.1, задача `5a007bed`, коммит `ca51ee6c`).** Маршрут принимает `?ast=<json>` — тело отбора профиля «вложения» (`{ version, filter, sort? }`), XOR с плоскими фильтрами `q`/`kind`/`exclude_owner_*`; одновременная передача → `VALIDATION_ERROR` (поле `ast`, `details.conflicts`). Плоской ФИЛЬТРУЕМОЙ формы у вложений не было (только `q`-поиск), поэтому компилятора нет — AST это НОВАЯ точка того же эндпоинта, результаты `q`-пути неизменны (фиксировано тестом). Операнды: `name` (заголовок: равно/не равно/содержит/не содержит/в списке/«есть слова»), `kind` (file/url), `mime_type` (равно/содержит/в списке), `owner` (владельцы: заполнено/не заполнено, в списке по типу, под-выборка по мыслям-владельцам `in`/`not_in`/`all_of`, «в иерархии», количество), `size` (байты: сравнения/«между»/заполнено). Исполняется единым AST-движком (`server/domain/attachment-service.ts`, `attachments_v`/`attachment_owners_v`), профиль `attachments` — реестр профилей `@etn/shared/filter-profiles` (ADR `0c02ab4f`); под-выборка владельцев валидируется профилем мыслей. Неисполнимые условия (удалённая сущность) — красная диагностика. Порядок результата — `created_at DESC` (как у `q`-поиска).

**DTO и usage (аудит).** Форма элемента `Attachment` и realtime-нагрузок — см. элемент спеки «DTO Attachment и события realtime (мульти-владение)». `GET /attachments/{id}/usage` (и MCP `attachments.usage`) возвращают по id ВЛОЖЕНИЯ: список владельцев + использования (иконки/обложки/вхождения в тексты), а не «по носителю».

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: attachments — вложения мыслей и связей
- применяется к: Вложения: операнды профиля — имя, тип, владельцы, размер, Переименование вложения: общий заголовок, доступно участнику, участвует в поиске, Мини-синтаксис ключевых слов: AND по словам, звёздочка, исключение

## GET /layers/{id}/diff — структурный дифф слоя против родителя

```
GET /api/v1/networks/{nid}/layers/{id}/diff
→ 200 { data: { layer: { id, title }, target_layer: { id, title },
                links: { added: [LinkDiffRow], removed: [LinkDiffRow],
                         type_changed: [{ id, from_type_id, to_type_id }],
                         reorder_collapsed: [{ thought_id, count }],
                         reparented: [{ thought_id, from_parent_id, to_parent_id }] },
                overridden: { thought_ids: […], link_ids: […] } } }
```

- `LinkDiffRow` — `{ id, source_id, target_id, type_id, position }`; сравнение идёт по **видимым** связям обоих контекстов — связи со скрытым концом исключены;
- `reparented` — свёртка 1:1 «одна входящая удалена + одна добавлена» у той же мысли (перецепка); более сложные случаи остаются честными парами added/removed;
- `reorder_collapsed` — свёртка position-only изменений по `source_id` (тот же формат, что у отчёта слияния);
- `overridden` — мысли и связи, имеющие версию слоя: собственные физические строки (тени, вставки, надгробия) **плюс владельцы зависимых строк** — синонимов, значений свойств, комментариев и вложений слоя. Правка свойства или комментария — такая же «правка мысли, уезжающая в основу при слиянии», как правка заголовка, — именно это множество клиент помечает на холсте;
- дифф основы (нет родителя) — 422; несуществующий id — 404.

Структурный дифф **слеп к изменениям текста**, поэтому в паре с ним обязателен текстовый дифф.

**Пагинация (ревизия 2026-09-30, задача `ddb67ddc`, коммит `cf9311da`).** Query-параметры: `sections` (повторяемый; подмножество `links.added|removed|type_changed|reorder_collapsed|reparented`, `overridden.thought_ids|link_ids`; неизвестная — 422), `limit` (1…1000, дефолт 200), `cursor` (keyset `next_cursor` предыдущей страницы; сортировка детерминированная секция+id). **Без параметров** — прежний полный отчёт (совместимость; используется синхронизацией перекрытий клиента). С любым из параметров — страница: `{ counts: {…все секции…}, sections: […], <данные только запрошенных секций>, limit, truncated, reason, next_cursor }`; страница ужимается байтовым бюджетом ≈48 КБ (limit — верхняя граница). Клиентский диалог отличий использует только постраничную форму (0.10.3, `52c776f1`).

**Дополнительные материалы**
- относится к подсистемам: Слои изменений (подсистема), REST API
- зависит от: Ветвимые и неветвимые таблицы: адресация строк парой id и слоя

## GET /layers/{id}/diff/doc — текстовый дифф слоя двумя markdown-документами

```
GET /api/v1/networks/{nid}/layers/{id}/diff/doc
→ 200 { data: { layer: { id, title }, target_layer: { id, title },
                layer_doc: "<markdown>", target_doc: "<markdown>" } }
```

Два **детерминированных** markdown-документа — по одному на контекст — для построчного сравнения на клиенте. Сервер не считает разницу сам — он готовит два сопоставимых текста.

Сборка плоская: все видимые мысли по `id`, у каждой — заголовок, постоянный комментарий, хроника и список исходящих связей. Детерминированность гарантируется порядком `id` и сортировкой связей по имени: без этого построчное сравнение давало бы ложные различия.

Иерархическая сборка документа — отдельная будущая работа; формат самого маршрута от неё не зависит.

Текстовый дифф **слеп к изменениям связей** — их показывает структурный дифф; оба маршрута обязательны и дополняют друг друга.

**Ревизия 2026-09-30 (задачи `ddb67ddc`, `52c776f1`).** Маршрут НЕ пагинируется и НЕ секционируется: строит два полных документа сети (ориентир — слой ~1142 перекрытых строк → ~17,5 МБ). Клиентский диалог «Отличия…» больше его не вызывает (0.10.3): точечный текстовый дифф одной мысли — `GET /layers/{id}/diff/thought/{thoughtId}`, большие слои — структурный дифф по секциям/страницам. Назначение маршрута — малые сети и точечный аудит/экспорт.

**Дополнительные материалы**
- относится к подсистемам: Слои изменений (подсистема), REST API

## GET /layers/{id}/diff/thought/{thoughtId} — по-мысленный текстовый дифф слоя

```
GET /api/v1/networks/{nid}/layers/{id}/diff/thought/{thoughtId}
→ 200 { data: { layer: { id, title }, target_layer: { id, title },
                thought_id, title, kind: "changed" | "added" | "removed" | "unchanged",
```

## GET /search — полнотекстовый поиск по сети

```
GET /api/v1/networks/{nid}/search?q=<text>&…
  ast=<json>                           # AST-условие мыслевых настроек (профиль thoughts), 0.13.1
  in=subtree&from_thought_id=<id>      # только в поддереве
  scope=thoughts|links|chronology|all  # умолчание all
  type_id=<id>&type_id=<id>            # типы мыслей (поддерево типов)
  link_type_id=<id>                    # типы связей (поддерево)
  show_inactive=true|false             # умолчание — из настроек пользователя
  trashed=true|false                   # умолчание false
  limit=50&offset=0
→ 200 { data: { by_names, by_texts, by_links, by_chrono },
        meta: { total_in_group: {…} } }
```

Группы результатов: по именам и синонимам мыслей, по текстам комментариев, по текстам связей и по хронике. Каждый результат несёт **сниппет с подсветкой** `<mark>…</mark>` вокруг совпадений (клиент рендерит его в своей теме), а группы по мыслям — также иконку найденной мысли.

**Синтаксис `q`** — тот же мини-синтаксис, что и у ключевых слов отбора: AND по словам, `*` — подстановка, `-слово` — исключение. **Запрос из одних исключений ничего не находит** (в отличие от отбора мыслей).

**Семантика совпадения — вхождение в любой части слова, не только с начала** (исправлено в 0.7.5, ошибка 0258fd9d): «публик» находит «опубликовано», «перепубликация» — не только слова, начинающиеся на «публик». Реализовано токенизатором FTS5 `trigram` (миграция `038_search_trigram.sql`) — он же даёт кейс-фолдинг кириллицы без какого-либо кастомного кода на стороне сервера. `*` внутри слова делит его на независимые литеральные фрагменты, объединяемые через `AND` (каждый должен встретиться где-то в тексте, относительный порядок фрагментов не гарантирован — в отличие от `LIKE`-паттерна `%…%…%`; это приемлемо, так как `*` внутри одного слова — редкий случай мини-синтаксиса, не основной сценарий бага).

**Ограничение индекса и область покрытия (Tier 1, см. хронику ошибки 0258fd9d):** триграмме нужно ≥3 символа на фрагмент — короче он не участвует в фильтрации. У мыслей (`by_names`) для таких фрагментов есть LIKE-fallback по `title_norm`/`synonym_norm` (уже NFC+lowercase, корректен для кириллицы) — они продолжают фильтроваться. У текстов комментариев (`by_texts`/`by_links`/`by_chrono`) такого fallback нет (`comments.body_md` не имеет нормализованной колонки) — запрос из одних коротких (<3 симв.) фрагментов для этих трёх групп возвращает пусто; при наличии хотя бы одного фрагмента ≥3 символа остальные (в т.ч. короткие) в эти три группы просто не участвуют в фильтрации. Полный паритет (Tier 2 — колонка `comments.body_norm`) пока не реализован.

**AST-условие мыслевых настроек (`ast`, 0.13.1).** Необязательный query-параметр `ast` — JSON-дерево отбора профиля `thoughts` (подкорень → строка «Родители/Потомки» «в иерархии»; типы мыслей; «показывать неактуальные»; «корзина»). Форма та же, что у тела `POST /thoughts/query`. Строгий разбор формы — доменный `parseFilterAst`, состав операндов — профиль `thoughts` (`assertFilterAstInProfile`); условие вне профиля даёт `VALIDATION_ERROR`.

**Правило `ast` XOR плоские МЫСЛЕВЫЕ параметры.** `ast` несовместим с одновременной передачей плоских МЫСЛЕВЫХ параметров (`type_id`, `show_inactive`, `trashed`, `in`/`from_thought_id`) — одновременная передача даёт `VALIDATION_ERROR`. Плоские мыслевые параметры сохранены для обратной совместимости и компилируются в тот же AST (паттерн `ast` XOR старые критерии в схеме тела `POST /thoughts/query`). Корпусные параметры (`q`, `scope`, `link_type_id`, `author_id`, `editor_id`) совместимы с `ast` всегда — в XOR не входят.

**Исполнение.** `ast` добавляется КОНЪЮНКЦИЕЙ к WHERE мыслевых FTS-групп (`filterAstClause`, `query-service.ts`); корпусные разделы (`by_links`, link-половина `by_chrono`) он не затрагивает. Ранжирование `ORDER BY rank` и сниппеты сохранены; множество id не материализуется. Подкорень выражается паттерном «ИЛИ(id в [корни], `parents` in_hierarchy [корни] с режимом `all_links`), включая сам корень». Веерный режим (`network_ids`) передаёт `ast`. См. требование «Поиск карты: настройки отбора компилируются в общий AST, текст запроса остаётся FTS» (`b91336e7`) и ADR «Точка поиска карты — гибрид: FTS-текст + AST-условия» (`7581ac14`).

### Кросс-сетевой режим (0.8.3, проектируется)

Веерная форма вызова — с перечнем сетей вместо `{nid}` (точная форма адреса — задача): та же семантика `q`, scope и групп, но выдача собирается по всем перечисленным сетям, у каждого результата `network_id`, в ответе справочник сетей (`id` + `display_name`). Только сети, где пользователь — участник; каждая читается в её сессионном слое; потолок выдачи и диагностика обрезки. Поведение одиночной сети не меняется. См. требование «Веерный режим поиска и выборки: network_ids».

**Ревизия (2026-10-13, задача d5e8ddc1, коммит 8a9f2481).** Точка поиска принимает необязательный `ast` (профиль `thoughts`); зафиксированы правило `ast` XOR плоские МЫСЛЕВЫЕ параметры при всегда совместимых корпусных, исполнение конъюнкцией к мыслевым FTS-группам (ранжирование и сниппеты сохранены) и паттерн подкорня «ИЛИ(id в [корни], parents in_hierarchy [корни] `all_links`)». Плоские мыслевые параметры сохранены для обратной совместимости. Актуализировано в одном цикле с кодом.

### Ревизия 0.14.1 (задача f0b06700): `*`-синонимы в `by_names`

Синтаксис `q` — мини-синтаксис §6.10 (AND по словам, `*`, `-слово`). В группе `by_names` слово запроса БЕЗ `*` совпадает литерально (FTS5-подстрока в названии/синониме) **ИЛИ** с ОДНИМ словом хранимого `*`-синонима по его границам: `проектиров*` находит «проектирование», `функциональност*` — «функциональности» (требование 35218826, сценарий «поиск»). Слова запроса независимы и могут совпасть с разными источниками одной мысли. Литеральные FTS-совпадения ранжируются как раньше (`rank`); pattern-совпадения идут ВТОРЫМ тиром после них, затем порядок `title_norm`/`id`; `meta.total_in_group.names` и `offset` учитывают оба тира. Слово запроса с `*` — только литерально (прежняя FTS-семантика); заголовок не расширяется; `-слово` симметрично включению. Сниппет pattern-совпадения не содержит `<mark>` — литерального вхождения в заголовке нет. Группы `by_texts`/`by_links`/`by_chrono` не затрагиваются; сеть без `*`-синонимов ведёт себя как раньше.

## GET /thoughts/{id}/hierarchy — один уровень иерархии для дерева

```
GET /api/v1/networks/{nid}/thoughts/{id}/hierarchy
    ?dir=parents|children&show_inactive=&exclude_ids=id1,id2,…&offset=0
    &link_filter={"type_ids":["<link_type_id>"],"include_structural":true}
→ 200 { data: { neighbors: [ ThoughtRef… ],
                edges: [ { id, source_id, target_id, type_id, color, style, width } ],
                truncated: false,   # DEPRECATED-алиас has_more
                has_more: false,
                directions: { "<thought_id>": { has_incoming, has_outgoing } } } }
```

Один шаг раскрытия ветки в дереве: соседи порцией 100 штук плюс связи между узлом и этой порцией.

- **`exclude_ids` применяются ДО `offset` и лимита** — так клиент убирает повторы в пределах ветки раскрытия (дедуп per-ветка). Пример: дети A = {Б, В}; при раскрытии Б с `exclude_ids=[A,Б,В]` из детей {В, Г} вернётся только Г;
- `offset` — сдвиг по уже отфильтрованному списку, отсортированному `alpha asc`; страница — 100 соседей. При запросе следующей страницы клиент передаёт те же `exclude_ids`, не добавляя в них уже показанных соседей той же ветки;
- до 1000 id в `exclude_ids`; сортировка соседей всегда `alpha asc` — дерево показывает единый стабильный порядок;
- `directions` даёт закраску эллипсов: есть ли у узла и соседей активные входящие/исходящие связи;
- `truncated` сохранён как алиас `has_more` только ради совместимости; новый код использует `has_more`;
- **`link_filter` — фильтр обхода по типам связей** (ошибка db504c1a, 0.8.2, коммит `8ee3bac`): JSON-объект `{ type_ids?: string[], include_structural?: boolean }` — та же форма и та же валидация, что у одноимённого поля тела `POST /thoughts/query`. Спуск идёт только по рёбрам перечисленных типов (каждый id — вместе с потомками по иерархии типов связей); нетипизированные (структурные) рёбра — только при `include_structural: true`. Соседи, `edges` ответа и `directions` считаются по тем же типам, поэтому раскрытая ветвь совпадает с результатами отбора `parent_ids` + `link_filter`. Параметр отсутствует — прежнее поведение (обход по всем рёбрам). Невалидный JSON, не-объект и пустой фильтр — `422 VALIDATION_ERROR` с `details.field = "link_filter"`. Клиент «Структур» кладёт сюда фильтр ПРИМЕНЁННОГО отбора.

**Видимость помеченных** (задача 77923b49, коммит e55e5c6). `show_trash` — настройка сети (дефолт `true`): при выключенной помеченные на удаление мысли и их рёбра не попадают ни в `neighbors`, ни в `edges`. Одноимённый строковый параметр переопределяет настройку. По умолчанию поведение прежнее — помеченные видны (355319d4).

**Признак корзины у соседа** (ошибка 8bbc9542, коммит `f188efa`, 0.8.2). `neighbors` — это `ThoughtRef`, и он несёт `marked_for_deletion` (канон отображения `REF_COLUMNS`): при включённой настройке помеченная мысль приходит с флагом, и дерево «Структур» рисует у неё метку корзины (клик — общий диалог восстановления/удаления). При выключенной настройке такой сосед в `neighbors` не попадает, и `directions` его ребра не считают — эллипс не обещает скрытого уровня (см. `POST /thoughts/query`).

- относится к подсистемам: REST API
- зависит от: links — направленные связи между мыслями

## GET /thoughts/{id}/mentions — неявные упоминания мысли в текстах

```
GET /api/v1/networks/{nid}/thoughts/{id}/mentions
→ 200 { data: [ { owner_type, owner_id, title, comment_id, snippet, active } ] }
```

Находит мысли и связи, в текстах которых встречается заголовок или синоним данной мысли. Один элемент на владельца: несколько совпавших комментариев схлопываются в один.

`active` — актуальность владельца: клиент показывает неактуальных только при включённой настройке и бледным начертанием.

**Термы упоминания** — части составного имени (имя разбивается по запятой: у «Проект А,Закрытые ошибки» ищутся оба терма по отдельности) и синонимы; термы соединяются через OR.

Каждый терм матчится как единое целое по правилам синонимов: слова без `*` совпадают точно (по границе слова, без склонений), `*` внутри слова не пересекает границу слова, слова многословного терма стоят подряд в заданном порядке. Поэтому «Проект А» находится в «Проект      А», но не в «А Проект»; склонения задаются `*`-синонимами.

**Реализация**: FTS даёт только кандидатов по литеральным префиксам слов, точную семантику проверяет регулярное выражение — фраза из нескольких префиксных токенов в FTS5 вырождается в AND отдельных слов.

- зависит от: thought_synonyms — синонимы мыслей

## GET /thoughts/{id}/neighbors — соседи мысли без смены фокуса

```
GET /api/v1/networks/{nid}/thoughts/{id}/neighbors
    ?dir=parents|children|siblings
    &sort=alpha|created|viewed|manual&order=asc|desc
    &limit=50&offset=0&type_id=…
```

Отдаёт соседей мысли **без перевода фокуса** и без записи метки просмотра — в отличие от фокус-запроса. Нужен там, где список соседей требуется служебно: drag-операции, диалоги выбора, агентский обход графа.

Поддерживает те же сортировки, что и зоны холста (включая `manual` для `parents`/`children`), пагинацию `limit`/`offset` и фильтр по типу мысли.

**`meta.total` — честный, не длина страницы** (bug fix 0.6.3, thought f2c7c7d3): считается тем же WHERE, что и выдача, но без LIMIT/OFFSET, поэтому `meta.total > data.length` — верный сигнал долистать через `offset`. До фикса `total` эхом повторял `data.length`, из-за чего раздел с более чем `limit` соседями выглядел полностью показанным.

**Видимость помеченных** (задача 77923b49, коммит e55e5c6, 0.8.2). Строковый параметр `show_trash` переопределяет настройку сети (дефолт — `true`): при `false` соседи и рёбра, помеченные на удаление (`l.marked_for_deletion` / `t.marked_for_deletion`), в ответ не попадают — как неактуальные при выключенном `show_inactive`. По умолчанию поведение прежнее (355319d4).

## GET /trash и POST /trash/purge — корзина мыслесети

```
GET  /api/v1/networks/{nid}/trash
→ 200 { data: { thoughts:     [ { …Thought,     blocked, blocking } ],
                links:        [ { …Link,        blocked, blocking } ],
                publications: [ { …Publication, blocked, blocking } ],   # 0.11.1
                shelves:      [ { …Shelf,      blocked, blocking } ] } } # 0.11.1

POST /api/v1/networks/{nid}/trash/purge            # тело необязательно
    { ids?: [ "<thoughtId|linkId|publicationId|shelfId>", … ] }         # 0.11.1: и публикации/полки
→ 200 { data: { purged: N, skipped: M } }
```

`GET /trash` — все помеченные на удаление записи, видимые в текущем слое, **каждая сразу с готовым результатом проверки блокировки** — чтобы диалог корзины не делал по запросу на строку. Список не постраничный: объём корзины по построению невелик — её регулярно опустошают. Разделы `thoughts`/`links` — с самого начала; `publications`/`shelves` — с 0.11.1 (карточки 200b87be, c80951ea): публикация блокируется живыми значениями свойств «Публикация» и удерживающими слоями, полка — рабочим слоем (её состав каскадом уходит вместе с ней, публикации живы); обе чистятся только в основе.

`POST /trash/purge` — «Удалить всё, что возможно»: физически удаляет каждую помеченную запись с `blocked = false`; заблокированные пропускаются **без ошибки** — это ожидаемый исход, а не сбой. Публикации обрабатываются доменным `purgePublication`, полки — со своим составом.

Необязательное `ids` сужает очистку до перечисленных записей — пер-элементное «Удалить совсем» (диалог удаления связи и экран корзины; `DELETE /links/{id}` снят 0.8.1, требование 3ea5c6af); с 0.11.1 принимает и id публикаций/полок. Запрошенный id вне корзины (не помечен или уже удалён) считается пропущенным; пустой массив — `VALIDATION_ERROR` (422), чтобы пустое тело по ошибке не чистило всё. Каскад: удаление мысли уносит её связи, удаление полки — её состав — кандидат, исчезнувший к моменту своей очереди, считается удалённым и получает своё событие `*.deleted`.

Тот же метод сервер вызывает сам сразу после удаления слоя и после слияния слоя — автоочистка снятых удержаний.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: deletion-check — проверка возможности удаления мысли или связи
- применяется к: Неактуальность, пометка на удаление и надгробие слоя — три разных механизма, Удаление значения свойства-связи помечает ребро в корзину

## GET и PATCH /me — профиль текущего пользователя

Самообслуживание владельца ключа: кто я и как меня зовут.

```
GET   /api/v1/me
→ 200 { data: { id, username, display_name, is_admin } }

PATCH /api/v1/me   { display_name?: string | null }
→ 200 { data: { id, username, display_name, is_admin } }
```

`GET /me` — штатный способ проверить валидность токена при подключении клиента.

`PATCH /me` меняет **только** `display_name` текущего пользователя:

- `is_admin`, `disabled`, `username` через этот маршрут не меняются — это делает админ через `PATCH /admin/users/{id}`;

- `null` или отсутствие поля — no-op, текущее значение сохраняется;
- успешное изменение пишется в журнал аудита: `category=user`, `action=user.update`, `details.display_name` с признаком `self: true` и `previous_display_name`.

```

PATCH /api/v1/networks/{id}   { display_name?, description?, when_to_use?,
```

## GET и POST /layers — список слоёв и создание слоя

Ресурс слоёв мыслесети.

```
GET  /api/v1/networks/{nid}/layers[?include_service=true]
→ 200 { data: [ Layer ] }

POST /api/v1/networks/{nid}/layers   { title, comment?, git_branch?, parent_id? }
→ 201 { data: Layer, meta: { version } }
```

`Layer`: `id`, `parent_id` (null у основы), `title`, `comment`, `git_branch`, `is_service`, `is_base`, `depth`, `created_by`, `created_at` (ISO-8601 до секунд), `last_activity_at`, `version`, `children_count`, `current`.

**Список:**

- по умолчанию **скрывает служебные слои** (`is_service = 1` — резервные копии слияний), иначе интерфейс завалит автосозданными; `include_service=true` показывает всё;
- `current: true` — у текущего слоя сессии: так сессия узнаёт свой слой без отдельного запроса (единственное чтение, сообщающее текущий слой);
- `children_count` — размер поддерева потомков (включая скрытые служебные); это же число клиент возвращает при удалении как `cascade`;
- сортировка — `depth`, затем `created_at`.

**Создание:**

- `parent_id` отсутствует — родителем становится текущий слой сессии; несуществующий — 404;
- **глубина ограничена**: родитель на 4-м уровне поверх основы — `422 VALIDATION_ERROR` (лимит «до 4 слоёв, 5 уровней с основой»);
- `title` — непустая строка до 200 символов; `comment`/`git_branch` — необязательные строки до 200 символов;
- **создание слоя не переключает сессию в него** — это отдельная операция выбора.

**Дополнительные материалы**
- относится к подсистемам: Слои изменений (подсистема), REST API
- зависит от: layers — таблица слоёв изменений

## GET и PUT /attachments/{id}/content — содержимое текстового вложения

Встроенный просмотр и правка текстовых файлов-вложений — без выхода во внешнее приложение.

```
GET /api/v1/networks/{nid}/attachments/{id}/content
→ 200 { data: { mime_type, text: string|null, html: string|null, truncated: boolean } }

PUT /api/v1/networks/{nid}/attachments/{id}/content   { data_base64, mime_type? }
→ 200 { data: { html: string|null } }
```

- работает только для `kind="file"` с текстовым типом (`text/*` или расширение `.txt`/`.md`/`.markdown`); для остальных чтение возвращает `text: null, html: null`, а запись — `422`;
- `text` обрезается на 200 000 символах с флагом `truncated: true`;
- `html` — markdown-рендер тем же безопасным рендерером, что и у комментариев; для не-markdown — `null`;
- запись перезаписывает файл (≤ 10 МиБ после декодирования), обновляет размер и MIME-тип, эмитит `attachment.updated`;
- **версионности нет** — last-write-wins: одновременная правка двумя клиентами молча теряет более раннюю.

- относится к подсистемам: REST API, Markdown-рендерер
- зависит от: attachments — вложения мыслей и связей
- применяется к: Серверный рендер markdown и политика безопасности HTML

## keyword_scope — где именно ищутся ключевые слова отбора

`keyword_scope` в отборе мыслей — подмножество `title` / `synonyms` / `comment` / `diary`, где именно искать ключевые слова.

- поле отсутствует или передан пустой массив — действует умолчание `["title", "synonyms"]`;
- `comment` ищет только по **постоянному** комментарию мысли, хроника сюда не входит;
- `diary` — дневниковые записи мысли (ревизия 2026-10-13, ошибка 2bc251de, требование 0882f8d5): мысль соответствует, если её хронологическая запись содержит слово — в теле или в заголовке записи; ни постоянный комментарий, ни наименование/синонимы сюда не входят;
- в листе AST `keywords` пустой `scope` — ОТКЛЮЧЁННОЕ условие: режима «искать везде» нет (требование 0882f8d5). Умолчание `["title", "synonyms"]` — поведение ПЛОСКОГО тела (поле `keyword_scope` отсутствует), к операнду AST оно не применяется;
- исключающие слова проверяются по тем же источникам, что и включающие.

**Контекст отбора хроники (ревизия 2026-10-13, ошибка fc97548d, требование ce111b0d).** В профиле хроники та же область `comment` ищет шире: постоянный комментарий мысли И комментарии её инцидентных связей с обеих сторон (фаза 1 двухфазного отбора) — слово, найденное только в комментарии связи, отбирает обе стороны связи. Отбор мыслей (`POST /thoughts/query`, `etn.thoughts.query`) этой семантики не получает: там `comment` — только постоянный комментарий самой мысли. Различие задаёт контекст точки применения, а не значение области.

Панель отбора в клиенте не позволяет снять все области (при попытке снять последнюю умолчания включаются автоматически), но случай пустого множества сохранён как страховка для сохранённых отборов и внешних клиентов REST.

**Семантика записей мысли (уточнение 2026-10-13, верификация 3223b8b0).** Область `diary` и операнд «Есть дневниковые записи» (`chronology`) матчат мысль по записям, где мысль — владелец/первичная цель (owner-based, `comments.owner_id`): запись с несколькими целями учитывается в профиле мыслей только за её первичную цель. Профиль хроники сопоставляет записи целям через `comment_targets_v` (target-based) — это предсуществующее различие профилей, не дефект. Перевод `diary`/`chronology` на target-based — потенциальное изменение поведения, предложено пользователю отдельно (не делается молча).

**Кто такая «первичная цель» (решение заказчика 2026-10-14):** мысль, в контексте которой запись создана — HOME панели «Дневника» (первый элемент targets, chronicle.ts) или открытая мысль редактора. Дополнительные цели записи в область diary не попадают — они учитываются профилем хроники (target-based). Оставлено как есть.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: Мини-синтаксис ключевых слов: AND по словам, звёздочка, исключение
- применяется к: POST /thoughts/query — отбор мыслей по критериям

## parent_ids — сужение отбора до поддеревьев указанных мыслей

`parent_ids` в отборе мыслей применяется **до остальных критериев**: множество кандидатов сначала сужается до объединения поддеревьев указанных мыслей, а остальные условия работают только внутри него.

- между несколькими id — OR: подходит поддерево любого из них;
- **перечисленные мысли входят в результат** (глубина 0) вместе со своими подчинёнными — та же семантика, что у MCP `in_subtree_of` (ошибка ad1551ea, 0.12.1);
- обход идёт по активным связям «источник → цель», глубина ограничена 20 уровнями, результат дедуплицируется по id;
- **граф может содержать циклы** — ограничение глубины и дедупликация не дают обходу зациклиться;
- несуществующий id молча пропускается; если не существует ни один — результат пуст (а не HOME: фильтр считается непустым).

Имя этого фильтра в REST — `parent_ids`; в MCP тот же смысл у `in_subtree_of`.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: links — направленные связи между мыслями
- применяется к: POST /thoughts/query — отбор мыслей по критериям

## PATCH /thoughts/{id} — изменение мысли и её оформления

```
PATCH /api/v1/networks/{nid}/thoughts/{id}   If-Match: <version>
{ title?, synonyms?, type_id?, icon?, icon_kind?, icon_color?, icon_attachment_id?, active?,
  marked_for_deletion?, fg_color?, bg_color?, font_bold?, font_italic?,
  font_underline?, font_strike? }
→ 200 { data: { …, version: N+1 } }
```

**Цвет символа иконки** (`icon_color`) — `null` или HEX `#rrggbb`: цвет значка, независимый от `fg_color`/`bg_color`; хранится при любом виде, но к рендеру применяется только у библиотечной `icon`; значение, отличное от HEX, — `VALIDATION_ERROR`. `null` — прежнее поведение (`currentColor`).

**Иконка-картинка** (`icon_attachment_id`) — вложение этой же мысли, чей оригинал показывается по Ctrl+наведению: `422`, если вложение не найдено, не является файлом-картинкой или принадлежит чужой мысли. Смена иконки на эмодзи/URL или её очистка сбрасывает ссылку в `NULL`; то же делает удаление или перенос вложения.

**Защита:** `422`, если `is_protected = 1` и делается попытка сменить `active` у корневой мысли (HOME).

**Корзина:** `marked_for_deletion` — это «Поместить в корзину» / «Вернуть из корзины»: `true` ставит пометку и заполняет `marked_for_deletion_at`/`_by`, `false` снимает. Пометка **не проверяет блокирующие ссылки** (это только у физического удаления) и не запрещена для защищённых мыслей: саму корзину использовать можно, нельзя лишь физически стереть защищённую мысль.

Пометка на удаление, неактуальность и надгробие слоя — три разных механизма, путать их нельзя.

**Актуализация 0.12.1 (задача 4105bd6a).** В тело PATCH добавлено поле `icon_color` (HEX `#rrggbb`/`null`), серверная валидация значения.

## POST /attachments/file — загрузка файла на сервер

```
POST /api/v1/networks/{nid}/thoughts/{id}/attachments/file
     { title?, mime_type, data_base64 }
→ 201 { data: Attachment, meta: { reused: boolean } }
```

Сервер сохраняет бинарник (**не более 10 МиБ**) в каталог вложений сети рядом с её базой данных и создаёт вложение `kind="file"` с `file_path` на эту копию.

**Дедупликация (ADR `e3a35864`).** Сервер считает SHA-256 содержимого и, если в видимом контексте слоя уже есть вложение `kind='file'` с тем же хэшем, ПЕРЕИСПОЛЬЗУЕТ его (`meta.reused=true`), просто добавляя текущий объект владельцем; новая копия файла не пишется. Иначе создаётся новое вложение с `content_hash`.

Отличие от обычного файлового вложения важно понимать: там `file_path` указывает на машину клиента и при работе с удалённого компьютера файл недоступен; здесь файл живёт на сервере и доступен всем клиентам сети.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: attachments — вложения мыслей и связей, Раскладка каталога данных сервера
- применяется к: Два вида файловых вложений и судьба файла при удалении, Лимиты вложений: файл ≤ 10 МиБ; число владельцев не ограничено

## POST /attachments/{id}/copy — копирование вложения нескольким мыслям

```
POST /api/v1/networks/{nid}/attachments/{id}/copy
     { target_owner_type: "thought", target_owner_ids: string[] }
→ 200 { data: { added: OwnerRef[], skipped: OwnerRef[] } }
```

## POST /chronicle/query — отбор хронологических записей

Список хронологических записей с привязками к мыслям и связям — двигатель вида «Дневник».

```
POST /api/v1/networks/{nid}/chronicle/query
{ keywords?, thought_ids?,          # ≤100 корней; пусто = все мысли сети
  include_subtree?, type_ids?, link_type_ids?,
  link_scope?: "sources"|"targets"|"both",
  date_from?, date_to?,             # полный UTC-инстанс или «голая дата» = сутки UTC
  order: "asc"|"desc", limit: 1..100 (=50), offset: >=0 }

{ ast: { version, filter, sort? } }  # XOR с плоскими критериями (0.13.1)
→ 200 { data: [ ChronicleRow ], meta: { total, offset, limit } }
```

`ChronicleRow`: `id`, `title`, `valid_from`, `valid_to`, `use_time`, `version`, даты и авторы, `snippet` (≈160 символов текста, вхождения ключевых слов обёрнуты в `<mark>`) и `targets` — все привязки записи, первичная первой. Привязка к связи несёт оба её конца и прямое/обратное имя типа — клиент рисует чип связи без дополнительных запросов.

**Время (0.10.1).** `valid_from`/`valid_to` в ответе — всегда полный UTC-инстанс ISO-8601 с мс. Запись попадает в выборку, если её интервал `[valid_from, valid_to]` пересекается с `[date_from, date_to]` (границы включительные). «Голая дата» во входе = сутки UTC `[00:00:00.000Z, 23:59:59.999Z]`. Сервер не конвертирует пояса и не округляет время.

**Сортировка (0.10.1)** в направлении `order`: класс записи (`0` — привязка только к HOME, `1` — прочие) → `valid_from` → `valid_to` → `created_at` → `id`. Прежние тайбрейкеры (NULL-и `valid_to`, `title`) отменены.

**Критерии целей (0.10.1).** Помимо критериев записи (текст, автор, даты), отбор принимает критерии целей — набор «Структур», включая значения свойств; запись проходит, если хотя бы одна её привязка удовлетворяет им. Период принимает динамические токены дат. Контракт критериев и токенов совпадает с MCP-выборкой и с `saved_filters` (`view = "chronicle"`).

Сохранение отборов Хроники — общий механизм именованных отборов с `view = "chronicle"`.

**Ключевые слова (0.10.1).** Мини-синтаксис `*`/`-слово` (AND). Слово ищется двумя путями: путь А — по мыслям (название, синонимы, постоянный комментарий мысли и комментарии её связей), путь Б — по телу и заголовку самой записи; результат — объединение. Путь Б действует при наличии включающих слов и не выходит за структурный отбор (`thought_ids`/`type_ids`). Исключающие слова вычитают мысль по текстам пути А и запись по её собственному тексту. Так сужается лента записей дня, привязанных только к HOME (иначе совпадение в теле выбирало бы корень и возвращало все его записи).

**Ревизия 2026-10-09 (0.12.1, задача `5a002590`).** Классовая сортировка ОТМЕНЕНА. Порядок в направлении `order` — ТОЛЬКО по дате/времени: `valid_from → valid_to → created_at → id`. Прежний ключ «класс записи» (`0` — привязка только к HOME, `1` — прочие, введён в 0.10.1) больше не применяется: записи не меняют положение при добавлении/снятии мыслей.

### Тело-отбор (AST), 0.13.1 — задача `4752b065`

Кроме плоской формы тело может нести дерево условий `ast` — профиль «хроника» (`{ version, filter, sort? }`, сущность Модель отбора (AST) и её wire-формат). Коммиты `223812de` (исполнитель записи, REST/MCP, профиль) и `b2de502c` (включающие границы «Времени записи», HTTP-тест XOR/link_scope). Требование Хроника REST/MCP компилируется в общий AST «Хроника REST/MCP компилируется в общий AST».

- **Один источник критериев.** `ast` несовместим с плоскими критериями (`keywords`, `keyword_scope`, `thought_ids`, `include_subtree`, `type_ids`, `link_type_ids`, `link_scope`, `targets`, `date_from`/`date_to`, `created_by`/`updated_by` + `_op`) — одновременная передача `VALIDATION_ERROR` (поле `ast`, `details.conflicts`). Пагинация (`limit`/`offset`), `order` и `date_mode` (режим полей панели, на выборку не влияет) допустимы с обеими формами.
- **Плоское тело компилируется в AST тем же движком** (`compileChronicleToAst`): `thought_ids`/`include_subtree`/`type_ids`/`keywords` → подграф / «Тип в иерархии» / «Есть слова» (точный `thought_ids` без поддерева — операнд `id` профиля мыслей); `date_from`/`date_to` → операнд «Время записи» с раскрытием токенов на сервере (пересечение интервала записи, границы включающие); `targets` → под-выборка «Цели»; `keyword_scope` → области операнда «Есть слова».
- **Операнд «Цели»** — под-выборка МЫСЛЕЙ (профиль `thoughts`): запись проходит, если привязана к мысли-цели ИЛИ к связи, конец которой ∈ под-выборке (ревизия #62475a6e); «хотя бы одна цель» — `in`, «все цели» — `all_of`, запись без целей не проходит.
- **Отказ от неподдержанного (ревизия v2 требования `0c83819c`).** AST выражает только `link_scope = "both"`: плоские тела с `link_scope` = `"sources"`/`"targets"` или непустым `link_type_ids` ОТКАЗЫВАЮТ `VALIDATION_ERROR` (поля `link_scope`/`link_type_ids`) — отказ вместо молчаливой подмены на `both`; стороны/типы связей в целях — задел будущих версий (затронутых отборов в сетях — 0).
- **Свежесть исполнения.** Место хранения не меняется; форма wire-ответа сохраняется; порядок — прежний (только по дате/времени, 0.12.1). Сниппет-подсветка ключевых слов для явного `ast`-тела — задел (плоские тела подсвечиваются как раньше). Грамматика AST, токены и под-выборки — `etn.guide { topic: "thoughts.query" }`.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: comments — постоянные и хронологические комментарии, comment_targets — привязки комментария к нескольким владельцам
- применяется к: Критерии отбора хроники: записи + цели, «хотя бы одна цель удовлетворяет», ADR: время хроно-записей — всегда полный UTC-инстанс, без серверной семантики дня, Порядок ленты хроники: только по дате/времени записи (valid_from, valid_to, created_at, id), Видимость записи в периоде: пересечение интервала записи с периодом, Двухфазный отбор хроники и попадание записи в период, Голая дата во входных параметрах API = сутки UTC

## POST /layers/{id}/merge — слияние слоя с родителем

```
POST /api/v1/networks/{nid}/layers/{id}/merge
     { tables?: { <ветвимая таблица>: [id, …] } }
→ 200 { data: MergeReport }
```

**Полное слияние** (тело пустое или без `tables`) переносит в родительский слой все строки слоя — теневые и надгробия. **Частичное** переносит только перечисленные логические id по таблицам; набор обязан быть **замкнутым**, сервер его не расширяет. Имена таблиц — из закрытого списка ветвимых; неизвестная таблица или id, которого в слое нет, — 422.

Запреты: основа не сливается (нет родителя) — 422; служебный слой слить нельзя — 422; несуществующий id — 404. Потомки слоя слиянию не мешают: их цепочка прозрачно разрешается через опустевший слой.

**Отказ целиком** (422, детали в теле ошибки): любое расхождение `base_version` — `conflicts: [{ table, id, expected_base_version, current_version }]`; незамкнутый набор — `missing_closure: [{ table, id, referenced_by }]`. Частичного применения не бывает. Единственное исключение — связь на физически отсутствующий конец: связь не создаётся, слияние продолжается, факт попадает в `skipped`.

**MergeReport:**

```json
{ "applied": { "thoughts": 2, "links": 3 },
  "skipped": [{ "table": "links", "id": "…", "reason": "endpoint_missing", "missing": "target" }],
  "reorder_collapsed": [{ "thought_id": "…", "count": 4 }],
  "reserve_layer_id": "…" | null,
  "purged": 0 }
```

- `applied` — сколько логических строк перенесено по таблицам (свёрнутые пачки переупорядочивания входят общим числом);
- `reorder_collapsed` — свёрнутые пачки «изменён порядок у N связей узла X»;
- `reserve_layer_id` — автосозданный служебный слой с до-слиянием состоянием затронутых строк родителя — ручной откат; `null`, когда перезаписывать нечего;
- `purged` — строки, снятые автоочисткой корзины сразу после слияния.

**Real-time:** слияние эмитит ровно одно событие `layer.merged` (`audience = network`, `layer_id` — слой-цель) с отчётом в данных; поштучной рассылки перенесённых строк нет — клиент делает полный ресинк.

**Дополнение (13-layers.md §8.4a).** В отчёт входит ещё `activity_rollup: { groups, removed }` — сводка авто-свёртки журнала активности для слитого слоя: сколько ключевых сущностей `(entity_type, entity_id)` получили итоговую запись в основе и сколько детальных строк журнала удалено. Считается той же транзакцией, что и слияние.

**Слияние одной мысли (0.10.3, задача `f5c363a3`, коммит `8bfc08a3`).** Тело может нести `{ thought_id, mode?: "overwrite" | "combine" }` вместо `tables` (взаимоисключающи; `mode` — только вместе с `thought_id`). Сервер сам собирает замкнутое подмножество строк этой мысли (мысль, синонимы, значения свойств, комментарии с целями, вложения, её рёбра и зависимые строки рёбер) и **не расширяет** его сверх мысли. `overwrite` — перед реплеем снимаются расхождения `base_version` по этим строкам (версия слоя побеждает целиком). `combine` — то же, но постоянный комментарий объединяется с основой построчно (LCS; конфликтный участок — блоком с маркерами `<<<<<<< слой` / `=======` / `>>>>>>> основа`; текст не теряется); хроно-записи переносятся все, связи/свойства/синонимы — версией слоя. Границы объединения — ADR `e4dfdda0`. Отчёт дополняется `thought_merge: { thought_id, mode, comment_merged, comment_conflicts }`. MCP: `etn.ops layers.merge` принимает те же параметры; «отказаться от изменений» — отдельная операция `layers.discard` (физическое удаление строк мысли из слоя, основа не тронута; REST `POST /layers/{id}/discard`).

**Дополнительные материалы**
- относится к подсистемам: Слои изменений (подсистема), REST API
- зависит от: layers — таблица слоёв изменений, Ветвимые и неветвимые таблицы: адресация строк парой id и слоя

## POST /mentions/scan — какие мысли упоминаются в произвольном тексте

Обратное направление к упоминаниям: не «дана мысль — где она упоминается», а «дан текст — какие мысли в нём упомянуты».

```
POST /api/v1/networks/{nid}/mentions/scan
{ texts: [ "<text>", … ],        # ≤50 элементов, суммарно ≤20000 символов
  show_inactive?: boolean,       # включить неактивные мысли-кандидаты
  exclude_thought_id?: "<uuid>" }  # никогда не матчить эту мысль
→ 200 { data: { results: [ [ { start, end, thoughts: [ { id, title, active } ] } ] ] } }
```

Результат — по одному массиву на каждый входной текст, в том же порядке. `start`/`end` — смещения в **UTF-16 code units** (полуинтервал `[start, end)`), совместимые с индексацией строк в JavaScript.

Термы строятся так же, как у упоминаний: части составного имени (значимы первые три запятые — максимум четыре части) и синонимы с учётом `*`.

**Разрешение конфликтов**: при пересечении совпадений побеждает **более длинное**; совпадения с одинаковыми границами (в том числе от разных мыслей) схлопываются в одну группу — не более **5** мыслей на группу, отсортированных по точности (часть составного имени → синоним → wildcard-синоним), затем по названию.

Клиент использует это, чтобы в HTML-просмотре комментария подчеркнуть пунктиром слова-совпадения и предложить переход или вставку ссылки.

**Дополнительные материалы**
- относится к подсистемам: REST API, Полнотекстовый поиск (FTS5)
- применяется к: Символы подстановки в синонимах и правила сопоставления

## POST /thoughts — создание мысли со связью-родителем

```
POST /api/v1/networks/{nid}/thoughts
{ title, synonyms?, type_id?, icon?, icon_kind?, icon_color?, active?,
  fg_color?, bg_color?, font_*?,
  create_link?: { direction: "parent"|"child", target_thought_id, type_id? },
  comment?: { body_md } }
→ 201 { data: { id, …, version: 1 }, meta: { request_id } }
```

- `synonyms` принимается и массивом, и строкой через запятую;
- `create_link` сразу подвешивает мысль к графу в той же транзакции. **`direction` называет роль `target_thought_id` для НОВОЙ мысли** — семантика единая для REST и MCP ([требование «Семантика direction в REST и в MCP единая»](#pub-e74b35a9); до 0.6.3 REST был инвертирован и это считалось «намеренным» — исправлено):
  - `"parent"` — target становится **родителем** новой мысли: новая мысль подвешивается ПОД target («создать мысль в разделе X»);
  - `"child"` — target становится **ребёнком** новой мысли: новая мысль — родитель target;
- `comment { body_md }` (0.12.1, задача `aa79c82d`): постоянный комментарий создаётся вместе с мыслью в **одной транзакции**; `body_html` предрендерится единым рендерером `@etn/markdown`. Явный `comment` побеждает непустой `comment_template_md` назначенного типа (шаблон не применяется). Пустой `body_md` — `VALIDATION_ERROR`;
- если у назначенного типа задан непустой шаблон комментария (`comment_template_md`) и явный `comment` не передан, сервер сразу создаёт постоянный комментарий с текстом шаблона — карточка получает структуру типа без отдельного запроса;
- **дедупликации на уровне API нет**: сервер создаёт мысль с тем именем, которое пришло. Поиск похожих — функция диалога добавления в клиенте (и отдельного MCP-инструмента поиска дублей);
- ключ идемпотентности `Client-Request-Id` защищает от двойного создания при повторе запроса.

**Актуализация 0.12.1 (задача 4105bd6a).** В тело создания мысли добавлено необязательное поле `icon_color` (HEX `#rrggbb`/`null`) — цвет символа иконки.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: thought_types — типы мыслей и их иерархия, thoughts — таблица мыслей, links — направленные связи между мыслями
- применяется к: Семантика direction в REST и в MCP единая — роль target для новой мысли, Атрибуты новых мыслей из выделения, Создание мыслей из выделения — существующим API, батч-эндпоинт не вводится, Обязательное свойство-связь проверяется сервером при записи

## POST /thoughts/batch — групповые операции над мыслями

```
POST /api/v1/networks/{nid}/thoughts/batch
{ ids: […],
  op: "set_type"|"clear_type"|"set_active"|"set_inactive"|"delete"|
      "trash"|"purge"|"link_to_focus"|"unlink_from_focus"|
      "link_parents"|"link_children"|"set_only_parents"|
      "unlink_parents"|"unlink_children",
  args: { type_id?, active?, focus_thought_id?, link_type_id?, direction?,
          parent_ids?, child_ids? } }
→ 200 { data: { affected: N, failures: [ { id, code, message } ] } }
```

**Ошибка отдельной мысли не отменяет всю операцию**: несуществующий id, защищённая HOME, заблокированное удаление — попадают в `failures`, остальные обрабатываются.

Операции корзины:

- `trash` — поставить `marked_for_deletion = true` каждой из `ids`. Снятие пометки пачкой не предусмотрено — восстановление из корзины делается по одной мысли;
- `purge` — физически удалить каждую; заблокированная остаётся и попадает в `failures` с `code: "VALIDATION_ERROR"`;
- `delete` — алиас `purge` ради обратной совместимости; новый код пишет `purge` явно.

Диалог группового удаления заранее разводит `ids` на два вызова (`trash` и `purge`) по выбору переключателя в каждой строке, а не передаёт выбор построчно одним запросом.

`link_to_focus`/`unlink_from_focus` — связать или разорвать связи всех `ids` с мыслью в фокусе клиента (`args.focus_thought_id` передаётся явно, сервер не знает фокуса); `args.direction` — `parent`/`child`.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: deletion-check — проверка возможности удаления мысли или связи, thoughts — таблица мыслей
- применяется к: Массовая перецепка связей: link_parents, link_children, set_only_parents, Операции над набором значений: добавить, убрать, заменить

## POST /thoughts/copy-batch — копирование подграфа мыслей между сетями

Атомарное копирование подграфа мыслей из одной сети в другую (или в ту же).

```
POST /api/v1/networks/{nid}/thoughts/copy-batch
{ source_network_id, parent_thought_id,
  thoughts: [ { source_id,
                thought: { title, synonyms?, type_id?, type_name?, active? },
                permanent_comment?: { title?, body_md } | null,
                properties?: { key: value|null },
                attachments?: [ { kind, url?, file_path?, title?, description? } ] } ],
  links: [ { source_id, target_id, type_id?, type_name?, active?,
             fg_color?, bg_color?, width?, style?,
             permanent_comment?, attachments? } ] }
→ 200 { data: { thought_id_map, link_id_map,
                created_thoughts, created_links, created_attachments } }
```

**Это «создай из снапшота», а не «скопируй из БД»**: сервер не читает `source_id` из исходной сети — он использует их только для карт соответствия и определения корней подграфа; все `source_id` обязаны быть валидными UUID. Карты `thought_id_map`/`link_id_map` нужны клиенту, чтобы переписать wiki-ссылки.

**Комментарии и вложения**: копируются постоянные комментарии мыслей и связей и метаданные вложений. Файлы вложений: при копировании в **другую** сеть (`source_network_id` ≠ целевая) сервер физически копирует файл в каталог `attachments/` сети-получателя (к имени добавляется номер копии — `<stem>-<n><ext>`, `n` ≥ 2, чтобы имена не столкнулись; один исходный файл на батч копируется один раз, все строки вложений с ним делят одну копию) и прописывает в копии вложения `file_path` на новый файл; при копировании **внутри одной** сети файл не дублируется — остаётся общий. Вложение с тем же `(kind, url/file_path)`, уже есть у целевой мысли — пропускается тихо. Отсутствующий на диске исходный файл — метаданные сохраняются, копия не создаётся, операция не падает (предупреждение в лог). Файлы записываются после фиксации транзакции БД (осиротевших файлов при откате не остаётся).

**(2026-10-07, ошибка `b83a7d89`, версия 0.12.1)** — правка контракта: ранее «файл на диске не дублируется» для всех случаев, и вложение в копии в другой сети было недоступно; теперь при межсетевом копировании файл копируется.

**Wiki-ссылки сервер не переписывает**: внутри одной сети `[[#<id>]]` остаются как есть; при кросс-сетевом копировании клиент обязан прислать уже переписанные строки формата `[[n:<net>#<id>]]`.

**Атомарность и идемпотентность**: вся операция — одна транзакция (при любой ошибке не создаётся ничего); повтор с тем же `Client-Request-Id` в течение 10 минут вернёт кэшированный ответ.

**Real-time**: на каждую созданную мысль шлётся `thought.created`, на каждую связь — `link.created`; автор операции своё эхо не получает.

**Права**: обе сети должны быть доступны тому же пользователю; админского «копировать чужое» нет.

**Ошибки**: `VALIDATION_ERROR` — пустой `thoughts`, невалидный `parent_thought_id` или `source_id` не UUID; `NOT_FOUND` — `parent_thought_id` нет в целевой сети; `FORBIDDEN` — защищённая мысль или нет доступа; `TRANSACTION_CONFLICT` — редкая гонка, клиент повторяет запрос.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: attachments — вложения мыслей и связей, Идемпотентность изменяющих запросов через client_request_id, thoughts — таблица мыслей
- применяется к: Что не копируется при копировании подграфа мыслей, Корни копируемого подграфа привязываются к мысли-приёмнику, Резолв типов и ссылок при копировании мыслей в другую сеть, Кросс-сетевые значения переносятся копированием как есть

## POST /thoughts/edges — связи среди видимых мыслей дерева

```
POST /api/v1/networks/{nid}/thoughts/edges
{ ids: […],              # до 2000 id — мысли, видимые в дереве
  show_inactive?: false }
→ 200 { data: { edges: [ { id, source_id, target_id, type_id, color, style, width } ] } }
```

Возвращает **все** связи, оба конца которых есть в `ids`, — не только пары «узел ↔ раскрытый сосед». Состав ответа оставлен полным (как `edges` фокус-ответа холста), а клиент дерева сам решает, что рисовать.

По умолчанию только активные связи; `show_inactive: true` добавляет неактуальные (клиент рисует их тусклыми).

`color`/`style`/`width` — переопределение стиля линии самой связью; `null` означает «наследовать от типа связи».

**Рёбра в корзине** (0.8.2, ошибка 355319d4). Ребро, помеченное на удаление, остаётся в выдаче и несёт `link_marked_for_deletion` — дерево «Структур» рисует его помеченным, а не обычным. Проекция ребра — общая с фокус-ответом (`toFocusEdge` в `link-service`), чтобы поля не разъезжались.

**Настройка видимости корзины** (задача 77923b49, коммит e55e5c6). Тело принимает `show_trash`; без него флаг берётся из настройки сети (дефолт `true`). При выключенной настройке помеченные рёбра в выдаче отсутствуют, а не приходят помеченными — абзац «Рёбра в корзине» описывает дефолтное поведение.

**Фильтр типов связей** (0.8.2, ошибка a617b4c6, ревизия 2026-09-28). Тело принимает `link_filter` той же формы, что фокус-ответ и страницы секторов карты/дерева, — `{ type_ids?: [id…], include_structural?: bool }`. Снимок возвращает только рёбра выбранных типов (с учётом их потомков); `include_structural: true` добавляет структурные рёбра без типа. Без ключа поведение прежнее — рёбра всех типов. Раньше поле не принималось, и снимок рёбер для догрузки порций игнорировал активный фильтр.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: links — направленные связи между мыслями, link_types — типы связей и их иерархия

## POST /thoughts/query — отбор мыслей по критериям

Отбор мыслей по критериям — двигатель рабочего стола «Структуры мыслей» и сохранённых отборов.

```
POST /api/v1/networks/{nid}/thoughts/query
{ keywords?, keyword_scope?, parent_ids?, type_ids?, link_type_ids?,
  properties?: [ { property_id, op, value } ],
  has_properties?, has_comment?, has_attachments?, has_chronology?,
  active?, show_inactive?, trashed?,
  sort: "alpha"|"created"|"viewed", order: "asc"|"desc",
  limit: 100, offset: 0, ids_only?, count?, cursor? }
→ 200 { data: [ ThoughtRef… ], meta: { total|null, limit, offset, directions, has_more, next_cursor } }
```

Критерии объединяются по AND; внутри `type_ids`/`link_type_ids` — OR, причём каждый id раскрывается до **поддерева типов** (подчинённые типы тоже соответствуют). `link_type_ids` требует активной связи такого типа в любом направлении.

Трёхсостоянные признаки `has_properties`/`has_comment`/`has_attachments`/`has_chronology`: `true` — только с наличием, `false` — только без, поле не передано — критерий не участвует.

`active` — актуальность: явное значение **переопределяет** настройку `show_inactive` в обе стороны; отсутствие поля — действует настройка. `trashed: false` (умолчание) исключает помеченные на удаление; саму корзину отдаёт отдельный маршрут, а не этот фильтр.

**Пагинация и счётчик (0.9.1).** Порядок страницы детерминирован: выбранная сортировка дополняется уникальным ключом `id`, поэтому на границе страниц строки не теряются и не дублируются. `count: true` — посчитать полное число совпадений; без флага (умолчание) `COUNT` не выполняется, `meta.total` = `null`, а наличие хвоста сообщает `meta.has_more`. `meta.next_cursor` — непрозрачный keyset-курсор следующей страницы (выдаётся только при `has_more`); переданный в теле `cursor` читает продолжение по ключу сортировки без `OFFSET` — глубокие страницы не деградируют, `offset` в этом случае игнорируется. Курсор обязан соответствовать `sort`/`order` запроса (иначе `VALIDATION_ERROR`). Регулируется требованиями «COUNT общего числа выполняется только по явному запросу» и «Выборки пагинируются keyset-курсором вместо OFFSET» (ADR «Точечные оптимизации выборок»).

**`ids_only: true`** — тот же набор кандидатов и тот же порядок, но страница несёт только id: `{ data: { ids: […], total|null, has_more, next_cursor } }`, без `meta.directions`. Потолок `limit` поднят со 100 до 2000 — команды отбора собирают весь результат за меньшее число запросов. Действия `count`/`cursor` те же.

`meta.directions` — `{ "<thought_id>": { has_incoming, has_outgoing } }` для всех мыслей страницы: клиент сразу закрашивает эллипсы корней дерева.

Сортировка: `alpha` — по заголовку (NOCASE), `created` — по дате создания, `viewed` — по метке просмотра текущего пользователя (NULL — последними при `asc`).

**Видимость помеченных в `meta.directions`** (ошибка 331ffb94, коммит `51cadb8`, 0.8.2). Тело принимает `show_trash` (boolean, REST-only поле обёртки): без него флаг берётся из настройки сети (`resolveShowTrash`, дефолт `true`). `meta.directions` считаются с этим флагом — ровно как раскрытие дерева (`GET /thoughts/{id}/hierarchy`): при выключенной настройке ни помеченное ребро, ни ребро в помеченную мысль эллипс не закрашивают. Так `directions` страницы и уровень раскрытия не расходятся (эллипс не обещает пустой ветви).

### Кросс-сетевой режим (0.8.3, проектируется)

Веерная форма вызова — с перечнем сетей вместо `{nid}` (точная форма адреса — задача): критерии применяются в каждой сети по её реестру (`type_ids`/`link_type_ids`/`properties` резолвируются отдельно; имени свойства или типа в сети нет — из неё попаданий нет), выдача сливаются: элементы несут `network_id`, в ответе справочник сетей. Свойства вида «кросс-сетевая ссылка» — операторы `eq`/`ne`/`any_of`/`all_of`/`none_of` по адресу. Только сети-участия пользователя, чтение в сессионном слое каждой сети. Поведение одиночной сети не меняется.

### Ревизия 0.12.1 (ошибка ad1551ea)

`parent_ids` — сужение до поддеревьев указанных мыслей: **перечисленные мысли входят в результат** (глубина 0) вместе со своими подчинёнными. Семантика совпадает с MCP `in_subtree_of` (05-mcp-server §4.1); прежде REST-фасад корни исключал. Обход — по активным связям «источник → цель», глубина ≤ 20, дедупликация по id; при `show_inactive` спуск идёт и по неактивным рёбрам.

### Ревизия 0.12.1 (ошибки 090d0242, 4f17cb73, f4580fff)

Условие `properties[]` обязано адресовать свойство: `property_id` (непустая строка). Условие без адреса или **неизвестное поле условия** — `VALIDATION_ERROR`; лишние поля условия не игнорируются молча.

**Код неразрешимой ссылки (ошибка f4580fff).** Ссылка на несуществующее (или невидимое в слое) свойство — `NOT_FOUND` (404) с указанием поля `property_id`, а НЕ молчаливое выпадение условия из отбора и НЕ `VALIDATION_ERROR`. Код выровнен по конвенции резолва реестровых сущностей (как у типа: несуществующее имя или `id` → `NOT_FOUND`, неоднозначность → `VALIDATION_ERROR` с `details.candidates`). Прежнее поведение (условие исчезало из `WHERE`, набор кандидатов расширялся до всей сети) устранено ещё в 090d0242/4f17cb73.

Движок отбора на неразрешённую ссылку даёт пустой набор («нет совпадений»): сохранённый отбор или рецепт публикации со ссылкой на удалённое свойство не расширяется до всей сети. В кросс-сетевом режиме сеть, где свойства нет, вносит пустой вклад (см. «Кросс-сетевой режим» выше) — это согласовано и не является ошибкой.

### Тело-отбор (AST), 0.13.1 — тех.проект «Ядро AST и операторы»

Кроме текущей плоской формы тело может нести дерево условий (AST) — сущность Модель отбора (AST) и её wire-формат: группы И/ИЛИ/НЕ, листья [сущность][оператор][значение], значение — скаляр/список/токен/под-выборка; сортировка — отдельное многоуровневое поле. Старые плоские тела (`parent_ids`, `type_ids`, `link_type_ids`, `properties[]`, `keywords`) остаются принимаемыми и компилируются в AST: `type_ids`/`link_type_ids` раскрываются по поддереву (в терминах AST — «Тип в иерархии»). Оба пути ведут в один исполнитель. Требования: «Старые тела REST/MCP компилируются в AST» Старые тела REST/MCP компилируются в AST, «Сортировка отбора…» Сортировка отбора: многоуровневая, направление на каждый ключ, «Один исполнитель AST…» Один исполнитель AST для REST, MCP и UI.

Правила приёма.

- **Один источник критериев.** `ast` несовместим с плоскими критериями отбора (`keywords`, `type_ids`, `link_type_ids`, `properties[]`, `has_*`, `active`/`show_inactive`, `trashed`, `created_by`/`updated_by` и даты) — одновременная передача `VALIDATION_ERROR`. **Фасадные пред-сужения `parent_ids` и `link_filter` совместимы с `ast`** и применяются ПОВЕРХ дерева (в AST не компилируются: `parent_ids` — обход поддерева с корнями, требование [parent_ids — сужение отбора до поддеревьев указанных мыслей](#pub-3482a399); `link_filter` вынесен из AST сущностью 489c394f). Плоское тело без `ast` продолжает работать: оно **компилируется в AST тем же движком** (единый исполнитель, требования Старые тела REST/MCP компилируются в AST и Один исполнитель AST для REST, MCP и UI); `type_ids`/`link_type_ids` раскрываются по поддереву («Тип в иерархии»).
- **Токены.** Календарные (`$today`, `$weekStart`/`$weekEnd`, …) и `$user` разрешает сервер по контексту запроса (первый день недели — настройка сети); неразрешимый токен даёт пустой результат с пояснением.
- **Неизвестные поля** (корень и любой уровень дерева) отклоняются `VALIDATION_ERROR` — форма валидируется строго доменным `parseFilterAst`.
- **Хранение.** `thought_type_views.definition` и `saved_filters.definition` хранят AST; старые `definition v1` компилируются при чтении (одноразовая миграция БД — отдельная задача).

#### `ast.sort` — исполнение многоуровневой сортировки (0.13.1, задача `3a157e66`)

Сортировка — **отдельное поле корня AST**, не узел дерева: `"sort": [{ "key", "order" }]`. Коммиты `73d4af83` (исполнение), `84b3d5f4` (сверка keyset-курсора с фактическим `ast.sort`, `body-override` в `views run`), `9de43cbb` (подпись курсора различает идентичность ключа-свойства). Требование Сортировка отбора: многоуровневая, направление на каждый ключ. Исполняется единым движком (REST `POST /thoughts/query`, `etn.views.run` и MCP `etn.thoughts.query`).

- **Многоуровневая:** порядок ключей — как объявлен в списке, направление задаётся на КАЖДЫЙ ключ. Ограничение «ровно один ключ» снято.
- **Ключи:** `title`/`created_at`/`updated_at` (псевдонимы `alpha`/`created`/`updated`) и свойства сети — по `property_id` или имени свойства. Свойство-связь сортировать нечем → `VALIDATION_ERROR`; неизвестный ключ (не фиксированный и не свойство сети) → `VALIDATION_ERROR` (`details.field = "ast.sort"`, `key`).
- **Порядок значений:** по булевым ключам ложь раньше истины (при `asc`); пустые значения ключа-свойства — в конце.
- **Детерминизм:** порядок дополняется уникальным `id` (совместимо с keyset-пагинацией); подпись курсора сверяется с ФАКТИЧЕСКИМ `ast.sort` — несовпадение → `VALIDATION_ERROR`.
- **Два источника порядка:** непустой `ast.sort` задаёт порядок целиком и перекрывает плоские `sort`/`order`; одновременная передача `ast.sort` и полей `sort`/`order` → `VALIDATION_ERROR` (поле `sort`, конвенция «оставьте один источник»).
- Грамматика AST, полный список ключей и операторов — `etn.guide { topic: "thoughts.query" }`.

### Ревизия 0.14.1 (задача f0b06700): `*`-синонимы в `keywords`

Мини-синтаксис §6.10: слово запроса БЕЗ `*` совпадает литерально (подстрока в заголовке/синониме) **ИЛИ** с ОДНИМ словом хранимого `*`-синонима по его границам — `проектиров*` находит «проектирование», `функциональност*` — «функциональности» (требование 35218826, сценарий «поиск»). Слова запроса независимы (AND, порядок любой) и могут совпасть с разными источниками одной мысли. Расширение действует только для источника `synonyms`; слово запроса с `*` — только литерально; `-слово` симметрично включению (литерал ИЛИ слово-паттерн); заголовок не расширяется. Точный предикат исполняется в SQL (функция `synonym_word_pattern_match`) ДО `COUNT`/`LIMIT`/keyset — `meta.total`, `has_more` и `next_cursor` точны. FTS-сужатель остаётся и расширен до надмножества (OR-ветка по мыслям с `*`-синонимами, требование 314cbb8d). Сеть без `*`-синонимов ведёт себя как раньше; работает и в AST-теле (операнд «Найти слова»), и в плоском теле — единый движок.

## POST /thoughts/{id}/focus — окрестность мысли для холста

Главная операция холста: перевод фокуса на мысль и получение всего, что нужно для отрисовки окрестности, одним запросом.

```
POST /api/v1/networks/{nid}/thoughts/{id}/focus
→ 200 { data: { focused, parents, children, siblings, edges,
                sorts: { parents: { sort, order }, children: {…}, siblings: {…} } } }
```

Побочный эффект: записывается метка просмотра (`last_viewed_at` текущего пользователя). А вот сама фокус-мысль как «последняя просмотренная» сервером не сохраняется — это клиентское состояние.

**Зоны взаимоисключающи**: мысль встречается не более чем в одной из `parents`/`children`/`siblings`; приоритет — фокус > parents > children > siblings.

Элемент зоны: `{ id, title, type_id, icon, active, link_id, link_type_id, link_active }` — то есть мысль вместе со связью, которой она держится за фокус.

`edges` — **все** active-связи, у которых оба конца входят в множество `{focused} ∪ parents ∪ children ∪ siblings`, включая связи сосед↔сосед: `{ id, source_id, target_id, type_id }`. От распределения мыслей по зонам не зависят — холсту нужны все видимые линии.

`sorts` — текущая сортировка пользователя по каждой зоне: `sort` — `manual`/`alpha`/`created`/`viewed` (дефолт `created`), `order` — `asc`/`desc`. Зона `siblings` вручную не упорядочивается (`manual` недоступен), но свою настройку несёт; объект возвращается для всех трёх зон, чтобы меню сортировки отмечало активный пункт.

Неактуальные мысли и связи попадают в ответ только при включённом `show_inactive`.

**Рёбра в корзине** (0.8.2, ошибка 355319d4). Связь, помеченная на удаление, остаётся в ответе: помеченную сущность холст обязан показать с признаком, а не спрятать (критерий S13 — «видно на холсте со значком 🗑»). И элемент зоны, и ребро `edges` несут `link_marked_for_deletion`; `link_active` остаётся `true` — пометка на удаление это не неактуальность. Пометка НЕ влияет на попадание ребра в ответ (`show_inactive` по-прежнему только про `active`).

**Настройка видимости корзины** (задача 77923b49, коммит e55e5c6). Тело запроса принимает `show_trash`; без него флаг берётся из `preferences.show_trash` пользователя (дефолт `true`). При выключенной настройке помеченные рёбра и помеченные соседи из ответа ИСКЛЮЧАЮТСЯ — этим уточнён абзац «Пометка НЕ влияет на попадание ребра в ответ»: он описывает поведение по умолчанию, когда содержимое корзины показывают.

**Дополнительные материалы**
- относится к подсистемам: REST API, Пользовательский интерфейс (холст и редактор)
- зависит от: user_focus_preferences — сортировка зон холста, thoughts — таблица мыслей, links — направленные связи между мыслями, thought_views — метки просмотра мыслей
- применяется к: Фильтр обхода по типам связей, Сценарий: карта — фильтр типов связей в том же исполнителе, ADR: фильтр типов связей на карте и link_filter — один операнд AST, место хранения не меняется, Порядок мыслей в зоне фокуса: правила применения сортировки, Фильтр типов связей на карте и link_filter — один и тот же AST

## POST /thoughts/{id}/usage/clear — очистить использование мысли в свойствах

```
POST /api/v1/networks/{nid}/thoughts/{id}/usage/clear
```

## POST /thoughts/{id}/views/run — ad-hoc AST-отбор относительно мысли

Исполняет ПРОИЗВОЛЬНОЕ AST-тело отбора относительно конкретной мысли — REST-паритет с MCP `etn.views.run { ast }` (задача 0e7e89f5); сохранённый отбор исполняет соседний маршрут [POST /thoughts/{id}/views/{view}/run — исполнение отбора относительно мысли](#pub-95273103).

```
POST /api/v1/networks/{nid}/thoughts/{id}/views/run
{ ast, sort?, order?, limit?, offset? }
→ 200 { data: [ ThoughtRef… ],
        meta: { total, limit, offset, directions, sort, order, ast: true,
                has_more, next_cursor, warnings?, unresolved? } }
```

`ast` — обязательное wire-тело отбора (сущность Модель отбора (AST) и её wire-формат; грамматика — `etn.guide { topic: "thoughts.query" }`). Тело строгое: неизвестные поля — `422 VALIDATION_ERROR`.

**Единая точка исполнения.** Маршрут и обе ветки `etn.views.run` исполняет один домен (`executeViewDefinitionForThought`): контекстная мысль из пути раскрывает токены `$thought*`, сама контекстная мысль исключается из страницы (с коррекцией `total`, если страница её потеряла), `total` — всегда COUNT, потолок `limit` — 200, хвост — `meta.has_more`/`meta.next_cursor`.

**Сортировка.** `ast.sort` и `sort`/`order` в одном вызове — `422 VALIDATION_ERROR` «оставьте один источник» (конвенция cb78315b). Без `ast.sort` поля `sort`/`order` задают плоскую сортировку движка.

**Диагностика.** Красная (условие ссылается на удалённую сущность) запрещает прогон — `422 VALIDATION_ERROR` с `details.diagnostics`. Жёлтая (свойство отвязано от типа) — в `meta.warnings`. Неразрешимые токены (в т.ч. `$thought.*` вне контекста мысли) — успешный ответ, `data` пуст, пояснения в `meta.unresolved` (`{token, reason}`, требование b7fdab20).

**Отличия от `:view/run`.** Нет сохранённого отбора — нет `meta.view`; `meta.ast: true`; событие `thought-type-view.run` НЕ эмитится (операция чтения). Границы: маршрут обслуживает предпросмотр отбора относительно мысли при наличии контекстной мысли; GUI-внедрение — вне задачи.

Ошибки: `404` — мысль-контекст не найдена; `422` — невалидное тело, конфликт сортировок или красная диагностика.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: POST /thoughts/query — отбор мыслей по критериям, thought_type_views — именованные отборы типов мыслей

## POST /thoughts/{id}/views/{view}/run — исполнение отбора относительно мысли

Исполняет отбор из эффективного набора мысли и возвращает страницу мыслей.

```
POST /api/v1/networks/{nid}/thoughts/{id}/views/{view}/run
{ limit?, offset?, sort?, order? }
→ 200 { data: [ ThoughtRef… ],
        meta: { total, limit, offset, directions, view: { id, name, type_id },
                unresolved?: [ { token, reason } ] } }
```

`{view}` — имя отбора или его id; имя ищется в **эффективном** наборе мысли, то есть находит и отбор, унаследованный от типа-предка.

**Двигатель тот же, что у отбора мыслей:** после подстановки токенов запрос выполняется как обычный отбор по критериям, поэтому пагинация, сортировки и `meta.directions` совпадают. `sort`/`order` в теле переопределяют сортировку, сохранённую в отборе.

**`meta.unresolved`** — непустой, если хоть один токен не разрешился: ответ успешный, `data` пуст, причина названа (см. требование о неразрешимом токене).

Ошибки: `404` — у мысли нет такого отбора; `422` — отбор сохранён с определением, несовместимым с текущей онтологией (свойство отключили от типа).

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: thought_type_views — именованные отборы типов мыслей, POST /thoughts/query — отбор мыслей по критериям

## PUT /system/logging — включить/выключить файловый журнал

```
PUT /api/v1/system/logging
Authorization: Bearer <admin-key>
Body: { enabled: boolean }
→ 200 { data: { enabled, logDir, retentionDays, files } }   // тот же объект, что у GET
→ 401 UNAUTHORIZED / 403 FORBIDDEN
→ 422 VALIDATION_ERROR (enabled отсутствует или не boolean)
```

Переключает флаг файлового журнала **в памяти сервера**: WARN/INFO/DEBUG пишутся только при `enabled=true`; ERROR пишутся всегда. Состояние НЕ сохраняется между перезапусками — при старте сервера флаг всегда выключен.

Побочный эффект: в сам файловый журнал пишется WARN-запись о факте переключения и том, кто его выполнил (actor `user=<login>`). Idempotent: повторная установка того же значения допустима, запись в журнал всё равно пишется.

## Блокировка удаления цели — флаг определения свойства-связи

**Область.** Требование — про защиту от удаления и очистку, НЕ про просмотр «Использования».

Проверку «использование мысли в свойствах других мыслей» (`deletion_check`, проверки перед физическим удалением) и очистку `usage/clear` обеспечивают только те свойства-связи, у которых в определении стоит `blocks_target_deletion = true`. Свойства без флага удаление цели не блокируют; `usage/clear` помечает в корзину рёбра только по таким свойствам.

Свойство «Использование» (`etn.thoughts.usage`, `GET /thoughts/{id}/usage`) — напротив, показывает ВСЕ формальные link-рёбра реестра, независимо от флага: это просмотр «кто ссылается на мысль», а не ветвь блокировки.

У мигрированных свойств флаг выставляется так, чтобы блокировка сохранилась там, где работала `thought_ref` (а она блокировала удаление цели всегда).

Изменено по решению пользователя 2026-09-26 (ошибка c0a2a2e6): «Использование» отделено от блокировки удаления.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, MCP-сервер
- применяется к: etn.thoughts.usage — формальные связи мысли, etn.thoughts.delete — физическое удаление с блокировкой, POST /thoughts/{id}/usage/clear — очистить использование мысли в свойствах, deletion-check — проверка возможности удаления мысли или связи

## Вид значения «тип связи» в реестре свойств

В реестре свойств появляется вид значения **«тип связи»** (`link`). Определение такого свойства в `config` несёт:

- `link_type_id` — тип связи, обязательный; действует инвариант «одно свойство-связь на тип связи», а не уникальность пары «тип связи + направление» (Свойство-связь одно на тип связи; сторона задана привязкой);
- `allowed_target_type_ids` — опциональное ограничение типов противоположной стороны; раскрывается до поддеревьев типов;
- `show_on_map` — рисовать ли связь на карте по умолчанию (по умолчанию `false`);
- `blocks_target_deletion` — блокирует ли ссылка физическое удаление цели (по умолчанию `false`).

Флаги — **настоящие JSON-булевы**, не `1`/`0`. Потребители сравнивают их строго: `config.show_on_map === true` в shared `computeDefaultCanvasLinkFilter`, `config.blocks_target_deletion === true` в доменном `listBlockingLinkProperties` и клиентском редакторе. На числе `1` строгая проверка не срабатывает — флаг молча выключается.

Поля `direction` в определении свойства нет: сторона участия (источник или назначение) задаётся привязкой — `side` в `type_properties` (Свойство-связь одно на тип связи; сторона задана привязкой).

Вид значения `thought_ref` из допустимых исключается (ADR «вид значения thought_ref упраздняется»). Смена `value_type` внутри скалярной категории выполняется доменной конверсией значений, как раньше; переход между скалярной категорией и «типом связи» запрещён в обе стороны (Категория вида значения неизменна: скаляры и «связь» не конвертируются).

### Использование `show_on_map` (0.8.1, доработка)

Клиент читает `show_on_map` всех свойств-связей сети и строит из них дефолтный набор видимых на карте типов связей — см. требование «Дефолт и хранение фильтра типов связей на карте». До 0.8.1 (доработка, ошибка show_on_map не влияет на отрисовку карты мыслей) флаг нигде не потреблялся.

### Значение флагов при миграции из 0.7.x

Миграции 0.8.1 выставляют флаги так, чтобы поведение не ухудшалось относительно 0.7.x:

- **авто-свойство «голого» типа связи → `show_on_map = true`** (миграция 042, сценарий Миграция 0.8.1: единый реестр свойств и связей): рёбра этих типов рисовались на карте до обновления всегда, `false` молча убрал бы их с карты;
- **свойство, конвертированное из `thought_ref` → `show_on_map = false`, `blocks_target_deletion = true`** (миграция 040, сценарий Сценарий: перевод thought_ref в свойства-связи): массовые ссылки не рисуются (ADR «вид значения thought_ref упраздняется»), но, как и прежде, блокируют удаление цели.

Дефолт `false` из списка выше — для новых свойств, заводимых пользователем в редакторе; миграции отступают от него осознанно, сохраняя прежнее поведение.

## Двухфазный отбор хроники и попадание записи в период

Отбор хроники выполняется **в две фазы**: сначала отбираются мысли, затем по ним — записи. Без этого порядка результат понять невозможно.

**Фаза 1 — мысли:**

- `thought_ids` (и подчинённые до 20 уровней при `include_subtree`) — обход по **ненаправленным** активным связям с защитой от циклов; несуществующие id игнорируются; пустой фильтр — все мысли сети;
- `type_ids` фильтрует по типу мысли (каждый id — до поддерева типов, OR);
- `keywords` ищутся в названии, синонимах, **текстах комментариев мысли** и **текстах комментариев её связей с обеих сторон**. Слово, найденное только в комментарии связи, отбирает **обе стороны** связи; исключающие слова вычитают мысли по тем же текстам;
- **неактуальные мысли включаются** (клиент затемняет их чипы).

**Фаза 2 — записи** (`kind = chronological`), привязанные к отобранной мысли по любой привязке **или** к связи, чей источник/назначение/любой конец (по `link_scope`) входит в отбор; при заданных `link_type_ids` — только связи этих типов (поддерево, OR).

**Период**: запись попадает в выдачу, если интервал `[valid_from, valid_to]` **пересекается** с `[date_from, date_to]`; открытый `valid_to = NULL` — бесконечность, обе границы запроса необязательны.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: Мини-синтаксис ключевых слов: AND по словам, звёздочка, исключение
- применяется к: POST /chronicle/query — отбор хронологических записей

## Динамические токены дат в периоде и сохранённых отборах

Период хроники и определение сохранённого отбора принимают динамические токены дат того же языка, что отбор мыслей: `$today`, `$now`, `$thought.[<дата>]`, арифметика. Токен раскрывается относительно текущего дня в момент применения отбора, а не сохранения.

- сохранённый отбор хранит токен в `definition` без изменений;
- ввод значения с токеном — через поле периода (единый контрол), а не текстом;
- язык токенов не дублируется: переиспользуется требование отбора мыслей.

**Уточнение реализации (T3, 2026-09-26).** В периоде хроники доступны только глобальные токены (`$today`, `$now`, арифметика `±Nd`); токен `$thought.[…]` требует контекста мысли, которого у периода нет, и во входных датах хроники отвергается `VALIDATION_ERROR`. Имя поля критериев целей в контракте — `targets` (состав `StructureFilter`, как в отборе «Структур»); в `saved_filters view=chronicle` хранится как есть.

**Расширение языка (0.10.1, доработка по замечаниям приёмки).**

- Добавлены глобальные токены ГРАНИЦ: `$week.start` — понедельник текущей недели, `$week.end` — воскресенье (неделя с понедельника), `$month.start` — первое число текущего месяца, `$month.end` — последнее число.
- Арифметика расширена тремя единицами: `±Nd` (дни), `±Nw` (недели = 7 суток), `±Nmo` (календарные месяцы). Месячная арифметика применяется к ЯКОРЮ месяца и прижимает день к концу месяца: `$month.end-1mo` — последний день прошлого месяца.
- Токены едут в периоде хроники и в отборе типов мыслей единым вычислителем `server/src/domain/thought-type-view-tokens.ts`; клиент раскрывает их для подсветки календаря тем же правилом (`$week`/`$month`, неделя с понедельника).
- Область поиска ключевых слов хроники (`keyword_scope`) — закрытый словарь `title`/`synonyms`/`comment`; отсутствие/пустой набор — поиск по всем областям (поведение до 0.10.1), тело/заголовок записи (путь T7) от области не зависят.

**Расширение языка (2026-09-26, задача 7edd1cce, приёмка №2).**

- Добавлены глобальные токены ГРАНИЦ ГОДА: `$year.start` — 1 января текущего года, `$year.end` — 31 декабря.
- Арифметика дополнена единицей `y` (календарные годы = 12 месяцев): `±Ny`.
- Панель «Дневника» получила режим «Пресеты»/«Даты» (поле `date_mode` в определении сохранённого отбора); режим хранится в `definition` как есть, значения-токены раскрываются в момент применения отбора.
- Правило выражения календарного выбора в режиме «Пресеты»: одиночный день — «сегодня±Nd» (если день = сегодня — `$today`); интервал, выровненный на неделю/месяц/год, — соответствующие пресеты границ (`±1w`/`±1mo`/`±1y`); произвольный интервал — день-арифметика `$today±Nd` на «С» и «По».

**Ревизия (2026-09-26, задача 9bef6a27, приёмка №3).** Новых токенов НЕ добавлено: панельный виджет «список + сдвиг ±N» — чисто клиентское представление поверх уже существующего языка. Базовые пресеты клиента («сегодня», границы недели/месяца/года) и сдвиг ±N с единицами [дн/нед/мес/лет] собираются в канонический токен (`$today`, `$week.start-1w`, `$month.end+2mo`, `$year.start`, `±Nd/Nw/Nmo/Ny`) и уходят на сервер как есть. Человекочитаемая композиция («начало недели − 1 нед») — только отображение; в определении сохранённого отбора и на сервер уходит токен, а не текст.

**Уточнение (2026-09-27, задача fd9eef49, приёмка №4 — кто раскрывает токен).** Язык токенов и правило «раскрывается в момент применения, а не сохранения» сохранены. Разграничение носителя часов:

- **Клиент** как носитель пояса наблюдателя раскрывает границы периода в ЛОКАЛЬНЫЕ календарные даты (та же арифметика, что для подсветки календаря) и отправляет в запрос «голую дату»; сервер трактует её как сутки UTC (требование 469d8d69). Так результат выборки согласован с локальным днём принадлежности записи (требование d58aa1a4) и с подсветкой календаря.
- **Серверное раскрытие токенов** остаётся для API/MCP-потребителей (там «текущий день» — UTC-сутки); токен в запросе валиден и по-прежнему принимается.

Причина уточнения: выбор `$today±Nd` относительно ЛОКАЛЬНОГО дня и его серверное раскрытие относительно UTC-суток расходились при смещении пояса — односекундный/суточный сдвиг уводил запись из своего дня (дефект закрыт ошибкой, задача fd9eef49).

**Уточнение (приёмка №4, по факту полигона).** Клиент отправляет не «голую дату», а полные UTC-инстансы ЛОКАЛЬНЫХ суток наблюдателя (начало/конец локального дня). Сервер трактует «голую дату» как сутки UTC (469d8d69) и она не покрывает запись у локальной полуночи (26.09 по Москве = 25.09T21:00Z) — поэтому ответственный за пояс клиент нормализует период сам; серверное раскрытие токенов остаётся для API/MCP.

**Дополнительные материалы**
- применяется к: Поле периода — одна дата или диапазон, saved_filters — именованные отборы видов

## Заполнение свойства-связи создаёт ребро без указания направления

## Значение свойства-связи вычисляется из рёбер при чтении

## Иерархия типов: дерево до четырёх уровней и неназначаемый корневой тип

Типы мыслей и типы связей образуют **дерево под единственным корневым типом** (`is_root: true`), который создаётся вместе с сетью и неудаляем.

- **глубина — не более 4 уровней, включая корень** (корень = уровень 1); нарушение лимита, цикл или перенос слишком глубокого поддерева — `422`;
- `parent_id` пустой или `null` означает «под корнем»: **очистка родителя равносильна присвоению корневого типа**;
- **смена родителя** (задача 8ea1ab6a, 0.8.2): безусловный запрет «тип используется в N записях» снят. Правила:
  - если **в любом живом (не базовом, не слитом, не удалённом) слое** сети есть мысль/связь с типом из множества `{изменяемый тип, его потомки, старый родитель, новый родитель}` — `422` `reparent_blocked_by_layer` с перечнем слоёв и счётчиками;
  - иначе для типа **мысли** — первый PATCH без подтверждения → `422` `reparent_impact` со счётчиком мыслей; повторный PATCH с `confirmed: true` → правка применяется;
  - для типа **связи** — изменение применяется сразу, без флага (предупреждать не о чем: состав свойств у связей в UI не показывается);
  - путь MCP `etn.ontology.write` (parent/parent_ref) применяет те же правила без интерактивности (передаёт `confirmed: true` для типов мыслей);
  - клиентский редактор `type-manager` показывает диалог подтверждения с количеством затронутых мыслей; редактор свойств `property-manager` (типы связей) диалога не показывает;
  - регрессии остальных защит L21 сохранены: циклы, глубина ≤4, неназначаемость корня, запрет удаления с детьми;
- удаление типа с подчинёнными типами — `422` (сначала удалить или перенести их); удаление корневого типа — `422` всегда;
- визуальные поля (иконка, цвета, начертание; для связей также цвет, стиль и толщина линии) со `значением null наследуются от родителя`, у корня берутся дефолты приложения;
- **корневой тип нельзя назначить** мысли или связи: запрос с `type_id` = id корня — `422`. Его настройки применяются к элементам **без типа** автоматически.

Фильтры по типам в отборе, поиске и хронике раскрывают каждый указанный тип до его поддерева.

**Уточнение (ошибка 1eb2a430, 0.10.2): паритет MCP↔REST по `parent`.**
- У КОРНЕВОГО типа родителя нет: явный `parent`/`parent_id` (значение-id, `null` или `""`) на нём отвергается `VALIDATION_ERROR` «у корневого типа нет родителя» — одинаково в REST `PATCH /thought-types|link-types` и в MCP `etn.ontology.write` (секции `thought_types[]`/`link_types[]`). Пропущенный ключ `parent` родителя не трогает.
- У некорневого типа пустая строка `parent: ""` равнозначна `null` — очистка родителя прикрепляет тип под корневой, как и в REST (`parent_id: ""` → null).

**Дополнительные материалы**
- относится к подсистемам: REST API, Ядро (доменный слой)
- применяется к: /thought-types и /link-types — CRUD типов и счётчики использования, thought_types — типы мыслей и их иерархия, link_types — типы связей и их иерархия

## Имена типов уникальны регистронезависимо

Имена типов уникальны **регистронезависимо**: «Тип» = «тип» = «ТИП»; сравнение идёт по нормализованному ключу.

- создание или переименование в уже занятое имя — `409 DUPLICATE`;
- для типов связей уникальна **пара имён** (прямое и обратное);
- смена регистра **собственного** имени допустима (это не конфликт с самим собой).

Правило важно агентам: тип можно адресовать именем вместо id, и имя гарантированно разрешается однозначно.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: UTF-8 и регистронезависимое сравнение текста
- применяется к: thought_types — типы мыслей и их иерархия, /thought-types и /link-types — CRUD типов и счётчики использования

<a id="pub-ee8f7b47"></a>

## Инварианты связи: без петель, уникальная тройка, смена концов только парой

Обязательные инварианты любой связи:

- **нет петель**: `source_id <> target_id`, иначе `422`;
- **тройка `(source_id, target_id, type_id)` уникальна**, повтор — `409 DUPLICATE`; две связи между теми же мыслями возможны только с разными типами;
- `type_id` может быть `NULL` — нетипизированная связь допустима;
- **концы меняются только парой**: `source_id` и `target_id` передаются в PATCH вместе — это инверсия связи. Оба конца обязаны существовать (иначе 404), петля — `422`, дубль в новом направлении с учётом типа — `409`. Инвариант уникальности проверяется для **результирующей** пары.

**Дополнительные материалы**
- относится к подсистемам: REST API, Ядро (доменный слой)
- применяется к: CRUD связей: POST, GET, PATCH, DELETE /links, links — направленные связи между мыслями

## Карточка отдаёт связи счётчиками; запрос значений возвращает идентификатор ребра

Агенту в карточке мысли связи отдаются **счётчиками** по каждому свойству-связи и направлению (готовый образец — `meta.link_stats`), а не списками целей: скаляры — значениями, связи — счётчиками.

Запрос значений свойства-связи (REST и MCP) возвращает по каждому ребру: **идентификатор ребра**, цель (id, title, тип), постоянный комментарий ребра. Без идентификатора ребра агент не смог бы обратиться к связи: карточка отдаёт счётчик, а адреса нет нигде.

В интерфейсе — первые десять значений в карточке и диалог с полным списком, где можно добавить, изменить и удалить.

**Актуализация 0.8.3**. Счётчики связей в карточке — единственный формат `meta.link_stats`, каждая запись дополнена именами типов связей; свойства структурных «Родители»/«Потомки» из карточки не возвращаются (meta-счётчиков достаточно); в `etn.thoughts.resolve` текст постоянного комментария — один экземпляр (`comment_preview`), дубль `meta.permanent` не отдаётся.

- относится к подсистемам: REST API, MCP-сервер
- применяется к: /thoughts/{id}/properties — чтение и запись значений свойств, GET /thoughts/{id} — карточка мысли, etn.thoughts.get — карточка мысли, Пользовательский интерфейс (холст и редактор)

## Каталог кодов ошибок REST API и их HTTP-статусы

Закрытый перечень машинных кодов, которыми сервер отвечает на неуспех. Клиент разбирает ситуацию по `error.code`, а не по тексту сообщения.

| HTTP | code | Когда |
|---|---|---|
| 400 | `BAD_REQUEST` | невалидное тело запроса |
| 401 | `UNAUTHORIZED` | нет ключа или ключ невалиден |
| 403 | `FORBIDDEN` | нет прав на ресурс |
| 404 | `NOT_FOUND` | ресурс не существует |
| 409 | `VERSION_CONFLICT` | не совпала версия из `If-Match` |
| 409 | `DUPLICATE` | нарушен UNIQUE-констрейнт (имя типа, пара связи, имя отбора) |
| 422 | `VALIDATION_ERROR` | ошибка бизнес-валидации: удаление защищённой мысли, превышение лимита, заблокированное удаление, неизвестное поле фильтра |
| 500 | `INTERNAL` | внутренняя ошибка сервера |

Отдельно встречается `TRANSACTION_CONFLICT` — редкая гонка при параллельном изменении тех же строк (например, при копировании подграфа); клиент повторяет запрос с тем же `Client-Request-Id`.

Различай 409 и 422: 409 — состояние на сервере разошлось с картиной клиента (версия, дубль), клиент перечитывает и повторяет; 422 — запрос противоречит правилам предметной области, повтор без изменения тела бессмыслен.

**Дополнительные материалы**
- относится к подсистемам: REST API

## Конверт ответа REST API: data, meta и error

Все ответы REST API упакованы в один из трёх конвертов — клиент разбирает их единообразно, не зная маршрута.

**Одиночный объект**

```json
{ "data": { … }, "meta": { "version": 7, "updated_at": "…" } }
```

**Список**

```json
{ "data": [ … ], "meta": { "total": 123, "offset": 0, "limit": 50 } }
```

**Ошибка**

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "title must not be empty",
              "details": [ { "field": "title", "issue": "required" } ],
              "request_id": "…" } }
```

Поля:

| Поле | Смысл |
|---|---|
| `data` | полезная нагрузка: объект или массив |
| `meta.version` | версия записи после операции (для последующего `If-Match`) |
| `meta.total/offset/limit` | пагинация списка |
| `meta.request_id` | идентификатор запроса, возвращается при создании |
| `meta.layer` | эхо текущего слоя сессии у ответов на запись в сети |
| `error.code` | машинный код из каталога кодов ошибок |
| `error.details` | структурированные подробности: поля, блокировки, конфликты |

В теле ошибки `details` — не свободный текст, а разбираемая структура: у валидации это список полей, у блокировки удаления — `blocking`, у конфликта слияния — `conflicts`/`missing_closure`.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: Каталог кодов ошибок REST API и их HTTP-статусы
- применяется к: Эхо текущего слоя в каждом ответе на запись

## Корни копируемого подграфа привязываются к мысли-приёмнику

При копировании подграфа связь с мыслью-приёмником (`parent_thought_id`) получают **только корни подграфа**, а не каждая скопированная мысль.

Алгоритм: для каждой копируемой мысли проверяется, есть ли в переданных связях входящая, **оба конца которой тоже в копируемом наборе**. Если такой связи нет — мысль считается корнем и получает дополнительную связь от `parent_thought_id` (без типа, идемпотентно — уже существующая связь той же пары пропускается).

Так при вставке «Проект A» вместе с его дочерними мыслями к мысли-приёмнику прицепляется только «Проект A», и иерархия не расплющивается.

Случай, когда `parent_thought_id` совпадает с копируемой мыслью, молча пропускается — петли не возникает.

**Дополнительные материалы**
- относится к подсистемам: REST API
- применяется к: POST /thoughts/copy-batch — копирование подграфа мыслей между сетями

## Критерии отбора хроники: записи + цели, «хотя бы одна цель удовлетворяет»

Отбор хроники = критерии записи (текст, автор, даты) + критерии целей (набор «Структур», включая значения свойств).

- запись проходит отбор, если хотя бы одна её привязанная мысль удовлетворяет критериям целей;
- привязки проверяются через `comment_targets`, включая вторичные;
- критерии записи и критерии целей комбинируются по AND, внутри группы — по AND;
- состав критериев — тот же, что у панели «Структур» (включая группу «Родительские мысли»: перечисленные мысли входят в результат вместе с подчинёнными — ошибка ad1551ea, 0.12.1); отбор выражается через `saved_filters` (`view = "chronicle"`).

**Дополнительные материалы**
- применяется к: etn.chronicle.query — хроника по фильтру, POST /chronicle/query — отбор хронологических записей, saved_filters — именованные отборы видов

## Массовая перецепка связей: link_parents, link_children, set_only_parents

Правила массовых операций со связями в групповом запросе (команды отбора панели «Структуры»).

**Якоря** — `args.parent_ids` / `args.child_ids`: непустые массивы id, дедуплицируются.

Общие правила:

- создаваемые связи получают тип `args.link_type_id`; отсутствует или `null` — связь **без типа** (структурная);
- создание идемпотентно по **тройке** `(source, target, args.link_type_id ?? null)`, а не по паре: повторный вызов не дублирует **живое** (не помеченное на удаление) ребро той же тройки, но ребро другого типа у пары не блокирует создание нового — инвариант миграции 029 и `createLink` (задача 3f35d354, решение 24.09.2026);
- совпадение якоря с самой обрабатываемой мыслью (петля) **молча пропускается**, а не падает ошибкой.

| Операция | Что делает с каждой мыслью из `ids` |
|---|---|
| `link_parents` | создать связи `каждый parent_ids → эта мысль` |
| `link_children` | создать связи `эта мысль → каждый child_ids` |
| `set_only_parents` | удалить **все** входящие связи любого типа, включая неактивные, кроме связей с `parent_ids`; недостающие создать |
| `unlink_parents` | удалить все связи `parent_ids → эта мысль` любого типа |
| `unlink_children` | удалить все связи `эта мысль → child_ids` |

Отсутствие связи с каким-то якорем при разрыве — не ошибка, а пустое действие.

Удаление в bulk-операциях в основе — **физическое** (`deleteLink` в базовом слое), минуя корзину: сносимые связи исчезают безвозвратно, а не помечаются на удаление. В рабочем слое удаление идёт надгробиями (13-layers.md §5.2).

Особо опасна `set_only_parents`: она сносит всю прежнюю родительскую обвязку, включая неактуальные связи, которые пользователь не видит на экране.

**Дополнительные материалы**
- относится к подсистемам: REST API
- применяется к: POST /thoughts/batch — групповые операции над мыслями, links — направленные связи между мыслями

## Мини-синтаксис ключевых слов: AND по словам, звёздочка, исключение

Единый язык ключевых слов во всех поисковых маршрутах: отбор мыслей, полнотекстовый поиск, поиск вложений, отбор хроники, фильтр `keywords` витрины инструкций.

- слова разделяются пробелами, порядок любой, **все обязательны (AND)**;
- `*` внутри слова — любое количество любых символов (`счет*` — подстрока с префиксом «счет»); слово без `*` — точная подстрока **ИЛИ** (в источнике `synonyms`) совпадение со СЛОВОМ хранимого `*`-синонима по его границам (`проектиров*` находит «проектирование», см. требование 35218826, сценарий «поиск»);
- `-слово` — исключение: слова не должно быть ни в одном из просматриваемых источников (симметрично включению — литеральная подстрока ИЛИ слово-паттерн);
- запрос из одних исключений — допустимый фильтр «всё, кроме…» в отборе мыслей; в полнотекстовом поиске такой запрос ничего не находит.

Пример: `счет* -вод*` соответствует «Счетчик электричества», но не «счета за воду».

Реализация литеральной ветки в отборе — параметризованный `LIKE … ESCAPE '\\'` по нормализованным колонкам заголовка и синонима, а для комментария — по приведённому к нижнему регистру тексту (`%`, `_`, `\\` экранируются).

**Маршруты единого языка (0.14.1).** Расширение сценария `*`-синонимов действует во всех маршрутах отбора: `etn.thoughts.query` (плоский `keywords` и AST-операнд «Найти слова»), `etn.views.run` (AST), REST `POST /thoughts/query`, плоский отбор хроники (сведён к общему предикату `buildKeywordWordClause`), фильтр `keywords` витрины инструкций (`etn.instructions`, REST `GET /networks/:networkId/instructions` — тот же общий предикат), а также группа `by_names` полнотекстового поиска (`etn.thoughts.search`, REST `GET /search`). Само слово ЗАПРОСА с `*` во всех маршрутах остаётся литеральным (D4).

**В полнотекстовом поиске семантика `*` у слова ЗАПРОСА слабее**: FTS-группы не выражают звёздочку внутри слова — она деградирует в разрыв фразы (`сло*во` → соседние префиксы), а концевая `*` даёт префиксное совпадение. Поиск без стемминга: склонения задаются звёздочкой вручную.

**С 0.9.1 (ADR 5f6cb775, требование 314cbb8d) реализация в отборе мыслей иная:** include-слова дополнительно сужаются индексом `fts_thought_names` (триграммы), LIKE-клауза остаётся остаточным фильтром и хранит семантику выше; сужатель не ставится, когда в области поиска есть комментарий. С 0.14.1 сужатель — надмножество точного предиката: к FTS-кандидатам добавляется OR-ветка по мыслям с `*`-синонимами (требование 314cbb8d).

**Дополнительные материалы**
- относится к подсистемам: REST API, Полнотекстовый поиск (FTS5)
- применяется к: GET /search — полнотекстовый поиск по сети, POST /thoughts/query — отбор мыслей по критериям, GET /attachments — поиск вложений по сети

## Наследование привязок по цепочке типов

Каждый тип наследует **все привязки своих предков** вплоть до корневого — привязки обеих сторон, источника и назначения. Эффективный список свойств типа собирается по цепочке «корень → … → сам тип», привязки каждого уровня добавляются в общем порядке.

**Одно свойство — одна привязка в цепочке.** Свойство, уже подключённое предком, потомку подключать не нужно: оно у него и так есть.

**Подключение свойства к родителю снимает избыточные привязки у потомков.** Когда тип подключает свойство, которое уже подключено каким-то из его потомков, привязки этого свойства у всех типов-поддерева удаляются в той же транзакции. Значения мыслей и связей при этом не меняются вообще: они ссылаются на свойство, а не на привязку, и свойство остаётся доступным — теперь по наследству. Это заменяет прежний запрет (`409 DUPLICATE` при совпадении имени в цепочке или поддереве), который был нужен, пока определение принадлежало типу.

**Что можно и чего нельзя подчинённому типу.**

- Природу унаследованного свойства (тип значения, конфигурацию, имя) менять нельзя: она одна на всю сеть и правится в справочнике — сразу для всех типов, куда свойство подключено.
- Обязательность унаследованной привязки потомок не переопределяет.
- Можно переопределить **значение по умолчанию** и **описание** — для себя и своего поддерева.

**В редакторе типа** видны и редактируются только **собственные** привязки; унаследованные показываются отдельной секцией — обеих сторон, источника и назначения. Правка обязательности унаследованной привязки по-прежнему недоступна, значение по умолчанию и описание переопределяются. Привязки подчинённых типов не видны и не учитываются.

**Владелец без типа** видит свойства корневого типа: запись значений для него резолвит привязки по цепочке из одного корня.

**Повторное подключение к тому же типу (0.8.2, ошибка 0bfd7180).** Подключить свойство, которое этот же тип уже несёт, — не ошибка: привязка обновляется на месте (тот же `id`, роль из запроса, порядок без явного `position` не переезжает). Прежний `409 DUPLICATE` на повтор снят — он ломал сценарий «создал свойство из диалога выбора → выбрал его → записал тип». `409 DUPLICATE` остаётся только для привязки предка (см. выше — свойство и так наследуется).

**В слоях (13-layers.md §13).** Наследование считается по **разрешённой** цепочке типов (правило «ближайший слой побеждает»), а не по сырым строкам физической таблицы: чтение типов, привязок и отборов идёт через представления `thought_types_v` / `type_properties_v` / `thought_type_views_v`. Copy-on-write распространяется на `thought_types`, `link_types`, `type_properties`, `type_property_overrides` наравне с содержательными таблицами — иначе типичное «добавить тип и свойство» в слое сразу стало бы видно всем. Следствие для слияния: мысль в основе не может ссылаться на тип, созданный только в слое, поэтому `type_id` мысли и связи участвуют в замыкании частичного слияния (см. «Типы и справочник свойств входят в замыкание частичного слияния»).

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), Пользовательский интерфейс (холст и редактор)
- применяется к: thought_types — типы мыслей и их иерархия, /types/{id}/properties — определения свойств типа и их порядок, /thoughts/{id}/properties — чтение и запись значений свойств, type_properties — привязка свойства к типу

## Неизвестные поля тела отбора отклоняются ошибкой, а не игнорируются

Неизвестное поле в теле отбора отклоняется `422 VALIDATION_ERROR` с `details.fields` (что пришло) и `details.allowed` (что допустимо), а не игнорируется молча.

Причина — реальный случай ложного вывода: имена фильтров расходятся между REST (`parent_ids`) и MCP (`in_subtree_of`). Агент, подставивший MCP-имя в REST-запрос, раньше получал `200` с пустой страницей и делал вывод «поддерево пусто».

Следствие для разработки: расширяя контракт отбора, новое поле надо добавлять в список разрешённых, иначе старый клиент сломается ошибкой валидации.

**Дополнительные материалы**
- относится к подсистемам: REST API, MCP-сервер
- применяется к: POST /thoughts/query — отбор мыслей по критериям

## Общие принципы REST API: префикс /api/v1, транспорт и обязательные заголовки

Единые правила обращения к серверу ETN: их соблюдает любой клиент REST — десктоп-приложение, скрипт, внешний интегратор.

- **Базовый префикс** всех маршрутов — `/api/v1`. Маршруты сети вложены в него: `/api/v1/networks/{nid}/...`.
- **Транспорт** — HTTPS. Простой HTTP допустим только для локальной разработки.
- **Авторизация** — заголовок `Authorization: Bearer <API-key>`; без валидного ключа сервер отвечает `401 UNAUTHORIZED`.
- **Формат обмена** — `application/json; charset=utf-8`.
- **Идемпотентность изменяющих запросов** — заголовок `Client-Request-Id: <UUID>`: повтор того же запроса в окне дедупликации возвращает кэшированный ответ, а не создаёт вторую запись.
- **Оптимистичный контроль версий** — изменяющий запрос передаёт `If-Match: <version>`; расхождение с текущей версией записи отвергается `409 VERSION_CONFLICT`.
- **Заголовок сессии** `Client-Id` определяет клиентскую сессию: по тройке (пользователь, клиент, сеть) сервер хранит текущий слой изменений и подавляет real-time эхо собственных изменений.

Любая операция REST наследует эти правила: в карточках отдельных маршрутов повторяются только отличия.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: Версионирование записей и разрешение конфликтов, Идемпотентность изменяющих запросов через client_request_id
- применяется к: Слой-осознанность REST API: все чтения и записи идут в слое сессии, Совместимость версий: клиент проверяет диапазон версий сервера

## Обязательное свойство-связь проверяется сервером при записи

Свойство-связь, объявленное в привязке с `required = true`, проверяется сервером при записи мысли: незаполненное попадает в `warnings` ответа (как незаполненные обязательные скаляры). Проверяется наличие хотя бы одного живого значения. Обязательность симметрична и работает у привязки со стороны назначения (Привязка со стороны назначения равноправна с привязкой источника): мысль этого типа без живого входящего ребра данного типа связи получает то же предупреждение.

Это заменяет дисциплинарное правило «требование без связи „применяется к“ считается потерянным» серверной проверкой.

Исключение: свойства «Родители» и «Потомки» обязательными не объявляются (см. их требование).

- относится к подсистемам: Ядро (доменный слой), REST API, MCP-сервер

## Операторы наборов значений: any_of, all_of, none_of

К действующим операторам (`eq`, `ne`, `contains`, `gt`, `gte`, `lt`, `lte`) добавляются три оператора для наборов значений:

- **`any_of`** — набор пересекается с перечисленными значениями (хотя бы одно);
- **`all_of`** — набор содержит все перечисленные значения;
- **`none_of`** — набор не содержит ни одного из перечисленных.

Операторы работают и для свойств-связей (набор целей рёбер), и для обычных множественных скалярных свойств (`config.multiple`). Поведение существующих скалярных операторов не меняется; отборы типов мыслей (views) строятся на тех же условиях и продолжают работать.

**Применение на структурных операндах (ревизия 2026-10-14, задача 759eedeb):** «Родители any_of [X]» = хотя бы один родитель ∈ X; «none_of» = ни один; «all_of» = родители содержат все перечисленные (родители ⊇ X); аналогично «Потомки». Направление all_of (набор содержит перечисленные) отличается от all_in под-выборки (перечисленные входят в выборку) — одноимённые операторы при разных формах значения, см. 485ff29e.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, MCP-сервер
- применяется к: POST /thoughts/query — отбор мыслей по критериям, etn.thoughts.query — структурная выборка, thought_type_views — именованные отборы типов мыслей

## Операции над набором значений: добавить, убрать, заменить

Поверх семантики полной замены (`values: {...}` перезаписывает набор целиком, пустой список очищает) вводятся идемпотентные операции над элементами набора свойства-связи:

- **добавить в набор** (`add`) — принимает цель и необязательный комментарий «зачем именно эта ссылка»; уже существующее живое ребро — no-op;
- **убрать из набора** (`remove`) — помечает ребро цели в корзину; отсутствующее — no-op;
- **заменить набор** (`set`) — текущая семантика `values`.

Семантика обобщается с `etn.thoughts.bulk_update` (`link_parents`/`unlink_parents`/`set_only_parents`) на любое свойство-связь. Добавление одной ссылки — один вызов, без предварительного чтения текущего набора: две параллельные записи не затирают друг друга.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, MCP-сервер
- применяется к: etn.thoughts.bulk_update — групповые операции над мыслями, etn.thoughts.write — батч-запись мыслей, связей и комментариев, /thoughts/{id}/properties — чтение и запись значений свойств, POST /thoughts/batch — групповые операции над мыслями

## Очистка корзины атомарна

**Очистка корзины атомарна.** Удаление пачки мыслей и связей выполняется одной транзакцией: сбой посреди очистки не оставляет корзину разобранной наполовину. Атомарность даёт обёртка записи домена, а не дисциплина вызывающего.

Последствие нарушения: `purgeTrash` удалял пачкой без транзакции (purgeTrash не транзакционен: сбой посреди очистки корзины оставляет частичное удаление).

## Поиск в контексте слоя: фильтрация видимости и дедупликация по логическому id

Полнотекстовый поиск выполняется в контексте слоя сессии, и это меняет весь порядок работы запроса.

**Порядок**: FTS5 сначала ранжирует, затем фильтруется видимость слоя, а результаты дедуплицируются по логическому id — джойном индекса с представлением-разрешателем по rowid строки-победителя.

**Пагинация**: `limit`/`offset` применяются к уже отфильтрованному и дедуплицированному списку — LIMIT **не проталкивается** внутрь FTS-запроса; `meta.total_in_group` считается после дедупликации — на объёмах MVP это точное значение ценой более дорогого подсчёта.

**Видимость**: перекрытые в слое редакции не находятся (ищется текст строки-победителя), а надгробия исключают строку полностью — даже если в основе текст найден.

**Индекс имён** несёт текст «заголовок + синонимы того же слоя»: унаследованные от предка синонимы ищутся, пока строка мысли не перекрыта в цепочке; после материализации тени в индексе остаются только заголовок и синонимы этого слоя.

**Механика (13-layers.md §9).** FTS-таблицы (`fts_thought_names`, `fts_thought_texts`, `fts_link_texts`) — автономные, не external-content, синхронизируются триггерами, поэтому `layer_id UNINDEXED` (миграция 025) не требует пересборки индекса. Фильтрация — rowid-джойн индекса с представлением-разрешателем: `thoughts_v.rowid = fts_thought_names.rowid`, `comments_v.rowid = fts_thought_texts.rowid`; rowid FTS-строки — `pk` физической строки, представление экспонирует rowid победителя, значит матчится только текст строки-победителя. Отсюда два следствия: дедупликация по логическому id выходит «бесплатно» (одна FTS-строка на победителя), а агрегатный текст индекса имён (`title` + синонимы того же слоя) перестаёт находиться по унаследованным синонимам, как только строка мысли перекрыта в цепочке (до перекрытия синонимы предка находятся через его строку). Синонимные триггеры не включают надгробия в агрегат (миграция 026): синоним, удалённый в слое, выпадает из текста строки слоя. Надгробие исключает строку из выдачи, даже если в основе текст найден. `LIMIT` не проталкивается внутрь `MATCH` — фильтрация и дедупликация идут в CTE поверх результата FTS со сканом шире страницы.

**Дополнительные материалы**
- относится к подсистемам: Полнотекстовый поиск (FTS5), Слои изменений (подсистема)
- зависит от: Слой-осознанность REST API: все чтения и записи идут в слое сессии, Полнотекстовые индексы FTS5 и триггеры их синхронизации
- применяется к: GET /search — полнотекстовый поиск по сети

## Порядок ленты хроники: только по дате/времени записи (valid_from, valid_to, created_at, id)

Сортировка ленты — по дате/времени записи; детерминированная и СТАБИЛЬНАЯ: не зависит от состава привязок (мыслей/связей), заголовка и времени изменения (`updated_at`).

1. `valid_from` — в направлении отбора;
2. `valid_to` — в направлении отбора;
3. тайбрейкеры `created_at`, затем `id` — в направлении отбора (уникальный `id` делает порядок тотальным и воспроизводимым).

Класс записи (близость к HOME) в сортировке НЕ участвует. Направление отбора (`order`: «возрастание»/«убывание») применяется ко всем ключам.

Следствия: добавление мысли к записи и снятие всех мыслей НЕ меняют позицию записи в ленте (нет «прыжков»); записи одного дня упорядочены строго по дате/времени.

## Префиксный поиск keywords выполняется через fts_thought_names

Поиск по префиксу слова в `keywords` выполняется через FTS5 `fts_thought_names`, а не LIKE-сканом; мини-язык §6.10 `03-server-api.md` не меняется.

**Проверка.** Тесты фильтра `keywords` не меняются и проходят зелёными; план запроса использует FTS-индекс.

### Ревизия 0.14.1 (задача f0b06700): FTS-сужение обязано быть надмножеством точного предиката

FTS5-сужение (`fts_thought_names`) — оптимизация производительности, а не критерий отбора: множество мыслей, дошедших до точного предиката, обязано содержать ВСЕ мысли, которые точный предикат признал бы совпавшими. Иначе мысли с `*`-синонимами (`35218826`, сценарий «поиск») теряются там, где FTS их не находит: FTS5-триграммы не матчат шаблоны `*`.

**Требование к сужателю (0.14.1).** Сужение для `keywords`/`by_names` строится как объединение (UNION/UNION ALL) FTS-выдачи и ad-hoc ветки по мыслям, у которых есть `*`-синонимы, чей слово-паттерн покрыт словом запроса без `*`; затем на объединении исполняется точный предикат (SQL-функция `synonym_word_pattern_match`) до `COUNT`/`LIMIT`/keyset. Сеть без `*`-синонимов даёт ровно прежнюю FTS-выдачу — надмножество совпадает с прежним множеством.

**Проверка.** Инвариант «SQL-кандидаты ⊇ точный фильтр» проверяется тестом на корпусе, где часть `*`-синонимов заведомо вне FTS-выдачи; при этом `meta.total`/`has_more` точны.

**Дополнительные материалы**
- относится к подсистемам: Полнотекстовый поиск (FTS5)
- зависит от: ADR: Точечные оптимизации выборок — FTS-префикс, keyset-пагинация, COUNT по запросу
- применяется к: query-service.ts (domain), search-service.ts (domain)

## Пустой фильтр отбора возвращает HOME и мыслей-сирот

Отбор без единого критерия (нет ни ключевых слов, ни поддеревьев, ни типов, ни свойств, ни признаков наличия, ни `active`) — не ошибка и не пустой результат.

Сервер возвращает **точки входа в граф**:

- начальную мысль сети HOME (`is_root = 1`) — **всегда первой**;
- всех «сирот» — мысли, у которых нет ни одной активной входящей связи.

Сироты идут за HOME в выбранной сортировке; `show_inactive` действует как обычно (неактуальные сироты попадают только при включённой настройке); `meta.total` — HOME плюс все сироты, пагинация идёт по объединённому списку.

Смысл поведения: при пустом отборе пользователь видит корни дерева сети, а не всю сеть целиком и не пустой экран.

Важное исключение: если передан `parent_ids` с несуществующими id, фильтр считается непустым и результат пуст, HOME не возвращается.

- относится к подсистемам: REST API
- применяется к: POST /thoughts/query — отбор мыслей по критериям

## Резолв типов и ссылок при копировании мыслей в другую сеть

При копировании подграфа типы и ссылки разрешаются **в сети-получателе**, потому что каталоги типов у сетей свои.

- **Тип мысли**: сначала по `type_id` в сети-получателе; не нашёлся — по имени `type_name`; не нашлось ничего — тип сбрасывается (`type_id = null`), мысль создаётся без типа, а не падает ошибкой.
- **Тип связи**: то же правило — по `type_id`, затем по имени (прямому или обратному).
- **Значения свойств типа `thought_ref`**: сначала по id, затем по нормализованному имени мысли в сети-получателе; не нашлось — значение сбрасывается в `null`. Ссылка мысли на саму себя не создаётся.

Практическое следствие: копия в чужую сеть **может приехать без типа и без части ссылок** — это штатное поведение, которое надо учитывать при переносе знаний между сетями.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: thought_types — типы мыслей и их иерархия
- применяется к: POST /thoughts/copy-batch — копирование подграфа мыслей между сетями

## Свойства «Родители» и «Потомки» объявлены на корневом типе и наследуются

Структурные (нетипизированные) связи выражаются двумя свойствами-связями на корневом типе: **«Родители»** (направление `in`) и **«Потомки»** (направление `out`), тип связи — без типа. Свойства наследуются всеми типами и присутствуют у каждой мысли. Обязательными они НЕ объявляются: у корневой мысли родителей нет, предупреждение там неуместно.

Это исключение из правила «одно свойство-связь на тип связи» (Свойство-связь одно на тип связи; сторона задана привязкой): у структурных свойств типа связи нет — их различает именно сторона (направление). В едином списке «Свойства и связи» они показываются системными строками без правки и удаления.

**Порядок детей** задаётся позицией значения в наборе «Потомки»; носитель порядка — прежний `position` ребра. Ребёнок, добавленный с обратной стороны (через своё свойство «Родители»), встаёт в конец списка у родителя.

Поверх «Родителей»/«Потомков» прежние нетипизированные рёбра работают без изменений: `direction` исчезает из обихода, включая структурные связи. Структур может быть несколько — каждая своим типом связи; обход выбирает нужную фильтром по типам.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), Пользовательский интерфейс (холст и редактор)
- применяется к: thoughts — таблица мыслей, type_properties — привязка свойства к типу, links — направленные связи между мыслями

## Семантика direction в REST и в MCP единая — роль target для новой мысли

Поле `direction` в REST (`create_link`) и в MCP (`etn.thoughts.write` `links[]`) использует ОДНУ семантику: значение называет роль `target_thought_id` для НОВОЙ (создаваемой/связываемой) мысли.

| Значение | Роль `target_thought_id` |
|---|---|
| `"parent"` | target становится родителем новой мысли — новая мысль подвешивается ПОД target (типичный кейс — «создать мысль в разделе X») |
| `"child"` | target становится ребёнком новой мысли — новая мысль становится родителем target |

До версии 0.6.3 семантика REST и MCP была **противоположной** (баг-фикс 045 вводил перевод значения на границе MCP-слоя, функция `toDomainLinkDirection`) — это было формально задокументировано здесь же как «намеренное», но с точки зрения согласованности API являлось дефектом проектирования: один и тот же вызов с одинаковым значением `direction` на двух публичных интерфейсах одной системы давал противоположную топологию графа. Исправлено задачей `09e10db0`: REST/доменный слой инвертирован под действовавшую MCP-семантику (признанную канонической — интуитивной, агент-ориентированной), перевод на границе MCP убран. Клиентский Electron UI синхронно поправлен.

Сомневаешься — создавай связь отдельной операцией с явными `source_id`/`target_id` (REST `POST /links`; в MCP — свойство-связь через `etn.properties.add` либо батч `etn.thoughts.write` с `links[]`): там неоднозначности нет.

- применяется к: POST /thoughts — создание мысли со связью-родителем, etn.thoughts.upsert_bundle — составная запись единицы знания, etn.thoughts.create — создание мысли, links — направленные связи между мыслями

## Семейство операций etn.links.* упраздняется, кроме восстановления из корзины

Создание и удаление связей через отдельные операции упраздняются: `etn.links.create`, `etn.links.delete`, `etn.links.trash`, `etn.links.get`, `etn.links.deletion_check` и их REST-аналоги (`POST /links`, `DELETE /links/{id}`) снимаются — создание и удаление уходят в операции над свойствами. ## Серверный рендер markdown и политика безопасности HTML

`body_html` комментария рендерит **сервер** единым рендерером `@etn/markdown` (markdown-it). Клиент свой markdown не собирает и разночтений в верстке не создаёт.

**Поддерживается**: GFM-таблицы, wiki-ссылки `[[имя|алиас]]`, размеры картинок `![alt|600px](url)` и `![alt|50%](url)`, подсветка fenced-кода.

**Безопасность (защита от XSS)**:

- `html: false` — сырой HTML в тексте экранируется, а не исполняется;
- allow-list протоколов: ссылки — `http`, `https`, `mailto` и `etnimg` (локальные файлы вложений); картинки — те же плюс `data:` и `file:`;
- лимит длины текста — 256 КиБ.

**Версия рендера**: при её смене сервер один раз при старте перерендеривает кеш `body_html` всех комментариев (маркер в настройке `md.render_version`). Менять правила рендера можно только в пакете `@etn/markdown` — локальные правки в сервере или клиенте запрещены.

**Дополнительные материалы**
- относится к подсистемам: Markdown-рендерер, REST API
- применяется к: comments — постоянные и хронологические комментарии, CRUD комментариев мыслей и связей, GET и PUT /attachments/{id}/content — содержимое текстового вложения

## Слой-осознанность REST API: все чтения и записи идут в слое сессии

Слои изменений — сквозное свойство всего API сети, а не отдельный набор маршрутов.

**Любой запрос к `/api/v1/networks/…` выполняется в контексте текущего слоя сессии**: чтения разрешаются по цепочке предков слоя, записи материализуются в нём теневыми строками и надгробиями.

Текущий слой — **умолчание сессии, хранимое на сервере**, а не параметр запроса:

- координаты сессии — тройка `(user_id, client_id, network_id)`; `client_id` приезжает заголовком `Client-Id`;
- запись живёт в неветвимой таблице `session_layers` сетевой БД;
- смена слоя — отдельная операция выбора слоя, а не переключение соединения на лету: пул держит по соединению на пару (сеть, слой);
- то же умолчание действует для MCP-вызовов того же ключа.

Права на слои у всех участников сети одинаковые: отдельной роли «владелец слоя» нет.

Опасность скрытого состояния очевидна: после перезапуска клиента можно писать не туда, поэтому каждый ответ на запись обязан нести эхо слоя.

**Дополнительные материалы**
- относится к подсистемам: Слои изменений (подсистема), REST API
- зависит от: Слои изменений: copy-on-write вместо копии сети, session_layers — текущий слой клиентской сессии
- применяется к: Общие принципы REST API: префикс /api/v1, транспорт и обязательные заголовки

## Смена концов связи в рабочем слое создаёт новую связь с новым id

Смена концов связи (перецепка) **в рабочем слое** выполняется как пометка старой связи на удаление плюс создание новой — а не как `UPDATE` той же строки.

Последствия, которые обязан учитывать клиент:

- ответ 200 несёт **новую связь с новым `id`** и `version: 1`;
- старый `id` в этом слое больше не разрешается;
- видимые зависимые строки старой связи (комментарии, вложения, значения свойств) скрываются каскадом, как при удалении;
- real-time шлёт `link.deleted` (старый id) и `link.created` (новая связь) вместо `link.updated`.

Исключения: PATCH, повторяющий текущие значения концов, — обычное обновление; **в основе** смена концов — обычный `UPDATE` с тем же `id`.

**Дополнительные материалы**
- относится к подсистемам: Слои изменений (подсистема), REST API
- зависит от: Слой-осознанность REST API: все чтения и записи идут в слое сессии
- применяется к: CRUD связей: POST, GET, PATCH, DELETE /links

## Снятие владения: защита своей иконки/обложки, предупреждение о текстах, чужие не мешают

Правило снятия владения — по паре (вложение, объект):

- **ЗАПРЕТ** (`409 ATTACHMENT_OWNER_IS_ICON`), если удаляемый ОБЪЕКТ сам использует вложение как свою иконку или обложку (`icon_attachment_id`/`cover_attachment_id`). Клиент сначала предлагает сменить/очистить;
- **ПРЕДУПРЕЖДЕНИЕ** (`409 ATTACHMENT_OWNER_IN_TEXT`), если вложение встречается в текстах комментариев этого объекта (постоянном или хрониковых) — «картинки перестанут отображаться». После подтверждения владение снимается, ССЫЛКИ в текстах остаются, но не отображаются (битая картинка-заглушка);
- **ЧУЖИЕ использования не мешают вовсе:** у чужих объектов своё владение; на них снятие не влияет.

Иначе — тихое снятие. Правило — и на сервере, и в UI вкладки «Вложения».

**Как определяются случаи (аудит).**
- «своя иконка/обложка» — прямая проверка: `icon_attachment_id` объекта (или `cover_attachment_id` публикации) = это вложение;
- «вложение в текстах» — сканирование `body_md` ВСЕХ комментариев сети (постоянных и хронологических) на ТОЧНОЕ вхождение `etnimg://attachment/<id>` (id → file_path не нужен; совпадение по id вложения). Проверка — по своей сущности владельца (его комментарии).

**Дополнительные материалы**
- применяется к: DELETE /attachments/{id}/owners — снять владение вложения, Вкладка «Вложения»

## Совместимость версий: клиент проверяет диапазон версий сервера

## Ссылка на картинку-вложение в markdown — etnimg://attachment/<id>

Картинка-вложение вставляется в текст комментария (постоянного или дневникового) ссылкой `![<подпись>](etnimg://attachment/<id>)`.

Форма выбрана ради устойчивости: id вложения не меняется при переездах файлов и виден в любом слое (форма `etnimg://attachment/<id>` уже обслуживается main-процессом — ADR `7682d51e`); форма по пути НЕ используется для вставленных в текст картинок.

Требования к рендеру (@etn/markdown и клиент): схема `etnimg` разрешена в позиции изображения и в ссылках; недоступное/удалённое вложение даёт заглушку/битую картинку, текст не ломается. Размер — по существующему синтаксису `![подпись|600px](…)`.

**Экспорт и печать (аудит).** При сборке публикации/экспорте `etnimg://attachment/<id>` резолвится id → `file_path`; файл недоступен — плейсхолдер + предупреждение в экспорте; совместимость с `data:`-URI и каталогом `assets/` (в zip картинка кладётся ассетом, ссылка переписывается на относительную).

**Дополнительные материалы**
- применяется к: attachments — вложения мыслей и связей, @etn/markdown

## Требование: авто-свёртка activity_log при слиянии и удалении слоя

**Слияние слоя в основу** автоматически сворачивает его события: в основе по каждой затронутой в слое сущности появляется ровно одна итоговая запись (`created`/`updated`/`deleted`) с **автором и временем исходного итогового события слоя** (не временем слияния и не исполнителем слияния). Детальные события слоя в основе не переносятся.

**Удаление слоя** (без слияния) удаляет все его события из `activity_log` вместе со слоем.

Действие согласуется с механикой слоёв `docs/13-layers.md` (файл — источник истины по слоям; правка матрицы ветвимости — задачей проекта).

**Детали (13-layers.md §8.4a).** Итоговая запись основы — `created`, если в слое было событие создания, иначе действие самого позднего события слоя (`updated`/`deleted`/`trashed`/`restored`). Автор и `occurred_at_ms` берутся из самого позднего события слоя, `entity_title` — снимок этого события (чтобы запись оставалась читаемой после удаления сущности). Детальные строки слоя (`layer_id = L`) удаляются; события с `layer_id ≠ L`, включая исходный `created` в основе, если сущность создавалась до слоя, не затрагиваются. Вся операция идёт в той же транзакции, что merge, и откатывается вместе; в отчёте слияния видна как `activity_rollup: { groups, removed }`. Удаление слоя без слияния вычищает события всего поддерева (`activity_log.layer_id ∈ subtree(L)`) до физического `DELETE FROM layers`. Ручные свёртка/обрезка — вне merge/delete, REST и MCP.

**Дополнительные материалы**
- относится к подсистемам: Слои изменений (подсистема), Хранилище (SQLite)
- применяется к: activity_log — журнал активности сети

## Требование: захват объекта — границы и запрет записи

**Актуализация 0.8.4 (задача 09f19952).** Операция явного захвата для агентов — действие `locks.acquire` исполнителя `etn.ops` (не отдельный инструмент). Детали — `etn.guide { topic: "locks.acquire" }`.

Объект (мысль, связь, тип мысли/связи, свойство, постоянный/хроно-комментарий, вложение), захваченный участником, недоступен для **записи** другим участникам через клиент, REST и MCP: операции создания/изменения/удаления этого объекта (и связей с захваченной мыслью) возвращают ошибку `LOCKED` с указанием, кто держит захват. **Чтение никогда не блокируется.**

**Начало редактирования** (захват ставит клиент автоматически): переход в режим правки комментария; открытие диалога настроек мысли/связи; открытие диалога изменения типа или свойства; открытие диалога подтверждения удаления; (MCP) явный захват инструментом `etn.locks.acquire` перед серией правок.

Повторный захват того же объекта тем же пользователем — продление; чужой активный захват делает acquire ошибкой.

**Дополнительные материалы**
- относится к подсистемам: REST API, Пользовательский интерфейс (холст и редактор), MCP-сервер
- применяется к: /locks — захват, снятие и сброс захватов объектов, etn.locks.* — захват объектов в MCP

## Удаление значения свойства-связи помечает ребро в корзину

Удаление значения из набора свойства-связи (операция `remove` или полная замена без этого элемента) помечает ребро `marked_for_deletion = true`, а не стирает физически: иначе постоянный комментарий связи («зачем эта ссылка») исчез бы молча. Восстановление — существующей операцией корзины. Физическая чистка — `etn.trash.purge` / `POST /trash/purge` как сегодня.

Пометка учитывается при чтении: помеченное ребро в значения свойства не попадает.

**Разграничение с удалением самого свойства-связи.** Удаление одного значения (цели) — корзина, как описано выше. А вот удаление самого свойства-связи рёбра в корзину НЕ отправляет (Свойство-связь и тип связи — единый жизненный цикл): тип связи удаляется вместе со свойством, рёбра теряют `type_id` и становятся структурными.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, MCP-сервер
- применяется к: CRUD связей: POST, GET, PATCH, DELETE /links, GET /trash и POST /trash/purge — корзина мыслесети, Корзина и проверки удаления в MCP

## Условия по свойствам в отборе: операции зависят от типа значения

Условия `properties: [...]` в плоской форме отбора (REST — `{ property_id, op, value? }`, MCP — `{ property_id | property, operator, value? }`) применяются к колонке, соответствующей типу значения определения свойства; все условия объединяются по AND.

Набор операторов плоской формы — единый канон из 14 (`eq`, `ne`, `contains`, `gt`, `gte`, `lt`, `lte`, `in`, `not_in`, `is_empty`, `not_empty`, `any_of`, `all_of`, `none_of`; `FLAT_PROPERTY_OPS` в `shared/src/enums.ts`). Паритет MCP/REST держит сторож `guard-flat-property-operators` (задача 40c76144). Enum описывает форму входа; применимость к природе свойства проверяет движок (`OPS_BY_VALUE_TYPE`), недопустимая пара «оператор × `value_type`» — `VALIDATION_ERROR` (`422`), а не тихий пустой результат:

| `value_type` | Допустимые `op` |
|---|---|
| text, url | `contains`, `eq`, `ne`, `in`, `not_in`, `is_empty`, `not_empty`, `any_of`, `all_of`, `none_of` |
| number, date | `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `is_empty`, `not_empty` |
| bool | `eq`, `ne` |
| link | `eq`, `ne`, `in`, `not_in`, `is_empty`, `not_empty`, `any_of`, `all_of`, `none_of` |
| thought_ref | `eq`, `ne`, `in`, `not_in`, `is_empty`, `not_empty`, `any_of`, `all_of`, `none_of` |
| cross_network_ref, publication | `eq`, `ne`, `any_of`, `all_of`, `none_of`, `is_empty`, `not_empty` |

- `in`/`not_in` принимают **непустой** массив значений (OR внутри списка); пустой массив — `VALIDATION_ERROR`;
- `is_empty`/`not_empty` — наличие значения: `value` не нужен (переданное ЛЮБОЙ формы, включая `null`/объект, игнорируется — паритет MCP и REST); `is_empty` — значения нет (нет строки `property_values` с непустой колонкой; у свойства-связи — **нет живого ребра `links_v`**, а не пустая строка значения), `not_empty` — есть. Для `bool` пара запрещена — тот же смысл дают `eq true`/`eq false`. Для операнда «Тип» наличие есть только в AST (`type: is_empty/not_empty`); в плоской форме типа его нет — не вводить (решение 40c76144);
- **множественное скалярное свойство** (`config.multiple`, требование 12fccde9; для `text` — comma-joined строка, `02-data-model` §3.4–3.5, для `url` — JSON-массив) операторы `in`/`not_in`/`any_of`/`all_of`/`none_of` матчат **поэлементно** (требование 92b9c55b): `in`/`any_of` — совпал хотя бы один элемент значения; `all_of` — совпали все перечисленные; `not_in`/`none_of` — не совпал ни один. Одиночное свойство — прежнее точное сравнение по хранимой строке (элемент один), поведение скалярных операций не меняется;
- для `thought_ref` сравнение видит **и id внутри JSON-массивов множественных значений**, не только одиночные ссылки; `is_empty`/`not_empty` — наличие хоть какого-то id;
- **условие с несуществующим `property_id` игнорируется**, а не падает ошибкой: определение могло быть удалено после сохранения отбора, и остальные условия должны продолжать работать (на границах ввода неразрешимая ссылка даёт `NOT_FOUND`/`VALIDATION_ERROR`, а не расширение отбора до всей сети — ошибки 4f17cb73/090d0242);
- Известное расхождение плоской формы и AST (вне DoD 40c76144): у множественных `url`/`cross_network_ref`/`publication` строка `'[]'` плоской формой считается значением (смотрит на хранимую строку), AST — пустым набором (считает элементы); достижимо только импортом/легаси;
- Наборы AST шире плоских (`PROPERTY_OPERATOR_SETS` в `shared/src/filter-profiles.ts`: `not_contains`, `between`, `in_hierarchy` и др.); таблица выше — только плоская форма.

**`contains` — только строка (0.14.1, ошибка 9420a34c).** Массив (в том числе `["alpha"]`), объект, `null` и число — `VALIDATION_ERROR` с `details { field: "value", operator: "contains", expected: "string" }`; одинаково на MCP и REST. Молчаливого stringify массива в `"al,pha"` больше нет: значение уходит в LIKE только как строка. Presence-операторы (`is_empty`/`not_empty`) правило не затрагивает — их `value` игнорируется в любой форме.

**Уточнение (2026-10-27, ошибка 9420a34c).** `contains ""` (пустая строка) допустим и совпадает со всеми непустыми значениями свойства — поведение прежнее, спекой до 0.14.1 не определялось; контракт не расширяется.

**Дополнительные материалы**
- относится к подсистемам: REST API
- применяется к: property_values — значения свойств мыслей и связей, POST /thoughts/query — отбор мыслей по критериям

## Фильтр обхода по типам связей

**Актуализация 0.8.4 (задача 09f19952).** `etn.thoughts.path` снят с постоянного набора MCP — это действие `thoughts.path` исполнителя `etn.ops` (read-only). Остальные упомянутые вызовы (`etn.thoughts.subgraph`, `etn.thoughts.neighbors`, `etn.thoughts.query`) — по-прежнему инструменты. Детали — `etn.guide { topic: "thoughts.path" }`.

Обход графа можно ограничить перечнем типов связей: `etn.thoughts.subgraph`, `etn.thoughts.neighbors`, `etn.thoughts.path`, `etn.thoughts.query { in_subtree_of }` и их REST-эквиваленты (`POST /thoughts/{id}/focus`, `GET /thoughts/{id}/neighbors`, `POST /thoughts/query`) принимают опциональный фильтр.

- **Нетипизированные (структурные) связи отбираются наравне с типизированными**: можно сказать «только структурные» и «только такой-то тип (или перечень)».
- **Иерархия типов связей:** отбор по родительскому типу включает его потомков.
- **Без фильтра поведение не меняется** — обход идёт по всем рёбрам, как сегодня.

Фильтр лечит шум там, где он возникает — в запросе: после него правило «больше 15 однотипных связей — группируй каталогом» больше не нужно.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, MCP-сервер
- применяется к: POST /thoughts/{id}/focus — окрестность мысли для холста, etn.thoughts.subgraph — подграф вокруг мыслей, etn.thoughts.query — структурная выборка, POST /thoughts/query — отбор мыслей по критериям, etn.thoughts.neighbors — соседи и обход графа, GET /thoughts/{id}/neighbors — соседи мысли без смены фокуса

## Фильтры по датам создания и изменения в отборе мыслей

Отбор мыслей принимает границы по датам создания и изменения: `created_after`, `created_before`, `updated_after`, `updated_before` (ISO-8601). Границы включительные, любая может быть опущена, комбинируются с остальными критериями по AND.

**Единый набор критериев везде.** Сегодня эти фильтры есть только в MCP-выборке, а в REST-отборе и в панели «Структур» их нет — из-за этого один и тот же по смыслу отбор нельзя выразить в интерфейсе и в отборе типа. Требование закрывает расхождение: критерии REST-отбора, панели отбора структур и отборов типов совпадают.

**В панели «Структур»** это отдельная сворачиваемая группа «Даты» с двумя парами полей; заполненная группа маркируется, как и прочие.

**В отборах типов** границы дат — главное место токенов `$today` и `$thought.[<дата>]`: без них не выражается ни «мысли этого дня» для ежедневника, ни «просроченные работы».

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, Пользовательский интерфейс (холст и редактор)
- применяется к: POST /thoughts/query — отбор мыслей по критериям, Панель отбора структур

## Что не копируется при копировании подграфа мыслей

Копирование подграфа — не клонирование. Намеренно **не переносятся**:

- служебные поля исходных записей: `id`, `version`, `created_at`, `updated_at`, `created_by`, `updated_by` — у копий они свои;
- сами файлы вложений и файлы иконок — копируются только метаданные (`url`/`file_path`), а общий файл остаётся общим;
- **хронологические комментарии** — копируется только постоянный комментарий;
- настройки типов мыслей и связей — у каждой сети свои каталоги типов.

**Защищённая мысль (HOME) не копируется вовсе** — попытка даёт `FORBIDDEN`.

Следствие для пользователя: история работы (хроника) остаётся в исходной сети; в копию переезжает только то, что описывает мысль по существу.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: Два вида файловых вложений и судьба файла при удалении
- применяется к: POST /thoughts/copy-batch — копирование подграфа мыслей между сетями

## Эхо текущего слоя в каждом ответе на запись

Каждый **успешный ответ на запись** в маршрутах сети обязан сообщать, в какой слой попала запись:

- ответы с телом — `meta.layer: { id, title }` (добавляется сервером во все mutating-ответы `/api/v1/networks…`, включая создание сети, участников, настроек и самих слоёв);
- безтельные `204` (DELETE-маршруты) — заголовки `X-Etn-Layer: <id>` и `X-Etn-Layer-Title: <title>`, где title percent-encoded (значения заголовков обязаны быть ASCII). Контракт 204 сохранён, чтобы не ломать клиентов;
- **ответы на чтение эхо не несут** — они неявно определены слоем сессии; единственное исключение — флаг `current` в списке слоёв.

Зачем: слой — скрытое состояние сессии, и без эха запись в чужой слой обнаруживается только постфактум — например, после перезапуска клиента.

**Дополнительные материалы**
- относится к подсистемам: Слои изменений (подсистема), REST API
- зависит от: Слой-осознанность REST API: все чтения и записи идут в слое сессии
- применяется к: Конверт ответа REST API: data, meta и error

## Поиск карты: настройки отбора компилируются в общий AST, текст запроса остаётся FTS

**Суть.** В точке поиска карты (`GET /search`, `etn.thoughts.search`) в общий AST (профиль `thoughts`) компилируются ТОЛЬКО мыслевые настройки, а текст запроса и корпусные настройки остаются параметрами полнотекстового FTS-поиска; отбор исполняется единым движком.

**В AST (профиль `thoughts`).**
- Подкорень → строка «Родители/Потомки» с оператором «в иерархии».
- Типы мыслей (`type_id`) — строками-условиями.
- «Показывать неактуальные» (`show_inactive`).
- «Корзина» (`trashed`).

**Остаётся параметром полнотекстового поиска (не в редакторе, не в AST).**
- Текст `q` (FTS5, мини-синтаксис).
- Области `scope` (имена/тексты/связи/хронология).
- Тип связи (`link_type_id`) — фильтрует ХИТЫ-связи и хроно-хиты по `l.type_id` (функции `searchLinks` и `buildChronoHalf`, `server/src/domain/search-service.ts`), а не мысль.
- Автор/редактор (`author_id`/`editor_id`) — для раздела «хронология» это авторство КОММЕНТАРИЯ (функция `buildChronoHalf`), для «текстов» — авторство мысли (функция `searchTexts`, `server/src/domain/search-service.ts`).

**Wire.** В точке поиска принимается необязательное поле `ast`; плоские мыслевые параметры (`type_id`, `show_inactive`, `trashed`, `in`/`from_thought_id`) сохраняются для обратной совместимости и компилируются в тот же AST. `ast` XOR плоские МЫСЛЕВЫЕ параметры: одновременная их передача даёт `VALIDATION_ERROR` (паттерн `ast` XOR старые критерии в схеме тела `POST /thoughts/query`, `server/src/contracts.ts`, константа `LEGACY_QUERY_CRITERIA`). Корпусные параметры (`q`, `scope`, `link_type_id`, `author_id`, `editor_id`) допустимы вместе с `ast` всегда — в XOR не входят. Веерный режим (`network_ids`) обязан передавать `ast` (сейчас не передаёт: фабрика маршрутов `createSearchRoutes`, `server/src/routes/search.ts`; `fanOutSearch`, `server/src/domain/cross-network-search-service.ts`).

**Пара `in`/`from_thought_id`.** Это НЕ самостоятельный критерий, а параметр СПОСОБА ОБХОДА подкорня: `in` обязан быть `subtree` и требует `from_thought_id` (иначе `VALIDATION_ERROR` — схема `RestSearchQuery`, `server/src/contracts.ts`), а домен включает подкорень только при `in = 'subtree'` (`subtreeIds` через `collectSubtreeIds`, `server/src/domain/search-service.ts`). В правиле XOR с `ast` пара считается ОДНОЙ группой (плоский подкорень): присутствие `in`/`from_thought_id` вместе с `ast` нарушает XOR так же, как и любой другой плоский мыслевой критерий.

**Режим обхода подкорня.** Прежнее поддерево поиска (`collectSubtreeIds`, рекурсивный CTE `descend`, `server/src/domain/search-service.ts`) идёт от корня к ПОТОМКАМ — связи `source → target` (`JOIN links_v l ON l.source_id = d.id AND (l.active = 1 OR :show_inactive)`, шаг на `l.target_id`), обходит ВСЕ связи без фильтра типа, включает сам корень и НЕ проверяет `marked_for_deletion`. Новый AST-обход (`collectHierarchySubtree`/`hierarchyStructuralLeafClause`, `server/src/domain/graph-traversal.ts`, `server/src/domain/query-service.ts`) в ОБОИХ режимах (`structural`/`all_links`) несёт `AND l.active = 1 AND l.marked_for_deletion = 0`. Поэтому подкорень компилируется паттерном «ИЛИ(id в [корни], parents in_hierarchy [корни] с режимом `all_links`), включая сам корень». Лист `parents` + `in_hierarchy` матчит мысль, у которой РОДИТЕЛЬ входит в поддерево корней, — это ровно ПОТОМКИ корней (сами корни добавляет лист `id в [корни]`); лист `children` + `in_hierarchy` дал бы обратное — мысли, у которых ПОТОМОК входит в поддерево (ПРЕДКИ корней), и для подкорня он не годится (`server/tests/filter-ast-hierarchy.test.ts`: `parents … in_hierarchy` ⇒ потомки корней). Режим `all_links` нужен, т.к. прежний обход шёл по ВСЕМ связям без фильтра типа; режим по умолчанию `structural` ограничился бы нетипизированными рёбрами. Прецедент — клиентский компилятор `compileFlatCriteriaToAst`/`applyLegacyHierarchyTraversal` (`client/src/renderer/lib/filter-builder.ts`, паттерн для корней `parent_ids`; коммит 480371c3).

**Рёбра корзины — намеренное изменение поведения (НЕ паритет).** Прежний `collectSubtreeIds` не проверял `marked_for_deletion`: мысль, достижимая ТОЛЬКО по ребру из корзины, в прежний подкорень ПОПАДАЛА. Новый AST-обход такие рёбра исключает (`AND l.active = 1 AND l.marked_for_deletion = 0` в обоих режимах), поэтому в новый подкорень такая мысль НЕ входит. Это объявленное НАМЕРЕННЫМ изменение поведения, а не паритет: уважение корзины — общая семантика обхода иерархии во всех местах, а фильтр `active`/`marked_for_deletion` — часть единого движка. Паритет подкорня — на деревьях БЕЗ рёбер корзины; наличие ребра корзины на пути меняет набор осознанно.

**Ресурсные предохранители подкорня.** Новый путь ограничен бюджетами `HIERARCHY_SUBTREE_MAX_NODES = 2000` (число узлов) и `TRAVERSAL_DEFAULTS.QUERY_TIMEOUT_MS = 5000` (время) — обе в `shared/src/constants.ts`. При превышении — явная ошибка `VALIDATION_ERROR` (`reason: hierarchy_budget`, функция `astHierarchySubtree`, `server/src/domain/query-service.ts`), без частичного результата. У прежнего `collectSubtreeIds` бюджета узлов/времени не было — только молчаливое усечение по глубине. Объявленное новое поведение: подкорень, превышающий ресурсный предел, даёт `VALIDATION_ERROR`, а не молчаливый (усечённый) результат.

**Глубина «в иерархии» и паритет.** Предел «в иерархии» по глубине — константа `TRAVERSAL_DEFAULTS.MAX_DEPTH = 20` (`shared/src/constants.ts`); в `shared/src/types/filter-ast.ts` лежит лишь комментарий о глубине 20, а не сама константа. Тем же `TRAVERSAL_DEFAULTS.MAX_DEPTH = 20` ограничен обход поддерева старой точки поиска (`collectSubtreeIds`, `server/src/domain/search-service.ts`). Паритет — на деревьях глубиной ≤ 20: набор совпадает с прежним. Глубже 20 старая точка поиска обрезалась тем же пределом. Усечение ПО ГЛУБИНЕ молчаливое в ОБОИХ путях; явная диагностика ресурсного бюджета (ошибка `VALIDATION_ERROR`) есть ТОЛЬКО у нового пути — это не «общая диагностика обрезки», а новое поведение нового пути.

**Операнд `link_type` в `ast`.** Точка поиска валидирует `ast` профилем `thoughts` (`assertFilterAstInProfile`) и дополнительных ограничений операндов НЕ вводит. Операнд `link_type` входит в профиль `thoughts` (`shared/src/filter-profiles.ts`, `THOUGHT_OPERANDS`), поэтому присланный клиентом лист `link_type` как МЫСЛИ-условие («у мысли есть инцидентная связь указанного типа») допустим и исполняется. Это не то же самое, что UI-настройка «типы связей» строки поиска: она остаётся КОРПУСНЫМ параметром `link_type_id` (фильтр ХИТОВ-связей и хроно-хитов) и в AST не компилируется. Запрета сверх профиля `thoughts` точка поиска не вводит.

**Профиль и исполнение.** Строка поиска использует профиль `thoughts` (`shared/src/filter-profiles.ts`). Профиль `map` имеет тот же состав операндов (`MAP_OPERANDS = [...THOUGHT_OPERANDS]`), но для строки поиска не применяется — расхождение наименования не вводить. Сервер валидирует `ast` профилем `thoughts` (`assertFilterAstInProfile`). AST-условие добавляется КОНЪЮНКЦИЕЙ в WHERE мыслевых FTS-групп (функция `filterAstClause`, `server/src/domain/query-service.ts`): движок даёт множество-кандидат, FTS — ранжированные совпадения и сниппеты, результат — пересечение. Так сохраняются `ORDER BY rank` и сниппеты; множество id не материализуется.

**MCP.** Инструмент `etn.thoughts.search` (`d7ced4bf`) принимает необязательный `ast` (профиль `thoughts`); актуализация карточки инструмента входит в ту же работу.

**Запреты.**
- Текст запроса `q` НЕ превращается в AST-лист «Есть слова».
- Области `scope` остаются частью полнотекстового поиска, а не листом «Есть слова».
- Корпусные НАСТРОЙКИ строки поиска (UI «типы связей» = `link_type_id`, авторство комментария) НЕ компилируются в мысли-условия AST; при этом сам операнд `link_type` в присланном `ast` профилем `thoughts` разрешён (см. «Операнд `link_type` в `ast`»).
- Мыслевые настройки НЕ дублируются плоскими параметрами как отдельный путь исполнения: `type_id`, `show_inactive`, `trashed`, `in`/`from_thought_id` компилируются в тот же AST.

**Границы.** Клиент + сервер. Форма wire-ответа (группы `by_names`/`by_texts`/`by_links`/`by_chrono`, сниппеты, пагинация) сохраняется.

**Критерии.** Поиск с мыслевыми настройками (поддерево/типы/неактуальные/корзина) даёт тот же набор, что до перевода, — на деревьях БЕЗ рёбер корзины (мысль, достижимая только по ребру, помеченному на удаление, в новый подкорень НАМЕРЕННО не входит); корпусные разделы (связи/хронология) не изменили поведения, включая фильтр по типу связи и авторство комментариев; ранжирование и сниппеты сохранены.

**Ревизия (2026-10-13, решение пользователя по развилке поиска: мыслевые → AST, корпусные → параметры поиска).** Прежняя редакция отправляла в AST и корпусные настройки (типы связей, автор/редактор), что противоречит смыслу: тип связи и авторство комментария описывают хит, а не мысль. Уточнено разделение «мыслевые → AST / корпусные → параметры FTS»; добавлены wire (необязательный `ast` + совместимые плоские мыслевые параметры), веерный режим, паритет глубины «в иерархии», приём `ast` в MCP.

Прежняя фраза «для «текстов» — авторство мысли» относится к мыслевым группам (именам и текстам) одинаково, а не к текстам только. Снятие полей «Автор»/«Редактор» с UI (решение заказчика) поэтому затрагивает фильтрацию хитов всех трёх групп — потеря поименована в ревизии 2026-10-15.
