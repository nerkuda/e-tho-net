# 05-mcp-server — MCP-сервер

**Автор:** Проект ETN

MCP-сервер для AI-агентов: транспорт, инструменты, ресурсы, лимиты и read-only режим.

<a id="pub-adda80e4"></a>

## AI-агент ограничен MCP-контуром

Внешний AI-агент подключается к MCP-серверу, авторизуется API-ключом и через инструменты MCP читает и изменяет мыслесеть **наравне с человеком** — с теми же событиями real-time и теми же проверками прав.

Два утверждения, которые должны выполняться одновременно:

1. **Агент не ограничен в данных** — особого «урезанного» набора операций для агентов нет; права определяются ключом и членством в сети, а не тем, что это агент.
2. **Агент ограничен в поверхности** — доступа к подсистемам вне MCP-контура у него нет.

Отсюда запрет: нельзя реализовывать правило в MCP-слое в обход ядра — иначе поведение для агента и для человека разойдётся.

Модель авторизации (агент действует от лица пользователя, чей ключ передан):

- видит и может менять только сети, в которых пользователь — участник;
- внутри сети — равноправный участник (как человек); никаких специальных «машинных» прав сверх прав пользователя;
- отображается в `audit_log` со своим `actor_user_id`.

Многоканальный агент: доступ к нескольким сетям — параметром `network_id` в каждом tool-вызове (ключ уже даёт доступ ко всем сетям пользователя). Текущий слой изменений — тоже пер-ключевое состояние: слой-сессия ключуется парой `(network_id, api_keys.id)`, поэтому два ключа одного пользователя держат независимые слой-сессии, и переключение слоя одним ключом не задевает другой.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер, Ядро (доменный слой), Аутентификация и права доступа

## etn.attachments.* — вложения в MCP

**Актуализация 0.8.4 (задача 09f19952).** Семейство `etn.attachments.*` снято с постоянного набора MCP — это действия исполнителя `etn.ops { action, params, confirm }`: `attachments.add`, `attachments.copy`, `attachments.search` (read-only), `attachments.update`, `attachments.delete` (confirm; отвязывает вложение, файл не удаляет). Детали — `etn.guide { topic: "attachments.add" }`. Ниже — исходные контракты (0.8.1).

**Загрузка файла (ревизия 2026-10-01, задача `75c75a2f`, коммит `4f79f263`).** MCP принимает содержимое файла наравне с REST (паритет `9e5cff3f` восстановлен): оба пути создания вложения — `etn.ops { action: "attachments.add" }` и `attachments[]` в `etn.thoughts.write` — принимают `mime_type` + `data_base64` при `kind: "file"`. Валидация: `data_base64` требует `kind='file'`, не сочетается с `url`/`file_path`/`file_size`/`position`/`description`; `mime_type` обязателен; лимит декодированного файла ~10 МиБ (`ATTACHMENT_FILE_MAX_BYTES`); в `audit_log` пишется только `data_base64_chars`, не пейлоад. Реализация — доменный диспетчер `createAttachmentFromInput` → `createAttachmentFile` (ADR `8c93f03a`: фасады без логики), та же, что у REST-операции `47215aab` «POST /attachments/file» (требование `a5456b79` «Два вида файловых вложений»); серверная копия — в каталоге вложений сети рядом с её БД. До 0.10.3 MCP умел только `url`/`file_path`, и агент был вынужден обходиться REST-ом.

**`etn.attachments.add`** — привязать URL, локальный путь файла или содержимое файла к мысли/связи: `owner_type`, `owner_id`, `kind` (`url`/`file`), `url?`/`file_path?` **или** `mime_type?`+`data_base64?` (для серверной копии, только с `kind='file'`), `title?`, `description?`.

**`etn.attachments.copy`** — скопировать вложение в одну или несколько мыслей (`target_owner_type: "thought"`, `target_owner_ids[]`); возвращает массив результатов по одному на созданную строку; цели с уже имеющимся вложением того же kind и того же url/file_path пропускаются без ошибки и без записи в массив.

**`etn.attachments.search`** (read-only) — поиск вложений сети: `q` обязателен (без него пустой массив), мини-синтаксис как у поиска мыслей (include-AND, `-слово` исключение); `exclude_owner_type?`/`exclude_owner_id?`, `kind?`, `limit?`, `offset?`.

**Ревизия 0.11.1 (ошибка `5fcb8307`, коммит `d4e46264`).** `file_path` при `kind='file'` — путь в файловой системе **СЕРВЕРА**. Нерезолвящийся на сервере путь теперь отвергается `VALIDATION_ERROR` (поле `file_path`, сам путь и подсказка в деталях), а не молча создаёт битое вложение с пустыми `mime_type`/`file_size` и недоступным файлом. Файл с машины клиента передаётся содержимым: `mime_type`+`data_base64` (серверная копия в каталоге вложений сети). Проверка — в доменном диспетчере `createAttachmentFromInput`, т.е. действует для `etn.attachments.add` и `attachments[]` в `etn.thoughts.write`. REST-маршрут `POST …/attachments` не менялся: там по-прежнему допустима «ссылка на путь в ОС клиента» (требование `a5456b79`, drag-and-drop в клиенте).

**Ожидаемая ревизия 0.12.1 (тех.проект `f9b8917c`, ADR `9f90b010`).** С приходом муль-владения параметры владельца уходят из «создания вложения» в управление владениями: `attachments.add` создаёт/переиспользует вложение (дедуп по хэшу) и добавляет владельца; `attachments.update` перестаёт менять владельца, остаётся правка метаданных (в т.ч. переименование); `attachments.copy` добавляет владельцев, а не строки; добавляется действие снятия владельца с защитами. `attachments.delete` убирается с публичного фасада — полное удаление выполняет owner-cleanup (см. дополнение ниже).

**Дополнение (аудит 0.12.1).** `attachments.usage` — по id вложения: владельцы + использования (иконки/обложки/тексты). Новое действие снятия владельца — **`attachments.removeOwner`** (аргументы `attachment_id`, `owner_type`, `owner_id`; деструктивное → confirm-политика как у прочих destructive-действий). `attachments.update` — только метаданные (`title`/`description`/`icon`). `attachments.delete` (полное удаление вложения) убрать с публичного фасада — вложение удаляется owner-cleanup’ом автоматически.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер

## etn.changes.list — дельта-фид событий для долгоживущих агентов

**Актуализация 0.8.4 (задача 09f19952).** `etn.changes.list` снят с постоянного набора MCP — это действие `changes.list` исполнителя `etn.ops` (read-only). В cookbook: `networks.list` — действие `networks.list`, `export.subgraph` — действие `export.subgraph` исполнителя `etn.ops`; `etn.thoughts.search` остаётся отдельным инструментом. Детали — `etn.guide { topic: "changes.list" }`.

Read-only. Delta-фид над буфером real-time событий `event_log` — для агента с собственным индексом/кэшем, которому дорого тащить всё через поиск.

Параметры: `network_id`; `since_seq` — эксклюзивная нижняя граница (события `seq > since_seq`, по возрастанию; `0` — «от начала удерживаемого буфера»); `limit?` 1..10 000 (дефолт 1000; потолок равен `EVENT_LOG_MAX_ROWS`). Буфер: TTL 24 ч, всегда хранятся 10 000 самых свежих.

Ответ: `cursor {min_seq, max_seq}` (null при пустом буфере), `events[]` (`type`, `seq`, `ts`, `audience`, `layer_id`, `data`), `truncated`, `limit`.

**Правила:**
- `audience: "user"` — только события, чей `actor.user_id` равен пользователю ключа (как у WebSocket-шлюза);
- события `audience: "network"` фильтруются видимостью в слое сессии вызывающего; `layer_id` каждого события информативен — из какого слоя пришло изменение;
- `truncated: true` — обязательная полная ресинхронизация (`etn.thoughts.search` по сети или `etn.export.subgraph` от HOME): либо `since_seq` уехал из окна буфера, либо предшествует последнему переключению слоя сессии (дельта через границу смешала бы два фильтра видимости). `since_seq = 0` и пустой буфер никогда не усечены;
- чистое чтение: без записи в `audit_log`, работает для read-only ключей.

Cookbook: при подключении снять снапшот (`networks.list` → `search`/`export.subgraph`) + `cursor.max_seq`; дальше опрос `since_seq = последний seq`; при `truncated` — пересохранить снапшот с нуля.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- зависит от: Real-time канал (WebSocket)
- применяется к: Сквозная слоистость MCP-инструментов

## etn.comments.* — комментарии в MCP

**Актуализация 0.8.4 (задача 09f19952).** `etn.comments.delete` снят с постоянного набора MCP — это действие `comments.delete` исполнителя `etn.ops` (confirm). Остальные перечисленные (`etn.comments.update`/`edit`/`get`) — по-прежнему отдельные MCP-инструменты. Детали — `etn.guide { topic: "comments.delete" }`.

**`etn.comments.upsert` — удалён в 0.8.2** (задача 937480ca). Создание/обновление комментариев — только батчем `etn.thoughts.write`: `comment` — постоянный (create-or-update), `chronicle[]` — добавляемые хронологические записи с `valid_from`/`valid_to`/`use_time`. Батч пишет комментарий одному владельцу; несколько владельцев у одной записи (targets[], первый — первичный, остальные — вторичные) — только REST/клиент (та же доменная функция, что в REST).

**`etn.comments.update`** — патч по `comment_id` (chronological или permanent; last-write-wins по полям; `valid_from`/`valid_to`/`use_time` применяются только к chronological), `expected_version?`.

**`etn.comments.edit`** — секционная правка ops-ами (`append`/`prepend`/`replace_section`/`delete_section`) одной транзакцией; адресация `comment_id` XOR `thought_id` (постоянный комментарий мысли).

**`etn.comments.get`** — полный текст по `comment_id` (любой комментарий) или постоянный комментарий мысли по `thought_id`.

**`etn.comments.delete`** (destructive) — удалить комментарий вместе со всеми привязками к владельцам.

Точечное привязывание/отвязывание одного дополнительного владельца к готовой записи — только REST/клиент, в MCP нет.

**Время хроно-записи (0.10.1).** `valid_from`/`valid_to` — полный UTC-инстанс ISO-8601 с миллисекундами; «голая дата» `YYYY-MM-DD` во входе = сутки UTC. `valid_to` обязателен: не задан — равен `valid_from`. `use_time` (bool) — показывать ли время в клиенте; на формат дат не влияет. См. ADR времени.

- относится к подсистемам: MCP-сервер
- зависит от: comments — постоянные и хронологические комментарии

## etn.comments.get — полный текст комментария

Read-only. Полный текст одного комментария, когда превью (`meta.permanent`, комментарии `subgraph`, `networks.structure`) показало `truncated: true` — `id` есть в самом превью.

Адресация — ровно одно из двух: `comment_id` (любой комментарий, постоянный или хронологический) или `thought_id` (постоянный комментарий этой мысли; `{thought_id, permanent: null}`, когда его нет).

Дополнительно возвращает `targets` — все привязки комментария `({owner_type, owner_id})`, включая вторичные (мультивладельческие записи).

## etn.guide — справочник редких операций MCP

Read-only витрина редких операций, вынесенных из постоянного набора инструментов (прогрессивное раскрытие, ADR «Прогрессивное раскрытие MCP вместо роста описаний инструментов»).

Без параметров — компактный реестр: имя действия → когда нужно (одна строка на действие), бюджет ≤ 10 КБ. С `topic: <имя действия>` — полная инструкция вызова: состав `params`, обязательность `confirm`, эффекты, коды ошибок. Descriptions гайда и исполнителя `etn.ops` перекрёстно ссылаются друг на друга: агент не вызывает исполнитель мимо инструкции. Схема входа — плоский объект без union (грабля: MCP-SDK публикует пустую схему для union inputSchema).

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер

## etn.layers.* — управление слоями через MCP

**Актуализация 0.8.4 (задача 09f19952).** Отдельными MCP-инструментами из этого набора остались только `etn.layers.list` и `etn.layers.select`; остальные — действия исполнителя `etn.ops { action, params, confirm }`: `layers.create`, `layers.update`, `layers.delete` (confirm), `layers.diff` (read-only), `layers.diff_doc` (read-only), `layers.merge` (confirm). Читать таблицу ниже следует как описания этих действий, а не отдельных инструментов; состав `params` — `etn.guide { topic: "layers.create" }` (аналогично для остальных действий).

Агент получает **полный паритет** с пользователем в клиенте и с REST по работе со слоями: восемь управляющих инструментов плюс сквозная слоистость всех остальных.

| Инструмент | Аннотация | Назначение |
|---|---|---|
| `etn.layers.list` | read-only | все слои сети с иерархией (`parent_id`, `depth`, `comment`, `git_branch`, `children_count` — число для подтверждения cascade при удалении) и `current: true` у слоя вызывающего ключа; `include_service?` показывает служебные резервные слои |
| `etn.layers.diff` | read-only | структурное отличие слоя от цели **постранично** (актуализация 0.10.3, задача `ddb67ddc`): 7 секций — `links.added|removed|type_changed|reorder_collapsed|reparented`, `overridden.thought_ids|link_ids`; params `sections?` (подмножество секций, неизвестная — `VALIDATION_ERROR`), `limit?` (1…1000, дефолт 200 — верхняя граница: страница дополнительно ужимается байтовым бюджетом ≈48 КБ), `cursor?` (keyset `next_cursor` предыдущей страницы, детерминированная сортировка секция+id — ADR `5f6cb775`); в каждом ответе `counts` по всем секциям, `truncated` + `reason`, `next_cursor`; вызов без параметров в MCP — первая страница (гарантия бюджета `maxModelBytes`), не полный отчёт |
| `etn.layers.diff_doc` | read-only | содержательное отличие: два детерминированных markdown-документа (`layer_doc`/`target_doc`) для построчного сравнения. **Не пагинируется и не секционируется** (0.10.3): на больших слоях ответ огромен (ориентир: слой ~1142 перекрытых строк → ~17,5 МБ) — инструмент для малых слоёв и точечного аудита; большие слои — через `layers.diff` по секциям/страницам |
| `etn.layers.create` | — | создать слой; `parent_id` по умолчанию — текущий слой ключа; `comment` настоятельно рекомендуется — по нему следующий агент поймёт назначение слоя; сессию не переключает |
| `etn.layers.update` | idempotent | переименовать/править комментарий; название основы фиксировано (422) |
| `etn.layers.delete` | destructive | удалить слой с поддеревом потомков; при `children_count > 0` обязателен `cascade` с этим числом (несовпадение — 409); физически удаляет тени и надгробия, автоочищает корзину; сессия ключа автоматически переключается на родителя |
| `etn.layers.select` | idempotent | переключить текущий слой ключа — все последующие вызовы (чтение и запись) идут в нём; служебный слой выбрать нельзя; повторный выбор того же — no-op |
| `etn.layers.merge` | destructive | слить слой в родителя: полностью или частично замкнутым подмножеством `tables`; конфликт версий или незамкнутость отклоняет всю операцию (422) — частичного применения не бывает; успех `{applied, skipped, reorder_collapsed, reserve_layer_id, purged}` + одно событие `layer.merged` |

**REST-паритет пагинации (0.10.3, задача `ddb67ddc`).** `GET /networks/:networkId/layers/:layerId/diff` принимает те же `sections`/`limit`/`cursor` (query; несколько `sections` повтором параметра); **без параметров — прежний полный отчёт** (совместимость текущего клиента до его перевода на страницы — задача `52c776f1`), с любым из параметров — страница той же формы, что MCP.

**Сверх паритета (13-layers.md §8.5, §10.2).** Агент получает путь аварийного согласования, которого нет у пользователя: `layers.conflicts` (read-only — предпросмотр строк, из-за которых слияние будет отклонено) и `layers.reset_override` (destructive, `confirm` — перепривязка `base_version` названных строк к актуальной основе). REST-маршрута и пункта меню клиента у них нет.

## etn.networks.structure — структура сети и правила записи

Read-only. Входная точка агента в базу знаний сети (self-description). Параметры: `network_id`, `include_examples?` (дефолт `false`).

**Что возвращает.** Активные мысли узлового типа сети (`node_section_type_id` — «узловые разделы», иерархия обычными parent-child связями) с обогащением:
- `permanent` — превью постоянного комментария (обрезка + `comment_id` для полного чтения через `etn.comments.get`);
- `properties` — резолвнутые значения (`thought_ref` → `{id, title}`);
- `counters` — `parents_count`, `children_count`, `attachments_count`, `deletion_blocks` (блокировки удаления — сколько ссылок через свойства-связи с `blocks_target_deletion` ведёт на раздел; задача cfc55b01, прежнее имя `usage_count`);
- `thought_types` — каталог типов, реально использованных в разделах, плюс сам узловой тип.

**`conventions` — всегда.** Правила записи сети возвращаются этим инструментом всегда (включая `has_structure: false` и `null`, если не заполнены) — MCP-агент не имеет ни `etn.networks.get` (инструмента нет), ни MCP-ресурсов (клиенты типа ZCode их агенту не подают), а `conventions` нужны перед каждым `create`/`update`. Лишнего вызова не появляется — инструмент и так первый при ориентировке. `examples` — объёмное поле, по умолчанию не входит; запрашивается явно `include_examples: true`.

Когда `node_section_type_id` не задан: `{ has_structure: false, sections: [] }` — агенту остаётся `etn.thoughts.search` / `etn.thoughts.query`.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- зависит от: networks — реестр мыслесетей и самоописание сети
- применяется к: networks.structure отдаёт худой перечень разделов, ADR: служебные типы сети адресуются ролями из словаря type_roles, Условная обрезка текстов в ответах MCP

## etn.thoughts.find_duplicates — поиск дублей перед созданием

## etn.thoughts.get — карточка мысли

Read-only. Полная карточка мысли: синонимы, тип (с AI-описанием), стили, свойства и блок `meta`.

## etn.thoughts.neighbors — соседи и обход графа

**Актуализация 0.8.4 (задача 09f19952).** Основной предмет карточки — `etn.thoughts.neighbors` — остаётся отдельным инструментом. Смежные семейства сняты: `etn.thoughts.path` — действие `thoughts.path` исполнителя `etn.ops` (read-only); `etn.links.get` упразднён вместе со всей семьёй `etn.links.*` (требование `3ea5c6af`) — чтение связи идёт через значения свойства (цель + комментарий + id ребра). Детали — `etn.guide { topic: "thoughts.path" }`.

Read-only. Соседи мысли по направлению `dir` (`parents`/`children`/`siblings`); `depth: 1` — прямые соседи, `> 1` — ограниченный BFS-обход с разрешёнными мыслями. Ответ несёт справочники `link_types`/`thought_types` (только реально использованные типы). Параметр `view` (`compact` дефолт / `full`) — проекция визуальных полей.

**`depth: 1` ограничен 50 строками, лимит/offset не настраиваются** (bug fix 0.6.3, thought f2c7c7d3): ответ несёт `total` (реальное число совпадений, без LIMIT) и `truncated` (`total > neighbors.length`). Когда `truncated: true`, весь список — через `etn.thoughts.query { in_subtree_of: <id>, max_depth: 1 }` (честный `total`/`truncated` и полноценная пагинация) или `depth > 1` этого же инструмента (BFS без постраничного лимита, но с `max_nodes_per_subgraph`). До фикса `total` эхом повторял длину уже обрезанной страницы — раздел с более чем 50 соседями выглядел полностью показанным, что приводило к ложному выводу об «осиротевших» мыслях.

Смежные инструменты навигации того же назначения:
- **`etn.thoughts.path`** — кратчайший путь между двумя мыслями по неориентированным parent/child рёбрам, ограничен `max_depth`; `path: null`, когда недостижимы; каталог `thought_types` по пути;
- **`etn.links.get`** — одна связь по `link_id` с её типом и AI-описанием типа.

**Рёбра в корзине** (0.8.2, ошибка 355319d4). Запись соседа несёт `link_marked_for_deletion` — связь, которой сосед держится за фокус, помечена на удаление. Сосед при этом НЕ скрывается (помеченную сущность показывают с признаком); у `siblings` параллельные рёбра схлопываются в одну строку, поэтому пометка ставится только когда помечены ВСЕ они.

- зависит от: links — направленные связи между мыслями
- применяется к: Каталоги типов в ответах read-инструментов, Рёбра выборок несут признаки наполнения связи, Компактная проекция ответов view compact и full, Фильтр обхода по типам связей

## etn.thoughts.query — структурная выборка

Read-only. Список мыслей по критериям **без текстового запроса** — когда искать нечего, а критерий структурный: «все ошибки в поддереве проекта», «свойство статус = согласовано», «изменённые за неделю». Все фильтры комбинируются AND.

| Параметр | Смысл |
|---|---|
| `in_subtree_of` | подчинённые мысли: направленный обход вниз по активным связям |
| `max_depth` | потолок глубины обхода (дефолт 20) |
| `type_id[]` / `type[]` | фильтр по типам (с подчинёнными); имена `type` резолвятся без учёта регистра |
| `active` | `true`/`false`/`any` (дефолт `true`) |
| `trashed` | пометка на удаление (дефолт `false`; независим от `active`) |
| `keywords` | подстрочный поиск по названию и синонимам; индекс `fts_thought_names` — сужатель, LIKE — остаточный фильтр |
| `properties[]` | `{property_id \| property, operator, value}` — условие обязано адресовать свойство; лишние поля отвергаются |
| `created_*` / `updated_*` | ISO-8601 диапазоны |
| `link_filter` | `{type_ids?, include_structural?}` — сужение рёбер спуска `in_subtree_of` |
| `sort` / `order` | `title`/`created_at`/`updated_at`, дефолт `title` `asc` |
| `limit`/`offset` | дефолт 50, максимум 200 |
| `count` | `true` — посчитать точное `total`; без флага COUNT не выполняется (`total` = `null`) |
| `cursor` | keyset-курсор продолжения страницы из `next_cursor` предыдущего ответа |

Операторы `properties`: `eq`, `ne`, `contains`, `gt`, `gte`, `lt`, `lte`, `any_of`, `all_of`, `none_of`. Тип `value` выбирает колонку: число → `value_number` (все, кроме `contains`); булево → `value_bool` (`eq`/`ne`); строка → `contains` по `value_text`, сравнения `gt/gte/lt/lte` по `value_date` (ISO-8601, лексикографически), `eq/ne` — по любой текстовой колонке.

Ответ: `{total: number|null, hits: [{id, title, type_id, active, depth}], has_more, next_cursor, truncated, reason, thought_types}`. `depth` — расстояние от `in_subtree_of` (0 — сам корень, `null` — корень не задан). Обход ограничен `max_nodes_per_subgraph`: при превышении `truncated: true, reason: "max_nodes"`.

**Пагинация и счётчик (0.9.1).** Порядок детерминирован (сортировка + уникальный `id`). `count: true` — точное `total`; без флага `total` = `null`, хвост сообщает `has_more`, а продолжение читается по `next_cursor` (keyset вместо `offset`; курсор выдаётся только при `has_more` и обязан соответствовать `sort`/`order`, иначе `VALIDATION_ERROR`). Поиск `keywords` идёт через индекс `fts_thought_names` — мини-язык §6.10 не меняется. Регулируется требованиями «COUNT общего числа выполняется только по явному запросу» и «Выборки пагинируются keyset-курсором вместо OFFSET», ADR «Точечные оптимизации выборок».

### Контракт условия отбора по свойству (0.12.1: ошибки 090d0242/4f17cb73/f4580fff)

Свойство адресуется `property_id` (registry id) или `property` (имя из реестра; резолвится без учёта регистра). Поля `key` контрактом НЕ предусмотрено: **неизвестное поле условия отвергается явной `VALIDATION_ERROR`** (а не вырезается молча). Условие без адреса либо одновременно `property_id` и `property` — тоже `VALIDATION_ERROR`.

Несуществующее имя или `property_id` (свойства нет в реестре/не видно в слое) → `NOT_FOUND` — та же конвенция, что у резолва имён типов (несуществующее имя или `id` реестровой сущности → `NOT_FOUND`, неоднозначность → `VALIDATION_ERROR` с `details.candidates`). Прежнее поведение (условие молча выпадало из отбора, расширяя набор до всей сети) устранено.

Свойство-связь (`value_type: "link"`) переводится в запрос по рёбрам: `eq`/`ne` со строкой — связь с конкретной целью, с boolean — наличие/отсутствие ребра такого типа; `any_of`/`all_of`/`none_of` — наборы целей. Отбор никогда не расширяется до всей сети из-за неразрешённого условия (сохранённый рецепт со ссылкой на удалённое свойство матчит пустой набор).

### Кросс-сетевой режим (0.8.3, проектируется)

Параметр `network_ids` — веерная выборка по сетям со слиянием: у каждого результата `network_id`, в ответе справочник сетей. Критерии (`type`, `keywords`, `properties`, даты) применяются в каждой сети по её реестру: имени свойства или типа там нет — сеть попаданий не даёт. Свойства вида «кросс-сетевая ссылка» фильтруются операторами `eq`/`ne`/`any_of`/`all_of`/`none_of` по адресу `n:<net>#<id>`. Права и слои — как у поиска; поведение при одной сети не меняется. См. требование «Веерный режим поиска и выборки: network_ids».

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- зависит от: thoughts — таблица мыслей
- применяется к: Отбор по кросс-сетевому значению: операторы по адресу, Каталоги типов в ответах read-инструментов, Справочник свойств и значения в ответах выборок, Фильтр обхода по типам связей, Операторы наборов значений: any_of, all_of, none_of, Веерный режим поиска и выборки: network_ids, Типы и свойства адресуются именами во всех фильтрах MCP, Выборка мыслей по условию на свойство-связь

## etn.thoughts.search — полнотекстовый поиск

Read-only. Полнотекстовый поиск (FTS5) по названиям мыслей, текстам комментариев, текстам связей и хронологии.

Параметры: `network_id`, `query`, `scope?` (`names`/`texts`/`links`/`chronology`/`all`), `in_subtree_of?`, `type_id?` (включая подчинённые типы), `limit?` 1–200 (дефолт 50), `offset?` ≥ 0.

Дефолты `limit = 50`, `offset = 0`. Без `scope: 'all'` лишние группы не возвращаются — пагинируется только заказанное. Поиск без стемминга: пробуй словоформы и `*`.

## etn.thoughts.subgraph — подграф вокруг мыслей

Read-only. Ключевой инструмент RAG-сценариев: готовый контекст для генерации. Параметры: `network_id`, `seed_ids[]` (до 50), `radius`, `max_nodes` (потолок — настройка `mcp.max_nodes_per_subgraph`), `include_comments?`, `view?`, `max_chars?`.

Ответ: `nodes` (полные мысли), `edges` (минимальная форма `id`/`source_id`/`target_id`/`type_id`), опциональные комментарии и справочники `thought_types`/`link_types` (реально использованные типы — агент читает AI-описания типов один раз, не перезапрашивая).

**Комментарии — превью, не полные тексты** (иначе большой подграф разрывает контекст): `permanent` — обрезка до 2000 символов; `chronological` — последние 10 записей по `valid_from` DESC, каждая с обрезкой и `chars_returned`/`chars_total`/`truncated`; уровень списка несёт `total`/`returned`/`truncated`. Каждое превью несёт `id` комментария — полный текст через `etn.comments.get`.

**Усечение** сообщается честно: `truncated: true` + `reason`:
- `max_nodes` — сработал жёсткий лимит обхода (не все достижимые узлы рассматривались);
- `max_chars_preview` — влезли после укорачивания превью (топология цела);
- `max_chars_nodes` — отброшены дальние узлы (семены не удаляются никогда);
- `null` — усечения нет.

При заданном `max_chars` ответ несёт блок `budget` (`max_chars`/`original_chars`/`final_chars`/`steps`) — для отладки и адаптивного подбора бюджета.

**Рёбра в корзине** (0.8.2, ошибка 355319d4). Каждое ребро `edges` несёт `link_marked_for_deletion`: помеченное ребро остаётся в подграфе (его не прячем), но агент и клиент видят, что оно в корзине. Счётчики `meta.link_stats` в `etn.thoughts.get`, наоборот, живые связи: рёбра корзины в них не попадают.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- зависит от: thoughts — таблица мыслей
- применяется к: Компактная проекция ответов view compact и full, Каталоги типов в ответах read-инструментов, Фильтр обхода по типам связей, Бюджет ответа subgraph: max_chars, Справочник свойств и значения в ответах выборок, Условная обрезка текстов в ответах MCP, Рёбра выборок несут признаки наполнения связи

## etn.types.list — каталоги типов с эффективными свойствами

Read-only. Оба каталога типов **целиком** (а не только использованные в чужом ответе): все типы мыслей и связей сети, включая корневой, с иерархией (`parent_id`/`is_root`) и **эффективными** свойствами — собственные плюс унаследованные от предков по цепочке. Эффективный набор свойств типа включает настоящие привязки обеих сторон — источника и назначения (бывшие зеркальные привязки больше не вычисляются на лету). У каждого свойства: `key`, `value_type`, `required`, `config` (`options`/`allowed_type_ids`/`default_value`), `inherited`, `defined_on(_name)`, эффективный `default_value`, эффективное `description` и `description_overridden`.

Параметры:
- `scope?` (`thoughts`/`links`/`all`, дефолт `all`) — раздельный запрос каталога: на зрелой сети полный ответ может превысить клиентский лимит, и хвост `link_types` не доедет;
- `in_subtree_of?` + `max_depth?` — ограничить типами, реально используемыми в поддереве мысли (неактивные пропускаются); у записи появляется `usage_count`. Ответ несёт блок `scope` с эхом и счётчиками; несуществующий `thought_id` → `NOT_FOUND`, пустое поддерево → пустые каталоги без ошибки.

Типичный сценарий: после `etn.networks.structure` → `etn.types.list { in_subtree_of: <раздел> }` — видно, какие типы живут в разделе и сколько раз.

**Тип по имени вместо `type_id`** (task O4): батч `etn.thoughts.write` принимает параметр `type` (строка) — в `thought` и в каждом `links[]` — ровно одно из `type_id`/`type`, иначе `VALIDATION_ERROR`. Резолв по `name_key` (case-insensitive); для связей — по `name_forward` **или** `name_reverse`. Имя не найдено → `NOT_FOUND`; несколько типов под одним именем → `VALIDATION_ERROR` с `details.candidates` (для связей реально возможно: уникальна только пара имён).

**Свойства-связи (0.8.1).** В эффективных свойствах типа свойство-связь (`value_type: "link"`) появляется с `key`, вычисленным из типа связи по стороне привязки (`name_forward` у источника, `name_reverse` у назначения), а не из справочника; имя в реестре не хранится. В `config` — `link_type_id`, `allowed_target_type_ids` (раскрывается до поддеревьев), `show_on_map`, `blocks_target_deletion`; поля `direction` в `config` нет — сторона задаётся привязкой (`side`).

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- зависит от: thought_types — типы мыслей и их иерархия
- применяется к: Имя свойства-связи берётся из типа связи по направлению, Вид значения «тип связи» в реестре свойств, Типы и свойства адресуются именами во всех фильтрах MCP, Зеркало: ограничение типа цели порождает обратное свойство

## etn.views.run — исполнение отбора типа агентом

Даёт агенту готовый результат отбора одним вызовом — без поиска id и конструирования запроса.

```
etn.views.run { network_id, thought_id, view, limit?, offset?, sort?, order? }
→ { data: [ … ], meta: { total, view, unresolved? } }
```

`view` — имя отбора из эффективного набора мысли (регистронезависимо) или его id.

**Где агент узнаёт про отборы.** Карточка мысли (`etn.thoughts.get`) несёт `meta.views` — имя, описание и тип-владелец каждого доступного отбора, без `definition`: агенту нужен смысл, а не внутренности. Каталог типов (`etn.types.list`) отдаёт отборы вместе с типом.

**Зачем это агенту.** Сегодня, чтобы получить работы версии, агент обязан знать про свойство «версия», найти id версии и собрать запрос. С отбором он читает карточку версии, видит «Работы версии — задачи и ошибки, запланированные на эту версию», и дёргает его. Знание о том, как устроена сеть, переезжает из промпта агента в саму сеть.

Операция read-only: бюджет записи не тратит, `audit_log` не пишет.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- зависит от: thought_type_views — именованные отборы типов мыслей

## MCP отдаёт body_md с развёрнутыми трансклюзиями и маркерами границ

**Утверждение.** Все MCP-инструменты чтения, отдающие текст комментария, возвращают развёрнутый текст: трансклюзии раскрыты до 5 уровней, вставленные фрагменты обёрнуты маркерами границ источника по формату ADR «Формат маркеров границ источника при MCP-развёртке трансклюзий». Агент видит весь текст без дополнительных запросов. В базе body_md хранится со ссылками; развёртка выполняется при отдаче.

**Область.** Сервер (MCP) и `@etn/markdown` (экспортируемая функция развёртки).

**Границы.** Обратная сборка ссылок из развёртки не входит. В критерии приёмки входит актуализация затронутых инструкций для агентов и conventions сети ETN (R10).

**Контракт поставки текстов (аудит проработки, итерации 1–2).** Развёртку выполняет экспортируемая функция `@etn/markdown` (условное имя `expandTransclusions(md, resolveTransclusion, { maxDepth: 5 })`) без доступа к БД: тексты она получает через инжектируемый резолвер-зависимость `resolveTransclusion(sourceId, sectionTitle?) → { found, body_md }`, передаваемый при вызове; рекурсия, глубина 5 и защита от циклов — внутри этой функции, а не на стороне вызывающего. Сервер (MCP-выдача и предрендер) и клиент вызывают функцию со своим резолвером: сервер — над доменом БД, клиент — над REST/кешем (ADR `8c41387c`).

**Scope описаний типов (аудит проработки, итерация 1).** Развёртка применяется не только к body_md комментариев, но и к description/comment_template типов в MCP-выдаче (`etn.types.list`) и в предрендере, где эти тексты отдаются.

**Дополнительные материалы**
- применяется к: server/src/mcp — MCP-сервер (реализация), @etn/markdown

## MCP предупреждает при записи, теряющей трансклюзии

**Утверждение.** Запись комментария или иного markdown-поля, при которой исчезают существовавшие ранее трансклюзии, возвращает предупреждение в ответе, но не запрещается. Проверка выполняется на серверном уровне записи комментария: сервер извлекает трансклюзии из старого и нового body_md парсером `@etn/markdown` (единый модуль, без собственного разбора) и сравнивает множество id трансклюзий; исчезновение любого ранее существовавшего id — в том числе потеря одной из нескольких или замена `![[#A]]` → `![[#B]]` — даёт warning. Так покрываются все пути записи — и MCP, и REST/клиент.

**Область.** Сервер (уровень записи комментария) — MCP-инструменты и REST/клиент. MCP-инструменты показывают warning в ответе.

**Границы.** Жёсткий запрет не вводится — решение пользователя/агента остаётся.

**Дополнительные материалы**
- применяется к: server/src/mcp — MCP-сервер (реализация)

## MCP-ресурсы etn:// — чтение данных по URI

Данные, которые агент читает по URI (static + templated). Отдаются как JSON (mime `application/json`); комментарии — как Markdown (`text/markdown`) для прямой передачи агенту. MCP-агенты ZCode-типа ресурсы не подаёт — поэтому всё важное продублировано инструментами `etn.*`.

| URI | Что возвращает |
|---|---|
| `etn://networks` | Список сетей пользователя (`description`/`when_to_use`/`has_structure`) |
| `etn://networks/{network_id}` | Метаданные сети: все 4 markdown-поля + `node_section_type_id` |
| `etn://networks/{network_id}/thoughts/{thought_id}` | Полная мысль: свойства, синонимы, тип, стили + блок `meta` |
| `…/thoughts/{thought_id}/neighbors` | Соседи + каталоги `link_types`/`thought_types` |
| `…/thoughts/{thought_id}/usage` | «Использование» мысли через thought_ref-свойства + `holding_layers` |
| `…/thoughts/{thought_id}/backlinks` | Явные ID-ссылки `[[#<id>]]` в комментариях |
| `…/thoughts/{thought_id}/comments` | Комментарии мысли |
| `…/thoughts/{thought_id}/attachments` | Вложения мысли |
| `…/links/{link_id}` | Связь с метаданными |
| `…/thought-types`, `…/link-types`, `…/thought-types/{id}` | Определения типов (у конкретного типа — включая `description` для контекста агента) |
| `etn://networks/{network_id}/trash` | Корзина сети с предрасчитанной блокировкой удаления |

**Блок `meta`** в чтении мысли — «сигналы полноты»: счётчики активных связей (`parents_count`/`children_count`), вложений, хронологии и блокировок удаления (`deletion_blocks` — сколько ссылок через свойства-связи с `blocks_target_deletion` блокируют удаление мысли; задача cfc55b01, прежнее имя `usage_count`) — агент по ним решает, какие ресурсы запрашивать дальше. Поле `permanent` — превью постоянного комментария с обрезкой до 2000 символов и метаданными `chars_returned`/`chars_total`/`truncated`; полный текст — инструментом `etn.comments.get` (превью всегда несёт `id` комментария).

**Свойства в чтении резолвнуты**: `thought_ref`-значение — `{id, title}`, а не голый UUID; `title: null` — висячая ссылка на удалённую мысль.

**Deep link** `etn://open?net={network_id}&thought={thought_id}` — не MCP-ресурс, а human-friendly URL-схема: агент строит её хелпером `buildDeepLinkUrl` из `@etn/shared` и возвращает пользователю; открывается в десктоп-клиенте через кастомный протокол `etn://`.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- зависит от: networks — реестр мыслесетей и самоописание сети

## MCP-сервер

Подсистема, экспонирующая ресурсы и инструменты по протоколу MCP для внешних AI-агентов.

Реализована **в том же серверном процессе**, использует **тот же доменный слой**, что и REST: агент читает и изменяет мыслесеть наравне с человеком — те же проверки прав, те же транзакции, те же события real-time. Отдельной бизнес-логики «для агентов» нет и быть не должно, иначе поведение системы разойдётся между двумя входами. Все инструменты именуются `etn.<сущность>.<действие>`.

Агент авторизуется API-ключом и не имеет доступа к подсистемам вне MCP-контура. Реализуется на официальном `@modelcontextprotocol/sdk`. Транспорт и авторизация — отдельная сущность; контроль операций (лимиты, read-only ключи, audit) — отдельная сущность.

**Дополнительные материалы**
- применяется к: ADR: консолидация MCP по сценарию записи, а не универсальные CRUD-мегатулы, ADR: прогрессивное раскрытие MCP вместо роста описаний инструментов, Паритет MCP-контура с REST по данным сети, Аннотации MCP-инструментов, Версионирование и обратная совместимость MCP, Сквозная слоистость MCP-инструментов, Расширение MCP-интерфейса — единая методика

## networks — реестр мыслесетей и самоописание сети

Реестр мыслесетей в системной БД. Сами данные сети лежат в отдельной БД, здесь — только запись о её существовании и самоописание.

| Столбец | Тип | Описание |
|---|---|---|
| `id` | TEXT PK | UUID; он же — имя каталога сети на диске |
| `display_name` | TEXT NOT NULL | Имя, меняется свободно |
| `owner_id` | TEXT NOT NULL FK → users.id ON DELETE RESTRICT | Владелец |
| `description` | TEXT | Назначение сети в 1–2 абзацах |
| `when_to_use` | TEXT | Когда агенту обращаться к сети: use cases и какие поля читать |
| `conventions` | TEXT | Правила записи: формат хронологий, пометка актуальности, нейминг, ссылки на типы и шаблоны |
| `examples` | TEXT | Примеры хороших и плохих записей |
| `node_section_type_id` | TEXT | Тип мысли, активные мысли которого образуют структуру сети. Без SQL-FK (ссылка в другую БД); тип, указанный в настройках сети, **нельзя удалить** — `DELETE /networks/{id}/thought-types/{tid}` отклоняется с `VALIDATION_ERROR`, пока ссылка не снята |
| `created_at` / `updated_at` | TEXT NOT NULL | |

**Неизменность id.** `id` равен имени каталога на диске и никогда не меняется; переименование сети затрагивает только `display_name`.

**Самоописание сети.** Четыре markdown-поля (`description`, `when_to_use`, `conventions`, `examples`) — это то, как сеть объясняет себя AI-агенту. Сервер хранит только исходник markdown; клиент рендерит preview на лету общим рендерером. Конвенция заполнения `when_to_use`: для каждого use case указываются релевантные поля сети (например, «Кодирование → structure, conventions») — агент не читает все поля подряд, а берёт только нужные текущей задаче.

**Компактность списка.** В списке сетей `conventions` и `examples` не отдаются — только `description` и `when_to_use`, иначе ответ раздувается при большом числе сетей.

**Дополнительные материалы**
- относится к подсистемам: Хранилище (SQLite), MCP-сервер
- применяется к: ADR: служебные типы сети адресуются ролями из словаря type_roles

## warnings — сигнал неполной карточки мысли

Когда батч `etn.thoughts.write` (или `etn.ontology.write`) создаёт/дополняет мысль, а карточка получается неполной (часть `required`-свойств типа без значений), ответ несёт **неломающий** блок `warnings: ThoughtCardWarning[]`:

```jsonc
{ "code": "REQUIRED_PROPERTY_MISSING", "key": "status", "property_id": "<uuid>", "defined_on": "<type-uuid>", "value_type": "text", "inherited": false }
```

Правила:
- проверка идёт по **эффективному** списку свойств типа (свои + унаследованные по цепочке) против живой таблицы `property_values`; дефолты не маскируют warning — они применяются к будущим значениям, а записи на момент проверки ещё нет;
- у `etn.thoughts.write` поле `warnings` присутствует **всегда** у каждого элемента батча (пустой массив, когда карточка полная) — форма стабильна для парсинга;
- мысль без типа → `warnings` пуст; корневой тип не объявляет required-свойств.

Агент узнаёт о неполной карточке из ответа и дозаполняет её тем же батчем (поле `properties`). REST-контракт не меняется — блок опционален на уровне MCP-фасада.

0.8.2 (задача 937480ca): `etn.thoughts.create`/`update`/`upsert_bundle` удалены — упоминания заменены на батч.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- применяется к: etn.thoughts.update — изменение мысли, etn.thoughts.create — создание мысли, etn.thoughts.upsert_bundle — составная запись единицы знания

## Агент собирает дайджест по теме

Действующее лицо — внешний AI-агент, подключённый по MCP. Задача: собрать сводку по теме из мыслесети и вернуть её пользователю.

1. `etn.thoughts.search { query: "<тема>", scope: "all" }` — получить кандидатов с оценками.
2. Для топ-5 результатов — `etn.thoughts.subgraph { seed_ids: [...], radius: 2, include_comments: true }` — готовый контекст: мысли, связи, превью комментариев.
3. Сформировать контекст и сгенерировать Markdown-дайджест в своей LLM.
4. Опционально — `etn.thoughts.write` с `chronicle[]`: хронологический комментарий у корневой мысли с дайджестом и `valid_from = сегодня`.
5. Участники сети тут же видят новый комментарий через WebSocket (real-time).

Ветвления: превью обрезаны — полные тексты через `etn.comments.get`; подграф усечён (`truncated/reason`) — сузить `radius` или повторить от других seed'ов.

- зависит от: etn.comments.* — комментарии в MCP, etn.thoughts.search — полнотекстовый поиск, etn.thoughts.subgraph — подграф вокруг мыслей

Канонический реестр — `MCP_TOOL_ANNOTATIONS` в `@etn/shared` (тип `McpToolAnnotations`).

Каждая регистрация инструмента (`server/src/mcp/tools.ts`) несёт блок `annotations` спецификации MCP — хинты, помогающие клиенту решать вопрос разрешений без ручной настройки:

| Хинт | Смысл | Кому ставится |
|---|---|---|
| `readOnlyHint: true` | нет DB-записей, real-time событий и `audit_log`-строк — клиент может выдавать доступ без подтверждения | всем read-инструментам + `find_duplicates`, `attachments.search`, `deletion_check`, `trash.list` |
| `destructiveHint: true` | удаляет сущности без отката — клиент обязан запросить подтверждение | `thoughts.delete`, `comments.delete`, `attachments.delete`, `trash.purge`, `layers.delete`, `layers.merge`, `locks.release`, `locks.clear`, `activity.rollup`, `activity.truncate`, `networks.delete`, `import.subgraph` |
| `idempotentHint: true` | повторный вызов с теми же аргументами не даёт дополнительного эффекта — безопасный ретрай | `thoughts.write`, `ontology.write`, `thoughts.trash`, `properties.add`/`remove`, `links.restore`, `layers.update/select`, `locks.acquire`, `attachments.update`, `networks.write` |

Остальные мутирующие (`comments.update`/`edit`/`delete`, `attachments.add`/`copy` и прочие без хинта) аннотаций не несут: клиент по умолчанию показывает обычный промпт подтверждения для любого записывающего вызова.

Хинты — **подсказки** по спеке MCP, а не гарантии: сервер всегда проверяет права и rate-limit перед записью.

Канонический реестр — `MCP_TOOL_ANNOTATIONS` в `@etn/shared` (тип `McpToolAnnotations`); фронтенд регистрации использует его при создании объекта tool, агентский клиент показывает блок в диалоге разрешений.

**Актуализация 0.8.3**. Descriptions не содержат отладочных меток разработки — номеров задач/ошибок и версионных пометок; история изменений живёт в CHANGELOG. Guard-тест на маски меток (8-символьный hex-идентификатор, пометки «(0.N.N, …)») защищает от повторного занесения.

## Блокировка удаления цели — флаг определения свойства-связи

**Область.** Требование — про защиту от удаления и очистку, НЕ про просмотр «Использования».

Проверку «использование мысли в свойствах других мыслей» (`deletion_check`, проверки перед физическим удалением) и очистку `usage/clear` обеспечивают только те свойства-связи, у которых в определении стоит `blocks_target_deletion = true`. Свойства без флага удаление цели не блокируют; `usage/clear` помечает в корзину рёбра только по таким свойствам.

Свойство «Использование» (`etn.thoughts.usage`, `GET /thoughts/{id}/usage`) — напротив, показывает ВСЕ формальные link-рёбра реестра, независимо от флага: это просмотр «кто ссылается на мысль», а не ветвь блокировки.

У мигрированных свойств флаг выставляется так, чтобы блокировка сохранилась там, где работала `thought_ref` (а она блокировала удаление цели всегда).

Изменено по решению пользователя 2026-09-26 (ошибка c0a2a2e6): «Использование» отделено от блокировки удаления.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, MCP-сервер
- применяется к: etn.thoughts.usage — формальные связи мысли, etn.thoughts.delete — физическое удаление с блокировкой, POST /thoughts/{id}/usage/clear — очистить использование мысли в свойствах, deletion-check — проверка возможности удаления мысли или связи

## Бюджет ответа subgraph: max_chars

Параметр `max_chars` (целое ≥ 1) задаёт **мягкий** потолок размера JSON-сериализации ответа `etn.thoughts.subgraph`: сервер ужимает полезную нагрузку под бюджет и честно сообщает, что отрезал. Без параметра — только жёсткий `max_nodes`.

Алгоритм (`shrinkSubgraphToBudget`, чистая функция без БД — удобна для unit-тестов):
1. Измерить весь payload (`nodes`, `edges`, комментарии, справочники). Влезает — вернуть как есть (`truncated: false`).
2. **Сжатие превью**: тела комментариев (постоянный и каждая хронологическая запись) обрезаются до 500 символов (`SUBGRAPH_BUDGET_PREVIEW_CHARS`); агент видит начало мысли и `comment_id` для полного чтения. Влезло — `reason: 'max_chars_preview'`, топология цела.
3. **Отбрасывание узлов**: BFS-расстояние от seed'ов; узлы сортируются по убыванию расстояния (дальние уходят первыми); удаление узла уносит инцидентные рёбра и его comment-слот. Seed'ы не удаляются никогда. Итог — `reason: 'max_chars_nodes'`; если не влезает даже один seed — максимально ужатый ответ без ошибки.

Если обход уже усечён по `max_nodes`, бюджетирование **не запускается**: `reason: 'max_nodes'` важнее (не все достижимые узлы рассматривались).

При заданном `max_chars` ответ несёт блок `budget: {max_chars, original_chars, final_chars, steps}` — для отладки и адаптивного подбора. Cookbook: «всё, что влезет» — не передавать; «жёсткий бюджет 8 KB» — `max_chars + include_comments`; «максимум топологии» — `view: 'compact'` вместе с `max_chars`; «не знаю бюджет» — измерить ответ и перезапросить с ×0.8.

**Актуализация 0.8.3**. Превью permanent-комментария в subgraph — 600 символов (было 2000); полный текст — `etn.comments.get`. Числовые бюджеты объёма типовых ответов (перечень инструкций, structure, карточка resolve) проверяются guard-тестом в CI.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- применяется к: etn.thoughts.subgraph — подграф вокруг мыслей

## Вид значения «тип связи» в реестре свойств

В реестре свойств появляется вид значения **«тип связи»** (`link`). Определение такого свойства в `config` несёт:

- `link_type_id` — тип связи, обязательный; действует инвариант «одно свойство-связь на тип связи», а не уникальность пары «тип связи + направление» (Свойство-связь одно на тип связи; сторона задана привязкой);
- `allowed_target_type_ids` — опциональное ограничение типов противоположной стороны; раскрывается до поддеревьев типов;
- `show_on_map` — рисовать ли связь на карте по умолчанию (по умолчанию `false`);
- `blocks_target_deletion` — блокирует ли ссылка физическое удаление цели (по умолчанию `false`).

Флаги — **настоящие JSON-булевы**, не `1`/`0`. Потребители сравнивают их строго: `config.show_on_map === true` в shared `computeDefaultCanvasLinkFilter`, `config.blocks_target_deletion === true` в доменном `listBlockingLinkProperties` и клиентском редакторе. На числе `1` строгая проверка не срабатывает — флаг молча выключается.

Поля `direction` в определении свойства нет: сторона участия (источник или назначение) задаётся привязкой — `side` в `type_properties` (Свойство-связь одно на тип связи; сторона задана привязкой).

Вид значения `thought_ref` из допустимых исключается (ADR «вид значения thought_ref упраздняется»). Смена `value_type` внутри скалярной категории выполняется доменной конверсией значений, как раньше; переход между скалярной категорией и «типом связи» запрещён в обе стороны (Категория вида значения неизменна: скаляры и «связь» не конвертируются).

### Использование `show_on_map` (0.8.1, доработка)

Клиент читает `show_on_map` всех свойств-связей сети и строит из них дефолтный набор видимых на карте типов связей — см. требование «Дефолт и хранение фильтра типов связей на карте». До 0.8.1 (доработка, ошибка show_on_map не влияет на отрисовку карты мыслей) флаг нигде не потреблялся.

### Значение флагов при миграции из 0.7.x

Миграции 0.8.1 выставляют флаги так, чтобы поведение не ухудшалось относительно 0.7.x:

- **авто-свойство «голого» типа связи → `show_on_map = true`** (миграция 042, сценарий Миграция 0.8.1: единый реестр свойств и связей): рёбра этих типов рисовались на карте до обновления всегда, `false` молча убрал бы их с карты;
- **свойство, конвертированное из `thought_ref` → `show_on_map = false`, `blocks_target_deletion = true`** (миграция 040, сценарий Сценарий: перевод thought_ref в свойства-связи): массовые ссылки не рисуются (ADR «вид значения thought_ref упраздняется»), но, как и прежде, блокируют удаление цели.

Дефолт `false` из списка выше — для новых свойств, заводимых пользователем в редакторе; миграции отступают от него осознанно, сохраняя прежнее поведение.

## Выборка мыслей по условию на свойство-связь

`etn.thoughts.query { properties: [...] }` принимает условия по свойствам-связям тем же синтаксисом, что и по скалярам. Условие транслируется в запрос по рёбрам (значения в `property_values` не хранятся), в обе стороны:

- «связь с конкретной целью» — значение = id мысли;
- «связь такого типа есть / отсутствует» — проверка наличия живого ребра по определению свойства.

Адресация свойства — по имени или id, как у скаляров. Это закрывает запрос «все мысли, у которых есть такая связь с этим», который сегодня не выражается никак.

## Журналирование критичных операций сервера

Сервер ведёт журнал административных и критичных операций в системной БД: кто, что, когда, в какой мыслесети и какого типа была операция.

Зачем: администрирование и разбор конфликтов — понять, кто и когда изменил состояние системы.

Граница: это **не** журнал всех изменений данных и не история мыслей. Он фиксирует операции аутентификации, управления пользователями, сетями, членством и крупные операции над данными. Чтения в журнал не попадают.

MCP-контур: каждый изменяющий tool-вызов агента пишется в `audit_log` с `category = 'data'`, `action` — по типу операции, в `details` — параметры вызова; актор — `actor_user_id` пользователя ключа. Батч `etn.thoughts.write` — одна запись на весь вызов. Агентские чтения в журнал не пишутся — их след виден в `thought_read_metrics`.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа, Ядро (доменный слой)
- применяется к: GET /admin/audit — журнал аудита сервера

## Заполнение свойства-связи создаёт ребро без указания направления

Заполнение свойства-связи (прямого или обратного) создаёт типизированное ребро; направление нигде в вызове не указывается — оно берётся из определения свойства. Запись в обратное свойство разрешена и создаёт то же ребро, что и запись в прямое: пара заполняется симметрично.

## Карточка отдаёт связи счётчиками; запрос значений возвращает идентификатор ребра

Агенту в карточке мысли связи отдаются **счётчиками** по каждому свойству-связи и направлению (готовый образец — `meta.link_stats`), а не списками целей: скаляры — значениями, связи — счётчиками.

Запрос значений свойства-связи (REST и MCP) возвращает по каждому ребру: **идентификатор ребра**, цель (id, title, тип), постоянный комментарий ребра. Без идентификатора ребра агент не смог бы обратиться к связи: карточка отдаёт счётчик, а адреса нет нигде.

В интерфейсе — первые десять значений в карточке и диалог с полным списком, где можно добавить, изменить и удалить.

**Актуализация 0.8.3**. Счётчики связей в карточке — единственный формат `meta.link_stats`, каждая запись дополнена именами типов связей; свойства структурных «Родители»/«Потомки» из карточки не возвращаются (meta-счётчиков достаточно); в `etn.thoughts.resolve` текст постоянного комментария — один экземпляр (`comment_preview`), дубль `meta.permanent` не отдаётся.

## Каталоги типов в ответах read-инструментов

Read-инструменты, возвращающие списки мыслей/связей, несут `type_id`/`link_type_id` как **ключи** сопроводительных справочников — reference-таблиц — только по реально использованным в ответе типам (не весь каталог сети; целиком его отдаёт `etn.types.list`). Цель — агент не делает дополнительных запросов и не получает повторяющийся текст в каждой записи.

- `thought_types`: `{[type_id]: {id, name, parent_id, is_root, description, icon}}` — в `subgraph`, `neighbors`, `query`, `path`, `usage`;
- `link_types`: `{[link_type_id]: {id, name_forward, name_reverse, parent_id, is_root, description, color, style}}` — в `subgraph` и `neighbors`.

`parent_id`/`is_root` описывают иерархию типов: `is_root: true` — корневой «основной тип» (не назначается напрямую; его настройки применяются к элементам без типа), остальные наследуют от `parent_id`. **Отбор по `type_id` соответствует типу и всем его подчинённым** (OR).

`description` — «комментарий для AI» из определения типа; для связи даны оба имени — агент выбирает по направлению ребра (source → target = `name_forward`). Неизвестные/удалённые типы пропускаются (нет SQL FK). Формат у инструмента и парного ресурса одинаков.

**Актуализация 0.8.3**. В списочных ответах справочники thought_types/link_types несут только id+name+icon; полные описания типов — в `etn.types.list`. В карточке (get/resolve) вложенный тип — name+description, без визуальных полей.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- применяется к: etn.metrics.reads — метрики чтений мыслей агентами, etn.thoughts.neighbors — соседи и обход графа, etn.thoughts.query — структурная выборка, etn.thoughts.subgraph — подграф вокруг мыслей, etn.thoughts.usage — формальные связи мысли

## Компактная проекция ответов view compact и full

Параметр `view` управляет проекцией read-ответов на уровне полей — убирает визуальные и служебные поля, которые агент не использует: `fg_color`/`bg_color`, `font_*`, `icon_kind`, `icon_attachment_id`, `is_protected`/`is_root`, а у связей и типов связей — `color`/`style`/`width`. На подграфе с сотнями узлов это заметная доля токенов без пользы для рассуждения.

- **`compact` — дефолт для MCP**: агент при первом подключении сразу видит компактные ответы; `icon` остаётся (семантический);
- **`full`** — легаси-вызовы и инструменты визуализации: ответ ровно в той же форме, что до введения проекции.

**Конверт не меняется**: набор ключей верхнего уровня и блоки `meta`/`properties`/`comments` одинаковы в обеих проекциях — различается только набор полей на самой мысли. Парсер, читающий только `id`/`title`/`meta.permanent`, работает идентично.

Параметр принимают `etn.thoughts.get`, `neighbors`, `subgraph`, `usage` (и `backlinks`). Прочие read-инструменты `view` не имеют: их ответы уже компактны либо специализированы.

`full` остаётся доступным неопределённо долго; отказ от него — только через отдельный период сосуществования. Типы в `@etn/shared`: `McpViewMode`, проекции `CompactThought`/`CompactThoughtRef`/`CompactLink`/`CompactLinkTypeRef`; помощники — `server/src/mcp/catalogs.ts`.

**Актуализация 0.8.3** (тех.проект «Оптимизация MCP-интерфейса ETN»). Все списочные ответы (search, views.run, resolve, neighbors, subgraph, instructions, networks.structure, types.list) формируются единым сериализатором compact-проекции. В compact не проходят: визуальные поля (icon_kind, icon_attachment_id, fg_color, bg_color, font_*), сервисные поля (version, created_by/updated_by, marked_for_deletion_at/by, manual_position). Пустые массивы/объекты (views, synonyms, link_types, chronological) не сериализуются. Точечный thoughts.get сохраняет полную проекцию. Guard-тест формы ответа краснеет на нарушении.

**Уточнение указателя** (0.8.3, задача 6ee904ad): единый сериализатор списочных проекций живёт в `server/src/mcp/projection.ts` (ключи полей и проекторы записей); в `catalogs.ts` остались каталоги типов и точечная проекция `thoughts.get`.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- применяется к: etn.thoughts.get — карточка мысли, etn.thoughts.subgraph — подграф вокруг мыслей, etn.thoughts.neighbors — соседи и обход графа, etn.thoughts.usage — формальные связи мысли

## Корзина и проверки удаления в MCP

**Актуализация 0.8.4 (задача 09f19952).** Все перечисленные вызовы сняты с постоянного набора MCP — это действия исполнителя `etn.ops`: `thoughts.trash` (пометить/вернуть из корзины), `thoughts.deletion_check` (read-only), `trash.list` (read-only, каждая строка сразу с результатом проверки блокировки), `trash.purge` (confirm). Отдельного действия «проверка блокировки связи» нет — проверка отдаётся по каждой строке в `trash.list`. Детали — `etn.guide { topic: "trash.list" }`.

Группа инструментов S13 — мягкое удаление и проверки перед физическим:

- **`etn.thoughts.trash` / `etn.links.trash`** (idempotent) — пометить на удаление (`trashed: true`) / вернуть из корзины (`false`); блокировку не проверяют — это делает только физический `delete`;
- **`etn.thoughts.deletion_check`** (read-only) — что блокирует физическое удаление мыслей: использование в `thought_ref`-свойствах, удерживающие слои, будущие «сироты» среди детей. Принимает массив `thought_ids[]` — один вызов покрывает одиночную и групповую проверку;
- **`etn.links.deletion_check`** (read-only) — то же для связей: только удерживающие слои, без использования в свойствах и сирот;
- **`etn.trash.list`** (read-only) — вся корзина сети: помеченные мысли и связи, каждая сразу с результатом проверки блокировки (без отдельного `deletion_check` на строку);
- **`etn.trash.purge`** (destructive) — «удалить всё, что возможно»: физически удаляет помеченные, для которых проверки не дают блокировки; заблокированные молча пропускаются. Возвращает `{purged, skipped}`.

---

**Термин (глоссарий 10).** **Пометка на удаление** (`marked_for_deletion`) — состояние сущности в корзине: видима, но помечена; окончательное удаление возможно только при отсутствии удерживающих ссылок.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- применяется к: Семейство операций etn.links.* упраздняется, кроме восстановления из корзины, Деструктивные операции не входят в составные write-инструменты, Удаление значения свойства-связи помечает ребро в корзину

## Лимиты и read-only режим MCP-операций

Настройки, ограничивающие агента в MCP-контуре. Живут в `_system.db` (`settings`); на MVP — фиксированные дефолты.

| Ключ | Смысл |
|---|---|
| `mcp.max_nodes_per_subgraph` | Жёсткий потолок узлов в `etn.thoughts.subgraph` (дефолт 500) — защита от выкачивания всей сети |
| `mcp.max_writes_per_minute` | Серверный дефолт бюджета записей на пользователя — защита от runaway-агента |
| `api_keys.max_writes_per_minute` | Per-key переопределение (task O8): `NULL` — серверный дефолт; задаётся при создании ключа и меняется через PATCH ключа. MCP-слой резолвит эффективный лимит на ключ при открытии сессии |

Правила:
- `etn.thoughts.write` считается **одной** записью бюджета, сколько бы сущностей ни записал;
- ключ с `read_only: true` пропускает только ресурсы и read-инструменты — проверка выполняется перед каждым изменяющим tool-вызовом («посмотреть — не трогать»);
- каждый изменяющий tool-вызов пишется в `audit_log` (`category = 'data'`, `action` — тип операции, `details` — параметры вызова).

Чтения в `audit_log` не попадают — вместо этого счётчики `thought_read_metrics`.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер, Аутентификация и права доступа
- зависит от: Аутентификация и права доступа
- применяется к: Составной write-инструмент — одна транзакция и одна запись бюджета

<a id="pub-7df6b966"></a>

## Обязательное свойство-связь проверяется сервером при записи

Свойство-связь, объявленное в привязке с `required = true`, проверяется сервером при записи мысли: незаполненное попадает в `warnings` ответа (как незаполненные обязательные скаляры). Проверяется наличие хотя бы одного живого значения. Обязательность симметрична и работает у привязки со стороны назначения (Привязка со стороны назначения равноправна с привязкой источника): мысль этого типа без живого входящего ребра данного типа связи получает то же предупреждение.

Это заменяет дисциплинарное правило «требование без связи „применяется к“ считается потерянным» серверной проверкой.

Исключение: свойства «Родители» и «Потомки» обязательными не объявляются (см. их требование).

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, MCP-сервер
- применяется к: POST /thoughts — создание мысли со связью-родителем, /thoughts/{id}/properties — чтение и запись значений свойств, etn.thoughts.write — батч-запись мыслей, связей и комментариев

<a id="pub-92b9c55b"></a>

## Операторы наборов значений: any_of, all_of, none_of

К действующим операторам (`eq`, `ne`, `contains`, `gt`, `gte`, `lt`, `lte`) добавляются три оператора для наборов значений:

- **`any_of`** — набор пересекается с перечисленными значениями (хотя бы одно);
- **`all_of`** — набор содержит все перечисленные значения;
- **`none_of`** — набор не содержит ни одного из перечисленных.

Операторы работают и для свойств-связей (набор целей рёбер), и для обычных множественных скалярных свойств (`config.multiple`). Поведение существующих скалярных операторов не меняется; отборы типов мыслей (views) строятся на тех же условиях и продолжают работать.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, MCP-сервер
- применяется к: POST /thoughts/query — отбор мыслей по критериям, etn.thoughts.query — структурная выборка, thought_type_views — именованные отборы типов мыслей

<a id="pub-b3ce5014"></a>

## Операции над набором значений: добавить, убрать, заменить

Поверх семантики полной замены (`values: {...}` перезаписывает набор целиком, пустой список очищает) вводятся идемпотентные операции над элементами набора свойства-связи:

- **добавить в набор** (`add`) — принимает цель и необязательный комментарий «зачем именно эта ссылка»; уже существующее живое ребро — no-op;
- **убрать из набора** (`remove`) — помечает ребро цели в корзину; отсутствующее — no-op;
- **заменить набор** (`set`) — текущая семантика `values`.

Семантика обобщается с `etn.thoughts.bulk_update` (`link_parents`/`unlink_parents`/`set_only_parents`) на любое свойство-связь. Добавление одной ссылки — один вызов, без предварительного чтения текущего набора: две параллельные записи не затирают друг друга.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, MCP-сервер
- применяется к: etn.thoughts.bulk_update — групповые операции над мыслями, etn.thoughts.write — батч-запись мыслей, связей и комментариев, /thoughts/{id}/properties — чтение и запись значений свойств, POST /thoughts/batch — групповые операции над мыслями

<a id="pub-5c44f6a7"></a>

## Отборы типов правятся инструментами онтологии, а не отдельным семейством операций

Создание, изменение и удаление отборов типов идут теми же инструментами, что правка типов, свойств и привязок:

- запись — секцией `type_views[]` идемпотентного батча онтологии, наравне с `thought_types[]`, `link_types[]`, `properties[]`, `type_properties[]`; повторный вызов с теми же аргументами не меняет состояние;
- удаление — общей операцией удаления элемента онтологии с видом `type_view`;
- локальные `ref` внутри батча действуют и для отборов: отбор можно завести одним вызовом вместе с типом, которому он принадлежит.

**Почему не отдельное семейство `etn.views.*` на запись.** Отбор — элемент онтологии; заводя ему свои инструменты, мы получаем второй путь правки той же сущности, свой бюджет записи, свою строку аудита и рассинхронизацию с батчем, где тип и его отбор создаются вместе.

**Исполнение отбора — не онтология, а чтение,** и остаётся отдельной операцией.

То же деление в REST: отборы — вложенный ресурс типа мысли, исполнение — отдельный маршрут.

**Запрет правки в не-основных слоях (0.7.4, задача `d9b66617-…`).** Секция `type_views[]` в `etn.ontology.write` принимается сервером только в Основе (`currentLayer.is_base === true`). В любом не-основном слое — 422 `VALIDATION_ERROR` с указанием роли слоя. Чтение (`etn.views.run`, `thought-type-views` GET) в не-основных слоях разрешено без ограничений: правки в слоях касаются собственно `thought_type_views`-строк этого слоя, но создать/изменить/удалить отбор типа через `etn.ontology.write` в слое изменений нельзя. Клиент защищает пользователя заранее понятными тостами и плейсхолдером в редакторе (см. `canvas/focus-filter-strip.ts`, `screens/thought-type/views-tab.ts`, `isInBaseLayer()`); серверная валидация остаётся последним рубежом для агентов.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер, REST API
- применяется к: etn.ontology.write — настройка онтологии сети одним вызовом

## Перечень etn.instructions отдаёт только корневые инструкции

Режим без `keywords` возвращает только корневые инструкции — мысли типа «инструкция», у которых среди родителей нет другой инструкции по **нетипизированному (родительскому)** ребру (модель скиллов). Типизированная связь («см. также» и любая другая) иерархии не образует и корневую инструкцию из перечня не прячет — учитываются только рёбра с пустым `type_id` (ошибка fa7df2c3). Под-инструкции агент находит из текста корневой (таблица «когда читать какую») и поиском по `keywords` — он ищет по всем инструкциям, включая подчинённые. Превью `preview.body_md` в перечне — до 300 символов (хватает блока «Когда применять»); полный текст — режимом `instruction_id`.

Условие корректности среза данных: иерархия инструкций размечена (задача «Привести иерархию инструкций к модели скиллов», 0.8.4) — до этого часть под-инструкций, висящих напрямую в разделе, в перечень не попадёт, что терпимо: они достижимы через keywords.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- применяется к: etn.instructions — витрина инструкций агентам

## Свойство-связь можно навесить на мысль вне типа

Свойство-связь можно навесить на конкретную мысль, не объявляя его в типе: запись значения несуществующего в типе свойства-связи создаёт внетиповое свойство-связь у этой мысли. Действующее правило «запись только для подключённого свойства» получает исключение для вида «тип связи» (см. правку требования «Запись значения допускается только для подключённого свойства»).

## Семейство операций etn.links.* упраздняется, кроме восстановления из корзины

Создание и удаление связей через отдельные операции упраздняются: `etn.links.create`, `etn.links.delete`, `etn.links.trash`, `etn.links.get`, `etn.links.deletion_check` и их REST-аналоги (`POST /links`, `DELETE /links/{id}`) снимаются — создание и удаление уходят в операции над свойствами. От семейства `etn.links.*` остаётся **восстановление из корзины** (`trashed: false`). Чтение отдельной связи заменяется запросом значений свойства (цель + комментарий + идентификатор ребра).

Обход графа не затрагивается: `subgraph`, `neighbors`, `path`, `in_subtree_of` работают как прежде — они про окружение и структуры, а не про манипуляцию отдельной связью.

Снятие без периода сосуществования — по ADR «поглощённые MCP-инструменты снимаются одним мажором» (0.8.1 — мажорная для модели данных граница).

- относится к подсистемам: REST API, MCP-сервер
- применяется к: Корзина и проверки удаления в MCP, CRUD связей: POST, GET, PATCH, DELETE /links, GET /thoughts/{id}/links — связи мысли для редактора, etn.links.delete — физическое удаление связи

## Сквозная слоистость MCP-инструментов

**Актуализация 0.8.4 (задача 09f19952).** Слоистость по-прежнему сквозная, но ростер вызовов сузился: `layers.create`/`layers.update`/`layers.delete`/`layers.diff`/`layers.diff_doc`/`layers.merge` — действия исполнителя `etn.ops`; инструментами остались только `etn.layers.list` и `etn.layers.select`. `etn.changes.list` — действие `changes.list` исполнителя `etn.ops` (read-only); семейство `etn.links.*` упразднено (требование `3ea5c6af`). Детали — `etn.guide { topic: "changes.list" }`.

Слои изменений — сквозное свойство всех MCP-инструментов, а не отдельные «послойные» варианты: **все** чтения и записи (`etn.thoughts.*`, `etn.links.*`, поиск, подграф, комментарии, свойства, bundle…) работают в контексте текущего слоя вызывающего ключа.

Слой сессии хранится в той же таблице `session_layers`, что и у REST, но ключуется иначе: у MCP нет `Client-Id` — идентичность сессии `mcp:<api_keys.id>`. Следствия:
- у каждого API-ключа своя независимая слой-сессия (два ключа одного пользователя не мешают друг другу) — фундамент будущего «ключ, прибитый к слою-песочнице»;
- `etn.layers.list` помечает `current` по ключу;
- `etn.changes.list` фильтрует события видимостью в слое ключа и отдаёт `truncated: true`, когда `since_seq` раньше последнего переключения слоя.

**Эхо слоя:** ответ каждого пишущего инструмента содержит `layer: {id, title}` — текущий слой ключа на момент ответа; агент, пишущий не в тот слой, видит это сразу, а не по последствиям. Read-ответы эха не несут (исключение — список слоёв с `current`).

Полный цикл агента без REST руками: `layers.list` → `layers.create` → `layers.select` → записи/чтения → `layers.merge` → `layers.delete` (после удаления слоя сессия ключа автоматически переключается на родителя — отдельный `select` обратно не нужен).

**Сверх паритета (13-layers.md §10.2, §8.5).** Помимо полного паритета по слоям, агент получает путь аварийного согласования конфликта `base_version`: `layers.conflicts` (read-only) и `layers.reset_override` (`confirm`) — снять расхождение, из-за которого слой стал несливаемым.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер, Слои изменений (подсистема)
- применяется к: etn.layers.* — управление слоями через MCP, etn.changes.list — дельта-фид событий для долгоживущих агентов, MCP-сервер

<a id="pub-428cd54c"></a>

## Транспорт и аутентификация MCP-сервера

Как внешний AI-агент подключается к MCP-серверу ETN и как авторизуется.

**Транспорты** (оба поддерживаются SDK `@modelcontextprotocol/sdk`):
- **stdio** — для локальных агентов, запускаемых на сервере; ключ — в переменной окружения `ETN_API_KEY` или аргументом `--api-key`;
- **StreamableHTTP** — для удалённых; ключ — заголовок `Authorization: Bearer <API-key>` (как в REST).

MCP-эндпоинт открывается на отдельном пути `/mcp` (или отдельном порту), отличном от REST, — чтобы изолировать трафик агентов.

**Время жизни HTTP-сессии.** StreamableHTTP-сессия живёт в памяти сервера и сметается, простояв без запросов дольше idle-TTL. TTL задаётся переменной окружения `ETN_MCP_SESSION_IDLE_TTL_MS` (целое число миллисекунд, допустимо 1000…2592000000, по умолчанию 86400000 — 24 часа). Следующий запрос сметённой сессии получает `404 NOT_FOUND` «Unknown or expired MCP session; re-run initialize.», и клиент обязан переинициализироваться. Дефолт намеренно велик: агент делает произвольно длинные паузы между вызовами, и короткий TTL рвёт его работу посреди задачи (ошибка `66dc78ef-1f8c-4629-88c4-cdbe01030feb`). Сессии перезапуск сервера не переживают — вся карта сессий теряется вместе с процессом.

**Live-рассылка событий зависит от транспорта.** В HTTP-режиме события публикуются в тот же внутрипроцессный брокер, что и у REST, — подключённые WebSocket-клиенты получают их сразу. В stdio-режиме (`etn mcp`, отдельный процесс) событие пишется в общий `event_log`; сервер подхватывает его event-log relay с задержкой до 300 мс, а при недоступном сервере клиенты догоняют запись через `resume` при переподключении.

Модель авторизации — см. требование «AI-агент ограничен MCP-контуром»: агент действует от лица пользователя, чей ключ передан.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер
- зависит от: Real-time канал (WebSocket)
- применяется к: Отзыв ключа разрывает активные WebSocket- и MCP-подключения

## Удаление значения свойства-связи помечает ребро в корзину

Удаление значения из набора свойства-связи (операция `remove` или полная замена без этого элемента) помечает ребро `marked_for_deletion = true`, а не стирает физически: иначе постоянный комментарий связи («зачем эта ссылка») исчез бы молча. Восстановление — существующей операцией корзины. Физическая чистка — `etn.trash.purge` / `POST /trash/purge` как сегодня.

Пометка учитывается при чтении: помеченное ребро в значения свойства не попадает.

**Разграничение с удалением самого свойства-связи.** Удаление одного значения (цели) — корзина, как описано выше. А вот удаление самого свойства-связи рёбра в корзину НЕ отправляет (Свойство-связь и тип связи — единый жизненный цикл): тип связи удаляется вместе со свойством, рёбра теряют `type_id` и становятся структурными.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, MCP-сервер
- применяется к: CRUD связей: POST, GET, PATCH, DELETE /links, GET /trash и POST /trash/purge — корзина мыслесети, Корзина и проверки удаления в MCP

## Фильтр обхода по типам связей

**Актуализация 0.8.4 (задача 09f19952).** `etn.thoughts.path` снят с постоянного набора MCP — это действие `thoughts.path` исполнителя `etn.ops` (read-only). Остальные упомянутые вызовы (`etn.thoughts.subgraph`, `etn.thoughts.neighbors`, `etn.thoughts.query`) — по-прежнему инструменты. Детали — `etn.guide { topic: "thoughts.path" }`.

Обход графа можно ограничить перечнем типов связей: `etn.thoughts.subgraph`, `etn.thoughts.neighbors`, `etn.thoughts.path`, `etn.thoughts.query { in_subtree_of }` и их REST-эквиваленты (`POST /thoughts/{id}/focus`, `GET /thoughts/{id}/neighbors`, `POST /thoughts/query`) принимают опциональный фильтр.

- **Нетипизированные (структурные) связи отбираются наравне с типизированными**: можно сказать «только структурные» и «только такой-то тип (или перечень)».
- **Иерархия типов связей:** отбор по родительскому типу включает его потомков.
- **Без фильтра поведение не меняется** — обход идёт по всем рёбрам, как сегодня.

Фильтр лечит шум там, где он возникает — в запросе: после него правило «больше 15 однотипных связей — группируй каталогом» больше не нужно.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, MCP-сервер
- применяется к: POST /thoughts/{id}/focus — окрестность мысли для холста, etn.thoughts.subgraph — подграф вокруг мыслей, etn.thoughts.query — структурная выборка, POST /thoughts/query — отбор мыслей по критериям, etn.thoughts.neighbors — соседи и обход графа, GET /thoughts/{id}/neighbors — соседи мысли без смены фокуса
