# Подключение AI-агентов к ETN (MCP)

ETN предоставляет MCP-сервер, через который внешние AI-агенты (Claude Desktop,
IDE-агенты, кастомные скрипты) читают и изменяют мыслесети наравне с людьми.

## 1. Авторизация

Агент действует от лица пользователя, чей API-key передан:

- Видит и меняет только сети, где этот пользователь — участник.
- Для «только чтения» выпустите read-only ключ (в клиенте: «Мои ключи» → создать
  с опцией read-only).

## 2. Режим stdio (локальные агенты)

```json
{
  "mcpServers": {
    "etn": {
      "command": "node",
      "args": ["/opt/etn/server/dist/mcp-stdio.js", "--api-key", "etn_..."],
      "env": { "ETN_DATA_DIR": "/var/lib/etn" }
    }
  }
}
```

> Точное имя stdio-точки входа см. в README сервера (`etn mcp` — CLI-команда).
> Ключ также можно передать через `ETN_API_KEY`.

## 3. Режим HTTP (удалённые агенты)

Включите на сервере `ETN_MCP_ENABLED=1`. Эндпоинт: `POST /mcp` (заголовок
`Authorization: Bearer <key>`).

## 4. Основные инструменты

| Инструмент | Назначение |
|-----------|------------|
| `etn.networks.list` | список доступных сетей |
| `etn.thoughts.search` | полнотекстовый поиск |
| `etn.thoughts.query` | структурная выборка по критериям: тип, поддерево, актуальность, ключевые слова, свойства, даты |
| `etn.thoughts.get` / `neighbors` | чтение мысли (с `meta`: счётчики связей/вложений/хроники/использований и превью постоянного комментария; `thought_ref`-значения свойств — `{id, title}`) и её окружения (с каталогами использованных типов `link_types`/`thought_types`). По умолчанию — компактная проекция (`view: "compact"`, task O12): без цветов/шрифтов/иконок; `view: "full"` — легаси-форма |
| `etn.thoughts.usage` | кто ссылается на мысль через свойства (формальные связи), сгруппировано по свойству |
| `etn.thoughts.subgraph` | подграф радиуса N (контекст для генерации) с каталогами типов и превью комментариев (`include_comments` — последние 10 хронологических записей, тела ≤ 2000 символов). Мягкий бюджет символов: `max_chars` (task O13) — сервер сначала сжимает превью до 500 символов, потом отбрасывает самые дальние от seed'ов узлы, пока не влезет; `truncated`/`reason`/`budget` в ответе подсказывают, что именно отрезали |
| `etn.thoughts.path` | путь между мыслями |
| `etn.thoughts.find_duplicates` | **обязателен перед созданием** — поиск дубликатов |
| `etn.types.list` | оба каталога типов целиком (иерархия + эффективные свойства L21) — что заполнять, до записи |
| `etn.thoughts.create/update/delete` | изменение мыслей; `create` принимает тип по `type_id` **или** `type` (по имени) |
| `etn.links.create/delete` | связи; `create` принимает тип по `type_id` **или** `type` (по `name_forward`/`name_reverse`) |
| `etn.comments.upsert` | комментарии (permanent — create-or-update, chronological — новая запись; `owner_type`+`owner_id` или `targets[]` для привязки одной хронологической записи к нескольким мыслям/связям сразу) |
| `etn.comments.update` / `delete` | правка и удаление комментария по `comment_id` |
| `etn.comments.get` | полный текст одного комментария (по `comment_id` или по `thought_id` — постоянный); вызывается, когда превью показывает `truncated: true` |
| `etn.properties.set` | значения свойств: одно (`key`+`value`) или набор (`values: {key: value\|null}` — одной транзакцией) |
| `etn.thoughts.upsert_bundle` | составная запись «единицы знания» (мысль + постоянный комментарий + свойства + связи + вложения) **одной транзакцией и одним вызовом** вместо 5–8 отдельных; `thought.type`/`links[].type` тоже принимают тип по имени |
| `etn.export.subgraph` | подграф как Markdown-документ |

## 5. Важное правило: не плодить дубликаты

Перед `etn.thoughts.create` агент **обязан** вызывать
`etn.thoughts.find_duplicates` и переиспользовать существующую мысль при
совпадении имени/синонима. `etn.thoughts.upsert_bundle` делает эту проверку
сам (параметр `on_duplicate: fail|reuse|update`, по умолчанию `fail`) — для
записи «мысль + всё остальное» одним вызовом предпочтительнее его, а не
связку `find_duplicates` → `create` → … .

## 6. Поведение

- Изменения агента проходят те же проверки прав и валидацию, что у людей.
- Участники сети видят изменения агента в реальном времени (WebSocket).
- Каждый изменяющий вызов фиксируется в аудите (`category=data`).
- Лимиты: `max_nodes_per_subgraph` (default 500), `max_writes_per_minute`
  (default 60) — настраиваются администратором.

## 7. Пример: собрать дайджест по теме

1. `etn.thoughts.search { query: "конкуренты", scope: "all" }`
2. `etn.thoughts.subgraph { seed_ids: [топ-5], radius: 2, include_comments: true,
   max_chars: 12000 }` — мягкий бюджет (task O13): сервер сначала сожмёт
   превью комментариев до 500 символов, при необходимости отбросит самые
   дальние узлы. Семантика усечения видна в `truncated`/`reason`/`budget`.
3. Сгенерировать дайджест в своей LLM.
4. Опционально: `etn.comments.upsert` — сохранить дайджест как хронологический
   комментарий у корневой мысли.

> Без `max_chars` сервер возвращает всё, что обошёл обход (до
> `max_nodes_per_subgraph`). Это нормально, если контекстное окно
> агента достаточно; `max_chars` — для жёсткого потолка.

## 8. Самоописание сети: маршрутизация и формат записи (задача O5)

### 8.1. Выбрать подходящую сеть

Когда у пользователя несколько сетей, агент должен сам решить, в какую писать.
`etn.networks.list` отдаёт `description` и `when_to_use` для каждой сети
плюс `has_structure: true|false`. Алгоритм:

1. Получить список: `etn.networks.list` (без параметров).
2. Прочитать `description` — общее назначение сети.
3. Прочитать `when_to_use` — список use cases, для каждого — какие ещё поля
   сети релевантны (например, «Кодирование → structure, conventions»).
4. Выбрать сеть, чей `when_to_use` соответствует текущей задаче.
5. Если `has_structure: true`, начать с `etn.networks.structure` (§8.2).
6. Если `has_structure: false` (или структура нерелевантна) — сразу
   `etn.thoughts.search` / `etn.thoughts.query`.

Не читайте все поля подряд (`conventions`, `examples`) у всех сетей —
это лишний расход контекста. Запрашивайте только нужные выбранной сети
(`GET /networks/{id}` или ресурс `etn://networks/{network_id}`).

### 8.2. Работа со структурой сети

Когда сеть объявляет `node_section_type_id`, агент читает «оглавление» через:

```
etn.networks.structure { network_id }
```

Ответ:

- `node_section_type_id` — тип мысли-раздела.
- `sections[]` — активные мысли этого типа с обогащением:
  - `permanent` — превью постоянного комментария (обрезка до 2000 символов
    + `comment_id` для полного чтения через `etn.comments.get`);
  - `properties` — резолвнутые значения (`thought_ref` → `{id,title}`);
  - `counters` — `parents_count`, `children_count`, `attachments_count`,
    `usage_count`.
- `thought_types` — каталог типов, использованных в разделах.
- `has_structure: false` — пустой `sections`, агент переходит к search/query.

Дальше — обычный drill-down по выбранному разделу:

1. Прочитать `permanent` целиком, если `truncated: true` —
   `etn.comments.get { comment_id }`.
2. Запросить **типы раздела** (task O16) — только типы, реально
   используемые в поддереве этого раздела:
   ```
   etn.types.list { network_id, in_subtree_of: <section.id> }
   ```
   Ответ содержит только релевантные `thought_types` и `link_types`, каждый
   с `usage_count` — счётчиком использования внутри раздела. Это второй
   шаг после `structure`; для записи в раздел у агента сразу есть
   «контекстный» каталог типов, без полного снимка всей сети.
3. Найти подходящие под-мысли:
   `etn.thoughts.query { network_id, in_subtree_of: <section.id>, ... }`
   или `etn.thoughts.search`.
4. Прочитать детали нужных мыслей: `etn.thoughts.get` или `subgraph`.

Если нужно изменить `max_depth` обхода поддерева — параметр `max_depth` (1..`TRAVERSAL_DEFAULTS.MAX_DEPTH`). При пустом поддереве (нет детей) —
пустые `thought_types` / `link_types`; это валидный ответ, не ошибка.

### 8.3. Запись в сеть: формы и правила

Перед `create` / `update` агент обязан прочитать `conventions` (правила
записи) и при сомнениях по форме — `examples` (хорошие/плохие записи).
Эти поля не возвращаются в `etn.networks.list`; запросите их явно через
`GET /networks/{id}` или ресурс.

Запись одной «единицы знания» — идемпотентная операция `upsert_bundle`
(см. `05-mcp-server.md` §5.2a): мысль + комментарий + свойства + связи +
вложения одной транзакцией. Политика `on_duplicate` (`fail` / `reuse` /
`update`) делает повторный импорт безопасным. Обязательный шаг —
`etn.thoughts.find_duplicates` перед `upsert_bundle`, чтобы не плодить
дубликаты, и сверка с `conventions` для типа.

## 9. Warnings о незаполненных `required`-свойствах (задача O6)

Тип мысли может объявлять `required`-свойства в `type_properties`. `etn.thoughts.create`,
`etn.thoughts.update` (когда `changes.type_id` присутствует) и `etn.thoughts.upsert_bundle`
**не падают**, если карточка получилась неполной — вместо этого возвращают неломающий
блок `warnings: [{code: "REQUIRED_PROPERTY_MISSING", key, property_id, defined_on,
value_type, inherited}]` по эффективному списку свойств типа (свои + унаследованные от
предков, L21). Это сигнал агенту «карточка записана, но карточка неполная — дозаполни».

Правила:

- Поле `warnings` появляется **только** когда есть расхождения. Для
  `etn.thoughts.upsert_bundle` это поле **всегда присутствует** (включая пустой массив)
  — удобнее для парсинга.
- Дефолты (`config.default_value` / `type_property_overrides.default_value`) **не
  маскируют** предупреждение: они применяются к будущим значениям, но в `property_values`
  на момент проверки записи нет — карточка по-прежнему считается неполной. Чтобы
  заглушить warning, запишите значение явно через `etn.properties.set` или добавьте
  его в `properties` следующего `upsert_bundle`.
- `warnings` появляется и при смене типа: если вы переводите мысль на тип, у которого
  есть `required`-свойства, не заполненные сейчас, вы получите их в ответе `update`.
- Тип **без** `required`-свойств → `warnings` отсутствует (для `create`/`update`) или
  пустой (для `upsert_bundle`).
- Мысль **без типа** → `warnings` отсутствует; корневой тип специально не объявляет
  `required`-свойств (его настройки применяются к безтиповым мыслям, §8.1).

Типичный сценарий «дозаполнения»:

```jsonc
// 1) upsert_bundle вернул warnings: [{ key: "status", ... }]
// 2) закрываем gap одним вызовом:
{
  "name": "etn.properties.set",
  "arguments": {
    "network_id": "...",
    "owner_type": "thought",
    "owner_id": "<id из шага 1>",
    "values": { "status": "active" }
  }
}
```

Совет: чтобы избежать двухэтапной записи, передавайте `required`-свойства прямо
в `properties` вашего `upsert_bundle` — `etn.types.list` (или
`etn.types.list(in_subtree_of=…)`) подскажет, какие ключи обязательны для типа.

## 10. Компактная проекция ответов `view: "compact" | "full"` (задача O12)

Четыре основных read-инструмента — `etn.thoughts.get`, `…neighbors`,
`…subgraph`, `…usage` — исторически возвращали вместе с полезными данными
визуальные/служебные поля, которые агент не использует при рассуждении о
графе: цвета текста и фона, флаги шрифта (`bold`/`italic`/`underline`/
`strike`), признак emoji/image у иконки, ссылку на файл иконки, флаги
`is_protected`/`is_root`, а для связей и типов связей — `color`/`style`/
`width`. На больших подграфах это заметная доля токенов без пользы.

Параметр `view` управляет проекцией:

- **`view: "compact"` (дефолт для MCP)** — выкидывает все эти поля из
  каждой мысли, каждой записи `ThoughtRef` и каждой записи каталога
  `link_types`. `icon` (emoji/путь к картинке) остаётся: он семантический,
  а не визуальный.
- **`view: "full"`** — возвращает ответ в той же форме, что и до O12.

Параметр принимают **только эти четыре инструмента**. Семантика:

- **Конверт ответа не меняется.** Например, `etn.thoughts.get` при
  `compact` и при `full` отдаёт один и тот же набор ключей верхнего уровня
  (`id`, `title`, `type`, `properties`, `meta`, …); различается только
  состав полей на самой мысли. Если ваш парсер смотрит только на `id`,
  `title`, `meta.permanent`, `properties`, он будет работать одинаково в
  обеих проекциях.
- **Дефолт — `compact`.** При первом подключении агент видит компактные
  ответы без дополнительной настройки.
- **`full` остаётся доступным неопределённо долго.** Когда придёт время
  полностью убрать `full` (если это произойдёт), это будет отдельный
  период сосуществования — на старте оба режима сосуществуют.

Когда переходить на `full`:

- Если вашему агенту нужно рендерить граф (например, генерировать
  визуальный отчёт), передайте `view: "full"` — иначе цвета и стили линий
  будут утрачены.
- В остальных сценариях (RAG, суммаризация, drill-down, дайджесты) —
  оставайтесь на `compact`: меньше токенов, тот же смысловой объём.

Cookbook (`docs/05-mcp-server.md` §5.1e):

```jsonc
// 1) Компактный drill-down (по умолчанию):
{
  "name": "etn.thoughts.subgraph",
  "arguments": {
    "network_id": "<net>",
    "seed_ids": ["<id раздела>"],
    "radius": 2,
    "include_comments": true
    // view: "compact" — дефолт, можно не указывать
  }
}

// 2) Полный ответ с цветами и стилями линий (для визуализации):
{
  "name": "etn.thoughts.subgraph",
  "arguments": {
    "network_id": "<net>",
    "seed_ids": ["<id раздела>"],
    "radius": 2,
    "view": "full"
  }
}
```

Невалидное значение (`"plaid"`, `"compact-only"` и т. п.) сервер отвергает
по схеме инструмента с `VALIDATION_ERROR` — менять контракт «на лету»
нельзя.

## 11. Бюджет ответа `etn.thoughts.subgraph`: `max_chars` (задача O13)

У `subgraph` есть жёсткий лимит `max_nodes` (default 500 узлов через
настройку `mcp.max_nodes_per_subgraph`), но нет лимита **символов**.
200 активных мыслей с `include_comments: true` могут давать сотни
килобайт JSON — и агент не может заранее знать, влезет ли ответ в его
контекстное окно. Параметр `max_chars` решает это явно: агент задаёт
мягкий потолок, сервер сам ужимает полезную нагрузку и честно
сообщает, что именно отрезал.

Семантика усечения (два шага, в этом порядке):

1. **Сжатие превью.** Каждое тело комментария — постоянный
   `permanent.body_md` и каждая запись `chronological.entries[i].body_md`
   — обрезается до 500 символов (`SUBGRAPH_BUDGET_PREVIEW_CHARS`). В
   ответе остаётся `comment_id` для полного чтения через
   `etn.comments.get`.
2. **Отбрасывание узлов.** Если даже с укороченными превью не влезает,
   сервер считает BFS-расстояние от seed'ов и удаляет самые дальние
   узлы (со связанными рёбрами и их comment-слотами). **Seed'ы никогда
   не удаляются**: даже если один seed уже тяжелее бюджета, ответ
   возвращается (с `truncated: true`, `reason: 'max_chars_nodes'`), а
   не ошибка.

Поля ответа:

| Поле | Смысл |
|------|-------|
| `truncated: boolean` | `true`, если хотя бы один шаг ужатия сработал |
| `reason: string \| null` | `'max_nodes'` (жёсткий лимит обхода), `'max_chars_preview'` (влезли после сжатия превью), `'max_chars_nodes'` (влезли после отбрасывания узлов), `null` (без усечения) |
| `budget?: { max_chars, original_chars, final_chars, steps }` | диагностика бюджета: сколько символов было до и после; присутствует только когда `max_chars` задан И обход не усекался по `max_nodes` |

Приоритет причин: `max_nodes` (от traversal) важнее любой `max_chars_*`
причины — он сигнализирует «обход неполный», дальнейшее сжатие не
поможет.

Cookbook (`docs/05-mcp-server.md` §5.1f):

```jsonc
// 1) Жёсткий бюджет 12 KB на контекст — сервер сначала сожмёт превью,
//    при необходимости отбросит дальние узлы:
{
  "name": "etn.thoughts.subgraph",
  "arguments": {
    "network_id": "<net>",
    "seed_ids": ["<id раздела>"],
    "radius": 3,
    "include_comments": true,
    "max_chars": 12000
  }
}

// 2) Адаптивный выбор: вызвать без max_chars, оценить размер на своей
//    стороне (`JSON.stringify(response).length`), затем перезапросить
//    с max_chars ≈ этот размер × 0.8 — с запасом на следующие изменения.

// 3) Максимум экономии токенов: view:'compact' (O12) + max_chars.
//    Компактная проекция снимает визуальные поля, бюджет — большие
//    комментарии и дальние узлы.
{
  "name": "etn.thoughts.subgraph",
  "arguments": {
    "network_id": "<net>",
    "seed_ids": ["<id раздела>"],
    "radius": 3,
    "include_comments": true,
    "view": "compact",
    "max_chars": 8000
  }
}
```

Если ответ пришёл с `reason: 'max_chars_nodes'` и агенту не хватило
полноты — есть три стратегии:

- **Сузить `radius`** (1 → 2 → 3) и повторить.
- **Разбить по seed'ам**: взять топ-N мыслей из предыдущего ответа и
  вызвать `subgraph` от каждой отдельно — топология в сумме шире, но
  каждый вызов влезает в бюджет.
- **Снизить `include_comments`** до `false` и подтянуть нужные
  комментарии точечно через `etn.comments.get(comment_id)`.

Полный текст комментария — всегда за `etn.comments.get` по `id` из
