## activity_log — журнал активности сети

Таблица БД сети — неизменяемый журнал «кто что сделал» для рабочего стола «События». Append-only: записи создаются, но никогда не правятся. Источник — НЕ `event_log` (тот — буфер синхронизации с окном удержания).

| Столбец | Тип | Описание |
|---|---|---|
| `id` | INTEGER PK | автоинкремент |
| `user_id` | TEXT NOT NULL | автор действия |
| `action` | TEXT NOT NULL | `created` / `updated` / `deleted` / `trashed` / `restored` |
| `entity_type` | TEXT NOT NULL | `thought` / `link` / `thought_type` / `link_type` / `property` / `comment` / `attachment` / `layer` |
| `entity_id` | TEXT NOT NULL | логический id сущности |
| `entity_title` | TEXT NOT NULL | краткий снимок описания («мысль без типа, "Название"»); лимит 256 символов, излишек обрезается — ссылок на удалённые сущности нет |
| `layer_id` | TEXT NULL | слой, в котором произошло событие |
| `occurred_at_ms` | INTEGER NOT NULL | время события, миллисекунды |

Индексы: `(occurred_at_ms)`, `(user_id, occurred_at_ms)`, `(entity_type, entity_id, occurred_at_ms)` — под три оси ленты.

**Ветвимость:** ветвимая таблица — события слоя пишутся в слое со своим `layer_id`; при слиянии и удалении слоя обрабатывается свёрткой (см. требование об авто-свёртке).

**Чего здесь нет.** Событий захвата (`edit.*`) и per-user состояния — журнал хранит только историю изменений сущностей сети.

---

**Термин (глоссарий 10).** **Журнал активности** (`activity_log`) — лента мутирующих операций сети (создание/правка/удаление мыслей, связей, типов, комментариев, вложений, слоёв); поддерживает свёртку и обрезку.

## ADR: вид значения thought_ref упраздняется — всякая ссылка на мысль есть свойство-связь

### Контекст

Устойчивой границы между «скалярной ссылкой на мысль» и «отношением» нет: у канонических кандидатов в скаляры (`версия` у работ, `источник` у элементов спеки) обратная сторона не просто осмысленна, а уже используется — отборы «Актуальные работы» и «Выполнено» у типа «версия» — это обратное чтение свойства `версия`; `usage` карточки файла — штатная проверка полноты переноса. Поддерживать два вида ссылок означало бы продолжать выбор при каждой записи.

### Решение

**Вид значения `thought_ref` упраздняется.** Всякая ссылка на мысль моделируется свойством-связью. Две возможности, которые были только у `thought_ref`, становятся флагами в определении свойства-связи:

- **рисовать ли связь на карте по умолчанию** — массовые ссылки (например, `версия`) не рисуются, чтобы не засорять карту;
- **блокирует ли ссылка удаление цели** — замена нынешней проверки `deletion_check` по `property_values`.

Существующие значения переводятся миграцией с материализацией рёбер (см. сценарий «Перевод thought_ref в свойства-связи»): каждому свойству подбирается тип связи с осмысленной парой имён, флаги выставляются так, чтобы поведение не ухудшилось.

С тех.проекта «Свойства и связи: единый список и единый редактор» вид убран и из выпадающего списка вида значения в клиенте (прежде предлагался как «ссылка на мысль (legacy)» с гарантированной ошибкой 422) — упоминаний `thought_ref` в интерфейсе больше нет вообще.

### Следствия

- `copy_subtree` резолвит ссылки как рёбра: по типу связи в сети-получателе, затем по имени; кросс-сетевые значения не резолвятся.
- Отбор по ссылке работает в обе стороны тем же синтаксисом, что и по скалярам.

### Запреты

- Не заводить новых свойств вида `thought_ref` и не возвращать вид значения в реестр.
- Не хранить идентификатор цели в `property_values` для свойств-связей.

*(Уточнение 0.8.3.)* Оба запрета действуют для внутрисетевых ссылок. Вид значения «кросс-сетевая ссылка» — цель всегда в другой сети, ребро невозможно в принципе — не возврат `thought_ref` и не свойство-связь; см. ADR «кросс-сетевая ссылка — отдельный вид значения, а не ребро».

### Использование флага (0.8.1, доработка)

До этой доработки `show_on_map` был мёртв: расставлялся в реестре, но нигде не читался при отрисовке (ошибка show_on_map не влияет на отрисовку карты мыслей). Теперь он потребляется: задаёт дефолт клиентского фильтра типов связей на карте мыслей (требование «Дефолт и хранение фильтра типов связей на карте», диалог Диалог фильтра типов связей на карте).

## ADR: свойство-связь — проекция ребра, а не второе хранилище

### Контекст

Отношение между мыслями выражалось двумя способами — ребром `links` и значением свойства `thought_ref`. Они пересекаются по смыслу, но различаются возможностями: ребро участвует в обходе графа и имеет имя в обе стороны, свойство даёт отбор, обязательность и наследование по цепочке типов. Ни одно не покрывает другое, поэтому автор мысли выбирал при каждой записи, а агент гадал, где искать отношение. Вторая беда — `direction` в инструментах записи: его значение описывает роль цели, а не источника, и на этом уже теряли время.

### Решение

**Хранение отношения — только ребро `links`.** Свойство-связь — это определение в реестре `properties` нового вида значения «тип связи» (тип связи, направление, опционально ограничение по типу цели) плюс **проекция**: при чтении мысли её типизированные рёбра ложатся в свойства с именем по направлению (у источника — прямое имя типа связи, у цели — обратное). В `property_values` значение свойства-связи не пишется — два источника истины исключены.

**Направление записано не в определении свойства, а в привязке** (уточнено в 0.8.1, тех.проект 9019a3e4): сторона участия задаётся полем `side` привязки свойства к типу; заполнение прямого и обратного свойства создаёт одно и то же ребро. Грабли «direction в MCP-инструментах» исчезают вместе с самим `direction`.

**Одно свойство-связь на тип связи** (уточнено в 0.8.1, тех.проект 9019a3e4): уникальна не пара «тип связи + направление», а сам тип связи — поэтому ребро всегда ложится ровно в одно свойство, и переопределять имя на уровне свойства не нужно. Разный смысл — потомки типа связи, а не отдельные свойства.

**Структурные связи — свойства «Родители» и «Потомки»** на корневом типе, наследуются всеми; порядок детей задаётся позицией в наборе «Потомки».

### Следствия

- Обязательность, наследование по цепочке типов и отбор распространяются на связи.
- Обход графа фильтруется по типам связей — шум массовых связей лечится в запросе.
- Чтение остаётся двойным осознанно: свойства несут семантику, соседи и обход — структуру и окружение.

### Запреты

- Не создавать второе хранилище отношений (копии рёбер в таблицах значений).
- Не вводить переопределение имени свойства-связи на уровне типа — имя правится только в типе связи.
- Не указывать направление связи в операциях записи — его место только в привязке свойства (`side`).

## ADR: у ребра нет собственных атрибутов — один комментарий как пояснение значения

### Контекст

У рёбер были собственные типизированные атрибуты (привязки свойств с `owner: "link_type"`), хронологические комментарии и вложения. На практике вложения нужны узлам, а не рёбрам; отношение, обросшее атрибутами («дата начала действия», «степень обязательности»), — почти всегда признак невыделенной сущности: моделировать его надо мыслью-применением с двумя связями.

### Решение

**У ребра остаётся ровно один постоянный комментарий, и он трактуется как комментарий к значению свойства-связи** — «зачем я добавил именно эту ссылку». Добавление связи и пояснение выполняются одним действием. Привязки свойств с `owner: "link_type"` снимаются, хронологические комментарии и вложения у рёбер упраздняются; судьба существующих данных решается до миграции (перенести смысл в комментарий, выделить сущность или согласовать потерю — с показом пользователю того, что будет потеряно).

### Следствия

- По атрибутам связи нельзя отбирать — остаётся полнотекстовый поиск по комментарию. Плата принята осознанно.
- Чтение значения свойства-связи возвращает цель, комментарий и идентификатор ребра — трёхчастный ответ.

### Запреты

- Не возвращать свойства, хронологию и вложения к рёбрам, пока опыт не покажет обратное — тогда решение пересматривается отдельным ADR.

## ANALYZE выполняется в конце применения миграций сети

По завершении применения миграций сети сервер выполняет `ANALYZE` (при необходимости — только для таблиц, затронутых миграциями), чтобы у планировщика появилась статистика до первого запроса.

**Проверка.** После миграции в базе есть `sqlite_stat1`; perf-стенд показывает ожидаемые планы горячих запросов.

## api_keys — таблица ключей доступа

API-ключи для авторизации клиентов и MCP-агентов. У одного пользователя может быть несколько ключей — например отдельный для десктопа и отдельный для агента.

|---|---|---|

| `user_id` | TEXT NOT NULL FK → users.id ON DELETE CASCADE | Владелец |
| `label` | TEXT | Метка («desktop», «mcp-agent») |
| `key_hash` | TEXT NOT NULL UNIQUE | SHA-256 от ключа; сам ключ не хранится |
| `key_prefix` | TEXT NOT NULL | Первые 8 символов ключа для отображения |
| `read_only` | INTEGER NOT NULL DEFAULT 0 | 1 — ключу запрещены изменяющие операции |
| `max_writes_per_minute` | INTEGER NULL | Переопределение лимита записи MCP для этого ключа; `NULL` — серверный дефолт |
| `created_at` | TEXT NOT NULL | |
| `last_used_at` | TEXT | |
| `disabled` | INTEGER NOT NULL DEFAULT 0 | |

Индексы: уникальный по `key_hash`, обычный по `user_id`.

**Формат ключа:** `etn_<32 hex>` (длина 36).

**Главное правило.** Сам ключ на сервере не хранится никогда — только хеш и префикс. Показать пользователю ключ повторно после выдачи невозможно; потерянный ключ только перевыпускают.

**Вложение и слои — тонкое место.** Привязка ветвится (надгробие в слое прячет вложение из этого слоя), но **физический файл один на все слои**. Удалять файл с диска можно только когда ссылок на него не осталось ни в одном слое сети.

**Картинки и файлы в комментариях** ссылаются либо привилегированной схемой клиента (отдаёт локальные файлы), либо обычными файловыми, HTTP(S) или data-схемами. Рендерер: `etnimg:` разрешена и в позиции изображений, и в ссылках — ссылки на локальные файлы вложений рендерятся как `<a>` и открываются по клику (с 0.6.1, docs/03-server-api.md §10); `data:` и `file:` — только в позиции изображений.

### Модель 0.8.1: вложения только у мыслей

Вложения у связей (`owner_type: "link"`) упраздняются: на практике вложения нужны узлам, а не рёбрам. Существующие вложения рёбер до миграции показываются пользователю; их судьба (перенос к мысли или потеря) решается по каждой сети.

## client_request_cache — кэш дедупликации запросов

Хранилище результатов уже обработанных запросов — техническая основа идемпотентности. Живёт в системной БД.

| Столбец | Тип | Описание |
|---|---|---|

## comment_targets — привязки комментария к нескольким владельцам

Привязки комментария к владельцам — связь многие-ко-многим. Одна хронологическая запись может быть привязана сразу к нескольким мыслям и связям. **Ветвимая** таблица.

| Столбец | Тип | Описание |
|---|---|---|
| `pk` | INTEGER PK AUTOINCREMENT | Суррогат |
| `id` | TEXT NOT NULL | UUID строки |
| `layer_id` / `deleted` / `base_version` | | Слой-колонки |
| `comment_id` | TEXT NOT NULL | Логический id комментария |
| `owner_type` | TEXT NOT NULL | `'thought'` или `'link'` |
| `owner_id` | TEXT NOT NULL | |
| UNIQUE | `(comment_id, owner_type, owner_id, layer_id)` | Контроль дублей привязок в пределах слоя |

Индексы: по владельцу (список его комментариев, включая вторичные привязки) и по слою.

**Первичная привязка дублируется в самом комментарии.** Поля владельца в таблице комментариев хранят **первую** привязку; полный набор лежит здесь. Это важно для поиска: FTS индексирует текст только по первичной привязке; тексты вторичных владельцев в индекс не попадают, а отбор хроники ищет по телам через эту таблицу напрямую. При переносе первичной привязки триггеры перестраивают строку индекса.

### Записи дневника (0.10.1)

«Запись дня» — хроно-запись без смысловых мыслей: первичный владелец HOME, чипсы-мысли — вторичные привязки через эту таблицу. Снятие последнего чипса возвращает запись в HOME (инвариант автопривязки). Удаление мысли-чипса не удаляет запись. Класс записи для сортировки ленты считается по этой таблице: только HOME — `0`, иначе — `1`. На одну дату может быть несколько записей дня. См. ADR HOME и требование «Запись дня».

**Два вида комментариев решают разные задачи.** Постоянный — суть владельца, верная всегда; хронологический — датированная запись о событии или периоде.

**Предрендер.** HTML хранится рядом с markdown и обновляется при записи — клиенту не нужно рендерить текст при каждом показе. Отсюда требование: рендерить обязан общий markdown-рендерер, иначе кэш разойдётся с тем, что показывает клиент.

**Отдельного хранения Markdown-AST нет** и не планируется: пары «markdown + HTML» достаточно.

### Время в датах (0.10.1)

`valid_from`/`valid_to` хронологической записи — всегда полный UTC-инстанс ISO-8601 с миллисекундами; date-only не хранится. Сервер не придаёт датам смысла «календарного дня» и не конвертирует часовые пояса. `valid_to` у хронологической обязателен (незаполненное = `valid_from`), у постоянного остаётся `NULL`. Флаг `use_time` хранится на записи и управляет только отображением/правкой времени в клиенте. «Голая дата» во входных параметрах = сутки UTC. Правила — требования «Формат дат хроно-записи», «Флаг «учитывать время»», «Миграция дат хроники», «Голая дата во входных параметрах API» и ADR времени.

### Модель 0.8.1: у рёбер остаётся только постоянный комментарий

Хронологические комментарии у связей (`owner_type: "link"`) упраздняются; постоянный комментарий ребра сохраняется и трактуется как комментарий к значению свойства-связи. Хроника остаётся у мыслей.

---

**Термин (глоссарий 10).** **Комментарий** — markdown-описание мысли или связи (`comments`). Виды: постоянный (`kind=permanent`, один на владельца, без даты) и хронологический (`kind=chronological`, с `valid_from`/`valid_to`).

Тип связи существует только в паре со своим свойством-связью (вид значения `link`) и проходит жизненный цикл через него: создаётся при создании свойства-связи, правится вместе с ним и удаляется вместе с ним ([Свойство-связь и тип связи — единый жизненный цикл](#pub-09f692ff)). `name_forward` и `name_reverse` — это имена сторон свойства: «в источнике» и «в назначении» соответственно. Хранение и иерархия при этом не меняются.

## links — направленные связи между мыслями

Связи между мыслями. **Направленные**: от источника к назначению. **Ветвимая** таблица.

| Столбец | Тип | Описание |
|---|---|---|
| `pk` | INTEGER PK AUTOINCREMENT | Суррогат |
| `id` | TEXT NOT NULL | Логический UUID |
| `layer_id` / `deleted` / `base_version` | | Слой-колонки |
| `source_id` | TEXT NOT NULL | Мысль-источник (родитель); SQL-FK снят |
| `target_id` | TEXT NOT NULL | Мысль-назначение (ребёнок); SQL-FK снят |
| `type_id` | TEXT | Тип связи; при удалении типа приложение ставит `NULL` |
| `position` | INTEGER NOT NULL DEFAULT 0 | Ручной порядок отображения — поле самой связи (решение T1): общее для всех пользователей, ветвится вместе со связью. **Пока не используется** — см. «Порядок ещё не сетевой» ниже |
| `color` / `style` / `width` | | Переопределение вида линии; `NULL` — наследуется от типа связи |
| `active` | INTEGER NOT NULL DEFAULT 1 | Актуальность |
| `marked_for_deletion` (+ `_at`, `_by`) | | Пометка на удаление |
| `version` / `created_at` / `updated_at` / `created_by` / `updated_by` | | |

Индексы: по `source_id`, `target_id`, `type_id`, `layer_id`, частичный по пометке на удаление и частичный уникальный по тройке (`idx_links_triple_live`), а также два частичных покрывающих (миграция 045, требование 7da6de92): `idx_links_target_live (target_id, type_id, source_id) WHERE deleted = 0` — EXISTS-проверки и отбор по родителю, и `idx_links_source_live (source_id, target_id, type_id, active, marked_for_deletion) WHERE deleted = 0` — обходы исходящих рёбер (BFS). Неселективные `idx_links_active`/`idx_thoughts_active` снесены миграцией 045 (ADR 6e4fef59): без статистики планировщик выбирал их и строил план O(мысли × рёбра) — см. исследование 603a8bcb.

**Порядок ещё не сетевой.** Колонка `position` заведена попутно, миграцией перехода на слои (`025_layers.sql`, там же ссылка на решение T1), но сама задача T1 не выполнена: поля нет в API связи (`link-service.ts` — «position is not part of the API Link yet»), клиент его не читает и не пишет. Фактический ручной порядок в зоне фокуса до сих пор **пер-пользовательский**: таблица `user_focus_order` и `POST /thoughts/{fid}/focus-order`. Пока T1 не закрыта, `position` у всех связей равен 0 и на выдачу не влияет.

**Запрет дублей.** Тройка «источник + назначение + тип» уникальна в пределах слоя и **только среди живых строк**: надгробие связи тройку освобождает. Иначе повторное создание той же связи в слое упиралось бы в собственное надгробие. Глобальная уникальность проверяется после разрешения слоёв.

**Нетипизированные дубли индекс не ловит** — SQLite считает `NULL` различными внутри UNIQUE. Их отвергает приложение; уберёшь эту проверку — появятся дублирующие рёбра.

**Инвариант.** Петли запрещены на уровне приложения.

**Видимость в слое.** Связь невидима, если один из её концов скрыт надгробием цепочки слоёв. Этот фильтр встроен в представление связей, а **не** дублируется в прикладных запросах.

**Стиль линии** разрешается как «собственное значение связи, иначе значение типа связи»; команда сброса в диалоге возвращает эти поля к наследованию.

### Модель 0.8.1: ребро — единственное хранение отношений

Типизированное отношение хранится только ребром; значения свойств-связей вычисляются из рёбер при чтении. `position` становится носителем порядка детей в наборе «Потомки» (ребёнок, добавленный с обратной стороны, встаёт в конец). Постоянный комментарий ребра трактуется как комментарий к значению свойства-связи («зачем именно эта ссылка»); собственных свойств, хронологии и вложений у рёбер больше нет — см. ADR «у ребра нет собственных атрибутов».

Ограничение допустимых типов значения свойства-связи здесь НЕ хранится: его источник — привязки (см. «Ограничение типов значения свойства-связи»).

**Область применения не хранится.** Свойство одинаково пригодно и мыслям, и связям; разделяет их только привязка.

**Ключи `config`** — `default_value` (**общее значение по умолчанию для стороны источников**; у скалярного свойства — единственная сторона) и `default_value_target` (**общее для стороны назначений**, только свойства-связи; отсутствие ключа — значения нет); для текстовых — `options` (**подсказка ввода, а не ограничение**) и `multiple` (несколько значений через запятую); для связей — `link_type_id` (обязателен), `show_on_map`, `blocks_target_deletion`. Legacy-ключи ограничения типов `allowed_type_ids` / `allowed_target_type_ids` / `allowed_source_type_ids` остаются частью серверного контракта (миграции, импорт, материализация зеркал — требование dde92461), но **настройкой UI не являются**: редактор свойства их не пишет и редактор значения их не читает (единственный источник ограничения — привязки).

**Смена `value_type`** в той же транзакции преобразует все значения свойства — сразу во всех типах, куда оно подключено; несовместимые удаляются. Ссылки на мысли не конвертируются. Исключение: переход между скалярной категорией (`text`/`number`/`date`/`bool`/`url`) и видом «связь» (`link`) запрещён в обе стороны — категория вида значения неизменна ([Категория вида значения неизменна: скаляры и «связь» не конвертируются](#pub-5a82c709)).

**Смена `options`, `multiple` и общих дефолтов никогда не трогает сохранённые значения** — старое значение может не соответствовать новой конфигурации.

**Переименование безопасно:** значения адресуются `id` свойства, а не его именем.

### Модель 0.8.1: вид значения «тип связи»

`value_type` пополняется значением `link`; `thought_ref` из допустимых исключается. Конфигурация свойства-связи в `config`: `link_type_id` (обязателен), `show_on_map` и `blocks_target_deletion` (флаги, по умолчанию `false`). Поля `direction` в `config` больше нет: сторона участия («источник» или «назначение») задаётся привязкой свойства к типу — `side` в `type_properties` ([Свойство-связь одно на тип связи; сторона задана привязкой](#pub-b9562306)). Значения таких свойств в `property_values` не хранятся — проекция рёбер (ADR «свойство-связь — проекция ребра»).

### Ограничение типов значения свойства-связи (0.8.2, ошибка a6513df0)

Единственный источник ограничения — **привязки свойства к типам** (`type_properties.side`), а не ключи `config`. Допустимы типы ПРОТИВОПОЛОЖНОЙ стороны привязки:

- привязка со стороны источника (`side = 'source'`; поле показывает прямое имя) → допустимые **цели** = типы привязок со стороны назначения (таблица «Типы назначений» редактора свойства);
- привязка со стороны назначения (`side = 'target'`; обратное имя) → допустимые **источники** = типы привязок со стороны источника («Типы источников»);
- противоположная таблица пуста → ограничения нет, кандидаты любые;
- типы раскрываются до поддеревьев (наследники допустимы).

Сервер вычисляет набор по реестру привязок при чтении эффективного определения (`allowed_opposite_type_ids` в `GET …/types/{id}/properties` и `etn.types.list`); клиент применяет его к живому поиску поля значения, к диалогу «выбрать» и к дефолт-пикерам редакторов типа и свойства. Это **подсказка отбора**: сохранённые значения фильтром не трогаются.

**Число целей свойства-связи не ограничено, и `config.multiple` для `link` не существует** (баг 03919899): набор целей — это живые рёбра, сервер никогда не отвергает второе и последующее ребро; редактор значения всегда работает в чип-режиме (см. «Таблица свойств редактора»). Флаг «несколько значений» осмыслен только для `text` и `url`; для `link` он в редакторе свойства не offered. Миграция 040 сохраняла старый `multiple` вербатим (legacy-маркер), но семантики он не несёт.

### Модель 0.8.2: дефолты на привязке, общие — по сторонам

Общие значения по умолчанию живут здесь, в `config` (`default_value` — источники, `default_value_target` — назначения). Дефолт конкретного типа — в `type_property_overrides` для любой привязки; при создании мысли применяется `override(тип) ?? общее стороны привязки`. Транзитивности дефолтов нет. Подробнее — ADR «дефолт свойства живёт на привязке, общие значения — по сторонам связи» (версия 0.8.2).

### Модель 0.8.3: вид значения «кросс-сетевая ссылка»

`value_type` пополняется видом «кросс-сетевая ссылка» (имя — на проработке задачи): значение адресует мысль ДРУГОЙ сети и хранится в `property_values` как скаляр — адрес `n:<network_id>#<thought_id>`; снапшот наименования цели живёт рядом, в служебном неветвимом хранилище. Конфигурация: `multiple` допустим (набор адресов); ключи `link_type_id`, `show_on_map`, `blocks_target_deletion` к виду не применяются; ограничение типов цели — тоже (типы чужих сетей несопоставимы). Ссылка на собственную сеть запрещена — для неё есть свойство-связь. Хранение значением, а не ребром — сознательное исключение из инварианта «всякая ссылка есть ребро»: через границу баз ребро невозможно (ADR «кросс-сетевая ссылка — отдельный вид значения, а не ребро»). Смена категории вида значения действует для него как для прочих скаляров.

## property_values — значения свойств мыслей и связей

Значения свойств — полиморфная EAV-таблица. **Ветвимая**.

| Столбец | Тип | Описание |
|---|---|---|
| `pk` | INTEGER PK AUTOINCREMENT | Суррогат |
| `id` | TEXT NOT NULL | Логический UUID |
| `layer_id` / `deleted` / `base_version` | | Слой-колонки |
| `owner_type` | TEXT NOT NULL | `'thought'` или `'link'` |
| `owner_id` | TEXT NOT NULL | Логический id мысли или связи |
| `property_id` | TEXT NOT NULL | Логический id свойства из справочника `properties` |
| `value_text` / `value_date` / `value_number` / `value_bool` / `value_thought_ref` | | Колонки по типам значений |
| `updated_at` | TEXT NOT NULL | |
| UNIQUE | `(owner_type, owner_id, property_id, layer_id)` | В пределах слоя |

**Значение адресуется свойством, а не привязкой к типу.** Поэтому значение переживает смену типа владельца, отключение свойства от типа и снятие избыточной привязки у потомка: оно остаётся на месте и становится значением вне типа (см. требование «Значения вне типа сохраняются»). Раньше `property_id` указывал на определение свойства конкретного типа, и та же операция значение теряла или удаляла.

**Одно значение — одна строка.** Заполняется только одна колонка значения — согласно типу свойства; остальные `NULL`. Множественные значения (строки через запятую, массивы ссылок) тоже хранятся **одной строкой** — нескольких строк на одно свойство владельца не бывает.

**Множественные ссылки на мысли.** Запись принимает массив id: пустой массив очищает значение, одиночный id нормализуется в массив из одного. Каждый id валидируется как обычная одиночная ссылка. Массив отвергается, если у свойства не выставлено множественное значение.

**Форма данных важнее флага.** При чтении массив всегда разбирается в список, а одиночный id у множественного свойства читается как список из одного элемента.

**Обратный поиск** использования и счётчик блокировок удаления (`deletion_blocks` — прежнее имя `usage_count`, задача cfc55b01) находят ссылки и внутри JSON-массивов — именно эти ссылки блокируют физическое удаление мысли. Группировка использования идёт по свойству, поэтому одно и то же поле даёт одну группу независимо от типов владельцев.

**При удалении владельца** его значения чистит приложение в той же транзакции — включая значения связей, удаляемых вместе с мыслью.

### Модель 0.8.1: значения свойств-связей не хранятся

Для свойств вида «тип связи» строки в этой таблице не пишутся: значение вычисляется из живых рёбер при чтении. Существующие значения `thought_ref` переводятся миграцией в рёбра, после чего их строки удаляются — см. сценарий «Перевод thought_ref в свойства-связи».

### Кросс-сетевые значения (0.8.3)

Значения вида «кросс-сетевая ссылка» пишутся в `value_text` адресом `n:<network_id>#<thought_id>` (набор — одной строкой, как у прочих множественных значений). Рядом со значением живёт **снапшот наименования цели** — в служебном неветвимом хранилище (точная схема — задача): обновление снапшота не создаёт теневых строк слоя, не расходует write-бюджет и не аудитируется как содержательная правка. Колонка `value_thought_ref` не задействуется: мысль своей сети вид не адресует (для неё — свойство-связь и рёбра). Обратный поиск (`usage`), счётчики блокировок удаления (`deletion_blocks`) кросс-сетевые значения не находят и не порождают.

| Столбец | Тип | Описание |
|---|---|---|

### Динамические даты и хроника (0.10.1)

Для `view = "chronicle"` определение включает период с динамическими токенами дат (`$today`, `$thought.[…]`, арифметика) и критерии целей (набор «Структур», включая значения свойств): запись проходит, если хотя бы одна её привязка удовлетворяет критериям целей. Токен хранится в `definition` без изменений и раскрывается при применении отбора. См. требования «Динамические токены дат в периоде и сохранённых отборах» и «Критерии отбора хроники: записи + цели».

## session_layers — текущий слой клиентской сессии

Умолчание «текущий слой сессии» — серверное скрытое состояние клиента. **Не ветвится**.

Сессия идентифицируется тройкой «пользователь + установка клиента + сеть»; установка передаётся заголовком запроса. Пустое значение означает вызов без заголовка — агент или скрипт.

| Столбец | Тип | Описание |
|---|---|---|
| `user_id` | TEXT NOT NULL | |
| `client_id` | TEXT NOT NULL DEFAULT '' | Идентификатор установки клиента |
| `layer_id` | TEXT NOT NULL | Текущий слой; SQL-FK нет — при удалении слоя записи переприцепляет приложение |
| `updated_at` | TEXT NOT NULL | |
| PRIMARY KEY | `(user_id, client_id)` | Одна запись на сессию |

**Все чтения и записи сессии** идут в контексте записанного слоя. Поскольку это скрытое состояние, каждый пишущий ответ возвращает **эхо текущего слоя** — чтобы состояние было обнаружимо и никто не писал в слой, о котором не знает.

**Деградация вместо ошибки.** Запись отсутствует или указывает на несуществующий слой — сессия работает в основе. Это защита от гонок: иначе удалённый слой ломал бы каждый запрос клиента.

## thought_read_metrics — счётчик чтений мыслей агентами

Агрегированный счётчик чтений мыслей через MCP-инструменты. **Не ветвится**.

| Столбец | Тип | Описание |
|---|---|---|
| `thought_id` | TEXT PK | SQL-FK снят; счётчик чистит приложение |
| `reads_count` | INTEGER NOT NULL DEFAULT 0 | Сколько раз мысль была возвращена читающими инструментами |
| `first_read_at` | TEXT NOT NULL | Момент первого чтения |
| `last_read_at` | TEXT NOT NULL | Момент последнего чтения |

Индекс по убыванию счётчика и даты — поддерживает «топ читаемых» без сортировки на лету.

**Назначение ровно одно** — аналитика для владельца базы: где мёртвые зоны и где перегретые узлы. Это **сетевой агрегат**, одинаковый для всех участников; оттого он и отделён от личных меток просмотра.

**Что инкрементит.** Получение мысли, подграф (все узлы), выборка по критериям (все хиты), полнотекстовый поиск (группы с мыслями; группа связей пропускается, там нет id мысли), чтение структуры сети.

**Что НЕ инкрементит.** Поиск упоминаний (это не «прочитано»), соседи, путь, использование, экспорт подграфа, перечень типов, лента изменений и само чтение метрик.

**Реализация.** Один батчевый упсерт на инкремент — N идентификаторов за один SQL-запрос. Дедупликация делается до SQL; несуществующие идентификаторы отбрасываются соединением с таблицей мыслей.

**Доступ.** Чтение метрик доступно любому участнику сети; запись происходит прозрачно, как побочный эффект других чтений. В журнал аудита это не попадает.

## type_properties — привязка свойства к типу

Подключение свойства из справочника `properties` к типу мыслей или типу связей. **Ветвимая** таблица, владелец полиморфный.

| Столбец | Тип | Описание |
|---|---|---|
| `pk` | INTEGER PK AUTOINCREMENT | Суррогат |
| `id` | TEXT NOT NULL | Логический UUID привязки |
| `layer_id` / `deleted` / `base_version` | | Слой-колонки |
| `owner_type` | TEXT NOT NULL | `'thought_type'` или `'link_type'` |
| `owner_id` | TEXT NOT NULL | Логический id типа |
| `property_id` | TEXT NOT NULL | Свойство из справочника `properties` |
| `side` | TEXT | Сторона участия типа в свойстве-связи: `'source'` (тип — источник рёбер) или `'target'` (тип — назначение); у скалярных привязок не задаётся |
| `required` | INTEGER NOT NULL DEFAULT 0 | Обязательность **в этом типе** |
| `position` | INTEGER NOT NULL DEFAULT 0 | Порядок отображения в этом типе |
| UNIQUE | `(owner_type, owner_id, property_id, layer_id)` | Одно свойство — одна привязка на тип |

**Природы свойства здесь нет.** Имя, тип значения, конфигурация и описание живут в `properties` и одинаковы во всех типах, куда свойство подключено. Привязка несёт только роль свойства в этом типе.

**Обязательность у каждого типа своя** и задаётся при подключении: одно свойство может быть обязательным в одном типе и необязательным в другом. Механизма переопределения унаследованной обязательности нет.

**Порядок (`position`) — тоже у каждого типа свой и общий для обеих сторон**: столбец не разделяет привязки источника и назначения, поэтому порядок задаётся для любой строки таблицы «Свойства типа», включая привязки стороны «назначение» (задача b044237d). Операции смены порядка — `reorderTypeProperties` (`PUT …/types/{id}/properties/reorder`), MCP `ontology.write type_properties[].position` — стороной не ограничены; эффективный список (`listEffectiveTypeProperties`, `etn.types.list`) сортирует привязки по `position` без учёта стороны.

**Значения от привязки не зависят.** `property_values.property_id` ссылается на свойство, а не на привязку, поэтому удаление привязки значений не трогает — они становятся значениями вне типа.

**Наследование** идёт по цепочке типов: тип видит свои привязки плюс привязки предков (см. требование «Наследование привязок по цепочке типов»).

**Историческая справка.** До 0.6.5 эта таблица была определением свойства: несла `key`, `value_type`, `config`, `description`, а уникальность держалась по `(owner_type, owner_id, key)`. Одно и то же по смыслу поле существовало в базе как отдельное определение в каждом типе, которому было нужно.

### Модель 0.8.1: привязки только к типам мыслей

`owner_type` сужается до `'thought_type'`: привязки свойств к типам связей (`owner: "link_type"`) упраздняются. Сторона участия типа в связи задаётся полем `side` привязки — `'source'` или `'target'`. Прежний запрет дублей «пара тип связи + направление уникальна» снят: направление больше не поле свойства, а вместо него действует инвариант «одно свойство-связь на тип связи» ([Свойство-связь одно на тип связи; сторона задана привязкой](#pub-b9562306)). Привязка со стороны назначения равноправна привязке источника: у обеих сторон задаются `required` и значение по умолчанию ([Привязка со стороны назначения равноправна с привязкой источника](#pub-115e44fa)). Обязательное свойство-связь проверяется сервером при записи мысли.

**Сторона и ограничение типов значения (0.8.2, ошибка a6513df0).** `side` определяет не только имя свойства-связи, но и допустимые типы его значения. Заполняется прямое имя (тип-источник) — допустимы **цели**, то есть типы привязок ЭТОГО же свойства со стороны `target`; заполняется обратное имя (тип-назначение) — допустимы **источники**, то есть типы привязок со стороны `source`. Набор считается по реестру `type_properties` (не по `config` владельца), раскрывается до поддеревьев и отдаётся клиенту в `allowed_opposite_type_ids` эффективного определения (`GET …/types/{id}/properties`, `etn.types.list`).

Переопределения значения по умолчанию и описания для привязок свойств. **Ветвимая** таблица.

| Столбец | Тип | Описание |
|---|---|---|
| `pk` | INTEGER PK AUTOINCREMENT | Суррогат |
| `id` | TEXT NOT NULL | Логический UUID |
| `layer_id` / `deleted` / `base_version` | | Слой-колонки |
| `owner_type` | TEXT NOT NULL | `'thought_type'` или `'link_type'` |
| `type_id` | TEXT NOT NULL | Тип, для которого задан дефолт или описание |
| `property_id` | TEXT NOT NULL | Свойство из справочника `properties` |
| `default_value` | TEXT NOT NULL | Дефолт привязки, JSON-кодированный; литерал `null` — дефолта на привязке нет (используется общее значение стороны из справочника) |

| UNIQUE | `(owner_type, type_id, property_id, layer_id)` | В пределах слоя |

**Одна строка держит оба переопределения.** Сброс одного аспекта не трогает второй; строка удаляется, когда сброшены оба.

Применение при создании мысли: `override(тип) ?? общее стороны привязки`.

**Описание — только унаследованных привязок, транзитивно (без изменений).** Переопределение описания действует и на подчинённые типы — пока те не переопределят своё. Описание свойства, подключённого самим типом, правится в справочнике `properties` — сразу для всех, кто это свойство подключил; сеттер описания отклоняет собственную привязку (422). Сеттер **дефолта** собственную привязку принимает.

**Зеркальные записи** (типы, покрытые `allowed_target_type_ids` без явной привязки) сюда не попадают — им доступно только общее значение для назначений.

## user_focus_order — ручной порядок мыслей в зоне фокуса

Ручной порядок мыслей зоны фокуса — только при ручной сортировке. Для родственников записи не создаются. **Не ветвится**.

| Столбец | Тип | Описание |
|---|---|---|
| `user_id` | TEXT NOT NULL | |
| `focus_thought_id` | TEXT NOT NULL | SQL-FK снят |
| `dir` | TEXT NOT NULL | `'children'` или `'parents'` |
| `thought_id` | TEXT NOT NULL | Ребёнок или родитель |
| `position` | INTEGER NOT NULL | Линейный индекс в порядке зоны |
| `updated_at` | TEXT NOT NULL | |

**Смысл `position`.** Это линейный индекс в списке зоны, упорядоченном построчно: первая мысль — 0, вторая — 1 и так далее, **без пропусков**. При построчной раскладке соответствие «визуальная ячейка = позиция» однозначно.

Удаление фокус-мысли или самой мысли-члена зоны чистит записи по обоим идентификаторам — явно приложением.

**Перспектива.** Ручной порядок переезжает в поле самой связи (общее для всех пользователей); до этого момента работает этот per-user механизм.

## user_settings системной БД — серверные настройки пользователя вне сети

Настройки пользователя уровня «пользователь × сервер», общие для всех сетей этого сервера. Лежат в системной БД `_system.db`.

| Столбец | Тип | Описание |
|---|---|---|
| `user_id` | TEXT NOT NULL FK → users.id ON DELETE CASCADE | |
| `key` | TEXT NOT NULL | Имя настройки |
| `value` | TEXT NOT NULL | JSON-значение |
| `updated_at` | TEXT NOT NULL | |
| PRIMARY KEY | `(user_id, key)` | |

**Граница.** Сюда попадает настройка пользователя, которая должна быть общей для всех устройств и всех сетей одного сервера, но не влияет на выборку данных внутри сети. Ключ сочетаний клавиш — `comment_hotkeys`.

## users — таблица пользователей сервера

Пользователи сервера. Живёт в системной БД — общая для всех мыслесетей.

| Столбец | Тип | Описание |
|---|---|---|

## Аутентификация и права доступа

Проверка, кто обращается к серверу, и что ему разрешено: пользователи, API-ключи, членство в мыслесетях и роли внутри них, административные права.

Единый механизм для всех входов: десктоп-клиент и MCP-агент авторизуются одним и тем же видом ключа, различаясь только меткой и ограничениями ключа (read-only, лимит записей).

Сами ключи на сервере не хранятся — только хеш и префикс для отображения.

## Ветвимые и неветвимые таблицы: адресация строк парой id и слоя

Содержательные таблицы сети делятся на два класса, и список закрыт: расширение требует правки спецификации слоёв.

**Ветвимые:** мысли, синонимы мыслей, связи, типы мыслей, типы связей, свойства типов, переопределения дефолтов, значения свойств, комментарии, привязки комментариев, вложения — плюс FTS-индексы (несут слой неиндексируемым полем).

Каждая ветвимая таблица:

- адресует строку парой **«логический `id` + `layer_id`»** (уникальное ограничение на эту пару); первичный ключ — суррогатный `pk`;
- несёт `layer_id` со значением по умолчанию в основу, `deleted` (надгробие — пометка «удалено в этом слое») и `base_version` — версию строки-предка на момент материализации, по которой детектируются конфликты при слиянии;
- **не имеет SQL-внешних ключей между сущностями**: ссылки идут на логический id, который в пределах таблицы больше не уникален. Это осознанная потеря целостности на уровне СУБД — целостность теперь поддерживает приложение;
- сохраняет прежние естественные ограничения уникальности, но **в пределах слоя и среди живых строк**.

**Неветвимые** (без `layer_id`, общие для всех слоёв): сама таблица слоёв, слой сессии, метрики чтений, настройки пользователя, просмотры, фокус-настройки и порядок, сохранённые отборы, закреплённые мысли, эмбеддинги — и журнал событий (он живёт в системной БД и несёт слой как атрибут полезной нагрузки).

**Следствие, о котором легко забыть.** Поскольку `id` мысли перестал быть уникальным, SQL-FK на него сняты и из неветвимых таблиц тоже — FK обязан указывать на уникальный ключ. Очистку при физическом удалении выполняет приложение.

### Дополнение (0.7.x): отборы и справочник свойств

В закрытый список ветвимых таблиц добавились `properties` (0.6.5) и `thought_type_views`; расширяется он только правкой спецификации слоёв.

Отбор типа мысли ветвится как любая ветвимая строка: заведённый в слое отбор не виден в основе; при частичном слиянии он замыкается на свой тип мысли (тип можно слить без отборов — обратное не требуется). Правка отборов разрешена только в Основе.

Справочник `properties` (имена свойств сети) ветвится с 0.6.5 и входит в замыкание частичного слияния: `type_properties.property_id`, `type_property_overrides.property_id` и `property_values.property_id` теперь ссылаются на запись `properties`, а не на саму привязку. Если в слияние включено значение/привязка, а свойство живёт только в слое, набор незамкнут и слияние отклоняется.

## Вид значения «тип связи» в реестре свойств

В реестре свойств появляется вид значения **«тип связи»** (`link`). Определение такого свойства в `config` несёт:

- `link_type_id` — тип связи, обязательный; действует инвариант «одно свойство-связь на тип связи», а не уникальность пары «тип связи + направление» ([Свойство-связь одно на тип связи; сторона задана привязкой](#pub-b9562306));
- `allowed_target_type_ids` — опциональное ограничение типов противоположной стороны; раскрывается до поддеревьев типов;
- `show_on_map` — рисовать ли связь на карте по умолчанию (по умолчанию `false`);
- `blocks_target_deletion` — блокирует ли ссылка физическое удаление цели (по умолчанию `false`).

Флаги — **настоящие JSON-булевы**, не `1`/`0`. Потребители сравнивают их строго: `config.show_on_map === true` в shared `computeDefaultCanvasLinkFilter`, `config.blocks_target_deletion === true` в доменном `listBlockingLinkProperties` и клиентском редакторе. На числе `1` строгая проверка не срабатывает — флаг молча выключается.

Поля `direction` в определении свойства нет: сторона участия (источник или назначение) задаётся привязкой — `side` в `type_properties` ([Свойство-связь одно на тип связи; сторона задана привязкой](#pub-b9562306)).

Вид значения `thought_ref` из допустимых исключается (ADR «вид значения thought_ref упраздняется»). Смена `value_type` внутри скалярной категории выполняется доменной конверсией значений, как раньше; переход между скалярной категорией и «типом связи» запрещён в обе стороны ([Категория вида значения неизменна: скаляры и «связь» не конвертируются](#pub-5a82c709)).

### Использование `show_on_map` (0.8.1, доработка)

Клиент читает `show_on_map` всех свойств-связей сети и строит из них дефолтный набор видимых на карте типов связей — см. требование «Дефолт и хранение фильтра типов связей на карте». До 0.8.1 (доработка, ошибка show_on_map не влияет на отрисовку карты мыслей) флаг нигде не потреблялся.

### Значение флагов при миграции из 0.7.x

Миграции 0.8.1 выставляют флаги так, чтобы поведение не ухудшалось относительно 0.7.x:

- **авто-свойство «голого» типа связи → `show_on_map = true`** (миграция 042, сценарий [Миграция 0.8.1: единый реестр свойств и связей](#pub-e93001ac)): рёбра этих типов рисовались на карте до обновления всегда, `false` молча убрал бы их с карты;
- **свойство, конвертированное из `thought_ref` → `show_on_map = false`, `blocks_target_deletion = true`** (миграция 040, сценарий [Сценарий: перевод thought_ref в свойства-связи](#pub-548268cf)): массовые ссылки не рисуются (ADR «вид значения thought_ref упраздняется»), но, как и прежде, блокируют удаление цели.

Дефолт `false` из списка выше — для новых свойств, заводимых пользователем в редакторе; миграции отступают от него осознанно, сохраняя прежнее поведение.

## Вид иконки мысли «icon» хранит имя каталога и проверяется сервером

Вид иконки `icon_kind='icon'` хранит в поле `icon` имя иконки каталога Lucide (kebab-case, например `search`). Сервер проверяет имя по каталогу допустимых имён (экспорт `@etn/shared`) и отвергает неизвестное имя с VALIDATION_ERROR. Значения `emoji` и `image` работают как прежде; схема БД не меняется (TEXT без CHECK). Вид наследуется вместе с иконкой. Цвет символа иконки хранится отдельным nullable-полем `icon_color` (HEX `#rrggbb`, миграция 049), независим от `fg_color`/`bg_color`; хранится при любом виде, но к рендеру значка применяется только у библиотечной `icon`; пусто — `currentColor` (цвет текста).

**Границы:** для сервера и клиента. `icon_attachment_id` к виду `icon` не применяется и сбрасывается при выборе иконки библиотеки.

**Проверка:** запись/чтение `icon_kind='icon'` с известным именем проходит оба REST-контракта; неизвестное имя — ошибка валидации; мысль с видом `icon` отображается облачком и в редакторе.

**Обоснование:** ADR [«Хранение иконки мысли вида «icon»: имя из каталога»](#pub-2b655b29).

**Актуализация 0.12.1 (задача 4105bd6a).** Добавлен цвет символа иконки `icon_color` (HEX `#rrggbb`): хранится для всех видов, рендерится только для `icon`, наследуется вместе с иконкой.

## Голая дата во входных параметрах API = сутки UTC

Если во входных параметрах операций хроники (`date_from`, `date_to`, входные даты комментов) передана «голая дата» `YYYY-MM-DD`, сервер трактует её как сутки UTC: `[00:00:00.000Z, 23:59:59.999Z]` включительно. Границы периода включительные.

Конвенция едина для агентов, REST и миграций; настроек сети для часового пояса не заводится. Полный инстанс передаётся как есть. См. ADR времени.

## Два вида файловых вложений и судьба файла при удалении

Файловое вложение бывает двух разных видов, и путать их нельзя.

1. **Загруженное на сервер.** Бинарник сохраняется в каталог вложений рядом с БД сети (единое хранилище, бэкапится вместе с БД), а путь указывает на эту копию. Так работает вставка файлов из буфера обмена в комментарии.
2. **Просто путь в ОС клиента.** Бинарник не копируется — сохраняется только ссылка на файл на машине пользователя. Так работает перетаскивание файла в зону вложений.

**При удалении вложения** сервер удаляет сохранённую копию, **только если она лежит внутри каталога вложений сети**. Пути в ОС клиента не трогаются никогда — это чужие файлы.

**При удалении владельца** вложения удаляются вместе с ним — тоже с сохранёнными копиями файлов.

**Перенос к другому владельцу** допустим правкой полей владельца; новый владелец обязан существовать.

### Слои: физический файл один на все слои

Привязка вложения (`attachments`) — ветвимая строка: удаление вложения в слое ставит надгробие привязке и не трогает основу. **Физический файл на диске общий для всех слоёв сети**; физическое удаление сохранённой копии допустимо только когда счётчик ссылок по всем слоям сети обнулился — иначе удаление в слое сломает основу и другие слои. Живые теневые строки, в том числе строки резервного слоя, удерживают вложение от физической очистки.

## Запись дня: владелец HOME, чипсы — вторичные привязки, несколько за день

«Запись дня» — хроно-запись, у которой нет ни одной смысловой мысли:

- первичный владелец — всегда HOME (корневая защищённая мысль сети);
- чипсы мыслей — вторичные привязки через `comment_targets`; количество чипсов не ограничено;
- снятие последнего чипса оставляет запись в дневнике и возвращает её в HOME (существующий инвариант автопривязки);
- на одну дату может быть несколько записей дня — ограничений «одна запись в день» нет;
- удаление мысли-чипса не удаляет запись (для этой мысли она вторична); удаление HOME (недопустимо) — отдельный случай.

Класс записи для сортировки считается по целям: только HOME — класс 0, иначе — класс 1. См. ADR HOME.

## Запись значения допускается только для подключённого свойства

Записать значение можно только для свойства, подключённого к типу владельца — собственной привязкой типа или привязкой любого из его предков. Свойство есть в справочнике, но к типу не подключено — `422 VALIDATION_ERROR`.

**Зачем запрет.** Значение адресуется свойством, а не привязкой, и без этого правила любой клиент или агент мог бы писать любое свойство любой мысли, превращая тип в фикцию, а карточку — в свалку невидимых значений.

**Следствие.** Значение вне типа — строго историческое состояние: его нельзя создать записью, оно появляется только после смены типа владельца или отключения свойства от типа. Повторная запись в такое значение (попытка «починить» его через API) тоже отклоняется — сначала подключи свойство к типу.

**Владелец без типа** видит привязки корневого типа — писать можно только их.

**Исключение с 0.8.1:** для свойств вида «тип связи» запись значения разрешена и без привязки к типу владельца — создаётся внетиповое свойство-связь у конкретной мысли (чтение помечает его `outside_type`). Для скалярных видов значений правило неизменно.

## Зеркало: ограничение типа цели порождает обратное свойство

Ограничение типов цели — это **привязки со стороны назначения**: у каждого допустимого типа назначения появляется привязка свойства-связи с `side: 'target'` и **обратным именем** (`name_reverse`). Зеркало больше не вычисляется на лету — это настоящие привязки с обязательностью и значением по умолчанию ([Привязка со стороны назначения равноправна с привязкой источника](#pub-115e44fa)), и создаются/правятся они в едином диалоге свойства (таблица «Типы назначений»). Привязка наследуется по цепочке этих типов и читается/пишется как обычное свойство-связь.

**Имя концепта и имя ключа.** «Типы назначений» — имя концепта (таблица привязок). Legacy-ключ `config.allowed_target_type_ids` (и симметричный `allowed_source_type_ids`) — исторический механизм материализации зеркал и миграций: он остаётся частью серверного контракта, но **настройкой UI не является**: редактор свойства его не пишет, а редактор значения ограничение из него не берёт. Читаемое ограничение всегда считается по привязкам противоположной стороны (ошибка a6513df0): прямое имя → допустимые цели из target-привязок, обратное имя → допустимые источники из source-привязок.

Если ограничение не задано (таблица назначений пуста), обратная сторона приходит при чтении как **внетиповое** свойство-связь с обратным именем (счётчиком, `outside_type: true`), и фильтра кандидатов у неё нет.

<a id="pub-ca2425af"></a>

## Значение свойства-связи вычисляется из рёбер при чтении

Значение свойства-связи — проекция живых типизированных рёбер мысли и не хранится в `property_values`: при чтении карточки значения вычисляются из рёбер по типу связи и стороне привязки. Запись значения создаёт/изменяет/помечает ребро (см. «Заполнение свойства-связи создаёт ребро»), но не строку значений.

Нетипизированные рёбра в свойства не проецируются — кроме структурных свойств «Родители» и «Потомков» (см. отдельное требование). Механика `outside_type` при чтении сохраняется: внетиповое свойство-связь помечается.

## Значения вне типа сохраняются

Система никогда не удаляет значение свойства сама. Значение, свойство которого не подключено к типу владельца (ни своей привязкой, ни привязкой предка), остаётся в `property_values` и называется **значением вне типа**.

**Два способа его получить:**

1. у мысли или связи сменили тип, а новый тип это свойство не подключает;
2. свойство отключили от типа — удалили привязку.

Снятие избыточной привязки у потомка, когда то же свойство подключил предок, значений вне типа **не порождает**: свойство остаётся доступным по наследству.

**Как читаются.** Чтение значений владельца возвращает и такие значения, помеченные признаком «вне типа», вместе с именем и типом значения свойства — иначе показать их пользователю нечем.

**Что с ними можно делать.** Только удалить вручную — по одному, в группе «Свойства вне типа» редактора. Подключение свойства к типу возвращает значение в обычную таблицу свойств без каких-либо действий с данными.

**Почему не удаляем автоматически.** Отключить свойство от типа или сменить тип легко по ошибке; каскадное удаление значений делало эту ошибку необратимой. До 0.6.5 `DELETE` определения свойства уносил все значения каскадом — это отменено.

**Побочный эффект.** Ссылка вне типа продолжает блокировать физическое удаление мысли-цели и видна в «Использовании» — теперь это не загадка, а видимое состояние, которое пользователь может разобрать.

## Идентификаторы сущностей — UUID v4 в текстовом первичном ключе

Идентификаторы сущностей — **UUID v4**, хранятся как TEXT из 36 символов в явном `id TEXT PRIMARY KEY`.

**Почему не целочисленные суррогаты.** Переносимость при экспорте и импорте: идентификатор остаётся осмысленным в другой мыслесети и на другом сервере, поэтому перенос не требует перенумерации и перестройки ссылок.

**Где суррогаты всё же есть.** Во внутренних связных таблицах и там, где строка адресуется парой значений: там первичным ключом служит автоинкрементный `pk`, а логический `id` остаётся UUID.

**Замечание о драйвере.** SQLite всегда имеет внутренний ROWID, но опираться на него как на идентификатор сущности нельзя: он не переживает экспорт и пересборку таблицы.

<a id="pub-09443c54"></a>

## Импорт .etnx: сопоставление мыслей и правила слияния

Импорт — это **слияние по тождеству**, а не добавление копий. Именно поэтому повторный импорт того же архива не плодит дубли.

**Порядок сопоставления мысли.**

1. Сначала **по идентификатору**: если в целевой сети есть мысль с таким же id — она берётся за основу.
2. Если не найдено — **по полному совпадению нормализованного названия**. Совпадение по синонимам и частичное — **игнорируются**.
3. Не найдено ни так, ни эдак — создаётся новая мысль.

**Diff при совпадении зависит от того, как мысль нашлась.**

- **По id:** название, синонимы, актуальность и тип берутся из импорта.
- **По названию (без совпадения id):** название сохраняется существующее, синонимы объединяются, тип сохраняется (кроме случая, когда типы не включены в выгрузку).
- **В обоих случаях** постоянный комментарий и значения свойств **перезаписываются импортом** — это теряющая операция, и пользователь должен понимать это до импорта.

**Хронологические комментарии** добавляются **без проверки дублей** — каждый импорт добавляет новые записи.

**Связи** вставляются напрямую; их концы — это идентификаторы, уже разрешённые на предыдущих шагах.

**Вложения:** для URL метаданные копируются как есть; для файловых бинарник извлекается в каталог вложений целевой сети под безопасным именем, и метаданные указывают на новый локальный путь.

**Безопасность распаковки.** Каждый извлекаемый путь проверяется на принадлежность каталогу вложений сети — защита от zip-slip (выхода за пределы каталога через `..` в именах файлов архива).

<a id="pub-141c2576"></a>

## Имя отбора уникально в пределах своего типа мысли

Имя отбора уникально среди отборов **одного типа**, сравнение регистронезависимо по `name_key`. Повторное имя — `409 DUPLICATE`.

**Совпадение с именем отбора предка — не дубль, а переопределение** (см. «Эффективный набор отборов мысли»). Поэтому уникальность проверяется по паре `(type_id, name_key)`, а не по эффективному набору: запретив совпадение с предком, мы лишили бы потомка возможности переопределить отбор.

Имя — непустая строка до 200 символов. Оно же подпись кнопки на холсте и ключ, по которому отбор адресуется в REST и MCP, поэтому переименование отбора ломает внешние вызовы по имени: агент должен перечитать список отборов, а не помнить имя между сессиями.

<a id="pub-b3a1e075"></a>

## Имя свойства уникально в пределах сети

В мыслесети не может быть двух свойств с одинаковым именем. Сравнение **регистронезависимое** и идёт по `name_key`, как у имён типов: «Путь» и «путь» — одно и то же имя.

Создание или переименование в занятое имя — `409 DUPLICATE`; в `details` возвращается id занявшего свойства, чтобы клиент мог предложить подключить существующее вместо создания нового.

**Зачем это важно.** Имя — единственный адрес свойства в MCP-записи (`properties`-карта батча `etn.thoughts.write`, ключ по имени) и в отборе по имени. Пока одно имя могло принадлежать разным определениям в разных типах, оба механизма были неоднозначны.

**Слои.** Уникальность проверяется по видимому в текущем слое состоянию справочника (`properties_v`), а не по физической таблице: в разных слоях одно и то же имя сосуществовать может, и конфликт вскроется при слиянии.

<a id="pub-38eaa15c"></a>

## Имя свойства-связи берётся из типа связи по направлению

Имя свойства-связи не хранится в определении свойства и не переопределяется на уровне типа. Оно вычисляется из типа связи по стороне привязки: у привязки со стороны источника — `name_forward`, у привязки со стороны назначения — `name_reverse`. Правка имён обеих сторон — в едином диалоге свойства «Свойство / связь»; она немедленно меняет имя свойства у всех владельцев.

Собственное `description` у свойства допустимо и уточняет его применение для конкретного типа мысли; в описание типа связи можно добавить пояснение обеих ролей.

<a id="pub-53ce7e9b"></a>

## Инварианты привязки комментариев к владельцам

Три инварианта, которые обязаны выполняться всегда.

1. **Один постоянный комментарий на владельца.** У постоянного всегда ровно одна привязка; дополнительные привязки запрещены.
2. **Хронологических — сколько угодно**, у каждого от одной до многих привязок. **Запись не может остаться без владельца**: отвязка последней привязки автоматически привязывает её к корневой защищённой мысли сети.
3. **Удаление владельца** удаляет те комментарии, где он **первичный**, вместе со всеми их привязками; а там, где он был вторичным, просто отвязывается. Это касается и связей, удаляемых каскадом вместе с мыслью.

Первый инвариант подкреплён частичным уникальным индексом в самой схеме, остальные два поддерживает приложение.

<a id="pub-42fb69a4"></a>

## Индексы idx_links_active и idx_thoughts_active удаляются при отсутствии регресса

Индексы `idx_links_active` и `idx_thoughts_active` удаляются из схемы, если perf-стенд не показывает регресса ни на одном горячем запросе.

**Проверка.** Миграция удаляет индексы; стенд до/после без регресса; миграция снабжена сторожем чистоты схемы.

<a id="pub-17cd8ccb"></a>

## Инициализация новой мыслесети

**Действующее лицо.** Пользователь, создающий мыслесеть; он же становится владельцем.

**Шаги клиента.**

1. Меню сети → «Создать сеть» → ввод имени (`display_name`) и описания.
2. `POST /api/v1/networks` — выполняются серверные шаги ниже.
3. Сеть появляется в списке «Мои сети» и открывается на мысли HOME.

**Шаги сервера.**

1. Генерирует идентификатор сети (UUID).
2. Создаёт каталог сети и внутри него каталоги вложений и снапшотов.
3. Открывает БД сети и выполняет миграции схемы. Одновременно создаётся **строка основы** в таблице слоёв — основа существует ещё до первой мысли.
4. В транзакции создаёт корневую мысль HOME: защищённая, корневая, актуальная. Слой явно не указывается — срабатывает значение по умолчанию (основа).
5. В системной БД добавляет запись в реестр сетей и членство создателя с ролью владельца.
6. Эмитит событие о создании сети.

**Результат.** Пустая сеть с единственной корневой мыслью, готовая к работе.

**Почему порядок важен.** Каталоги и основа создаются до первой записи данных; запись в системную БД делается после успешного создания БД сети — иначе в реестре появится сеть без файлов.

<a id="pub-5a82c709"></a>

## Категория вида значения неизменна: скаляры и «связь» не конвертируются

Вид значения выбирается при создании свойства и задаёт его категорию: скалярную (`text`, `number`, `date`, `bool`, `url`) или «связь».

- Переход **внутри скалярной категории** разрешён и выполняется доменной конверсией значений, как сегодня (с подтверждением и отчётом `converted`/`dropped`).
- Переход **скаляр ↔ «связь» отклоняется всегда** — `422 VALIDATION_ERROR` с внятным сообщением. Причина: значения связи живут рёбрами, а не в таблице значений — конвертация бессмысленна и сегодня молча теряет данные.
- Вид `thought_ref` недоступен в интерфейсе выбора (запрет на сервере действует с 0.8.1, [ADR: вид значения thought_ref упраздняется — всякая ссылка на мысль есть свойство-связь](#pub-4b21f468)).

Тех.проект: Свойства и связи: единый список и единый редактор.

## Миграции схемы баз данных

Каждая БД ведёт собственную таблицу применённых миграций (`id`, `name`, `applied_at`).

**Где лежат.** В репозитории, двумя наборами: отдельно для системной БД и отдельно для БД мыслесети.

**Когда применяются.** К системной БД — при старте сервера; к БД сети — при её открытии. Поэтому сеть, которую долго не открывали, догоняет схему в момент первого обращения, а не при деплое.

**Требования к самим миграциям.**

- Идемпотентность в контрольной точке (создание объектов только если их ещё нет).
- Необратимые миграции выполняются в транзакции — чтобы прерванная миграция не оставила базу в половинчатом состоянии.

Миграция — единственный допустимый способ менять схему: правка таблиц вручную рассинхронизирует сети между собой.

## Миграция 0.8.1: единый реестр свойств и связей

Действующее лицо — мигратор сервера при старте после обновления. Предусловие — резервная копия `data.db` сети (миграция необратима). В одной транзакции:

1. **Слияние встречных свойств.** Для каждой пары свойств вида «связь» с одним `link_type_id` и противоположными направлениями: выживает одна строка — привязки прямой стороны становятся привязками источника, привязки обратной — привязками назначения. Расхождения конфигов (флаги `show_on_map`/`blocks_target_deletion`, дефолты) решаются в пользу прямой стороны; отчёт миграции перечисляет расхождения.
2. **Свойство каждому «голому» типу связи.** Тип связи, у которого нет свойства в реестре, получает свойство вида «связь» с пустыми таблицами источников и назначений; существующие рёбра этого типа видны как свойства вне типа и доступны к правке. Авто-свойство получает `show_on_map = true`: до 0.8.1 рёбра этих типов рисовались на карте всегда, а флаг стал дефолтом клиентского фильтра типов связей (Дефолт и хранение фильтра типов связей на карте) — `false` молча убрал бы их с карты.
3. **Материализация зеркал.** Для каждого свойства-связи с непустым `allowed_target_type_ids` создаются настоящие привязки со стороны назначения (`required = false`, без дефолта) — поведение не меняется, но привязки становятся редактируемыми.
4. **Снятие направления.** Поле `direction` удаляется из конфигов свойств; сторона живёт только в привязках (`side`).
5. **Удаление висячих ссылок.** Свойства-связи, чей `link_type_id` указывает на несуществующий тип, получают тип связи заново по шагу 2 (с восстановлением имён из описания свойства, если возможно) — имя свойства больше не деградирует до идентификатора.

**Флаги конфига записываются настоящими JSON-булевыми** (`json('true')`/`json('false')`, не `1`/`0`): потребители сравнивают их строго (`config.show_on_map === true` в shared `computeDefaultCanvasLinkFilter`, `config.blocks_target_deletion === true` в доменном `listBlockingLinkProperties` и клиентском редакторе), а на числе строгая проверка не срабатывает. Это относится и к родственному маршруту перевода `thought_ref` (миграция 040): там `show_on_map = false` (массовые ссылки не рисуются, ADR «вид значения thought_ref упраздняется»), `blocks_target_deletion = true`.

Результат: у каждого типа связи ровно одно свойство; ни одно ребро не потеряно и не сменило типа; все имена свойств разрешаются; рёбра, видимые на карте до обновления, остаются видимыми. Потерь данных нет — расхождения конфигов при слиянии перечислены в отчёте миграции.

Родственный маршрут (перевод `thought_ref`) — [Сценарий: перевод thought_ref в свойства-связи](#pub-548268cf); принцип «необратимо, откат из бэкапа» общий. Тех.проект: Свойства и связи: единый список и единый редактор.

## Миграция дат хроники: date-only → 00:00:01Z, флаг выключен

Миграция сети приводит все хронологические комментарии к единому формату:

- значение `valid_from`/`valid_to` без времени превращается в `YYYY-MM-DDT00:00:01.000Z` — маркер «время при миграции не задавалось»;
- флаг «учитывать время» у таких записей выставляется выключенным — время в клиенте скрыто;
- после миграции хранить date-only нельзя; повторный запуск идемпотентен.

Миграция выполняется автоматически на новой сети, как прочие миграции схемы. См. ADR времени.

<a id="pub-2ae35dc0"></a>

## Миграция свойств в справочник: слияние дублей и переименование

Одноразовая миграция сети при обновлении на 0.6.5: каждое старое определение свойства типа становится записью справочника плюс привязкой к своему типу.

**Критерий слияния.** Два определения из разных типов становятся одним свойством, если совпадают все четыре признака:

1. имя (`key`), регистронезависимо;
2. тип значения (`value_type`);
3. множественность (`config.multiple`);
4. список подсказок (`config.options`); у обоих отсутствует — тоже совпадение.

Расходится хотя бы один — это разные свойства.

**`allowed_type_ids` в критерий не входит.** У сливаемых ссылочных свойств списки допустимых типов **объединяются**: ни одно уже сохранённое значение не становится недопустимым.

**Различия, которые слиянию не мешают,** переезжают в привязки и сохраняются как были: обязательность, порядок, значение по умолчанию, описание. При совпадении имён с разным регистром выживает написание раньше созданного определения.

**Переименование несовпадающих.** Одноимённые, но разные по природе свойства не могут сосуществовать при сетевой уникальности имён, поэтому получают составное имя `<имя типа>.<имя свойства>` (например, `проблема.подсистема`); для типа связи берётся имя «вперёд», при остаточном совпадении добавляется числовой суффикс. **Это мера миграции, а не соглашение об именовании:** после обновления пользователь сам приводит такие имена в порядок.

**Переадресация ссылок.** У слитых дублей на выживший идентификатор переписываются `property_values.property_id`, `type_property_overrides.property_id` и условия отбора внутри JSON `saved_filters.definition`. Это единственное место, где миграция трогает данные.

**Необратимость.** Отката нет; перед обновлением нужна резервная копия `data.db` сети.

**Следствие для агентов.** Переименованное свойство меняет ключ, по которому его пишут в MCP (поле `properties` батча `etn.thoughts.write`); после миграции инструкции сети и поле `conventions` надо проверить на упоминания старых имён.

<a id="pub-12fccde9"></a>

## Множественное свойство подставляется списком и допустимо только в операциях со списком

Токен свойства с `config.multiple = true` подставляется **списком значений**, а не одним значением.

**Где допустим.** Только в условиях «в списке» и «не в списке». Скалярные операции (равно, не равно, содержит, больше, меньше) со списочным токеном — `422 VALIDATION_ERROR` при сохранении отбора.

**Почему не «первое значение».** Тихое взятие первого элемента даёт отбор, который работает на тестовой мысли с одним значением и незаметно врёт на мысли с двумя. Ошибка при сохранении дешевле, чем правдоподобный неверный список.

**Пустой список** (свойство есть, но значений нет) — случай неразрешимого токена: пустой результат с пояснением, а не «в списке из ничего».

Одиночное свойство в операции «в списке» допустимо и нормализуется в список из одного элемента — так же, как это делает запись значений `thought_ref`.

<a id="pub-23e0f78e"></a>

## Мысль без типа: отборы корневого типа действуют, добавление отбора запрещено

У мысли без типа эффективный набор отборов — отборы **корневого типа**. Это продолжение общего правила: настройки корневого типа (иконка, цвета, привязки свойств) и так применяются к мыслям без типа.

**Добавление отбора с холста запрещено.** Кнопка «+» у мысли без типа недоступна: приписывать отбор некуда — корневой тип нельзя назначить мысли, и предлагать его как владельца нового отбора значит менять правила для всей сети из-под безымянной мысли. Отбор корневому типу заводится осознанно, в редакторе типов.

Переключение уже существующих отборов корневого типа при этом работает, как у любой другой мысли: кнопки видны, результат исполняется, `$thought.type` разрешается в пустое значение (и делает условие по типу неразрешимым — см. соответствующее требование).

<a id="pub-0da6f02a"></a>

## Наследование визуального стиля мысли от её типа

Облачко мысли может брать визуальные настройки от своего типа. Именно так они разрешаются:

- **иконка** — собственная, иначе иконка типа, иначе дефолт приложения. Вместе с иконкой наследуются и **её вид** (эмодзи / картинка / имя иконки библиотеки при `icon_kind='icon'`), и **цвет символа** (`icon_color`, HEX `#rrggbb`): унаследованная от типа иконка берёт цвет того типа, что её дала, а собственная иконка мысли — свой цвет, иначе цвет типа, иначе прежнее поведение (`currentColor`). Пусто (`NULL`) = наследовать;
- **цвета** — `NULL` → цвет типа → дефолт приложения;
- **шрифтовые флаги** — собственное значение, иначе значение типа, иначе «выключено».

**Хранение и контракт — разные вещи.** В БД шрифтовые поля хранят 0/1, а признак «ручное ли поле» живёт в bitmap-колонке. В API же сервер отдаёт их как `boolean | null`, где `null` = «наследуется»: при чтении пара «значение + бит» сворачивается в три состояния, при записи `null` сбрасывает бит.

**Смена типа мысли** меняет только те визуальные поля, которые не были заданы вручную. Свойства прежнего типа **скрываются, но их значения не удаляются**: вернёшь прежний тип — значения снова видны (они привязаны к определению свойства, которое не удалялось).

**Сброс.** Команда сброса в диалоге настроек убирает все ручные настройки сразу — мысль снова отображается стилем своего типа.

**Актуализация 0.12.1 (задача 4105bd6a).** Наследование распространено на новый **цвет символа иконки** (`icon_color`): он наследуется по цепочке типов ВМЕСТЕ с иконкой (LEVEL-21). Цвет хранится при всех видах, к рендеру применяется только библиотечной `icon`.

## Наследование привязок по цепочке типов

Каждый тип наследует **все привязки своих предков** вплоть до корневого — привязки обеих сторон, источника и назначения. Эффективный список свойств типа собирается по цепочке «корень → … → сам тип», привязки каждого уровня добавляются в общем порядке.

**Одно свойство — одна привязка в цепочке.** Свойство, уже подключённое предком, потомку подключать не нужно: оно у него и так есть.

**Подключение свойства к родителю снимает избыточные привязки у потомков.** Когда тип подключает свойство, которое уже подключено каким-то из его потомков, привязки этого свойства у всех типов-поддерева удаляются в той же транзакции. Значения мыслей и связей при этом не меняются вообще: они ссылаются на свойство, а не на привязку, и свойство остаётся доступным — теперь по наследству. Это заменяет прежний запрет (`409 DUPLICATE` при совпадении имени в цепочке или поддереве), который был нужен, пока определение принадлежало типу.

**Что можно и чего нельзя подчинённому типу.**

- Природу унаследованного свойства (тип значения, конфигурацию, имя) менять нельзя: она одна на всю сеть и правится в справочнике — сразу для всех типов, куда свойство подключено.
- Обязательность унаследованной привязки потомок не переопределяет.
- Можно переопределить **значение по умолчанию** и **описание** — для себя и своего поддерева.

**В редакторе типа** видны и редактируются только **собственные** привязки; унаследованные показываются отдельной секцией — обеих сторон, источника и назначения. Правка обязательности унаследованной привязки по-прежнему недоступна, значение по умолчанию и описание переопределяются. Привязки подчинённых типов не видны и не учитываются.

**Владелец без типа** видит свойства корневого типа: запись значений для него резолвит привязки по цепочке из одного корня.

**Повторное подключение к тому же типу (0.8.2, ошибка 0bfd7180).** Подключить свойство, которое этот же тип уже несёт, — не ошибка: привязка обновляется на месте (тот же `id`, роль из запроса, порядок без явного `position` не переезжает). Прежний `409 DUPLICATE` на повтор снят — он ломал сценарий «создал свойство из диалога выбора → выбрал его → записал тип». `409 DUPLICATE` остаётся только для привязки предка (см. выше — свойство и так наследуется).

**В слоях (13-layers.md §13).** Наследование считается по **разрешённой** цепочке типов (правило «ближайший слой побеждает»), а не по сырым строкам физической таблицы: чтение типов, привязок и отборов идёт через представления `thought_types_v` / `type_properties_v` / `thought_type_views_v`. Copy-on-write распространяется на `thought_types`, `link_types`, `type_properties`, `type_property_overrides` наравне с содержательными таблицами — иначе типичное «добавить тип и свойство» в слое сразу стало бы видно всем. Следствие для слияния: мысль в основе не может ссылаться на тип, созданный только в слое, поэтому `type_id` мысли и связи участвуют в замыкании частичного слияния (см. «Типы и справочник свойств входят в замыкание частичного слияния»).

## Неактуальность, пометка на удаление и надгробие слоя — три разных механизма

Три соседних, но разных механизма — путать их нельзя.

| Механизм | Смысл | Влияет на существование? | Обратимо? |
|---|---|---|---|
| Неактуальность (`active = 0`) | «Не учитывать при определении актуального» | Нет — элемент истории | Да, в любой момент |
| Пометка на удаление (`marked_for_deletion = 1`) | Намерение удалить при первой возможности | Нет — строка полноценно читается и редактируется | Да, возвратом из корзины |
| Надгробие (`deleted = 1`, только внутри слоя) | Copy-on-write механизм слоёв, а не пользовательская корзина | Да — строка не видна в этом слое | Только через слияние или удаление слоя |

**Корзины как хранилища не существует.** Пометка на удаление — обычный столбец строки; список корзины — это выборка помеченных среди видимых строк сети.

**Пометка ветвится** вместе со строкой, как любое другое поле: поставленная в слое, она не затрагивает основу, пока слой не слит.

<a id="pub-b7fdab20"></a>

## Неразрешимый токен даёт пустой результат с пояснением, а не отбрасывается

Токен считается неразрешимым, если у мысли-контекста нет запрошенного свойства или его значение пусто (а также если свойство отключили от типа после сохранения отбора).

**Что происходит.** Отбор возвращает пустой результат и признак, что условие не разрешилось, с указанием токена. Клиент показывает это текстом в нижней зоне («Отбор не выполнен: у мысли не заполнено свойство „версия“»), агент получает то же в ответе инструмента.

**Чего делать нельзя.** Молча выбрасывать условие из отбора. Отбор «Работы версии» без условия по версии превращается в «все работы сети» — пользователь увидит правдоподобный, но неверный список и заметит это не сразу. Пустой результат с причиной честнее полного результата без причины.

Это не ошибка запроса: код ответа успешный, отбор просто ничего не нашёл. Ошибкой (`422`) неразрешимость становится только при сохранении отбора, когда токен вообще не существует в пространстве имён.

<a id="pub-93d76ff0"></a>

## Отборы типов ветвятся слоями и замыкаются на свой тип при частичном слиянии

`thought_type_views` — ветвимая таблица: отбор виден в слое, где создан, и во всех его потомках, а в основу попадает только слиянием.

**Замыкание частичного слияния.** Взяли в слияние строку отбора — обязаны взять и её тип мысли, если тот создан в том же слое. Обратное не требуется: тип можно слить без своих отборов, они останутся в слое.

**Разрешение по цепочке слоёв** — как у прочих ветвимых таблиц: строка ближнего слоя перекрывает строку основы по `id`, надгробие скрывает отбор основы, не удаляя его.

**Наследование по дереву типов и наследование по слоям — разные механизмы,** их нельзя путать: сначала слой решает, какие строки видимы, и только потом из видимых собирается эффективный набор по цепочке типов.

Следствие для агентов: отбор, заведённый в слое версии, не виден пользователю в основе, пока ветка не ушла в `main`. Заводить отборы «на будущее» в основе нельзя — это описание невыпущенного поведения.

**Запрет правки в не-основных слоях (0.7.4, задача `d9b66617-…`).** Создание, изменение и удаление отборов типов разрешены только в Основе; в любом не-основном слое — запрещены. Причина: отборы — сервисный инструмент общего пользования, а не предмет для «песочниц» и защиты от неполных данных (один и тот же отбор должен работать у всех, кто видит мысль в фокусе, независимо от того, в каком слое они сейчас). В не-основном слое разрешены только просмотр и исполнение через `etn.views.run`. Клиент обеспечивает это в `client/src/renderer/canvas/focus-filter-strip.ts` и `client/src/renderer/screens/thought-type/views-tab.ts` (через `isInBaseLayer()` из `client/src/renderer/lib/layer-base.ts`) — в слое изменений кнопки «+», «Изменить», «Удалить» и переключатель «по умолчанию» не открывают диалог правки, а показывают понятное сообщение с предложением переключиться в Основу. Серверная валидация в `etn.ontology.write` для `type_views[]` в не-основе сохраняется как защита от агентов в обход клиента.

## Полнотекстовые индексы FTS5 и триггеры их синхронизации

Полнотекстовый поиск сети строится на виртуальных таблицах FTS5.

**Три индекса:**

1. По именам мыслей и синонимам;
2. по текстам комментариев мыслей (и постоянных, и хронологических);
3. по заголовкам и текстам комментариев связей.

Каждая таблица хранит идентификатор владельца и слой как **неиндексируемые** поля плюс сам текст.

**Четвёртая группа результатов — «найдено в хронологии» — отдельного индекса не имеет**: это фильтр по виду комментария поверх текстовых индексов.

**Токенайзер** `unicode61` с удалением диакритики — корректно работает с кириллицей и латиницей без дополнительных словарей. Стемминга нет — поиск идёт по словоформам.

**Синхронизация — триггерами БД, а не приложением.** Правка мысли обновляет индекс имён (текст = заголовок плюс синонимы **того же слоя**, только живые — надгробия в агрегат не попадают); правка синонима обновляет строку его мысли в том же слое; правка комментария — соответствующий текстовый индекс. **Меняешь схему этих таблиц — проверяй триггеры.**

**Слои и ранжирование.** Индексы автономные (не external-content), пересборки не требуют. FTS сначала **ранжирует**, а видимость слоя фильтруется поверх результата с дедупликацией по логическому id.

## Полнотекстовый поиск (FTS5)

Поиск по текстам сети на виртуальных таблицах FTS5: имена и синонимы мыслей, тексты комментариев мыслей и связей.

Индексы поддерживаются триггерами БД, а не приложением — правка схемы мыслей, синонимов или комментариев требует проверки триггеров.

Поиск работает **в пределах одной сети**: общего индекса по нескольким мыслесетям нет и на MVP не планируется. Семантический (векторный) поиск в подсистему не входит — задел оставлен только в схеме данных.

С 0.7.5 все три индекса — `tokenize = 'trigram case_sensitive 0'` (был «`unicode61`», миграция `038_search_trigram.sql`, ошибка 0258fd9d): искомое вхождение в любой части слова (не только префикс), с встроенным кейс-фолдингом кириллицы. Ограничение: ≥3 символа на фрагмент запроса — коротише индекс не ищет; `by_names` покрывает такие случаи LIKE по `title_norm`/`synonym_norm`, у `by_texts`/`by_links`/`by_chrono` такого fallbackа нет (см. `GET /search`).

**В слоях (13-layers.md §9).** FTS-таблицы несут `layer_id UNINDEXED` (миграция 025), автономны (не external-content) и синхронизируются триггерами, поэтому слоистость не потребовала пересборки индекса. Поиск выполняется в контексте слоя сессии: FTS5 сначала ранжирует, затем результат фильтруется по видимости слоя и дедуплицируется по логическому id — см. требование «Поиск в контексте слоя: фильтрация видимости и дедупликация по логическому id».

## Привязка со стороны назначения равноправна с привязкой источника

Привязка свойства-связи к типу мысли со стороны назначения — настоящая привязка, а не вычисляемое зеркало. В ней задаются:

- **обязательность**: мысль этого типа без живого входящего ребра данного типа связи получает предупреждение о незаполненном обязательном свойстве — тот же механизм, что у стороны источника (Обязательное свойство-связь проверяется сервером при записи); запись не блокируется;
- **значение по умолчанию**: набор мыслей-**источников** (`string[]`); при создании мысли этого типа создаются входящие рёбра от них — зеркальное отражение правила Набор целей как дефолт свойства-связи применяется созданием рёбер, включая молчаливый пропуск неприменимых целей и отсутствие маскировки предупреждения.

Привязки назначения наследуются по цепочке типов наравне с привязками источника ([Наследование привязок по цепочке типов](#pub-216ab5b7)). Снятие привязки назначения не удаляет рёбра: они остаются у мыслей и видны как свойство вне типа.

Тех.проект: Свойства и связи: единый список и единый редактор.

<a id="pub-31d2d70f"></a>

## Разделение хранения: системная БД и отдельная БД на каждую мыслесеть

Хранение разделено на две зоны, и это разделение обязательно:

- **Системная БД** (одна на сервер) — глобальные данные: пользователи, API-ключи, реестр мыслесетей, членство и роли, серверные настройки пользователей, журнал аудита.
- **Отдельная БД на каждую мыслесеть** — всё содержимое сети: мысли, связи, типы, свойства, комментарии, вложения, поисковые индексы.

**Зачем.** Сеть целиком умещается в один файл: её можно скопировать, перенести или удалить независимо от остальных, а write-lock одной сети не тормозит работу в других.

**Режим работы обеих БД.** SQLite в режиме **WAL** с включёнными внешними ключами (`PRAGMA foreign_keys = ON`).

**Следствие для ссылок.** Ссылка из одной зоны в другую не может быть SQL-внешним ключом — такие связи валидирует приложение.

## Раскладка каталога данных сервера

Все данные сервера лежат под одним настраиваемым корнем (по умолчанию `/var/lib/etn/`):

```
<корень данных>/
├── _system.db            ← системная БД
├── _system.db-wal
├── _system.db-shm
└── networks/
    ├── <network-uuid>/
    │   ├── data.db       ← данные мыслесети
    │   ├── data.db-wal
    │   ├── data.db-shm
    │   ├── attachments/  ← сохранённые файлы вложений
    │   └── snapshots/    ← экспорт-снапшоты и бэкапы
    └── <network-uuid-2>/
```

Правила:

- Имя каталога сети равно её `id` (UUID) и **неизменно**; отображаемое имя сети меняется свободно и на путь не влияет.
- Все сети лежат в одном `networks/`; шардинга по дискам нет.
- `attachments/` — единое хранилище загруженных на сервер файлов, бэкапится вместе с БД сети.
- Каталоги `attachments/` и `snapshots/` создаются при создании мыслесети, а не по требованию.

<a id="pub-9d688725"></a>

## Резервное копирование сервера и снапшот мыслесети

**Действующее лицо.** Администратор сервера.

**Полный бэкап.**

1. Выполнить `PRAGMA wal_checkpoint(TRUNCATE)` — иначе часть данных останется в WAL и копия будет неполной.
2. Скопировать системную БД и каталоги сетей целиком, включая файлы WAL/SHM и каталог вложений.

**Снапшот одной мыслесети.**

Выполнить `VACUUM INTO` в файл внутри каталога снапшотов сети — получается единый файл без WAL, пригодный к переносу.

**Чего не делать.** Копировать `data.db` без контрольной точки и без сопутствующих файлов — такая копия может оказаться несогласованной.

**Отличие от экспорта.** Бэкап и снапшот работают с файлами БД целиком и сохраняют всё, включая per-user состояние и слои; экспорт — это выборочный срез графа для переноса в другую сеть.

<a id="pub-fcdf78f9"></a>

## Свойства «Родители» и «Потомки» объявлены на корневом типе и наследуются

Структурные (нетипизированные) связи выражаются двумя свойствами-связями на корневом типе: **«Родители»** (направление `in`) и **«Потомки»** (направление `out`), тип связи — без типа. Свойства наследуются всеми типами и присутствуют у каждой мысли. Обязательными они НЕ объявляются: у корневой мысли родителей нет, предупреждение там неуместно.

Это исключение из правила «одно свойство-связь на тип связи» ([Свойство-связь одно на тип связи; сторона задана привязкой](#pub-b9562306)): у структурных свойств типа связи нет — их различает именно сторона (направление). В едином списке «Свойства и связи» они показываются системными строками без правки и удаления.

**Порядок детей** задаётся позицией значения в наборе «Потомки»; носитель порядка — прежний `position` ребра. Ребёнок, добавленный с обратной стороны (через своё свойство «Родители»), встаёт в конец списка у родителя.

Поверх «Родителей»/«Потомков» прежние нетипизированные рёбра работают без изменений: `direction` исчезает из обихода, включая структурные связи. Структур может быть несколько — каждая своим типом связи; обход выбирает нужную фильтром по типам.

<a id="pub-09f692ff"></a>

## Свойство-связь и тип связи — единый жизненный цикл

Свойство вида «связь» и его тип связи создаются, правятся и удаляются **одним действием**:

- **Создание** свойства вида «связь» создаёт тип связи; имена «в источнике» и «в назначении» вводятся в том же диалоге и пишутся в `name_forward`/`name_reverse`.
- **Правка** имён сторон, описания, оформления линии и родительского типа связи правит тип связи; отдельного редактора типа связи не существует.
- **Удаление** свойства удаляет и тип связи — принудительно, без требования разобрать рёбра: рёбра не удаляются, а теряют `type_id`, становясь структурными связями «Родители/Потомки», и появляются в иерархии мыслей; постоянные комментарии рёбер сохраняются. Диалог подтверждения показывает число рёбер прямым текстом: «N связей станут структурными связями „Родители/Потомки“ и появятся в иерархии мыслей».

Прямое создание и удаление типа связи через CRUD типов связей (`POST/DELETE /link-types`) перестаёт быть пользовательской операцией; эндпоинты остаются служебными (миграции, MCP-обслуживание). Для скалярных свойств прежнее правило блокировки удаления действует без изменений (#c0dd62e2).

Тех.проект: Свойства и связи: единый список и единый редактор.

<a id="pub-b9562306"></a>

## Свойство-связь одно на тип связи; сторона задана привязкой

В реестре свойств сети на один тип связи существует **ровно одно** свойство вида «связь». Исключение — структурные «Родители» и «Потомки»: у них типа связи нет, они остаются двумя системными строками.

Направление (`direction: out|in`) **упразднено** как поле `config` свойства. Сторона, с которой тип мысли участвует в связи, задаётся привязкой: привязка свойства к типу выполняется **со стороны источника** либо **со стороны назначения** (`type_properties.side`).

Инвариант чтения: живое типизированное ребро ложится ровно в одно свойство — у источника по привязке источника, у цели по привязке назначения; если у типа мысли привязки нет, ребро видно как свойство вне типа с именем по стороне.

Попытка создать второе свойство вида «связь» на тот же тип связи отклоняется — `409 DUPLICATE` с `conflict_property_id` в деталях.

<a id="pub-35218826"></a>

## Символы подстановки в синонимах и правила сопоставления

Синоним может содержать `*`. Правила сопоставления жёсткие:

- `*` означает **любое количество символов в пределах одного слова** и не пересекает границу слова.
- Граница слова — начало/конец текста либо любой символ, не являющийся буквой, цифрой или подчёркиванием. Поэтому имя в кавычках, скобках или после знака пунктуации всё равно находится.
- Слова многословного синонима должны встречаться **подряд и в заданном порядке**; отличаться могут только части слов на месте `*`.

Пример: синоним `Петров* Игор*` соответствует «Петрова Игоря», но не «Петрович передал Игорю».

**Главное различие двух сценариев, где применяются подстановки:**

- при **поиске дублей** паттерн сопоставляется со **всем** введённым названием мысли: синоним `грабл*` — дубль для ввода «грабли», но не для фразы «не наступать на грабли»;
- при **поиске упоминаний** — с фрагментом текста комментария: слово «грабли» внутри фразы упоминание находит.

Не учесть это различие — значит либо завалить пользователя ложными дублями, либо потерять большую часть упоминаний.

**Оговорка гейта записи (0.10.3, задача bf9f46bd).** Правила сопоставления выше описывают матчинг `find_duplicates` (информационный). Гейт `etn.thoughts.write` строже: wildcard-маска и частичное совпадение НЕ блокируют создание новой мысли (даже совпавшую с маской целиком) — они лишь возвращаются кандидатами в `duplicate_candidates`; блокирует только точное совпадение названия (или литерального синонима) при том же типе.

<a id="pub-d9b5901c"></a>

## Слои изменений (подсистема)

Механизм copy-on-write-веток внутри мыслесети: содержательные строки живут в контексте слоя, изменение в слое материализует теневую строку, не трогая основу; слой можно слить в родителя или удалить целиком.

Подсистема сквозная — она меняет адресацию строк во всех ветвимых таблицах (пара «логический id + `layer_id`»), правила чтения (ближайший слой цепочки), удаления (надгробия вместо физического DELETE) и полнотекстового поиска.

Полная модель слоёв — отдельная спецификация; модель данных отражает её только в схеме БД.

<a id="pub-bc312576"></a>

## Соединение выборок открывается с единым профилем прагм SQLite

Соединение, обслуживающее выборки, открывается с единым профилем прагм: `cache_size=-65536`, `mmap_size=268435456`, `temp_store=MEMORY`, `synchronous=NORMAL`, конечный `busy_timeout`; WAL включён.

**Проверка.** Профиль задаётся в одной точке открытия соединения и действует и для главного потока, и для reader-воркеров.

<a id="pub-9ea49391"></a>

## Состояние уровня «пользователь × мыслесеть» и его синхронизация

Часть данных в БД сети принадлежит не сети целиком, а **конкретному пользователю в этой сети**: настройки, метки просмотра, сортировки и ручной порядок зон, сохранённые отборы, закреплённые мысли.

**Обязательное свойство:** эти данные одинаковы на всех клиентах одного пользователя и синхронизируются между ними событиями real-time, адресованными пользователю, а не всей сети. Открыл клиент на другом компьютере — видит те же закрепления и те же отборы.

**Граница с локальным состоянием клиента.** То, что привязано к конкретной установке (геометрия окна, текущий фокус, черновики), хранится локально и сюда не попадает.

**Ни одна из этих таблиц не ветвится** по слоям изменений: личное состояние пользователя не зависит от того, в каком слое он работает. При удалении мысли соответствующие записи чистит приложение — SQL-FK на мысль сняты.

**Переносу между сетями не подлежит.** Экспорт не включает эти данные: в чужой сети они бессмысленны.

## Сценарий: перевод thought_ref в свойства-связи

Маршрут перевода рабочих данных на единую модель связей (миграция сети).

1. **Сбор перечня.** По каждой сети — все свойства вида `thought_ref`, привязки с `owner: "link_type"`, значения на рёбрах (`owner_type: "link"`), хронологические комментарии и вложения рёбер. Каждому свойству-ссылке подбирается тип связи: из существующих или новый с осмысленной парой имён (прямое/обратное) — имя обратного станет видимым в карточках целей.
2. **Прогон (dry-run).** Отчёт без применения: что станет рёбрами (сколько значений), какие значения не резолвятся (цель удалена/в корзине/в другой сети), что будет потеряно (хроника/вложения/свойства рёбер) — пользователю показывают потери явно, молча стирать нельзя.
3. **Применение.** Одна транзакция на сеть: значения → рёбра с флагами (`show_on_map = false` для массовых, `blocks_target_deletion = true` где блокировал `thought_ref`), строки `property_values` с `thought_ref` удаляются, судьба потерь — по решению из шага 2 (перенос смысла в комментарий / выделение сущности / потеря).
4. **Откат.** До фиксации результата — восстановление из бэкапа сети; после — только вперёд.

Проверка: `copy_subtree` переносит подграф без потери ссылок (резолв рёбер по типу связи, затем по имени); отборы «Актуальные работы»/«Выполнено» и `usage` карточек работают через рёбра.

Следующая миграция реестра (слияние встречных свойств, свойства «голым» типам связей, материализация зеркал) — [Миграция 0.8.1: единый реестр свойств и связей](#pub-e93001ac).

## Токены отбора разрешаются сервером относительно мысли-контекста

Отбор типа исполняется **относительно конкретной мысли** — мысли-контекста. Перед выполнением сервер заменяет токены в значениях условий на фактические данные этой мысли и текущий момент.

**Пространство имён закрыто и вычислимо.**

| Токен | Значение |
|---|---|
| `$thought` | id мысли-контекста (синоним `$thought.id`) |
| `$thought.title` | название |
| `$thought.synonyms` | синонимы одной строкой |
| `$thought.type` | id типа мысли |
| `$thought.active` | актуальность |
| `$thought.author` / `$thought.editor` | автор и последний редактор |
| `$thought.created` / `$thought.updated` | даты создания и изменения |
| `$thought.[<Имя свойства>]` | значение свойства, которое даёт мысли её тип |
| `$today` / `$now` | текущая дата / текущий момент |
| `$user` | пользователь, от имени которого исполняется отбор |

**Скобки у свойств обязательны.** Имя свойства — произвольный текст сети, с пробелами и любым регистром, и оно может совпасть с именем поля: `$thought.type` — тип мысли, `$thought.[type]` — свойство с именем «type».

**Арифметика — только над датами и только в днях:** `$today-7d`, `$thought.[Плановый срок]+3d`. Ничего другого грамматика не допускает (ADR «Токены отбора — закрытое пространство имён»).

**Разрешение — на сервере, а не на клиенте.** Иначе результат у человека на холсте и у агента через MCP разойдётся. `$user` подставляется по владельцу ключа, которым исполняется отбор, — у разных агентов он законно разный.

**Валидация при сохранении.** Неизвестное поле, свойство, не подключённое к типу отбора, или арифметика над не-датой отвергаются `422` в момент сохранения отбора, а не при первом исполнении.

<a id="pub-b0c7a57c"></a>

## Требование: activity_log — состав записи

Каждая операция изменения сущности сети (создание, правка, удаление, пометка на удаление, восстановление) пишет в `activity_log` одну запись: автор — исполнитель операции, `entity_title` — краткий снимок описания на момент события («мысль без типа, "Название"», «связь A → B», «тип мысли "задача"»; лимит 256 символов).

**Не пишутся:** события захвата (`edit.*`), события per-user состояния (audience=user), операции чтения.

Запись ведётся сервером в тех же местах, где пишется `event_log`; сбой записи журнала не отменяет бизнес-операцию (журнал — вспомогательный).

<a id="pub-e6d4165e"></a>

## Требование: колонки авторства у редактируемых сущностей

У каждой редактируемой сущности сети есть колонки `created_by`, `updated_by` (TEXT, id пользователя), `created_at_ms`, `updated_at_ms` (INTEGER, миллисекунды). Заполняются сервером: первые два — при INSERT, вторые — при каждом UPDATE.

**Охват таблиц:** `thoughts`, `links`, `thought_types`, `link_types`, `properties`, `comments`, `attachments`, `layers` и таблицы значений свойств (правка значения = правка мысли/связи-владельца).

**Приравнивание:** изменение значений свойств мысли/связи обновляет `updated_by`/`updated_at_ms` мысли/связи; изменение настроек типа (включая подключение свойств) — типа.

**Отображение:** пользователю даты показываются с точностью до секунды; миллисекунды используются только для сортировки.

**Существующие поля** `created_at`/`updated_at` (ISO TEXT) сохраняются для совместимости.

<a id="pub-c6fd9d80"></a>

## Требование: миграция авторства — backfill первым пользователем

Миграция добавляет колонки авторства (см. «колонки авторства») и заполняет их для существующих строк: `created_by` = `updated_by` = id **первого пользователя сервера** (`is_first_user=1`; по ADR «Защищённые сущности» он же первый администратор — root инсталляции). Миллисекундные даты вычисляются из существующих `created_at`/`updated_at` (нет — из времени миграции).

После миграции в сети не остаётся строк с пустым авторством; «неизвестный автор» в UI не появляется.

<a id="pub-7263e565"></a>

## У типа мысли не более одного отбора по умолчанию

В пределах одного типа мысли отбор с `is_default = 1` может быть только один; допустимо и ни одного.

**Кто держит инвариант.** Сервер: пометка отбора «по умолчанию» снимает пометку с прежнего отбора того же типа в той же транзакции. Попытка выставить второй параллельным запросом не отвергается ошибкой, а переносит пометку — иначе интерфейс заставлял бы пользователя сначала снимать её вручную.

**Что делает клиент.** При переводе мысли в фокус нижняя зона открывает отбор по умолчанию из эффективного набора. Помеченного нет — открываются потомки («Потомки» — всегда первая кнопка и поведение по умолчанию при отсутствии пометки).

Ограничение действует на уровне типа, а не эффективного набора: у предка и у потомка могут стоять свои пометки, и это не конфликт — сработает пометка потомка.

<a id="pub-23737403"></a>

## Удаление мыслесети администратором

**Действующее лицо.** Только администратор системы — владелец сети такими правами не обладает.

**Шаги.**

1. Контрольная точка WAL с усечением на БД сети.
2. Закрытие соединения с этой БД.
3. Удаление каталога сети целиком — вместе с вложениями и снапшотами.
4. Удаление записи из реестра сетей в системной БД; каскад убирает членство и серверные настройки пользователей по этой сети.
5. Запись в журнал аудита.

**Почему шаги 1–2 обязательны.** Без контрольной точки и закрытия соединения удаление каталога может оставить заблокированные файлы или упасть на половине.

**Операция необратима.** Вернуть сеть можно только из резервной копии.

<a id="pub-c0dd62e2"></a>

## Удаление свойства блокируется привязками и значениями

Свойство удаляется из справочника только тогда, когда оно **ни к чему не подключено и нигде не заполнено**. Есть хотя бы одна привязка или хотя бы одно значение (в том числе значение вне типа) — удаление отклоняется.

Отказ возвращает в `details` два счётчика: сколько типов свойство подключили и сколько значений заполнено, чтобы клиент мог объяснить пользователю, что именно держит свойство.

**Порядок для пользователя:** отключить свойство от всех типов → разобрать оставшиеся значения в группе «Свойства вне типа» → удалить свойство. Сервисных команд пакетной очистки в 0.6.5 нет.

**Почему не удаляем каскадом.** Свойство теперь общее: удаление затронет все типы сразу, а не один, как раньше. Цена ошибки выросла — выросла и защита.

**Исключение — свойство-связь (0.8.1).** Для свойства вида «связь» удаление разрешено и при живых рёбрах ([Свойство-связь и тип связи — единый жизненный цикл](#pub-09f692ff)): вместе с ним принудительно удаляется тип связи, рёбра не удаляются, а теряют `type_id` и становятся структурными; подтверждение показывает число затронутых рёбер. Правило блокировки выше остаётся для скалярных свойств.

<a id="pub-91ba5b3f"></a>

## Флаг «учитывать время»: хранение и влияние на показ

У каждой хронологической записи есть булев флаг «учитывать время». Он:

- хранится в самой записи и синхронизируется между клиентами пользователя как прочие поля;
- управляет только показом и правкой времени в клиенте — флаг включён: видны и редактируются часы:минуты; выключен: показывается только дата;
- НЕ влияет на формат и значения `valid_from`/`valid_to` — они всегда полные UTC-инстансы;
- у новых записей по умолчанию выключен; включение происходит при явной правке времени пользователем.

Правка часов:минут не меняет секунды и миллисекунды записи. См. ADR времени.

## Формат .etnx — архив переноса мыслей

Файл переноса мыслей между разными мыслесетями и компьютерами — zip-архив с расширением `.etnx`.

**Структура архива.**

```
<имя>.etnx
├── manifest.json      ← всё содержимое графа
└── attachments/       ← опционально, только с включёнными вложениями
```

Манифест — единственный обязательный файл. Все пути внутри архива относительные.

**Поля манифеста.**

| Поле | Описание |
|---|---|
| `format` | Маркер формата (обязательный) |
| `version` | Версия формата |
| `exported_at` | Момент экспорта |
| `source.network_id` | UUID исходной сети |
| `source.network_name` | Имя исходной сети — только для информации, при импорте **не используется** |
| `source.user_id` | Кто выполнил экспорт |
| `thought_types` / `link_types` / `type_properties` | Определения типов и их свойств |
| `thoughts` / `thought_synonyms` / `links` | Сам граф |
| `comments` / `comment_targets` | Комментарии обоих видов и их привязки |
| `property_values` | Значения свойств |
| `attachments` | Метаданные вложений; для файловых — путь относительно каталога вложений внутри архива |

Схемы записей совпадают с общими DTO проекта — одна и та же сериализация читается и клиентом, и сервером.

**Совместимость.** Текущая версия формата — первая, поэтому проверок совместимости нет: импортёр логирует версию для диагностики, но не отказывает. При изменении формата версия инкрементируется, и тогда же появляется ветка апгрейда старого манифеста.

## Формат дат хроно-записи: полные UTC-инстансы и обязательный valid_to

У любой хроно-записи:

- `valid_from` и `valid_to` — полный UTC-момент ISO-8601 с миллисекундами (как `created_at`); значения без времени недопустимы;
- `valid_to` NOT NULL: если пользователь не задал окончание, оно равно `valid_from`;
- у постоянного комментария `valid_to` остаётся NULL — правило про хронологические записи.

Сервер не придаёт датам смысла «календарного дня»: не конвертирует часовые пояса и не округляет время. День принадлежности записи вычисляет клиент в локальном поясе наблюдателя. См. ADR времени.

## Хранение иконки мысли вида «icon»: имя из каталога

### Контекст

Выбор иконки мысли сегодня ограничен эмодзи и картинкой: `icon_kind ∈ {emoji, image}`, значения хранятся в TEXT-колонках `thoughts.icon_kind` и `thought_types.icon_kind` без CHECK-констрейнта. Нужно добавить выбор иконки библиотеки (ТП0) с обратной совместимостью и без миграции схемы.

### Решение

- Расширить `ICON_KINDS` (`@etn/shared`) третьим значением **`icon`**.
- При `icon_kind='icon'` поле `icon` хранит **имя иконки каталога Lucide** (kebab-case, например `search`, `book-open`).
- Схема БД не меняется: колонки остаются TEXT без CHECK, существующие значения `emoji`/`image` работают как прежде.
- Каталог допустимых имён экспортируется из `@etn/shared`; сервер (`server/src/contracts.ts`) валидирует имя по каталогу и отвергает неизвестное (VALIDATION_ERROR), клиент рендерит вид `icon` через фасад.
- Вид наследуется вместе с иконкой (как эмодзи/картинка) — правила требования [«Наследование визуального стиля мысли от её типа»](#pub-0da6f02a) распространяются на три вида.
- Цвет символа иконки вводится отдельным nullable-полем **`icon_color`** (HEX `#rrggbb`) у мысли и у типа — миграция 049 (`ALTER TABLE … ADD COLUMN`, схема-констрейнта нет). Оно независимо от `fg_color`/`bg_color`, хранится при всех видах иконки, а к рендеру применяется только у библиотечной `icon`; пусто = прежнее поведение (`currentColor`). Наследуется вместе с иконкой.

### Следствия

- Иконка мысли имеет три вида; превью/облачко/редактор показывают вид `icon` тем же путём, что эмодзи (символьный слот).
- `icon_attachment_id` к виду `icon` не применяется (картинки нет) — при выборе иконки библиотеки поле сбрасывается.
- `icon_color` применим и к эмодзи/картинке в хранении, но визуально окрашивает только библиотечный значок; сервер валидирует значение (не-HEX — VALIDATION_ERROR).

### Запреты

- Хранить в `icon` произвольную SVG-разметку или URL для вида `icon`.
- Добавлять CHECK-констрейнт на значения `icon_kind`.
- Принимать имя, отсутствующее в каталоге.
- Принимать в `icon_color` значение, отличное от `#rrggbb` (или `NULL`).

**Актуализация 0.12.1 (задача 4105bd6a).** Введено поле `icon_color` (HEX `#rrggbb`, миграция 049) — цвет символа иконки у мысли и типа; независимо от `fg_color`/`bg_color`, применяется только к библиотечной `icon`, наследуется вместе с иконкой.

## Хранилище (SQLite)

Слой хранения — обёртки над двумя видами баз SQLite: системной `_system.db` и по одной `data.db` на каждую мыслесеть.

Обе базы работают в режиме WAL с включёнными внешними ключами (`PRAGMA foreign_keys = ON`). Доступ — через `better-sqlite3` (синхронный API, FTS5 из коробки). Тот же драйвер используется и в локальном хранилище клиента, поэтому модель работы с SQL единая.

Write-lock WAL сериализует записи в пределах одной сети — это принятая граница: система рассчитана на 2–5 одновременных активных редакторов сети, а не на произвольную нагрузку.

## Что блокирует физическое удаление мысли или связи и что уходит каскадом

Проверяется и при прямом удалении, и при очистке корзины.

**Что блокирует удаление.**

1. **Использование в значениях свойств** — на мысль ссылаются другие мысли через свойство-ссылку. Только для мыслей — у связей такого не бывает.
2. **Изменённая теневая строка этой мысли в каком-либо слое**, не помеченная там на удаление.
3. **Изменённая теневая строка связи, у которой эта мысль — конец.** Для самой связи это единственный вид блокировки.

**Проверка из рабочего слоя.** Теневая строка **самого текущего слоя** удержанием не считается — иначе мысль, созданная в слое, блокировала бы сама себя. А вот живая строка **основы** удерживает: «удалить совсем» в слое — это лишь надгробие, поэтому для строки из основы в слое разрешена только пометка на удаление.

**Что НЕ проверяется.** Wiki-ссылки по id, ссылки из других мыслесетей, текстовые упоминания — потерянные ссылки этого рода признаны нормой: проверять дороже, чем терпеть.

**Каскад при физическом удалении мысли.** Собственные связи с обеих сторон, комментарии, значения свойств, синонимы, привязки вложений и per-user состояние (просмотры, фокус-настройки и порядок, закрепления, метрики чтений). Весь каскад выполняет приложение в одной транзакции — SQL-FK больше нет.

**Дети не удаляются.** Каскад бьёт по строкам связей, а не по дочерним мыслям: ребёнок остаётся, но теряет эту связь и, если других родителей нет, выпадает из навигации.

**Автоочистка после операций со слоями.** Удаление и слияние слоя снимают часть удерживающих ссылок — сразу после этих операций сервер сам прогоняет корзину и удаляет всё, что перестало быть заблокированным. Подтверждения не требуется: пометка на удаление и есть заранее выраженное согласие.

## Экспорт в .etnx: состав выгрузки и сбрасываемые поля

Что попадает в архив и что с ним происходит при выгрузке.

**Опции экспорта** управляют составом: включать ли типы, вложения, хронику, подчинённые мысли и на какую глубину. По умолчанию типы и хроника включены, вложения и подчинённые — выключены. Глубина задаёт, сколько уровней потомков добавляется к корневым мыслям.

**Инварианты экспорта.**

- **UUID сохраняются как есть.** Никакой перегенерации; совпадение идентификаторов в целевой сети разрешает политика импорта.
- **Флаги корневой и защищённой мысли сбрасываются** на импорте: у целевой сети своя корневая мысль, а защита — свойство конкретной сети.
- **Авторство переписывается** на текущего пользователя целевой сети; исходный автор остаётся только в манифесте, для истории.
- **Актуальность сохраняется** как есть.
- **Per-user данные НЕ экспортируются**: просмотры, фокус-настройки и порядок, закрепления, сохранённые отборы, метрики чтений. Они принадлежат пользователю в исходной сети и бессмысленны при переносе.
- **Превью-иконка вложения** экспортируется как есть.
- **Цвет символа иконки и вид иконки типов не переносятся.** `.etnx` не выгружает `icon_color` (ни у мыслей, ни у типов) и `icon_kind` типов; на импорте эти поля остаются пустыми. Осознанное ограничение 0.12.1 (задача 4105bd6a), вне DoD; вместе с `icon_kind` типов устраняется отдельной задачей.

**Актуализация 0.12.1 (задача 4105bd6a).** Зафиксировано осознанное ограничение: `.etnx` не переносит `icon_color` и `icon_kind` типов.

## Экспорт и импорт

Перенос содержимого между мыслесетями и компьютерами: экспорт среза графа в архив `.etnx`, его импорт в другую сеть, выгрузка подграфа в читаемые форматы.

Ключевое свойство: импорт — не добавление копий, а слияние по тождеству мыслей, поэтому повторный импорт того же архива не плодит дубли.

Сюда же относится резервное копирование и снапшоты сети — работа с целыми файлами баз, а не с мыслями.

## Эффективный набор отборов мысли: свои плюс унаследованные от типов-предков

Мысль показывает не только отборы своего типа: эффективный набор собирается по цепочке типов от корня к типу мысли — отборы предков плюс собственные.

**Правило перекрытия.** Одноимённый отбор (сравнение по `name_key`, регистронезависимо) ближнего к мысли типа перекрывает отбор дальнего целиком: определение, описание, признак «по умолчанию». Частичного наследования полей нет.

**Порядок кнопок** — от корня к типу мысли, внутри уровня по `position`. Перекрывающий отбор занимает место перекрытого, а не уезжает в конец: иначе перестановка кнопок зависела бы от того, на каком уровне отбор переопределён.

**Признак «по умолчанию» тоже наследуется.** Если у типа своего отбора по умолчанию нет, действует ближайший помеченный у предков. Собственный отбор по умолчанию у потомка отменяет наследуемый.

Так же наследуются иконка, цвета и стили типа — механика та же, и пользователь вправе её ожидать. Шаблон комментария из этого правила выпадает намеренно (он не наследуется), поэтому равнять отборы на него нельзя.
