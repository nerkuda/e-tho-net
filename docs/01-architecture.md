## AI-агент ограничен MCP-контуром

Внешний AI-агент подключается к MCP-серверу, авторизуется API-ключом и через инструменты MCP читает и изменяет мыслесеть **наравне с человеком** — с теми же событиями real-time и теми же проверками прав.

Два утверждения, которые должны выполняться одновременно:

1. **Агент не ограничен в данных** — особого «урезанного» набора операций для агентов нет; права определяются ключом и членством в сети, а не тем, что это агент.
2. **Агент ограничен в поверхности** — доступа к подсистемам вне MCP-контура у него нет.

Отсюда запрет: нельзя реализовывать правило в MCP-слое в обход ядра — иначе поведение для агента и для человека разойдётся.

Модель авторизации (агент действует от лица пользователя, чей ключ передан):

- видит и может менять только сети, в которых пользователь — участник;
- внутри сети — равноправный участник (как человек); никаких специальных «машинных» прав сверх прав пользователя;
- отображается в `audit_log` со своим `actor_user_id`.

Многоканальный агент: доступ к нескольким сетям — параметром `network_id` в каждом tool-вызове (ключ уже даёт доступ ко всем сетям пользователя). Текущий слой изменений — тоже пер-ключевое состояние: слой-сессия ключуется парой `(network_id, api_keys.id)`, поэтому два ключа одного пользователя держат независимые слой-сессии, и переключение слоя одним ключом не задевает другой.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер, Ядро (доменный слой), Аутентификация и права доступа

## etn init — инициализация сервера и первого администратора

CLI-команда первичной инициализации сервера.

```
etn init --username admin --display-name "Administrator"
```

**Что делает.**

- создаёт системную БД `_system.db` и применяет миграции;
- создаёт первого пользователя: `is_admin = 1`, `is_first_user = 1` — администратор системы и root инсталляции;
- генерирует первичный API-ключ и **выводит его в консоль один раз**; повторно ключ показать невозможно, только перевыпустить;
- пишет в журнал аудита запись с `category = system`, `action = init`.

**Без инициализации сервер не стартует.** Пока на сервере нет ни одного администратора, запуск отклоняется — иначе получился бы работающий сервер, которым некому управлять.

**Инвариант, который закладывает команда.** Первого пользователя нельзя удалить и нельзя снять с него права администратора — защита от сервера, оставшегося без единого администратора.

**Когда вызывается.** Один раз, при развёртывании. Повторный вызов на уже инициализированном сервере второго root-администратора не создаёт.

---

**Термин (глоссарий 10).** **`etn init`** — CLI-команда инициализации сервера: создаёт каталог данных и `_system.db`, применяет миграции, создаёт первого администратора и печатает его API-key.

- относится к подсистемам: Аутентификация и права доступа

## MCP-сервер

Подсистема, экспонирующая ресурсы и инструменты по протоколу MCP для внешних AI-агентов.

Реализована **в том же серверном процессе**, использует **тот же доменный слой**, что и REST: агент читает и изменяет мыслесеть наравне с человеком — те же проверки прав, те же транзакции, те же события real-time. Отдельной бизнес-логики «для агентов» нет и быть не должно, иначе поведение системы разойдётся между двумя входами. Все инструменты именуются `etn.<сущность>.<действие>`.

Агент авторизуется API-ключом и не имеет доступа к подсистемам вне MCP-контура. Реализуется на официальном `@modelcontextprotocol/sdk`. Транспорт и авторизация — отдельная сущность; контроль операций (лимиты, read-only ключи, audit) — отдельная сущность.

**Дополнительные материалы**
- применяется к: ADR: консолидация MCP по сценарию записи, а не универсальные CRUD-мегатулы, ADR: прогрессивное раскрытие MCP вместо роста описаний инструментов, Паритет MCP-контура с REST по данным сети, Аннотации MCP-инструментов, Версионирование и обратная совместимость MCP, Сквозная слоистость MCP-инструментов, Расширение MCP-интерфейса — единая методика

## Real-time канал (WebSocket)

WebSocket-шлюз сервера: удерживает подключения клиентов, фильтрует события по `network_id`, доставляет изменения подписчикам в реальном времени.

События он не порождает — только доставляет: изменение пишет ядро, оно же эмитит событие в pub/sub канала сети, шлюз пушит его участникам. Правки человека и правки MCP-агента идут одним путём, поэтому участники видят их одинаково.

Часть событий адресована не всей сети, а конкретному пользователю (`audience=user`) — так синхронизируются его личные настройки между его же клиентами.

**Дополнительные материалы**
- применяется к: Границы MVP: чего в системе намеренно нет, Масштабирование real-time: in-memory pub/sub, дальше Redis

<a id="pub-04d7b538"></a>

## REST API

CRUD-контур сервера для клиентов: мысли, связи, типы, свойства, комментарии, вложения, поиск, административные операции.

Собственной бизнес-логики не содержит: маршрут разбирает запрос, отдаёт работу ядру и возвращает DTO. Изменяющие операции принимают `client_request_id` (идемпотентность) и порождают события real-time через pub/sub сети.

Реализуется на Fastify. Клиенты работают только через этот контур — прямого доступа к БД у них нет.

<a id="pub-a995045f"></a>

## SQL только в домене; импорт между фасадами запрещён

**Запись в БД идёт через домен.** Фасады (routes, MCP) не содержат SQL и не импортируют друг друга; SQL живёт только в домене и репозиториях. Импорт из `routes/*` в `mcp/*` и наоборот запрещён.

Последствие нарушения: MCP-слой импортировал хелпер из HTTP-слоя — единственная инверсия зависимости сервера.

**Дополнительные материалы**
- применяется к: server/src/mcp — MCP-сервер (реализация)

## UTF-8 и регистронезависимое сравнение текста

Везде используется UTF-8. Регистронезависимое сравнение делается либо через `COLLATE NOCASE`, либо через отдельный нормализованный столбец (lowercase + trim + Unicode NFC), который хранится рядом с исходным текстом.

**Запрет.** Никакой «Unicode-магии»: самодельных транслитераций, точечных замен символов и скрытых преобразований при сравнении быть не должно — иначе поиск и дедупликация начинают вести себя по-разному в разных местах системы.

Нормализованные столбцы — это то, по чему работают поиск дублей и сравнение имён типов; полнотекстовый поиск использует свой токенайзер.

**Дополнительные материалы**
- относится к подсистемам: Хранилище (SQLite), Полнотекстовый поиск (FTS5)

## Версионирование записей и разрешение конфликтов

Каждая содержательная запись несёт целочисленный `version` и `updated_at`. Версия растёт при каждой правке **собственных полей записи**. Запись значения свойства обновляет `updated_at/by` владельца, но его `version` не поднимает: маршрут значений (§9) `If-Match` не несёт, а приравнивание «правка значения = правка владельца» действует по `updated_*` (требование e6d4165e), не по версии (ревизия 2026-09-28, ошибка af104f16, фикс 01bf39fe).

Клиент, изменяющий запись, передаёт версию, которую он видел (контракт `If-Match` в REST, `expected_version` в доменных вызовах и MCP).

`If-Match` проверяется на **текущей версии сущности**. Дальше — политика MVP: last-write-wins на уровне поля + явный сигнал конфликта:

- изменяемые поля не пересекаются с чужими правками — **мирное слияние**: сервер применяет только свои поля, не трогая чужие, и возвращает 200 с актуальной версией. Пример: А поменял заголовок при v=5 → v=6; Б шлёт `If-Match: 5` с новой иконкой — поля разные, сервер применяет иконку, не трогая заголовок → v=7, 200;
- набор изменяемых полей совпадает (заголовок против заголовка) — `409 VERSION_CONFLICT` с телом `{ server_value, server_version }`; клиент показывает уведомление и предлагает «перезаписать» или «оставить чужое».

Передача версии необязательна: без неё действует last-write-wins пополёвно.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), REST API, Real-time канал (WebSocket)
- применяется к: links — направленные связи между мыслями, thoughts — таблица мыслей

## Границы MVP: чего в системе намеренно нет

Явные ограничения, принятые осознанно. Наткнувшись на любое из них, не надо считать это дефектом и «чинить» попутно:

- **Один серверный процесс.** Нет кластеризации и реплик; pub/sub — внутрипроцессный, в памяти.
- **Записи сериализованы** write-lock’ом WAL в пределах одной сети. Расчёт — на 2–5 одновременных активных редакторов.
- **Нет шардинга сетей по дискам** — все сети в одном каталоге данных.
- **Поиск только внутри одной сети** — сквозного индекса по нескольким мыслесетям нет.
- **Нет офлайна на клиенте.**
- **Нет встроенной генерации документов и презентаций** — это работа для внешнего агента.
- **Нет векторного (семантического) поиска.** Задел оставлен только в схеме данных — зарезервированной таблицей эмбеддингов, чтобы будущая реализация не требовала миграций.

**Ограничения модели слоёв (13-layers.md §11).** Осознанные следствия модели «слой — плёнка, а не снимок»; наткнувшись на любое, не считать дефектом:

- **Состояние слоя на прошлую дату невоспроизводимо** — слой видит текущую основу, история пересчитывается при каждом чтении.
- **«Отличие слоя» двусмысленно**: относительно основы-сейчас (показ пользователю) и относительно основы-на-момент-создания слоя (слияние, через `base_version`).
- **Логическое противоречие с основой не обнаруживается**, если строки не перекрываются.
- **Слияние не разрешает конфликты, только детектирует**; three-way merge с выбором стороны — вне фазы S.
- **Разделение прав по слоям не входит в фазу S** — права у всех участников одинаковые (см. «Равные права на слои у всех участников сети»).

**Вне рамок фазы S по слоям (13-layers.md §17).** Кроме разделения прав и three-way merge (см. выше): автоматическая сверка `git_branch` слоя с состоянием git-репозитория — поле зарезервировано, но скрипт сверки в MVP фазы S не входит.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), Хранилище (SQLite), Полнотекстовый поиск (FTS5), Десктоп-клиент (Electron)
- применяется к: Хранилище (SQLite), Real-time канал (WebSocket), Десктоп-клиент (Electron), Полнотекстовый поиск (FTS5)

## Десктоп-клиент (Electron)

Настольное приложение на Electron — основной человеческий вход в систему.

Делится на два процесса: **главный** — окно, локальный SQLite, сетевой клиент (REST плюс пул WebSocket-соединений, по сокету на открытую сеть) и безопасное хранение API-ключа средствами ОС; **renderer** — собственно интерфейс. Граница жӑсткая: renderer получает данные только через IPC-контракт `window.etn`.

В одном окне можно держать несколько открытых мыслесетей и несколько табов одной сети: «текущая сеть» и «текущий фокус» — это всегда сеть и фокус активного таба.

Локально хранятся только персональные настройки, UI-состояние, состояние поиска, история открытых мыслей, табы и черновики правок — никаких содержательных данных сети. Ключевое ограничение: клиент **онлайн-only**.

**Дополнительные материалы**
- применяется к: Тема оформления и масштаб интерфейса клиента в MVP, Поставка десктоп-клиента: платформы, сборка и автообновление, REST-клиент главного процесса: заголовки, повторы и таймауты, Онлайн-only режим десктоп-клиента, Realtime-клиент главного процесса: догон, проброс событий и реконнект, Хранение API-ключа на клиенте: safeStorage и изоляция renderer, Разделение процессов клиента: renderer работает только через IPC, Границы MVP: чего в системе намеренно нет

## Журнал активности отражает то, что записано

**Журнал активности пишется по факту записи.** Обёртка берёт данные журнала из результата записи, а не из аргументов вызова.

Последствие нарушения: MCP-ветка `unlink_parents`/`unlink_children` собирала для журнала фальшивый DTO с `type_id: null` (MCP-операции unlink_parents/unlink_children пишут в activity_log тип связи null) — журналировалось не то, что записано.

## Журналирование критичных операций сервера

Сервер ведёт журнал административных и критичных операций в системной БД: кто, что, когда, в какой мыслесети и какого типа была операция.

Зачем: администрирование и разбор конфликтов — понять, кто и когда изменил состояние системы.

Граница: это **не** журнал всех изменений данных и не история мыслей. Он фиксирует операции аутентификации, управления пользователями, сетями, членством и крупные операции над данными. Чтения в журнал не попадают.

MCP-контур: каждый изменяющий tool-вызов агента пишется в `audit_log` с `category = 'data'`, `action` — по типу операции, в `details` — параметры вызова; актор — `actor_user_id` пользователя ключа. Батч `etn.thoughts.write` — одна запись на весь вызов. Агентские чтения в журнал не пишутся — их след виден в `thought_read_metrics`.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа, Ядро (доменный слой)
- применяется к: GET /admin/audit — журнал аудита сервера

<a id="pub-ded417d2"></a>

## Идемпотентность изменяющих запросов через client_request_id

Каждый изменяющий запрос принимает `client_request_id` (UUID, генерирует клиент). Сервер сохраняет результат обработки на ограниченное время и на повторный запрос с тем же идентификатором возвращает **сохранённый ответ**, а не выполняет операцию заново.

Зачем: клиент и агент могут повторить запрос после таймаута или обрыва связи, не зная, дошёл ли первый. Без этого механизма ретрай порождает дубль мысли или связи.

Сохранённые ответы живут в системной БД с ограниченным TTL и чистятся фоновой задачей — это кэш дедупликации, а не журнал операций.

**Дополнительные материалы**
- относится к подсистемам: REST API, Ядро (доменный слой), MCP-сервер

## Изменение мыслесети AI-агентом через MCP

**Действующее лицо.** Внешний AI-агент с API-ключом.

**Предусловия.** Ключ действителен и не read-only; владелец ключа — участник мыслесети.

**Шаги.**

1. Агент вызывает изменяющий инструмент MCP.
2. MCP-сервер передаёт вызов **в тот же доменный слой**, что использует REST.
3. Ядро выполняет те же проверки и ту же транзакцию, что и для человека, и эмитит событие.
4. Агент получает ответ инструмента.
5. Участники сети видят изменение по WebSocket наравне с человеческими правками.

**Результат.** Изменение применено и неотличимо от правки человека — разница только в авторе события.

**Зачем этот сценарий важен.** Он — проверка главного инварианта архитектуры: если после правки агента участники не увидели изменение или поведение отличается от REST — где-то появилась логика в обход ядра.

**Дополнительные материалы**
- относится к подсистемам: MCP-сервер, Ядро (доменный слой), Real-time канал (WebSocket)
- зависит от: MCP-сервер

<a id="pub-f4ab035e"></a>

## Назначение ETN и модель совместной работы

ETN — **self-hosted** система для построения личных и совместных мыслесетей: графов мыслей и связей с многослойным описанием (свойства, постоянные и хронологические комментарии, вложения).

Обязательные свойства продукта, из которых следует остальная архитектура:

- **Self-hosted.** Система разворачивается на сервере владельца; облачной зависимости нет и быть не должно.
- **Несколько пользователей на одном сервере** работают над общими сетями параллельно.
- **Обновления в реальном времени.** Изменение одного участника остальные видят без перезагрузки.
- **Агенты — полноправные участники.** Внешние AI-агенты подключаются через MCP и работают с данными наравне с человеком.

Запрет, следующий из двух последних пунктов: нельзя вводить операции, меняющие данные в обход общего доменного слоя и без порождения событий — иначе часть участников увидит устаревшую картину.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой), MCP-сервер, Real-time канал (WebSocket)
- применяется к: Ядро (доменный слой)

## Обязательный технологический стек по слоям системы

Какой слой системы на чём обязан быть реализован. Обоснование конкретных версий и спорных выборов живёт в отдельных ADR и карточках технологий; здесь — само соответствие.

| Слой | Технология | Почему именно она |
|---|---|---|
| Сервер | Node.js LTS + TypeScript | Единый язык с клиентом, эффективный I/O для WebSocket и SQLite |
| HTTP-фреймворк | Fastify | Производительность, плагины, типизация |
| WebSocket | `ws` либо `@fastify/websocket` | Простой контроль жизненного цикла подключения |
| Хранение | SQLite через `better-sqlite3` | Синхронный API, WAL и FTS5 из коробки |
| MCP | `@modelcontextprotocol/sdk` | Официальный SDK протокола |
| Клиент | Electron + TypeScript | Кроссплатформенный десктоп, доступ к ФС и хранилищу ключей ОС |
| Рендеринг холста | Canvas/WebGL либо SVG с виртуализацией | Плавный зум и панорамирование, динамические связи, много облачков |
| Локальное хранилище клиента | `better-sqlite3` | Тот же драйвер, что на сервере — единая модель работы с SQL |
| Защита API-key | Electron `safeStorage` (keychain ОС) | Ключи не лежат в открытом виде |

**Что запрещено.** Хранить API-key в конфиге или открытом файле вместо `safeStorage`. Держать общие типы и DTO двумя копиями в сервере и клиенте вместо общего пакета. Заменять SQLite на клиент-серверную СУБД — это ломает модель «одна БД на мыслесеть» и требует отдельного решения.

**Дополнительные материалы**
- относится к подсистемам: Хранилище (SQLite), REST API, Десктоп-клиент (Electron), Real-time канал (WebSocket), Пользовательский интерфейс (холст и редактор)
- применяется к: Хранилище (SQLite)

## Онлайн-only режим десктоп-клиента

Клиент работает **только при живом соединении с сервером**. Офлайн-режима нет.

При разрыве связи клиент обязан:

- **блокировать сохранение** — никаких попыток применить правку локально и дослать потом;
- **буферизовать несохранӑнное в черновик** локального хранилища, чтобы работа пользователя не пропала;
- **показывать индикатор статуса** соединения, а не делать вид, что всё в порядке.

**Индикатор статуса** в строке состояния имеет три положения: «Подключено» (зелӑный), «Переподключение…» (жёлтый), «Нет связи» (красный). В жёлтом и красном состояниях интерфейс переходит в режим только для чтения: последнее полученное состояние продолжает показываться, но изменения заблокированы.

Причина ограничения: источник истины — сервер, а сетью одновременно правят другие люди и агенты. Локальное хранилище клиента под реплику графа не рассчитано и механизма слияния офлайн-правок нет.

**Дополнительные материалы**
- относится к подсистемам: Десктоп-клиент (Electron), Пользовательский интерфейс (холст и редактор)
- применяется к: Десктоп-клиент (Electron), drafts — черновики правок на клиенте

## Переменные окружения сервера

Сервер настраивается переменными окружения — конфигурационного файла на MVP нет.

| Переменная | Назначение |
|---|---|
| `ETN_DATA_DIR` | Корень данных сервера (`_system.db` и `networks/`) |
| `ETN_HOST` | Адрес прослушивания |
| `ETN_PORT` | Порт прослушивания |
| `ETN_TLS_CERT` | Путь к сертификату TLS |
| `ETN_TLS_KEY` | Путь к приватному ключу TLS |
| `ETN_MCP_ENABLED` | `1` — поднять MCP-эндпоинт `/mcp` на HTTP-сервере |
| `ETN_MCP_PORT` | Отдельный порт только для `/mcp` (изоляция трафика агентов) |
| `ETN_MCP_SESSION_IDLE_TTL_MS` | Время жизни простаивающей MCP-сессии, мс: целое в диапазоне 1000…2592000000, по умолчанию 86400000 (24 часа) |

Значения разбираются и валидируются в `server/src/config.ts` при старте: мусор в любой переменной — `ConfigError` с понятным оператору сообщением, сервер не поднимается. Справка по всем переменным есть в выводе `etn --help`.

TLS настоятельно рекомендуется: клиент и агенты передают API-key в каждом запросе, поэтому HTTP/WS без шифрования допустим только в доверенной локальной сети.

Секреты (сами API-ключи) в переменных окружения сервера не хранятся — сервер знает только их хеши.

**Дополнительные материалы**
- относится к подсистемам: Хранилище (SQLite), REST API, MCP-сервер

## Полнотекстовый поиск (FTS5)

Поиск по текстам сети на виртуальных таблицах FTS5: имена и синонимы мыслей, тексты комментариев мыслей и связей.

Индексы поддерживаются триггерами БД, а не приложением — правка схемы мыслей, синонимов или комментариев требует проверки триггеров.

Поиск работает **в пределах одной сети**: общего индекса по нескольким мыслесетям нет и на MVP не планируется. Семантический (векторный) поиск в подсистему не входит — задел оставлен только в схеме данных.

С 0.7.5 все три индекса — `tokenize = 'trigram case_sensitive 0'` (был «`unicode61`», миграция `038_search_trigram.sql`, ошибка 0258fd9d): искомое вхождение в любой части слова (не только префикс), с встроенным кейс-фолдингом кириллицы. Ограничение: ≥3 символа на фрагмент запроса — коротише индекс не ищет; `by_names` покрывает такие случаи LIKE по `title_norm`/`synonym_norm`, у `by_texts`/`by_links`/`by_chrono` такого fallbackа нет (см. `GET /search`).

**В слоях (13-layers.md §9).** FTS-таблицы несут `layer_id UNINDEXED` (миграция 025), автономны (не external-content) и синхронизируются триггерами, поэтому слоистость не потребовала пересборки индекса. Поиск выполняется в контексте слоя сессии: FTS5 сначала ранжирует, затем результат фильтруется по видимости слоя и дедуплицируется по логическому id — см. требование «Поиск в контексте слоя: фильтрация видимости и дедупликация по логическому id».

**Дополнительные материалы**
- применяется к: Границы MVP: чего в системе намеренно нет

## Пользовательский интерфейс (холст и редактор)

Видимая часть клиента: холст с облачками мыслей и линиями связей, редактор мысли, поиск, выделения, диалоги и меню.

## Раскладка каталога данных сервера

Все данные сервера лежат под одним настраиваемым корнем (по умолчанию `/var/lib/etn/`):

```
<корень данных>/
├── _system.db            ← системная БД
├── _system.db-wal
├── _system.db-shm
└── networks/
    ├── <network-uuid>/
    │   ├── data.db       ← данные мыслесети
    │   ├── data.db-wal
    │   ├── data.db-shm
    │   ├── attachments/  ← сохранённые файлы вложений
    │   └── snapshots/    ← экспорт-снапшоты и бэкапы
    └── <network-uuid-2>/
```

Правила:

- Имя каталога сети равно её `id` (UUID) и **неизменно**; отображаемое имя сети меняется свободно и на путь не влияет.
- Все сети лежат в одном `networks/`; шардинга по дискам нет.
- `attachments/` — единое хранилище загруженных на сервер файлов, бэкапится вместе с БД сети.
- Каталоги `attachments/` и `snapshots/` создаются при создании мыслесети, а не по требованию.

**Дополнительные материалы**
- относится к подсистемам: Хранилище (SQLite)
- применяется к: Разделение хранения: системная БД и отдельная БД на каждую мыслесеть

## Резервное копирование сервера и снапшот мыслесети

**Действующее лицо.** Администратор сервера.

**Полный бэкап.**

1. Выполнить `PRAGMA wal_checkpoint(TRUNCATE)` — иначе часть данных останется в WAL и копия будет неполной.
2. Скопировать системную БД и каталоги сетей целиком, включая файлы WAL/SHM и каталог вложений.

**Снапшот одной мыслесети.**

Выполнить `VACUUM INTO` в файл внутри каталога снапшотов сети — получается единый файл без WAL, пригодный к переносу.

**Чего не делать.** Копировать `data.db` без контрольной точки и без сопутствующих файлов — такая копия может оказаться несогласованной.

**Отличие от экспорта.** Бэкап и снапшот работают с файлами БД целиком и сохраняют всё, включая per-user состояние и слои; экспорт — это выборочный срез графа для переноса в другую сеть.

**Дополнительные материалы**
- относится к подсистемам: Хранилище (SQLite), Экспорт и импорт
- зависит от: Раскладка каталога данных сервера

## Создание мысли клиентом: от запроса до real-time доставки

**Действующее лицо.** Человек в десктоп-клиенте.

**Предусловия.** Живое соединение с сервером; пользователь — участник мыслесети.

**Шаги.**

1. Клиент отправляет запрос создания мысли в REST API, приложив `client_request_id`.
2. Ядро валидирует вход и проверяет права на сеть.
3. Запись выполняется **одной транзакцией** в БД этой мыслесети; в той же транзакции инкрементируется счётчик `network_seq` в `_system.db` — событие получает свой `seq`.
4. После коммита транзакции ядро эмитит событие создания в `EventEmitter` по `network_id`.
5. WebSocket-шлюз доставляет событие подписчикам с фильтрацией: `audience=user` — только подключения того же `user_id`; `audience=network` — все участники **за вычетом фильтра видимости по слою подписчика**; источник по `actor.client_id` эхо не получает.
6. Клиент-автор получает успешный ответ с созданной мыслью.
7. Остальные клиенты применяют событие к текущему состоянию холста и редактора — без перезагрузки.

**Результат.** Мысль создана и видна всем участникам сети.

**Ветвления и ошибки.** Событие эмитится только после успешной транзакции — при откате подписчики ничего не видят. Повтор запроса с тем же `client_request_id` вторую мысль не создаёт, а возвращает сохранённый ответ.

**Дополнительные материалы**
- относится к подсистемам: REST API, Ядро (доменный слой), Хранилище (SQLite), Real-time канал (WebSocket)
- зависит от: REST API, Конверт события real-time

## Только параметризованные SQL-запросы

Все обращения к БД идут только через параметризованные запросы. Интерполяция значений в текст SQL — любых, включая «заведомо безопасные» числа и внутренние идентификаторы — запрещена.

Почему без исключений: значение, сегодня приходящее из кода, завтра придёт из запроса пользователя или агента, а проверка происхождения при каждой правке не воспроизводится.

Допустимо собирать из кода только структуру запроса (имена таблиц и столбцов из закрытого списка, число плейсхолдеров), но не сами значения.

- относится к подсистемам: Хранилище (SQLite)
- применяется к: Хранилище (SQLite)

## Тяжёлые выборки уходят в пул reader-воркеров, запись — в главном потоке

Тяжёлые выборки выполняются в пуле reader-соединений на `worker_threads`; запись в базу остаётся единственной и выполняется в главном потоке.

**Проверка.** Тяжёлый запрос выборки не задерживает параллельный ping; конкурентные тесты чтение/запись зелёные.

## Хранилище (SQLite)

Слой хранения — обёртки над двумя видами баз SQLite: системной `_system.db` и по одной `data.db` на каждую мыслесеть.

Обе базы работают в режиме WAL с включёнными внешними ключами (`PRAGMA foreign_keys = ON`). Доступ — через `better-sqlite3` (синхронный API, FTS5 из коробки). Тот же драйвер используется и в локальном хранилище клиента, поэтому модель работы с SQL единая.

Write-lock WAL сериализует записи в пределах одной сети — это принятая граница: система рассчитана на 2–5 одновременных активных редакторов сети, а не на произвольную нагрузку.

**Дополнительные материалы**
- применяется к: Только параметризованные SQL-запросы, Ветвимые и неветвимые таблицы: адресация строк парой id и слоя, Обязательный технологический стек по слоям системы, Границы MVP: чего в системе намеренно нет

<a id="pub-26bba44b"></a>

## Экспорт и импорт

Перенос содержимого между мыслесетями и компьютерами: экспорт среза графа в архив `.etnx`, его импорт в другую сеть, выгрузка подграфа в читаемые форматы.

Ключевое свойство: импорт — не добавление копий, а слияние по тождеству мыслей, поэтому повторный импорт того же архива не плодит дубли.

Сюда же относится резервное копирование и снапшоты сети — работа с целыми файлами баз, а не с мыслями.

<a id="pub-ada008a0"></a>

## Ядро (доменный слой)

Единственное место бизнес-логики сервера: правила создания и удаления, контроль доступа, дедупликация мыслей, транзакции, генерация событий real-time.

Над ядром стоят входы — REST API и MCP-сервер; под ним — слой хранения. Ключевой инвариант: **все входы ходят через ядро**, поэтому человек и агент получают одинаковое поведение, а новое правило пишется один раз.

С переходом на слои изменений ядро отвечает и за целостность данных: SQL-внешние ключи в ветвимых таблицах сняты, каскадные удаления и валидацию ссылок выполняет приложение в одной транзакции.
