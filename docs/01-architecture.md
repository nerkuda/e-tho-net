# 01. Общая архитектура

## 1. Назначение

ETN — self-hosted система для построения личных и совместных «мыслесетей»:
графов мыслей и связей с многослойным описанием (свойства, постоянные и
хронологические комментарии, вложения). Несколько пользователей на одном сервере
могут параллельно работать над общими мыслесетями с обновлениями в реальном
времени. Внешние AI-агенты подключаются к данным через MCP-сервер.

### 2.1. Сервер (Node.js)

Единый процесс (на MVP — без горизонтального масштабирования). Подсистемы:

- **REST API** — CRUD-операции для клиентов (мысли, связи, типы, комментарии,
  вложения, поиск, административные операции).
- **WebSocket-шлюз** — удерживает подключения клиентов, фильтрует события по
  `network_id`, доставляет изменения в реальном времени.
- **MCP-сервер** — экспонирует ресурсы и инструменты по протоколу MCP для
  внешних AI-агентов. Использует тот же слой ядра, что и REST.
- **Ядро (domain layer)** — бизнес-логика над данными: правила создания/удаления,
  контроль доступа, дедупликация мыслей, транзакции, генерация событий real-time.
- **Слой хранения** — обёртки над `_system.db` и сетевыми `data.db`.
- **Pub/sub по network_id** — внутренний `EventEmitter` (на MVP in-memory). При
  записи изменения ядро эмитит событие в канал сети, REST/WS-шлюз доставляет его
  подписчикам.

### 2.2. Десктоп-клиент (Electron)

- Главный процесс: управление окном, локальный SQLite, сетевой клиент
  (REST + WebSocket), безопасное хранение API-key.
- Renderer-процесс: UI (холст, редактор, поиск, выделения, диалоги).
- Локальное хранилище (см. [07-client-electron.md](07-client-electron.md)):
  персональные настройки, UI-state, состояние поиска, черновики правок.
- Онлайн-only: при разрыве связи блокирует сохранение, буферизует правки в
  черновик, показывает индикатор статуса.

### 2.3. Внешний AI-агент

Подключается к MCP-серверу. Авторизуется API-key. Через инструменты MCP читает и
изменяет мыслесеть наравне с человеком (с теми же событиями real-time). Не имеет
доступа к подсистемам, не относящимся к MCP-интерфейсу.

## 3. Технологический стек

| Слой | Технология | Обоснование |
|------|------------|-------------|
| Сервер | **Node.js 20+**, TypeScript | Единый язык с клиентом; богатая экосистема; эффективный I/O для WebSocket и SQLite. |
| HTTP-фреймворк | **Fastify** | Производительность, плагины, типизация. |
| WebSocket | **ws** (или `@fastify/websocket`) | Простой контроль над жизненным циклом подключения. |
| Хранение | **SQLite** через `better-sqlite3` | Синхронный API, высокая производительность, WAL, FTS5 из коробки. |
| MCP | **@modelcontextprotocol/sdk** | Официальный SDK протокола. |
| Клиент | **Electron** + TypeScript | Кроссплатформенный десктоп; доступ к локальной ФС и хранилищу ключей. |
| UI рендеринг холста | **Canvas/WebGL** (или SVG с виртуализацией) | Требования: плавный зум/пан, динамические связи, много облачков. Финальный выбор — в [08-ui-spec.md](08-ui-spec.md). |
| Локальное хранилище клиента | **better-sqlite3** | Тот же драйвер, что на сервере — единая модель работы с SQL. |
| Защита API-key | **Electron `safeStorage`** (OS keychain) | Не хранить ключи в открытом виде. |

## 4. Развёртывание

```
/var/lib/etn/                           ← корень данных сервера (настраивается)
├── _system.db                          ← системная БД
├── _system.db-wal
├── _system.db-shm
└── networks/
    ├── <network-uuid-1>/
    │   ├── data.db                     ← данные мыслесети
    │   ├── data.db-wal
    │   ├── data.db-shm
    │   ├── attachments/                ← локальные файлы вложений (будущее; MVP = только URL)
    │   └── snapshots/                  ← экспорт-снапшоты, бэкапы
    └── <network-uuid-2>/
        └── ...
```

- Сервер настраивается переменными окружения: `ETN_DATA_DIR`, `ETN_HOST`,
  `ETN_PORT`, `ETN_TLS_CERT`/`ETN_TLS_KEY` (рекомендуется HTTPS/WSS).
- Первый пользователь создаётся при инициализации (CLI-команда `etn init`) и
  становится **администратором**.
- Бэкап на MVP = копирование каталога `networks/<id>/` и `_system.db` (WAL
  контрольная точка перед копированием).

## 5. Потоки данных

### 5.1. Создание мысли клиентом

```
Клиент ──POST /networks/{id}/thoughts──▶ REST API
                                              │
                                              ▼
                                   Ядро: валидация, права
                                              │
                                              ▼
                          Транзакция в networks/{id}/data.db
                                              │
                                              ▼
                          Pub/sub: emit("thought.created", netId)
                                              │
                                              ▼
                          WebSocket: пуш всем подписчикам сети
                                              │
                          ◀─── 200 OK + мысль ──────────── Клиенту-автору
```

### 5.2. Запрос MCP-агента

```
Агент ──MCP tool: create_thought──▶ MCP-сервер
                                         │
                                         ▼
                            Ядро (тот же доменный слой)
                                         │
                                         ▼
                         Транзакция + emit (тот же путь, что у человека)
                                         │
                                         ▼
                          ◀── MCP response ── Агенту
                                         │
                                         ▼
                          WebSocket: участники сети видят новую мысль
                          наравне с человеческими правками
```

### 5.3. Real-time обновление у другого участника

```
Сервер ──WS event {network_id, type, payload}──▶ Клиент Б
                                                      │
                                                      ▼
                                  Применение изменения к локальному
                                  состоянию холста/редактора
                                  (без перезагрузки)
```

## 6. Сквозные принципы

- **Идемпотентность операций.** Каждый изменяющий запрос принимает
  `client_request_id` (UUID); сервер хранит результат N минут в `_system.db`,
  повторный запрос с тем же id возвращает сохранённый ответ. Защита от дублей при
  ретраях клиента.
- **Версионирование сущностей.** Каждая запись имеет `version` (целое) и
  `updated_at`. Записи с `updated_at` старше версии у клиента считаются
  конфликтующими — см. [04-realtime.md](04-realtime.md), раздел «Конфликты».
- **Журналирование.** В `_system.db` ведётся `audit_log` (кто, что, когда,
  network_id, тип операции) — для администрирования и разбора конфликтов.
- **Без Unicode-магии.** Везде UTF-8, регистронезависимое сравнение через
  `COLLATE NOCASE` или нормализованный столбец.
- **Все SQL — параметризованные.** Никакой интерполяции значений в запросы.

## 7. Границы MVP (явные ограничения)

- Один серверный процесс (нет кластеризации, нет реплик).
- WAL-режим SQLite, write-lock сериализует записи в пределах одной сети
  (допустимо для 2–5 одновременных активных редакторов).
- Нет горизонтального шардинга сетей по дискам (все сети в одном `networks/`).
- Нет встроенного полнотекстового индексирования по нескольким сетям
  одновременно (поиск — в пределах одной сети).
- Нет офлайна на клиенте.
- Нет встроенной генерации документов/презентаций (через MCP-агента — в будущем).
- Векторный индекс для семантического поиска не входит в MVP; задел — в схеме
  данных (`embeddings`-таблица зарезервирована).
