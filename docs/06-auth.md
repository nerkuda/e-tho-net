# 06. Аутентификация и контроль доступа

## 1. Модель аутентификации

- **Способ:** статические API-key (bearer token). Никаких паролей, сессий, OAuth,
  JWT на MVP.
- **Кто выдаёт:** администратор при создании пользователя (`POST /admin/users`
  → возвращает сгенерированный ключ один раз), либо сам пользователь
  (`POST /me/keys`) для дополнительных ключей.
- **Передача:** заголовок `Authorization: Bearer <API-key>` во всех запросах к
  REST, WebSocket и MCP.
- **Хранение на сервере:** только SHA-256(key) в `api_keys.key_hash`. Сам ключ
  не сохраняется — восстановить нельзя, можно только перевыпустить.

## 2. Формат ключа

```
etn_<32 hex>      например: etn_a1b2c3d4e5f6...
```

- Префикс `etn_` — для отличия от других токенов в конфигах.
- 32 hex-символа = 128 бит энтропии.
- В таблице хранится `key_prefix` = первые 8 символов после `etn_` — для
  отображения в интерфейсе (`etn_a1b2c3d4…`) без раскрытия ключа.

## 3. Проверка ключа на каждый запрос

1. Извлечь `Bearer`-токен.
2. `key_hash = sha256(token)`.
3. `SELECT * FROM api_keys JOIN users ON ... WHERE key_hash = ? AND disabled = 0
   AND users.disabled = 0`.
4. Если нет → 401.
5. Обновить `last_used_at` (асинхронно, чтобы не тормозить запрос).
6. В контекст запроса помещается `{ user, key_id, key_scopes }`.

Для производительности `key_hash` индексирован (UNIQUE). При 100k ключей поиск O(1).

## 4. Роли и контроль доступа

### 4.1. Три уровня

| Роль | Область | Права |
|------|---------|-------|
| **Администратор системы** | весь сервер | Всё, на каждой сети — с эффективными правами владельца, **даже без явного членства** в `network_members`. Управление пользователями и их ключами. Управление любой сетью и её членством. Удаление любой сети. Чтение `audit_log`. |
| **Владелец сети** | конкретная сеть | Всё внутри сети + управление её членством (добавить/исключить участника, передать владение). Переименование/удаление сети (владелец может удалить свою сеть). |
| **Участник сети** | конкретная сеть | Полный доступ к данным сети без отличий от владельца (создание/изменение/удаление мыслей, связей, комментариев и т.д.). Не может менять членство сети (только просматривать список участников). |

### 4.2. Где хранятся роли
- `users.is_admin` — глобальный флаг администратора.
- `network_members.role` — `'owner'` или `'member'` для конкретной сети.

### 4.3. Особые случаи

- **Первый пользователь** (`is_first_user = 1`): создаётся командой `etn init`,
  неудаляем, всегда `is_admin = 1`. Это «root» инсталляции.
- **Владелец не может выйти из своей сети**, пока не передаст владение.
- **Администратор не обязан быть членом сети** — ни для управления её
  членством, ни для чтения/записи данных сети (мыслей/связей/типов/
  комментариев и проч.). `network_members` остаётся источником истины для
  «личного» списка сетей пользователя (`GET /networks`, `etn.networks.list`,
  которые по-прежнему показывают только сети явного членства — это сознательный
  выбор UX, а не ограничение доступа) и для отображения роли, но не является
  предохранителем: `is_admin = 1` даёт доступ к любой сети сервера напрямую по
  id, минуя эту таблицу (task 0.4.2 bug-fix; было наоборот на MVP — админ без
  членства не мог даже читать чужие данные, это оказалось не тем поведением,
  которое нужно для эксплуатации).
- **Удаление пользователя**: каскад удаляет `api_keys`, `network_members`,
  серверные `user_preferences`. Сети, которыми он владел, переходят к
  администратору (или блокируют удаление, пока не передано владение — выбираем
  **второе** на MVP, чтобы не было сирот). Поэтому `DELETE /admin/users/{id}`
  возвращает 422, если пользователь владеет хотя бы одной сетью.

## 5. Проверка доступа (middleware)

Все REST-обработчики декорируются требованиями:
```ts
requireAuth                          // любой валидный ключ
requireAdmin                        // is_admin = 1
requireNetworkMember(role?: "owner") // член сети (или владелец), либо любой admin
```

Псевдокод проверки прав на эндпоинт сети (и REST `requireNetworkMember`, и
эквивалентная проверка в MCP-инструментах/ресурсах, `assertNetworkAccess` в
`server/src/mcp/context.ts`, — единый источник правды):
```
1. Извлечь network_id из пути/аргумента.
2. Если user.is_admin → доступ разрешён (владелец-эквивалент), проверка окончена.
3. Заглянуть в _system.network_members (user_id, network_id).
4. Если записи нет → 403 FORBIDDEN.
5. Если требуется role: "owner" — записи должно быть достаточно с role="owner".
   (Для операций с данными сети — мысли/связи/типы/комментарии/свойства/
   вложения — роль "member" достаточна и ничем не отличается от "owner":
   различие ролей действует только для управления самим членством сети.)
```

Управление списком участников сети (`POST`/`DELETE`/`PATCH
/networks/{id}/members...`) доступно владельцу сети или любому admin
(`requireOwnerOrAdmin` в `server/src/routes/networks.ts`); обычный участник
может только читать список (`GET /networks/{id}/members` требует лишь
`requireNetworkMember()`).

Кеширование членства: в памяти процесса (Map по user_id → Set<network_id>),
сбрасывается при `member.added`/`member.removed`/`member.role_changed`. Кеш
хранит только явные строки `network_members`; результат для админов не
кешируется отдельно — `user.is_admin` читается из уже проверенного `req.auth`
на каждый запрос.

## 6. Создание API-key

### 6.1. Администратором для пользователя
```
POST /api/v1/admin/users/{id}/keys { label: "desktop", read_only?: false, max_writes_per_minute?: null|int }
→ 201 { data: { id, key: "etn_...", prefix, label, created_at } }
```
Полный ключ возвращается **один раз**. Админ копирует его из UI кнопкой
«Копировать» и передаёт пользователю through out-of-band канал.

### 6.2. Самим пользователем
```
POST /api/v1/me/keys { label, read_only?, max_writes_per_minute? }
→ 201 { data: { id, key, prefix } }
```

### 6.2a. Лимит записи на ключ (task O8)

`max_writes_per_minute` — необязательное переопределение лимита записи MCP
для конкретного ключа (`NULL`/отсутствует — серверный дефолт
`mcp.max_writes_per_minute`, см. 05-mcp-server.md §6.2). Позволяет выдать
ключу легитимного bulk-импорта базы знаний отдельный бюджет, не поднимая
глобальную защиту от runaway-агента. Принимает положительное целое или
`null`; MCP-слой резолвит эффективный лимит на ключ, bundle-вызов (O1)
считается одной записью.

### 6.2b. Редактирование лимита ключа
```
PATCH /api/v1/me/keys/{id}                    { max_writes_per_minute: null|int }
PATCH /api/v1/admin/users/{uid}/keys/{id}     { max_writes_per_minute: null|int }
→ 200 { data: { id, prefix, max_writes_per_minute, ... } }
```
Меняет только `max_writes_per_minute` существующего ключа (`null` — сброс к
серверному дефолту). Остальные поля ключа (`label`, `read_only`) не
редактируются — для их изменения ключ перевыпускается.

### 6.3. Отзыв
```
DELETE /api/v1/me/keys/{id}
DELETE /api/v1/admin/users/{uid}/keys/{id}
→ 204
```
Все активные WebSocket/MCP-подключения с этим ключом закрываются кодом `4401`.

## 7. Хранение ключа на клиенте

- Electron-клиент использует **`safeStorage`** (encrypting string with OS
  keychain: DPAPI на Windows, Keychain на macOS, libsecret на Linux).
- На диске лежит зашифрованный блоб в конфиге приложения.
- В рантайме ключ расшифровывается в памяти главного процесса и передаётся в
  сетевой клиент; renderer не получает ключ напрямую — все сетевые вызовы идут
  через IPC из главного процесса.

## 8. Инициализация сервера (`etn init`)

CLI-команда при первом запуске:
```
etn init --username admin --display-name "Administrator"
```
- Создаёт `_system.db`, применяет миграции.
- Создаёт пользователя с `is_admin = 1, is_first_user = 1`.
- Генерирует первичный API-key, выводит его **один раз** в консоль.
- Пишет в `audit_log` категорию `system`, action `init`.

Без `etn init` сервер отказывается стартовать (нет ни одного админа).

## 9. Защита от перебора

- На `401` от любых эндпоинтов включается счётчик по IP+key_prefix: 10 неудач /
  минуту → 429 на 5 минут. Логируется в `audit_log` (`category=auth`).
- WebSocket при 5 неудачных подключениях подряд с одного IP → временный бан.

## 10. Что НЕ делается на MVP

- Двухфакторная аутентификация, SSO, OAuth.
- Временные токена с истечением (ключ бессрочный, отзыв — ручной).
- Шифрование данных сети в покое (SQLCipher) — **опционально**, если будет
  запрошено; зарезервировано, в схему не включено.
- IP-whitelisting на уровне сервера (можно сделать через reverse-proxy).
