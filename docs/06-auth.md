## /admin/users — администрирование пользователей и их ключей

Админские маршруты управления учётными записями сервера. Доступны только ключу пользователя с `is_admin = 1`; остальным — `403 FORBIDDEN`.

```
GET    /api/v1/admin/users
POST   /api/v1/admin/users            { username, display_name, is_admin? }
                                      → 201 + автоматически созданный API-ключ
GET    /api/v1/admin/users/{id}
PATCH  /api/v1/admin/users/{id}       { display_name?, is_admin?, disabled? }
DELETE /api/v1/admin/users/{id}

POST   /api/v1/admin/users/{id}/keys  { label, read_only?, max_writes_per_minute? }
                                      → 201 { key, prefix }
PATCH  /api/v1/admin/users/{id}/keys/{key_id}  { max_writes_per_minute: null | int }
DELETE /api/v1/admin/users/{id}/keys/{key_id}
```

- создание пользователя сразу выдаёт ему ключ; передать ключ владельцу — забота админа (повторно ключ не показывается);
- **первого пользователя сервера (`is_first_user = 1`) удалить нельзя** — `422`: иначе сервер можно оставить без администратора;
- `disabled` блокирует вход, не удаляя данные пользователя;
- админ выпускает и отзывает ключи любого пользователя теми же правилами, что и владелец через `/me/keys`.

**Дополнительные материалы**
- относится к подсистемам: REST API, Аутентификация и права доступа
- зависит от: users — таблица пользователей сервера, api_keys — таблица ключей доступа
- применяется к: Удаление пользователя: каскад и запрет при владении сетью, Требование: запрет физического удаления пользователя-автора

## /me/keys — управление своими API-ключами

Пользователь сам заводит и отзывает свои ключи доступа — отдельный ключ на каждый клиент и на каждого агента.

```
GET    /api/v1/me/keys        # список: только prefix, без полного ключа
POST   /api/v1/me/keys        { label, read_only?, max_writes_per_minute? }
                              → 201 { data: { id, key, prefix } }
PATCH  /api/v1/me/keys/{id}   { max_writes_per_minute: null | int }
DELETE /api/v1/me/keys/{id}   # отозвать
```

**Полный ключ возвращается только один раз — в ответе на создание.** Дальше виден только префикс: в базе хранится хеш, восстановить потерянный ключ невозможно — только выпустить новый.

- `read_only` — ключ только для чтения (пригоден агенту-наблюдателю);
- `max_writes_per_minute` — персональный бюджет записей ключа; `null` снимает персональный лимит и возвращает к серверному умолчанию;
- `DELETE` — отзыв: ключ перестаёт работать немедленно.

**Дополнительные материалы**
- относится к подсистемам: REST API, Аутентификация и права доступа
- зависит от: api_keys — таблица ключей доступа
- применяется к: Отзыв ключа разрывает активные WebSocket- и MCP-подключения

## api_keys — таблица ключей доступа

API-ключи для авторизации клиентов и MCP-агентов. У одного пользователя может быть несколько ключей — например отдельный для десктопа и отдельный для агента.

| Столбец | Тип | Описание |
|---|---|---|
| `id` | TEXT PK | UUID |
| `user_id` | TEXT NOT NULL FK → users.id ON DELETE CASCADE | Владелец |
| `label` | TEXT | Метка («desktop», «mcp-agent») |
| `key_hash` | TEXT NOT NULL UNIQUE | SHA-256 от ключа; сам ключ не хранится |
| `key_prefix` | TEXT NOT NULL | Первые 8 символов ключа для отображения |
| `read_only` | INTEGER NOT NULL DEFAULT 0 | 1 — ключу запрещены изменяющие операции |
| `max_writes_per_minute` | INTEGER NULL | Переопределение лимита записи MCP для этого ключа; `NULL` — серверный дефолт |
| `created_at` | TEXT NOT NULL | |
| `last_used_at` | TEXT | |
| `disabled` | INTEGER NOT NULL DEFAULT 0 | |

Индексы: уникальный по `key_hash`, обычный по `user_id`.

**Формат ключа:** `etn_<32 hex>` (длина 36).

**Главное правило.** Сам ключ на сервере не хранится никогда — только хеш и префикс. Показать пользователю ключ повторно после выдачи невозможно; потерянный ключ только перевыпускают.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа, MCP-сервер
- применяется к: Аутентификация статическими API-ключами без паролей и сессий, Защита от перебора ключей: блокировка по IP и префиксу, Проверка API-ключа на каждом запросе

## Администратор системы имеет доступ к любой сети без членства

`is_admin = 1` даёт эффективные права владельца на **любую** сеть сервера напрямую по её id — и на чтение с записью данных (мысли, связи, типы, комментарии), и на управление членством. Запись в `network_members` для этого не требуется.

**Чем тогда остаётся `network_members`.** Источником истины для «личного» списка сетей пользователя и для отображения роли. `GET /networks` и `etn.networks.list` по-прежнему показывают только сети явного членства — в том числе администратору. Это сознательный выбор в пользу удобства, а не ограничение доступа: администратор попадает в любую сеть, обратившись к ней по id.

**Предохранителем эта таблица не является.** Проверка доступа пропускает администратора раньше, чем заглядывает в `network_members`.

На MVP поведение было обратным: администратор без членства не мог даже читать чужие данные. При эксплуатации это оказалось неверным — поведение изменено баг-фиксом версии 0.4.2. Не возвращай прежнюю логику, увидев администратора, отсутствующего в списке участников.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа
- применяется к: /admin/networks — админский обзор и правка мыслесетей, network_members — членство пользователей в мыслесетях

## Журналирование критичных операций сервера

Сервер ведёт журнал административных и критичных операций в системной БД: кто, что, когда, в какой мыслесети и какого типа была операция.

Зачем: администрирование и разбор конфликтов — понять, кто и когда изменил состояние системы.

Граница: это **не** журнал всех изменений данных и не история мыслей. Он фиксирует операции аутентификации, управления пользователями, сетями, членством и крупные операции над данными. Чтения в журнал не попадают.

MCP-контур: каждый изменяющий tool-вызов агента пишется в `audit_log` с `category = 'data'`, `action` — по типу операции, в `details` — параметры вызова; актор — `actor_user_id` пользователя ключа. Батч `etn.thoughts.write` — одна запись на весь вызов. Агентские чтения в журнал не пишутся — их след виден в `thought_read_metrics`.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа, Ядро (доменный слой)
- применяется к: GET /admin/audit — журнал аудита сервера

## Защита от перебора ключей: блокировка по IP и префиксу

Неудачные попытки аутентификации ограничиваются по скорости, чтобы ключ нельзя было подобрать перебором.

**HTTP-контур.** На каждый ответ `401` от любого эндпоинта наращивается счётчик по паре (IP, `key_prefix`). 10 неудач за минуту → `429` на 5 минут.

**WebSocket.** 5 неудачных подключений подряд с одного IP → временный бан этого IP.

**Почему по префиксу, а не по ключу.** Полный ключ на сервере не хранится, а префикс позволяет отличить подбор одного конкретного ключа от массового сканирования.

Срабатывания пишутся в журнал аудита с `category = auth` — без этого администратор не увидит атаку.

Это защита от подбора чужого ключа, а не от перегрузки сервера валидным ключом: ограничение частоты записей агента — отдельный механизм лимитов MCP.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа
- зависит от: Журналирование критичных операций сервера
- применяется к: api_keys — таблица ключей доступа

## Кеш членства в сетях и его инвалидация

Членство кешируется в памяти процесса сервера: `Map` вида `user_id → Set<network_id>`. Без кеша каждый запрос к сети шёл бы в системную БД за строкой `network_members`.

**Инвалидация.** Кеш сбрасывается по событиям `member.added`, `member.removed`, `member.role_changed`. Любое новое изменение членства обязано порождать одно из этих событий, иначе права останутся старыми до перезапуска процесса.

**Что в кеш не кладётся.** Только явные строки `network_members`. Результат для администраторов отдельно не кешируется: `user.is_admin` берётся из уже проверенного контекста запроса (`req.auth`) на каждом запросе — иначе снятие флага администратора не подхватилось бы до сброса кеша по членству.

**Граница.** Кеш локален для одного процесса. Несколько процессов сервера над одной системной БД потребуют другого механизма инвалидации — внутрипроцессного события для этого не хватит.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа
- применяется к: network_members — членство пользователей в мыслесетях

## Отзыв ключа разрывает активные WebSocket- и MCP-подключения

Отзыв ключа (`DELETE /me/keys/{id}` или `DELETE /admin/users/{uid}/keys/{id}`) действует немедленно: сервер обязан закрыть все активные WebSocket- и MCP-подключения, открытые этим ключом, кодом закрытия `4401`.

**Почему это обязательно.** Ключ бессрочен, а проверка ключа выполняется при установлении соединения. Если не рвать уже открытые соединения, отозванный ключ продолжит работать неограниченно долго — отзыв окажется фиктивным.

`4401` — **терминальный** код закрытия: клиент не переустанавливает такое соединение автоматически, а требует нового ключа. Тот же код возвращается при попытке подключиться невалидным ключом или ключом без прав на сеть.

Так же обрабатываются отключение ключа (`disabled = 1`) и отключение учётной записи владельца: для проверки ключа это тот же случай, что и отсутствие ключа.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа, Real-time канал (WebSocket), MCP-сервер
- применяется к: WS /api/v1/realtime — подключение к каналу событий сети, Транспорт и аутентификация MCP-сервера, /me/keys — управление своими API-ключами

## Проверка API-ключа на каждом запросе

Каждый запрос к REST, WebSocket и MCP проходит одну и ту же проверку ключа — маршрутов без аутентификации нет.

**Порядок проверки.**

1. Извлечь bearer-токен из заголовка `Authorization`.
2. Вычислить `key_hash = sha256(token)`.
3. Найти ключ вместе с владельцем: `api_keys JOIN users` по `key_hash` при `api_keys.disabled = 0` и `users.disabled = 0`.
4. Не нашли — `401`. Отключённый ключ и отключённая учётка внешне неотличимы от несуществующего ключа: по коду ответа нельзя выяснить, существует ли ключ.
5. Обновить `last_used_at` **асинхронно** — эта запись не должна задерживать ответ.
6. Положить в контекст запроса `{ user, key_id, key_scopes }`. Все дальнейшие проверки прав идут по этому контексту, а не по повторному чтению базы.

**Почему это дёшево.** Поиск идёт по уникальному индексу `key_hash`, поэтому стоимость проверки не зависит от числа ключей на сервере.

Проверка отвечает только на вопрос «кто обращается». Что именно ему разрешено — решает отдельная проверка доступа к сети.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа, REST API
- применяется к: users — таблица пользователей сервера, api_keys — таблица ключей доступа

## Проверка доступа к сети: единый алгоритм REST и MCP

Права на операцию с сетью проверяются **одним и тем же алгоритмом независимо от канала**: REST-декоратор `requireNetworkMember` и проверка `assertNetworkAccess` в MCP-инструментах и ресурсах обязаны вести себя одинаково. Расхождение между ними — баг, а не особенность канала.

**Декораторы REST-обработчиков.**

| Декоратор | Кого пропускает |
|---|---|
| `requireAuth` | любой валидный ключ |
| `requireAdmin` | `is_admin = 1` |
| `requireNetworkMember(role?)` | член сети (владелец — при `role: "owner"`), либо любой администратор |
| `requireOwnerOrAdmin` | владелец сети или администратор |

**Алгоритм проверки доступа к сети.**

1. Извлечь `network_id` из пути или аргумента вызова.
2. `user.is_admin` — доступ разрешён с правами владельца, проверка окончена.
3. Иначе искать строку в системной таблице `network_members` по паре (`user_id`, `network_id`).
4. Строки нет — `403 FORBIDDEN`.
5. Требуется `role: "owner"` — найденная строка обязана иметь `role = 'owner'`.

Для операций с данными сети роль `member` достаточна и ничем не отличается от `owner`.

**Управление списком участников** (`POST`, `PATCH`, `DELETE` на `/networks/{id}/members…`) доступно владельцу сети или любому администратору. Читать список участников (`GET`) может любой член сети.

Реализация: `server/src/mcp/context.ts` (`assertNetworkAccess`), `server/src/routes/networks.ts` (`requireOwnerOrAdmin`).

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа, REST API, MCP-сервер
- применяется к: network_members — членство пользователей в мыслесетях

## Три роли доступа: администратор системы, владелец и участник сети

Ролей ровно три, дробить их на более мелкие права не предусмотрено.

| Роль | Область | Права |
|---|---|---|
| **Администратор системы** | весь сервер | Всё на любой сети с эффективными правами владельца — **даже без явного членства**. Управление пользователями и их ключами. Управление любой сетью и её членством. Удаление любой сети. Чтение журнала аудита. |
| **Владелец сети** | одна сеть | Всё внутри сети плюс управление её членством: добавить и исключить участника, передать владение. Переименование и удаление своей сети. |
| **Участник сети** | одна сеть | Полный доступ к данным сети — мысли, связи, типы, комментарии, свойства, вложения — без отличий от владельца. Членство менять не может, только просматривать список участников. |

**Где хранятся роли.** `users.is_admin` — глобальный флаг администратора системы; `network_members.role` (`'owner'` или `'member'`) — роль в конкретной сети.

**Главное, что путают.** Для операций с данными сети `owner` и `member` не различаются вообще. Различие ролей действует только при управлении самим членством сети. Не выдумывай ограничений участнику на запись данных — их нет.

---

**Термины (глоссарий 10).** **Администратор системы** (`is_admin=1`) — глобальная роль: пользователи и их ключи, любая сеть и её членство, чтение `audit_log`. **Владелец сети** (`role=owner`) — создатель сети или получатель владения; управляет членством. **Участник сети** (`role=member`) — полный доступ к данным сети без управления членством.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа
- применяется к: users — таблица пользователей сервера, network_members — членство пользователей в мыслесетях

## Удаление пользователя: каскад и запрет при владении сетью

**Запрет.** `DELETE /admin/users/{id}` возвращает `422`, если пользователь владеет хотя бы одной мыслесетью. Сначала передают владение, потом удаляют — так в системе не появляется бесхозных сетей.

Альтернатива — автоматически передавать осиротевшие сети администратору — рассматривалась и отклонена: молчаливая смена владельца хуже явной ошибки.

**Каскад при успешном удалении.** Удаляются все `api_keys` пользователя, его строки `network_members` и серверные `user_preferences`.

**Что не удаляется никогда.** Пользователь с `is_first_user = 1` — иначе сервер можно оставить без администратора.

**Отключение — не удаление.** `disabled = 1` блокирует вход, но строка остаётся, чтобы ссылки на авторство записей не повисали. Это штатный способ закрыть доступ, когда удаление невозможно или нежелательно.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа
- применяется к: users — таблица пользователей сервера, /admin/users — администрирование пользователей и их ключей, network_members — членство пользователей в мыслесетях

## Хранение API-ключа на клиенте: safeStorage и изоляция renderer

Десктоп-клиент обязан хранить API-ключ через Electron `safeStorage` — шифрование средствами ОС: DPAPI на Windows, Keychain на macOS, libsecret на Linux. На диске в конфиге приложения лежит только зашифрованный блоб.

**Изоляция процессов.** В рантайме ключ расшифровывается в памяти **главного процесса** и передаётся сетевому клиенту. **Renderer ключ не получает никогда**: все сетевые вызовы идут через IPC из главного процесса.

**Запрещено:** хранить ключ в конфиге открытым текстом, пробрасывать его в renderer ради «простоты» сетевого кода и писать его в логи.

Причина жёсткости: ключ бессрочен и даёт полные права своего владельца, а автоматического истечения, которое ограничило бы ущерб от утечки, нет.

**Дополнительные материалы**
- относится к подсистемам: Аутентификация и права доступа, Десктоп-клиент (Electron)
- применяется к: server_profiles — подключения клиента к серверам ETN, Десктоп-клиент (Electron)
