# Фаза O — MCP: эффективность и удобство для AI-агентов

> [← Workplan (индекс)](../workplan.md) — оглавление, статусы фаз и решения.

> По запросу пользователя (21.08.2026), по итогам исследования «что улучшить в
> архитектуре ETN/MCP для агентов» (ветка `mcp/upgrade-1`). Сквозная цель —
> использование мыслесети как базы знаний AI-агентами: меньше вызовов на
> операцию, атомарная запись «единицы знания», самоописание сети, экономия
> контекстного окна. Блок Retrieval (O11–O15) — **опциональный**, выполняется
> последним и только по отдельному решению пользователя.

## O1. Составная запись «единицы знания»: `etn.thoughts.upsert_bundle`
- **Статус:** `done` · **Зависимости:** F, N
- **Описание:** создание одной осмысленной мысли сейчас требует 5–8
  последовательных вызовов (`thoughts.create` → `comments.upsert` →
  `properties.set` × N → `links.create` × M → `attachments.add`), каждый
  промежуточный шаг неатомарен (упавший агент оставляет мысль без свойств и
  связей), а серия упирается в `max_writes_per_minute`. Новый изменяющий
  инструмент `etn.thoughts.upsert_bundle`: мысль (title, type, synonyms,
  active) + permanent-комментарий + карта свойств `{key: value}` + связи
  (направление, цель, тип) + вложения — **одной транзакцией** доменного слоя.
  Политика дублей `on_duplicate: fail | reuse | update` (по
  `find_duplicates`-матчу: `fail` — ошибка с кандидатами, `reuse` — дополнить
  существующую мысль, `update` — обновить поля) закрывает гонку двухшагового
  паттерна `find_duplicates → create` и делает повторный импорт идемпотентным.
- **DoD:**
  - [x] Типы bundle-входа/выхода в `@etn/shared`; zod-схема в `mcp/tools.ts`.
  - [x] Доменная транзакция (создание/дополнение мысли + комментарий +
    свойства + связи + вложения; корректные real-time события по каждой
    сущности).
  - [x] Политика `on_duplicate` с использованием `findDuplicates`.
  - [x] Один bundle-вызов считается одной записью для rate-лимита (см. O8).
  - [x] Спека `docs/05-mcp-server.md` §4.2 + `docs/mcp-clients.md`; тесты
    (атомарность при ошибке на середине, все три политики); typecheck зелёный.

## O2. `etn.properties.set`: несколько свойств за вызов
- **Статус:** `todo` · **Зависимости:** F
- **Описание:** инструмент принимает одно свойство за вызов — заполнение
  карточки из 4–5 свойств стоит 4–5 записей. Расширить вход картой
  `values: {key: value|null}` (набор пишется одной транзакцией, `null` —
  очистка), сохранив обратную совместимость одиночной формы `key`/`value`.
- **DoD:**
  - [ ] Схема входа: ровно одно из `key`+`value` / `values` (zod refine).
  - [ ] Доменная запись набора значений одной транзакцией + события.
  - [ ] Спека `docs/05-mcp-server.md` §4.2 + `docs/mcp-clients.md`; тесты
    (смешанные типы значений, ошибка валидации одного ключа откатывает все);
    typecheck зелёный.

## O3. `etn.comments.upsert`: мульти-привязки `targets[]`
- **Статус:** `todo` · **Зависимости:** F
- **Описание:** модель и REST поддерживают привязку хронологического
  комментария к нескольким владельцам (L20, `comment_targets`), но MCP-агент
  может создать запись только с одной привязкой — ограничение прямо оговорено
  в `05-mcp-server.md` §4.1. Добавить опциональный параметр `targets[]`
  (`{owner_type, owner_id}`, только для `kind: 'chronological'`; первый —
  первичный владелец).
- **DoD:**
  - [ ] Параметр `targets[]` в схеме инструмента; валидация владельцев.
  - [ ] Переиспользование доменной логики привязок L20 (REST-путь).
  - [ ] Спека `docs/05-mcp-server.md` §4.1/§4.2 (снять оговорку) +
    `docs/mcp-clients.md`; тесты; typecheck зелёный.

## O4. Каталог типов как инструмент: `etn.types.list` + резолв типа по имени
- **Статус:** `todo` · **Зависимости:** F
- **Описание:** `thoughts.create`/`links.create` требуют `type_id`, но
  получить каталог типов агент может только через resources
  (`etn://…/thought-types`), которые многие MCP-клиенты не используют, —
  либо косвенно из reference-таблиц случайных read-ответов. Новый read-only
  инструмент `etn.types.list`: типы мыслей и связей с иерархией
  (`parent_id`/`is_root`), description (комментарий для AI) и **определениями
  свойств** (key, value_type, required, options/allowed_type_ids, default) —
  агент до записи видит, что заполнять. Дополнительно: в `thoughts.create`,
  `links.create` и O1-bundle принимать тип **по имени** (`type: "Грабли"`,
  регистронезависимо по `name_key`; неоднозначность/отсутствие — ошибка со
  списком кандидатов).
- **DoD:**
  - [ ] Инструмент `etn.types.list` (оба каталога + эффективные свойства по
    цепочке наследования L21).
  - [ ] Резолв `type`-имени в create-инструментах (мысли и связи; для связи —
    по `name_forward`/`name_reverse`).
  - [ ] Спека `docs/05-mcp-server.md` §4.1/§4.2 + `docs/mcp-clients.md`;
    тесты (иерархия, unknown/ambiguous name); typecheck зелёный.

## O6. Warnings о незаполненных `required`-свойствах
- **Статус:** `todo` · **Зависимости:** F
- **Описание:** `thoughts.create` и смена типа молча пропускают незаполненные
  обязательные свойства типа — агент не узнаёт, что карточка неполная. В
  ответы изменяющих инструментов (`thoughts.create`, `thoughts.update` при
  смене `type_id`, O1-bundle) добавить неломающий блок
  `warnings: [{code: 'REQUIRED_PROPERTY_MISSING', key, …}]` по эффективному
  списку свойств типа (с учётом наследования L21). Поведение REST/клиента не
  меняется.
- **DoD:**
  - [ ] Доменная проверка required-свойств по цепочке типа.
  - [ ] `warnings` в ответах перечисленных инструментов (тип в `@etn/shared`).
  - [ ] Спека `docs/05-mcp-server.md` §4.2 + `docs/mcp-clients.md`; тесты;

## O7. MCP tool annotations
- **Статус:** `todo` · **Зависимости:** F
- **Описание:** инструменты регистрируются без аннотаций спецификации MCP —
  клиенты не могут отличить чтение от записи без ручных разрешений. Проставить
  `readOnlyHint` (все read-инструменты), `destructiveHint`
  (`thoughts.delete`, `links.delete`, `comments.delete`), `idempotentHint`
  (`set_active`, `properties.set`, upsert-семантика O1) в регистрации
  `mcp/tools.ts`.
- **DoD:**
  - [ ] Аннотации на всех инструментах; сверка с таблицей инструментов спеки.
  - [ ] Спека `docs/05-mcp-server.md` §4 (таблица с колонкой аннотаций);
    тесты на выдачу аннотаций в `initialize`/`tools/list`; typecheck зелёный.

## O8. Rate-limit записи: per-key переопределение

## O10. Метрики использования базы знаний агентами
- **Статус:** `todo` · **Зависимости:** F
- **Описание:** `thought_views` фиксирует только фокус людей; чтения через
  MCP нигде не агрегируются — владелец БЗ не видит «мёртвые зоны» (что
  никогда не находится) и перегретые узлы. Агрегированный учёт агентских
  чтений (счётчик обращений к мысли из read-инструментов: get, subgraph-узлы,
  хиты query/search) + простая выборка «топ читаемых / не читанных с даты»
  (REST или инструмент). Без записи в `audit_log` на каждое чтение —
  отдельная компактная таблица-агрегат.
- **DoD:**

## O13. (опц.) Бюджет ответа `subgraph`: `max_chars`
- **Статус:** `todo` · **Зависимости:** F, N5
- **Описание:** у `subgraph` есть лимит узлов, но нет лимита символов — 200
  узлов с `include_comments` дают ответ, не помещающийся в контекст. Параметр
  `max_chars`: сервер сам ужимает ответ под бюджет (сначала укорачивает
  превью комментариев, затем отбрасывает самые дальние от seed узлы) и честно
  сообщает `truncated`/`reason` — агент перестаёт угадывать «влезет ли».
- **DoD:**
  - [ ] Алгоритм ужатия (комментарии → дальние узлы) + признаки усечения.
  - [ ] Спека `docs/05-mcp-server.md` §4.1; тесты (бюджет меньше/больше
    ответа, порядок отбрасывания); typecheck зелёный.

## O15. (опц.) Семантический поиск: embeddings + hybrid search
- **Статус:** `todo` · **Зависимости:** F; самая дорогая задача блока
- **Описание:** FTS5 находит только точные слова/префиксы — агентские
  формулировки «своими словами» промахиваются. Задействовать
  зарезервированную таблицу `embeddings` (`02-data-model.md` §3.12): конвейер
  эмбеддинга при записи мысли/комментария (модель — конфигурируемая: локальная
  или внешний API; при недоступности — деградация до FTS), hybrid-режим в
  `etn.thoughts.search` (FTS + косинусная близость), семантические кандидаты
  в `find_duplicates`, инструмент «similar thoughts». Требует отдельного
  проектного решения (модель, хранение векторов, инкрементальный пересчёт) —
  перед реализацией согласовать дизайн с пользователем.
- **DoD:**
  - [ ] Дизайн-записка (модель, размерность, триггеры пересчёта) согласована.
  - [ ] Конвейер эмбеддинга + hybrid search + семантика в `find_duplicates`.
  - [ ] Спеки `docs/02-data-model.md` §3.12, `docs/05-mcp-server.md` §4.1;
