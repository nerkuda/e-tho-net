# Фаза O — MCP: эффективность и удобство для AI-агентов

> [← Workplan (индекс)](../workplan.md) — оглавление, статусы фаз и решения.

> По запросу пользователя (21.08.2026), по итогам исследования «что улучшить в
> архитектуре ETN/MCP для агентов» (ветка `mcp/upgrade-1`). Сквозная цель —
> использование мыслесети как базы знаний AI-агентами: меньше вызовов на
> операцию, атомарная запись «единицы знания», самоописание сети, экономия

> последним и только по отдельному решению пользователя.

## O1. Составная запись «единицы знания»: `etn.thoughts.upsert_bundle`
- **Статус:** `done` · **Зависимости:** F, N
- **Описание:** создание одной осмысленной мысли сейчас требует 5–8
  последовательных вызовов (`thoughts.create` → `comments.upsert` →
  `properties.set` × N → `links.create` × M → `attachments.add`), каждый
  промежуточный шаг неатомарен (упавший агент оставляет мысль без свойств и
  связей), а серия упирается в `max_writes_per_minute`. Новый изменяющий
  инструмент `etn.thoughts.upsert_bundle`: мысль (title, type, synonyms,
  active) + permanent-комментарий + карта свойств `{key: value}` + связи
  (направление, цель, тип) + вложения — **одной транзакцией** доменного слоя.
  Политика дублей `on_duplicate: fail | reuse | update` (по
  `find_duplicates`-матчу: `fail` — ошибка с кандидатами, `reuse` — дополнить
  существующую мысль, `update` — обновить поля) закрывает гонку двухшагового
  паттерна `find_duplicates → create` и делает повторный импорт идемпотентным.
- **DoD:**
  - [x] Типы bundle-входа/выхода в `@etn/shared`; zod-схема в `mcp/tools.ts`.
  - [x] Доменная транзакция (создание/дополнение мысли + комментарий +
    свойства + связи + вложения; корректные real-time события по каждой
    сущности).
  - [x] Политика `on_duplicate` с использованием `findDuplicates`.
  - [x] Один bundle-вызов считается одной записью для rate-лимита (см. O8).
  - [x] Спека `docs/05-mcp-server.md` §4.2 + `docs/mcp-clients.md`; тесты
    (атомарность при ошибке на середине, все три политики); typecheck зелёный.

## O2. `etn.properties.set`: несколько свойств за вызов
- **Статус:** `done` · **Зависимости:** F
- **Описание:** инструмент принимает одно свойство за вызов — заполнение
  карточки из 4–5 свойств стоит 4–5 записей. Расширить вход картой
  `values: {key: value|null}` (набор пишется одной транзакцией, `null` —
  очистка), сохранив обратную совместимость одиночной формы `key`/`value`.
- **DoD:**
  - [x] Схема входа: ровно одно из `key`+`value` / `values` (zod refine).
  - [x] Доменная запись набора значений одной транзакцией + события.
  - [x] Спека `docs/05-mcp-server.md` §4.2 + `docs/mcp-clients.md`; тесты
    (смешанные типы значений, ошибка валидации одного ключа откатывает все);
    typecheck зелёный.

## O4. Каталог типов как инструмент: `etn.types.list` + резолв типа по имени
- **Статус:** `done` · **Зависимости:** F
- **Описание:** `thoughts.create`/`links.create` требуют `type_id`, но
  получить каталог типов агент может только через resources
  (`etn://…/thought-types`), которые многие MCP-клиенты не используют, —
  либо косвенно из reference-таблиц случайных read-ответов. Новый read-only
  инструмент `etn.types.list`: типы мыслей и связей с иерархией
  (`parent_id`/`is_root`), description (комментарий для AI) и **определениями
  свойств** (key, value_type, required, options/allowed_type_ids, default) —
  агент до записи видит, что заполнять. Дополнительно: в `thoughts.create`,
  `links.create` и O1-bundle принимать тип **по имени** (`type: "Грабли"`,
  регистронезависимо по `name_key`; неоднозначность/отсутствие — ошибка со
  списком кандидатов).
- **DoD:**
  - [x] Инструмент `etn.types.list` (оба каталога + эффективные свойства по
    цепочке наследования L21).
  - [x] Резолв `type`-имени в create-инструментах (мысли и связи; для связи —

## O5. Самоописание сети: четыре markdown-поля + узловой тип раздела
- **Статус:** `done` · **Зависимости:** B (L2 — единый диалог настроек), F, O4
- **Описание:** агенту при первом подключении к сети нужно понять три вещи:
  «что в сети», «когда в неё обращаться», «по каким правилам в ней
  писать». Часть уже есть: короткое поле `description`
  (`networks.description`, задача `9330181b` — единый диалог настроек,
  L2, страница «Мыслесеть»), каталоги типов с описаниями и свойствами
  (O4). Дополнить сеть четырьмя markdown-полями и сделать **структуру
  сети** машино-читаемой — не markdown-оглавлением, которое надо вручную
  синхронизировать с мыслями (переименовал/переместил мысль — оглавление
  устарело), а ссылкой на тип мысли: владелец в настройках сети указывает
  тип «узловых разделов», и все активные мысли этого типа становятся
  структурой сети автоматически.

  Четыре markdown-поля сети (все `TEXT NULL`, редактируются владельцем):

  | Поле | Что в нём | Кто читает |
  |------|-----------|-----------|
  | `description` | Назначение сети в 1–2 абзацах (уже есть, L2) | Человек + агент при выборе сети |
  | `when_to_use` | Когда агенту обращаться к сети: список use cases, для каждого — какие ещё поля сети читать | Агент при маршрутизации между сетями |
  | `conventions` | Правила записи: формат хронологий, пометка активности, нейминг, ссылки на типы и шаблоны | Агент перед `create` / `update` |
  | `examples` | Примеры хороших и плохих записей | Агент при сомнениях по форме |

  Конвенция заполнения `when_to_use`: для каждого use case указываются
  релевантные поля сети (например, «Кодирование → structure,
  conventions»). Агент не читает все поля подряд, а берёт только нужные
  текущей задаче.

  Структура сети: в настройках сети выбирается **один тип мысли** —
  узловой раздел (`node_section_type_id`). Все активные мысли этого типа —
  узловые разделы; их постоянные комментарии описывают назначение
  раздела. Иерархия — обычными parent-child связями. Тип, указанный в
  настройках сети, удалить нельзя (проверка использования при удалении
  типа). Никаких корневых узлов отдельно не выделяется — все узловые
  мысли равноправны, агент работает с их списком.

- **DoD:**
  - [x] Миграция `_system.db`: три новых `TEXT NULL` колонки в `networks`
    — `when_to_use`, `conventions`, `examples` (`description` уже есть,
    миграция `003_networks.sql`) + `node_section_type_id` TEXT NULL
    (ссылка на тип мысли сети).
  - [x] REST: `PATCH /networks/:id` принимает новые поля +
    `node_section_type_id` (owner-only, как `display_name`/`description`);
    `GET /networks/:id` отдаёт все поля; `GET /networks` (список) отдаёт
    `description`, `when_to_use` полностью и признак `has_structure`
    (`node_section_type_id IS NOT NULL`); `conventions`/`examples` в
    списке — `null` (не раздувать ответ при большом числе сетей).
  - [x] Защита типа: удаление типа, указанного как `node_section_type_id`
    любой сети, отклоняется с понятной ошибкой (проверка использования

  - [x] MCP: `etn.networks.list` отдаёт `description`, `when_to_use`,

## O16. Контекстная типизация: `etn.types.list` с `in_subtree_of`
- **Статус:** `done` · **Зависимости:** F, O4
- **Описание:** `etn.types.list` возвращает весь каталог типов сети сразу;
  при десятках типов ответ раздувается, а агенту для работы в конкретном
  разделе нужны только типы, которые там реально используются. Добавить
  необязательный параметр `in_subtree_of` (ID мысли): сервер берёт мысли
  поддерева, собирает distinct типы мыслей и типы связей, используемые в
  нём, и возвращает только их — с описаниями, определениями свойств и
  счётчиком использования в поддереве (для типа мысли — сколько мыслей
  этого типа в поддереве; для типа связи — сколько связей между мыслями
  поддерева). Автоматический контекстный фильтр: добавил/удалил мысли —
  выборка меняется сама, ручной поддержки нет. Работает в паре с O5:
  агент получает узлы через `etn.networks.structure`, а типы раздела —
  через `types.list(in_subtree_of=<узел>)` для уточнения поиска и выбора
  типа при записи.
- **DoD:**
  - [x] Параметр `in_subtree_of` в схеме `etn.types.list` (для каталогов
    и мыслей, и связей); distinct-выборка использованных типов по
    поддереву с обходом visited-set (граф может быть циклическим) и
    лимитом; счётчики использования.
  - [x] Спека `docs/05-mcp-server.md` §4.1 + `docs/mcp-clients.md`
