# 13. Слои изменений

> Источник истины фазы **S** (workplan). До согласования этого документа код фазы
> S не пишется — задачи S2–S14 реализуют то, что здесь описано, и правят
> соответствующие места 02/03/04/05/07/08/09 (см. §16).

## TL;DR

Слой — это **copy-on-write ветка мыслесети без слова «ветка»**: пользователь или
агент работает в слое, его правки не видны остальным (кроме тех, кто явно
переключился в тот же слой), пока слой не **слит** в родителя. Слой — не снимок,
а **прозрачная плёнка поверх живой основы**: всё, что слой не перекрыл, показывает
текущее состояние предка. Строка адресуется парой (логический `id`, `layer_id`);
побеждает строка из ближайшего слоя в цепочке «текущий → предок → … → основа».
Глубина — до 4 слоёв, 5 уровней вместе с основой.

## 1. Терминология

| Понятие | Русский термин | Идентификатор в коде |
|---|---|---|
| Copy-on-write ветка мыслесети | **слой изменений** (кратко — **слой**) | `layer` |
| Корень иерархии слоёв, обычное состояние сети | **основа** | `base` |
| Перенос правок слоя в родителя с перезаписью | **слить слой в основу** / **слияние** | `merge` |
| Логическая строка удалена в слое, но жива у предка | **надгробие** | `deleted` / tombstone |
| Автоматически создаваемый слой-снимок перед слиянием | **резервный слой** | service layer, `is_service = 1` |
| Мысль/связь, у которой в текущем слое есть более новая версия | **перекрытая** мысль/связь | `overridden` |

**Слово «ветка» в контексте мыслесети запрещено** — в проекте оно означает
только ветку git (поле `git_branch` слоя, см. §2.2). Использование слова
«ветка» применительно к слою — ошибка терминологии, а не стиля: она порождает
ложные git-ожидания (быстрое переключение, дешёвое существование множества
веток, слияние как в VCS), которых слой не даёт.

## 2. Модель

### 2.1. Иерархия

Слои образуют дерево с единственным корнем — **основой**. Основа не «слой без
родителя», а материализованная строка в той же таблице `layers`
(`is_base = 1`, ровно одна на сеть, `parent_id = NULL`), потому что адресация
строк парой `(id, layer_id)` требует, чтобы `layer_id` был всегда определён —
`NULL` для базовых строк сломал бы `UNIQUE (id, layer_id)` (SQLite считает NULL
различными для UNIQUE, то есть не гарантировал бы уникальность). Основа создаётся
одновременно с мыслью HOME при инициализации сети, `is_protected`-семантика та
же: удалить, переименовать или перевести в служебные нельзя.

Глубина: **до 4 обычных слоёв поверх основы, 5 уровней считая основу**
(`base → L1 → L2 → L3 → L4`). Создание слоя с родителем на 4-м уровне — 422
`VALIDATION_ERROR`. Резервные слои (§8.2) в счётчик глубины не входят — они не
предназначены для работы и не выбираются пользователем, поэтому ограничение
глубины на них не распространяется.

### 2.2. Метаданные слоя

Таблица `layers` (`networks/<id>/data.db`, не ветвится — см. §3):

| Столбец | Тип | Описание |
|---|---|---|
| `id` | TEXT PK | UUID |
| `parent_id` | TEXT FK → layers.id | `NULL` только у основы |
| `title` | TEXT NOT NULL | Имя слоя. У основы фиксировано («Основа»), не редактируется |
| `comment` | TEXT | Необязательный, но настоятельно рекомендуемый — по нему агент и коллега понимают назначение слоя, не расспрашивая автора |
| `git_branch` | TEXT | Необязательная строка. Ничем не проверяется автоматически на MVP; зарезервировано под будущий скрипт сверки с `git branch`, который покажет слои, чья ветка давно слита, а слой висит |
| `is_service` | INTEGER NOT NULL DEFAULT 0 | 1 — резервный слой (см. §8.2): не показывается в списке выбора |
| `is_base` | INTEGER NOT NULL DEFAULT 0 | 1 ровно у одной строки на сеть |
| `depth` | INTEGER NOT NULL | Денормализованная глубина (0 — основа), для быстрой проверки лимита §2.1 |
| `created_by` | TEXT NOT NULL | user_id |
| `created_at` | TEXT NOT NULL | ISO-8601, точность до секунды |
| `last_activity_at` | TEXT NOT NULL | Момент последней записи в любую ветвимую строку этого слоя (не время правки метаданных слоя) — чтобы находить заброшенные |
| `version` | INTEGER NOT NULL DEFAULT 1 | Версия строки слоя для `expected_version` при переименовании/правке комментария — сама таблица `layers` не ветвится, обычная оптимистическая блокировка |

### 2.3. Жизненный цикл

1. **Создание.** От указанного родителя (по умолчанию — текущий слой сессии,
   см. §7). Обязателен `created_by`; `comment` необязателен, но интерфейс и MCP
   обязаны его предлагать (см. §16.3, §16.5). Глубина проверяется на создании.
2. **Работа.** Все чтения и записи выполняются в контексте выбранного слоя
   сессии (§7). Слой живёт сколько угодно, `last_activity_at` обновляется при
   каждой записи.
3. **Слияние** (§8) — полное или частичное. Слитые строки удаляются из слоя
   (не помечаются надгробием — они физически ушли к предку, хранить в слое
   больше нечего). Слой как сущность (метаданные) при этом не удаляется
   автоматически — это отдельное действие пользователя/агента.
4. **Удаление.** См. §2.4.

### 2.4. Удаление слоя

Удаление слоя с потомками — вопрос, который S7 и S11 оставили этой
спецификации. Решение: **удаление слоя каскадно удаляет все его слои-потомки**
(поддерево целиком), а не только сам слой — частичное удаление («удали слой,
но оставь его детей осиротевшими на слое-деде») создаёт дыру в цепочке
разрешения, которую пришлось бы разруливать индивидуально для каждого потомка.
Это решение с высокой ценой ошибки, поэтому:

- REST и MCP требуют явного подтверждения — `DELETE …?cascade=<N>`, где `N` —
  число потомков, которое клиент/агент получил из ответа списка слоёв
  (`children_count`) и обязан передать обратно; несовпадение — 409, ответ без
  него при `children_count > 0` — 422 с телом `{ children_count }`;
- клиент показывает диалог с числом потомков и коротким списком их
  заголовков перед удалением — тот же паттерн, что и у разрушительных команд
  «Структур» (08-ui-spec.md §15.3.1: подтверждение с числом затрагиваемых);
- удаление слоя **физически удаляет все его теневые строки и надгробия**
  (не переносит их предку — это не слияние);
- **основу удалить нельзя** — 422 независимо от прав;
- **клиенты, сидящие на удаляемом слое** (или на любом из его потомков),
  переключаются сервером на родителя удаляемого слоя и получают
  `layer.deleted` (см. §12) — это полный ресинк, а не «слой стал недоступен»;
- сразу после удаления — автоочистка корзины: удаление слоя снимает часть
  удерживающих ссылок (02-data-model.md §3.1.2, S13, §6.3 ниже; серверный
  вызов — тот же `POST /trash/purge`, что и у ручной очистки, 03-server-api.md
  §14b).

## 3. Ветвимые и неветвимые таблицы

Список закрыт — расширять его при реализации отдельных задач S2–S14 нельзя
без правки этого документа.

**Ветвимые** (получают `layer_id`, адресация строки — пара `(id, layer_id)`,
`UNIQUE (id, layer_id)`, первичный ключ — суррогатный):

`thoughts`, `thought_synonyms`, `links`, `thought_types`, `link_types`,
`type_properties`, `type_property_overrides`, `property_values`, `comments`,
`comment_targets`, `attachments`. Плюс FTS-индексы `fts_thought_names`,
`fts_thought_texts`, `fts_link_texts` — не в смысле copy-on-write (это
автономные, не external-content таблицы, см. 02-data-model.md §3.11), а в
смысле «несут `layer_id UNINDEXED`» — подробности в §9.

**Порядок связей** (задача T1, отдельная от фазы S, но обязана быть готова до
S2) переносится из пер-пользовательской `user_focus_order`
(02-data-model.md §3.10.4) в поле самой строки `links` — значит физически
переезжает из неветвимого в ветвимое: порядок копируется в слой вместе со
связью и участвует в слиянии (см. §6.5).

**Неветвимые** (без `layer_id`, общие для всех слоёв сети): `layers` (сама
таблица слоёв), `event_log` (событие несёт слой как атрибут полезной
нагрузки, но не ветвится — см. §12), `thought_read_metrics`,
`user_preferences` (серверные, `_system.db` и сетевые), `thought_views`,
`user_focus_preferences`, `saved_filters`, `user_pinned_thoughts`,
`embeddings` (зарезервировано). Обоснование: это либо персональное состояние
пользователя (не относится к содержанию сети), либо служебные метрики/журнал,
которым семантика «вариант содержания» не нужна.

## 4. Семантика чтения

### 4.1. Правило разрешения

Для логического `id` в контексте слоя `L` строится цепочка предков
`L → parent(L) → … → base` (глубина ≤ 5). Побеждает строка из **ближайшего**
слоя цепочки, где строка для этого `id` вообще есть (неважно — обычная или
надгробие). Если победившая строка — надгробие, логическая сущность **не
видна** в этом слое, даже если у более дальнего предка есть неудалённая
версия.

### 4.2. Механизм: представления поверх временной таблицы цепочки

Правило не должно писаться в каждом запросе — иначе забытый запрос станет
утечкой чужого слоя в ответ. Решение:

1. При открытии соединения (пул ключуется парой `(network_id, layer_id)`,
   не только `network_id`, — с WAL и `better-sqlite3` это допустимо: писатель
   всё равно один) заполняется временная таблица `layer_chain(layer_id,
   depth)` — обход `layers.parent_id` от `L` до `base`, `depth = 0` у `L`,
   возрастает к основе.
2. На каждую ветвимую таблицу заводится представление (`thoughts_v`,
   `links_v`, `thought_types_v`, `link_types_v`, `type_properties_v`,
   `type_property_overrides_v`, `property_values_v`, `comments_v`,
   `comment_targets_v`, `attachments_v`), которое джойнит физическую таблицу с
   `layer_chain`, выбирает строку с минимальной глубиной, затем отфильтровывает
   `deleted = 1`. Норма — семантика «минимальная глубина», а не конкретная
   SQL-конструкция: при `UNIQUE (id, layer_id)` оконная функция
   `ROW_NUMBER() OVER (PARTITION BY id ORDER BY depth ASC)` и анти-джойн
   «NOT EXISTS строки того же id из более близкого слоя» эквивалентны;
   реализация (S3) использует анти-джойн, потому что SQLite не проталкивает
   предикат вызова (`WHERE id = ?`) сквозь оконную функцию — точечный lookup
   по представлению деградировал бы до полного прохода с сортировкой.
   Представление также экспонирует `rowid` физической строки-победителя: FTS
   джойнится с ним (`comments_v.rowid = fts_thought_texts.rowid`), а rowid
   теневой строки слоя не равен rowid строки основы того же логического id.
3. **Репозитории читают только из представлений** и о слоях не знают.
   Обязательный тест/линт-правило: прямое чтение физических таблиц в доменном
   слое запрещено и должно быть обнаружимым (S3, S12).

Это правило действует **во всех чтениях без исключения**: `query`, `search`,
`subgraph`, `neighbors`, `path`, `usage`, `mentions`, `backlinks`, а также
внутренние выборки для валидации при записи и слиянии.

### 4.3. FTS — особый случай

FTS5 сначала ранжирует, потом видимость слоя фильтруется поверх результата
(детали и последствия для пагинации — §9).

## 5. Семантика записи

### 5.1. Материализация теневой строки

Первая запись по логическому `id` в слое, где строки для этого `id` ещё нет,
**материализует теневую строку**: копия разрешённой (§4.1) строки предка с
применёнными изменениями, плюс:

- `layer_id` = текущий слой;
- `version` — **продолжает нумерацию предка**, а не начинается с 1: копируется
  текущая версия разрешённой строки предка, затем обычным образом
  инкрементируется при каждой следующей правке в этом же слое. Это сохраняет
  привычную семантику `expected_version`/`If-Match` — клиент всегда сверяется
  с последней увиденной версией независимо от того, в каком слое она была
  прочитана;
- `base_version` — **версия строки предка на момент материализации**,
  записывается один раз и больше не меняется. Используется только при
  слиянии (§8) для детекции конфликта — она не участвует в обычном
  `expected_version`-контроле записи внутри слоя.

Последующие записи по тому же `id` в том же слое — обычный `UPDATE` теневой
строки: `version` растёт, `base_version` не трогается.

### 5.2. Удаление — тоже материализация

Удаление логической строки в слое — не физический `DELETE`, а материализация
теневой строки с `deleted = 1` (надгробие) по тем же правилам версий из §5.1.
Надгробие **обязано** нести `base_version` — иначе оно молча затёрло бы при
слиянии правку, сделанную в предке уже после создания слоя (проверка §8.1
не сработает без него).

Прикладной каскад удаления (S4): удаление мысли в слое материализует
надгробия для **всех** её зависимых строк в этом слое — собственных связей
(с обеих сторон), комментариев, значений свойств, синонимов, привязок
вложений — по тем же правилам версий. Дети мысли **не удаляются**: каскад
задевает строки связей, а не дочерние мысли — ребёнок остаётся, но теряет
эту связь.

**Связь с невидимым концом.** Конец связи может быть скрыт надгробием в
цепочке текущего слоя и независимо от самой связи (каскад — лишь один из
путей, конец мог быть скрыт раньше). Связь, у которой хотя бы один конец не
разрешается в живую мысль, **невидима в этом слое целиком** — иначе чтения
начнут отдавать висячие рёбра. Фильтр встроен в представление `links_v`
(§4.2), а не пишется в каждом прикладном запросе.

### 5.3. Вложения — файл один на все слои

Физический файл вложения на диске общий для всех слоёв (сама привязка
`attachments` — ветвимая, файл — нет). Удаление в слое ставит надгробие
привязке; физическое удаление файла допустимо только когда счётчик ссылок по
**всем** слоям сети обнулился — иначе удаление в слое сломает основу и другие
слои.

## 6. Связи в слоях

Связь — не обычная строка: её идентичность — `id`, а смысл — тройка
`(source_id, target_id, type_id)` с `UNIQUE` в пределах слоя. Отсюда
расхождения с обычным copy-on-write.

### 6.1. Смена концов — не `UPDATE`

Изменение `source_id`/`target_id` связи в слое — это надгробие старой связи
плюс создание новой (со своим новым `id`). При слиянии старая связь удаляется
физически, новая создаётся в основе. `UPDATE`-семантику (правка теневой
строки на месте) сохраняют смена типа, стиля, порядка и свойств связи — они
не меняют идентичность тройки.

### 6.2. Логический дубль — схлопывается, а не отклоняется

Два независимых слоя могут создать `A → B` одного типа — это две строки с
разными `id`, сверка `base_version` их не видит (у обеих нет общего предка).
При слиянии второй из них в ту же цель поиск дубля идёт **по тройке**
`(source_id, target_id, type_id)` в целевом слое; найден — схлопывается
(новая связь не создаётся, но если у сливаемой связи изменены порядок/стиль/
свойства — эти правки применяются к уже существующей).

### 6.3. Помеченный на удаление конец не блокирует создание связи

Если один из концов новой связи помечен в корзину (S13), но ещё не удалён
физически, связь всё равно создаётся при слиянии — мысль остаётся
помеченной, а не превращается в висячую ссылку. Это работает только потому,
что проверка перед **физическим** удалением из корзины обязана учитывать не
только теневые строки самой мысли, но и теневые строки связей, у которых эта
мысль — конец. Правило — пункты 2–3 блокировки в 02-data-model.md §3.1.2;
здесь подтверждается как инвариант слоёв (проверяется тем же эндпоинтом
`deletion-check`, 03-server-api.md §6.5a, а не отдельной логикой слияния).

### 6.4. Остаточный случай: конец физически отсутствует

Если к моменту слияния конец связи всё же отсутствует физически (был
безвозвратно удалён из корзины по всем слоям) — связь **не создаётся**,
но слияние в целом **не отклоняется**: факт идёт отдельной строкой в отчёт
о слиянии (§8.3). Это единственное расхождение с общим правилом
«конфликт → отказ всей операции» (§8.1) — здесь конфликта в смысле
одновременной правки нет, есть просто утраченная цель.

### 6.5. Порядок связей ветвится вместе со связью

По решению T1 порядок — отдельное поле строки `links`, общее для всех, без
персональных перекрытий (§3). Следствие: массовое переупорядочивание N
дочерних связей — это N изменённых строк и потенциально до N конфликтов при
слиянии. Отчёт о слиянии обязан **сворачивать** такую пачку в одну позицию
«изменён порядок у N связей узла X», а не показывать N отдельных отказов —
конкретный UI сворачивания проектирует S11 (клиентский дифф), это
спецификация лишь фиксирует требование к отчёту.

### 6.6. Концы связи в слой не копируются

Рассматривался и отклонён вариант «при правке связи копировать в тот же слой
обе связанные мысли»: копия замораживает мысль (правки из основы перестают в
неё протекать — противоречит прозрачности слоя, §11.1), замороженная копия
попадает под сверку `base_version` и слияние начинает отказывать из-за
мыслей, которых никто по существу не трогал, а дополнительной гарантии
целостности копия не даёт — защита всё равно держится на проверке из §6.3
(и 02-data-model.md §3.1.2) перед физическим удалением. Если сканирование
теневых связей при проверке корзины окажется дорогим на практике, вместо
копии допустимо вести **индекс удержаний** (слой → множество `id`
удерживаемых мыслей) — это индекс, а не копия, он ничего не замораживает;
вводится по необходимости, не в MVP фазы S.

### 6.7. Тип связи, созданный в слое, — часть замыкания

`type_id` связи — тоже ссылка на ветвимую сущность (§3, S5), просто про неё
легко забыть, потому что она не «конец». Замыкание при частичном слиянии
(§8.1) обязано включать типы наравне с концами.

## 7. Передача слоя, права, эхо

### 7.1. Текущий слой сессии

Текущий слой запоминается **на сервере** как умолчание сессии (по клиенту,
как и прочее в 11-settings-and-state.md). Скрытое состояние опасно тем, что
после перезапуска клиента можно случайно писать не туда — поэтому:

**Каждый ответ на запись (REST и MCP) обязан содержать эхо текущего слоя** —
`meta.layer: { id, title }`. Это делает запись в чужой слой обнаружимой
сразу, а не по последствиям. Ответы на чтение эхо слоя не несут — они и так
неявно определены слоем сессии, а раздувать каждый список полем ради
единообразия не оправдано; исключение — список слоёв (§10.1), где сервер явно
отмечает, какой из перечисленных элементов текущий.

### 7.2. Права

У всех, кто имеет доступ к мыслесети, права на слои одинаковые: любой
участник создаёт, выбирает, сливает и удаляет любой слой. Разделение прав —
отдельная задача за пределами фазы S, после того как структуры и метаданные
устоятся (потенциальная ценность: агенту, которому не доверяешь писать в
основу, выдать ключ, прибитый к слою-песочнице).

## 8. Слияние

### 8.1. Алгоритм и детекция конфликтов

Слияние слоя `L` в родителя `P` — это **посрочный реплей** финального
состояния каждой затронутой логической строки `L` в `P`, с теми же
правилами версий, что и у обычной записи: `base_version` теневой строки
играет роль `expected_version`/`If-Match` относительно текущей версии этой же
строки в `P`.

Порядок для набора строк: **надгробия → обновления → вставки** — иначе новая
строка с той же тройкой `(source, target, type)` упрётся в ещё не удалённую
старую (актуально для связей, §6.2).

**Детекция конфликта.** «Затереть» безопасно только если строка в `P` не
менялась с момента, на который указывает `base_version`. Сравнение идёт для
**каждой** затронутой строки; при **любом** расхождении вся операция слияния
отклоняется целиком (422) со списком расхождений — это не разрешение
конфликтов, а превращение тихой потери данных в сообщение. Частичного
применения «то, что сошлось — слито, остальное — нет» не бывает: атомарность
важнее удобства повторного вызова.

**Замыкание при частичном слиянии.** Выбранное пользователем/агентом
подмножество строк обязано быть замкнуто по ссылкам: концы связей, типы (§6.7),
владельцы комментариев и вложений — либо уже есть в `P`, либо входят в то же
слияние. Сервер **не расширяет** набор автоматически (это скрыло бы от
пользователя, что реально уехало в основу) — при незамкнутом наборе операция
отклоняется (422) со списком недостающих ссылок; клиент/агент дополняет
выбор и повторяет вызов.

Исключение из «конфликт → отказ»: остаточный случай §6.4 (физически
отсутствующий конец связи) — не блокирует слияние, только не создаёт связь и
попадает в отчёт.

### 8.2. Резервный слой

Перед перезаписью строк в `P` их текущее (до-слияния) содержимое копируется в
автоматически создаваемый **служебный слой** — дочерний по отношению к `P`,
`is_service = 1` (скрыт из списка выбора, §2.2), с автосгенерированным
комментарием («резерв: слияние «{L.title}» → «{P.title}», {timestamp}»).
Механизм копирования тот же самый copy-on-write — взамен появляется
возможность отката слияния (ручного, через сравнение с резервным слоем),
которой иначе не было бы вообще. Резервные слои не считаются в лимит глубины
(§2.1) — они не предназначены для работы.

### 8.3. Отчёт о слиянии

Ответ на успешное слияние обязан содержать:

- `applied` — сколько логических строк перенесено (по таблицам);
- `skipped` — остаточные случаи §6.4 (связь на физически отсутствующий конец) —
  список с причиной;
- `reorder_collapsed` — свёрнутые пачки переупорядочивания (§6.5), формат
  `{ thought_id, count }` вместо N отдельных позиций;
- `reserve_layer_id` — id созданного резервного слоя (§8.2).

Ответ на отклонённое слияние (422) содержит `conflicts: [{ table, id,
expected_base_version, current_version }]` и, отдельно, `missing_closure:
[{ table, id, referenced_by }]`, если причина — незамкнутость набора (§8.1).

### 8.4. После слияния

Успешно слитые строки **удаляются из слоя `L`** физически (не надгробием —
они и так ушли к предку, хранить в `L` больше нечего; после полного слияния
слой `L` пустеет относительно `P`, но как сущность не удаляется автоматически
— это отдельное действие, см. §2.4). Сразу после слияния — автоочистка
корзины: слияние снимает удерживающие ссылки так же, как удаление слоя
(02-data-model.md §3.1.2; серверный вызов — `POST /trash/purge`,
03-server-api.md §14b).

## 9. Полнотекстовый поиск (S6)

FTS-таблицы (`fts_thought_names`, `fts_thought_texts`, `fts_link_texts`) —
автономные, не external-content, синхронизируются триггерами
(02-data-model.md §3.11), поэтому добавление `layer_id UNINDEXED` не требует
пересборки индекса. Ловушка: FTS5 сначала ранжирует, **потом** нужно
отфильтровать по видимости (§4.1) и дедуплицировать по логическому `id` —
`LIMIT` нельзя протолкнуть внутрь `MATCH`. На объёмах MVP (тысячи мыслей)
решение — фильтрация и дедупликация в CTE поверх результата FTS, скан шире
запрошенной страницы. Следствие, которое нужно честно документировать в
03-server-api.md: `meta.total_in_group` для полнотекстового поиска в слое
считается **после** дедупликации, то есть может быть дороже или чуть
неточнее (граница страницы) обычного `COUNT`. Надгробия исключают строку из
выдачи, даже если в основе текст найден.

Механизм фильтрации — rowid-джойн индекса с представлением-разрешателем
(`thoughts_v.rowid = fts_thought_names.rowid`,
`comments_v.rowid = fts_thought_texts.rowid`): rowid FTS-строки — `pk`
физической строки, представление экспонирует rowid победителя (§4.2), значит
матчится только текст строки-победителя. Отсюда два следствия: дедупликация
по логическому `id` получается «бесплатно» (одна FTS-строка на победителя) и
агрегатный текст индекса имён (`title` + синонимы **того же слоя**) перестаёт
искаться по унаследованным синонимам, как только строка мысли перекрыта в
цепочке слоя — до перекрытия синонимы предка продолжают находиться через его
строку. Синонимные триггеры не включают надгробия в агрегат (миграция 026):
синоним, удалённый в слое, выпадает из текста строки слоя, а не остаётся в
нём.

## 10. REST, MCP, клиент — обзор (детали в 03/05/07/08)

Этот раздел — сводка контракта, чтобы задачи S7/S10/S11 стартовали с общего
понимания. Формат маршрутов, инструментов и экранов — их предмет.

### 10.1. Ресурс слоёв (S7 → 03-server-api.md)

Список с иерархией и метаданными (§2.2), создание от указанного предка,
переименование, правка комментария, удаление (§2.4), переключение текущего
слоя сессии. Список по умолчанию скрывает служебные слои (`is_service = 1`).
Слияние — отдельный маршрут (§8), не CRUD-операция над ресурсом слоёв.
Каждый элемент списка несёт признак «это текущий слой сессии».

### 10.2. MCP (S10 → 05-mcp-server.md)

По стандарту «Паритет возможностей»: агент должен уметь всё то же, что
пользователь в клиенте, — список слоёв и текущий слой, создание (с
запрошенным комментарием), переименование, удаление, переключение,
слияние (полное и частичное) с отчётом об отказе. **Все существующие
инструменты чтения и записи обязаны уважать слой сессии**, а не только новые
— это не отдельный набор инструментов, а сквозное свойство существующих.
Эхо слоя (§7.1) обязательно в ответе каждого пишущего инструмента.

### 10.3. Клиент (S11 → 07/08)

Меню «Основа» рядом с меню «Мыслесеть»: список слоёв + «Создать новый слой»;
выбор слоя меняет заголовок самого меню на его имя (заголовок и есть
постоянный индикатор «где я сейчас»); при выбранном слое добавляются
«Слить слой в основу» и «Удалить слой». Диалог создания объясняет механику
одной строкой, предлагает комментарий и (если уместно) ветку git. Слой —
свойство таба, а не окна (после фазы Q это позволяет сравнивать два слоя
рядом).

**Дифф — двумя способами:** содержательный (текстовый дифф собранных из сети
документов, дешёвый при детерминированной сборке — T2) и структурный по
связям (обязателен отдельно, т.к. текстовый дифф слеп к смене типа связи,
добавлению «см. также», перецепке без изменения иерархии разделов — ровно
тот случай, ради которого слои и заводят). Семантику структурного диффа
задаёт §6; форму его показа проектирует S11.

## 11. Явные ограничения

Осознанные следствия модели «слой — плёнка, а не снимок» (§0/TL;DR):

- **Состояние слоя на прошлую дату невоспроизводимо.** Слой видит текущую
  основу, а не основу-на-момент-создания — история пересчитывается заново
  при каждом чтении.
- **«Отличие слоя» двусмысленно** и требует двух разных ответов: относительно
  основы-сейчас (для показа пользователю, §10.3) и относительно
  основы-на-момент-создания слоя (для слияния, §8.1, через `base_version`).
- **Логическое противоречие с основой не обнаруживается**, если строки не
  перекрываются: если слой не тронул строку, а основа тем временем изменила
  её так, что это стало противоречить содержимому слоя в другом месте, —
  система об этом не узнает. Обнаружение противоречий вне пересечения строк
  не входит в фазу S.
- **Слияние не разрешает конфликты, только детектирует.** Разрешение
  (three-way merge с выбором стороны) — за пределами фазы S.
- **Разделение прав по слоям не входит в фазу S** — у всех участников сети
  права на слои одинаковые (§7.2).

## 12. Real-time и MCP-дельта-фид (S9 → 04-realtime.md)

Правило видимости для подписчика в слое: он **должен** получать события
основы по строкам, которые не перекрыл в своём слое (они ему видны через
§4.1), и **не должен** — по перекрытым. Рассылка становится вычислением
видимости на подписчика (дёшево: есть ли у его слоя теневая строка для этого
`id`), а не широковещанием без разбора.

**Переключение слоя — полный ресинк.** `last_seq` глобален по сети; после
смены слоя кэш клиента (и `etn.changes.list` у агента) невалиден целиком —
сервер отдаёт `truncated: true`, требуя полной пересинхронизации, а не
пытается прислать дельту с учётом смены контекста.

Слияние может породить лавину событий в основе. Решение (принято в S9,
детали — 04-realtime.md §11.4): слияние эмитит **ровно одно** событие
`layer.merged` (`audience = "network"`, `layer_id` — слой-цель) с отчётом
слияния §8.3 в данных; получив его, клиент и агент выполняют полный ресинк
видимого состояния. Поштучной рассылки строк слияния нет.

## 13. Типы и определения свойств в слоях (S5)

Copy-on-write распространяется на `thought_types`, `link_types`,
`type_properties`, `type_property_overrides` наравне с содержательными
таблицами (§3) — без этого типичное «добавить тип и свойство» в слое сразу
становится видно всем, и слой теряет половину смысла. Наследование свойств
(L21, 02-data-model.md §3.4.1) считается по **разрешённой** (§4.1) цепочке
типов, а не по сырым строкам физической таблицы. Мысль в основе не может
ссылаться на тип, созданный только в слое, — при слиянии это проверяется
через замыкание (§8.1, §6.7): `type_id` мысли/связи участвует в замыкании
так же, как и `type_id` связи.

## 14. Экспорт/импорт `.etnx`

Выгружается то, что выбрано у пользователя или агента на момент экспорта:
выбрана основа — выгружается основа, выбран слой — выгружается **разрешённое
по §4.1 состояние этого слоя** (то есть плёнка вместе со всем, что она не
перекрыла у предков), а не только теневые строки слоя как таковые — иначе
экспорт слоя без большинства мыслей сети был бы бесполезен. Импорт кладёт
результат в **текущий выбор** целевой сессии (основу или слой) — импортёр не
знает и не восстанавливает исходную слоистую структуру источника, он видит
уже разрешённый граф. Затрагивает фазу P и задачу O17; формат манифеста
(02-data-model.md §9) не меняется — слой не является полем `.etnx`, это
свойство того, **что** экспортируется, а не того, как записан экспортируемый
граф.

## 17. Вне рамок фазы S

- Разделение прав по слоям (§7.2, §15) — будущая задача, после того как
  структуры и метаданные устоятся.

  даёт только детекцию (§8.1) и резервный слой как ручной путь отката (§8.2).
- Автоматическая сверка `git_branch` со состоянием репозитория (§2.2) —
  поле зарезервировано, скрипт сверки не входит в MVP фазы S.
- Обнаружение логических противоречий без пересечения строк (§11).
