## /activity — лента, свёртка и обрезка журнала активности

Чтение и обслуживание журнала активности.

```
GET  /api/v1/networks/{nid}/activity
     ?from_ms&to_ms&user_id&entity_type&entity_id&limit&offset
     → 200 { data: [ { id, user_id, user_name, action, entity_type,
                       entity_id, entity_title, layer_id, occurred_at_ms } ] }
POST /api/v1/networks/{nid}/activity/rollup   { until_ms }  → 200 { removed, kept }
POST /api/v1/networks/{nid}/activity/truncate  { until_ms }  → 200 { removed }
```

- фильтры комбинируются (период × пользователь × сущность); сортировка по `occurred_at_ms` убыв.; пагинация `limit`/`offset`;
- `rollup`/`truncate` необратимы; сервер возвращает счётчики удалённых/оставшихся записей;
- запись журнала отдельной операцией не редактируется (append-only).

---

**Термины (глоссарий 10).** **Свёртка** (`rollup`) — агрегация повторяющихся событий журнала в одну запись со счётчиком за окно времени. **Обрезка** (`truncate`) — ретенция старых записей журнала по порогу. Авто-свёртка журнала выполняется при слиянии или удалении слоя.

## etn.layers.* — управление слоями через MCP

**Актуализация 0.8.4 (задача 09f19952).** Отдельными MCP-инструментами из этого набора остались только `etn.layers.list` и `etn.layers.select`; остальные — действия исполнителя `etn.ops { action, params, confirm }`: `layers.create`, `layers.update`, `layers.delete` (confirm), `layers.diff` (read-only), `layers.diff_doc` (read-only), `layers.merge` (confirm). Читать таблицу ниже следует как описания этих действий, а не отдельных инструментов; состав `params` — `etn.guide { topic: "layers.create" }` (аналогично для остальных действий).

Агент получает **полный паритет** с пользователем в клиенте и с REST по работе со слоями: восемь управляющих инструментов плюс сквозная слоистость всех остальных.

| Инструмент | Аннотация | Назначение |
|---|---|---|
| `etn.layers.list` | read-only | все слои сети с иерархией (`parent_id`, `depth`, `comment`, `git_branch`, `children_count` — число для подтверждения cascade при удалении) и `current: true` у слоя вызывающего ключа; `include_service?` показывает служебные резервные слои |
| `etn.layers.diff` | read-only | структурное отличие слоя от цели **постранично** (актуализация 0.10.3, задача `ddb67ddc`): 7 секций — `links.added|removed|type_changed|reorder_collapsed|reparented`, `overridden.thought_ids|link_ids`; params `sections?` (подмножество секций, неизвестная — `VALIDATION_ERROR`), `limit?` (1…1000, дефолт 200 — верхняя граница: страница дополнительно ужимается байтовым бюджетом ≈48 КБ), `cursor?` (keyset `next_cursor` предыдущей страницы, детерминированная сортировка секция+id — ADR `5f6cb775`); в каждом ответе `counts` по всем секциям, `truncated` + `reason`, `next_cursor`; вызов без параметров в MCP — первая страница (гарантия бюджета `maxModelBytes`), не полный отчёт |
| `etn.layers.diff_doc` | read-only | содержательное отличие: два детерминированных markdown-документа (`layer_doc`/`target_doc`) для построчного сравнения. **Не пагинируется и не секционируется** (0.10.3): на больших слоях ответ огромен (ориентир: слой ~1142 перекрытых строк → ~17,5 МБ) — инструмент для малых слоёв и точечного аудита; большие слои — через `layers.diff` по секциям/страницам |
| `etn.layers.create` | — | создать слой; `parent_id` по умолчанию — текущий слой ключа; `comment` настоятельно рекомендуется — по нему следующий агент поймёт назначение слоя; сессию не переключает |
| `etn.layers.update` | idempotent | переименовать/править комментарий; название основы фиксировано (422) |
| `etn.layers.delete` | destructive | удалить слой с поддеревом потомков; при `children_count > 0` обязателен `cascade` с этим числом (несовпадение — 409); физически удаляет тени и надгробия, автоочищает корзину; сессия ключа автоматически переключается на родителя |
| `etn.layers.select` | idempotent | переключить текущий слой ключа — все последующие вызовы (чтение и запись) идут в нём; служебный слой выбрать нельзя; повторный выбор того же — no-op |
| `etn.layers.merge` | destructive | слить слой в родителя: полностью или частично замкнутым подмножеством `tables`; конфликт версий или незамкнутость отклоняет всю операцию (422) — частичного применения не бывает; успех `{applied, skipped, reorder_collapsed, reserve_layer_id, purged}` + одно событие `layer.merged` |

**REST-паритет пагинации (0.10.3, задача `ddb67ddc`).** `GET /networks/:networkId/layers/:layerId/diff` принимает те же `sections`/`limit`/`cursor` (query; несколько `sections` повтором параметра); **без параметров — прежний полный отчёт** (совместимость текущего клиента до его перевода на страницы — задача `52c776f1`), с любым из параметров — страница той же формы, что MCP.

**Сверх паритета (13-layers.md §8.5, §10.2).** Агент получает путь аварийного согласования, которого нет у пользователя: `layers.conflicts` (read-only — предпросмотр строк, из-за которых слияние будет отклонено) и `layers.reset_override` (destructive, `confirm` — перепривязка `base_version` названных строк к актуальной основе). REST-маршрута и пункта меню клиента у них нет.

**По-мысленный текстовый дифф (0.10.3, задача `52c776f1`).** REST-аналог в MCP отсутствует (клиентская потребность): `GET /layers/{id}/diff/thought/{thoughtId}` — точечное сопоставление полей мысли (элемент спеки `622d246d`). Диалог отличий клиента строится на постраничном структурном диффе и по-мысленном диффе; `diff_doc` клиентом больше не вызывается.

## layers — таблица слоёв изменений

Сама таблица слоёв изменений внутри БД сети. Сама она **не ветвится**.

| Столбец | Тип | Описание |
|---|---|---|
| `id` | TEXT PK | UUID |
| `parent_id` | TEXT FK → layers.id ON DELETE CASCADE | `NULL` только у основы. Каскад: удаление слоя удаляет всё поддерево слоёв вместе с теневыми строками |
| `title` | TEXT NOT NULL | Имя слоя. У основы фиксировано и не редактируется |
| `comment` | TEXT | Необязателен, но настоятельно рекомендуется |
| `git_branch` | TEXT | Необязательная ветка репозитория; автоматически не проверяется |
| `is_service` | INTEGER NOT NULL DEFAULT 0 | 1 — резервный слой, не показывается в списке выбора |
| `is_base` | INTEGER NOT NULL DEFAULT 0 | 1 ровно у одной строки на сеть |
| `depth` | INTEGER NOT NULL | Денормализованная глубина (0 — основа) |
| `created_by` | TEXT NOT NULL | У засеянной миграцией основы — `system` |
| `created_at` | TEXT NOT NULL | ISO-8601, точность до секунды |
| `last_activity_at` | TEXT NOT NULL | Момент последней записи в любую строку слоя — чтобы находить заброшенные |
| `version` | INTEGER NOT NULL DEFAULT 1 | Обычная оптимистическая блокировка метаданных |

Индексы: по `parent_id`, частичный по служебным слоям.

**Основа.** Ровно одна на сеть, создаётся миграцией одновременно с инициализацией БД — то есть существует ещё до первой мысли. Её нельзя удалить, переименовать или перевести в служебные.

**Фиксированный id основы** одинаков во всех сетях и задан константой в общем пакете. Он же стоит значением по умолчанию в ветвимых таблицах — поэтому код, ничего не знающий про слои, пишет в основу без изменений.

**Глубина** ограничена четырьмя обычными слоями поверх основы.

### colors — цветовая индикация слоя (0.6.4)

Столбец `colors` (миграция `031_layer_colors.sql`) — JSON-объект `{ focus_stripe, background }`, каждый ключ — пара тем `dark`/`light` в формате `#rrggbb`. У основы всегда `NULL`; у не-основного слоя `NULL` — сигнал «клиент применит дефолтные цвета создания». Назначение цветов основе — 422. Миграция `033_authorship_columns.sql` добавила в таблицу и `updated_by`.

Полная семантика — требование «Цветовая индикация слоя: поле colors и контракт его правки».

## POST /layers/{id}/merge — слияние слоя с родителем

```
POST /api/v1/networks/{nid}/layers/{id}/merge
     { tables?: { <ветвимая таблица>: [id, …] } }
→ 200 { data: MergeReport }
```

**Полное слияние** (тело пустое или без `tables`) переносит в родительский слой все строки слоя — теневые и надгробия. **Частичное** переносит только перечисленные логические id по таблицам; набор обязан быть **замкнутым**, сервер его не расширяет. Имена таблиц — из закрытого списка ветвимых; неизвестная таблица или id, которого в слое нет, — 422.

Запреты: основа не сливается (нет родителя) — 422; служебный слой слить нельзя — 422; несуществующий id — 404. Потомки слоя слиянию не мешают: их цепочка прозрачно разрешается через опустевший слой.

**Отказ целиком** (422, детали в теле ошибки): любое расхождение `base_version` — `conflicts: [{ table, id, expected_base_version, current_version }]`; незамкнутый набор — `missing_closure: [{ table, id, referenced_by }]`. Частичного применения не бывает. Единственное исключение — связь на физически отсутствующий конец: связь не создаётся, слияние продолжается, факт попадает в `skipped`.

**MergeReport:**

```json
{ "applied": { "thoughts": 2, "links": 3 },
  "skipped": [{ "table": "links", "id": "…", "reason": "endpoint_missing", "missing": "target" }],
  "reorder_collapsed": [{ "thought_id": "…", "count": 4 }],
  "reserve_layer_id": "…" | null,
  "purged": 0 }
```

- `applied` — сколько логических строк перенесено по таблицам (свёрнутые пачки переупорядочивания входят общим числом);
- `reorder_collapsed` — свёрнутые пачки «изменён порядок у N связей узла X»;
- `reserve_layer_id` — автосозданный служебный слой с до-слиянием состоянием затронутых строк родителя — ручной откат; `null`, когда перезаписывать нечего;
- `purged` — строки, снятые автоочисткой корзины сразу после слияния.

**Real-time:** слияние эмитит ровно одно событие `layer.merged` (`audience = network`, `layer_id` — слой-цель) с отчётом в данных; поштучной рассылки перенесённых строк нет — клиент делает полный ресинк.

**Дополнение (13-layers.md §8.4a).** В отчёт входит ещё `activity_rollup: { groups, removed }` — сводка авто-свёртки журнала активности для слитого слоя: сколько ключевых сущностей `(entity_type, entity_id)` получили итоговую запись в основе и сколько детальных строк журнала удалено. Считается той же транзакцией, что и слияние.

**Слияние одной мысли (0.10.3, задача `f5c363a3`, коммит `8bfc08a3`).** Тело может нести `{ thought_id, mode?: "overwrite" | "combine" }` вместо `tables` (взаимоисключающи; `mode` — только вместе с `thought_id`). Сервер сам собирает замкнутое подмножество строк этой мысли (мысль, синонимы, значения свойств, комментарии с целями, вложения, её рёбра и зависимые строки рёбер) и **не расширяет** его сверх мысли. `overwrite` — перед реплеем снимаются расхождения `base_version` по этим строкам (версия слоя побеждает целиком). `combine` — то же, но постоянный комментарий объединяется с основой построчно (LCS; конфликтный участок — блоком с маркерами `<<<<<<< слой` / `=======` / `>>>>>>> основа`; текст не теряется); хроно-записи переносятся все, связи/свойства/синонимы — версией слоя. Границы объединения — ADR `e4dfdda0`. Отчёт дополняется `thought_merge: { thought_id, mode, comment_merged, comment_conflicts }`. MCP: `etn.ops layers.merge` принимает те же параметры; «отказаться от изменений» — отдельная операция `layers.discard` (физическое удаление строк мысли из слоя, основа не тронута; REST `POST /layers/{id}/discard`).

## Ветвимые и неветвимые таблицы: адресация строк парой id и слоя

Содержательные таблицы сети делятся на два класса, и список закрыт: расширение требует правки спецификации слоёв.

**Ветвимые:** мысли, синонимы мыслей, связи, типы мыслей, типы связей, свойства типов, переопределения дефолтов, значения свойств, комментарии, привязки комментариев, вложения — плюс FTS-индексы (несут слой неиндексируемым полем).

Каждая ветвимая таблица:

- адресует строку парой **«логический `id` + `layer_id`»** (уникальное ограничение на эту пару); первичный ключ — суррогатный `pk`;
- несёт `layer_id` со значением по умолчанию в основу, `deleted` (надгробие — пометка «удалено в этом слое») и `base_version` — версию строки-предка на момент материализации, по которой детектируются конфликты при слиянии;
- **не имеет SQL-внешних ключей между сущностями**: ссылки идут на логический id, который в пределах таблицы больше не уникален. Это осознанная потеря целостности на уровне СУБД — целостность теперь поддерживает приложение;
- сохраняет прежние естественные ограничения уникальности, но **в пределах слоя и среди живых строк**.

**Неветвимые** (без `layer_id`, общие для всех слоёв): сама таблица слоёв, слой сессии, метрики чтений, настройки пользователя, просмотры, фокус-настройки и порядок, сохранённые отборы, закреплённые мысли, эмбеддинги — и журнал событий (он живёт в системной БД и несёт слой как атрибут полезной нагрузки).

**Следствие, о котором легко забыть.** Поскольку `id` мысли перестал быть уникальным, SQL-FK на него сняты и из неветвимых таблиц тоже — FK обязан указывать на уникальный ключ. Очистку при физическом удалении выполняет приложение.

### Дополнение (0.7.x): отборы и справочник свойств

В закрытый список ветвимых таблиц добавились `properties` (0.6.5) и `thought_type_views`; расширяется он только правкой спецификации слоёв.

Отбор типа мысли ветвится как любая ветвимая строка: заведённый в слое отбор не виден в основе; при частичном слиянии он замыкается на свой тип мысли (тип можно слить без отборов — обратное не требуется). Правка отборов разрешена только в Основе.

Справочник `properties` (имена свойств сети) ветвится с 0.6.5 и входит в замыкание частичного слияния: `type_properties.property_id`, `type_property_overrides.property_id` и `property_values.property_id` теперь ссылаются на запись `properties`, а не на саму привязку. Если в слияние включено значение/привязка, а свойство живёт только в слое, набор незамкнут и слияние отклоняется.

## Видимость событий по слою подписчика

Событие `audience=network` с `layer_id=EL` доставляется подписчику, чья сессия сидит в слое `L`, только если:

1. `EL` лежит на цепочке предков `L` (`L → parent(L) → … → base`; события основы проходят всегда), **и**
2. ближайшая строка для логического `id` события в цепочке `L` живёт именно в `EL` — то есть `L` не материализовал для этого `id` более близкую теневую строку или надгробие.

Проверка — точечный lookup `(table, id)` через `layer_chain` без фильтра `deleted=1`: событие удаления-надгробия обязано дойти, если ближе ничего не перекрывает.

**Исключение.** Событие `*.deleted`, для которого на цепочке `L` нет строки вообще, доставляется: строка была физически удалена (автоочистка корзины) уже после записи события, и каждый подписчик, держащий её в кэше, обязан её выкинуть. Лишняя доставка незнакомого `id` безвредна — applier игнорирует неизвестные сущности идемпотентно.

Неветвимые события (сеть/членство/присутствие, `audience=user` настройки) видимость не проверяют: нет строки-носителя, маршрутизация обычная.

Реализация: `server/src/realtime/layer-visibility.ts`.

## Выборки в слое читают временный снапшот видимости соединения

Видимость слоя для чтения материализуется временным снапшотом на соединение; служебная live-таблица не вводится.

**Проверка.** Результаты выборок в слое совпадают с эталоном; снапшот инвалидируется при смене слоя и изменении версий.

## Границы MVP: чего в системе намеренно нет

Явные ограничения, принятые осознанно. Наткнувшись на любое из них, не надо считать это дефектом и «чинить» попутно:

- **Один серверный процесс.** Нет кластеризации и реплик; pub/sub — внутрипроцессный, в памяти.
- **Записи сериализованы** write-lock’ом WAL в пределах одной сети. Расчёт — на 2–5 одновременных активных редакторов.
- **Нет шардинга сетей по дискам** — все сети в одном каталоге данных.
- **Поиск только внутри одной сети** — сквозного индекса по нескольким мыслесетям нет.
- **Нет офлайна на клиенте.**
- **Нет встроенной генерации документов и презентаций** — это работа для внешнего агента.
- **Нет векторного (семантического) поиска.** Задел оставлен только в схеме данных — зарезервированной таблицей эмбеддингов, чтобы будущая реализация не требовала миграций.

**Ограничения модели слоёв (13-layers.md §11).** Осознанные следствия модели «слой — плёнка, а не снимок»; наткнувшись на любое, не считать дефектом:

- **Состояние слоя на прошлую дату невоспроизводимо** — слой видит текущую основу, история пересчитывается при каждом чтении.
- **«Отличие слоя» двусмысленно**: относительно основы-сейчас (показ пользователю) и относительно основы-на-момент-создания слоя (слияние, через `base_version`).
- **Логическое противоречие с основой не обнаруживается**, если строки не перекрываются.
- **Слияние не разрешает конфликты, только детектирует**; three-way merge с выбором стороны — вне фазы S.
- **Разделение прав по слоям не входит в фазу S** — права у всех участников одинаковые (см. «Равные права на слои у всех участников сети»).

**Вне рамок фазы S по слоям (13-layers.md §17).** Кроме разделения прав и three-way merge (см. выше): автоматическая сверка `git_branch` слоя с состоянием git-репозитория — поле зарезервировано, но скрипт сверки в MVP фазы S не входит.

## Два вида файловых вложений и судьба файла при удалении

Файловое вложение бывает двух разных видов, и путать их нельзя.

1. **Загруженное на сервер.** Бинарник сохраняется в каталог вложений рядом с БД сети (единое хранилище, бэкапится вместе с БД), а путь указывает на эту копию. Так работает вставка файлов из буфера обмена в комментарии.
2. **Просто путь в ОС клиента.** Бинарник не копируется — сохраняется только ссылка на файл на машине пользователя. Так работает перетаскивание файла в зону вложений.

**При удалении вложения** сервер удаляет сохранённую копию, **только если она лежит внутри каталога вложений сети**. Пути в ОС клиента не трогаются никогда — это чужие файлы.

**При удалении владельца** вложения удаляются вместе с ним — тоже с сохранёнными копиями файлов.

**Перенос к другому владельцу** допустим правкой полей владельца; новый владелец обязан существовать.

### Слои: физический файл один на все слои

Привязка вложения (`attachments`) — ветвимая строка: удаление вложения в слое ставит надгробие привязке и не трогает основу. **Физический файл на диске общий для всех слоёв сети**; физическое удаление сохранённой копии допустимо только когда счётчик ссылок по всем слоям сети обнулился — иначе удаление в слое сломает основу и другие слои. Живые теневые строки, в том числе строки резервного слоя, удерживают вложение от физической очистки.

## Меню слоёв

Меню `[▤ Основа ▾]` в toolbar видов, между меню «Мыслесеть» и переключателем видов. **Заголовок — имя текущего слоя сессии** (по умолчанию «Основа»): это единственный индикатор «где я сейчас».

При открытии показывается: список слоёв сети (служебные/резервные скрыты; текущий отмечен галочкой; вложенность — отступом), команда «Создать новый слой…», а для не-основного слоя ещё «Отличия от „…“…», «Слить „…“ в „…“…» и «Удалить „…“…» (danger).

Выбор слоя переключает серверную сессию и запоминает слой за **активным табом** (слой — свойство таба; два таба одной сети могут смотреть разные слои). Смена слоя — **полный ресинк видимого состояния**: перечитываются фокус и перекрытия, сбрасываются кеши редактора и активная мысль «Структур» — редактор показывает данные нового слоя.

**Диалог «Новый слой»** — одна строка механики («Правки останутся в слое. Основа не изменится, пока вы не сольёте слой»), название (обязательно), комментарий (рекомендуется), ветка git (необязательно). Создание переключает таб на новый слой.

**Диалог «Удалить слой?»** — при наличии потомков их число и заголовки (паттерн подтверждения «Структур») + пометка «основа не пострадает».

**Диалог «Отличия…» (ревизия 0.10.3, задача `52c776f1`).** Единая прокручиваемая лента различий без вкладок: строки группируются по секциям структурного диффа в каноническом порядке (`links.added/removed/type_changed/reorder_collapsed/reparented`, `overridden.thought_ids/link_ids`), перед каждой непустой секцией — заголовок с общим счётчиком из `counts`. Лента грузится порциями (REST `diff?limit&cursor`, infinite scroll, keyed-рендер), при загрузке — прелоадер, по ошибке — сообщение с «Повторить», пустой отчёт — пустое состояние. Клик по мысли из `overridden.thought_ids` открывает **отдельный диалог построчного текстового диффа** этой мысли (REST `diff/thought/:id`; поля: название, тип, синонимы, актуальность, постоянный комментарий; красный/зелёный). Полный `diff/doc` диалогом не запрашивается (лечит фриз `14a3a642`). До 0.10.3: вкладки «Связи»/«Содержание», «Содержание» — построчный дифф двух полных markdown-документов.

**Слияние** — из меню, с подтверждением; успешный ответ — отчёт (перенесённые строки, свёрнутые пачки, пропущенные связи, резервный слой); отказ 422 — список конфликтов/незамкнутости.

### Цветовая индикация слоёв (0.6.4, задача 6c31d64f)

**Диалог «Свойства слоя».** Правка title/комментария и, для не-основного слоя, цветов: «полоса фокуса» и «фон» для текущей темы (color picker + hex). Для основы выбор цветов скрыт (основа — всегда цвета темы). Отдельного переключателя нет: выбрал цвета — применяются. При сохранении цвет противоположной темы вычисляется инверсией светлоты (HSL, L→1−L) и хранится вместе с заданным (`colors.focus_stripe/background × dark/light`, контракт — 13-layers.md §2.2a). При создании слоя клиент передаёт цвета по умолчанию (тёмная тема: полоса #7e57c2, фон #191327; светлые — инверсии), заметно отличные от основы.

### colors = null у не-основного слоя (0.7.4)

MCP-схема `etn.layers.create` поле `colors` не принимает, поэтому слой, созданный агентом через MCP, приходит с `colors: null`. Клиент распознаёт `null` у не-Основы (`currentLayerColors()`, `client/src/renderer/lib/layer-colors.ts`) и подставляет дефолтную фиолетовую пару (полоса `#7e57c2`, фон `#191327` для тёмной темы; светлые — инверсия по HSL), чтобы активный слой был визуально отличим от основы независимо от способа создания. Применение — через CSS-переменные `--layer-focus-stripe`/`--layer-bg`; при их отсутствии стили откатываются к токенам темы.

### Точечное слияние мыслей (0.10.3, задача `f5c363a3`)

Команда **«Слить мысль в основу…»**: (1) контекстное меню мысли на канве — только для мысли, перекрытой в текущем не-основном слое; (2) «Действия» панели выделенных — при наличии перекрытых выбранных. Диалог (вертикальная группа вариантов с пояснениями): «Отказаться от изменений» (с подтверждением; `layers.discard` — строки мысли удаляются из слоя, основа не тронута) / «Полностью переписать мысль в основе» (`merge` `mode=overwrite`) / «Объединить изменения» (только для мыслей с расширенным постоянным комментарием; `mode=combine`, маркеры конфликтов git-стиля; границы — ADR `e4dfdda0`). При сбое чтения диффа вариант «Объединить» недоступен с инлайн-сообщением в теле диалога. После операции мысль уходит из списка отличий и с неё снимается пометка перекрытия.

## Наследование привязок по цепочке типов

Каждый тип наследует **все привязки своих предков** вплоть до корневого — привязки обеих сторон, источника и назначения. Эффективный список свойств типа собирается по цепочке «корень → … → сам тип», привязки каждого уровня добавляются в общем порядке.

**Одно свойство — одна привязка в цепочке.** Свойство, уже подключённое предком, потомку подключать не нужно: оно у него и так есть.

**Подключение свойства к родителю снимает избыточные привязки у потомков.** Когда тип подключает свойство, которое уже подключено каким-то из его потомков, привязки этого свойства у всех типов-поддерева удаляются в той же транзакции. Значения мыслей и связей при этом не меняются вообще: они ссылаются на свойство, а не на привязку, и свойство остаётся доступным — теперь по наследству. Это заменяет прежний запрет (`409 DUPLICATE` при совпадении имени в цепочке или поддереве), который был нужен, пока определение принадлежало типу.

**Что можно и чего нельзя подчинённому типу.**

- Природу унаследованного свойства (тип значения, конфигурацию, имя) менять нельзя: она одна на всю сеть и правится в справочнике — сразу для всех типов, куда свойство подключено.
- Обязательность унаследованной привязки потомок не переопределяет.
- Можно переопределить **значение по умолчанию** и **описание** — для себя и своего поддерева.

**В редакторе типа** видны и редактируются только **собственные** привязки; унаследованные показываются отдельной секцией — обеих сторон, источника и назначения. Правка обязательности унаследованной привязки по-прежнему недоступна, значение по умолчанию и описание переопределяются. Привязки подчинённых типов не видны и не учитываются.

**Владелец без типа** видит свойства корневого типа: запись значений для него резолвит привязки по цепочке из одного корня.

**Повторное подключение к тому же типу (0.8.2, ошибка 0bfd7180).** Подключить свойство, которое этот же тип уже несёт, — не ошибка: привязка обновляется на месте (тот же `id`, роль из запроса, порядок без явного `position` не переезжает). Прежний `409 DUPLICATE` на повтор снят — он ломал сценарий «создал свойство из диалога выбора → выбрал его → записал тип». `409 DUPLICATE` остаётся только для привязки предка (см. выше — свойство и так наследуется).

**В слоях (13-layers.md §13).** Наследование считается по **разрешённой** цепочке типов (правило «ближайший слой побеждает»), а не по сырым строкам физической таблицы: чтение типов, привязок и отборов идёт через представления `thought_types_v` / `type_properties_v` / `thought_type_views_v`. Copy-on-write распространяется на `thought_types`, `link_types`, `type_properties`, `type_property_overrides` наравне с содержательными таблицами — иначе типичное «добавить тип и свойство» в слое сразу стало бы видно всем. Следствие для слияния: мысль в основе не может ссылаться на тип, созданный только в слое, поэтому `type_id` мысли и связи участвуют в замыкании частичного слияния (см. «Типы и справочник свойств входят в замыкание частичного слияния»).

## Переключение слоя сессии — полный ресинк через switched_at_seq

**Актуализация 0.8.4 (задача 09f19952).** `etn.changes.list` снят с постоянного набора MCP — это действие `changes.list` исполнителя `etn.ops` (read-only). Детали — `etn.guide { topic: "changes.list" }`.

`last_seq` глобален по сети, а фильтр видимости — по слою подписчика, поэтому после смены слоя кэш клиента невалиден целиком и дельта через границу переключения невозможна (она смешала бы два разных фильтра).

Сервер запоминает в `session_layers.switched_at_seq` (миграция 028) — `max_seq` сети на момент переключения — и использует его как границу, аналогично окну удержания:

- `resume` с `last_seq < switched_at_seq` → `resume.stale { last_seq: switched_at_seq }`, даже если позиция ещё внутри окна удержания;
- позициям `>= switched_at_seq` доверяют: подписчик, выполнивший ресинк после `layer.switched`/`layer.deleted`/`resume.stale`, продолжает с них и больше не получает stale по этой причине;
- `etn.changes.list` зеркалит правило: `truncated: true` при `since_seq < switched_at_seq`.

Переключение на уже текущий слой — не переключение: `switched_at_seq` не трогается, ресинк не форсируется.

## Поиск в контексте слоя: фильтрация видимости и дедупликация по логическому id

Полнотекстовый поиск выполняется в контексте слоя сессии, и это меняет весь порядок работы запроса.

**Порядок**: FTS5 сначала ранжирует, затем фильтруется видимость слоя, а результаты дедуплицируются по логическому id — джойном индекса с представлением-разрешателем по rowid строки-победителя.

**Пагинация**: `limit`/`offset` применяются к уже отфильтрованному и дедуплицированному списку — LIMIT **не проталкивается** внутрь FTS-запроса; `meta.total_in_group` считается после дедупликации — на объёмах MVP это точное значение ценой более дорогого подсчёта.

**Видимость**: перекрытые в слое редакции не находятся (ищется текст строки-победителя), а надгробия исключают строку полностью — даже если в основе текст найден.

**Индекс имён** несёт текст «заголовок + синонимы того же слоя»: унаследованные от предка синонимы ищутся, пока строка мысли не перекрыта в цепочке; после материализации тени в индексе остаются только заголовок и синонимы этого слоя.

**Механика (13-layers.md §9).** FTS-таблицы (`fts_thought_names`, `fts_thought_texts`, `fts_link_texts`) — автономные, не external-content, синхронизируются триггерами, поэтому `layer_id UNINDEXED` (миграция 025) не требует пересборки индекса. Фильтрация — rowid-джойн индекса с представлением-разрешателем: `thoughts_v.rowid = fts_thought_names.rowid`, `comments_v.rowid = fts_thought_texts.rowid`; rowid FTS-строки — `pk` физической строки, представление экспонирует rowid победителя, значит матчится только текст строки-победителя. Отсюда два следствия: дедупликация по логическому id выходит «бесплатно» (одна FTS-строка на победителя), а агрегатный текст индекса имён (`title` + синонимы того же слоя) перестаёт находиться по унаследованным синонимам, как только строка мысли перекрыта в цепочке (до перекрытия синонимы предка находятся через его строку). Синонимные триггеры не включают надгробия в агрегат (миграция 026): синоним, удалённый в слое, выпадает из текста строки слоя. Надгробие исключает строку из выдачи, даже если в основе текст найден. `LIMIT` не проталкивается внутрь `MATCH` — фильтрация и дедупликация идут в CTE поверх результата FTS со сканом шире страницы.

## Полнотекстовый поиск (FTS5)

Поиск по текстам сети на виртуальных таблицах FTS5: имена и синонимы мыслей, тексты комментариев мыслей и связей.

Индексы поддерживаются триггерами БД, а не приложением — правка схемы мыслей, синонимов или комментариев требует проверки триггеров.

Поиск работает **в пределах одной сети**: общего индекса по нескольким мыслесетям нет и на MVP не планируется. Семантический (векторный) поиск в подсистему не входит — задел оставлен только в схеме данных.

С 0.7.5 все три индекса — `tokenize = 'trigram case_sensitive 0'` (был «`unicode61`», миграция `038_search_trigram.sql`, ошибка 0258fd9d): искомое вхождение в любой части слова (не только префикс), с встроенным кейс-фолдингом кириллицы. Ограничение: ≥3 символа на фрагмент запроса — коротише индекс не ищет; `by_names` покрывает такие случаи LIKE по `title_norm`/`synonym_norm`, у `by_texts`/`by_links`/`by_chrono` такого fallbackа нет (см. `GET /search`).

**В слоях (13-layers.md §9).** FTS-таблицы несут `layer_id UNINDEXED` (миграция 025), автономны (не external-content) и синхронизируются триггерами, поэтому слоистость не потребовала пересборки индекса. Поиск выполняется в контексте слоя сессии: FTS5 сначала ранжирует, затем результат фильтруется по видимости слоя и дедуплицируется по логическому id — см. требование «Поиск в контексте слоя: фильтрация видимости и дедупликация по логическому id».

## Сквозная слоистость MCP-инструментов

**Актуализация 0.8.4 (задача 09f19952).** Слоистость по-прежнему сквозная, но ростер вызовов сузился: `layers.create`/`layers.update`/`layers.delete`/`layers.diff`/`layers.diff_doc`/`layers.merge` — действия исполнителя `etn.ops`; инструментами остались только `etn.layers.list` и `etn.layers.select`. `etn.changes.list` — действие `changes.list` исполнителя `etn.ops` (read-only); семейство `etn.links.*` упразднено (требование `3ea5c6af`). Детали — `etn.guide { topic: "changes.list" }`.

Слои изменений — сквозное свойство всех MCP-инструментов, а не отдельные «послойные» варианты: **все** чтения и записи (`etn.thoughts.*`, `etn.links.*`, поиск, подграф, комментарии, свойства, bundle…) работают в контексте текущего слоя вызывающего ключа.

Слой сессии хранится в той же таблице `session_layers`, что и у REST, но ключуется иначе: у MCP нет `Client-Id` — идентичность сессии `mcp:<api_keys.id>`. Следствия:
- у каждого API-ключа своя независимая слой-сессия (два ключа одного пользователя не мешают друг другу) — фундамент будущего «ключ, прибитый к слою-песочнице»;
- `etn.layers.list` помечает `current` по ключу;
- `etn.changes.list` фильтрует события видимостью в слое ключа и отдаёт `truncated: true`, когда `since_seq` раньше последнего переключения слоя.

**Эхо слоя:** ответ каждого пишущего инструмента содержит `layer: {id, title}` — текущий слой ключа на момент ответа; агент, пишущий не в тот слой, видит это сразу, а не по последствиям. Read-ответы эха не несут (исключение — список слоёв с `current`).

Полный цикл агента без REST руками: `layers.list` → `layers.create` → `layers.select` → записи/чтения → `layers.merge` → `layers.delete` (после удаления слоя сессия ключа автоматически переключается на родителя — отдельный `select` обратно не нужен).

**Сверх паритета (13-layers.md §10.2, §8.5).** Помимо полного паритета по слоям, агент получает путь аварийного согласования конфликта `base_version`: `layers.conflicts` (read-only) и `layers.reset_override` (`confirm`) — снять расхождение, из-за которого слой стал несливаемым.

## Слой изменений

**Слой изменений** (кратко — **слой**) — именованный набор изменений поверх **основы**. Пользователь или агент работает в слое, его правки не видны остальным, пока слой не **слит в основу**.

### Как устроен

Копируются только изменённые строки (copy-on-write). Что слой не перекрыл — видно из основы, как через прозрачный слой в графическом редакторе. Слои вложены: можно создать слой поверх слоя, побеждает ближайший. Глубина — до 4 слоёв, то есть 5 уровней вместе с основой.

**Слой — не снимок.** Он видит текущее состояние основы во всём, что не перекрыл: правка в основе сразу видна в слое. Это осознанное решение — работая в слое, хочешь видеть свежие знания, а не состояние недельной давности.

### Словарь

| По-русски | В коде | Значение |
|---|---|---|
| основа | `base` | то, что видят все; корень иерархии слоёв |
| слой изменений, слой | `layer` | набор изменений поверх основы |
| слить слой в основу | `merge` | перенести изменения вниз |
| удалить слой | `delete` | отказаться от изменений; основа не страдает |
| перекрытая мысль (связь) | `overridden` | та, у которой в слое своя версия |
| резервный слой | `backup layer` | служебный слой, создаваемый автоматически перед слиянием, чтобы слияние можно было откатить |

Русское «слить» выбрано как более привычное в IT, чем «свести»; английское `merge` — по той же причине.

### Почему не «ветка»

Слово «ветка» создаёт git-ожидания, которые здесь неверны: ветка git — снимок от точки расхождения, есть rebase и cherry-pick, слияние разрешает конфликты. Ничего из этого у слоя нет. Пользователь с опытом git счёл бы багом то, что сделано намеренно.

Побочный выигрыш: слово **«ветка» освобождается** и в проекте означает только ветку git — без уточнений.

Реализация — фаза S в разделе «Планы работ»; спецификация — задача S1.

### Надгробие (deleted / tombstone)

Строка, удалённая в слое: она скрывает сущность в этом слое, но у предка версия продолжает жить. Это copy-on-write механизм слоёв, а не пользовательская корзина и не признак неактуальности — см. требование «Неактуальность, пометка на удаление и надгробие слоя — три разных механизма».

Идентификаторы в коде: слой — `layer`, основа — `base`, слияние — `merge`, резервный слой — service layer (`is_service = 1`), перекрытая строка — `overridden`.

<a id="pub-3f2c04db"></a>

## Слой-осознанность REST API: все чтения и записи идут в слое сессии

Слои изменений — сквозное свойство всего API сети, а не отдельный набор маршрутов.

**Любой запрос к `/api/v1/networks/…` выполняется в контексте текущего слоя сессии**: чтения разрешаются по цепочке предков слоя, записи материализуются в нём теневыми строками и надгробиями.

Текущий слой — **умолчание сессии, хранимое на сервере**, а не параметр запроса:

- координаты сессии — тройка `(user_id, client_id, network_id)`; `client_id` приезжает заголовком `Client-Id`;
- запись живёт в неветвимой таблице `session_layers` сетевой БД;
- смена слоя — отдельная операция выбора слоя, а не переключение соединения на лету: пул держит по соединению на пару (сеть, слой);
- то же умолчание действует для MCP-вызовов того же ключа.

Права на слои у всех участников сети одинаковые: отдельной роли «владелец слоя» нет.

Опасность скрытого состояния очевидна: после перезапуска клиента можно писать не туда, поэтому каждый ответ на запись обязан нести эхо слоя.

<a id="pub-1f1200a1"></a>

## Смена концов связи в рабочем слое создаёт новую связь с новым id

Смена концов связи (перецепка) **в рабочем слое** выполняется как пометка старой связи на удаление плюс создание новой — а не как `UPDATE` той же строки.

Последствия, которые обязан учитывать клиент:

- ответ 200 несёт **новую связь с новым `id`** и `version: 1`;
- старый `id` в этом слое больше не разрешается;
- видимые зависимые строки старой связи (комментарии, вложения, значения свойств) скрываются каскадом, как при удалении;
- real-time шлёт `link.deleted` (старый id) и `link.created` (новая связь) вместо `link.updated`.

Исключения: PATCH, повторяющий текущие значения концов, — обычное обновление; **в основе** смена концов — обычный `UPDATE` с тем же `id`.

<a id="pub-88d12c99"></a>

## Событие layer.merged — одно событие на слияние

Единое событие успешного слияния слоя: `audience=network`, `layer_id` конверта — слой-цель; `data` — отчёт слияния (`applied`, `skipped`, `reorder_collapsed`, `reserve_layer_id`) плюс `layer: { id, title }` (слитый слой) и `target_layer: { id, title }` (цель).

Ровно одно событие на слияние, поштучной рассылки изменённых строк нет: построчная дала бы лавину с проверкой видимости на каждого подписчика. Получив событие, клиент и агент выполняют полный ресинк видимого состояния (тот же путь, что после `resume.stale`).

Фильтрацию видимости по слоям событие не проходит: оно описывает не отдельную строку, а смену состояния слоя-цели целиком.

<a id="pub-1f7f789b"></a>

## Требование: авто-свёртка activity_log при слиянии и удалении слоя

**Слияние слоя в основу** автоматически сворачивает его события: в основе по каждой затронутой в слое сущности появляется ровно одна итоговая запись (`created`/`updated`/`deleted`) с **автором и временем исходного итогового события слоя** (не временем слияния и не исполнителем слияния). Детальные события слоя в основе не переносятся.

**Удаление слоя** (без слияния) удаляет все его события из `activity_log` вместе со слоем.

Действие согласуется с механикой слоёв `docs/13-layers.md` (файл — источник истины по слоям; правка матрицы ветвимости — задачей проекта).

**Детали (13-layers.md §8.4a).** Итоговая запись основы — `created`, если в слое было событие создания, иначе действие самого позднего события слоя (`updated`/`deleted`/`trashed`/`restored`). Автор и `occurred_at_ms` берутся из самого позднего события слоя, `entity_title` — снимок этого события (чтобы запись оставалась читаемой после удаления сущности). Детальные строки слоя (`layer_id = L`) удаляются; события с `layer_id ≠ L`, включая исходный `created` в основе, если сущность создавалась до слоя, не затрагиваются. Вся операция идёт в той же транзакции, что merge, и откатывается вместе; в отчёте слияния видна как `activity_rollup: { groups, removed }`. Удаление слоя без слияния вычищает события всего поддерева (`activity_log.layer_id ∈ subtree(L)`) до физического `DELETE FROM layers`. Ручные свёртка/обрезка — вне merge/delete, REST и MCP.

<a id="pub-ebb924a7"></a>

## Эхо текущего слоя в каждом ответе на запись

Каждый **успешный ответ на запись** в маршрутах сети обязан сообщать, в какой слой попала запись:

- ответы с телом — `meta.layer: { id, title }` (добавляется сервером во все mutating-ответы `/api/v1/networks…`, включая создание сети, участников, настроек и самих слоёв);
- безтельные `204` (DELETE-маршруты) — заголовки `X-Etn-Layer: <id>` и `X-Etn-Layer-Title: <title>`, где title percent-encoded (значения заголовков обязаны быть ASCII). Контракт 204 сохранён, чтобы не ломать клиентов;
- **ответы на чтение эхо не несут** — они неявно определены слоем сессии; единственное исключение — флаг `current` в списке слоёв.

Зачем: слой — скрытое состояние сессии, и без эха запись в чужой слой обнаруживается только постфактум — например, после перезапуска клиента.

<a id="pub-5fb8dfb6"></a>

## etn.layers.conflicts / layers.reset_override — аварийное согласование конфликта base_version

Аварийное согласование конфликта `base_version` — путь, доступный **только агенту** через исполнителя `etn.ops`; REST-маршрута и пункта меню клиента нет (это не пользовательская операция).

```
etn.ops { action: "layers.conflicts",      params: { network_id, layer_id } }
  → { layer, target_layer, overridden, conflicts: [LayerOverrideRow] }        // read-only

etn.ops { action: "layers.reset_override", params: { network_id, layer_id,
            tables: { <ветвимая таблица>: [id, …] } }, confirm: true }
  → { layer, target_layer, reset: [LayerOverrideRow], unchanged: [{ table, id, reason }] }
```

**`layers.conflicts`** (read-only) перечисляет строки, из-за которых слияние будет отклонено, и по каждой отдаёт «было в основе / стало в слое». `overridden` — сколько теневых строк физически держит слой (объём, адресуемый сбросом). Бюджет записи не тратит.

**`layers.reset_override`** (destructive, `confirm`) перепривязывает `base_version` названных строк к текущей версии предка, при необходимости поднимает `version` (поле `version_raised_to`). Каждая строка отчёта несёт `previous_base_version`, `current_version`, `layer_version`, признаки надгробия и список изменённых столбцов. `unchanged` — строки, оставленные как есть, с причиной `up_to_date` или `not_versioned`.

**Проверки:** слой рабочий (не основа и не служебный), каждая названная строка физически есть в слое (иначе 422 со списком `unknown`), набор не пуст, имена таблиц — из закрытого списка ветвимых (иначе 422).

**Побочные эффекты:** журнальная строка `layer.updated`, audit-запись, обновление `last_activity_at` слоя. Семантика и обоснование — «Снятие расхождения base_version у строки слоя (reset_override)».

<a id="pub-4c51c495"></a>

## Правило разрешения строки в слое: побеждает ближайший слой цепочки

Для логического `id` в контексте слоя `L` побеждает строка из **ближайшего** слоя цепочки `L → parent(L) → … → основа`, где строка для этого `id` вообще есть (неважно — обычная или надгробие). Если победившая строка — надгробие, сущность **не видна** в этом слое, даже если у более дальнего предка есть живая версия.

Глубина цепочки — до 5 уровней (4 слоя + основа). Правило действует **во всех чтениях без исключения**: `query`, `search`, `subgraph`, `neighbors`, `path`, `usage`, `mentions`, `backlinks`, а также во внутренних выборках для валидации при записи и слиянии.

Следствие: слой видит **текущее** состояние основы во всём, что не перекрыл (плёнка, а не снимок) — «непрерывное rebase» без явного действия.

<a id="pub-0cfb07c0"></a>

## Ветвимые таблицы читаются только через представления слоя

Репозитории читают ветвимые таблицы **только через представления слоя** (`<таблица>_v`) и о слоях не знают. Прямое чтение физических таблиц в доменном слое **запрещено** и обязано быть обнаружимым тестом/линт-правилом: иначе забытый запрос читает физическую таблицу и утекает чужой слой в ответ.

Устройство на соединении: временная таблица `layer_chain(layer_id, depth)` — обход `layers.parent_id` от текущего слоя к основе; при наличии слоёв поверх основы представления читают temp-снапшот видимости, в контексте основы — живую таблицу напрямую (конкурирующих версий нет). Пул соединений ключуется парой `(network_id, layer_id)`, а не только сетью. Представление обязано экспонировать `rowid` строки-победителя — на него джойнятся FTS-индексы.

<a id="pub-163d34d9"></a>

## Цветовая индикация слоя: поле colors и контракт его правки

`layers.colors` — JSON-объект из двух ключей, каждый — пара «тёмная/светлая тема»: `focus_stripe` (полоса фокуса: фон средней зоны карты и рамка мысли, открытой в редакторе) и `background` (фон холста на всех экранах).

**Контракт.** У основы `colors` всегда `NULL`, назначение ей — 422 `VALIDATION_ERROR` (как и переименование). У не-основного слоя `NULL` означает «клиент применит дефолтные цвета создания». `POST /layers` принимает необязательный `colors`; `PATCH /layers/{id}` принимает `colors` — полная замена объекта или `null` (сброс к цветам темы); частичный объект (не оба ключа / не обе темы) или не-hex значение (`#rrggbb`) — 422. Правка цветов участвует в оптимистической блокировке `version` (`If-Match`) наравне с `title`/`comment`. `GET /layers` возвращает `colors` у каждого элемента.

MCP `etn.layers.create`/`etn.layers.update` цвета **не принимают** (цветовая индикация — прерогатива клиента), `etn.layers.list` поле возвращает. Реализация — миграция `031_layer_colors.sql`. Зачем вообще: слой визуально почти неотличим от основы, и пользователь не понимает, почему другие не видят его правок.

<a id="pub-725626a3"></a>

## Версии теневой строки слоя: version продолжает предка, base_version фиксируется

Первая запись по логическому `id` в слое, где строки для него ещё нет, материализует теневую строку — копию разрешённой правилом §4.1 строки предка с применёнными изменениями. Два правила версий:

- `layer_id` = текущий слой;
- `version` **продолжает нумерацию предка**, а не начинается с 1: копируется текущая версия разрешённой строки предка, затем инкрементируется при каждой следующей правке в этом же слое. Это сохраняет привычную семантику `expected_version`/`If-Match` — клиент всегда сверяется с последней увиденной версией независимо от того, в каком слое она была прочитана;
- `base_version` — **версия строки предка на момент материализации**, записывается один раз и больше не меняется. Используется только при слиянии для детекции конфликта, в обычном `expected_version`-контроле записи внутри слоя не участвует.

Последующие записи по тому же `id` в том же слое — обычный `UPDATE`: `version` растёт, `base_version` не трогается. У безверсионных ветвимых таблиц `base_version` всегда 0.

<a id="pub-5b92fc55"></a>

## layer-write.ts (db) — материализация теневых строк и надгробий

Единственный путь записи в ветвимые таблицы из рабочего слоя. Экспортирует:

- `materializeShadow` — первая правка логического `id` в слое копирует разрешённую правилом §4.1 строку предка в текущий слой (тень);
- `materializeTombstone` — удаление в слое материализует надгробие (`deleted = 1`) вместо физического `DELETE`;
- `deleteRowLayered` — единая точка «удалить строку X»: в основе физический `DELETE`, в слое надгробие.

Строка копируется из физической строки-победителя по `rowid`, который экспонирует представление `*_v`, поэтому тень несёт все столбцы предка, а не только те, что знает конкретный сервис. Писать в ветвимые таблицы минуя этот модуль нельзя: иначе запись уйдёт в основу и потеряет слой-осознанность.

<a id="pub-99faace2"></a>

## Удаление в слое ставит надгробие deleted=1 с base_version предка

Удаление логической строки в слое — не физический `DELETE`, а материализация теневой строки с `deleted = 1` (надгробие) по тем же правилам версий, что и обычная запись: `version` инкрементируется (удаление — тоже правка), повторное удаление уже удалённой строки — no-op.

Надгробие **обязано** нести `base_version` версии предка — иначе при слиянии оно молча затрёт правку, сделанную в предке уже после создания слоя (проверка конфликта без него не сработает).

Физически удаляют строку только слияние (перенос надгробия предку) и удаление слоя; в основе обычное удаление — физический `DELETE`.

<a id="pub-824e708e"></a>

## layer-service.ts (domain) — CRUD слоёв, глубина, цвета, удаление поддерева

Сервис слоёв изменений: список с иерархией и метаданными (скрывая служебные), создание слоя с проверкой лимита глубины (4 уровня поверх основы), переименование и правка комментария, валидация и замена `colors`, удаление поддерева с подтверждением `cascade = children_count`, выбор текущего слоя сессии.

Важно перед правкой: основу нельзя удалить, переименовать или перевести в служебные — все эти попытки дают 422 `VALIDATION_ERROR`; правка метаданных участвует в оптимистической блокировке `version`; удаление слоя физически сносит всё поддерево (не переносит правки предку).

<a id="pub-584039fb"></a>

## Каскад удаления мысли в слое: надгробия зависимых строк, дети остаются

Удаление мысли в слое материализует надгробия для **всех** её зависимых строк в этом слое: собственных связей (с обеих сторон), комментариев и их привязок, значений свойств, синонимов, привязок вложений — по тем же правилам версий, что и сама мысль.

Дети мысли **не удаляются**: каскад задевает строки связей, а не дочерние мысли — ребёнок остаётся, потеряв только эту связь.

В основе тот же прикладной каскад выполняет физический `DELETE` (SQL-каскады сняты вместе с FK на логический `id`).

<a id="pub-516b0499"></a>

## Дубль связи при слиянии схлопывается поиском по тройке

Два независимых слоя могут создать связь `A → B` одного типа — это две строки с разными `id`; сверка `base_version` их не видит (у обеих нет общего предка). При слиянии второй из них в ту же цель поиск дубля идёт **по тройке** `(source_id, target_id, type_id)` в целевом слое: найден — связь **схлопывается** (новая не создаётся), но если у сливаемой связи изменены порядок/стиль/свойства — эти правки применяются к уже существующей, а её версия инкрементируется как при обычной правке.

Исключение: таблицы с естественными ключами (уникальность синонима, единственный постоянный комментарий, имена типов) не схлопываются — конфликт вне тройки связей не детектируется и операция падает 422 с указанием таблицы.

<a id="pub-76ffa576"></a>

## Модуль видимости real-time событий по слою подписчика

Модуль per-subscriber видимости real-time событий по слою (`server/src/realtime/layer-visibility.ts`, `isEventVisibleInLayer`). Рассылка становится вычислением видимости на подписчика, а не широковещанием без разбора: подписчик в слое `L` **должен** получать события основы по строкам, которые не перекрыл, и **не должен** — по перекрытым.

Правило: событие о ветвимой строке доставляется, только если слой события лежит на цепочке предков `L` и `L` не материализовал более близкую строку или надгробие для того же логического id. Быстрый путь — событие слоя самого подписчика. Проверка — точечный lookup `(table, id)` через `layer_chain` **без фильтра `deleted = 0`**: событие-надгробие обязано дойти, если ближе ничего не перекрывает.

События о неветвимых данных (сеть, членство, presence, пользовательские настройки) и `layer.merged` фильтра не проходят — всегда видимы. Исключение: `*.deleted` при отсутствии строки на цепочке — это физическая очистка, событие всё равно доставляется, чтобы подписчик сбросил устаревший кэш (применяющие события к неизвестному id идемпотентны).

<a id="pub-60631e03"></a>

## Связь на помеченный в корзину конец создаётся при слиянии

Если один из концов новой связи помечен в корзину (`marked_for_deletion`), но ещё не удалён физически, связь всё равно создаётся при слиянии — мысль остаётся помеченной, а не превращается в висячую ссылку.

Это работает только потому, что проверка перед **физическим** удалением из корзины учитывает не только теневые строки самой мысли, но и теневые строки связей, у которых эта мысль — конец. Инвариант проверяется тем же эндпоинтом `deletion-check`, а не отдельной логикой слияния.

<a id="pub-b78545ff"></a>

## Связь на физически исчезнувший конец пропускается, слияние не отклоняется

Если к моменту слияния конец связи всё же отсутствует физически (безвозвратно удалён из корзины по всем слоям), связь **не создаётся**, но слияние в целом **не отклоняется**: факт идёт отдельной строкой `skipped` в отчёт о слиянии. Это единственное расхождение с общим правилом «конфликт → отказ всей операции»: конфликта одновременной правки здесь нет, есть утраченная цель.

Служебные (резервные) слои в «по всем слоям» не считаются — их копии страховка отката, а не рабочее состояние, и держать висячее ребро ради строки резерва нельзя.

<a id="pub-b6a3750a"></a>

## Порядок связей ветвится со связью; пачки порядка сворачиваются в отчёте слияния

По решению T1 порядок связей — отдельное поле `position` строки `links`, общее для всех, без персональных перекрытий; порядок ветвится вместе со связью и участвует в слиянии.

Следствие: массовое переупорядочивание N дочерних связей — это N изменённых строк и потенциально до N конфликтов при слиянии. Отчёт о слиянии **обязан сворачивать** такую пачку в одну позицию `reorder_collapsed: { thought_id, count }`, а не показывать N отдельных отказов.

Механизм свёртки: сворачиваются только строки `links`, у которых при слиянии меняется **исключительно** `position` (тройка, стиль и остальные поля совпадают с целевыми); группы образуются по `source_id` (для направленных связей переупорядочивается список детей); в `applied` строки пачки входят общим счётчиком по таблице. Свёртка не скрывает конфликты: если хоть у одной строки пачки `base_version` не сошёлся — слияние отклоняется по общему правилу.

Оговорка состояния: колонка `position` заведена миграцией `025_layers.sql`, но в API связи пока не выведена (T1 не закрыта), поэтому фактический ручной порядок в зоне фокуса до сих пор пер-пользовательский (`user_focus_order`, `POST /thoughts/{fid}/focus-order`).

<a id="pub-35ab4c7e"></a>

## Концы связи в слой при правке не копируются

Вариант «при правке связи копировать в тот же слой обе связанные мысли» рассмотрен и **отклонён** — копировать концы связи в слой при правке запрещено. Причины: копия замораживает мысль (правки из основы перестают в неё протекать — противоречит прозрачности слоя), замороженная копия попадает под сверку `base_version`, и слияние начинает отказывать из-за мыслей, которых по существу никто не трогал; дополнительной гарантии целостности копия не даёт — защита держится на проверке теневых связей перед физическим удалением из корзины.

Если сканирование теневых связей при проверке корзины окажется дорогим, вместо копии допустимо вести **индекс удержаний** (слой → множество `id` удерживаемых мыслей) — это индекс, а не копия, он ничего не замораживает; вводится по необходимости, не в MVP фазы S.

<a id="pub-5e5cf228"></a>

## Типы и справочник свойств входят в замыкание частичного слияния

`type_id` связи и `type_id` мысли — ссылки на ветвимые сущности, поэтому замыкание при частичном слиянии обязано включать **типы** наравне с концами: мысль в основе не может ссылаться на тип, созданный только в слое.

При незамкнутом наборе операция отклоняется 422 со списком недостающих ссылок; сервер **не расширяет** набор автоматически — это скрыло бы от пользователя, что реально уехало в основу. С 0.6.5 в замыкание входит и справочник `properties` (`property_values.property_id`, `type_properties.property_id`): если в слияние включено значение или привязка, а свойство живёт только в слое, набор незамкнут; строка `properties` ни от чего не зависит — её надо включить явно. Отбор типа мысли (`thought_type_views`) замыкается на свой тип мысли.

<a id="pub-3095ae04"></a>

## Равные права на слои у всех участников сети

Права на слои **не разделяются**: любой участник мыслесети — наравне со всеми — создаёт, выбирает, сливает и удаляет любой слой.

Разделение прав по слоям (например, ключ агента, прибитый к слою-песочнице, чтобы не доверять ему запись в основу) сознательно вынесено за рамки фазы S и не входит в MVP: ценность появится после того, как структуры и метаданные устоятся.

Это не отменяет проверку доступа к сети: она выполняется до слоёв и от слоя не зависит — слой не является объектом прав.

<a id="pub-24ca954b"></a>

## Слияние слоя — посрочный реплей с отказом целиком при конфликте

Слияние слоя `L` в родителя `P` — **посрочный реплей** финального состояния каждой затронутой логической строки `L` в `P`, по тем же правилам версий, что у обычной записи: `base_version` теневой строки играет роль `expected_version`/`If-Match` относительно текущей версии той же строки в `P`.

Порядок применения набора: **надгробия → обновления → вставки** — иначе новая строка с той же тройкой `(source, target, type)` упрётся в ещё не удалённую старую.

**Конфликт — отказ целиком.** Любое расхождение `base_version` хотя бы по одной строке отклоняет операцию (422) со списком `conflicts: [{ table, id, expected_base_version, current_version }]`; частичного применения («что сошлось — слито») не бывает: атомарность важнее удобства повторного вызова. Это не разрешение конфликтов, а превращение тихой потери данных в сообщение.

Уточнения:

- безверсионные ветвимые таблицы (синонимы, привязки комментариев, вложения, значения и определения свойств) конфликтов не детектируют — реплей идёт last-write-wins, страховка — служебный слой точки отката;
- перенесённая строка сохраняет свою нумерацию (`version` уезжает в `P` как есть), чтобы клиент продолжал сверять `If-Match` без ошибок; исключение — схлопывание дубля связи, там версия чужой строки инкрементируется как у обычной правки;
- реплей затрагивает **только строки `P`**: надгробие удаляет строку цели физически только в `P` и не выметает тени соседних слоёв — их собственные слияния позже поймают расхождение по `base_version`;
- таблицы с естественными ключами (уникальный синоним, единственный постоянный комментарий, имена типов) могут столкнуться с независимой правкой `P` — операция падает 422 с указанием таблицы.

Исключение из «конфликт → отказ»: связь на физически отсутствующий конец не блокирует слияние, только не создаётся и попадает в отчёт (`skipped`).

**Узкое исключение (0.10.3, ADR `e4dfdda0`, задача `f5c363a3`):** слияние одной мысли в режиме `combine` объединяет постоянный комментарий слой+основа (LCS, конфликтные блоки с маркерами) — единственное содержательное слияние текстов; предшественник (предок) комментария системой не хранится, поэтому строгий three-way невозможен. Все прочие строки и все прочие режимы остаются посрочным реплеем.

<a id="pub-406f432e"></a>

## Замыкание частичного слияния: набор обязан быть замкнутым по ссылкам

Набор строк, выбранный для **частичного** слияния, обязан быть **замкнут по ссылкам**: концы связей, типы (`type_id` связи и мысли), владельцы комментариев и вложений, `property_id` — либо уже есть в родителе, либо входят в то же слияние.

«Входит в слияние» — строка есть в наборе **независимо от состояния**: живая или надгробие (надгробие тоже переносится и ссылку на себя не нарушает).

Сервер **не расширяет** набор автоматически — это скрыло бы от пользователя, что реально уехало в основу. При незамкнутом наборе операция отклоняется (422) со списком `missing_closure: [{ table, id, referenced_by }]`; клиент или агент дополняет выбор и повторяет вызов.

Проверка выполняется и при полном слиянии: там она вырождена (набор замкнут по построению), но ловит ссылки, исчезнувшие из основы, пока слой жил. Остаточный случай — связь на физически отсутствующий конец — обрабатывается отчётом (`skipped`), а не отказом.

<a id="pub-570e3f14"></a>

## Автосоздаваемый служебный слой перед перезаписью родителя (точка отката)

Перед перезаписью строк в `P` их текущее (до-слияния) содержимое копируется в автоматически создаваемый **служебный слой** — дочерний к `P`, `is_service = 1` (скрыт из списка выбора), с автокомментарием «резерв: слияние «{L.title}» → «{P.title}», {timestamp}». Механизм — тот же copy-on-write; выигрыш — возможность **ручного отката** слияния сравнением с этим слоем, которой иначе не было бы.

Копируются **строки-победители цепочки `P`** для каждого затронутого логического id, а не только физически лежащие в `P`: слой обязан показывать до-слияния **состояние**, видимое из `P`. Если перезаписывать нечего (слой пуст либо содержит только вставки), служебный слой не создаётся, а отчёт несёт `reserve_layer_id: null`.

Строки служебного слоя — живые теневые строки, но удерживающими при физической очистке они **не считаются** (ошибка 1d0620a8): резерв — техническая копия для ручного отката, а не слой с собственными живыми правками, и физическое `DELETE FROM <table> WHERE id = ?` в любом случае снесло бы его теневыми строками вместе с остальными. Иначе purge после любого перезаписывающего слияния был бы навсегда заблокирован до ручного удаления резерва, а автоочистка корзины (§8.4) не срабатывала бы. Такие слои **не считаются в лимит глубины** и не предназначены для работы.

<a id="pub-1d363f1e"></a>

## После слияния строки уходят из слоя, корзина очищается, слой сохраняется

Успешно слитые строки **физически удаляются из слоя `L`** — не надгробием: они ушли к предку, хранить в `L` больше нечего. После полного слияния `L` пустеет относительно `P`, но как сущность **автоматически не удаляется** — это отдельное действие пользователя.

Сразу после слияния выполняется **автоочистка корзины**: слияние снимает удерживающие ссылки так же, как удаление слоя, поэтому помеченные на удаление сущности могут быть вычищены физически; их число попадает в отчёт полем `purged` (серверный вызов очистки — `POST /trash/purge`).

Строки, пропущенные при реплее (связь на физически отсутствующий конец), остаются в слое.

<a id="pub-b1918244"></a>

## Снятие расхождения base_version у строки слоя (reset_override)

`base_version` теневой строки фиксируется при первой материализации и больше не меняется. Поэтому независимая правка той же строки в предке, пока слой жив (типичный случай — хотфикс в основе), делает слой **несливаемым целиком**; снять расхождение прежде было нечем — аналога rebase у слоёв нет.

**Перепривязка** адресует **конкретные строки слоя** (`tables: { ветвимая_таблица: [id…] }`), а не слой целиком, и для каждой теневой строки переставляет `base_version` на текущую версию той же логической строки цепочки предка (победитель, надгробия считаются). Содержимое слоя сохраняется, предок не меняется — слой заявляет «я видел чужую правку и беру ответственность»; после этого сверка проходит и слияние переносит содержимое как обычно. Если строки в предке нет (вставка слоя), `base_version` становится `0` — семантика вставки.

Отдельно, по тому же принципу нумерации: если `version` тени **отстала** от версии строки предка, она поднимается до неё (в отчёте `version_raised_to`) — иначе реплей перенёс бы в предок меньшую версию и откатил нумерацию против монотонности `If-Match`. Версия тени, опережающая предка, не трогается.

**Неразрушающий предпросмотр** (read-only) перечисляет строки слоя, из-за которых слияние будет отклонено, и по каждой отдаёт расхождение «было в основе / стало в слое» (изменившиеся копируемые столбцы). Пробное слияние для этой проверки не годится: слой без конфликтов слился бы раньше времени.

Строки без `version` (синонимы, вложения, значения свойств) конфликтов не детектируют: сброс возвращает их как `unchanged` с причиной `not_versioned`, уже совпадающие — `up_to_date`.

Сброс деструктивен по смыслу — теряет сигнал «основа менялась» для выбранных строк; поэтому требует явного `confirm` и предпросмотра и не запускается автоматически при слиянии (атомарность слияния сохраняется). Операции доступны только агенту (MCP), см. «etn.layers.conflicts / layers.reset_override — аварийное согласование конфликта base_version». Выбор стороны (three-way merge) по-прежнему отсутствует.

## Экспорт и импорт .etnx в контексте слоя

Слой меняет смысл и экспорта, и импорта — но сам слой полем `.etnx` при этом **не становится**: он определяет не то, как записан граф, а то, **что** выгружается и куда попадает результат.

**Экспорт.** Выгружается то, что выбрано у пользователя или агента на момент экспорта: выбрана основа — выгружается основа; выбран слой — выгружается **разрешённое состояние этого слоя** (плёнка вместе со всем, что она не перекрыла у предков), а не только теневые строки слоя — иначе экспорт слоя без большинства мыслей сети был бы бесполезен.

**Импорт.** Результат кладётся в **текущий выбор** целевой сессии (основу или слой). Импортёр не знает и не восстанавливает исходную слоистую структуру источника — он видит уже разрешённый граф.

Формат манифеста (02-data-model.md §9) не меняется: слой — свойство того, **что** экспортируется, а не того, как записан экспортируемый граф.

## Слияние слоя: детекция конфликтов вместо разрешения

### Контекст

При слиянии слоя в основу теневая строка слоя перезаписывает строку предка. Если предок за время жизни слоя тоже изменился (кто-то правил основу параллельно), простое затирание молча уничтожает чужую правку — а внешних ключей и `ON DELETE CASCADE`, которые могли бы подстраховать на уровне СУБД, после S2 уже нет.

### Решение

Слияние (docs/13-layers.md §8) даёт только **детекцию** конфликта, не его разрешение. Каждая затрагиваемая строка несёт `base_version` — версию строки предка на момент материализации теневой строки в слое. При слиянии `base_version` сравнивается с текущей версией строки в предке (та же роль, что `expected_version`/`If-Match` у обычной записи). При любом расхождении вся операция отклоняется целиком (не частично) со списком конфликтов; three-way merge с автоматическим выбором стороны или ручным разрешением конфликтов в фазу S не входит.

Перед перезаписью текущее содержимое затрагиваемых строк предка копируется в автоматически создаваемый резервный служебный слой (`is_service = 1`) — не как альтернатива детекции, а как способ ручного отката уже применённого слияния.

### Следствия

- слияние атомарно: либо применяется целиком, либо отклоняется целиком со списком расхождений — нет промежуточного «частично слито»;
- частичное слияние (набором строк) обязано быть замкнуто по ссылкам (концы связей, типы, владельцы комментариев) — иначе основа получит висячие ссылки, которые больше некому ловить;
- пользователь/агент, получивший отказ, разрешает конфликт вручную (правкой в слое или в основе) и повторяет попытку слияния — инструментов трёхстороннего слияния система не предоставляет.

### Что нельзя делать

Реализовывать «умное» автоматическое разрешение конфликтов (взять более позднее по времени, взять версию с большим `version`, слить текстовые поля построчно и т.п.) — это выходит за рамки принятой модели и должно обсуждаться отдельно, если вообще понадобится. Нельзя также применять слияние частично («что сошлось — то слито») — это скрывает от пользователя реальный результат операции.

### ADR: жизненный цикл журнала — свёртка и обрезка вместо ретенции

#### Контекст

Журнал активности растёт на каждую правку; старые записи нужны от случая к случаю. Автоматическая ретенция (окно N дней) молча выбрасывает и нужное, и ненужное одинаково.

#### Решение

Управляемый жизненный цикл: **свёртка** (до даты — остаются только создание и последнее изменение ключевых сущностей; по удалённым — единственная запись удаления) и **обрезка** (до даты — удаляется всё). Обе операции ручные, необратимые. Слияние слоя в основу сворачивает его события автоматически; удаление слоя удаляет их.

#### Следствия

Глубина детализации истории — выбор администратора сети; свёрнутая история остаётся осмысленной (авторы и итоги сохраняются).

#### Что нельзя

Автоматически удалять записи по возрасту без команды; восстанавливать свёрнутое (операции необратимы).

### Слияние одной мысли из GUI: объединение постоянного комментария как узкое отступление от посрочного реплея

#### Контекст

Слияние слоя — **посрочный реплей без слияния содержимого** (требование 24ca954b); ADR «Слияние слоя: детекция конфликтов вместо разрешения» (db7efc04) прямо объявляет, что three-way merge не входит в модель, а «умное» автоматическое разрешение конфликтов делать нельзя. Задача f5c363a3 («Слияние отдельных мыслей в основу из GUI с разрешением конфликтов») требует дать пользователю разрешить конфликт по **одной мысли** прямо в GUI, включая вариант «Объединить изменения» — серверное объединение постоянного комментария с маркерами конфликтов git-стиля. Это осознанное отступление от 24ca954b, согласованное с пользователем.

#### Решение

Вводится **узкое** отступление: операция слияния одной мысли (`POST /layers/{id}/merge` с `thought_id` и `mode=combine`) объединяет **постоянный комментарий** мысли на сервере, помечая расходящиеся участки маркерами конфликтов git-стиля (`<<<<<<< слой` / `=======` / `>>>>>>> основа`).

Границы отступления:

- объединяется **только постоянный комментарий**; связи, значения свойств, синонимы, вложения и хроно-записи переносятся **версией слоя** обычным реплеем (хроно-записи аддитивны — дописываются в основу как есть);
- только для **одной мысли**: `mode` задаётся лишь вместе с `thought_id`; слияние слоя целиком и слияние набором строк (`tables`) сохраняют прежнюю семантику без слияния содержимого;
- набор строк мысли сервер собирает сам как **замкнутое** подмножество (мысль, её зависимые строки, её рёбра), но **не расширяет** его за пределы мысли: незамкнутый набор по-прежнему отклоняется 422 `missing_closure` (требование 406f432e);
- режимы `overwrite` и `combine` снимают расхождение `base_version` по строкам мысли — это явно выбранный пользователем вариант «версия слоя побеждает»; вариант «Отказаться от изменений» — отдельная операция `layers.discard`, физически удаляющая строки мысли из слоя.

#### Ограничение алгоритма (общего предка нет)

Содержимое комментария-предка система **не хранит** (в `comments` только текущее тело и `version`), поэтому настоящий трёхсторонний дифф невозможен. Объединение — построчное по LCS двух доступных версий (слой и основа): непересекающиеся участки объединяются, а участок, где у обеих версий есть свои строки, сохраняется целиком в конфликтном блоке. Ни один текст не теряется. Если основа комментарий не меняла (`base_version` тени совпал с версией основы), побеждает версия слоя без маркеров.

#### Следствия

- пользователь разрешает конфликт, не выходя из GUI: «отказаться» / «переписать» / «объединить»;
- после обработки мысль уходит из списка отличий слоя (перекрытие снято);
- ADR db7efc04 остаётся в силе для всех прочих слияний; запрет «умного» авторазрешения сохраняется — объединение здесь не авторазрешение, а явный выбор пользователя с сохранением обоих текстов.

#### Что нельзя делать

- расширять слияние содержимого на другие поля/таблицы или на слияние слоя целиком;
- разрешать конфликт молча (без явного выбора пользователя) или терять текст одной из сторон;
- автоматически достраивать набор строк сверх замкнутого подмножества мысли.
