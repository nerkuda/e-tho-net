## client_meta — состояние установки клиента

Состояние, уникальное для **установки приложения** и не зависящее ни от мыслесети, ни от пользователя, — уровень L5. Простое хранилище «ключ → значение»: `key` TEXT PK, `value` TEXT (строка или JSON).

**Зарезервированные ключи:**

- `client_id` — UUIDv4 установки. Генерируется один раз при первом запуске и дальше не меняется; уходит серверу заголовком `Client-Id` в каждом запросе и при WebSocket-подключении. По нему клиент узнаӑт эхо собственных изменений; потеря `client_id` равносильна появлению нового клиента.
- `last_seq` — объект `{ [network_id]: <seq> }`, позиция в журнале событий каждой сети. Обновляется по мере применения пришедших событий и уходит в кадре догона при переподключении. Значение **per-client, а не per-user**: две установки одного человека догоняют журнал независимо. Разбивка по сетям важна: табы держат несколько сетей открытыми одновременно.
- `theme`, `zoom`, `active_profile_id` — настройки самой установки: тема оформления, масштаб интерфейса, текущий серверный профиль.

**Дополнительные материалы**
- относится к подсистемам: Десктоп-клиент (Electron), Real-time канал (WebSocket)
- применяется к: Тема оформления и масштаб интерфейса клиента в MVP

## event_log — журнал событий сети

**Актуализация 0.8.4 (задача 09f19952).** `etn.changes.list` снят с постоянного набора MCP — это действие `changes.list` исполнителя `etn.ops` (read-only). Детали — `etn.guide { topic: "changes.list" }`.

Таблица `_system.db` — буфер всех событий сети. Источник для восстановления после обрыва (кадр `resume`) и дельты `etn.changes.list`.

| Колонка | Смысл |
|---|---|
| `network_id` | сеть |
| `seq` | монотонный номер (общий счётчик с конвертом события) |
| `ts` | время записи |
| `type` | вид события |
| `data` | полезная нагрузка |

Окно удержания — по умолчанию последние 10 000 событий или 24 часа; старые записи удаляет фоновая джоба. Клиент с `last_seq` старше окна получает `resume.stale` и делает полный рефетч состояния, а не дельту.

- относится к подсистемам: Real-time канал (WebSocket), Хранилище (SQLite)
- зависит от: Конверт события real-time

## GET и PATCH /me — профиль текущего пользователя

Самообслуживание владельца ключа: кто я и как меня зовут.

```
GET   /api/v1/me
→ 200 { data: { id, username, display_name, is_admin } }

PATCH /api/v1/me   { display_name?: string | null }
→ 200 { data: { id, username, display_name, is_admin } }
```

`GET /me` — штатный способ проверить валидность токена при подключении клиента.

`PATCH /me` меняет **только** `display_name` текущего пользователя:

- `is_admin`, `disabled`, `username` через этот маршрут не меняются — это делает админ через `PATCH /admin/users/{id}`;
- значение обрезается по краям; пустая строка после trim сохраняется как `null`; лимит 200 символов, иначе `VALIDATION_ERROR`;
- `null` или отсутствие поля — no-op, текущее значение сохраняется;
- успешное изменение пишется в журнал аудита: `category=user`, `action=user.update`, `details.display_name` с признаком `self: true` и `previous_display_name`.

**Дополнительные материалы**
- относится к подсистемам: REST API, Аутентификация и права доступа
- зависит от: users — таблица пользователей сервера

## networks — реестр мыслесетей и самоописание сети

Реестр мыслесетей в системной БД. Сами данные сети лежат в отдельной БД, здесь — только запись о её существовании и самоописание.

| Столбец | Тип | Описание |
|---|---|---|
| `id` | TEXT PK | UUID; он же — имя каталога сети на диске |
| `display_name` | TEXT NOT NULL | Имя, меняется свободно |
| `owner_id` | TEXT NOT NULL FK → users.id ON DELETE RESTRICT | Владелец |
| `description` | TEXT | Назначение сети в 1–2 абзацах |
| `when_to_use` | TEXT | Когда агенту обращаться к сети: use cases и какие поля читать |
| `conventions` | TEXT | Правила записи: формат хронологий, пометка актуальности, нейминг, ссылки на типы и шаблоны |
| `examples` | TEXT | Примеры хороших и плохих записей |
| `node_section_type_id` | TEXT | Тип мысли, активные мысли которого образуют структуру сети. Без SQL-FK (ссылка в другую БД); тип, указанный в настройках сети, **нельзя удалить** — `DELETE /networks/{id}/thought-types/{tid}` отклоняется с `VALIDATION_ERROR`, пока ссылка не снята |
| `created_at` / `updated_at` | TEXT NOT NULL | |

**Неизменность id.** `id` равен имени каталога на диске и никогда не меняется; переименование сети затрагивает только `display_name`.

**Самоописание сети.** Четыре markdown-поля (`description`, `when_to_use`, `conventions`, `examples`) — это то, как сеть объясняет себя AI-агенту. Сервер хранит только исходник markdown; клиент рендерит preview на лету общим рендерером. Конвенция заполнения `when_to_use`: для каждого use case указываются релевантные поля сети (например, «Кодирование → structure, conventions») — агент не читает все поля подряд, а берёт только нужные текущей задаче.

**Компактность списка.** В списке сетей `conventions` и `examples` не отдаются — только `description` и `when_to_use`, иначе ответ раздувается при большом числе сетей.

**Дополнительные материалы**
- относится к подсистемам: Хранилище (SQLite), MCP-сервер
- применяется к: ADR: служебные типы сети адресуются ролями из словаря type_roles

## POST /focus-order — ручной порядок мыслей в зоне фокуса

```
POST /api/v1/networks/{nid}/thoughts/{fid}/focus-order
     { dir: "children"|"parents", ordered_ids: ["id1","id2","id3"] }
→ 200 { data: { focus_thought_id, dir, ordered_ids } }
```

Сервер записывает `position` = индекс в массиве для каждой мысли; прочие записи по ключу (пользователь, фокус, направление) удаляются — **replace-семантика**. Побочный эффект полезен: осиротевшие записи от удалённых связей подчищаются автоматически.

**Клиент обязан слать только id, реально присутствующие в текущей зоне, и в нужном порядке**: сервер длину и полноту не валидирует, он лишь записывает присланное.

Зона `siblings` ручного порядка не имеет — только `children` и `parents`. Порядок виден только при `sort: "manual"` соответствующей зоны.

**Дополнительные материалы**
- относится к подсистемам: REST API, Пользовательский интерфейс (холст и редактор)
- зависит от: user_focus_order — ручной порядок мыслей в зоне фокуса
- применяется к: Сервер: тест записи покрывает каждое значение вида REST-контракта

## POST /thoughts/copy-batch — копирование подграфа мыслей между сетями

Атомарное копирование подграфа мыслей из одной сети в другую (или в ту же).

```
POST /api/v1/networks/{nid}/thoughts/copy-batch
{ source_network_id, parent_thought_id,
  thoughts: [ { source_id,
                thought: { title, synonyms?, type_id?, type_name?, active? },
                permanent_comment?: { title?, body_md } | null,
                properties?: { key: value|null },
                attachments?: [ { kind, url?, file_path?, title?, description? } ] } ],
  links: [ { source_id, target_id, type_id?, type_name?, active?,
             fg_color?, bg_color?, width?, style?,
             permanent_comment?, attachments? } ] }
→ 200 { data: { thought_id_map, link_id_map,
                created_thoughts, created_links, created_attachments } }
```

**Это «создай из снапшота», а не «скопируй из БД»**: сервер не читает `source_id` из исходной сети — он использует их только для карт соответствия и определения корней подграфа; все `source_id` обязаны быть валидными UUID. Карты `thought_id_map`/`link_id_map` нужны клиенту, чтобы переписать wiki-ссылки.

**Комментарии и вложения**: копируются постоянные комментарии мыслей и связей и метаданные вложений. Файлы вложений: при копировании в **другую** сеть (`source_network_id` ≠ целевая) сервер физически копирует файл в каталог `attachments/` сети-получателя (к имени добавляется номер копии — `<stem>-<n><ext>`, `n` ≥ 2, чтобы имена не столкнулись; один исходный файл на батч копируется один раз, все строки вложений с ним делят одну копию) и прописывает в копии вложения `file_path` на новый файл; при копировании **внутри одной** сети файл не дублируется — остаётся общий. Вложение с тем же `(kind, url/file_path)`, уже есть у целевой мысли — пропускается тихо. Отсутствующий на диске исходный файл — метаданные сохраняются, копия не создаётся, операция не падает (предупреждение в лог). Файлы записываются после фиксации транзакции БД (осиротевших файлов при откате не остаётся).

**(2026-10-07, ошибка `b83a7d89`, версия 0.12.1)** — правка контракта: ранее «файл на диске не дублируется» для всех случаев, и вложение в копии в другой сети было недоступно; теперь при межсетевом копировании файл копируется.

**Wiki-ссылки сервер не переписывает**: внутри одной сети `[[#<id>]]` остаются как есть; при кросс-сетевом копировании клиент обязан прислать уже переписанные строки формата `[[n:<net>#<id>]]`.

**Атомарность и идемпотентность**: вся операция — одна транзакция (при любой ошибке не создаётся ничего); повтор с тем же `Client-Request-Id` в течение 10 минут вернёт кэшированный ответ.

**Real-time**: на каждую созданную мысль шлётся `thought.created`, на каждую связь — `link.created`; автор операции своё эхо не получает.

**Права**: обе сети должны быть доступны тому же пользователю; админского «копировать чужое» нет.

**Ошибки**: `VALIDATION_ERROR` — пустой `thoughts`, невалидный `parent_thought_id` или `source_id` не UUID; `NOT_FOUND` — `parent_thought_id` нет в целевой сети; `FORBIDDEN` — защищённая мысль или нет доступа; `TRANSACTION_CONFLICT` — редкая гонка, клиент повторяет запрос.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: attachments — вложения мыслей и связей, Идемпотентность изменяющих запросов через client_request_id, thoughts — таблица мыслей
- применяется к: Что не копируется при копировании подграфа мыслей, Корни копируемого подграфа привязываются к мысли-приёмнику, Резолв типов и ссылок при копировании мыслей в другую сеть, Кросс-сетевые значения переносятся копированием как есть

## POST /thoughts/{id}/focus — окрестность мысли для холста

Главная операция холста: перевод фокуса на мысль и получение всего, что нужно для отрисовки окрестности, одним запросом.

```
POST /api/v1/networks/{nid}/thoughts/{id}/focus
→ 200 { data: { focused, parents, children, siblings, edges,
                sorts: { parents: { sort, order }, children: {…}, siblings: {…} } } }
```

Побочный эффект: записывается метка просмотра (`last_viewed_at` текущего пользователя). А вот сама фокус-мысль как «последняя просмотренная» сервером не сохраняется — это клиентское состояние.

**Зоны взаимоисключающи**: мысль встречается не более чем в одной из `parents`/`children`/`siblings`; приоритет — фокус > parents > children > siblings.

Элемент зоны: `{ id, title, type_id, icon, active, link_id, link_type_id, link_active }` — то есть мысль вместе со связью, которой она держится за фокус.

`edges` — **все** active-связи, у которых оба конца входят в множество `{focused} ∪ parents ∪ children ∪ siblings`, включая связи сосед↔сосед: `{ id, source_id, target_id, type_id }`. От распределения мыслей по зонам не зависят — холсту нужны все видимые линии.

`sorts` — текущая сортировка пользователя по каждой зоне: `sort` — `manual`/`alpha`/`created`/`viewed` (дефолт `created`), `order` — `asc`/`desc`. Зона `siblings` вручную не упорядочивается (`manual` недоступен), но свою настройку несёт; объект возвращается для всех трёх зон, чтобы меню сортировки отмечало активный пункт.

Неактуальные мысли и связи попадают в ответ только при включённом `show_inactive`.

**Рёбра в корзине** (0.8.2, ошибка 355319d4). Связь, помеченная на удаление, остаётся в ответе: помеченную сущность холст обязан показать с признаком, а не спрятать (критерий S13 — «видно на холсте со значком 🗑»). И элемент зоны, и ребро `edges` несут `link_marked_for_deletion`; `link_active` остаётся `true` — пометка на удаление это не неактуальность. Пометка НЕ влияет на попадание ребра в ответ (`show_inactive` по-прежнему только про `active`).

**Настройка видимости корзины** (задача 77923b49, коммит e55e5c6). Тело запроса принимает `show_trash`; без него флаг берётся из `preferences.show_trash` пользователя (дефолт `true`). При выключенной настройке помеченные рёбра и помеченные соседи из ответа ИСКЛЮЧАЮТСЯ — этим уточнён абзац «Пометка НЕ влияет на попадание ребра в ответ»: он описывает поведение по умолчанию, когда содержимое корзины показывают.

**Дополнительные материалы**
- относится к подсистемам: REST API, Пользовательский интерфейс (холст и редактор)
- зависит от: user_focus_preferences — сортировка зон холста, thoughts — таблица мыслей, links — направленные связи между мыслями, thought_views — метки просмотра мыслей
- применяется к: Фильтр обхода по типам связей, Порядок мыслей в зоне фокуса: правила применения сортировки

## PUT /focus-preferences — выбор сортировки зоны фокуса

```
PUT /api/v1/networks/{nid}/thoughts/{fid}/focus-preferences
    { dir: "children"|"parents"|"siblings",
      sort: "manual"|"alpha"|"created"|"viewed",
      order: "asc"|"desc" }
→ 200 { data: { focus_thought_id, dir, sort, order } }
```

Выбор сортировки хранится **per-user, per-focus, per-направление** и синхронизируется между клиентами того же пользователя real-time событием с `audience = user`.

**При `sort: "manual"` параметр `order` обязан быть `asc`** (или опущен — нормализуется в `asc`); `desc` отвергается `VALIDATION_ERROR`: ручной порядок задан явно и обращать его нечем.

Зона `siblings` ручного порядка не имеет, но свои `alpha`/`created`/`viewed` хранит.

**Дополнительные материалы**
- относится к подсистемам: REST API, Пользовательский интерфейс (холст и редактор)
- зависит от: user_focus_preferences — сортировка зон холста
- применяется к: Сервер: тест записи покрывает каждое значение вида REST-контракта, Состояние уровня «пользователь × мыслесеть» и его синхронизация, Порядок мыслей в зоне фокуса: правила применения сортировки

## Real-time канал (WebSocket)

WebSocket-шлюз сервера: удерживает подключения клиентов, фильтрует события по `network_id`, доставляет изменения подписчикам в реальном времени.

События он не порождает — только доставляет: изменение пишет ядро, оно же эмитит событие в pub/sub канала сети, шлюз пушит его участникам. Правки человека и правки MCP-агента идут одним путём, поэтому участники видят их одинаково.

Часть событий адресована не всей сети, а конкретному пользователю (`audience=user`) — так синхронизируются его личные настройки между его же клиентами.

**Дополнительные материалы**
- применяется к: Границы MVP: чего в системе намеренно нет, Масштабирование real-time: in-memory pub/sub, дальше Redis

## saved_filters — именованные отборы видов

Именованные отборы — критерии и сортировка, сохранённые пользователем для повторного применения. **Не ветвятся**.

| Столбец | Тип | Описание |
|---|---|---|
| `id` | TEXT NOT NULL | UUID; первичный ключ |
| `user_id` | TEXT NOT NULL | Владелец; через API доступны только свои отборы |
| `view` | TEXT NOT NULL | К какому виду относится отбор |
| `name` | TEXT NOT NULL | Имя отбора |
| `definition` | TEXT NOT NULL | JSON с критериями и сортировкой; набор полей зависит от вида |
| `created_at` / `updated_at` | TEXT NOT NULL | |
| UNIQUE | `(user_id, view, name)` | Повторное имя в том же виде отвергается как дубль |

Отборы строго личные: чужие не видны и не редактируются даже владельцем сети. Между клиентами одного пользователя синхронизируются событиями real-time.

### Динамические даты и хроника (0.10.1)

Для `view = "chronicle"` определение включает период с динамическими токенами дат (`$today`, `$thought.[…]`, арифметика) и критерии целей (набор «Структур», включая значения свойств): запись проходит, если хотя бы одна её привязка удовлетворяет критериям целей. Токен хранится в `definition` без изменений и раскрывается при применении отбора. См. требования «Динамические токены дат в периоде и сохранённых отборах» и «Критерии отбора хроники: записи + цели».

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор), Полнотекстовый поиск (FTS5)
- применяется к: Отбор типа мысли — строка отдельной ветвимой таблицы, а не поле типа, Динамические токены дат в периоде и сохранённых отборах, Критерии отбора хроники: записи + цели, «хотя бы одна цель удовлетворяет»

## server/src/domain/graph-traversal.ts — единый helper обхода

### Назначение

Единый helper обхода графа на сервере: BFS от seed-узлов с `visited: Set<string>`, лимитами `maxDepth`/`maxNodes` и причиной остановки `'max_depth' | 'max_nodes'`. Используется операциями `subgraph` и другими обходами доменного слоя.

### Важно знать перед правкой

- Дефолт `maxDepth` — `TRAVERSAL_DEFAULTS.MAX_DEPTH` (20) из `@etn/shared`; `maxNodes` — из настройки `mcp.max_nodes_per_subgraph`.
- Защита от циклов — именно `visited`-set: повторно посещённый узел не обходится и не эмитится.
- Узел может встретиться на разных глубинах (алмаз, взаимные связи A↔B) — visited гарантирует однократную обработку; это НЕ считается зацикливанием.
- Сложные обходы с фильтрами по типам идут здесь, в TypeScript; в SQL обход реализован рекурсивным CTE с `UNION`-дедупликацией (см. `search-service.ts`), path-CTE отброшен.

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой)
- применяется к: Граф может содержать циклы — обход с visited-set и лимитами, Границы обхода графа: глубина, узлы, таймаут

## user_focus_order — ручной порядок мыслей в зоне фокуса

Ручной порядок мыслей зоны фокуса — только при ручной сортировке. Для родственников записи не создаются. **Не ветвится**.

| Столбец | Тип | Описание |
|---|---|---|
| `user_id` | TEXT NOT NULL | |
| `focus_thought_id` | TEXT NOT NULL | SQL-FK снят |
| `dir` | TEXT NOT NULL | `'children'` или `'parents'` |
| `thought_id` | TEXT NOT NULL | Ребёнок или родитель |
| `position` | INTEGER NOT NULL | Линейный индекс в порядке зоны |
| `updated_at` | TEXT NOT NULL | |
| PRIMARY KEY | `(user_id, focus_thought_id, dir, thought_id)` | |

**Смысл `position`.** Это линейный индекс в списке зоны, упорядоченном построчно: первая мысль — 0, вторая — 1 и так далее, **без пропусков**. При построчной раскладке соответствие «визуальная ячейка = позиция» однозначно.

**Осиротевшие записи допускаются и это не баг.** Если связь удалена, а пользователь после этого не менял порядок, запись остаётся. Выборка зоны такие записи не возвращает, они не мешают и чистятся автоматически при следующем успешном изменении порядка для этой пары «фокус + направление» (семантика полной замены).

Удаление фокус-мысли или самой мысли-члена зоны чистит записи по обоим идентификаторам — явно приложением.

**Перспектива.** Ручной порядок переезжает в поле самой связи (общее для всех пользователей); до этого момента работает этот per-user механизм.

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор), Хранилище (SQLite)
- зависит от: user_focus_preferences — сортировка зон холста
- применяется к: Порядок мыслей в зоне фокуса: правила применения сортировки

## visit_history — история открытых мыслей на клиенте

Единая история мыслей, открытых в редакторе на этом клиенте — общая для всех видов (карта, структуры, хроника). Локальное состояние уровня L4 со скоупом `(profile_id, network_id, tab_id)`.

| Столбец | Тип | Смысл |

## WS /api/v1/realtime — подключение к каналу событий сети

WebSocket-канал доставки событий одной мыслесети. Один сокет = одна сеть.

Адрес: `ws(s)://<host>/api/v1/realtime?network_id=<nid>`
Заголовки: `Authorization: Bearer <API-key>`; `Client-Id: <UUID установки клиента>`.

## Виртуальная сетка холста

Зоны верх-лево, верх-право и низ представляются таблицами с ячейками одинаковой ширины (колонки фиксированы, высота строки — по содержимому); одна ячейка — одно облачко.

- Ширина ячейки = `cloud_width` (L4), высота строки = наибольшее облачко строки (дыр в сетке нет), плюс отступ `cloud_gap` между ячейками. Все размеры умножаются на множитель `canvas_zoom` (масштаб холста): `cols`/`rows` и виртуализация считаются по эффективным размерам.
- `cols = floor(zone_width / (cloud_width + gap))`; число строк — по фактическим высотам. Мыслей больше ячеек — прокрутка; сетка виртуальная, рендерятся только видимые + запас.
- Позиция в сетке = **порядок** мысли в зоне; свободных (x, y) координат нет. Заполнение по строкам (row-major): ячейка (c, r) содержит мысль индекса `c + r × cols`; чтение «слева направо, сверху вниз» совпадает с упорядоченным списком зоны — база курсорной навигации стрелками и `Ctrl+Shift+↑/↓`.
- Ручное упорядочивание = перетаскивание с `Ctrl+Shift` (меняет `position` в `user_focus_order`).
- Центральная зона (фокус) — не часть сетки: фокус-облачко по центру холста со своими правилами размера.

**Прокрутка:** все зоны прокручиваются вертикально (row-раскладка противоречит горизонтальной прокрутке исходного замысла). На полосе прокрутки отображается диапазон видимых мыслей (`12–36`). Виртуализация рендера по сетке: неотрисованные строки оцениваются по минимальной высоте облачка, после отрисовки измеряются и раскладка один раз пересчитывается.

**Якорь раскладки (задача f45ffc8a).** Сетка якорится внутри зоны, а не в её левом верхнем углу: смещение сетки = (размер зоны − размер контента) × доля якоря по каждой оси (чистая `anchorOffset`, `lib/pure.ts`). Предки (верх-лево) — правый-нижний край, родня (верх-право) — левый-нижний край, потомки (низ) — центр-верх: так зоны стягиваются к фокус-ряду. Смещение двигает только начало всей сетки — порядок облачков (row-major), отступы, окно виртуализации и попадание курсором не меняются; выравнивание внутри облачка не затрагивается. Контент больше зоны — прижат к началу оси, дальше прокрутка. Ручные позиции (`manual_position` — номер в `user_focus_order`) и ручное упорядочивание от якоря не зависят.

 Ширина контента для якоря — самый широкий РЯД облачков, а не коробка сетки: `gridTemplateColumns` фиксирует все `cols` колонок, поэтому у неполного ряда коробка шире контента и якорь по ней обнуляется (чистая `zoneContentWidth`, `lib/pure.ts`).

**Ширина коробки сетки (ошибка 1deced69).** `gridTemplateColumns` фиксирует все `cols` колонок, поэтому коробке `.zone-grid` явно выставляется ширина = ширине видимого контента (`zoneContentWidth`, самый широкий ряд): пустые хвостовые колонки не выносятся якорем за правый край зоны и не рождают горизонтальную прокрутку. Ширина коробки задаётся в строке, поэтому остаточная коробка пустого сектора сбрасывается. Коробка шире зоны только когда одно облачко шире зоны (`cols === 1`) — тогда прокрутка законна.

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор)
- зависит от: user_focus_preferences — сортировка зон холста

## Горячие клавиши клиента

Набор глобальных клавиатурных команд клиента.

- `Ctrl+Shift+F` — глобальный поиск (только в виде «Карта мыслей»); `Ctrl+F` — поиск внутри текущего текстового поля (умолчания поля комментария — в разделе ниже).
- На карте (фокус клавиатуры на холсте): стрелки — курсор-рамка по облачкам; `Home`/`End` — край зоны; `Enter` — открыть мысль курсора в редакторе; `Ctrl+Enter` — перевести в фокус; `Ctrl+Shift+↑/↓` — ручная перестановка в зоне.
- `Ctrl+клик` — toggle выделения.
- `Ctrl+C` — скопировать мысль под курсорной рамкой холста, без активной рамки — мысль в фокусе; содержимое панели выделения не влияет. В редактировании (`<input>`, CM6, `contenteditable`) и при непустом текстовом выделении вне полей — нативная копия текста.
- `Ctrl+V` — вставить под мысль под курсорной рамкой (или под единственную выделенную); в облачко, в комментарий (только wiki-ссылки) или кросс-сетью — пока системный буфер не перезаписан. Перезаписан — системный clipboard парсится как текст (UUID → связь; строка → новая мысль). В редактировании — нативная вставка (перехват только файлы и wiki-ссылки ETN).
- `Ctrl+=` / `Ctrl++` — масштаб холста +5% (до 200%); `Ctrl+-` — −5% (до 50%); `Ctrl+0` — сброс 100%. Действуют на экране сети; масштаб показывается в статус-баре и сохраняется (L4 `canvas_zoom`).
- Стрелки без модификаторов — навигация по карте; с `Alt`/`Shift` навигации не выполняют.
- В диалогах: `Escape` снимает верхний диалог без применения (нижележащие не трогаются); `Ctrl+Enter` — «OK»/«Применить» (кроме полей со своим значением: пакетное добавление, выбор кандидата). Клик по подложке диалог НЕ закрывает (задача c9353ce1): закрывают только кнопки диалога, выбор из списка и Esc; клик мимо тела диалога гасится и не проваливается на холст.
- `Ctrl+наведение` на иконку-картинку — «лупа»: всплывашка с полной картинкой (≤70% окна); скрывается при отпускании `Ctrl`, уходе курсора, скролле, `Escape`.
- `Ctrl+колесо` над markdown-полем — масштаб документа (не холста).

## Границы обхода графа: глубина, узлы, таймаут

### Утверждение

Любой обход графа на сервере ограничен тремя пределами:

| Параметр | Default | Где задаётся |
|---|---|---|
| `max_depth` (subtree/subgraph) | 20 | параметр запроса, переопределяется агентом |
| `max_nodes` (subgraph) | `mcp.max_nodes_per_subgraph` (500) | L1-настройка сервера |
| `query_timeout_ms` | 5000 | хард-лимит сервера |

Дефолты глубины и таймаута — `TRAVERSAL_DEFAULTS` в `@etn/shared` (`shared/src/constants.ts`): `MAX_DEPTH = 20`, `QUERY_TIMEOUT_MS = 5000`.

При превышении `max_nodes` сервер обязан вернуть частичный результат с `meta.truncated = true` и указанием причины (`max_depth` / `max_nodes`), а не ошибку и не полный обход.

Защита от цикла (visited-set / UNION-CTE) включена всегда — см. ADR «Граф может содержать циклы — обход с visited-set и лимитами».

### Границы применения

Серверная сторона. Касается всех операций обхода: `etn.thoughts.subgraph`, `search` с `in_subtree_of`, `neighbors` при `depth > 1`, `thoughts.path` (0.8.3, действие `etn.ops`), сценариев «добавить всех потомков в выделение».

**Дополнительные материалы**
- относится к подсистемам: Ядро (доменный слой)
- применяется к: server/src/domain/graph-traversal.ts — единый helper обхода

## Кадр resume — догон пропущенных событий после обрыва

Клиентский кадр восстановления после обрыва: `{"type":"resume","last_seq":41}`. Сервер отдаёт все события сети с `seq > last_seq`, накопленные в окне удержания `event_log`, пропуская события, невидимые в текущем слое сессии подписчика.

Если позиция устарела, сервер отвечает `{"type":"resume.stale","last_seq":<граница>}` — клиент выполняет полную перезагрузку состояния (повторно вызывает `POST /thoughts/{id}/focus`) и продолжает с позиции, названной сервером. Причины `resume.stale`:

- `last_seq` старше окна удержания `event_log`;
- `last_seq` предшествует последнему переключению слоя сессии (`switched_at_seq`) — дельта через границу переключения невозможна.

Реконнект: при обрыве клиент повторяет подключение с экспоненциальным backoff и jitter 1→30 с; после каждого переподключения шлёт `resume`.

**Дополнительные материалы**
- относится к подсистемам: Real-time канал (WebSocket)
- зависит от: POST /thoughts/{id}/focus — окрестность мысли для холста, event_log — журнал событий сети
- применяется к: Видимость событий по слою подписчика, Переключение слоя сессии — полный ресинк через switched_at_seq

## Клавиатурная навигация по карте

Навигация клавиатурой доступна, пока фокус клавиатуры на холсте (клик мышью по холсту/облачку оставляет его там).

- **Стрелки** перемещают курсор (пунктирная рамка на облачке): ближайшее облачко в направлении стрелки по видимой геометрии (включая фокус-облачко; до первого шага курсор стоит на фокус-облачке). Нет облачков в направлении, но зона скроллится — прокрутка и повтор против свежего окна.
- **Tab / Shift+Tab** — как стрелки → / ← (нативный порядок табуляции не используется: он следует слотам виртуализации).
- **Home / End** — первое/последнее облачко зоны курсора; с фокус-облачка — край первой/последней непустой зоны (Home: верх-лево → верх-право → низ; End — обратно).
- **Enter** — как одиночный клик (открыть в редакторе с ореолом; на фокус-облачке — вернуть редактор к фокусной мысли). **Ctrl+Enter** — как двойной (перевести в фокус).
- **Ctrl+Shift+← / →** — переместить мысль курсора на позицию в порядке зоны (сервер — `focus_order`); только зоны верх-лево/низ при ручной сортировке (иначе подсказка). При row-major — естественное движение на одну мысль влево/вправо с оборачиванием по строкам.
- **Escape** — снять рамку.

Курсор сбрасывается при смене фокуса; рамка переезжает с облачком при реордеринге и пере-применяется после перерисовок (включая виртуализацию).

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор)

## Конверт события real-time

**Актуализация 0.8.4 (задача 09f19952).** `etn.changes.list` снят с постоянного набора MCP — это действие `changes.list` исполнителя `etn.ops` (read-only). Детали — `etn.guide { topic: "changes.list" }`.

Единый формат каждого события, доставляемого сервером клиентам через WebSocket, и каждой записи `event_log`.

| Поле | Тип | Смысл |
|---|---|---|
| `type` | string | вид события, напр. `thought.created` |
| `seq` | int | монотонный номер события в пределах сети; счётчик `network_seq` в `_system.db` инкрементируется **в той же транзакции**, что и запись |
| `ts` | ISO-8601 | момент события |
| `actor` | `{user_id, client_id}` | кто изменил; `client_id` — для подавления эха (клиент игнорирует события, инициированные им самим) |
| `network_id` | UUID | сеть события |
| `layer_id` | UUID | слой, в котором материализовалась запись; `BASE_LAYER_ID` для записей в основе и для неветвимых событий; заполнен всегда — конверт единообразен |
| `data` | object | полезная нагрузка; свой формат у каждого семейства событий |
| `meta` | `{version, request_id}` | `version` сущности после изменения; `request_id` = `Client-Request-Id` запроса — по нему клиент сопоставляет свой запрос с пришедшим эхом |
| `audience` | `"network"` \| `"user"` | `network` (по умолчанию) — все участники сети; `user` — только подключения того же `user_id` (приватные пользовательские настройки) |

`seq` — основа пропуска/повторной доставки: клиент хранит последний полученный seq и досылает его в кадре `resume` после обрыва. `layer_id` используется WebSocket-шлюзом и `etn.changes.list` для вычисления видимости события на подписчика.

**Дополнительные материалы**
- относится к подсистемам: Real-time канал (WebSocket)

## Копирование и вставка мыслей

Перенос мыслей и подграфов через буфер: в облачко (карта/структуры), в комментарий (CM6) и кросс-сетью. Серверная операция — `POST /thoughts/copy-batch`; состояние буфера — L26.

**Что копируется.** `Ctrl+C` копирует мысль под курсорной рамкой холста, без рамки — в фокусе редактора; панель выделения не влияет. Несколько мыслей — команда «Скопировать мысли» меню «Действия» (без горячей клавиши — `Ctrl+C` всегда одна мысль); копируются и связи между ними. Приоритет текстового выделения: непустое видимое выделение вне полей → нативная копия текста. В снапшот попадают: title, synonyms, active, стиль, иконка, тип (+имя для резолва), постоянный комментарий, значения свойств (thought_ref — id+title), вложения (url/путь+мета; байты файла в снапшот не кладутся — только путь), межмыслевые связи. Не копируются: id, настройки типов, хронология, таймстемпы. Сервер резолвит типы и thought_ref в сети-получателе (по id, затем по имени; не нашлось — `null`).

**Вложения.** Метаданные вложения переносятся всегда, а байты файла снапшот не несёт — только путь. При копировании в ДРУГУЮ сеть сервер физически копирует файл вложений в сеть-получатель (к имени добавляется номер копии — `<stem>-<n><ext>`, чтобы имена не столкнулись; один исходный файл на батч копируется один раз) и прописывает в копии вложения ссылку на новый файл. При копировании ВНУТРИ одной сети файл не дублируется — остаётся единственный экземпляр.

**(2026-10-07, ошибка `b83a7d89`, версия 0.12.1)** — правка поведения: ранее файлы вложений не копировались вовсе, и в копии мысли вложение было недоступно (`HTTP 404`); теперь при межсетевом копировании файлы копируются, внутри сети — общий файл.

**Зеркалирование в системный буфер:** вместе со снапшотом ETN пишет в системный буфер wiki-ссылки `[[#<id>]]` (через запятую) — приватный текст наружу не утекает, буфер всегда осмыслен, и отличим «наш» буфер от перезаписанного.

**Wiki-ссылки в комментариях:** та же сеть — `[[#<id>]]` остаётся (id ремапится); кросс-сеть — клиент переписывает на `[[n:<net>#<id>]]` (сервер этого не делает). Ссылки без изменений не переписываются.

**Вставка в облачко:** цель — фокусная мысль (меню «Вставить» другого облачка), иначе мысль под курсорной рамкой, иначе единственная выделенная, иначе `focus.focused`. Вызывается `pasteThoughtsTo(targetId)`: copy-batch с `parent_thought_id`; связь-родитель получает только корень подграфа (мысль без входящей от скопированных). Буфер пуст/устарел, а в системном текст: UUID → поиск и связь; иначе новая мысль по строке (до `|` имя, после — синонимы); многострочно — по строке.

**Вставка в комментарий (CM6):** нативная вставка не перехватывается; перехват только: 1) файлы в буфере → сохраняются вложениями + markdown-ссылка `![alt](etnimg:…)`; 2) wiki-ссылки ETN (системный буфер совпадает с записанным при копировании и снапшот жив) → вставка `[[#<id>]]`/`[[n:…]]` через запятую. Прочий текст — нативно (снапшот не подменяет). Для давних копий — команда «Вставить ссылки на мысли» в контекстном меню комментария.

**Кросс-сеть:** разрешена между сетями одного пользователя; `source_network_id` фиксирован в снапшоте; та же сеть — перезапись ссылок не нужна.

**Состояние буфера:** только в памяти клиента (перезапуск сбрасывает — намеренно); при переключении сети сохраняется, `cursorId` сбрасывается; команды «Очистить буфер» нет. **Устаревание:** снапшот действителен, пока системный буфер не перезаписан (сверка в момент вставки с записанными wiki-ссылками); после — работа с фактическим содержимым буфера.

**Обратная связь (notice):** «Скопировано: «title»» / «Скопировано мыслей: N (со связями: M)» / «Вставлено: N» / «Не выбрана мысль для копирования…» / «Не выбрана мысль для вставки…» / «Не удалось прочитать системный буфер: err».

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор)
- зависит от: POST /thoughts/copy-batch — копирование подграфа мыслей между сетями

## Лимиты и read-only режим MCP-операций

Настройки, ограничивающие агента в MCP-контуре. Живут в `_system.db` (`settings`); на MVP — фиксированные дефолты.

| Ключ | Смысл |
|---|---|
| `mcp.max_nodes_per_subgraph` | Жёсткий потолок узлов в `etn.thoughts.subgraph` (дефолт 500) — защита от выкачивания всей сети |
| `mcp.max_writes_per_minute` | Серверный дефолт бюджета записей на пользователя — защита от runaway-агента |
| `api_keys.max_writes_per_minute` | Per-key переопределение (task O8): `NULL` — серверный дефолт; задаётся при создании ключа и меняется через PATCH ключа. MCP-слой резолвит эффективный лимит на ключ при открытии сессии |

Правила:
- `etn.thoughts.write` считается **одной** записью бюджета, сколько бы сущностей ни записал;
- ключ с `read_only: true` пропускает только ресурсы и read-инструменты — проверка выполняется перед каждым изменяющим tool-вызовом («посмотреть — не трогать»);
- каждый изменяющий tool-вызов пишется в `audit_log` (`category = 'data'`, `action` — тип операции, `details` — параметры вызова).

Чтения в `audit_log` не попадают — вместо этого счётчики `thought_read_metrics`.

- относится к подсистемам: MCP-сервер, Аутентификация и права доступа
- зависит от: Аутентификация и права доступа
- применяется к: Составной write-инструмент — одна транзакция и одна запись бюджета

## Масштаб холста

Множитель `canvas_zoom` (L4, 50–200%, шаг 5%, дефолт 100%), меняется клавишами `Ctrl+=`/`Ctrl+-`/`Ctrl+0`.

Применяется ко всем простым облачкам разом: эффективная ширина = `cloud_width × zoom`, шрифт, высота строки, высота эллипсов и вертикальные отступы пропорционально масштабируются (линии рамки остаются 1 px); действует и на фокус-облачко (шрифт, иконка, минимальная ширина; переменная ширина «по содержимому» сохраняется) и на оформление линий (кегль подписей, радиус бейджа, толщина). `cloud_width`/`cloud_gap` не перезаписываются — зум это множитель поверх, а не четвёртая настройка размера. `cols`/`rows` и виртуализация считаются по эффективным размерам.

Масштаб показывается в статус-баре и сохраняется.

## Облачко мысли на карте

Карточка мысли на холсте. Структура одинакова для всех облачков; различаются правила размера.

**Состав:** иконка-полоса слева на всю высоту (эмодзи или картинка, глиф крупный); правая колонка — заголовок в 1–3 строки, под ним строка индикаторов (мельче, по левому краю заголовка): `📝` постоянный комментарий (кликабельный — открывает редактор на нём), `📅 N` хронология (кликабельно — разворачивает список), `📎 N` вложения, `🗑` помечена на удаление. Верхняя и нижняя стороны рамки несут компактные эллипсы (высота 4 px × zoom, ширина 25%, по центру) — индикаторы входящих/исходящих связей и точки drag.

**Значок корзины** (помеченная на удаление): облачко приглушается как неактуальное (прозрачность ×0.5, курсив); кружок в левом верхнем углу, на 70% больше индикатора позиции, на чёрном фоне — ярко-красная корзина `#e53935`. Кликабелен — открывает диалог одиночного удаления; появляется/снимается сразу после операции, без смены фокуса.

**Бейдж слоя** (сессия в слое, не в основе): пунктирная фиолетовая рамка + кружок-бейдж в правом верхнем углу (`#8c9eff`; корзина слева, слой справа). Говорит «несёт версию слоя»; список перекрытых id — из `overridden` структурного диффа (включая владельцев зависимых строк), обновляется при переключении слоя/таба, после `layer.merged`/`layer.deleted` и сразу после мутаций (своих и чужих).

**Индикатор позиции** — в зонах с ручной сортировкой кружок 16 px в правом нижнем углу (число = `position + 1`, обновляется при reorder и refresh); для мыслей без записи в `user_focus_order` скрыт.

**Размеры:** простые облачка — ширина = `cloud_width` (ограничена константами), высота динамическая (1–3 строки + индикаторы + эллипсы), заголовок до 3 строк с `…`, полный текст в tooltip. Фокус-облачко — ширины не имеет: от содержимого до предела центральной зоны, заголовок до 3 строк (до 400 символов в tooltip), ярче заливка/рамка, увеличенный шрифт (`FOCUS_FONT_SCALE`), свечение `--shadow-focus`.

**Цвета** наследуются от типа или собственных настроек; задан только фон → цвет текста выбирается по яркости фона автоматически, явный цвет текста побеждает. Иконочная полоса закрашена ТЕМ ЖЕ фоном, что и остальное облачко, при любом фоне — дефолтном (`--surface`), унаследованном от типа и заданном вручную: собственного фона полоса не имеет (`background: inherit` от облачка вместо прежнего `--surface-2`), разделительная линия не рисуется (прозрачна при сохранённой толщине 1 px — геометрия полосы не смещается). Это исключает видимую «ступеньку» между зоной иконки и остальной частью облачка; поведение действует во всех применениях фабрики (холст, фокус-облачко, нижняя зона отбора, строка «Структур», `graph`-профиль, `prop-ref-cloud`). Неактуальные приглушены. Стиль: скругление 14 px, мягкая двухслойная тень, hover усиливает рамку/тень без сдвига (не конфликтует с FLIP), иконка — круглый медальон, line-height 1.35.

*(Ревизия 2026-09-29, задача 1dc56942: фон иконочной полосы равен фону облачка при ЛЮБОМ фоне; прежнее поведение «без резолвнутого фона полоса остаётся `--surface-2`» отменено — оно и было дефектом.)*

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор)
- применяется к: Наследование визуального стиля мысли от её типа, Составные имена мыслей, ADR: обрезка текста в интерфейсе — раскладкой, а не подсчётом символов, Лимиты размеров облачка и масштаба холста, ADR: облачко мысли собирает одна фабрика DOM, различия — именованные профили

## Обновление истории посещений при открытии мысли в редакторе

При открытии мысли в редакторе история переписывается одной локальной транзакцией — переход `oldId → newId`, где `oldId` — мысль, открытая в редакторе до перехода (при смене фокуса холста — прежний фокус, при открытии из «Структур» или «Хроники» — прежняя открытая мысль), `newId` — открываемая.

Шаги в пределах скоупа `(profile_id, network_id, tab_id)`:

1. `newId` **удаляется** из истории — он теперь открыт в редакторе, а не «посещён ранее»;
2. `oldId` вставляется в начало истории со значением `seq = MAX(seq) + 1` в этом же скоупе (счётчик per-tab);
3. история подрезается до **50** самых свежих записей: всё, что не входит в топ-50 по `seq`, удаляется.

**Ветвления.** `oldId = null` (первое открытие в табе, редактор с нуля) — шаг 2 пропускается. `oldId = newId` (повторное открытие той же мысли) — операция целиком no-op.

**Открытие связи операцию не вызывает** — связь не является посещённой мыслью.

**Очистка при удалении.** По real-time событию об удалении мысли соответствующая запись истории удаляется обязательно — иначе в списке останется ссылка в никуда. Неактуальные мысли из истории **не** вычищаются: они скрываются на уровне рендера при выключенном показе неактуальных.

**Дополнительные материалы**
- относится к подсистемам: Десктоп-клиент (Electron), Пользовательский интерфейс (холст и редактор)
- применяется к: visit_history — история открытых мыслей на клиенте

## Общие принципы REST API: префикс /api/v1, транспорт и обязательные заголовки

Единые правила обращения к серверу ETN: их соблюдает любой клиент REST — десктоп-приложение, скрипт, внешний интегратор.

- **Базовый префикс** всех маршрутов — `/api/v1`. Маршруты сети вложены в него: `/api/v1/networks/{nid}/...`.
- **Транспорт** — HTTPS. Простой HTTP допустим только для локальной разработки.
- **Авторизация** — заголовок `Authorization: Bearer <API-key>`; без валидного ключа сервер отвечает `401 UNAUTHORIZED`.
- **Формат обмена** — `application/json; charset=utf-8`.
- **Идемпотентность изменяющих запросов** — заголовок `Client-Request-Id: <UUID>`: повтор того же запроса в окне дедупликации возвращает кэшированный ответ, а не создаёт вторую запись.
- **Оптимистичный контроль версий** — изменяющий запрос передаёт `If-Match: <version>`; расхождение с текущей версией записи отвергается `409 VERSION_CONFLICT`.
- **Заголовок сессии** `Client-Id` определяет клиентскую сессию: по тройке (пользователь, клиент, сеть) сервер хранит текущий слой изменений и подавляет real-time эхо собственных изменений.

Любая операция REST наследует эти правила: в карточках отдельных маршрутов повторяются только отличия.

**Дополнительные материалы**
- относится к подсистемам: REST API
- зависит от: Версионирование записей и разрешение конфликтов, Идемпотентность изменяющих запросов через client_request_id
- применяется к: Слой-осознанность REST API: все чтения и записи идут в слое сессии, Совместимость версий: клиент проверяет диапазон версий сервера

## Один сокет — одна сеть: несколько открытых сетей у клиента

Серверный контракт: один WebSocket = одна сеть (`?network_id=…`). Клиент с несколькими открытыми сетями (табы в одном окне) держит по одному сокету на каждую — это нужно для маркера «*» на любом табе, включая неактивные: клиент должен знать о событиях во всех открытых сетях.

- Пул `RealtimeClient` на клиенте: счётчик ссылок на сеть; при первом «открытии» сети сокет поднимается, при последнем «закрытии» — опускается.
- Серверу безразлично число сокетов одного `Client-Id` (реестр byClient поддерживает множественные подключения); серверный лимит на WS per client_id не вводится — сценарий «10 табов» штатный. Лимит одновременно открытых сетей — клиентский.
- `last_seq` в `client_meta` уже хранится per network_id — серверных изменений не требуется.
- При потере доступа (`network.deleted`, `member.removed` для своего `user_id`) клиент закрывает соответствующий сокет и помечает таб как «inaccessible». Терминально закрытые (4401/4404) и закрытые пользователем соединения не переустанавливаются.

**Дополнительные материалы**
- относится к подсистемам: Real-time канал (WebSocket), Десктоп-клиент (Electron)
- применяется к: WS /api/v1/realtime — подключение к каналу событий сети

## Применение real-time событий клиентом и пропуск эха

Правила applier — как клиент применяет входящие события к локальному кэшу и UI:

- `created` — добавить в кэш, обновить холст/редактор при необходимости;
- `updated` — при `meta.version < local.version` игнор (устаревшее); иначе применить; сущность в фокусе/на холсте — обновить визуально; сущность открыта в редакторе с несохранёнными локальными правками — индикатор «изменено другим пользователем» + актуальная версия при следующем сохранении;
- `deleted` — убрать из кэша; если была в фокусе — возврат к HOME или последней доступной мысли;
- `reordered` — обновить сортировку зоны холста.

**Пропуск эха.** REST-ответ на изменяющий запрос уже несёт применённое состояние (новую версию), поэтому WebSocket-эхо того же события не применяется дважды. Клиент распознаёт эхо по `meta.request_id` = `Client-Request-Id` своего запроса либо по `actor.client_id` = собственному `Client-Id`. Совпадение — игнор или пометка «подтверждено».

### Инкрементальное применение к видимым спискам (2026-09-28, задача afcfb144, коммит 3b1967de)

Видимые списки «Структуры мыслей» и «Дневник» применяют чужие события к локальному снимку точечно, без полного перезапроса страницы. Очередь событий за окно дебаунса (400 мс «Структуры», 250 мс «Дневник») применяется ОДНИМ батчем → один reconcile/renderFeed на окно. Событие, которое нельзя применить уверенно, помечает окно как fallback: батч отбрасывается, выполняется полный путь (перезапрос страницы и раскрытых уровней). Таблица «событие → инкрементальное действие или fallback»:

| Событие | «Структуры мыслей» | «Дневник» |
|---|---|---|
| `thought.updated` | видимая мысль, правка без влияния на отбор/порядок → обновление `refs` + `update()` одной строки; иначе/невидима → fallback/игнор | fallback (чипсы показывают заголовки мыслей) |
| `thought.deleted` | убрать мысль из снимка (строка уходит removed-путём сверки) | fallback, если мысль — чипс загруженной записи |
| `thought.created` | fallback (вхождение в отбор не проверяется) | — |
| `link.updated` | нарисованное ребро, правка оформления → `edges` + перерисовка линий; смена концов/активности → fallback | fallback (подписи чипсов связей) |
| `link.deleted` | нарисованное ребро → убрать + перерисовать линии | fallback |
| `link.created` | fallback | — |
| `property-value.*`, каталог типов, `layer.merged`, `thought.reordered` | fallback | fallback |
| `comment.created` | — (постоянные комментарии ленту не наполняют) | хроно-запись хотя бы с одной привязкой, отбор только период/порядок → доар целей + вставка строки; иначе fallback/игнор |
| `comment.updated` | — | строка в ленте → слияние + доар `body_html`, переразрешение привязок; вне периода — удаление строки |
| `comment.deleted` | — | строка в ленте → удаление строки |
| `attachment.*`, настройки | fallback/без изменений | fallback/без изменений |

Границы fallback «Структур»: сортировка `alpha` + смена заголовка; текстовый отбор + синонимы; отбор по типам + тип мысли; скрытые неактуальные/корзина + `active`/`marked_for_deletion`. Событие по невидимой сущности игнорируется — состав отбора по нему не перестраивается. Локальные производители зовут полный путь сами (своё realtime-эхо до рендерера не доходит).

#### Уточнение fallback (2026-09-28, задача afcfb144, круг 1 проверки, фикс 0da22ff5)

Ряд границ полного пути уточнён после независимой проверки:

- `thought.updated` в «Структурах» уходит в полный путь также при сортировке `updated` (ключ `updated_at` — порядок сдвигает любая правка) и при смене `title`/`synonyms` ПОД АКТИВНЫМ ТЕКСТОВЫМ ОТБОРОМ (ключевые слова по умолчанию ищут по наименованию/синонимам — переименование может вывести мысль из отбора).
- `comment.updated` в «Дневнике» по записи, которой нет в загруженной ленте: полный комментарий читается точечным додаром (`etn.comments.get`) и строка вставляется, если запись попадает в применённый период (отбор без дополнительных критериев); при доп. критериях — полный путь. Правка даты переставляет строку по серверному порядку; локальная вставка помечает страницу к сверке (`pendingReconcile`).
- Снимок «Структур» поддерживается и когда вид НЕ показан (гейт по `activeView` снят) — `thought.deleted` вне экрана чистит `refs`/активную мысль, чтобы при возврате не оставалось устаревшей строки.

#### Додар направлений раскрываемости (2026-09-28, ошибка 989691da, фикс fd886daf)

Для `link.updated`/`link.deleted` в «Структурах» инкрементальный путь помимо точечного применения к `edges` и перерисовки линий помечает концы ребра к точечному додару направлений: `refreshDirections(ids)` перечитывает флаги раскрываемости через `fetchHierarchy` с тем же `link_filter` отбора и видимостью корзины (соседей ответа в снимок не сливает — сервер считает directions по всем активным связям мысли, включая невидимые, поэтому локальный пересчёт из `edges` неверен); сбой додара уводит в полный путь. Чистое оформление ребра (цвет/стиль/ширина) дадара не требует; смена концов, `active`, а также `type_id` под активным фильтром — полный путь.

#### Ревизия 2026-09-28 (ошибки 8da8e6b4 и 0af1d810, коммит 3afe73f2)

Границы полного пути расширены: пометка ребра корзиной (смена `marked_for_deletion`) при скрытой «корзине» и смена `type_id` при активном `link_filter` — всегда полный путь. Как следствие, точечный додар направлений выполняется только для `link.deleted`; для `link.updated` оба прежних триггера додара стали полным путём и мёртвый код удалён.

#### Ревизия 2026-09-28 (ошибка 8e702d8c, коммит ee2968af)

Полный путь realtime в «Структурах» выполняется ТОЛЬКО когда вид показан. При скрытом виде fallback-событие (а также сбой точечного додара `refreshDirections`) не запускает `reloadAll()`, а помечает снимок «грязным» (`fullRefreshPending`); перезагрузка страницы и раскрытых уровней идёт при следующем показе вида. Инкрементальные события по-прежнему поддерживают снимок вне экрана (гейт по `activeView` не возвращается). Отложенная пометка сбрасывается при полной инициализации снимка (смена сети/вкладки) — там снимок и так грузится целиком.

## Снапшот буфера обмена мыслей

### Что это

Runtime-состояние клиента (уровень L1, per-client): снимок мыслей и связей, скопированных пользователем, — основа операции «копировать и вставить мысль/подграф». Вход операции `copy-batch` (см. «Копирование и вставка мыслей»).

В БД не сохраняется, между клиентами одного пользователя не синхронизируется, real-time не порождает, при перезапуске приложения (или kill процесса) сбрасывается. Явного сброса нет — следующая копия перезаписывает буфер целиком.

### Поля

Реализация — `client/src/renderer/canvas/clipboard.ts`, типы — `shared/src/types/thought-copy.ts`:

| Поле | Тип | Смысл |
|---|---|---|
| `sourceNetworkId` | string | сеть-источник; фиксируется в момент копирования (для кросс-сети) |
| `sourceNetworkName?` | string | имя сети-источника для UI |
| `thoughts` | `ThoughtCopyItem[]` | скопированные мысли |
| `links` | `ThoughtCopyLink[]` | связи с обоими концами внутри выделения |

`ThoughtCopyItem`: `thought` (заголовок, синонимы, тег типа `{id, name}`, стиль, `icon`/`icon_kind`, `active`), опциональные `source_id`, `permanent_comment`, `properties` (по ключам свойств-скаляров), `attachments`. Вложения переносят только видимые поля (`kind`, `url`/`file_path`, `file_size`, `mime_type`, `title`, `description`) — файл-байты не копируются, только путь.

**Снапшот несёт только путь, а физическое копирование файла выполняет сервер** (2026-10-07, ошибка `b83a7d89`, версия 0.12.1): при межсетевом копировании файл вложения копируется в сеть-получатель, при копировании внутри сети остаётся общим — см. «POST /thoughts/copy-batch» и «Копирование и вставка мыслей».

Снапшот живёт в памяти процесса рендерера и НЕ подменяет системный буфер обмена: в системный клипборд кладутся только wiki-ссылки.

### Расхождение со спекой

Спека §6.1 описывает структуру как `ThoughtClipboardSnapshot` со snake_case, `thoughts: Map<string, ThoughtCopyItem>` и полем `created_at`. Фактический код: camelCase `{ sourceNetworkId, sourceNetworkName?, thoughts: ThoughtCopyItem[], links: ThoughtCopyLink[] }`, `created_at` отсутствует, мысли — массив; `font_*` в коде — `boolean | null` (в спеке `boolean`); вложения получили `file_size`/`mime_type`; `icon_kind` обязателен. Истина — в коде; спека требует правки.

## Состояние уровня «пользователь × мыслесеть» и его синхронизация

Часть данных в БД сети принадлежит не сети целиком, а **конкретному пользователю в этой сети**: настройки, метки просмотра, сортировки и ручной порядок зон, сохранённые отборы, закреплённые мысли.

**Обязательное свойство:** эти данные одинаковы на всех клиентах одного пользователя и синхронизируются между ними событиями real-time, адресованными пользователю, а не всей сети. Открыл клиент на другом компьютере — видит те же закрепления и те же отборы.

**Граница с локальным состоянием клиента.** То, что привязано к конкретной установке (геометрия окна, текущий фокус, черновики), хранится локально и сюда не попадает.

**Ни одна из этих таблиц не ветвится** по слоям изменений: личное состояние пользователя не зависит от того, в каком слое он работает. При удалении мысли соответствующие записи чистит приложение — SQL-FK на мысль сняты.

**Переносу между сетями не подлежит.** Экспорт не включает эти данные: в чужой сети они бессмысленны.

**Дополнительные материалы**
- относится к подсистемам: Хранилище (SQLite), Real-time канал (WebSocket), Пользовательский интерфейс (холст и редактор)
- применяется к: Уровни настроек и состояния клиента (L1–L5), user_preferences мыслесети — настройки пользователя внутри сети, События пользовательского состояния (audience=user), PUT /focus-preferences — выбор сортировки зоны фокуса

## Уровни настроек и состояния клиента (L1–L5)

Все настройки и состояние ETN распределены по уровням; уровень определяет, **где** хранится значение и **как** оно синхронизируется.

| Уровень | Где хранится | Синхронизация | Примеры |
|---|---|---|---|
| **L1. Системный** | `_system.db`, таблица `settings` | нет; меняет только администратор | лимиты MCP, TTL и окно `event_log`, защита от перебора |
| **L2. Сеть** | `_system.db.networks` (на MVP) | все участники сети | `display_name`, `description`, `owner_id` |
| **L3. Пользователь × сеть** | `data.db`, таблицы `user_*` | real-time события с `audience = user` | `show_inactive`, сортировка зоны фокуса, ручной порядок, `last_viewed_at`, сохранённые отборы, закреплённые мысли |
| **L3s. Пользователь × сервер** | `_system.db`, таблица `user_settings` | на сервере; общее для всех сетей и устройств пользователя этого сервера | серверные настройки пользователя вне сети: сочетания клавиш клиента (`comment_hotkeys`) |
| **L4. Клиент × пользователь × сеть** | локальный SQLite, `ui_state` | нет — только на этой установке | текущий фокус, активный вид, structures/chronicle-state, история посещений, `cloud_width`/`cloud_gap`, `search_state`, `editor_position`, layout окна, `canvas_zoom` |
| **L5. Клиент (установка)** | локальный SQLite, `client_meta` | нет | `client_id`, `last_seq`, тема, `zoom`, `active_profile_id` |

Отдельно выделяется **L4+tab**: состояние, привязанное к табу, пишется в `ui_state` суффиксом ключа `:<tab_id>` и в `visit_history.tab_id`; табы одной сети ведут независимые контексты.

**Как выбрать уровень.** Три вопроса: (1) должно ли значение быть общим для всех сетей одного сервера? Да → L3s. (2) должно ли значение быть одинаковым на всех клиентах пользователя в этой сети? Да → L3, нет → L4. (3) влияет ли значение на выборку данных с сервера? Да → обязательно L3, сервер обязан знать значение при запросе. Подробнее — требование «Принцип выбора уровня настройки»; синхронизация L3 — «Состояние уровня «пользователь × мыслесеть» и его синхронизация».

**Уровень L3s введён проработкой ТП1 «Команды редактирования комментария» (0.12.1):** пользовательские сочетания клавиш хранятся на сервере и действуют во всех сетях сервера для пользователя. Хранилище — `user_settings`, доступ — `/api/v1/users/me/settings`.

**Подтверждение (2026-10-07).** Уровень L3s «Пользователь × сервер» подтверждён пользователем.

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор), Хранилище (SQLite)
- применяется к: Состояние уровня «пользователь × мыслесеть» и его синхронизация, Принцип выбора уровня настройки

## Принцип выбора уровня настройки

При добавлении новой настройки или состояния уровень определяется двумя вопросами, в этом порядке:

1. **Должно ли значение быть одинаковым на всех клиентах этого пользователя в этой сети?** Да → L3. Нет → L4.
2. **Влияет ли значение на выборку данных с сервера?** Да → обязательно L3: сервер обязан знать значение при выполнении запроса. Нет → допустим L3 или L4 по ответу на первый вопрос.

Следствия из спеки: `show_inactive` влияет на выборку → L3. `current_focus_thought_id` на каждом клиенте свой → L4. `search_state` своё → L4. `visit_history` своё → L4.

Нарушение: настройка, положенная не на свой уровень, даёт расхождение между клиентами одного пользователя (L3-значение в L4) либо лишний трафик синхронизации (L4-значение в L3).

**Дополнительные материалы**
- относится к подсистемам: Хранилище (SQLite), Пользовательский интерфейс (холст и редактор)
- применяется к: Уровни настроек и состояния клиента (L1–L5)

## Лимиты размеров облачка и масштаба холста

Пользовательские L4-настройки `cloud_width`, `cloud_gap` и `canvas_zoom` ограничены системными константами. Это не настройки, а часть кода приложения: в БД они не хранятся. Значения — в `@etn/shared` (`shared/src/constants.ts`).

| Константа | Значение | Назначение |
|---|---|---|
| `CLOUD_WIDTH_MIN` / `CLOUD_WIDTH_MAX` / `CLOUD_WIDTH_DEFAULT` | 120 / 400 / 200 px | ширина облачка |
| `CLOUD_GAP_MIN` / `CLOUD_GAP_MAX` / `CLOUD_GAP_DEFAULT` | 4 / 40 / 12 px | отступ между ячейками |
| `FOCUS_FONT_SCALE` | 1.3 | множитель шрифта заголовка фокус-облачка |
| `FOCUS_TITLE_MAX_LINES` | 4 | максимум строк заголовка |
| `CANVAS_ZOOM_MIN` / `CANVAS_ZOOM_MAX` / `CANVAS_ZOOM_STEP` / `CANVAS_ZOOM_DEFAULT` | 0.5 / 2.0 / 0.05 / 1.0 | масштаб холста |

Правила:
- при сохранении значение клиппится в `[MIN, MAX]`; `canvas_zoom` дополнительно округляется к сетке, кратной `CANVAS_ZOOM_STEP`;
- `canvas_zoom` — множитель поверх `cloud_width`/`cloud_gap`, он их не перезаписывает: эффективная ширина облачка = `cloud_width × zoom`, эффективный отступ = `cloud_gap × zoom`, шрифт, высота строки, эллипсы и вертикальные отступы масштабируются тем же множителем; линии рамки облачка остаются 1 px. Сетка зон и виртуализация считаются по эффективным размерам;
- высота облачка — не настройка и не константа: вычисляется из CSS (1–4 строки заголовка + индикаторы + эллипсы), динамическая, в пределах `FOCUS_TITLE_MAX_LINES` строк заголовка.

> Актуализировано 2026-09-30: `FOCUS_TITLE_MAX_LINES` в коде равно 4 (в спеке ранее фигурировало 3).

- применяется к: Масштаб холста, ui_state — персональное UI-состояние клиента по сети, Облачко мысли на карте

## Порядок мыслей в зоне фокуса: правила применения сортировки

При загрузке зоны холста для фокуса F, направления D и пользователя U порядок соседей строится так:

1. `SELECT sort, sort_order FROM user_focus_preferences WHERE user_id=U AND focus_thought_id=F AND dir=D`. Записи нет → дефолт `created` / `asc`.
2. Взять соседей по соответствующему направлению связей.
3. Применить сортировку: `alpha` → по заголовку без учёта регистра; `created` → по дате создания; `viewed` → по `thought_views.last_viewed_at`; `manual` → по `user_focus_order.position` (мысли без позиции — в конце, по алфавиту).
4. Применить `sort_order`. При `sort = manual` порядок всегда `asc`: `desc` отвергается `VALIDATION_ERROR`, а отсутствующий параметр нормализуется в `asc`.

`position` при ручной сортировке — линейный индекс в построчном (row-major) списке зоны, без пропусков. Соседи возвращаются клиенту уже в серверном порядке; клиент **не** пересортировывает их и кладёт в DOM в том же порядке, а CSS Grid с `grid-auto-flow: row` раскладывает их row-major — слева направо в строке, затем следующая строка.

**Дополнительные материалы**
- относится к подсистемам: Пользовательский интерфейс (холст и редактор), REST API, Хранилище (SQLite)
- применяется к: user_focus_preferences — сортировка зон холста, thought_views — метки просмотра мыслей, user_focus_order — ручной порядок мыслей в зоне фокуса, POST /thoughts/{id}/focus — окрестность мысли для холста, PUT /focus-preferences — выбор сортировки зоны фокуса
