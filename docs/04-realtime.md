# 04. Real-time (WebSocket)

## 1. Назначение

Канал доставки изменений в мыслесети всем подключённым участникам без
перезагрузки. Доставка — от сервера к клиенту; запросы на изменение идут через
REST (WebSocket не используется для команд), что упрощает контроль доступа и
идемпотентность.

## 2. Подключение

```
ws(s)://<host>/api/v1/realtime?network_id=<nid>
Header: Authorization: Bearer <API-key>
        Client-Id: <UUID установки клиента>
```

- `network_id` — сеть, к которой подключается клиент.
- `Client-Id` — UUIDv4, генерируется при первом запуске клиента и хранится в его
  локальном SQLite (`client_meta.client_id`). **Один пользователь на разных
  компьютерах = разные Client-Id.** Используется для подавления эха и маршрутизации
  `audience=user` событий. Не авторизует.

Подробное описание идентификации клиентов, `last_seq` per client и сценарии
«один пользователь на нескольких компьютерах» — см.
[11-settings-and-state.md](11-settings-and-state.md), разделы 1–2.

Подключение без валидного ключа или без прав на сеть → закрытие с кодом `4401`.
Сеть без такого id → `4404`.

### 2.0. Несколько сетей на одном клиенте (табы, фаза Q)

Серверный контракт WebSocket — **один сокет = одна сеть** (`?network_id=…`,
см. выше). Клиент с фазой Q (табы в одном окне, 08-ui-spec.md §1) может
одновременно держать **несколько** WebSocket-соединений — по одному на
каждую открытую сеть. Это нужно для маркера «\*» на любом табе, включая
неактивные: клиент должен знать о событиях во всех открытых сетях, а не
только в активной.

- На стороне клиента — пул `RealtimeClient` (см.
  [07-client-electron.md](07-client-electron.md), §2/§4.2): счётчик
  ссылок на сеть, при первом «открытии» сети сокет поднимается, при
  последнем «закрытии» — опускается. Серверу всё равно, сколько сокетов у
  одного `Client-Id` — `byClient` уже поддерживает множественные
  подключения ([11-settings-and-state.md](11-settings-and-state.md), §1.2).
- `last_seq` в `client_meta` уже хранится per network_id
  ([11-settings-and-state.md](11-settings-and-state.md), §1.3) — изменений
  на сервере не требуется.
- Лимит количества одновременно открытых сетей — клиентский; серверный
  лимит на число WS per `client_id` не вводится (сценарий «10 табов»
  считается штатным).
- При потере доступа к сети (`network.deleted`, `member.removed` для
  своего `user_id`) клиент закрывает соответствующий сокет и помечает
  таб как «inaccessible» (08-ui-spec.md §1).

### 2.1. Ping/pong
- Сервер шлёт пинг каждые 30 с. Клиент без pong в течение 60 с закрывается.
- Клиент может слать текстовый фрейм `{ "type": "ping" }`, ответ — `{ "type": "pong" }`.
- **Watchdog клиента на простой приёма (дефект 7f4cef31).** Клиент
  отслеживает время последнего входящего фрейма любого вида (событие,
  `ping`, `pong`). Если за 100 с (3 серверных интервала + запас) не пришло
  ничего, соединение считается half-open (типично после спящего режима ПК
  или смены сети: сервер уже закрыл свою сторону, но FIN/RST до клиента не
  дошёл). Клиент принудительно обрывает сокет и уходит в штатный реконнект
  (§2.2) с последующим `resume` — пассивного close/error в этой ситуации
  не бывает.
- **Системные события реконнекта.** На выход ПК из спящего режима
  (`powerMonitor` `resume` в main-процессе клиента) и на событие `online`
  окна renderer (рендерер пересылает его в main по IPC) клиент немедленно
  переустанавливает все открытые realtime-соединения, не дожидаясь
  watchdog-таймаута и без backoff; счётчик попыток реконнекта при этом
  сбрасывается. Терминально закрытые (4401/4404) и закрытые пользователем
  соединения не переустанавливаются.

### 2.2. Реконнект
- Клиент при обрыве экспоненциально повторяет с jitter 1→30 с.
- После переподключения клиент запрашивает «пропущенные» события (см. п. 6).

## 3. Структура события

```json
{
  "type": "thought.created",
  "seq": 42,
  "ts": "2026-08-12T10:00:00.000Z",
  "actor": { "user_id": "...", "client_id": "..." },
  "network_id": "...",
  "layer_id": "<id слоя, в котором материализовалась запись>",
  "data": { ... },
  "meta": { "version": 1, "request_id": "..." }
}
```

- `seq` — монотонно возрастающий номер события в пределах сети (хранится в
  `_system.db` счётчиком на сеть). Для пропуска/повторной доставки.
- `actor.user_id` — кто изменил; `actor.client_id` — для подавления эха (клиент
  игнорирует события, инициированные им самим).
- `layer_id` — слой изменений, в котором материализовалась запись (13-layers.md
  §12, задача S9). `BASE_LAYER_ID` для записей в основе и для неветвимых
  событий — поле заполнено всегда, чтобы конверт был единообразным.
  Используется шлюзом и `etn.changes.list` для вычисления видимости на
  подписчика (§11.2).
- `audience` — `"network"` (по умолчанию; получают все участники сети) или
  `"user"` (получают только подключения того же `user_id`). `audience=user`
  используется для приватных пользовательских настроек (см. п. 4.8 и
  [11-settings-and-state.md](11-settings-and-state.md), п. 4).
- `meta.request_id` соответствует `Client-Request-Id` запроса — клиент может
  сопоставить свой запрос с пришедшим эхом.

## 5. Маршрутизация на сервере

1. Изменяющий запрос приходит в REST.
2. Ядро выполняет запись в `data.db` в транзакции.
3. **В той же транзакции** инкрементируется `_system.db.network_seq` для сети,
   формируется событие с присвоенным `seq`.
4. После коммита транзакции ядро эмитит событие в `EventEmitter` по `network_id`.
5. WebSocket-шлюз фильтрует подписчиков сети:
   - для `audience = "user"` событие получают только подключения того же
     `user_id`;
   - для `audience = "network"` (по умолчанию) — все участники сети, **за
     вычетом фильтра видимости по слою подписчика** (§11.2): подписчик в слое
     не получает события по перекрытым им строкам и события слоёв вне его
     цепочки предков;
   - источник по `actor.client_id` эхо не получает (если не запрошено явно).
   См. [11-settings-and-state.md](11-settings-and-state.md), п. 4.3.

### 5.1. События внешних процессов (event-log relay)

`EventEmitter` — внутрипроцессный: события, записанные в `event_log` **другим
процессом** (stdio-режим MCP-сервера `etn mcp` работает отдельным процессом
поверх той же `_system.db`), до живой рассылки сами не доходят. Чтобы такие
записи всё же оповещали подключённых клиентов, сервер запускает **event-log
relay** (`server/src/realtime/event-log-relay.ts`):

- реле периодически (по умолчанию каждые 300 мс) сканирует `event_log` каждой
  сети и публикует в `EventEmitter` события, которые этот процесс ещё не
  раздавал;
- события, записанные самим процессом (REST и HTTP-MCP), уже прошли через
  `EventEmitter` — реле их не дублирует (отслеживание через подписку на
  брокер, позиция сканирования — по последнему прочитанному `seq`, поэтому
  «дыра» из внешней записи между двумя своими догоняется);
- при старте сервера позиция сканирования инициализируется текущей вершиной
  лога — история до старта живой рассылке не подлежит (клиенты получают её
  через `resume`, см. п. 6);
- задержка доставки внешних записей ограничена интервалом сканирования
  (300 мс), данные при этом не теряются: запись уже в `event_log`, и при
  реконнекте клиент догонит её через `resume`.

## 6. Восстановление после обрыва

После переподключения клиент шлёт:
```json
{ "type": "resume", "last_seq": 41 }
```
Сервер отдаёт все события сети с `seq > 41`, накопленные в окне
(по умолчанию — последние 10 000 событий или 24 часа), пропуская события,
невидимые в текущем слое сессии (§11.2). Если `last_seq` старше
окна — сервер отвечает:
```json
{ "type": "resume.stale", "last_seq": 100 }
```
и клиент выполняет полный переревыгруз состояния (повторно вызывает
`POST /thoughts/{focus}/focus`). Тот же ответ `resume.stale` клиент получает,
когда `last_seq` предшествует последнему переключению слоя сессии
(`switched_at_seq`, §11.3) — дельта через границу переключения невозможна,
нужен полный ресинк. Получив `resume.stale` (по любой причине) или живой кадр
`layer.switched`/`layer.deleted` (§11.1), клиент обязан выполнить полный ресинк
и продолжить с позиции, названной сервером.

Буфер событий хранится в `_system.db` в таблице `event_log` (network_id, seq,
ts, type, data). Старые записи удаляются джобой за пределами окна.

## 7. Применение событий клиентом

- `created` — добавить в локальный кэш, обновить холст/редактор при необходимости.
- `updated` — если `meta.version < local.version` → игнор (устаревшее). Иначе
  применить; если сущность в фокусе/на холсте — обновить визуально; если сущность
  открыта в редакторе у локального пользователя и есть несохранённые локальные
  правки → индикатор «изменено другим пользователем» + актуальная версия при
  следующем сохранении.
- `deleted` — убрать из кэша; если была в фокусе → возврат к HOME или последней
  доступной мысли.
- `reordered` — обновить сортировку зоны холста.

## 8. Конфликты при совместном редактировании

Политика MVP — **last-write-wins на уровне поля** + явный сигнал конфликта:

1. Клиент А редактирует заголовок мысли (version=5).
2. Клиент Б одновременно редактирует иконку той же мысли (version=5).
3. Клиент А шлёт `PATCH If-Match: 5` с новым заголовком → сервер применяет,
   version=6, рассылает `thought.updated`.
4. Клиент Б шлёт `PATCH If-Match: 5` с новой иконкой → сервер видит, что текущая
   версия 6 ≠ 5. **Однако поля разные**, поэтому сервер применяет только изменение
   иконки, не трогая заголовок, version=7. Возвращает 200 с актуальной версией.
5. Если бы Б менял тот же заголовок — сервер вернул бы `409 VERSION_CONFLICT` с
   телом `{ server_value: "...", server_version: 6 }`. Клиент показывает
   уведомление и предлагает «перезаписать» или «оставить чужое».

`If-Match` проверяется на **текущей версии сущности**. Совпадение набора
изменяемых полей (заголовок у заголовка) → конфликт; разный набор → мирное
слияние.

## 9. Пропуск эха

Клиент после отправки изменяющего запроса получает REST-ответ с уже применённым
состоянием (новой версией). Чтобы WebSocket-эхо того же события не применялось
дважды, клиент:

- Сопоставляет `meta.request_id` в событии с `Client-Request-Id` отправленного
  запроса. Совпадение → игнор (или пометить как «подтверждено»).
- Либо использует `actor.client_id` = собственный `Client-Id`.

## 10. Нагрузка и масштаб

На MVP (один серверный процесс) — достаточно. Ожидаемая нагрузка: 1–20
одновременных участников на сеть, 1–10 активных сетей. In-memory pub/sub
справляется. При росте — переход на Redis Pub/Sub (требование появится раньше,
чем SQLite перестанет справляться).

## 11. Слои изменений (S9)

Real-time учитывает слой подписчика (13-layers.md §12): рассылка — не
широковещание без разбора, а вычисление видимости на каждого подписчика.
Реализация — `server/src/realtime/layer-visibility.ts`.

### 11.1. Слой подключения

Слой WebSocket-подключения — это слой сессии `(user_id, client_id)` из
`session_layers` (13-layers.md §7.1), разрешаемый при подключении и повторно —
при позднем кадре `hello` (клиент мог не передать `Client-Id` в момент
upgrade). Пока сокет жив, сервер держит фильтр подключения в актуальном
состоянии:

- **Переключение слоя сессии** (REST `POST …/layers/:id/select`,
  13-layers.md §7.1) — живым подключениям той же сессии сервер немедленно шлёт
  управляющий кадр `layer.switched { layer: { id, title } }` и переключает их
  фильтр на месте.
- **Удаление слоя** (13-layers.md §2.4) — подключения, сидящие на удалённом
  слое или его потомке, пересаживаются на родителя удалённого и получают
  `layer.deleted { layer: { id, title } }`.

Оба кадра адресованы **точечно** — ровно тем подключениям, чья сессия
изменилась, а не рассылаются по `audience` как события каталога: ни `network`
(все участники), ни `user` (все клиенты пользователя) не соответствуют «этой
одной клиентской сессии». Кадры не несут `seq`/`network_id`, поэтому старый
клиент без поддержки слоёв их безопасно игнорирует (не проходят валидацию
конверта события). После любого из этих кадров кэш клиента невалиден целиком —
клиент обязан сделать полный ресинк (§11.3).

### 11.2. Правило видимости

Событие `audience = "network"` с `layer_id = EL` доставляется подписчику,
сессия которого сидит в слое `L`, если:

1. `EL` лежит на цепочке предков `L` (`L → parent(L) → … → base`; для событий
   основы выполняется всегда), **и**
2. ближайшая строка для логического `id` события в цепочке `L` живёт именно в
   `EL` — то есть `L` не материализовал для этого `id` более близкую теневую
   строку или надгробие (13-layers.md §4.1). Проверка — точечный lookup по
   `(table, id)` через `layer_chain` без фильтра `deleted = 1` (событие
   удаления-надгробия обязано дойти, если ближе ничего не перекрывает).

Исключение: событие `*.deleted`, для которого на цепочке `L` **нет строки
вообще**, доставляется — строка была физически удалена (автоочистка корзины,
13-layers.md §2.4/§6.3, S13) уже после записи события, и каждый подписчик,
держащий её в кэше, обязан её выкинуть. Возможная лишняя доставка незнакомого
`id` безвредна: applier игнорирует неизвестные сущности идемпотентно.

Неветвимые события (network/membership/presence, `audience = "user"` настройки
— 13-layers.md §3) видимость по слою не проверяют: у них нет строки-носителя,
маршрутизация остаётся прежней (§5).

### 11.3. Переключение слоя — полный ресинк

`last_seq` глобален по сети, а фильтр видимости — по слою подписчика. После
смены слоя кэш клиента невалиден целиком, и дельта через границу переключения
в принципе невозможна (она смешала бы два разных фильтра). Поэтому сервер
запоминает в `session_layers.switched_at_seq` (миграция 028) — `max_seq` сети
на момент переключения — и использует его так же, как границу окна удержания:

- `resume` с `last_seq < switched_at_seq` отвечает `resume.stale { last_seq:
  switched_at_seq }`, даже если позиция ещё внутри окна удержания;
- позиции `>= switched_at_seq` доверяются: подписчик, выполнивший ресинк после
  `layer.switched`/`layer.deleted`/`resume.stale`, продолжает с этой позиции и
  больше не получает stale по этой причине;
- `etn.changes.list` зеркалит правило: `truncated: true` при
  `since_seq < switched_at_seq` (05-mcp-server.md §5.1c).

Переключение на уже текущий слой — не переключение: `switched_at_seq` не
трогается, ресинк не форсируется.

### 11.4. Слияние — одно событие, не лавина

Успешное слияние слоя (S8, 13-layers.md §8) перезаписывает сразу много строк
цели — построчная рассылка дала бы лавину событий с проверкой видимости на
каждого подписчика. Решение, зафиксированное задачей S9: эмитится **ровно
одно** событие `layer.merged`:

- `audience = "network"`, `layer_id` — слой-цель слияния;
- `data` — отчёт слияния (13-layers.md §8.3: `applied`, `skipped`,
  `reorder_collapsed`, `reserve_layer_id`) плюс `layer: { id, title }` и
  `target_layer: { id, title }`;
- получив его, клиент и агент выполняют полный ресинк видимого состояния
  (тот же путь, что после `resume.stale`, §11.3); поштучной рассылки строк
  слияния нет.
