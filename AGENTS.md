# AGENTS.md — инструкции для агентов проекта ETN

> **TL;DR.** Это **ETN** — self-hosted граф мыслей (аналог TheBrain). Спецификации
> в [`docs/`](docs/) — **источник истины** (авторитетнее кода). MVP (фазы A–K из
> [`docs/workplan.md`](docs/workplan.md)) собран; проект в режиме **тестовой
> эксплуатации и баг-фиксов**: пользователь сообщает об ошибках/замечаниях, агент
> воспроизводит, диагностирует, чинит и проверяет.

## 0. Текущий режим работы

- **MVP сдан.** Все задачи `docs/workplan.md` (фазы A–K) — `done`. Workplan теперь
  скорее историческая справка и источник контекста, чем очередь работ.
- **Входной поток задач — от пользователя-тестировщика.** Пользователь гоняет
  сервер+клиент и сообщает дефекты/замечания. Новую функциональность «с нуля» не
  начинать без явной задачи с ID.
- **Сервер и клиент запускаются под Node 22 LTS** (см. `.nvmrc`, п. 4). Это
  осознанное решение ради prebuilt-бинарника `better-sqlite3`.

## 1. Главные правила

1. **Спецификации в `docs/` — источник истины.** При конфликте кода и спецификации
   остановись, не правь молча ни то, ни другое. Сначала разберись: если поведение
   расходится со спецификацией — это баг кода; если код следует спецификации, а
   пользователю удобно иначе — это запрос на изменение спецификации (отдельный
   `docs:`-коммит). Подними вопрос, если неоднозначно.
2. **Не начинай новую функциональность «мимо плана».** Текущая работа — баг-фиксы и
   мелкие правки из отчётов пользователя. Всё, что выходит за рамки фикса, получает
   новый ID в `workplan.md` (фаза L — `L1`, `L2`, …).
3. **Не ломай `done`-области.** Если фикс затрагивает чужую область — прочитай
   связанную спецификацию и убедись, что не нарушаешь контракт.
4. **Не коммить runtime- и build-артефакты:** `*.db`, `*.db-wal`, `*.db-shm`,
   `etn_data/`, `data/`, `var/`, `.env`, `node_modules/`, `dist/`, `out/`, `build/`,
   `release/` (см. `.gitignore`).

## 2. Структура репозитория

```
etn/
├── docs/        # спецификации (01..11) + README + workplan + руководства
├── server/      # @etn/server  — Fastify + better-sqlite3 + WebSocket + MCP
│   ├── src/     #   исходники
│   ├── migrations/{system,network}/  # идемпотентные SQL-миграции
│   └── dist/    #   сборка (tsc) — НЕ коммитить
├── client/      # @etn/client  — Electron + electron-vite (vanilla TS, без React)
│   ├── src/{main,preload,renderer}/
│   └── out/     #   сборка electron-vite (main/preload/renderer) — НЕ коммитить
├── shared/      # @etn/shared  — общие типы, DTO, константы, коды ошибок
├── .nvmrc       # Node 22 LTS
└── package.json # npm workspaces: shared, server, client
```

- **Клиент `type: "module"`,** поэтому preload собирается как `out/preload/index.mjs`
  (а не `.js`). В `main/index.ts` путь указан именно так; не «чинить» обратно на `.js`.
- **Входы рантайма:** сервер — `server/dist/index.js`; клиент (Electron) —
  `client/out/main/index.js` (поле `main` в `client/package.json`).

## 3. Жизненный цикл работы

### 3.1. Баг-фикс из отчёта пользователя (основной режим)

1. **Воспроизведи** дефект локально (запусти `dev:server` + `dev:client`, см. п. 5).
   Если воспроизвести не удалось — уточни у пользователя шаги/окружение, не
   гадай.
2. **Диагностируй корень**, а не симптом. Прочитай связанную спецификацию и код.
3. **Определи тип:** баг кода → правь код; неточность/пробел в спецификации →
   правь `docs/` отдельным коммитом; неоднозначность → подними вопрос.
4. **Чини**, не нарушая архитектурных ограничений (п. 7).
5. **Проверь:** `npm run typecheck` + затронутые тесты + ручная проверка пути.
6. **Коммить** `fix(<scope>): <summary>` (префикс ID не нужен для точечного фикса).
   Если фикс разрастся до нескольких областей/архитектуры — заведи ID в `workplan.md`
   (фаза L) и коммить `[<ID>] ...`.

### 3.2. Задача из workplan (если работа возобновляется по плану)

1. Выбери задачу `todo`, у которой все зависимости `done`.
2. Переведи в `in_progress`, заполни `Assignee`.
3. Прочитай спецификацию и существующий код.
4. Реализуй, напиши тесты, собери (п. 5).
5. Отметь DoD, переведи в `done`.
6. Коммить `[<TASK_ID>] <type>(<scope>): <summary>`.

Статусы: `todo` → `in_progress` → `done` (или `blocked` с причиной).

## 4. Соглашения по коду

- **Язык:** TypeScript везде (`strict`, `noUncheckedIndexedAccess`).
- **Node 22 LTS** (см. `.nvmrc`). Не Node 20/24: для 22 есть prebuilt
  `better-sqlite3` (и для сервера, и для нативного ребилда клиента); на 24 нужен
  Python/node-gyp, на 20 — нет гарантий prebuilt.
- **ESM** (`"type": "module"` во всех workspace).
- **Пакетный менеджер:** `npm` (workspaces). Установка — `npm install` в корне.
- **После установки клиента:** один раз `npm -w @etn/client run rebuild:native` —
  пересобирает `better-sqlite3` под ABI Electron (иначе падает на старте в dev).
- **Комментарии и имена — английские**, публичные API — с TSDoc. UI-тексты и
  пользовательская документация — русские.
- **SQL — параметризованный**, без интерполяции значений. Все миграции — в
  `server/migrations/{system,network}/*.sql`, идемпотентные в контрольной точке.
- **Никаких `any` без обоснования в комментарии.** Для внешних данных — `unknown`
  + валидация (zod или ручная).
- **Клиентский preload — ESM, поэтому `sandbox: false`** (см. комментарий в
  `client/src/main/index.ts`). Песочница Electron не грузит ESM-preload. Граница
  безопасности сохранена через `contextIsolation: true` + `nodeIntegration: false`
  + доверенный first-party preload. Не возвращай `sandbox: true`, не переведя
  preload в CommonJS.
- Следуй стилю окружающего кода; не переформатируй чужие файлы.

## 5. Команды (обязательны перед коммитом)

```bash
nvm use 22                       # активировать нужный Node (Windows: nvm-windows)
npm install                      # после checkout / смены ветки
npm -w @etn/client run rebuild:native   # один раз после install (натива под Electron)

npm run dev:server               # сервер в dev-режиме (ts-watch)
npm run dev:client               # Electron-клиент в dev-режиме (electron-vite)

npm run typecheck                # типы во всех workspace
npm -w @etn/server test          # тесты сервера
npm -w @etn/client test          # тесты клиента
npm run build                    # сборка всех workspace
```

Если `typecheck` или затронутые тесты красные — чинить до коммита.

> Команды выше — для Git Bash (основной shell на этой машине). В PowerShell
> работают те же `npm …`; `nvm use` — через `nvm-windows`.

## 6. Коммиты и ветки

- **Баг-фикс (тестовая эксплуатация):** `fix(<scope>): <summary>` — например
  `fix(client): focus cloud overflow clips instead of expanding grid`.
- **Задача workplan:** `[<TASK_ID>] <type>(<scope>): <summary>` — например
  `[B7] feat(server): Fastify bootstrap with health/version`.
- **Правка спецификации:** отдельный коммит `docs(<area>): ...`, не смешивать с
  кодом.
- Один коммит = одна осмысленная правка. Не мешай фиксы разных дефектов.
- Коммитишь только когда `typecheck` + затронутые тесты зелёные.
- Деструктивные операции (удаление/перезапись файлов, `git push --force`) — только
  после подтверждения пользователя.

## 7. Специфические архитектурные ограничения (часто нарушаются)

- **Онлайн-only клиент.** Локальный SQLite клиента — **только** для персональных
  настроек, UI-state, черновиков, истории фокуса, `client_id`, `last_seq`. Никаких
  авторитетных данных сети локально.
- **Хранение:** `_system.db` (общая) + `networks/<uuid>/data.db` на сеть. На MVP —
  один серверный процесс, без кластеризации.
- **Идемпотентность:** каждый изменяющий запрос обязан принимать
  `Client-Request-Id`; сервер кеширует ответ 10 мин.
- **Real-time:** `audience: "network"` (по умолчанию) или `"user"` (приватные
  настройки пользователя — `show_inactive`, порядок фокуса и т.п.).
- **Граф может содержать циклы.** Любой обход — с visited-set или path-CTE, с
  лимитами `max_depth`/`max_nodes` (см. [`docs/11-settings-and-state.md`](docs/11-settings-and-state.md), п. 5).
- **Защищённые сущности:** корневая мысль HOME (`is_protected=1, is_root=1`) —
  неудаляема. Первый пользователь (`is_first_user=1`) — неудаляем и всегда админ.
- **API-key** сохраняется только SHA-256 хешем; полный ключ возвращается
  пользователю **ровно один раз** при генерации.
- **MCP-агент должен вызывать `find_duplicates` перед `create_thought`** — чтобы
  не плодить дубликаты.

## 8. Если обнаружил проблему

- **Противоречие в спецификациях** → не выбирай «правильную» версию молча. Опиши
  расхождение пользователю/в issue и попроси решения.
- **Спецификация устарела/неполна** → предложи правку отдельным коммитом
  `docs: ...`, не смешивая с кодом.
- **Задача/фикс оказалась больше** → разбей; для крупной работы заведи ID в
  `workplan.md` (фаза L), обнови план.
- **Нашёл баг в чужой `done`-области** → чини как обычный баг-фикс (п. 3.1), но
  предварительно прочитай связанную спецификацию; если сомневаешься — согласуй.

## 9. Чек-лист перед коммитом

- [ ] Код следует п. 4 (TypeScript strict, без `any` без причины, TSDoc).
- [ ] `npm run typecheck` зелёный.
- [ ] Тесты затронутой области зелёные.
- [ ] Спецификация соблюдена (или правка спецификации — отдельным коммитом).
- [ ] Для задачи workplan: чекбоксы DoD отмечены, статус переведён в `done`.
- [ ] Коммит с правильным префиксом (`fix(...)` / `[<ID>] ...` / `docs(...)`).
- [ ] Runtime- и build-артефакты не закоммичены.
