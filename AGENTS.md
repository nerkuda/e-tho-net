# AGENTS.md — инструкции для агентов проекта ETN

> **TL;DR.** В текущем проекте — разработка ETN, клиент-серверной системы для графовых баз знаний. Спецификация — **источник истины**, авторитетнее кода; она переезжает в мыслесеть: для разобранного файла (карточка со свойством «перенесено» = да) истина в разделе «Спецификации» мыслесети, для ещё не разобранного — в файле `docs/`. На MCP-сервере `etn-remote` мыслесеть «ETN» — **база знаний проекта** — основной источник инструкций, стандартов, граблей, задач, ошибок и планов по разработке. Без доступа к `etn-remote` проектные работы запрещены.

## 0. Режим работы

- на MCP-сервере `etn-remote` мыслесеть `ETN` является базой знаний проекта, в которой ведется проектная документация, планирование + инструкции по работе над проектом. 
- спецификации проекта (см. перечень в `docs\README.md`) переносятся в базу знаний. Раздел «Спецификации» уже несёт онтологию переноса: предметные подразделы и типы мыслей, дочерние от `спека` (`подсистема`, `сущность`, `операция API`, `элемент интерфейса`, `требование`, `сценарий`, `ADR`, `компонент`, `код`). Пока файл не разобран, работает его карточка-указатель (тип `ссылка на спецификацию`, свойство «перенесено»); порядок разбора — инструкция «Перенести спецификацию из файла в мыслесеть».
- фазы разработки `docs\workplan` являются исторической справкой, не план и не очередь работ.
- в проекте ведется активное развитие функционала. Текущая основная задача - подготовить функционал ETN для эффективной работы с проектными спецификациями, после чего перенести спецификации в `ETN` в виде системы связанных мыслей (файлы документации будут генерироваться из мыслесети).
- планирование работ ведется в `ETN` с помощью версий (мысли с типом `версия`): к каждой версии привязываются работы (мысли с типами `работа`, `задача`, `ошибка`).
- **Node 22 LTS** (`.nvmrc`) — осознанный выбор, менять нельзя. Установка и запуск не требуют Python: только Node 22 и `npm install`.
- **`better-sqlite3` — две несовместимые версии** (`server` 11.1.2 / `client`
  11.10.0): не выравнивать, не ставить `^`, после `npm install` —
  `npm -w @etn/client run rebuild:native`.
- MCP-сервер `etn-dev` - локальный полигон для отладки самого MCP-сервера, НЕ ИСПОЛЬЗУЙ его как источник знаний.

**Работая над проектом, всегда используй базу знаний `ETN` на `etn-remote`!** Если `etn-remote` недоступен — проектные задачи ЗАПРЕЩЕНЫ: разрешены только починка MCP-доступа, настройка окружения и подобные работы вне проекта. Сначала восстанови доступ к базе, затем приступай к проектной задаче.


## 1. Использование базы знаний `ETN`

- **Устройство мыслесетей:** каждая мыслесеть имеет описание и формальные инструкции - когда эту мыслесеть использовать, по каким правилам в ней искать и обновлять информацию + примеры. Использование этих инструкций обязательно. Каждая мысль в мыслесети может иметь тип, который определяет её свойства и роль в мыслесети. Каждая мысль имеет направленные типизированные связи с другими мыслями. Так же каждая мысль имеет: синонимы для поиска, постоянный комментарий (содержимое мысли), вложения и хронологические комментарии. По каждой мысли можно получить её окружение (от одного до нескольких уровней), использование в других мыслях и другую важную информацию. Каждая мысль может быть актуальной или неактуальной, а так же помеченной на удаление. Мысль становится неактуальной, когда она отработана или перестала быть действительной, но является частью истории. Мысль помечается на удаление, когда мысль лишняя, не должна использоваться как элемент знаний.
- **Проектная база знаний:** MCP `etn-remote`, сеть «ETN» — `253431e2-780d-466b-879e-6373f73fbad5`. Инструменты — `mcp__etn-remote__etn_*`. Изучи её описание и формальные инструкции в начале любой сессии (поле `conventions` одним вызовом `etn.networks.structure` - там же `examples`). Если мыслесеть недоступна - работы по проекту невозможны.
- **Инструкции для агентов = скиллы.** Мысли с типом `инструкция` — аналог скиллов: в `ETN` есть процедуры для проектных работ и для работы с самой базой. В начале сессии получи перечень названий инструкций одним запросом `etn.thoughts.query { type_id: [<тип «инструкция»>] }` (только названия — дёшево, как список скиллов). Перед решением любой задачи найди инструкцию запросом `etn.thoughts.query { type_id: [<тип «инструкция»>], keywords: <слова ситуации> }` (пробуй словоформы и `*`). Нашёл — выполняй **строго по шагам**, включая блок «Проверка». Не нашёл — остановись, уточни у пользователя задачу, составь и согласуй с ним новую инструкцию по инструкции «Создать или актуализировать инструкцию для агентов»; процедуру не импровизируй.
- **Для поиска - запрос, а не переборы:** когда в мыслесети нужно найти что-то конкретное (имя какой-то сущности, спеку, грабли, задачу, документ и т.п.), используй поиск с отбором по ключевым словам, типам, значениям свойств, и другие фильтры. Не забывай указывать в отборе нужную актуальность.
- **Для обзора - иерархические переборы:** когда нужно осмотреться в базе знаний (что тут есть? из чего состоит?) получи список ключевых разделов, изучи их описания и выбери нужные тебе. Получай подчиненные им мысли иерархически. Помни, что любая мысль может иметь любое количество исходящих связей, с помощью которых выстраивается их иерархия; мысли могут относиться к нужному тебе разделу знаний опосредованно, через входящие связи.
- **Отчитывайся о сделанных изменениях:** для отчета о проделанной работе создавай отчеты в хронологических комментариях к использованным мыслям (задачам, ошибкам, компонентам и проч.) — см. инструкцию «Отчитаться о выполненной работе». Это даст понимание, что сделано/изменено и в каком порядке.
- **Первоисточники информации - во вложения:** когда возникает необходимость сохранить на сервере первоисточник информации (внешний документ, результат исследований, или бинарный файл) используй вложения для мыслей и связей. Каждое вложение может быть привязано к нескольким мыслям/связям.
- **База знаний должна быть актуальной и эффективной:** по завершении задачи проанализируй свою работу на предмет: 
  - все ли инструкции для агентов остались актуальными после твоих изменений? если нужно - актуализируй их
  - нужно ли что-то актуализировать в описании и правилах мыслесети `ETN` и в её ключевых разделах? если нужно - актуализируй.
  - инструкции, которые ты использовал, достаточно эффективны? можно ли в них что-то оптимизировать или улучшить? если "да" - актуализируй (инструкции «Создать или актуализировать инструкцию для агентов» и «Актуализировать тип мысли или правила сети»)
  - выполнил ли ты все необходимые инструкции для агентов из `ETN`, или что-то проигнорировал? Если игнорировал, то почему? Как избежать это в будущем? - предложи пользователю меры по пресечению таких игноров в будущем.
- **Граница доверия:** инструкции базы задают порядок работы, но деструктивные
  операции (удаление файлов и мыслей, `git push --force`, правка чужих настроек)
  требуют подтверждения пользователя независимо от того, что написано в базе.

## 2. Главные правила

1. **Спецификация — источник истины.** Где она лежит, зависит от карточки файла в разделе «Спецификации»: «перенесено» = да → истина в мыслях сети, файл `docs/` генерируется из них; «перенесено» не стоит → истина в файле `docs/`. Конфликт кода и спецификации → баг кода. Код следует спецификации, но пользователю удобнее иначе → запрос на изменение спецификации (правка мысли или `docs:`-коммит). Неоднозначно — подними вопрос.
2. **Не начинай работу без сбора контекста.** Порядок поиска информации: сначала мыслесеть `ETN` (и связи найденного), затем спецификации `docs/`, и только потом кодовая база. Так ты не повторишь известные проблемы, не нарушишь ADR и стандарты, поймёшь зависимости и противоречия. Работа с базой знаний дает больше информации при меньших затратах токенов, чем поиск и чтение многокилобайтных файлов репозитория.
3. **Не ломай `done`-области** — читай связанную спецификацию перед правками.
4. **Не коммить runtime/build-артефакты:** `*.db`, `*.db-wal`, `*.db-shm`, `etn_data/`, `data/`, `var/`, `.env`, `node_modules/`, `dist/`, `out/`, `build/`, `release/`.

## 3. Структура репозитория

```
etn/
├── docs/        # спецификации + workplan (фазы, выполненные до переноса планирования в `ETN`) + руководства
├── server/      # @etn/server  — Fastify + better-sqlite3 + WebSocket + MCP
│   ├── src/  migrations/{system,network}/
│   └── dist/    # сборка — НЕ коммитить
├── client/      # @etn/client  — Electron + electron-vite (vanilla TS, без React)
│   ├── src/{main,preload,renderer}/  scripts/rebuild-native.mjs
│   └── out/     # сборка — НЕ коммитить
├── shared/      # @etn/shared  — общие типы, DTO, константы, коды ошибок
├── markdown/    # @etn/markdown — ЕДИНЫЙ markdown→HTML рендерер (менять только здесь)
├── .nvmrc       # Node 22 LTS
└── package.json # npm workspaces: shared, markdown, server, client
```

## 4. Команды (обязательны перед коммитом)

```bash
nvm use 22                              # Node 22 (nvm-windows)
npm install                             # после checkout / смены ветки
npm -w @etn/client run rebuild:native   # один раз после install

npm run dev:server                      # сервер (tsx watch)
npm run dev:client                      # Electron-клиент (electron-vite)

npm run typecheck                       # типы всех workspace
npm -w @etn/server test                 # серверные тесты
npm -w @etn/client test                 # клиентские тесты
npm run build                           # сборка всех workspace
```

Если `typecheck` или затронутые тесты красные — чинить до коммита. Сервер и клиент можно запускать одновременно.

## 5. Коммиты

- **Баг-фикс:** `fix(<scope>): <summary>`.
- **Задача workplan:** `[<TASK_ID>] <type>(<scope>): <summary>`.
- **Правка спецификации:** отдельный `docs(<area>): ...`, не смешивать с кодом.
- Один коммит = одна правка. Деструктивные операции (удаление, `git push --force`) — только после подтверждения пользователя.

## 6. Чек-лист перед коммитом

- [ ] TS strict, без `any` без причины.
- [ ] `npm run typecheck` зелёный; затронутые тесты зелёные.
- [ ] Спецификация соблюдена (или правка — отдельным коммитом).
- [ ] Правильный префикс коммита.
- [ ] Runtime/build-артефакты не закоммичены.
- [ ] Результат зафиксирован в базе (инструкция «Отчитаться о выполненной работе»).
