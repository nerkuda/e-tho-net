# installer/ — установщик ETN для Windows

Комбинированный установщик (`etn.iss`, Inno Setup 6) ставит сервер ETN
службой Windows и/или клиент. Каталоги `payload/`, `.cache/` — артефакты
сборки и в репозитории не версионируются.

```
installer/
├── etn.iss                 сценарий Inno Setup (каркас — задача a1211915)
├── build.ps1               сборка release/ETN-Setup-<версия>.exe
├── fetch-payload.ps1       подготовка payload (Node, WinSW, сервер, клиент)
├── service/
│   └── etn-service.xml     шаблон службы WinSW (плейсхолдеры {{...}})
├── third-party/            лицензии Node.js и WinSW, NOTICE.md
├── tests/                  silent-контракт, init/ключ, staged-запуск, фикстуры payload
├── payload/                (gitignored) готовый payload для etn.iss
└── .cache/                 (gitignored) скачанные архивы и staging сборки
```

## Порядок сборки

```powershell
nvm use 22
npm install                                   # один раз после checkout
pwsh -File installer/fetch-payload.ps1        # Node, WinSW, сервер, клиент + проверки
pwsh -File installer/build.ps1                # release/ETN-Setup-<версия>.exe
```

`fetch-payload.ps1` идемпотентен: скачанные Node и WinSW кэшируются в
`installer/.cache` и сверяются по SHA-256 при каждом запуске, каталоги
`payload/node`, `payload/service`, `payload/server` и `payload/client`
пересоздаются. Клиент собирается `electron-builder --dir` (цель `win: dir`,
NSIS снят задачей `98ad5eec`) в `client/release/win-unpacked` и копируется в
`payload/client` целиком: `ETN.exe`, `resources/app.asar`, миграции и
`THIRD-PARTY-NOTICES.txt`.

Подготовка клиента требует двух условий окружения: закрытого dev-клиента
(`node_modules/electron` держит `better_sqlite3.node`, electron-builder
пересобирает его под Electron ABI — иначе EBUSY/EPERM) и права создавать
символьные ссылки при распаковке `winCodeSign` (Developer Mode или запуск
от администратора; иначе electron-builder падает на
`Cannot create symbolic link … libcrypto.dylib`). Второе условие относится к
`rcedit` (иконка и версия exe) и действует для любой Windows-цели, включая
прежнюю NSIS.

`build.ps1` перед продуктовой сборкой проверяет свежесть payload (задачи
`9b310991`, `98ad5eec`): обязательные файлы на месте (включая
`client\ETN.exe`, `client\resources\app.asar` и паспорт поставки
`server-manifest.json`), версия сервера совпадает с репозиторием,
`client_version` из манифеста — с `client/package.json`, хэши файлов
`client\` — с картой `client.hashes` манифеста, **весь** `server\dist`,
**все** `server\migrations` и шаблон службы совпадают по SHA-256, CLI умеет
`--check` и `--key-out`, инструмент `server\dist\db\db-backup.js` умеет
`backup --to` и `restore --from` (задача `3acd9c3c`), в шаблоне есть все
плейсхолдеры. Устаревшая поставка
не превращается в exe, падающий на `etn init`: сборка останавливается с
указанием обновить payload (`fetch-payload.ps1`). Обновить и собрать одним
запуском — `build.ps1 -RefreshPayload`. В `-TestMode` (тестовая сборка на
фикстуре) проверка пропускается.

Паспорт поставки пишется `fetch-payload.ps1` последним шагом, а в начале
прогона удаляется: неудачная сборка клиента (`package:dir` упал на занятом
`better_sqlite3.node`) не оставляет манифест, по которому старый payload
выглядел бы свежим. Проверить свежесть без компиляции —
`build.ps1 -CheckPayloadOnly` (код 0 — свежий; полная сборка exe на машине с
занятым native-модулем недоступна).

Проверки, которые выполняет скрипт (без установки в систему):

1. `node.exe -v` из поставки — ровно закреплённая версия линии 22;
2. `require('better-sqlite3')` и реальный SQL-запрос под поставленным
   `node.exe` — нативный модуль собран под ABI Node 22;
3. ESM-импорт `@etn/shared` и `@etn/markdown` из `server\node_modules`;
4. наличие миграций `server\migrations\system` и `network`;
5. smoke-test (если не указан `-SkipSmokeTest`): `etn init` на временном
   `ETN_DATA_DIR`, запуск `node.exe server\dist\index.js` на свободном порту,
   `GET /api/v1/health` → 200 со `status=ok` и версией из
   `server\package.json`, остановка процесса.

## Экраны GUI (задача 112642a4)

Первый экран мастера — **компоненты и приветствие** (стандартные страницы
приветствия и лицензии Inno отключены). Экран собран из списка
`TNewCheckListBox` с собственной прокруткой и **неподвижного нижнего блока**.
В списке — два флажка (сервер, клиент) и серые строки-описания под каждым:
состояние компонента на машине и что установщик с ним сделает. Текст строк
переносится по словам, поэтому длинные сообщения видны целиком.

Нижний блок снизу вверх: причина неактивности «Далее» (красная строка
«Далее недоступна: …», видна всегда), при первой установке — чекбокс «Я
принимаю условия лицензии MIT» и ссылка на текст лицензии (локальный файл
`LICENSE` внутри установщика, интернет не нужен), каталог данных сервера
(показывается, когда сервер выбран или уже установлен) и ссылка на другие
варианты установки сервера (удалённый сервер, Docker). Список занимает всю
оставшуюся высоту: при маленьком окне или крупном масштабе прокручивается
только он, нижний блок остаётся на месте.

Подписи флажков зависят от состояния машины; при обновлении (сервер или
клиент уже установлен) лицензия не запрашивается. Без принятия лицензии или
без выбранного компонента «Далее» неактивна, причина показана в нижнем блоке.
Радиокнопок режима и подсказок, скрываемых пересчётом высот, больше нет.
Геометрию и тексты экрана проверяет `silent-codes.ps1` (`/TESTLAYOUT`);
отрисовку при масштабе 100% и 150% проверяет человек визуально —
автоматический прогон окно не открывает.

Далее — экраны администратора (логин и отображаемое имя), параметров сервера
и первичного API-ключа. Режим установки выбирается **по фактическим правам
процесса**: продуктовая сборка работает с `PrivilegesRequired=lowest` и не
перезапускает мастер (ошибка aa5af30c — respawn после диалога режима ломал
ввод). Обычный запуск — только клиент «только для меня» в профиль, без UAC.
Сервер и клиент «для всех пользователей» — запуск установщика **от имени
администратора** (правый клик → «Запуск от имени администратора»); в этом
режиме каталог программы — `%ProgramFiles%\ETN`, ярлыки — общие. Флаг
`/ALLUSERS` сохранён для тихого автообновления службы: LocalSystem уже
элевирован, Inno включает административный режим без UAC и без respawn.
Старый клиент ETN 0.14.x,
установленный NSIS-установщиком electron-builder, ищется в реестре и удаляется
его деинсталлятором до копирования файлов (машинную запись — в административном
режиме) и только если клиент выбран в этом запуске. Деинсталлятор запускается
с `/S` и `_?=<каталог деинсталлятора>` (последним параметром, без кавычек —
требование NSIS 3.2.2): без `_?=` NSIS копирует себя в `%TEMP%`, возвращает
управление сразу, и удаление идёт параллельно установке. После запуска
установщик дополнительно ждёт исчезновения записи `Uninstall` (до 10 секунд):
это надёжный признак того, что удаление действительно закончилось. Ненулевой
код или не исчезнувшая запись — установка не начинается: причина показывается
пользователю, файлы клиента не копируются. В тестовой сборке поиск и удаление
старого клиента не выполняются (`GTestMode`).

Прогресс установки подписывает текущий этап в `StatusLabel` страницы
установки: замена файлов, остановка службы, подготовка каталогов данных,
настройка службы, правило брандмауэра, инициализация сервера, запуск службы,
health-check, запись параметров. Подписи стоят в точках вызова операций;
остановку/запуск службы и бэкап выполняет задача `bb063ac3` (бэкап
реализован через CLI сервера — см. «Бэкап и восстановление БД»). Установка идёт
**одним процессом** (в административном режиме или в режиме «только для меня»),
поэтому этапы видны и в `StatusLabel`, и в журнале установки. При **отмене UAC** (элевация по
`/ALLUSERS` из неэлевированного процесса; обычный запуск и запуск от имени
администратора UAC внутри мастера не запрашивают) установщик молча
завершается — код 2 (`ecCancelledBeforeInstall`),
без диалогов; прочие ошибки элевации Windows/Inno показывает в диалоге с кодом
и текстом. Журналы не создаются в обоих случаях: наш install-лог доступен
только после начала установки (ограничение диагностики `2dd215f7`; в исходниках
Inno 6.7.3 `RespawnSetupElevated` вызывается до `StartLogging`, а отмена UAC
обрабатывается как `Abort` без сообщения). ErrorCode в нашем журнале пишется
для отказов **после** старта лога — например, `ShellExec` лицензии и повторной
установки.

При сбое показывается **экран ошибки**: причина, путь к журналу, путь к
последней резервной копии баз и следующий шаг, кнопки «Открыть журнал»,
«Открыть папку данных» и «Повторить установку». Успешное завершение — экран
**итоговой сводки**: локальный адрес сервера `http://127.0.0.1:<порт>`,
адрес в локальной сети при открытом брандмауэре (LAN-IPv4 определяется через
PowerShell; виртуальные адаптеры Hyper-V, VMware/VirtualBox, VPN и
Tailscale/ZeroTier исключаются, в сводке адрес помечен как «может
отличаться»), каталог данных, журнал, резервная копия, напоминание сохранить
ключ и кнопки «Запустить клиент» (только если клиент выбран и установлен),
«Открыть папку данных», «Открыть журнал». Ошибка netsh предупреждением
входит в сводку.

## Клиент: область установки, ярлыки, закрытие (задача 98ad5eec)

Клиент поставляется тем же установщиком, одним компонентом с сервером
(выбор — на экране компонентов). Собственного экрана каталога нет: каталог
фиксирован ADR `144bcdb0`, а область установки определяет и путь, и права:

| область | каталог | файлы | служба/данные |
|---|---|---|---|
| «только для меня» (`client_scope=user`) | `%LOCALAPPDATA%\Programs\ETN` | `{app}\ETN.exe` + `resources\` | не требуются, установка без UAC |
| «для всех пользователей» (`client_scope=machine`) | `%ProgramFiles%\ETN` | `{app}\client\ETN.exe` + `resources\` | ставит запуск от имени администратора (или `/ALLUSERS`) |

Каталог установки показан на экране компонентов рядом с описанием клиента
(`ClientInstallPath`), чтобы область была видна до начала установки. Выбора
области в мастере нет: её задают фактические права процесса (радиокнопки
удалены как недостижимые). При обновлении выбранная область выводится текстом
(`GScopeFixedLabel`, `ClientScopeFixed`, `ClientScopeText`). Копия клиента
«только для меня» видна и при запуске от имени администратора: `ClientFilesPresent`
проверяет профиль и машинную область, а при найденной user-копии мастер честно
говорит, что она останется в профиле, а рядом появится копия «для всех».
Оговорка: под Administrator Protection элевированный процесс видит
`{localappdata}` профиля SMAA, поэтому копию исходного пользователя установщик
может не обнаружить — тогда мастер её не назовёт (установка при этом
корректна).
Машинная область сохраняется в `install.json` (`mode=client`,
`client_scope=machine`) даже
если сервер не выбран: иначе повторный запуск потерял бы область и поставил
вторую пользовательскую копию.

Ярлыки создаёт `[Icons]`: машинные — рабочий стол `{commondesktop}` и меню
«Пуск» `{commonprograms}\ETN`, пользовательские — `{userdesktop}` и
`{userprograms}\ETN`. Явные константы нужны потому, что при
`PrivilegesRequired=lowest` элевированный процесс остаётся в
неадминистративном режиме установки, и `{autodesktop}`/`{autoprograms}`
указывали бы на профиль. Цель и `Check` зависят от области — машинный ярлык
указывает на `{app}\client\ETN.exe`, пользовательский на `{app}\ETN.exe`;
машинные ярлыки создаёт запуск от имени администратора, пользовательские —
обычный запуск.
Деинсталлятор удаляет созданные ярлыки сам (записи `[Icons]` попадают в его
журнал), отдельного кода удаления нет. В тестовой сборке каталоги ярлыков
уведены в песочницу `.tmp\installer-tests\shortcuts` — прогон не трогает
рабочий стол и меню пользователя.

**Закрытие запущенного клиента.** Перед заменой файлов (в GUI — на экране
готовности с предупреждением, в silent — молча)
установщик ищет процессы `ETN.exe` (PowerShell `Get-Process`) в **двух
каталогах** (`ClientCloseRoots`): выбранной области и втором варианте ADR
`144bcdb0`. При запуске от имени администратора порядок — `%ProgramFiles%\ETN`, затем
`%LOCALAPPDATA%\Programs\ETN`; в режиме «только для меня» — наоборот.
Закрываются только процессы, чей путь начинается с одного из этих каталогов
(`ClientRootCondition`), поэтому клиент другого пользователя не трогается —
иначе его `ETN.exe` давал бы 30+15 с ожидания и код 20 при per-user установке.
Под Administrator Protection `%LOCALAPPDATA%` элевированного процесса — профиль
SMAA, поэтому пользовательский клиент исходного пользователя в admin-режиме
может не закрыться; машинный клиент из Program Files закрывается всегда.
Найденные процессы закрываются **мягко**: `taskkill /PID`
без `/F` (WM_CLOSE, Electron завершает работу сам), ожидание выхода — 30 с,
опрос раз в 250 мс. Только если процесс не вышел за бюджет, применяется
`taskkill /F /PID … /T` и ожидание ещё 15 с. Если процесс жив и после этого,
установка не начинается: код 20, причина в журнале и в reason-файле; экран
ошибки показывает текст причины (`GFailureReason` → `FailureReasonText` /
`ErrorMemoText`), reason-файл читают тесты. Файлы не заменяются. Отказ пользователя в GUI
(«Закрыть клиент и продолжить установку?» — «Нет») возвращает на экран
компонентов. Установка только сервера запущенный клиент не трогает:
клиент не выбран — закрывать нечего.

**Запуск после установки.** Кнопка «Запустить клиент» на итоговой сводке
видна только при успешной установке и выбранном клиенте; клиент запускается
от исходного пользователя (`ShellExecAsOriginalUser`), даже если установщик
повышал права, — иначе профиль и данные оказались бы у другого
администратора. `/SERVERONLY` клиент не ставит и кнопку не показывает;
silent-контракт (`/VERYSILENT /SERVERONLY`) клиент не устанавливает, коды
0/10/20 сохраняются (код 20 — в том числе отказ закрыть клиент).

## Раскладка payload

`etn.iss` при компиляции проверяет наличие ключевых файлов и пропускает
секции `[Files]`, если каталога нет (видны предупреждения компилятора).
Контракт раскладки:

| payload | куда ставится | что это |
|---|---|---|
| `node\node.exe` | `{app}\node\node.exe` | Node 22 LTS из официального win-x64 zip |
| `service\etn-service.exe` | `{app}\service\etn-service.exe` | WinSW 2.12.0 (x64, self-contained) |
| `service\etn-service.xml` | `{app}\service\etn-service.xml` | шаблон службы (см. ниже) |
| `server\package.json` | `{app}\server\package.json` | манифест сервера; версия читается установщиком |
| `server\dist\` | `{app}\server\dist\` | сборка `@etn/server` (`index.js`, `cli.js`, …) |
| `server\migrations\` | `{app}\server\migrations\` | миграции `system/` и `network/` |
| `server\node_modules\` | `{app}\server\node_modules\` | prod-зависимости + собранные `@etn/shared`, `@etn/markdown` |
| `client\` | `{app}\` (для меня) / `{app}\client\` (для всех) | распакованная сборка клиента: `ETN.exe`, `resources\app.asar`, `resources\migrations`, `resources\THIRD-PARTY-NOTICES.txt` |
| `server-manifest.json` | (не ставится) | паспорт поставки: версии, SHA-256 Node/WinSW, resolved-зависимости, `client_version`, Electron и хэши файлов `client\` (`client.hashes`) |

Внешний Node на машине не нужен и не проверяется (ADR `01c38213`);
`better-sqlite3` жёстко 11.1.2 и собран под ABI Node 22.

**Размер payload.** Каталог `client\` — около 473 МБ (`ETN.exe` ~181 МБ,
`resources\app.asar` ~223 МБ), и почти всё это — бандл renderer. Пакеты,
нужные только для renderer (lucide, es-toolkit, `@awesome.me`, mermaid,
codemirror, vaadin, d3), сейчас лежат в `dependencies` клиента и дублируют
`out/renderer`: продуктовый `app.asar` тяжелее необходимого. Это задел на
оптимизацию отдельной работой (перенос renderer-only пакетов в
`devDependencies`/бандл), на контракт payload и установщик не влияет.

## Служба Windows и плейсхолдеры

`service/etn-service.xml` — шаблон конфигурации WinSW (ADR `db60302a`).
WinSW читает файл `<имя exe>.xml` из своего каталога, поэтому установленная
копия лежит рядом с `etn-service.exe`: `{app}\service\etn-service.xml`.

Три плейсхолдера **подставляет установщик** (`installer/etn.iss`) в момент
установки или обновления сервера (задача `9b310991`): после копирования файлов
`InstallServiceConfig` читает `{app}\service\etn-service.xml` как UTF-8,
заменяет значения и записывает обратно; если в файле остались `{{`, установка
завершается кодом 10 — службу с плейсхолдерами регистрировать нельзя: литерал
`{{PORT}}` попадёт в окружение сервера, и он не стартует (ADR `db60302a`).

| плейсхолдер | значение по умолчанию установки | куда попадает |
|---|---|---|
| `{{DATA_DIR}}` | `%ProgramData%\ETN` (ADR `144bcdb0`) | env `ETN_DATA_DIR`, каталог журнала службы |
| `{{PORT}}` | 4321 | env `ETN_PORT` |
| `{{HOST}}` | `0.0.0.0` при разрешённых подключениях, `127.0.0.1` — иначе | env `ETN_HOST` |

Кроме подставляемых значений, шаблон фиксирует
`<env name="ETN_DEPLOYMENT" value="windows-service"/>`: сервер узнаёт, что
запущен службой, и разрешает обновление из клиента (ошибка `e375123f`).
Режим `app` этот файл не использует — там сервер без переменной считает себя
`standalone`, Docker определяется по маркеру контейнера (`server/src/update/deployment.ts`).

Пути к программе в шаблоне заданы через `%BASE%` — переменную самого WinSW
(каталог, где лежит `etn-service.exe`), поэтому шаблон не зависит от
каталога установки и переживает обновление без переписывания путей.

Точка запуска — `node.exe server\dist\index.js`, **не** `etn`: `etn` без
команды печатает справку и возвращает 1, служба ушла бы в цикл
перезапусков.

Журнал службы (stdout/stderr сервера) — `{{DATA_DIR}}\logs\service`,
файлы `etn-service.out.log` и `etn-service.err.log`, ротация по размеру:
10 МБ, хранится 8 файлов. WinSW сам каталог не создаёт — его обязан создать
установщик до старта службы (задача `9b310991`). Файловый журнал приложения
пишется отдельно и с этими файлами не пересекается.

Аварийное поведение: `<onfailure>` перезапускает службу через 10/30/60 с,
счётчик падений сбрасывается после часа работы; `<stoptimeout>30sec</stoptimeout>`
даёт серверу время на штатную остановку (чекпойнт WAL) до принудительного
снятия процесса. Служба работает под `LocalSystem` — у системной учётной
записи есть доступ к `%ProgramData%\ETN`.

Остановку, состояние и запуск службы выполняет установщик командами WinSW
(`etn-service.exe stop|status|start`), а не `sc` — задачи `bb063ac3` и
`34f8e315`. `stop` не ждёт фактической остановки, а `stopwait` ждёт её без
тайм-аута, поэтому установщик после `stop` опрашивает `etn-service.exe status`
(Started/Stopped/NonExistent, exit 0) до подтверждённого `Stopped`; бюджет —
60 с по системным часам, опрос раз в 500 мс. Режим «обычное приложение» (без
службы) — тот же `node.exe server\dist\index.js` с `ETN_DATA_DIR`, `ETN_PORT`,
`ETN_HOST` и без `ETN_DEPLOYMENT` (сервер считает себя `standalone`); его
запускает ярлык, отдельного helper-процесса нет.

### Регистрация и снятие службы (задачи 8b1f5980, 34f8e315)

Служба регистрируется в `CurStepChanged(ssPostInstall)`:

1. `InstallServiceConfig` подставляет плейсхолдеры в
   `{app}\service\etn-service.xml`;
2. `RegisterServiceIfNeeded` — `{app}\service\etn-service.exe install`
   (конфигурация WinSW читается из файла рядом с exe). Уже
   зарегистрированную службу установщик не перегистрирует: изменённые
   `ETN_DATA_DIR`/`ETN_PORT`/`ETN_HOST` WinSW читает из xml при каждом старте.
   Перед этим проверяется личность службы: `ImagePath` должен указывать на
   `{app}\service\etn-service.exe`; `Start=4` (disabled), `DeleteFlag=1`
   (помечена на удаление) и `status=NonExistent` при живом ключе — код **20**
   **до** копирования файлов (чужая/устаревшая служба не должна запускаться
   после замены файлов). Код 1073 от `install` — успех только для своей
   службы. Сбой регистрации после копирования — silent-код **10** с причиной;
   `install.json` не пишется;
3. `start` вызывается всегда для зарегистрированной службы и не ждёт
   `RUNNING`: WinSW возвращает управление раньше, чем сервер начнёт слушать
   порт. `start` на уже работающей службе завершается кодом 1056 — это успех.
   Готовность подтверждает только health-check (бюджет 60 с фактического
   времени). Сбой `start` после замены файлов — silent-код **10** с причиной;
   `install.json` не пишется, обновление откатывается к прежней версии.

В режиме `app` служба не регистрируется и не запускается: сервер поднимает
пользователь, health-check пропускается, `install.json` получает
`"mode":"app"`. При обновлении режим фиксирован записью установки
(`install.json`).

При удалении программы `CurUninstallStepChanged(usUninstall)` вызывает
`RemoveServiceOnUninstall` — **до** удаления файлов, пока
`etn-service.exe` ещё на месте: `status` (Stopped/NonExistent — `stop` не
нужен, иначе `stop` с ожиданием), затем `uninstall`. После `uninstall` с кодом
0 (включая 1072, когда служба помечена на удаление) установщик опрашивает
`status` до `NonExistent`: exit 0 не доказывает удаление. Осталось
`Started`/`Stopped` — удаление не завершено, причина в журнале; `NonExistent`
при оставшемся ключе — SCM завершит удаление после перезагрузки (файлы
удалять можно). Чужую/устаревшую службу (другой `ImagePath`) установщик не
трогает: предупреждение, файлы программы при этом удаляются. Путь к службе
вычисляется из `{app}` по месту (`ServiceDir`), а не из `GServerDir`: Inno
**не вызывает `InitializeSetup` в деинсталляторе**, и глобалы установщика там
пусты (блокер приёмки 4151edf6). `InitializeUninstall` задаёт только то, что
нужно удалению: каталог данных и режим из `install.json` (иначе
`%ProgramData%\ETN`) и собственный журнал
`%ProgramData%\ETN\logs\uninstall-*.log` — без него причина отказа снятия
службы осталась бы только в журнале Inno, который ведётся лишь при `/LOG`.
Отказ (служба не остановилась или `uninstall` вернул ошибку) отменяет
удаление: причина в журнале удаления и в сообщении, файлы не удаляются,
службу можно снять вручную командами `etn-service.exe stop` → дождаться
`status=Stopped` → `etn-service.exe uninstall`. Inno не поддерживает
собственный код возврата uninstaller: по документации любой ненулевой код
означает, что удаление не завершено; контрактный код **10** с причиной
проверяется пробой `/TESTUNINSTALLSERVICE` (та же функция
`RemoveServiceOnUninstall`), а сам деинсталлятор — поведенческим кейсом с
моделью службы (раздел 28 `installer/tests/silent-codes.ps1`). Повторная
установка после успешного удаления создаёт службу заново.

Права: служба работает под `LocalSystem` (доступ к `%ProgramData%\ETN`), а
`install`/`uninstall`/`stop`/`start` требуют прав администратора — установщик
и деинсталлятор машинной установки уже элевированы, UAC повторно не
показывается. Проверить службу:

```bat
{app}\service\etn-service.exe status   :: Started | Stopped | NonExistent
sc qc ETN                              :: путь к etn-service.exe и стартовый режим
Get-Service ETN                        :: PowerShell
```

Ожидаемое состояние после установки и перезагрузки — `Started`, стартовый
режим `AUTO_START`. Если служба не запускается, смотрите
`%ProgramData%\ETN\logs\service\etn-service.err.log` (stdout/stderr сервера)
и `etn-service.wrapper.log` в том же каталоге; повторная регистрация —
`{app}\service\etn-service.exe install` из консоли администратора.

### Остаточный риск: осиротевший `node.exe`

`status=Stopped` подтверждает, что служба остановлена, но не гарантирует, что
`node.exe`, осиротевший после прошлого падения WinSW, не держит файлы или БД:
такой процесс не является ребёнком службы. Предпроверка порта ловит только
слушающий орфан; неслушающий процесс с открытой БД установщик не обнаружит.
Если обновление падает на занятых файлах — проверьте
`Get-Process node | Where-Object Path -like '*ETN*'` и завершите процесс
вручную. Реальный E2E с медленной остановкой и осиротевшим процессом —
задача `8789381a`.


## Каталог данных, порт, брандмауэр

- **Каталог данных** фиксирован: `%ProgramData%\ETN` (ADR `144bcdb0`), поля
  выбора нет. Перед стартом службы установщик создаёт `logs`, `logs\service`
  (журнал WinSW сам не создаёт) и `backups`. В каталоге живут `_system.db`,
  `install.json`, `logs`, `backups`.
- **Порт по умолчанию — 4321**, задаётся на экране «Параметры сервера»
  (сохраняется в `install.json` и `ETN_PORT`). При обновлении/ремонте поле
  только показывается: параметры берутся из `install.json`.
- **Чекбокс «Разрешить подключения с других компьютеров в локальной сети»** —
  единственный источник `ETN_HOST`: включён — `0.0.0.0`, выключен —
  `127.0.0.1`. Включённый чекбокс создаёт правило брандмауэра Windows
  `ETN Server` (TCP, порт, профили `domain,private`; публичные сети не
  открываются), выключенный — удаляет его. Правило удаляется при удалении
  программы. Ошибка `netsh` установку не отменяет: `install.json` получает
  значение чекбокса (`"firewall": true`), сервер слушает `0.0.0.0`, но
  подключения из локальной сети могут блокироваться брандмауэром Windows.
  Предупреждение с причиной пишется в журнал установки и показывается на
  финальном экране GUI; silent-режим показывает его только в журнале.
- **Предпроверки до изменений** (`CheckServerEnvironment`): корректность и
  занятость порта — перечисляются все IPv4-слушатели порта (wildcard,
  loopback, конкретные адреса локальной сети). Порт, занятый собственной
  службой ETN, не ошибка: служба останавливается перед заменой файлов;
  слушатель распознаётся по PID службы и цепочке её потомков (WinSW 2.x
  запускает сервер дочерним процессом). IPv6-слушатели в перебор не входят:
  `ETN_HOST` в 0.15.1 — только IPv4, IPv6-only слушатель серверу не мешает;
  dual-stack `::` блокирует bind `0.0.0.0` и определяется пробной привязкой
  (если сервер начнёт слушать IPv6, перечисление надо расширить). Далее —
  путь каталога данных не занят файлом,
  запись в каталоги данных и программы (только в элевированном процессе),
  свободное место не меньше 300 МБ на дисках данных и программы. Причина
  отказа пишется в журнал и в файл `reason_file` (его показывает экран
  ошибки и читают тесты);
  в GUI показывается сообщением, фокус переводится на поле порта. Изменения
  при отказе не выполняются: ни файлов, ни `install.json`.
- **`etn init --check` и sidecars.** Проверка открывает `_system.db` строго на
  чтение, но SQLite в режиме WAL может создать рядом `_system.db-shm` и
  `_system.db-wal` — нормальные служебные файлы SQLite; содержимое базы не
  меняется, критерий `hasFirstUser()` не затронут. Установщик наличие
  sidecar-файлов не считает признаком данных: решение принимается по коду
  возврата `etn init --check`.

## Бэкап и восстановление БД: CLI сервера, не Pascal

SQLite-операции выполняет CLI сервера (задача `3acd9c3c`), установщик только
запускает его и разбирает отчёт. В поставку установщика входит
самодостаточный файл `server\dist\db\db-backup.js` (`[Files]` с
`DestName: "etn-db-tool.mjs"` и `dontcopy`): расширение `.mjs` нужно, потому
что вне пакета `@etn/server` Node иначе считает `.js` CommonJS. Инструмент
извлекается в `{tmp}` **до** остановки службы; нет файла или `node.exe` —
обновление не начинается, служба продолжает работать.

Запуск — `node.exe` поставки (`{app}\node\node.exe`, в тестовой сборке
`/TESTNODEEXE`) с рабочим каталогом `{app}\server`: оттуда резолвятся
`archiver`/`yauzl` и читается `package.json` версии. Аргументы:

```
backup  --to <данные>\backups --report-out <tmp>\etn-backup-report.txt --data-dir <данные>
restore --from <архив этого запуска> --force --report-out ... --data-dir ...
```

Отчёт — текст `key=value` (`code`, `archive`, `databases`, `bytes`, `error`,
`warnings`), поэтому установщику не нужен JSON-парсер. Путь архива и причина
отказа попадают в `GLastBackupDir`/`GBackupReason`, журнал
`%ProgramData%\ETN\logs\install-*.log`, экран ошибки и сводку; любой
ненулевой код инструмента — silent-код **10**.

Архив — ZIP по спецификации (сущность `2975c553`):
`%ProgramData%\ETN\backups\etn-backup-<версия>-<YYYYMMDD-HHMMSS>.zip` (при
совпадении секунды — суффикс `-2`), внутри `_system.db` и
`networks\<uuid>\data.db`; вложения не копируются. Хранятся три последних
архива, чужие файлы и каталоги в `backups` не трогаются. Копии баз снимаются
Online Backup API (`better-sqlite3`), поэтому WAL-хвост попадает в копию даже
без чекпойнта; каждая копия проходит `PRAGMA integrity_check`, битая —
отказ до замены файлов. Ротация, целостность и формат ZIP покрыты
`server/tests/db-backup.test.ts`; installer-тесты проверяют контракт вызова,
отчёт и коды.

Восстановление при откате — `restore --force` **только из архива этого
запуска** (`GLastBackupDir`), никогда из самого свежего архива прошлых
обновлений. `--force` допустим: служба уже остановлена вызывающим. Инструмент
до перезаписи проверяет ZIP и `integrity_check` всех баз, удаляет `-wal`/
`-shm` с проверкой и подменяет файлы через staged-копию; занятая БД без
`--force` — отказ. Ремонт той же версии, первая установка и adopt
(`686c5d76`) выполняются без бэкапа: прежней версии нет, данные установщик не
меняет.

## Обновление сервера: остановка службы, health-check и откат

Порядок фаз задан в `CurStepChanged(ssInstall)` — **до** копирования файлов
(задача `bb063ac3`): иначе занятые `node.exe`, `better-sqlite3` и файлы
сервера не заменить.

1. **Проверка личности службы.** Если ключ `HKLM\SYSTEM\CurrentControlSet\Services\ETN`
   есть, `ImagePath` должен указывать на `{app}\service\etn-service.exe`;
   `Start=4`, `DeleteFlag=1` или `status=NonExistent` при живом ключе —
   silent-код **20** до копирования файлов. Чужая/устаревшая служба не должна
   запускаться после замены файлов.
2. **Остановка службы.** Сначала `etn-service.exe status`. `Stopped` —
   `stop` не нужен; `Started` — `stop`, затем опрос `status` каждые 500 мс до
   `Stopped`; бюджет — 60 с по системным часам (не суммой шагов: один вызов
   `status` — отдельный процесс ~350 мс). WinSW 2.12.0 на `StartPending`
   возвращает 1061 — `stop` повторяется раз в секунду в пределах бюджета
   (StartPending мог перейти в Running); 1062 — не ошибка. `NonExistent` при
   живом ключе — несогласованное состояние, код **20**. Служба не
   остановилась — silent-код **20**, изменения не выполнялись.
3. **Бэкап БД** (см. раздел выше) — только при смене версии. Неудачный бэкап
   отменяет обновление до замены файлов: служба поднимается обратно, затем
   ограниченный health-check прежней версии; если она не отвечает — в причину
   дописывается «служба не запущена; запустите вручную (`etn-service.exe
   start`)», silent-код **10** (сценарий `bc7cc846`). Сообщение называет
   причину, требуемый объём (сумма `_system.db` и `networks\<uuid>\data.db`) и
   путь к журналу.
4. **Снимок отката** — `%ProgramData%\ETN\.install\rollback\<YYYYMMDD-HHmmss>\`
   с копиями каталогов `server` и `service` (данные не копируются: для них
   есть архив БД). Хранится только копия текущего запуска: при создании нового
   снимка прежние удаляются, после успешного обновления — все. При неудаче
   снимок остаётся точкой ручного восстановления до следующего успешного
   обновления. Неудачный снимок — код **10**, служба возвращается и
   проверяется так же, как после бэкапа.
5. **Замена файлов, настройка и регистрация службы, запуск** — как и раньше;
   уже зарегистрированная служба не перегистрируется (личность проверена до
   копирования), `start` не ждёт `RUNNING`: подтверждение — health-check.
   Сбой регистрации или `start` после копирования — код **10**.
6. **Health-check** — бюджет **60 с фактического времени** (не сумма `Sleep`:
   один запрос с `--max-time 5` может занять до 5 с, поэтому бюджет считается
   по системным часам, а пауза перед повтором не выходит за остаток), повтор
   каждые 2 с: один `GET /api/v1/health` → 200, `status:"ok"`, `db:"ok"`,
   `version` = целевая. Версия читается из тела того же ответа; отдельный
   `GET /api/v1/version` установщик не вызывает — эндпоинт остаётся для
   клиентов и диагностики. Поле `api` не проверяется: успешный
   `/api/v1/health` уже доказывает `api=v1`. Разбирается тело ответа, а не
   только HTTP-код (требование `0a79d9de`, задача `a1ea1d40`). В режиме `app`
   сервер установщик не запускает: health-check пропускается, обновление не
   уходит в откат.
7. **Успех** — сначала пишется `install.json` (иначе после отката файл врал бы
   о новой версии), и только после успешной записи удаляется снимок отката:
   сбой записи оставляет снимок и возвращает прежнюю версию.
8. **Неудача** — автоматический откат: служба останавливается (если не
   удалось — файлы и БД **не** восстанавливаются, снимок и архив остаются
   точкой ручного восстановления, причина и пути в журнале), каталоги
   `server` и `service` подменяются содержимым снимка целиком (файлов,
   которых не было в прежней версии — новых миграций, `dist\cli.js`, новых
   зависимостей — после отката нет), БД восстанавливается **только из архива
   этого запуска** (журналы `-wal`/`-shm` неудачного запуска удаляются).
   Архив прошлых обновлений (`LatestBackupDir`) в автоматическом откате не
   используется: он не отражает состояние базы на момент остановки службы.
   Архива в этом запуске не было (ремонт той же версии) — база остаётся как
   есть, об этом прямо сказано в журнале и сообщении. Затем прежняя версия
   запускается и проверяется health-check без требования целевой версии;
   если она не отвечает, это не маскируется — диагностика health и подсказка
   о ручном запуске службы (`ServiceStartManually`) дописываются в причину
   отказа и reason-файл, WARN остаётся в журнале (задача `a1ea1d40`).
   Silent-код **10**; в журнале — «Откат выполнен» либо «Откат не выполнен,
   архив: <путь>» с путями к архиву, снимку и журналу и прямым указанием, что
   записи, сделанные после остановки службы (создания архива), потеряны либо
   невосстановимы. Причина и итог отката перезаписываются в reason-файл:
   экран ошибки показывает их, а не только код 10.

**Почему бюджет вернулся с 120 до 60 с (`34f8e315` → `a1ea1d40`).** `34f8e315`
временно поднял бюджет health-check до 120 с, чтобы сохранить прежний
суммарный бюджет «ожидание `RUNNING` 60 с + health 60 с». В 0.15.3 требование
`0a79d9de` снова действует буквально: 60 с фактического времени. Health идёт
уже после `listen`, а миграция при обновлении касается только `_system.db`;
markdown-переиндексация при старте может занять больше — это отдельный риск,
и расширять бюджет здесь не следует.

Silent-коды обновления: `0` — успех (включая «уже актуально»), `20` —
предусловие не выполнено **до** замены файлов (занятый порт, режим `app` в
silent-самообновлении, служба не остановилась, чужая/отключённая/помеченная
на удаление служба, нет `ImagePath`/status), `10` — сбой выполнения (бэкап,
снимок, регистрация службы, запуск службы, health-check или сам откат; файлы
могли быть заменены). Сообщений `MsgBox` нет — только `SuppressibleMsgBox` и
журнал `%ProgramData%\ETN\logs\install-*.log`.

В тестовой сборке (`-DTestMode`) служба и health-check подменяются хуками
`/TESTSERVICE`, `/TESTSERVICECMD`, `/TESTSERVICESTATE`, `/TESTSERVICESTOP`,
`/TESTSERVICESTART`, `/TESTSERVICEWAIT`, `/TESTSERVICEINSTALL`,
`/TESTSERVICEUNINSTALL`, `/TESTSERVICEREALFILE`, `/TESTSERVICESTATUS`,
`/TESTSERVICEIMAGE`, `/TESTSERVICESTARTTYPE`, `/TESTSERVICEDELETEFLAG`,
`/TESTUNINSTALLSERVICE`, `/TESTHEALTHURL`, `/TESTHEALTHWAIT`,
`/TESTHEALTHSTEP`, `/TESTHEALTH`, `/TESTROLLBACK`, `/TESTNODEEXE`; все они
разбираются только под `#ifdef TestMode` и в продуктовую сборку не попадают.
Тестовая сборка вообще не трогает службы рабочей машины: без `/TESTSERVICE`
команды WinSW не выполняются. Модель: `status` возвращает
`Started`/`Stopped`/`NonExistent`; `/TESTSERVICESTATE=running|stopped` —
статическое состояние (команды его не меняют — проверка тайм-аута),
`/TESTSERVICESTOP=1061|1062` — переход/«уже остановлена»,
`1061` повторяется до успеха; `/TESTSERVICESTATUS=fail|garbage|nonexistent` —
ошибка/неизвестный вывод/NonExistent при живом ключе;
`/TESTSERVICEIMAGE`, `/TESTSERVICESTARTTYPE=4`, `/TESTSERVICEDELETEFLAG=1` —
подмена реестровой личности; `/TESTSERVICESTART=1056|1061` — коды старта;
`/TESTSERVICEUNINSTALL=1072` — uninstall с оставшимся ключом и подтверждением
через status; `/TESTSERVICEREALFILE=1` добавляет проверку наличия
`etn-service.exe`, как в продуктовой ветке (этим ловится неверный путь к
службе в деинсталляторе). Поведенческая матрица — `installer/tests/silent-codes.ps1`
(разделы `bb063ac3`, `8b1f5980` и `34f8e315`): порядок фаз, коды 10/20,
успешное обновление с сохранением данных и без `etn init`, один GET
`/api/v1/health` без второго `/version` и бюджет фактического времени (не
сумма `Sleep`), откат файлов точным составом снимка и БД только из архива
своего запуска, откат при неудачной остановке (файлы/БД не тронуты), ремонт
той же версии со старым архивом, режим `app`, неудачный бэкап с
подтверждением службы health-check-ом, неудачный откат с диагностикой health
прежней версии в причине, регистрация службы на чистой машине, повторная
установка (1073, в том числе при уже работающей службе), stop 1061/1062,
ошибка `status`, проверка личности службы до копирования, снятие при удалении
(status → stop → uninstall → подтверждение) и его отказы, `uninstall` 1072,
а также запуск **настоящего** деинсталлятора с моделью службы (отдельная
тестовая сборка с деинсталлятором и своим AppId).
