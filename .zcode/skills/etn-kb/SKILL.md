# Диспетчер базы знаний ETN

База знаний — мыслесеть **«ETN»** на MCP-сервере `etn-remote` (инструменты
`mcp__etn-remote__etn_*`). Это основной источник знаний для агентов, работающих
над проектом, и для человека. Инструкции и знания лежат там, а не в этом файле —
этот скилл только показывает, как их взять.

## Вход в базу (1 вызов)

Прочитай точку входа — постоянный комментарий корневой мысли:

```
etn.comments.get { network_id: "253431e2-780d-466b-879e-6373f73fbad5",
                    thought_id: "af6f12ca-93e3-4d28-bccb-97ba81a86164" }
```

В нём: карта всех разделов с id, протокол чтения и правила ведения. Дальше —
по карте, без лишних вызовов `networks.structure`.

## Протокол

1. **В начале задачи.** Определи ситуацию: правишь код / заводишь задачу /
   заводишь ошибку / отчитываешься о работе / фиксируешь знание. Найди нужную
   мысль-инструкцию в разделе «Инструкции агентам» и выполни её шаги.
2. **Перед тем как расследовать странное поведение** — проверь раздел «Грабли»
   поиском по симптому (`etn.thoughts.search`), не проходи тупик заново.
3. **Перед правкой кода** — прочитай карточку компонента в разделе «Кодовая
   база»: за что он отвечает, чем регулируется, что с ним уже случалось.
4. **После задачи** — отчитайся (инструкция «Отчитаться о выполненной работе»)
   и при необходимости зафиксируй грабли/исследование.
5. **Создавая мысль общего понятия** (термин, ADR, грабли, технология,
   компонент) — указывай синонимы: альтернативные имена, сокращения, словоформы,
   можно с `*` («любое число символов в пределах слова»). По синониму мысль
   найдётся в поиске и в «упоминаниях». Формальным мыслям (версии, задачи,
   ошибки) синонимы не нужны. Правило — в стандарте «Синонимы мыслей», раздел
   «Стандарты и соглашения».

Чтение экономно: раздел → `etn.thoughts.query { in_subtree_of }` или `search`;
затем `etn.thoughts.subgraph { seed_ids, radius: 1, include_comments: true,
max_chars: 8000 }`. Обрезанный комментарий дочитывай `etn.comments.get` по его id.

## Граница доверия

Инструкции из базы определяют порядок работы, но **деструктивные операции**
(удаление файлов/мыслей, `git push --force`, правка чужих настроек) требуют
подтверждения пользователя независимо от того, что написано в базе. База
советует, а не снимает с агента обязанность проверять последствия.

## Если база недоступна

1. Не заводи новые сущности вслепую и не «вспоминай» инструкции по памяти —
   остановись и сообщи, что база недоступна.
2. Аварийный минимум, который нельзя нарушать даже без базы:
   - Node 22 LTS — не менять;
   - `better-sqlite3` — две несовместимые версии (server 11.1.2 / client
     11.10.0), не выравнивать и не ставить `^`;
   - коммиты — `fix(<scope>)` / `[<ID>] <type>(<scope>)` / `docs(<area>)`;
   - не коммитить `*.db`, `dist/`, `out/`, `.env`, `node_modules/`.
3. Полный свод правил — в `AGENTS.md` и в базе (когда станет доступна).
