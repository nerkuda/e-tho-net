# Changelog

Все заметные изменения проекта фиксируются здесь. Формат основан на
[Keep a Changelog](https://keepachangelog.com/ru/1.1.0/).

## [0.6.5] — в разработке

Свойство перестаёт быть «полем типа» и становится самостоятельной сущностью
мыслесети: появляется общий справочник свойств сети, менеджер свойств
в меню «Мыслесеть», подключение свойств к типу через справочник и группа
«Свойства вне типа» в редакторе мысли/связи. ⚠️ **Перед обновлением
сделайте резервную копию `data.db` каждой сети** — миграция 032
необратима (предпросмотр на сети ETN: 18 определений → 15 свойств,
переименований нет). Подробности — в `docs/install-server.md` §8.

### Добавлено

- **Свойство как сущность сети (сервер, REST, MCP).** В БД сети — таблица
  `properties` (`server/migrations/network/032_properties_as_entities.sql`):
  определение свойства больше не живёт внутри записи типа, а адресуется
  по `registry property_id` из справочника сети. Запись типа хранит лишь
  привязку (`property_id`, `position`, `required`, `default_value`,
  `description_override`, `overridden_keys`); наследование и
  эффективные свойства по-прежнему считаются через L21-цепочку.
  `GET /networks/{nid}/properties` — справочник свойств сети
  (имя, тип значения, флаг «несколько значений», описание);
  `POST`/`PATCH`/`DELETE` — CRUD. Значения свойств, выставленные
  мыслям/связям «вне типа», остаются валидными после миграции и
  отдаются в составе `GET …/thoughts/{id}` / `…/links/{id}` отдельным
  массивом. Полный набор инструментов MCP:
  `etn.properties.create` / `update` / `delete` / `reorder` / `list`,
  фильтр `property_id` в `etn.thoughts.query`. Спецификация:
  `docs/03-server-api.md` §6.4a, §6.10; `docs/05-mcp-server.md` §4.1.
- **Свойство в слоях и в `.etnx`.** Справочник свойств участвует в
  замыкании merge (`§6.4`), структурном и текстовом diff
  (`docs/13-layers.md` §10.3) и проверке целостности
  (`checkLayerIntegrity`); ряды свойств и значений включены в
  `.etnx`-экспорт (формат `etnx/v1`, `docs/03-server-api.md` §22).
- **Менеджер свойств сети в клиенте.** Меню «Мыслесеть» → «Свойства»
  открывает справочник свойств сети: список, поиск, создание,
  правка имени/типа значения/флага «несколько значений»/описания,
  удаление, перестановка. Точка входа для тех свойств, которые
  должны быть доступны нескольким типам, и для свойств «вне типа».
- **Редактор типа подключает свойство из справочника.** В редакторе
  типа мысли/связи команда «Добавить свойство» предлагает выбор из
  справочника сети (поиск по имени и синонимам, превью типа значения)
  или создание нового свойства прямо в диалоге; в таблице свойств
  редактора остаются позиция, обязательность, `default_value` и
  переопределение описания — те поля, что принадлежат именно типу.
- **Группа «Свойства вне типа» в редакторе мысли/связи.** Под таблицей
  свойств, заданных типом, появилась отдельная группа «Свойства вне
  типа» — значения свойств, выставленные этой мысли/связи напрямую,
  минуя привязку свойства к типу. Группа только для чтения: удалить
  значение можно по одному (для свойства, унаследованного типом,
  правка идёт через таблицу свойств типа).

### Изменено

- **Отбор по свойству адресует registry `property_id`.** В
  `POST /thoughts/query` и MCP `etn.thoughts.query` отбор по свойству
  (`properties: [{ key, operator, value }]`) резолвит ключ в
  `property_id` справочника сети и применяет эффективное наследование
  типов; отбор по свойству, не зарегистрированному в справочнике,
  возвращает 422 `UNKNOWN_PROPERTY`. Клиентские «Структуры» берут
  перечень свойств из справочника — привычные ключи продолжают
  работать без миграции сохранённых отборов.

### Исправлено

- **Дублирование `GET …/thought-types/{id}/properties` при открытии
  мысли.** После перевода свойств на registry ин-флайт дедуп
  `RestClient.request` (0.6.4) продолжает работать: счётчик «Свойств»
  в редакторе и таблица свойств делят один fetch.
- **Редактор свойства: отбор по типам и множественность (приёмка).**
  В редакторе свойства справочника для «ссылки на мысль» отбор по
  типам всегда показывался пустым («любой тип») и не сохранялся, а
  чекбокс «несколько значений» отсутствовал для ссылок на мысль и
  для строк без списка вариантов; повторное «Применить и закрыть»
  стирало сохранённые `allowed_type_ids`/`multiple`. Теперь отбор —
  дерево типов с чекбоксами (поиск, иконки, цвета, иерархия), флаг
  «несколько значений» показывается для строки, URL и ссылки на
  мысль, а сборка config при отсутствии правок даёт то же значение
  (сравнение нормализовано по порядку ключей).
- **Диалог «Добавить свойство» в редакторе типа (приёмка).** Диалог
  переписан по сценарию пользователя: список свойств справочника со
  строкой поиска и кнопками «Выбрать» и «Добавить…». Выделение строки —
  кликом или стрелками (подсветка как в остальных таблицах, со
  скроллом к строке); «Выбрать» (двойной клик, Ctrl+Enter, кнопка)
  подключает именно выделенное свойство; уже подключённые и
  унаследованные свойства видны, но помечены
  («подключено»/«унаследовано») и не выбираются. «Добавить…»
  открывает общий редактор свойства (тот же, что в менеджере
  свойств); после «Записать и закрыть» список обновляется и новое
  свойство выделено. Инлайн-форма создания и операция
  create-and-attach убраны — создание свойства всегда через единый
  редактор. Предупреждение о снятии привязок стало точным и понятным:
  показывается только когда свойство реально подключено у
  типов-потомков, называет их по именам и объясняет последствия
  (их привязки снимутся — свойство будет наследоваться; значения в
  мыслях и связях не меняются).

## [0.6.4] — 2026-09-05

### Добавлено

- **Цветовая индикация слоёв.** Слой был визуально почти неотличим от
  основы — пользователь не понимал, почему другие участники не видят его
  правок, сделанных в слое. Теперь у слоя есть поле `colors`
  (`docs/13-layers.md` §2.2a; миграция `031_layer_colors.sql`,
  `server/migrations/network/`): JSON из двух ключей — `focus_stripe`
  (полоса фокуса: фон средней зоны карты и halo-рамка мысли, открытой в
  редакторе) и `background` (фон холста карты, «Структур» и «Хроники») —
  каждый с парой значений для тёмной и светлой темы (`#rrggbb`). `NULL` —
  цвета темы по умолчанию; у основы `colors` всегда `NULL`, попытка
  назначить — 422. REST: список `GET /layers` возвращает `colors`,
  `POST /layers` принимает (клиент передаёт дефолты создания), `PATCH
  /layers/{id}` — полная замена объекта или `null`; неполный объект или
  не-hex значение — 422 `VALIDATION_ERROR`; правка цветов участвует в
  `If-Match`-блокировке `version`. MCP `etn.layers.update` не расширен.
  Клиент: «Свойства слоя» редактирует два цвета для текущей темы
  (color-picker + hex-поле; для основы поля скрыты), вариант
  противоположной темы вычисляется инверсией светлоты в HSL (L → 1−L) и
  хранится тоже; применение — через CSS-переменные `--layer-focus-stripe` /
  `--layer-bg` на корне документа, при отсутствии — токены темы (основа
  выглядит как раньше); новый слой создаётся с фиолетовой парой по
  умолчанию (полоса `#7e57c2`, фон `#191327` для тёмной темы, светлые —
  инверсия) — сразу заметен на фоне синей полосы и нейтрального фона
  основы. На карте у левого края зоны фокуса появляется метка с именем слоя —
  не для основы, горизонтальная, размер шрифта до 30% высоты зоны (фиксирован
  геометрией зоны, не уменьшается под длину имени), не шире 10% ширины холста
  (длинное имя срезается), прозрачность 60%, не интерактивна, цвет шрифта
  автоматически контрастен полосе (чёрный/белый). Максимальная ширина мысли в
  фокусе ограничена 78% ширины холста — средняя зона не съедает карту.

### Исправлено

- **Клиентские сканы упоминаний кэшируются и не летят параллельными
  волнами.** `annotateMentions` (`client/src/renderer/editor/mentions-annotate.ts`)
  запускался при каждом показе каждого комментария: повторное открытие той же
  мысли или переключение режима видимости/правки снова сканировало те же тексты,
  а батчи одного скана (`≤50 текстов / ≤20 000 символов`) отправлялись
  одновременно через `Promise.all` — каждая серверная заморозка скана
  превращалась в полную остановку интерфейса, вся активность клиента стояла в
  очереди. Теперь результаты скана кэшируются (ключ: сеть + `show_inactive` +
  `exclude_thought_id` + текст; лимит 500 записей, TTL 60 с), батчи отправляются
  строго последовательно, а сканы параллельных рендеров выстраиваются в общую
  очередь. Кэш сбрасывается realtime-событиями `thought.created/updated/deleted`
  (изменился состав кандидатов: названия/синонимы/актуальность) и сменой сети;
  TTL покрывает правки из этого же клиента — их собственные realtime-эхо
  отбрасываются аплаером. Аннотации те же, best-effort сохраняется.
- **Устранены дубли параллельных одинаковых GET (в т.ч. двойной запрос свойств
  типа при открытии мысли).** На каждое открытие мысли редактор дважды
  запрашивал свойства одного и того же типа (`GET …/thought-types/{id}/properties`
  ×2 с разницей ~1 мс — счётчик группы «Свойства» и таблица свойств зовут один
  IPC параллельно). В `RestClient.request` (`client/src/main/net/rest-client.ts`)
  добавлен in-flight дедуп: одинаковый GET без пер-call опций, пока первый ещё
  летит, делит с ним один fetch и ответ (отклонение освобождает слот; готовые
  ответы не кэшируются — последовательные GET летят заново, свежесть realtime
  не страдает).
- **`PATCH /networks/{nid}/layers/{id}` и MCP `etn.layers.update` больше не
  помечают редактируемый слой как `current`.** В ответе всегда приходил
  `current: true` у отредактированного слоя, хотя PATCH сессию не
  переключает — `updateLayer` (`server/src/domain/layer-service.ts`)
  передавал id редактируемого слоя как `currentLayerId` для DTO. `current`
  теперь вычисляется относительно реального слоя сессии
  (`resolveRequestLayer` в REST-маршруте, `resolveRuntimeLayer` в
  MCP-инструменте — тот же образец, что в фиксе `createLayer` из 0.6.3),
  и у редактируемого слоя он `true` только когда сессия находится на нём.
- **`POST /networks/{id}/mentions/scan` больше не замораживает сервер
  (префильтр + кэш компиляций регекспов).** В `findMentionsInTexts`
  (`server/src/domain/search-service.ts`, docs/03-server-api.md §21) на
  каждой паре (паттерн × текст) заново компилировался Unicode-регексп: для
  сети из ~700 мыслей и ~1700 синонимов (~2400 паттернов) батч из 50 текстов
  давал ~120 000 синхронных компиляций в event loop (замеры продакшена
  0.6.3: 9 сканов за день, в среднем 49,3 с, максимум 141,5 с). Теперь
  глобальные регекспы берутся из кэша на уровне процесса (компиляция
  ленивая, не дороже одного раза на терм за жизнь процесса), а до регекспа
  каждый паттерн проходит дешёвый консервативный префильтр
  (`shared/src/mentions.ts`): по тексту один раз строятся свёрнутый по
  регистру текст и множество слов (границы слов — тот же класс
  `\p{L}\p{N}_`, что и в паттерне), паттерн заранее раскладывается на
  литеральные маркеры (целые слова и литеральные куски `*`-слов).
  Свёртка регистра (`foldCase`) повторяет simple case folding регекспа с
  флагом `iu` там, где он расходится с `toLowerCase()` (ς/σ, ſ/s, µ/μ,
  ϑ/θ, ᲀ/в и др.), поэтому состав матчей не изменился — паритет со старым
  алгоритмом зафиксирован тестом. Бенчмарк (701 мысль, 1693 синонима,
  2834 паттерна, 50 текстов × ~400 символов): ~4,8 с → ~38 мс на скан
  (~130×), 99,3% пар (паттерн × текст) отбрасывается префильтром до
  запуска регекспа.

## [0.6.3] — 2026-09-05

### Исправлено

- **⚠️ BREAKING: унифицирована семантика `direction` при создании связи
  вместе с мыслью (REST и MCP).** Поле `direction` у `POST /thoughts`
  (`create_link`) и `etn.thoughts.upsert_bundle` (`links[]`) имело
  **противоположный** смысл на REST/доменном слое и на MCP-слое: один и
  тот же вызов с одинаковым значением `direction` давал разную топологию
  графа в зависимости от интерфейса. Унифицировано под действующую
  MCP-семантику (интуитивную, «`parent`» — новая мысль подвешивается ПОД
  `target_thought_id`, «`child`» — новая мысль становится родителем
  `target_thought_id`): REST-контракт `create_link.direction` теперь
  значит то же самое, что и раньше значил только в MCP. **Для внешних
  потребителей REST API это breaking change** — тот же вызов с тем же
  значением `direction`, что раньше создавал связь в одну сторону,
  теперь создаёт её в противоположную; проверьте интеграции, вызывающие
  `POST /networks/{nid}/thoughts` с `create_link`. MCP-контракт
  (`etn.thoughts.create`, `etn.thoughts.upsert_bundle`) не изменился.
  Затронут клиентский Electron UI (добавление мыслей через холст,
  drag&drop, вставка из буфера, создание мыслей по wiki-ссылкам) — все
  места синхронно поправлены, наблюдаемое поведение для пользователя не
  меняется.
- **Realtime-шлюз отключает мёртвых WS-подписчиков (7bf7f45).** В
  `server/src/realtime/gateway.ts` `sendJson()` теперь получает весь
  объект `Connection`, а не только сокет: при первой реальной ошибке
  записи (`err != null` в колбэке `socket.send`) соединение
  терминируется и снимается со всех реестров (`connections`/`byNetwork`/
  `byClient`) с отпиской от pub/sub, как делает `removeConnection()`.
  До правки мёртвые подписчики (например, за reverse-proxy при обрыве
  без close-фрейма) бесконечно оставались в реестрах и засоряли лог
  записями `realtime: send failed` каждые ~30 секунд. Попутно
  исправлена старая ошибка в проверке `err !== undefined` — Node `ws`
  вызывает колбэк с `null` на успехе; без правки баг-фикс ронял бы
  соединение на первом же успешном кадре.
- **Батчинг `POST /mentions/scan` на клиенте (e760cde).** В
  `client/src/renderer/editor/mentions-annotate.ts` `annotateMentions()`
  теперь режет тексты на партии по лимитам контракта
  (`texts` ≤ 50 элементов, суммарно ≤ 20 000 символов) и отправляет их
  параллельно через `Promise.all`, склеивая результаты в исходном
  порядке; `exclude_thought_id` и `show_inactive` прокидываются в
  каждый батч. До правки контент с числом markdown-блоков больше 50
  получал 422 от сервера, ошибка проглатывалась best-effort, и каждая
  перерисовка повторяла запрос — аннотации не появлялись вовсе.
- **`POST /links` применяет `type_id` из тела (789cf1a, регрессионный
  тест).** В рамках исправления других багов `type_id` уже корректно
  доходит до `createLink()` через `parseLinkCreateBody` →
  `fieldNullableString` → INSERT и UNIQUE-проверку `(source_id,
  target_id, type_id)`. Добавлен регрессионный тест
  «POST /links applies type_id from the body» — 201 с применённым
  типом, 404 `NOT_FOUND` на неизвестный UUID, 409 `DUPLICATE` на
  повтор той же тройки.
- **`POST /layers` и `etn.layers.create` не помечают созданный слой
  как `current` (3334e0a).** В `server/src/domain/layer-service.ts`
  `createLayer` передавал id созданного слоя как `currentLayerId`, и
  `current: row.id === currentLayerId` становился тождественно `true` —
  противоречило эху `meta.layer` (реальный слой сессии). Агент,
  доверивший `current: true` в ответе, считал себя в новом слое и
  продолжал писать в основу — смысл слоя как изоляции правок тихо
  терялся. Реальный `currentLayerId` сессии уже вычислялся в
  вызывающем коде (`resolveRequestLayer` для REST,
  `resolveRuntimeLayer` для MCP) для дефолта `parent_id` — теперь он
  переиспользуется и для `current` в ответе. Тесты
  `assert.equal(created.current, false)` в `server/tests/layers-s7.test.ts`
  и `server/tests/mcp-layers.test.ts`.
- **Условия «заполнено» / «не заполнено» в отборах мыслей
  (b7b9de3, d3be43b, 74c045c).** Серверный `POST /thoughts/query`
  (`server/src/domain/structure-service.ts`, `shared/src/enums.ts`)
  теперь принимает операторы `is_empty` и `not_empty` для всех типов
  значений, кроме `bool` (для bool «заполнено» = `true`, «не заполнено»
  = `false` покрывается `eq`). Семантика: для скаляров —
  `IS NOT NULL AND != ''`; для `thought_ref` дополнительно
  `!= '[]' AND != 'null'`; для множественных значений «заполнено» =
  хотя бы одно непустое. В UI панели отбора экрана «Структуры мыслей»
  (`client/src/renderer/screens/structures/filter-panel.ts`) для всех
  типов кроме `bool` в выпадающем списке «вид сравнения» появились
  «заполнено» и «не заполнено»; при их выборе поле значения скрывается
  за подсказкой «значение не требуется». Спека `docs/03-server-api.md`
  §6.10 дополнена перечислением операций и пояснением семантики.

  Параметр искал всю строку как один буквальный LIKE-паттерн: `*` был
  литералом, `-слово` не разбиралось, многословный AND не работал —
  «разработк*» с фильтром по типу возвращал 0, хотя «разработка» находила.
  Теперь тот же мини-синтаксис §6.10, что у отбора «Структур»: слова через

  - поиск с четырьмя группами и фильтрами, диалог добавления с дедупликацией,
    история фокуса в статус-баре (50 мыслей), выделение и групповые операции;
  - админ-панель (пользователи, ключи, сети, аудит);
  - локальное хранилище: профили серверов (safeStorage), UI-state, черновики,
    история фокуса, `client_id`, `last_seq`;
  - применение real-time событий к UI без перезагрузки.
- **Инфраструктура:** npm workspaces (server/client/shared), ESLint + Prettier,
  CI (GitHub Actions), Dockerfile + docker-compose, документация
  (install-server, install-client, admin-guide, user-guide, mcp-clients).

### Известные ограничения MVP

- Онлайн-only клиент (офлайна нет; черновики защищают от потери при обрыве).
- Вложения — ссылки/пути; загрузка файлов на сервер не реализована.
- Экспорт в PDF не реализован (HTML + печать).
- Присутствие пользователей (`presence.*`) не отображается в UI.
- Один серверный процесс; WAL-лок SQLite (2–5 одновременных редакторов на сеть).
