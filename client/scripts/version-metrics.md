# version-metrics — метрики эффективности разработки версии

Скрипт `version-metrics.mjs` собирает метрики версии ETN по базе знаний
(`etn-remote`, REST) и git-истории: одна команда — числа для замера эффекта
реорганизации процесса (критерий «в следующей версии меньше переделок и
GUI-находок», ретро-исследование `c2ca8173`; задача `81a9a521`).

Зависимостей нет: только node builtins (global `fetch`, `node:child_process`),
Node 22 LTS. Ключ доступа в коде НЕ зашит и в отчёт не попадает.

## Запуск

```bash
# одна версия (тег, номер, id мысли-версии или git-диапазон)
node client/scripts/version-metrics.mjs v0.12.1
node client/scripts/version-metrics.mjs 30a10102-2c4b-4702-83f2-f6f220bedf1a --json .tmp/0.12.1.json

# сравнение двух версий (таблица метрика → A → B → Δ)
node client/scripts/version-metrics.mjs --compare v0.11.2 v0.12.1
node client/scripts/version-metrics.mjs --compare v0.11.2..v0.12.1 v0.12.1
```

Для git-диапазона берётся «предыдущий тег..тег версии» (например
`v0.11.2..v0.12.1`); каждый аргумент `--compare` — версия (тег, номер, id или
git-диапазон, ПРАВЫЙ конец которого задаёт версию для чтения базы).

### Доступ к базе

Адрес REST и ключ берутся (в порядке приоритета):

1. флаги `--base` / `--token`;
2. окружение `ETN_REMOTE_URL` / `ETN_REMOTE_TOKEN` (также `ETN_URL` / `ETN_TOKEN`);
3. MCP-конфиг ZCode с сервером `etn-remote`: `--config <файл>`, затем
   `.zcode/config.json` репозитория, `~/.zcode/cli/config.json`,
   `~/.zcode/config.json`. Из блока берётся `url` (без хвоста `/mcp`) и
   заголовок `Authorization: Bearer …`.

Репозиторийный `.zcode/config.json` содержит только полигон `etn-dev` — скрипт
его пропускает (ищет блок `etn-remote`) и доходит до пользовательских
конфигов; надёжнее всего для проектной базы — `--config` на конфиг с
`etn-remote` либо `ETN_REMOTE_URL` / `ETN_REMOTE_TOKEN`.

## Что и как считается

| Метрика | Источник | Правило |
| --- | --- | --- |
| Состав работ | REST `POST /thoughts/query` по свойству-связи «запланировано в версию» | активные + снятые с учёта; разбивка по типам (тех.проект / задача / ошибка) |
| fix:feat | `git log --format=%s <range>` | тип из Conventional Commits: `[<id>] type(scope): …`; двойной префикс `[a][b]` раскрывается |
| first-pass | хроно-комментарии задач | задача принята с первой сдачи, если ни один вердикт верификатора не содержит «не принято»; группировка — по ближайшему тех.проекту-родителю задачи |
| повторные делегации | хроно всех работ | есть запись «повторная делегация»/«повторно делегировать»/«уже исправлено(сделано, реализовано, закрыто, выполнено)» |
| пользовательские GUI-находки | постоянные комментарии ошибок | источник — пользователь: «найдено/сообщил/выявлено/обнаружено пользователем», «живая/визуальная проверка пользователя», «со слов пользователя», «запрос пользователя», «симптом (пользователь…» |
| длительность версии | мысль-версия + её свойства | от `created_at` до «Дата публикации», иначе до `updated_at` |

### Точность эвристик

Числа воспроизводимы, но эвристики (first-pass, повторные делегации,
пользовательские находки) — текстовые. Они ловят явные маркеры и НЕ ловят
переделки без формального вердикта «не принято». Это осознанное упрощение ради
стабильного сравнения версий. Смена формулировок в базе может сдвинуть числа —
тогда правится регулярка в `version-metrics.mjs`, а тесты (на реальных
снимках хроник в `client/tests/fixtures/version-metrics/`) покажут сдвиг.

Группировка first-pass по проектам: задача относится к ближайшему тех.проекту в
цепочке её структурных родителей. Задачи без проекта-родителя попадают в счётчик
`ungroupedTasks` и в общую долю не входят.

## Воспроизведение чисел ретро 0.12.1

Прогон на данных 0.12.1 (мыcль-версия `30a10102-…`, ретро `c2ca8173`):

| Метрика ретро | Ретро | Скрипт | Комментарий |
| --- | --- | --- | --- |
| Работ всего | ~209 | **209** (206 «Выполнено» + 3 актуальных) | совпадает точно |
| Коммитов | 255 | **255** | совпадает точно |
| fix | ≈150 | **154** | совпадает (двойные префиксы раскрыты) |
| feat | ≈45 | **59** | ретро недооценило |
| first-pass (общая доля) | ~65 % | **48/71 = 67.6 %** | в пределах 10 % |
| ошибок | ~60 | **127** | ретро недооценило (все 127 созданы 06–10.10) |
| пользовательские GUI-находки | — | **28** | новая метрика |
| повторные делегации | — | **4** | новая метрика |

First-pass по проектам (скрипт): «Команды редактирования» 7/16, «Трансклюзии»
8/13, «Манипуляции с выделением» 4/6, «Иконочная библиотека» 7/9, «Живой блок
трансклюзии» 6/8, «Дневник без псевдослота» 5/5, «Общие вложения» 11/14. Ретро
давало 12/21, 7/11, 5/7, 11/15 — там группы были сведены вручную (ТП0+ТП1 одной
строкой) и посчитаны приблизительно; общая доля (ключевой ориентир DoD) сходится.

**Расхождения >10 %.** `feat` 59 против ≈45 и ошибки 127 против ≈60 — обе оценки
ретро занижены: `feat` считается механически по типу коммита (ретро, видимо,
объединяло часть с повторными коммитами той же задачи), а «~60 ошибок» — грубая
оценка по хроникам (в базе все 127 ошибок типа «ошибка» привязаны к версии и
созданы в её окне). Скрипт даёт машинный, воспроизводимый счёт; расхождение —
артефакт ручного анализа, а не ошибка инструмента.

## Тесты

```bash
npm -w @etn/client test   # tests/version-metrics.test.ts
```

Фикстуры — снимки реальных данных сети ETN на момент ретро 0.12.1
(`client/tests/fixtures/version-metrics/`): subject'ы `git log`, хроники работ
(ТП «Общие вложения», выборка ошибок, отдельные работы), образец MCP-конфига
(ключ обезличен). Тела комментариев обрезаны (2500/5000 символов) — маркеры
эвристик стоят в начале текста/заголовке.

## Ограничения

- Требуется доступ к `etn-remote` (REST) и локальный git-репозиторий.
- Прогон делает много REST-запросов (работы версии + комментарии каждой работы
  + родители задач). Для крупной версии — минуты; результат можно сохранить в
  `--json` и сравнивать офлайн.
- Идентификаторы сети, типа «версия» и свойства «запланировано в версию» —
  константы сети ETN (переопределяются `--network` / `--link-property` и ENV).
