# version-metrics — метрики эффективности разработки версии

Скрипт `version-metrics.mjs` собирает метрики версии ETN по базе знаний
(`etn-remote`, REST) и git-истории: одна команда — числа для замера эффекта
реорганизации процесса (критерий «в следующей версии меньше переделок и
GUI-находок», ретро-исследование `c2ca8173`; задача `81a9a521`).

Зависимостей нет: только node builtins (global `fetch`, `node:child_process`),
Node 22 LTS. Ключ доступа в коде НЕ зашит и в отчёт не попадает.

## Запуск

```bash
# одна версия (тег, номер, id мысли-версии или git-диапазон)
node client/scripts/version-metrics.mjs v0.12.1
node client/scripts/version-metrics.mjs 30a10102-2c4b-4702-83f2-f6f220bedf1a --json .tmp/0.12.1.json

# сравнение двух версий (таблица метрика → A → B → Δ)
node client/scripts/version-metrics.mjs --compare v0.11.2 v0.12.1
node client/scripts/version-metrics.mjs --compare v0.11.2..v0.12.1 v0.12.1
```

Для git-диапазона берётся «предыдущий тег..тег версии» (например
`v0.11.2..v0.12.1`); каждый аргумент `--compare` — версия (тег, номер, id или
git-диапазон, ПРАВЫЙ конец которого задаёт версию для чтения базы).

### Доступ к базе

Адрес REST и ключ берутся (в порядке приоритета):

1. флаги `--base` / `--token`;
2. окружение `ETN_REMOTE_URL` / `ETN_REMOTE_TOKEN` (также `ETN_URL` / `ETN_TOKEN`);
3. MCP-конфиг ZCode с сервером `etn-remote`: `--config <файл>`, затем
   `.zcode/config.json` репозитория, `~/.zcode/cli/config.json`,
   `~/.zcode/config.json`. Из блока берётся `url` (без хвоста `/mcp`) и
   заголовок `Authorization: Bearer …`.

Репозиторийный `.zcode/config.json` содержит только полигон `etn-dev` — скрипт
его пропускает (ищет блок `etn-remote`) и доходит до пользовательских
конфигов; надёжнее всего для проектной базы — `--config` на конфиг с
`etn-remote` либо `ETN_REMOTE_URL` / `ETN_REMOTE_TOKEN`.

## Что и как считается

| Метрика | Источник | Правило |
| --- | --- | --- |
| Состав работ | REST `POST /thoughts/query` по свойству-связи «запланировано в версию» | активные + снятые с учёта; разбивка по типам (тех.проект / задача / ошибка) |
| fix:feat | `git log --format=%s <range>` | тип из Conventional Commits: `[<id>] type(scope): …`; двойной префикс `[a][b]` раскрывается |
| first-pass | хроно-комментарии задач | задача принята с первой сдачи, если ни один вердикт верификатора не содержит «не принято»; группировка — по ближайшему тех.проекту-родителю задачи |
| повторные делегации | хроно всех работ | есть запись «повторная делегация»/«повторно делегировать»/«уже исправлено(сделано, реализовано, закрыто, выполнено)» |
| пользовательские GUI-находки | постоянные комментарии ошибок (+ заголовок работы) | источник — пользователь/заказчик: «найдено/сообщил/выявлено/обнаружено пользователем», «живая/визуальная проверка пользователя», «со слов/запрос пользователя», «симптом (пользователь…», а также замечания визуальной проверки: «замечания заказчика», «по визуальной проверке», «заказчик требует/надоело»; «формулировки заказчика» — только вместе со «полировка» (в заголовке или тексте). Каждая находка делится на `polish`/`defect` по маркерам формулировок (см. ниже) |
| длительность версии | мысль-версия + её свойства | от `created_at` до «Дата публикации», иначе до `updated_at` |

### Точность эвристик

Числа воспроизводимы, но эвристики (first-pass, повторные делегации,
пользовательские находки) — текстовые. Они ловят явные маркеры и НЕ ловят
переделки без формального вердикта «не принято». Это осознанное упрощение ради
стабильного сравнения версий. Смена формулировок в базе может сдвинуть числа —
тогда правится регулярка в `version-metrics.mjs`, а тесты (на реальных
снимках хроник в `client/tests/fixtures/version-metrics/`) покажут сдвиг.

### Эвристика пользовательских GUI-находок (ревизия 0.13.2)

До 0.13.2 метрика искала только «пользовательские» формулировки и на 0.13.1
дала 1 находку, тогда как визуальные замечания оформлялись карточками
«полировка по визуальной проверке» с маркерами «замечания/формулировки
заказчика», «заказчик ТРЕБУЕТ», «заказчику надоело» (ретро 0.13.1, 017c73f7).
В 0.13.2 маркеры расширены (задача 92674032):

| Семейство | Маркеры |
| --- | --- |
| пользователь | «найдено/сообщил/выявлено/обнаружено пользователем», «живая/визуальная проверка пользователя», «со слов пользователя», «запрос пользователя», «симптом (пользователь…», «пользователь сообщил» |
| заказчик / визуальная проверка | «замечания заказчика», «по визуальной проверке», «заказчик требует», «заказчику надоело»; «формулировки заказчика» — уточняющий маркер: считается только в карточке, явно помеченной «полировка» (в заголовке работы или тексте комментария) |

Проверка на реальных данных (2026-10-18): 0.13.1 — 6 полировочных карточек
(4258e694, f4e99090, 696b3c3b, 609deba0, 50d9bf4e, 23c7d3e9) + a1100e0c
(«со слов пользователя») = **7** (было 1); 0.12.1 — **28**, число не
изменилось: его находки сформулированы «пользовательскими» маркерами, новые
маркеры их не пересчитывают. Эталонный снимок —
`client/tests/fixtures/version-metrics/polish-0.13.1.json`; юнит-тест
закрепляет 7 находок и проверяет каждый новый маркер отдельно.

Точность и полнота. Маркеры «по визуальной проверке»/«формулировки
заказчика» могут встретиться в цитате или описании процесса, а не в симптоме —
тогда карточка засчитается ложно. Поэтому «формулировки заказчика» — не
самостоятельный маркер: в 0.13.1 он есть и в раннем визуальном аудите 498876c4
(13.10, «Пользователь (заказчик) осмотрел…»), который не входит в перечень
6 полировочных карточек; самостоятельный счёт дал бы 8, а не 7. Решение
метрики (задача 92674032): маркер учитывается только в карточке с
«полировкой». Классические маркеры определяют источник, а «заказчиковые» —
происхождение замечаний; для ретро 0.13.1 это дало полное покрытие 6/6
полировочных карточек. Замечания без словесного маркера (например, просто
«поправить кнопку») эвристика не ловит — осознанное упрощение ради
воспроизводимости.

**Правило ревизии метрики.** Расширение маркеров меняет числа прошлых версий,
если их тексты содержат новые маркеры. Ревизия фиксируется здесь и в хроно
задачи; число прошлой версии пересчитывается только осознанно — иначе
сравнение версий теряет сопоставимость. На 0.13.2: 0.12.1 осталось 28,
0.13.1 — 7 (обе цифры воспроизводимы одним прогоном).

### Разбиение находок: полировка и дефект (ревизия 0.13.2, задача 3e30f200)

Решение пользователя 2026-10-19: полировки неизбежны (цвет, фокус, надпись —
многое видно только на практике), а реальные ошибки агента (игнорирование
требований, отход от сценария, домысливание) — главный показатель. Итоговый
счётчик сохранён, но раскрыт: `userGuiFindings = { total, polish, defect }`,
плюс `userGuiPolishIds` / `userGuiDefectIds` (JSON и `--compare`).

| Класс | Маркеры в заголовке работы и постоянном комментарии |
| --- | --- |
| `polish` (доводка) | «полировка», «стало лучше/удобней», «переименовать», «компактнее», «перенести», «убрать кнопку/строку», «порядок пар», «вместо id», «помещается / не помещается», «ширина» (в связке с UI-объектом: колонка, строка, поле, панель, диалог, таблица, меню, кнопка, чип, редактор, элемент), «тултип» |
| `defect` (ошибка агента) | «ОШИБКА» и «КРИТИЧНО» (только капсом), «не работает», «падает/роняет», «теряется», «не совпадает с», «нарушает требование/ADR», «пустой результат» |

Правило классификации: маркер дефекта важнее — карточка со смешанным составом
(есть и полировочная, и дефектная лексика) считается `defect`; иначе маркер
полировки → `polish`; ни одного маркера → `defect` (сомнительная находка не
раздувает полировки).

**Границы эвристики (осознанные упрощения).**

- «Смешанный состав» — не редкость: карточки «полировка по визуальной проверке»
  содержат пункты, помеченные «ОШИБКА:»/«КРИТИЧНО». Поэтому из 6 полировочных
  карточек 0.13.1 в `polish` попала только 4258e694; f4e99090, 696b3c3b,
  609deba0, 50d9bf4e, 23c7d3e9 — `defect` (в них есть дефектные пункты), как и
  требуют правила. Спорный пример смешанного аудита — 498876c4 (полировочная
  лексика + пункт 15 «ОШИБКА»): `defect`; в счёт находок он не входит
  (задача 92674032: «формулировки заказчика» без «полировки» не считаются).
  Снимок — `client/tests/fixtures/version-metrics/mixed-498876c4.json`.
- «ОШИБКА» и «КРИТИЧНО» сравниваются с учётом регистра: строчное «ошибка» —
  обычное слово в тексте карточки и маркером не является.
- «Ширина» учитывается только в связке с UI-объектом: техническое «outline
  уходил за границы из-за ширины блока» — не полировка (реальный дефект
  39553204 остаётся дефектом).
- «Тултип» — самостоятельный маркер: карточка, где дефект исправляется в том
  числе тултипом, без дефектной лексики уйдёт в `polish` (пример 0.12.1:
  de14e6d2 — кнопка «Редактировать» и тултип). Это принятая цена простоты.
- Находка без словесных маркеров класса (просто «поправить кнопку») — `defect`
  консервативно; полнота эвристики ограничена формулировками в базе.

**Числа (прогон 2026-10-19, `--compare v0.12.1 v0.13.1`).** 0.12.1: 28 =
полировка 1 (de14e6d2) + дефект 27; 0.13.1: 7 = полировка 1 (4258e694) +
дефект 6. Разбиение воспроизводимо: те же id при повторном прогоне; фикстуры
`polish-0.13.1.json` (1/6) и `mixed-498876c4.json` его закрепляют.

Группировка first-pass по проектам: задача относится к ближайшему тех.проекту в
цепочке её структурных родителей. Задачи без проекта-родителя попадают в счётчик
`ungroupedTasks` и в общую долю не входят.

First-pass по проектам (скрипт): «Команды редактирования» 7/16, «Трансклюзии»
8/13, «Манипуляции с выделением» 4/6, «Иконочная библиотека» 7/9, «Живой блок

давало 12/21, 7/11, 5/7, 11/15 — там группы были сведены вручную (ТП0+ТП1 одной
строкой) и посчитаны приблизительно; общая доля (ключевой ориентир DoD) сходится.

**Расхождения >10 %.** `feat` 59 против ≈45 и ошибки 127 против ≈60 — обе оценки
ретро занижены: `feat` считается механически по типу коммита (ретро, видимо,
объединяло часть с повторными коммитами той же задачи), а «~60 ошибок» — грубая
оценка по хроникам (в базе все 127 ошибок типа «ошибка» привязаны к версии и
созданы в её окне). Скрипт даёт машинный, воспроизводимый счёт; расхождение —
артефакт ручного анализа, а не ошибка инструмента.

## Тесты

```bash
npm -w @etn/client test   # tests/version-metrics.test.ts
```

Фикстуры — снимки реальных данных сети ETN (`client/tests/fixtures/version-metrics/`):
subject'ы `git log`, хроники работ (ТП «Общие вложения», выборка ошибок,
отдельные работы), 7 эталонов эвристики замечаний заказчика
(`polish-0.13.1.json`), спорный смешанный аудит (`mixed-498876c4.json`),
образец MCP-конфига (ключ обезличен). Тела комментариев обрезаны
(2500/5000 символов) — маркеры эвристик стоят в начале текста/заголовке.

## Ограничения

- Требуется доступ к `etn-remote` (REST) и локальный git-репозиторий.
- Прогон делает много REST-запросов (работы версии + комментарии каждой работы
  + родители задач). Для крупной версии — минуты; результат можно сохранить в
  `--json` и сравнивать офлайн.
- Идентификаторы сети, типа «версия» и свойства «запланировано в версию» —
  константы сети ETN (переопределяются `--network` / `--link-property` и ENV).
