# GUI-стенд клиента ETN (`client/scripts/ui-probe*`)

Штатный инструмент GUI-проверки клиента без видимого окна: подключается к
клиенту по Chrome DevTools Protocol (CDP), прогоняет JSON-сценарий и отдаёт
ТЕКСТОВЫЙ отчёт «шаг → проба → факт/ожидание». Модель проверяет поведение
пробы и чтения БД, а не картинки: PNG сохраняется только как доказательство
найденной ошибки.

Инструмент — **платформа**, а не набор зашитых проверок: сценарии пишутся под
задачу и поставляются вместе с работой. Единственный встроенный сценарий —
эталонный smoke (см. ниже), он же образец.

## Состав

## Быстрый старт (одна команда)

```bash
# собрать сервер и клиент один раз
npm -w @etn/server run build
npm -w @etn/client run build
npm -w @etn/client run rebuild:native   # один раз после npm install

# эталонная самопроверка стенда (подключение → мысль → правка комментария →
# форматирование → сохранение → контроль в БД стенда)
node client/scripts/ui-probe-stand.mjs --scenario client/scripts/ui-probe.smoke.scenario.json
```

Команда сама: готовит изолированный каталог данных и инициализирует сервер,
засеивает пробную сеть, поднимает скрытый клиент с изолированным профилем,
прогоняет сценарий, проверяет эффект по REST и гасит стенд (включая дерево
процессов Electron). Код возврата — код прогона (0 — все шаги сошлись).

Интерактивный режим (стенд живёт до Ctrl+C, печатает готовую команду прогона):

```bash
node client/scripts/ui-probe-stand.mjs            # свежая база + сид
node client/scripts/ui-probe-stand.mjs --data-from C:/zSpace/ETN_data --api-key etn_…
```

### Язык интерфейса (`ru`/`en`/`zh`, профиль и наследование)

С 0.15.2 (ADR `daab6ac4`, задачи faba9ff4 и 222666db) «язык приложения» живёт
в профиле пользователя на сервере, а `client_meta.lang` — только кэш для
офлайн-старта. Пользовательский путь — «Все настройки → Клиент → язык
приложения»; при доступном сервере там «использовать язык сетей» или
конкретный каталог, значение сохраняется в профиль и применяется на лету.
Язык сети меняется в «Все настройки → Мыслесеть → Язык сети» (владелец/админ),
язык сервера — во вкладке «Сервер» админ-панели.

Три сценария покрывают модель целиком (production-сборка, сервер по умолчанию
`en`; язык ОС на стенде может быть любым):

```bash
node client/scripts/ui-probe-stand.mjs \
  --scenario client/scripts/ui-probe.222666db-language-ui.scenario.json
node client/scripts/ui-probe-stand.mjs \
  --scenario client/scripts/ui-probe.faba9ff4-language-migration.scenario.json --keep
node client/scripts/ui-probe-stand.mjs \
  --scenario client/scripts/ui-probe.faba9ff4-language-second-client.scenario.json \
  --data-from <work миграции>/data --api-key <ключ миграции> --no-seed
```

Первый проверяет живое переключение на всех уровнях (профиль, сеть, сервер),
включая WS-кадр от «второго клиента» и деградацию недоступного каталога;
второй — разовую миграцию локального кэша в профиль и приоритет профиля над
кэшем; третий — что новый профиль клиента получает язык из профиля при входе.
Переходы ru↔en↔zh на конкретных экранах и полноту каталогов проверяют
сценарии d08c422d (en) и f7dba88c (zh) — они тоже ходят через «Все настройки →
Клиент».

Режим `test` нужен только сценариям, которым мало production-каталогов
(фикстура `zz` с узнаваемыми подписями):

```bash
npm -w @etn/client run build -- --mode test
node client/scripts/ui-probe-stand.mjs \
  --scenario client/scripts/ui-probe.e6374cd1-i18n-live.scenario.json
```

В тестовой сборке `app.ts` регистрирует фикстуру `lib/locales/test.ts` (код
`zz`, несколько узнаваемых подписей); в production-сборке ветка статически
ложна, и фикстура в бандл не попадает. После прогона верни обычную сборку
(`npm -w @etn/client run build`).

### Фикстура данных сценария (`--scenario-seed`)

Если сценарию нужны данные сверх пробной сети (например, 12 рёбер одной пары),
передай скрипт фикстуры — стенд запустит его ПОСЛЕ засева и ДО сценария, сам
подставив `--data-dir`, `--network-id`, `--center-id`, `--api`, `--api-key`:

```bash
node client/scripts/ui-probe-stand.mjs \
  --scenario client/scripts/ui-probe.42a7c0a1-mass-links.scenario.json \
  --scenario-seed client/scripts/ui-probe.42a7c0a1-seed.mjs
```

Дополнительные аргументы фикстуры — повторяемый `--scenario-seed-arg <значение>`
(например, `--scenario-seed-arg --trash --scenario-seed-arg 1`). Ненулевой код
фикстуры останавливает прогон; с `--no-seed` опция несовместима. Фикстура
обязана быть идемпотентной: повторный запуск на том же стенде не должен менять
данные — иначе ожидания сценария разъедутся.

## Сценарий

Формат — JSON-объект `{ name?, description?, timeout?, steps: [...] }`. Каждый
шаг — ровно одно действие (+ необязательные `name`, `timeout`, `expect`,
`expectFrom`). В строках работают подстановки `{{имя}}`; значения задаёт раннер
через `--var имя=значение` (стенд подставляет адрес, API-key и id засеянных
сущностей).

Ожидание у шагов `probe`/`api` задаётся одним из двух (взаимоисключающе):
`expect` — литерал, либо `expectFrom` — **снимок** значения, прочитанного
ранее выполненным шагом `probe`/`api`. Ссылка идёт по имени ШАГА — полю `name`
уровня шага (`api.name`/`probe.name` внутри действия — только метка записи в
отчёте); имя шага необязательно, по умолчанию это `<номер>:<вид>`
(например `"3:probe"`), и автоимя тоже годится как ссылка. Оба поля —
**соседи действия**, то есть лежат в объекте ШАГА рядом с `probe`/`api`, а не
внутри этого объекта: `{ "probe": "…", "expect": true }` — верно,
`{ "probe": { "expression": "…", "expect": true } }` — ошибка валидации
(неизвестное поле `probe.expect`).

Снимок делает сценарий самопроверяемым: «после равно до» без зашитого списка
(например, паритет заголовков разделов до и после правки рецепта — сценарий
`ui-probe.publication-recipe.scenario.json`).

| Действие | Вид | Назначение |
| --- | --- | --- |
| `key` | `{ "key": "ArrowDown", "modifiers": ["shift"] }` | клавиши/сочетания (CDP `Input.dispatchKeyEvent`) |
| `click` | `"#sel"` \| `{ "selector": "#sel", "at": [4,4] }` \| `[640,400]` \| `{ "x":10, "y":20 }` \| `{ "selector": "#sel", "count": 2 }` \| `{ "selector": ".canvas", "at": [300,40], "allowMismatch": true }` | клик по элементу/координатам (CDP); `count: 2` — двойной клик (`click.detail >= 2`); точка сверяется с целью (см. «Проверка точки ввода»), промах валит шаг, `allowMismatch` — явное исключение |
| `hover` | та же форма точки, что у `click`, БЕЗ `count`/`allowMismatch` | навести курсор БЕЗ клика (`mouseMoved`) — включает CSS `:hover`; точка наведения сверяется с целью, промах валит шаг без отправки события |
| `drag` | `{ "from": "#handle", "to": { "selector": "#row", "at": [10,2] }, "expect": "#row", "steps": 8, "duration": 120, "modifiers": ["shift"] }` | составной жест: сверка `from`, pointerdown в `from`, `steps` промежуточных `mouseMoved`, ожидание попадания в `expect`, pointerup в `to`. `expect` обязателен — промах координат ПРОВАЛИВАЕТ шаг (грабли `7c521541`), ожидание — по условию `elementFromPoint` (грабли `03e33360`); промах `from` — шаг падает без нажатия и перемещений |
| `text` | `"строка"` | ввод текста (CDP `Input.insertText`) |
| `waitFor` | `"expr"` \| `{ "expression": "…", "frames": 2 }` \| `2` | ожидание по условию; кадровые ожидания — только при активном окне |
| `probe` | `"expr"` \| `{ "name": "rows", "expression": "…" }` | прочитать значение, записать в отчёт и в снимок под именем ШАГА (для `expectFrom`); `expect`/`expectFrom` — сверка «факт/ожидание» |
| `eval` | `"expr"` | побочное действие без записи значения |
| `shot` | `"01.png"` \| `{ "file": "01.png", "clip": "#sel" }` | PNG (только доказательство ошибки) |
| `assert` | см. ниже | растровый ассерт: кроп + проверки, результат текстом |
| `api` | см. ниже | HTTP-запрос к серверу стенда ИЗ РАННЕРА (проверка эффекта/БД) |

### Проверка точки ввода (`click`, `hover`, `drag.from`)

Точка, которую шаг получил по селектору (`selector` + необязательный `at`),
сверяется с целью НЕПОСРЕДСТВЕННО перед отправкой события: `document
.elementFromPoint(x, y)` и `closest(selector)`. Прямоугольник элемента и
событие разнесены по времени (hover, постановка кадра), и за это время разметка
может сдвинуться — первый рендер холодного клиента, загрузка картинки, смена
размера окна. Событие в устаревшую точку браузер доставит соседнему элементу,
и действие молча пропадёт (симптом `af96d388`: таймаут следующего `waitFor` без
единого запроса на сервере; грабли `7c521541`).

- При промахе точка перемеряется (до 4 раз, сдвиг разметки), результат виден в
  отчёте: `[точка x,y, перемер N]`.
- Попадания нет и после перемеров — **шаг падает**, событие НЕ отправляется:
  для `click` — ни нажатия, для `hover` — ни `mouseMoved`, для `drag.from` —
  ни нажатия, ни перемещений. В отчёте: `— ПРОМАХ: <элемент под указателем>`.
- Точечное исключение есть только у `click`: `allowMismatch: true` (только
  вместе с `selector`) разрешает нажать в точку вне элемента-якоря (особая
  точка холста, смещение за границы) — в отчёте это `— ПРОМАХ (разрешён
  allowMismatch)`. У `hover` и точек `drag` флага нет: наведение и захват
  обязаны попадать в свой элемент (холст наводится на сам элемент холста),
  промах там — дефект сценария или разметки.
- Без `selector` (чистые координаты `[x,y]` или `{x,y}`) сверять нечего —
  событие отправляется как задано.

### Прогрев клиента и `--cold-start` / `--no-warmup`

Перед первым шагом раннер по умолчанию ждёт готовности приложения: документ
`complete` и в `#app` появился экранный корень (`#app > .screen` онбординг/список
сетей либо `#app > .workspace` рабочее пространство — все корни, которые стенд
встречает после сценариев). Это снимает гонку с первым рендером холодного
клиента, которого стенд поднимает заново на каждый прогон.

- `--cold-start` — прогон помечается холодным (стенд ставит флаг всегда).
  Подсказка «холодный старт» добавляется к тексту таймаутов только при
  ДОКАЗАННОМ медленном старте: прогрев занял больше порога (1 с) или сам
  прогрев не дождался экрана. При быстром прогреве условие падает по своей
  причине, и подсказка не подмешивается.
- `--no-warmup` — не ждать готовности (и не измерять старт). В этом режиме
  подсказка «холодный старт» НЕ добавляется: причина таймаута не измерена,
  недоказанная гипотеза в текст не кладётся.

Время прогрева попадает в отчёт строкой `прогрев: клиент готов за N мс`
(или `прогрев: отключён (--no-warmup)`) — по нему видно, был ли старт медленным.

### Растровые ассерты (`assert`)

```json
{
  "assert": {
    "name": "focus-cloud",
    "region": ".canvas-focus-row .cloud",
    "checks": [
      { "kind": "notBlank", "minRatio": 0.05 },
      { "kind": "distinct", "minColors": 3 },
      { "kind": "hasColor", "color": "#1b1b1b", "tolerance": 24, "minPixels": 10 },
      { "kind": "colorAt", "at": [4, 4], "color": "#ffffff", "tolerance": 8 }
    ],
    "evidence": false
  }
}
```

`region` — селектор | `[x,y,w,h]` | `{x,y,width,height}`. Проверки:
`notBlank` (доля пикселей, отличных от фонового), `colorAt` (цвет пикселя по
смещению), `hasColor` (число пикселей нужного цвета), `distinct` (число
различимых цветов). PNG пишется только при `evidence: true`.

### Проверки на сервере (`api`)

```json
{
  "api": {
    "name": "comment-in-db",
    "method": "GET",
    "path": "/networks/{{networkId}}/thoughts/{{thoughtId}}/comments",
    "expression": "data.find((c) => c.kind === 'permanent').body_md"
  },
  "expect": "**текст**"
}
```

Обёртка `data` ответа разворачивается; `expression` вычисляется от неё;
`expect` (мета) — ожидаемое значение, его можно заменить снимком `expectFrom`
— тогда сверяется значение `expression`, а не тело ответа целиком (см.
«Самопроверка „до ↔ после“»). Так проверяется эффект ИМЕННО на
сервере/в БД: CDP страницы не видит HTTP main-процесса Electron (грабли
`aa5cf162`).

Необязательное поле `body` (объект) шлёт JSON-тело запроса — сценарий может
не только проверять эффект, но и ЗАСЕИВАТЬ данные перед прогоном (например,
POST дневниковой записи). Пример — `ui-probe.diary-create-thought.scenario.json`.

### Самопроверка «до ↔ после» (`expectFrom`)

Ожидание можно не зашивать, а взять из снимка, снятого ранее тем же сценарием:
шаг `probe`/`api` сохраняет своё значение и кладёт его в снимки прогона
(`context.values`) под именем ШАГА, а последующий шаг с
`"expectFrom": "<имя шага>"` сверяется с ним. Так проверяется паритет результата
до и после правки:

```json
{ "name": "headings-before",
  "api": { "name": "headings-before", "method": "GET",
           "path": "/networks/{{networkId}}/publications/{{pubId}}/assembly",
           "expression": "data.sections.map((s) => s.heading)" } },
{ "name": "headings-after",
  "api": { "name": "headings-after", "method": "GET",
           "path": "/networks/{{networkId}}/publications/{{pubId}}/assembly",
           "expression": "data.sections.map((s) => s.heading)" },
  "expectFrom": "headings-before" }
```

Живой образец — `ui-probe.publication-recipe.scenario.json`.

**Ссылка — по имени ШАГА.** Ключ снимка — поле `name` объекта ШАГА (сосед
действия). Внутренние `api.name`/`probe.name` — только метка записи в отчёте:
по ним `expectFrom` не ищет. В примере выше имена совпали ради читаемости, но
это не обязательно — скажем, шаг `"name": "before"` с
`"api": { "name": "assembly-before", … }` ссылается как `"before"`, а не
`"assembly-before"`.

Имя шага необязательно: по умолчанию шаг получает автоимя `<номер>:<вид>`
(`"1:probe"`, `"3:probe"`, `"2:api"`; номер — позиция шага в `steps`, счёт
с 1), и автоимя допустимо как ссылка — именовать шаг не требуется:

```json
{ "probe": "document.querySelectorAll('.row').length" },
{ "probe": "document.querySelectorAll('.row').length",
  "expectFrom": "1:probe" }
```

У `probe`/`api` есть ещё собственные имена по умолчанию внутри действия —
`probe<N>` и `api<N>`; это метки отчёта, к `expectFrom` отношения не имеют.

**Что снимается.** `probe` — значение выражения. `api` — значение поля
`expression`, вычисленное от развёрнутого `data` ответа, а НЕ тело ответа
целиком; `api` без `expression` снимает весь `data`.

**Как сверяется.** Сравнение глубокое, через каноническую сериализацию
(`stableStringify`, `client/scripts/ui-probe.mjs`): порядок ключей объекта не
важен (`{a,b}` ≡ `{b,a}`), порядок элементов массива важен (`[1,2]` ≠ `[2,1]`),
типы строгие (`1` ≠ `"1"`, `true` ≠ `"true"`), `null` ≠ отсутствующее поле.
Совпало — шаг `ok`; расхождение валит шаг текстом
`проба «<probe.name>»: факт <…> ≠ ожидание <…>` (у `api` — `api «<api.name>»: …`).
В отчёте значения для читаемости обрезаются до 160 символов — сравнение идёт по
полным значениям.

**Ограничения.**

- Только у шагов `probe`/`api`; у остальных действий — ошибка разбора:
  `шаг N: поле «expectFrom» допустимо только у шагов probe и api`.
- `expect` и `expectFrom` взаимоисключающи:
  `шаг N: «expect» и «expectFrom» взаимоисключающи — задайте одно`.
- Ссылка на самого себя запрещена: значение кладётся в снимки ДО сверки, и шаг
  сверялся бы с собственным значением. Ошибка разбора:
  `шаг N: «expectFrom» ссылается на сам шаг «<имя>» — сравнение стало бы
  тавтологичным (шаг сверяется с собственным значением)`.
- Ссылка вперёд и ссылка на несуществующее имя — НЕ ошибка разбора (парсер не
  знает, выполнится ли шаг), а ошибка шага при прогоне:
  `шаг «<имя>»: expectFrom ссылается на шаг «<ссылка>» — его значения нет (шаг
  не выполнен или не probe/api)`.

**Признак в отчёте.** У сверки со снимком рядом с ожиданием стоит
`— снимок шага «<имя>»`, например:

```text
ok    2 probe   2:probe probe2 = "ETN" (ожидание "ETN" — снимок шага «1:probe») (1 мс)
ok    2 api     2:api thought-title-again GET /networks/… = "Проба стенда" (ожидание "Проба стенда" — снимок шага «1:api») (11 мс)
```

Строки — из реального вывода прогона (путь у `api` сокращён). В них видно и
разделение имён: шаг `2:api` — автоимя шага, `thought-title-again` — метка
действия; и то, что `api` печатает перед ожиданием метод и путь.

Без `expectFrom` (литерал `expect`) пометки нет, а шаг без ожидания даёт только
факт.

### Затравка markdown-поля (CodeMirror) — только через API

Текст в markdown-поле (постоянный комментарий, тело записи) сценарий заводит
**шагом `api`**, а НЕ «печатью» в редактор. CodeMirror 6 живёт на собственной
транзакционной модели: ни CDP `Input.insertText` (шаг `text`), ни синтетические
`paste`/`beforeinput`/`ClipboardEvent` её не меняют — DOM может измениться, а
состояние редактора НЕТ: сохранение не уходит, в БД остаётся старый текст, и все
последующие пробы читают прежний контент (грабли `4c035087`). Клавиатурные
сочетания при этом работают (шаг `key` с `modifiers`) — не работает только набор
текста.

Рецепт самодостаточного сценария (без `--seed-comment`):

```json
{ "name": "seed-comment-api",
  "api": { "name": "seededComment", "method": "POST",
           "path": "/networks/{{networkId}}/thoughts/{{homeId}}/comments",
           "body": { "kind": "permanent", "body_md": "…исходник с URL…" },
           "expression": "data.kind" },
  "expect": "permanent" }
```

Дальше — открыть владельца (`click` по `[data-id="{{homeId}}"].cloud` для
корневой мысли), поле покажет заведённый текст.

- Постоянный комментарий заводится только там, где его ещё НЕТ (иначе
  `DUPLICATE`): у корневой мысли HOME своего комментария нет — удобный владелец.
- Альтернатива — `--seed-comment` стенда (тот же путь через REST), но тогда
  сценарий несамодостаточен: без флага прогон разваливается.
- Пробы, читающие DOM, снимай после стабилизации (образец — установленный
  `window.__poll` в `ui-probe.comment-autolink-37458cbc.scenario.json`): сразу
  после записи поле перерисовывается realtime-событием, и проба может поймать
  промежуточный DOM.

## Управляемая сетевая среда: задержки, отказы, подавление realtime

Флаги стенда (полный список — `node client/scripts/ui-probe-stand.mjs --help`)
поднимают между скрытым клиентом и сервером прокси `ui-probe-delay-proxy.mjs`.
Через прокси идёт HTTP-трафик клиента и его WebSocket; шаги `api` сценария
ходят на сервер НАПРЯМУЮ (их задержка не касается). Прокси трогает только
запросы засеянной сети — путь содержит сегмент `/<networkId>/` или
заканчивается им (`/networks/<id>`); остальные запросы проходят сразу.
WebSocket-апгрейды задержкой не замедляются.

### Два вида задержки — не путать

| Флаги | Что задерживается | Что видит сервер |
| --- | --- | --- |
| `--delay-seed-ms <ms>` + `--delay-seed-path <substr>`, `--delay-seed-rule <ms>:<path>` | ОТПРАВКА запроса: пауза перед форвардом | читает данные ПОСЛЕ паузы — ответ всегда свежий |
| `--delay-seed-response-rule <ms>:<path>` | ОТВЕТ: запрос уходит сразу, ответ придерживается перед отдачей клиенту | читает данные в момент запроса — клиент получает снимок ДО правки |

Различие принципиальное: задержка отправки не воспроизводит «ответ вычислен
до правки, а доставлен после» — им проверяется только гонка «поздний ответ
openNetwork» (`--delay-seed-rule`, ошибки `58c55bb9`, `6d78ccab`). Дедуп
in-flight GET проверяется ТОЛЬКО задержкой ответа (грабли `a5bca281`).

- `--delay-seed-ms` — одна задержка на все запросы сети; `--delay-seed-path`
  сужает её до подстроки пути (требует `--delay-seed-ms`). Без ведущего
  слеша — Git Bash подменит абсолютный путь своим (грабля `de3b6a85`).
- `--delay-seed-rule <ms>:<path>` и `--delay-seed-response-rule <ms>:<path>` —
  **повторяемые** правила. Синтаксис единый: миллисекунды, первое двоеточие —
  разделитель, остальное — путь (подстрока), путь непустой. Первое совпадение
  выигрывает; порядок применения: правило `--delay-seed-ms` (если задано), затем
  `--delay-seed-rule` в порядке передачи. В путь подставляются id засеянных
  сущностей (`{{networkId}}`, `{{thoughtId}}`, `{{homeId}}`).
- Режимы независимы: можно одновременно задерживать отправку одного пути и
  ответ другого.
- `--delay-seed-response-limit <n>` — придержать ответы только у первых `n`
  совпавших запросов (`0`, по умолчанию, — все). Счёт идёт **после** фильтров
  пути и метода: несовпавший запрос слот не занимает; счётчик общий на все
  правила ответа. `1` — придержан ровно первый ответ. Этим получают обратный
  порядок доставки: устаревшее чтение придержано, свежее после мутации идёт
  сразу. Требует `--delay-seed-response-rule`.
- `--delay-seed-response-method <M>` — фильтр по HTTP-методу (регистр
  нормализуется, применяется ко всем правилам ответа). **При `limit 1` не
  обязателен**: слот занимает первый совпавший GET, и ответ DELETE «Очистить»
  не придерживается. Проверено на гейте `clear-row`: без флага на дофиксовой
  сборке `3a4ccdc4` — 2/2 красных, DELETE не задержан («Method-флаг —
  страховка, не обязателен»). Флаг нужен при иных лимитах или порядке
  запросов — чтобы придержать чтения, но не собственную мутацию сценария.

### Инъекция отказа

- `--fail-seed-path <substr>` — «форвард + подмена статуса»: запрос засеянной
  сети всё равно уходит на сервер (эффект в БД сохраняется, `serverLog` его
  видит), а клиент получает отказ с кодом `PROBE_INJECTED`. Режим глобальный на
  прогон (все совпавшие запросы), требует засеянную сеть.
- `--fail-seed-status <n>` — статус подмены, 400..599 (по умолчанию 404).
  Без `--fail-seed-path` проходит только 404 (совпадает с дефолтом — exit 0);
  любой другой статус без пути — ошибка разбора (exit 2). 500 —
  «сетевой/серверный» отказ, который не считается stale-хитом (ошибка
  `53d21e82`).

### Подавление realtime-эха (`--mute-ws-event`)

`--mute-ws-event <подстрока>` не доставляет клиенту серверные WebSocket-сообщения,
текст которых содержит подстроку. Это подавляет realtime-эхо СОБСТВЕННОЙ
мутации сценария: без него эхо двигает поколение чтения и маскирует гонку
(ошибка `da7bbb53`, круг 4).

- Прокси разбирает серверные **текстовые немаскированные** кадры RFC 6455.
  Сжатие (`permessage-deflate`) в ETN выключено; при его включении фильтр
  придётся расширять — сжатый текст по подстроке не ищется.
- Фрагментированное сообщение собирается и решается **целиком** — подстрока,
  разрезанная между кадрами, тоже подавляется (иначе фильтр молча стал бы
  вакуумным). Рукопожатие `101`, control-кадры (`ping`/`pong`/`close`),
  бинарные кадры, кадры клиент→сервер и HTTP-трафик проходят байт-в-байт.
- Требует прокси; при одном этом флаге прокси тоже поднимается. Совместим с
  `--no-seed` (тогда delay/fail-правил нет).

### Примеры

```bash
# задержка ОТВЕТА на чтении свойств: снимок до правки, доставка после
# (задача ddcb8e84; сценарии ui-probe.ddcb8e84-p1p2p1*.scenario.json)
node client/scripts/ui-probe-stand.mjs \
  --scenario client/scripts/ui-probe.ddcb8e84-p1p2p1.scenario.json \
  --scenario-seed client/scripts/ui-probe.ddcb8e84-p1p2p1-seed.mjs \
```

### Вакуумные гейты: проверяй красную фазу

Стенд считает срабатывания каждого правила задержки (отправки и ответа) и
подмены статуса и валит прогон кодом 1, если правило не совпало ни разу
(«гейт вакуумный»), а на успехе печатает счётчики. Числа идут по каждому
правилу через `/`: при одном правиле — `задержка ответа сработала по всем
правилам (1)`, при двух — `(1/1)`; у подмены — `подмена HTTP 404 сработала
(запросов: N)`.

У `--mute-ws-event` счётчика и вакуумной проверки НЕТ: фильтр только
подавляет кадры, стенд сверяет счётчики лишь задержек и подмены. Опечатка в
подстроке mute не ловится — подавление просто не срабатывает, и гейт молча
вырождается. Поэтому для гейтов с mute обязательна красная фаза на дофиксовой
сборке (см. ниже). Счётчик ловит только опечатку в пути — НЕ логику сценария.

**RestClient склеивает одновременные чтения одного URL в один GET**
(`client/src/main/net/rest-client.ts`, дедуп in-flight GET): два «разных»
чтения панели свойств с одинаковым URL уходят на сервер одним запросом.
Поэтому легко получить вакуумный гейт — придержан один ответ, а гонки нет
либо придержано не то чтение.

Проверенный пример — `ui-probe.da7bbb53-clear-row.scenario.json`: типовое и
внетиповое чтения свойств идут одним URL и склеиваются в один GET. Гейт
держится на ДВУХ флагах: `--mute-ws-event property-value.deleted` (эхо своей
мутации не маскирует гонку) и `--delay-seed-response-limit 1` (придержано
ровно одно ДО-мутационное чтение; при `limit 2` в слот попадало свежее чтение
после мутации, и гейт вырождался). Убери любой из них — на дофиксовой сборке
прогон зелёный (проверено: 27/27). `--delay-seed-response-method GET` при
`limit 1` не нужен (см. выше).

Поэтому каждый новый гейт с задержкой/подавлением обязан быть проверен
**красной фазой**: прогон на дофиксовой сборке должен падать именно по
проверяемому дефекту. Зелёный прогон на исправленной сборке сам по себе
ничего не доказывает — он одинаков у настоящего гейта и у вакуумного.

## Отчёт

`<out>/report.txt` — человекочитаемый «шаг → проба → факт/ожидание»;
`<out>/report.json` — машинный. PNG — только при шаге `shot` или `assert` с
`evidence: true`.

В текстовом отчёте первыми идут строки прогрева (`прогрев: клиент готов за
N мс` / `прогрев: отключён (--no-warmup)`), а у шагов с проверкой точки —
`[точка x,y, перемер N]` и `— ПРОМАХ…` (см. «Проверка точки ввода»). В JSON те
же данные лежат в `entry.click` / `entry.hover` / `entry.drag.fromCheck`.

Шаги `probe`/`api` без `expect`/`expectFrom` дают только факт; с `expect` —
сверку с литералом, с `expectFrom` — сверку со снимком ранее выполненного шага
и пометку `— снимок шага «<имя>»` у ожидания (см. «Самопроверка „до ↔ после“
(`expectFrom`)»).

## Рецепт изолированного стенда (перенесён из карточки компонента `9eddf9c0`)

Раньше стенд поднимали вручную; `ui-probe-stand.mjs` делает это одной
командой. Рецепт ниже — для понимания, что происходит «под капотом», и для
ручной отладки.

1. **Данные.** Изолированный каталог, чтобы не трогать полигон:

   ```bash
   rm -rf .tmp/<st>/data && mkdir -p .tmp/<st>
   ETN_DATA_DIR=C:/R/ETN/.tmp/<st>/data ETN_PORT=4405 node server/dist/cli.js init --username admin > .tmp/<st>/init.log
   grep -o "etn_[a-f0-9]*" .tmp/<st>/init.log | head -1 > .tmp/<st>/key.txt
   ```

2. **Сервер в фоне:**

   ```bash
   ETN_DATA_DIR=C:/R/ETN/.tmp/<st>/data ETN_PORT=4405 ETN_HOST=127.0.0.1 node server/dist/index.js > .tmp/<st>/server.log 2>&1 &
   curl -s http://127.0.0.1:4405/api/v1/health    # готовность
   ```

3. **Сид через REST** (`Authorization: Bearer <key>`): сеть (`POST /networks`),
   HOME (`POST /networks/<id>/thoughts/query`, искать `title === 'HOME'`),
   мысль с комментарием (`POST /networks/<id>/thoughts` с `comment` и
   `create_link.direction = 'parent'`).

4. **Скрытый клиент** (нужна сборка `npm -w @etn/client run build`):

   ```bash
   node client/scripts/ui-probe-launch.mjs --port 9340 --profile C:/R/ETN/.tmp/<st>/profile
   ```

5. **Онбординг сценарием**: `input[placeholder^='http']` = адрес сервера,
   `input[type=password]` = ключ, клик по кнопке «Подключиться»
   (`.onboarding-card .ui-btn--primary`); затем открыть сеть кликом по
   `.network-item`.

6. **Пробуждение скрытой страницы** — раннер делает это сам (по умолчанию) через
   CDP: `Page.bringToFront`, `Emulation.setFocusEmulationEnabled`,
   `Page.setWebLifecycleState('active')` (грабли `03e33360`).

7. **Подсчёт/контроль эффекта — по серверу** (access-log или REST), не по UI
   (грабли `aa5cf162`).

8. **Закрытие.** `ui-probe-stand.mjs` гасит дерево процессов (`taskkill /T`);
   вручную — по PID процесса CDP: `taskkill //PID <pid> //T //F`.

## Грабли (обязательно к учёту)

- **`03e33360`** — в скрытом окне заморожены rAF/layout, документ `hidden`.
  Раннер «будит» страницу через CDP; ждать — по условию/строке, НЕ по кадрам.
- **`aa5cf162`** — CDP страницы не видит HTTP main-процесса Electron: эффект

- **`91720eda`** — без изолированного профиля клиент делит лок и БД с клиентом
  пользователя и поднимает ЕГО окно. Запускать клиент ТОЛЬКО через

- **`4c035087`** — CDP-ввод не меняет состояние CodeMirror: шаг `text`

- **Видимое окно запрещено** на рабочей машине пользователя: окно проверки не
  должно перехватывать фокус. `ETN_HIDDEN_WINDOW=1` ставит обёртка.
